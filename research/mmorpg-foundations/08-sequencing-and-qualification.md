# Sequencing, qualification and decisions

## Prioritize irreversible assumptions, not maximal infrastructure

An early requirement is valuable when delaying it would spread an incorrect assumption through many callers, saved fields or world definitions. A mechanism is worth deferring when it can be changed behind a stable contract and has no demonstrated consumer yet. This distinction is the practical answer to avoiding another broad rewrite without prematurely scaling a zero-user game.

The existing NSC sequence remains intact: complete the smaller native pipeline, compare one/multiple workers, decide adoption, convert the supported game, qualify cells, then conditionally distribute and adapt. This research does not require all MMORPG preparation to finish before a native experiment or a worthwhile small-world improvement.

## Sequence by consumption point

### Now: before native types and high-volume interfaces spread

Complete the precision/space audit and independent-world identity/lifecycle mapping. Reconcile supported capability work/influence with the existing native conversion inventory. Keep partial-data and scoped-capture semantics representable even where today's implementation is fully resident. Add the necessary measurements to existing PF/NSC scenarios rather than build a parallel benchmark driver.

The smallest outcome is not “distributed MMO ready.” It is a correct native proof whose APIs do not accidentally encode one machine, one global coordinate precision, one fully resident world or one provider session. Missing future physical streaming can remain explicitly unsupported. It must not masquerade as a complete negative or be silently implemented by whole-world materialization.

### Soon: before vast geography, persistent service or offered population growth

Design the supported physical residency/coverage lifecycle; qualify topology-local preparation and large-coordinate provider boundaries. Resolve the chosen unattended service profile through PS. Reconcile aggregate host resource and publication lifetimes, mature-state recovery and many-world startup with existing BK/NET/PD/PF owners.

Use actual player/NPC journeys: leave a chosen activity underway, return to the same changed place, enter a partially prepared area, observe a consequential event with distinct knowledge, or restore one of two seed worlds. Completion should make those journeys reliable, not merely produce a more elaborate architecture chart.

### Later: only after a measured bottleneck or hosted promise

Consider physical database partitioning/sharding, multiple compute machines, region-independent advancement, adaptive placement, live precopy, fleet orchestration, specialized historical search and high availability. Each must include its complete added cost and failure behavior. Native distribution remains same-operator/same-build initially; intercontinental low-latency simulation and cross-operator federation are not hidden requirements of this research.

## Small qualification scenarios with high architectural value

These are scenario requirements for existing owners, not newly authored automated tests or claims that checks ran. Select the smallest disposable actual-consumer journey that resolves the question. Speed measurements follow repository policy and run on the authorized AWS worker; source reasoning and static documentation checks are not timing evidence.

| Scenario | Question it resolves | Required evidence / failure to catch | Existing owner |
| --- | --- | --- | --- |
| Two worlds from the same seed | Are world, local entity and job namespaces really separate? | Equal local IDs; different inventory/history; delayed result from A cannot affect B; restore A leaves B unchanged | Creation/SL/NSC, MSF03 preparation |
| Same small scene at a large global offset | Does every provider preserve enough precision? | Equivalent contact/support/reach/path/received outcomes within declared tolerances; no narrowing at bridge/save/wire; rebase creates no fictional movement | SW/NSC, MSF01 |
| Small active area with much larger cold extent | Does routine work depend on the entire map? | Resident bytes and examined work; explicit incomplete coverage; entrant cannot pass through an unloaded blocker or lose an incoming effect | SW/data/PF, MSF02 |
| Dense versus dispersed equal population | Are costs driven by coupling and audience? | Actual interactions, recipients, total CPU and command/capture tails; no silent hearing/cognition/physics reduction | PF/PS/NSC |
| Idle-but-advancing versus deliberately suspended world | Is absence policy truthful? | Time progress, resource use, actual obligations, funding, reactivation and no invented catch-up | PS/continuing-life, MSF05 |
| Old history with the same active actors | Does world age affect current play or restoration? | Indexed examined work, physical bytes, cleanup lag, cold-read coverage, restore peak memory and time | BK/SL/PD/PF |
| One busy and one quiet world on shared resources | Do aggregate bounds and fairness hold? | Quiet-world command progress; bounded native/SQL/provider/capture work; no per-world multiplication of host limits | Scheduling/NET/PF, MSF06 |
| Slow SQL, provider or client | Are lifetimes bounded while truth is preserved? | Exact reservations, queue age, retained bytes, admission outcome, no duplicate paid request or dropped accepted effect | BK/NET/NSC/PD |
| Reconnect/startup wave | Is recovery capacity distinct from steady state? | Bounded starts, initial exposure/capture load, legitimate resync, no duplicate initialization or authority | PD/PF/SL |
| Deterministic worker-count variation | Does scheduling change mechanics? | Same supported intermediate outcomes, random progression, receipts and source chronology, not only final positions | NSC03 |
| Border crossing with a large body and a distant dependency | Does the scope include actual influence? | One authority/effect, coherent timing, complete overlap, no observer knowledge leak | NSC05 and later NSC06 |

A result must state source/build, installed definitions, actual family scope, populations by role, geography/density, offered/achieved time, retained age, model mode, hardware and instrumentation. Count accepted useful work and refused/stale work separately. A run with models disabled cannot qualify live autonomous quality or inference economics. A native fixture can qualify an interface without claiming an enjoyable NPC.

## Measurements that answer the foundational questions

Reuse existing hierarchical profiling and native diagnostic integration. Separate clean throughput/latency comparisons from instrumented diagnosis. Relevant measurements include native/host CPU, serial application time, worker queue/service/waits, memory/capture/undo peaks, bridge bytes, input candidates versus selected outputs, fan-out, saved bytes/rows, SQL examined work, maintenance debt, actual world-time progress and command-to-visible-effect latency.

For a new boundary, identify its originator, ownership key, input size, output size, retained lifetime, retry/cancel rule and failure state. The point is not to collect every possible metric forever. It is to expose where work moved, multiplied or became pending. Optional telemetry itself needs bounded retention and must not become a reason to retain private prompts or entire worlds.

No universal p95, NPC count, tolerated density, map extent, recovery window or headroom percentage is selected here. The existing owner sets criteria before a measurement. An offered target does not pass when participants are merely queued outside it or required outcomes are omitted.

## Evidence that should change priority

| Observation | Response to consider | What it does not justify |
| --- | --- | --- |
| Correct native interfaces already cover a proposed gap on the implementation branch | Record the verified implementation and close that preparation item in its owner | Rebuilding the same abstraction to match this research's wording |
| Precision conversion fails at a modest required extent | Fix the space/provider contract before more spatial code depends on it | Switching every numeric field or replacing the renderer without attribution |
| Local command cost grows with inactive map size | Reconcile selection/residency/preparation boundary | Immediate multi-machine distribution |
| World age increases ordinary current-query cost | Repair query shape, retained-data preparation or maintenance ownership | Deleting meaningful history without a selected policy |
| One world saturates a host despite equivalent efficient execution | Qualify later NSC distribution and its coordination cost | Assuming a second machine doubles capacity |
| Many worlds saturate a shared service | Bound/isolate the actual shared resource and qualify whole-world placement | Repartitioning every world's physical simulation |
| Dense coupling dominates | Revisit the explicit encounter/service envelope with product owners | Invisible instancing, dropped effects or unannounced time dilation |
| Provider/context demand dominates total cost | Evaluate aggregate cognition service through existing AI/PS owners | A new per-frame model loop or silent personality reduction |

## Decisions reserved for the product owner

The research can proceed without choosing exact answers. Before the relevant offer, the existing decision owners need: maximum intended extent and spatial tolerance; whether and how unattended worlds advance; the economic/service horizon for that advancement; dense-encounter congestion behavior; ordinary/protected durability and recovery promises; supported live-world upgrades; and any real cross-world travel or shared-campaign semantics.

The November 9 working 1,000-player-per-world ambition must be reconciled with older release/growth profiles when those profiles are selected for qualification. Do not automatically raise every queue/capacity setting to 1,000 or lower an earlier growth ambition. A configuration limit is not supported capacity.

## Explicit exclusions

No runtime implementation, gameplay retuning, new cognition/sight algorithm, production infrastructure design, cloud purchase, paid inference, benchmark execution, new maintained test suite, database sharding, broker adoption, automatic migration or compatibility layer is authorized by this research. Implementation and actual qualification remain future tasks in existing owners. The research itself is complete only when its evidence, current coverage, actionable gaps and navigation are committed and reviewed; runtime stages remain visibly open.
