# Networking, persistence, and replay

Research date: **23 October 2026**. Engine baseline: **Unreal Engine 5.8.4** and **Unity 6000.6.7f1**; see the [version and evidence baseline](01-evidence-and-version-baseline.md). Unity networking packages have their own versions. The inspected Netcode for Entities and Transport manuals identify **6.6.0**; the GameObjects manual identifies **2.13.3**, whose changelog dates that patch to **14 September 2026**. The Unity 6000.6.0f1 launch package matrix listed NGO 2.13.2, so that matrix is not the current package patch ledger. [NGO changelog](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/changelog/CHANGELOG.html)

This chapter studies how engines move state between simulations, retain it between sessions, and reconstruct an earlier presentation. It does not propose an OpenLegend networking or storage design. The relevant distinction for the existing OpenLegend context is that an authoritative world, a person's permitted observations, an actor's remembered beliefs, a browser's presentation, and a durable record are different data products. An engine's replicated object is not automatically all five.

## 1. What the different mechanisms guarantee

The following is an analytical classification of the documented mechanisms developed below, not a vendor feature ranking.

| Mechanism | Producer and consumer | Meaning of success | Separate question it does not answer |
| --- | --- | --- | --- |
| State replication | Authoritative simulation to remote simulation or presentation | A receiver obtains selected state according to delivery and relevancy rules | Whether every intermediate event, private fact, or durable transaction is represented |
| Input prediction and correction | Client's speculative simulation, checked against server snapshots | A responsive local state can be corrected and replayed | Whether a speculative action was authorized or durably accepted |
| RPC or event message | Sender to selected network recipients | Delivery and execution under that channel's rules | Whether a late joiner can reconstruct the event or its consequences |
| Save serialization | Selected runtime state to a storage representation | Data can be encoded and later decoded | Whether the snapshot is causally consistent, compatible with future content, or committed atomically with external records |
| Replication replay | Recorded state changes to a replay world | A previous replicated presentation can be reconstructed | Whether the entire original simulation can be recomputed from inputs |
| Browser-local persistence | Client data to the browser's local storage context | Data is available under that storage lifecycle | Whether it is the server's canonical world state |

## 2. Unreal: Iris, filtering, and scheduling work

### Current maturity and the copied-state pipeline

Epic's June 2026 announcement explicitly identifies **Iris as production-ready in UE 5.8**. Some current documentation pages still show Experimental warnings or older experimental source paths. The dated release statement establishes maturity; the older banner is retained here as a documentation inconsistency, not treated as the current product status. [State of Unreal 2026](https://www.unrealengine.com/news/state-of-unreal-2026-top-news-from-the-show)

Iris holds a quantized replication representation separate from gameplay objects. A replication bridge starts and stops participation, links gameplay objects to network handles, and supplies type-level protocols plus instance-specific access. During pre-send processing, Iris polls where required, copies dirty gameplay state, resets dirty markers, and calculates connection eligibility and priority. Sending then works from the stored representation. This separates repeated network work from repeated traversal of gameplay objects and enables work to be shared across connections. At the receiver, packet data is read before state dispatch; newly encountered objects may be instantiated immediately because their protocols are needed to interpret the payload. The copy is a deliberate extra representation with its own lifecycle, not an elimination of serialization or memory cost. [Components of Iris](https://dev.epicgames.com/documentation/unreal-engine/components-of-iris-in-unreal-engine)

Migration preserves much of the familiar replicated-property and RPC surface, but several contracts change. Iris favors explicit dirty notification; without push support it can still poll at the configured update frequency. Registered subobject lists are required, and other replicated UObject types need replication-fragment registration. Custom network serializers are another compatibility boundary: the migration documentation calls for an Iris implementation or a checked reflection-based alternative. Its more explicit APIs also replace some legacy virtual-function decision paths. Existing replication annotations therefore do not establish complete behavioral compatibility by themselves. [Migrate to Iris](https://dev.epicgames.com/documentation/en-us/unreal-engine/migrate-to-iris-in-unreal-engine)

### Eligibility and priority are different operations

Iris filters include owner-only, explicit connection, group, and dynamic filters. Group filters can update the eligibility of many related objects together, reducing repeated per-object decisions when the same access relationship changes. Dynamic spatial filters evaluate objects against connection-specific views. These are mechanisms for deciding which connections receive which objects; distance is one available rule, not a definition of semantic knowledge. [Iris filtering](https://dev.epicgames.com/documentation/unreal-engine/iris-filtering-in-unreal-engine)

The current `SetFilter` API documents two concrete lifecycle details. An object filtered away from a remote connection is destroyed on that receiver. If setting a filter fails, the resulting filter is unspecified: it might remain the old filter or become no filter. Consequently, the API's failure return cannot be interpreted as a successful restriction of visibility. [SetFilter API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/IrisCore/UReplicationSystem/SetFilter)

Prioritization decides which eligible changes fit the current sending opportunity. Iris accumulates priority until an object is sent and then resets it. Values below one are not considered for that frame; dirty objects at or above one become candidates. Static values and dynamic prioritizers support different policies, while batched interfaces allow cache-friendly processing. Accumulation favors waiting objects but does not, by itself, specify a maximum delivery delay under arbitrary load. [Iris prioritization](https://dev.epicgames.com/documentation/en-us/unreal-engine/iris-prioritization-in-unreal-engine)

**Interpretation for OpenLegend's subject matter:** spatial eligibility, scheduling priority, and a character's sensory access answer different questions. A visible body might contain undisclosed intentions or memories. Removing a remote representation cannot retract facts that were already delivered. This conclusion follows from the direction of information flow; the cited engine mechanisms do not claim to enforce an authored world's epistemic rules.

### Replication Graph and dormancy address different repeated costs

Replication Graph uses persistent nodes to retain and reuse replication lists across frames and connections. Nodes can organize actors spatially or by shared behavior, avoiding a fresh full actor-versus-connection evaluation for every send. Its central contribution is reusable query structure. The documentation's historical production example is not a transferable actor-capacity measurement, and this report does not treat Replication Graph and Iris as interchangeable stages of one mandatory pipeline. [Replication Graph](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)

Dormancy suppresses repeated collection and property checks for actors that seldom change. The documented contract requires waking or flushing dormancy **before** mutating replicated state, including relevant subobjects; otherwise an update can be missed. Repeatedly entering and leaving dormancy can erase its savings. Dormant actors ordinarily remain represented on server and client and are not subject to the same ordinary relevancy processing as active actors; Replication Graph has separate optional dormant-actor destruction behavior. Dormancy is thus a network-update state, not a statement that the actor stopped existing or thinking. [Actor network dormancy](https://dev.epicgames.com/documentation/unreal-engine/actor-network-dormancy-in-unreal-engine)

Epic's ordering documentation also limits the meaning of a received sequence. It does not promise a deterministic order among separate replicated-property notifications. Reliable RPC ordering is scoped to the same actor and its subobjects, rather than to all actors globally; mixtures of reliable and unreliable RPCs have additional ordering limits. An application-level causal history cannot be inferred merely by concatenating callbacks from unrelated objects. [Replicated object execution order](https://dev.epicgames.com/documentation/unreal-engine/replicated-object-execution-order-in-unreal-engine)

## 3. Unity: two networking models with different prediction contracts

### Netcode for GameObjects: state, events, and anticipation

NGO distinguishes persistent-in-session state from one-time messages. A NetworkVariable supplies current state to a late joiner; past RPC invocations are not replayed automatically. Intermediate variable assignments can be coalesced before synchronization, whereas separate RPC invocations represent separate messages subject to their delivery semantics. Here, persistent describes ongoing network state, not a disk transaction or a permanent event archive. [RPCs versus NetworkVariables](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/learn/rpcvnetvar.html)

NGO's current client-anticipation documentation explicitly says it does **not** supply a complete prediction-and-reconciliation loop. Anticipated variables and transforms separate a locally displayed value from authoritative state. Anticipation counters help classify a response as stale relative to a newer local action; handling can ignore stale corrections or trigger reanticipation. The authoritative value still updates. Hooks such as `OnReanticipate` permit application-specific resimulation, but the user supplies that behavior. Smoothing a visual correction does not turn anticipation into the tick-indexed input-history replay provided by Netcode for Entities. [Client anticipation](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/client-anticipation.html)

The 2.13.3 changelog provides a useful example of why patch provenance matters: it records corrections to transform interpolation time references and frame-rate independence, as well as half-float position handling. A description of the networking model can remain valid while its timing and numerical edge behavior changes in a package patch. This is evidence of specific fixes, not a claim that all interpolation behavior is now error-free. [NGO changelog](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/changelog/CHANGELOG.html)

### Distributed authority changes trust and ownership

NGO distributed authority distributes ownership and simulation responsibilities among clients. A session owner handles session-wide tasks such as scene and late-join coordination, with replacement when that client departs. Distributable objects can be reassigned as participants join or leave. Unity explicitly describes the greater reliance on trusted clients and the absence of a single authoritative physics simulation, and cautions about use cases demanding tightly authoritative competitive prediction. This is a distinct authority topology, not simply a cheaper deployment of the same dedicated-server contract. [Distributed authority](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/distributed-authority.html)

Connection approval is a separate admission mechanism. In the inspected NGO version it is not supported by distributed authority. Server approval can remain pending while external validation runs, but is bounded by a connection timeout. The approval payload itself is not encrypted or authenticated by this API; the documentation explicitly separates it from protection of credentials or tickets. Passing admission therefore does not establish authorization for every subsequent world action, nor does it establish transport confidentiality. [Connection approval](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/connection-approval.html)

### Netcode for Entities: snapshots and replayed ticks

Netcode for Entities calls replicated entities ghosts. The server controls their authoritative creation, updates, and destruction; clients maintain selected representations. Ghosts can be interpolated, predicted, or owner-predicted. A snapshot need not contain every ghost. Its content depends on changes, importance, rate limits, and available packet space. A configured maximum send rate is a ceiling rather than a delivery deadline. [Ghosts and snapshots](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/ghost-snapshots.html)

Prediction runs the relevant simulation against tick-indexed state and may execute multiple simulation steps during one rendered frame. `PredictedGhost` and the `Simulate` tag govern which entities participate in a step. The current server tick, interpolation tick, and partial-tick state describe different temporal positions. The documentation exposes a first-time prediction check for effects such as one-time spawning or presentation events; without a distinction between first execution and replay, repeated simulation can repeat side effects. Correctness depends on the simulation consuming the intended tick's inputs and participating entities, not merely using a fixed time interval. [Prediction implementation](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/prediction-n4e.html)

Partial snapshots make rollback more complicated than resetting the whole client to one uniform past. Only ghosts updated by a snapshot are rolled back; other ghosts may remain at a newer state while some are resimulated. Interactions between these groups can consequently use states from different times. The documentation illustrates velocity-changing interactions where the other object is not advanced alongside the rolled-back object. It also describes a finite input history, so arbitrarily old corrections cannot be replayed without limit. These are documented operating boundaries of the current system. [Prediction edge cases](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/prediction-details.html)

Replay cost depends on both the simulation and the number of steps repeated after correction. The current optimization documentation describes several explicit exchanges: reducing snapshot frequency can reduce rollback frequency but increase correction magnitude; added input latency reduces the prediction span while delaying input response; reusing history across structural changes can reduce work while accepting additional correctness hazards. It also observes that scheduling many small jobs during replay can cost more than executing that particular workload synchronously. None of these observations establishes a universally superior setting. [Reduce prediction overhead](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/optimization/reduce-prediction-overhead.html)

Prediction switching permits an eligible client ghost to move between predicted and interpolated modes. That changes its temporal position from a predicted future to an interpolated past, or vice versa; smoothing hides some of the transition but does not make the timelines identical. Owner-predicted ghosts already have ownership-driven mode behavior and are excluded from this manual switching path. Fast changes in direction can expose transition artifacts. [Prediction switching](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/prediction-switching.html)

The command stream carries tick-associated input and acknowledgement information. It continues keepalive and acknowledgement traffic even when the client has no controlled entity. Input-event facilities preserve one-shot actions through dropped input ticks. Ownership of an input stream is therefore distinct from authority over the resulting simulation state: the stream supplies the server with an action proposal tied to time. [Command stream](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/command-stream.html)

## 4. Network costs: work can fall while bytes stay constant, or the reverse

Ghost sending uses chunk importance and time since last send, with per-connection adjustments. Relevancy supports explicit connection–ghost membership and global fallback rules. Making an existing ghost irrelevant despawns its client representation without necessarily destroying the server entity. Preserialization changes another axis: ordinary serialization occurs on demand for each connection, whereas preserialization produces shared data once per tick. That amortizes work across many consumers but also serializes on ticks when no client receives the ghost. Its benefit therefore depends on actual fan-out and send frequency. [Optimize ghosts](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/optimization/optimize-ghosts.html)

The serializer may do substantial work even when very little reaches the network. Write access can trigger serialization and comparison before the system concludes there is no change to send. Netcode for Entities normally uses several acknowledged baselines to predict values before delta encoding. A single-baseline option exchanges some of that prediction work for different bandwidth behavior; static optimization also uses a single baseline. Small packet sizes alone therefore do not measure the CPU work spent discovering that state was unchanged. [Manage serialization costs](https://docs.unity3d.com/Packages/com.unity.netcode@6.6/manual/optimization/manage-serialization-costs.html)

The browser adds a transport boundary. Unity Transport uses UDP in its ordinary native path, but the Web platform uses WebSockets because it lacks direct UDP access. The server must offer the matching transport; mixed native/Web support can use multiple drivers. Unity Transport's WebSocket mode still uses Unity Transport's protocol, so it is not a generic connection to an arbitrary WebSocket application server. Secure WebSocket deployment is another layer. These constraints concern transport interoperability, not who is entitled to mutate world state. [Transport WebSocket support](https://docs.unity3d.com/Packages/com.unity.transport@6.6/manual/websockets.html)

**Independent interpretation:** a hidden autonomous actor, a distant visible actor, and an inactive physical representation can generate three different workloads. The hidden actor may still consume authoritative simulation and persistence work while producing no client replication. The distant visible actor may produce a low-rate presentation without exposing private memory. The inactive representation may still have outstanding durable changes. Measuring bytes, entity count, or rendered actor count independently cannot establish the total cost of that persistent world.

## 5. Saving state: extraction, coherence, identity, and storage

### Unreal SaveGame and the actual asynchronous boundary

The SaveGame workflow defines a data object containing selected information, transfers runtime values into it, writes it, and later transfers decoded values back to runtime objects. The engine does not infer that every actor, transient task, or external record belongs in that object. The official guide supports multiple save classes and slots for different categories of data. [Saving and loading](https://dev.epicgames.com/documentation/unreal-engine/saving-and-loading-your-game-in-unreal-engine)

The current `AsyncSaveGameToSlot` API specifies the thread boundary precisely: **serialization runs on the game thread; the platform-specific write runs on a worker; completion returns to the game thread**. Its delegate is copied across the worker boundary and must be safe to copy by value. Asynchronous storage therefore removes a particular blocking write from the game thread while retaining serialization CPU there. The completion callback reports this save operation's outcome; it does not claim an atomic transaction with unrelated databases or network messages. [AsyncSaveGameToSlot API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UGameplayStatics/AsyncSaveGameToSlot)

Epic's 2026 Persistence Lab sample is a useful current implementation companion. It targets UE 5.8.0 and combines SaveGame with per-world and session-lifetime subsystems. It distinguishes actors already authored in a map from dynamically spawned actors and entities that must be recreated. Its README explicitly says the overall sample has not been battle-tested in a shipped title. Experimental plugin status and the maturity of the assembled example must therefore remain separate from the maturity of the core engine. [Persistence Lab sample](https://github.com/ZKShao-EpicGames/Sample-PersistenceLab)

The associated Unreal Fest text companion exposes important lifecycle details. Mass fragment extraction occurs outside active processor execution. Instanced Actors restore data through their `UInstancedActorsData` owner rather than assuming a corresponding Mass entity already exists: creation can be deferred and time-sliced, and the owning data also participates in replication. Dehydrating an actor requires transferring persistent values before its actor-side storage disappears. The sample groups saved entities by originating configuration and distinguishes restoring instances from running a spawner again. These are concrete examples of identity and ownership crossing representation boundaries. Only indexed text excerpts of this talk companion were available; the video and complete page body were not inspected. [Persisting world state with Actors, Instanced Actors, and Mass](https://dev.epicgames.com/community/learning/tutorials/1mj4/unreal-engine-persisting-world-state-with-actors-instanced-actors-and-mass)

### Unity serialization has changed; old blanket restrictions are unsafe

Unity's JSON facilities serialize structured fields. Unknown input keys are ignored; absent keys do not mean the same thing in every operation. Object construction supplies defaults for normal deserialization, while `FromJsonOverwrite` retains existing values for fields absent from the input. Overwrite also supports Unity object types for which ordinary `FromJson` is not the applicable path. The documented background-thread allowance does not permit concurrent unsynchronized mutation of the same object. These details affect whether a partial document is interpreted as a replacement, a patch, or a malformed record. [JSON serialization](https://docs.unity3d.com/6000.6/Documentation/Manual/json-serialization.html)

**Unity 6.6 now documents built-in dictionary serialization.** A dictionary field must use the specified opt-in field attribute even when public; supported key/value types and collection nesting still have restrictions. Insertion order is serialized, which is distinct from how an Inspector may display entries. Advice that Unity serialization categorically cannot serialize dictionaries is outdated for this baseline. The capability also does not imply arbitrary collection or object-graph support. [Dictionary serialization in Unity 6.6](https://docs.unity3d.com/6000.6/Documentation/Manual/script-serialization-dictionaries.html)

Entities exposes binary world serialization through `SerializeUtility.SerializeWorld`, including overloads that return referenced Unity objects or accept entity-remapping information. Its matching deserializer takes an `ExclusiveEntityTransaction` and a Unity-object array for reference patching. The API describes atomicity of the deserialization transaction inside the ECS world. It does not document that operation as a cross-process database transaction or a universal format migration service. A world snapshot, its external object references, and the meaning of entity identity remain distinguishable parts of the operation. [SerializeWorld](https://docs.unity3d.com/Packages/com.unity.entities@6.6/api/Unity.Entities.Serialization.SerializeUtility.SerializeWorld.html), [DeserializeWorld](https://docs.unity3d.com/Packages/com.unity.entities@6.6/api/Unity.Entities.Serialization.SerializeUtility.DeserializeWorld.html)

**Independent interpretation:** serialization is an encoding capability. Durable authored worlds also have semantic questions: whether an entity was deleted or merely unloaded, which content revision gives a stored identifier its meaning, whether a belief describes past observation or current truth, and whether a write corresponds to an accepted action. The inspected APIs do not resolve those questions merely because an object can round-trip through a serializer. No new OpenLegend storage architecture is inferred here.

## 6. Replay is a choice of recorded information

Unreal's replay system records replicated data through `DemoNetDriver` and a replay streamer. It can include properties designated for replay and supports playback, pausing, and seeking. This is state replication used as a recording source. It is not evidence that the original simulation can be reproduced from player inputs alone, nor that unreplicated private state was captured. [Replay system](https://dev.epicgames.com/documentation/unreal-engine/using-the-replay-system-in-unreal-engine)

Streamers provide storage arrangements such as local files, memory, save slots, and HTTP. Seeking uses checkpoints plus subsequent changes, exchanging checkpoint frequency and size against reconstruction work. The documentation identifies a subtle coherence issue: time-slicing a checkpoint can record different actors on different frames, causing visible inconsistencies. It also warns that replay actors can invoke gameplay functions affecting shared game-level objects, so a replay world is not automatically free of live side effects. Storage medium, checkpoint consistency, and replay execution isolation are separate concerns. [DemoNetDriver and streamers](https://dev.epicgames.com/documentation/unreal-engine/demonetdriver-and-streamers-in-unreal-engine)

The examined general replay pages do not, on their own, establish every supported combination of Iris, replay streamer, custom replicated serializer, platform, or game-specific persistence system. This report therefore does not advertise universal compatibility from the presence of both features in the same engine release.

**Independent interpretation for authored persistent worlds:** replay can mean at least three things: reconstructing what a client saw, reconstructing an authoritative state at a point in time, or rerunning a transition sequence and obtaining the same result. A recorded observation can be correct even when it omits hidden facts; a full server snapshot can be inappropriate as a record visible to a character. Engine networking and replay terminology must be read with the recorded information and intended consumer made explicit.

## 7. Cross-system findings and evidence limits

The strongest commonality is explicit state ownership across time and representation boundaries. Iris separates gameplay state from a sendable copy. Ghost prediction separates speculative state from server-confirmed state. Persistence samples separate authored instance identity from its current actor or entity. Replay separates recorded replicated state from live execution. These mechanisms explain where work moves and which component owns the next transition.

The important limits are equally concrete. Scheduling priority is not a latency guarantee. Network state is not an event archive. Anticipation is not a complete replay loop. Serialization off the critical storage path can still consume game-thread time. Despawning a client representation is not necessarily an entity's death. None of these engines' throughput mechanisms automatically defines the contents of a private memory or a permitted observation.

No engine binaries, live network sessions, persistent servers, or packet-loss experiments were run for this research. Capacity, correction quality, pause times, and recovery behavior remain workload-dependent and unmeasured here. [Profiling and verification](10-profiling-and-verification.md) examines what the current tools can observe and what those observations can establish.
