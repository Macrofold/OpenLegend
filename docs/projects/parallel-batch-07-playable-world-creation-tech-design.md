## OC01 — A deterministic supported initial-world candidate

### One definition of the opening

Add a typed initial-world candidate understood by a world-owned creation profile. The first profile is the already supported bundled family, with a declared set of supported scene elements and editable fields. It selects exact installed law/content definitions, a locality layout, fresh actor descriptions and roles, initial finite stock, explicit starting knowledge and an optional scenario intention. Source-world instance IDs, memories, inventories, runtime receipts and active work are not valid inputs.

Reuse the existing world initialization code by separating common definition installation, fresh state initialization and authored population. Keep the ordinary `createWorld` entry as a caller of those owners. The creation caller constructs only its selected opening; it does not remove the current world's people, clone a live save, mutate the source or depend on CE01's proposed removal behavior. Default setting, vocabulary, presets, resource choices and story opportunities remain under `packages/domain/src/worlds/base/` and `docs/worlds/base/`.

The profile offers the actual native scene/body/item types it can construct, with validation and readable metadata. It may arrange supported existing terrain/support elements and contents; it supplies no arbitrary mesh, physics, script, remote import or new executable family. Unsupported essential requirements remain attached to the candidate. A host-protected rule cannot be changed by selecting a different label or a prose instruction.

The application allocates a project ID, candidate revision, prospective world ID and actor/item identities once. Generated proposal-local references resolve only within that candidate through the owning typed mapping. Names are display fields. Save retained random results and RNG state; opening the same revision or retrying Start does not reroll identities, layout, traits or supplies. A deliberately requested variation is a new revision with recorded ancestry.

### Initial state, knowledge and personal history

Build the fresh world through current semantic owners, with no active actions, conversations, projectiles, imported command receipts or copied control leases. Exact definitions and valid native derived state remain necessary. Authored resources are explicit finite initial endowment; they are not outputs of invented historical work. `installRecipe` can install an authored method, while the initial-knowledge owner separately specifies which character knows it. Neither admission nor knowledge creates physical stock.

Use the current character authorship boundary: traits/disposition and personal backstory describe the person, current location/possessions remain actual state, and a seeded intention is visibly authored scenario setup. Do not encode a required helpful response or provisioning schedule in biography. An optional resident omitted at construction creates no death, deletion event or memory. Authored background and beliefs retain their source and remain distinct from simulated events.

The builder returns a complete candidate world plus its initial account-role bindings and applicable explicit setup grants as one validated preparation result. It does not connect a database, publish history, buy model work or grant a control lease. Validate the full current model, stable references, definition pins, body/geometry requirements, quantities and initial knowledge through the existing owners before readiness or activation.

The current identity record already permits a null starting-resident binding, while convenience callers of `defaultResidentEntityId` throw when none exists. Trace the new solitary opening through `identity.ts`, `world-service.ts`, `context.ts`, `ai-director.ts`, HTTP and client entry. Require an explicit eligible target for resident-only operations and show the ordinary absent-target state; do not fabricate a resident, default to the human or broadly replace strict identity checks with fallbacks. This is creation integration, not a dependency on another task's character deletion.

## OC02 — The existing World Agent retains meaning and preparation

Add a creation kind/profile to the existing authoring service and workspace, using their session, draft revision, source-attributed requirements, question, validation, review and operation identities. Authoring starts from an existing creator session with current `create` authority; an ordinary player or characterless visitor gains no new authoring grant. A prepared opening can use native selection/editing without paid generation. The model receives the creation profile's supported fields and required source constraints, not a whole source-world snapshot.

The new payload references the world's supported creation profile and its exact candidate revision. Store large prepared candidate material through existing durable authoring storage with an exact reference; do not inflate every tool call or prompt with the generated world. Native field changes and conversational revisions use the same candidate. Existing byte, question, history and funding controls apply. An over-limit candidate is retained with a precise blocked status; never silently discard required contents to fit a tool envelope.

Keep source creation-session authority and destination start authority separate. Draft preparation can finish before a destination is available. Choosing a target adds its operator-selected capability/funding/account profile to review but does not authorize new laws or spending. Loss of source permission fences subsequent authoring and publication. Questions, reconnection and rereading never create new paid allowances; uncertainty follows current reservation/receipt recovery.

Paid rehearsal is optional and separately admitted within the current session. Native readiness requires no model call. Future destination cognition uses that destination's existing payer/settings after entry, never copied credentials or a newly inferred allowance. This feature neither changes the provider nor requires an external Macrofold API.

## OC03 — Readiness and preview describe real opportunities

Prepare one complete immutable candidate and scoped findings per relevant revision. Check exact supported definitions; valid account-role/character binding; coherent geometry, support and body clearance; reachable required supplies; real custody/material eligibility; initial knowledge; and actual enabled actions for the selected opening. Use the current spatial and action owners, including their normal bounded navigation preparation. A stopped search is incomplete, not proof of reachability or absence.

Each selected opening profile declares the concrete activity it must support and its required native checks. For the familiar case, verify the character can reach relevant supplies, perform the known portions of making/food/rest and has a valid supported invention opportunity. Readiness does not predict which invention the model will propose, guarantee a hunting hit, prescribe the resident's choice or certify enjoyment. For deliberate harshness, show the chosen failure pressure; do not classify intentional scarcity as an unrequested repair.

Reuse qualified unchanged definition behavior. Run a native isolated rehearsal only for an actual uncertain composition or an explicit creator request. Rehearsal uses a separate temporary world and RNG copy, disables external AI dispatch and authoritative publication, and retains only evidence linked to candidate digest, input assumptions, checker revision and result. It never grants final characters memories, knowledge, items or practice. A paid character rehearsal, if later explicitly selected within supported controls, retains the same strict separation; it is not needed for first release acceptance.

Show the concrete starting layout with the existing presentation capability and a text/list alternative naming positions, access, people, resources and activity requirements. Only the proposed world's creator-permitted setup is visible; never overlay source-world private data. Existing native appearances suffice. Preview interactions inspect or revise the candidate, not issue live-world commands. Do not modify the renderer or picking lifecycle unless the existing preview surface demonstrably requires it; apply its normal guidance if it does.

Cache preparation by candidate identity/digest, exact definitions, check inputs and target profile where relevant. Appearance/name edits need not repeat unchanged geometry checks, but actual layout/body/resource/policy changes invalidate the relevant evidence. Review lists unresolved requirements and practical consequences without exposing hashes as the primary interface. A candidate is ready only when required native findings are current and no essential human requirement is unresolved.

## OC04 — Exact start on an operator-prepared empty target

### Operator configuration and target lifecycle

For the first release, the source host may address only explicit operator-configured local target records. Each record identifies the target's private intake address, public entry address, immutable target ID/generation, allowed creator accounts, intended account-role binding and existing operating configuration. The destination operator prepares its independent PostgreSQL database and data directory. The source receives no destination database connection: `PostgresDatabase` retains its single-writer advisory lock, and the destination host alone owns registration and activation writes. Intake credentials and filesystem/database details stay server-side. The client/model supplies a target ID from its permitted projection, never a URL, connection string, path, account entitlement or arbitrary process command. This is an installation adapter for the prepared-host boundary, not general provisioning or public cross-host federation.

Add an explicit **awaiting creation** startup mode. It initializes storage/schema and the target-registration record but does not construct `WorldService`, seed the bundled world, run a director, advance time or accept gameplay/authoring commands. Its lightweight HTTP state says that no world is running. Ordinary existing-host startup is unchanged. A target with a world root, retained world data, incompatible current records or a previous different activation is occupied/refused; an apparently absent root is not permission to overwrite leftover authoritative data.

The prepared host adopts only a valid committed initial-activation receipt for its target generation. Check at process startup and on an explicit readiness/entry request, with one in-flight adoption; no simulation tick or recurring AI poll is needed while empty. It then starts the ordinary service/director using that existing saved world, rebuilds process resources and exposes its usual entry/authentication route. No child process command or operating-system supervisor is authored by the model. A failed runtime start leaves the committed candidate available for ordinary restart; there is no reseeding or reset path.

### Review and destination authority

Native preparation chooses a particular candidate revision/digest and target generation. Bind review to the complete compiled world digest, included definitions, meaningful limits, target profile, intended creator/control-account mapping and start operation ID. The existing review owner records explicit human approval for this new-world operation. The model cannot call Start by writing an approving sentence.

Before a new activation, recheck the current source session/grant and exact reviewed candidate, the operator's current target allowlist/generation and account mapping, the destination's current emptiness and supported host/definition profile. A source `create` grant is insufficient without destination authorization. Initial grants are derived from existing authenticated account identities and the target's configured policy; world prose supplies none. Preparing the candidate confers no control lease. The character enters only through the normal authenticated participation operation after publication.

Keep operator configuration revision and target-registration data coherent: updating the target's permitted profile/allowlist advances its generation before another Start can commit. The destination exposes only narrow authenticated **prepare/check**, **activate exact approved candidate** and **read exact activation receipt** operations for configured source installations. The server-held service authorization identifies that source and target; each operation additionally binds target generation, allowed creator account, immutable candidate digest and source approval/operation identity. Use the operator's existing local transport/security configuration, strict request schemas and current body/work admission. Do not pass the service credential to the model/browser, accept arbitrary remote URLs, download candidate dependencies or expose a general destination mutation/read API. The destination's sole repository writer implements the native handlers.

Source permission is checked and the exact approved dispatch is recorded at the source admission boundary. The dispatch authorization permits only that one reviewed operation/candidate/target generation, under the existing bounded operation lifetime; it is not a reusable creator grant. Destination permission is independently checked again at its own commit boundary; a source `create` grant never substitutes for its allowlist/account policy. These are two authority domains, not an atomic cross-database revocation promise. Revoking source permission prevents a new dispatch, but cannot promise to retract an already accepted destination Start. Changing/revoking the destination registration before its commit refuses that operation; after commit it cannot erase the created world. The UI follows the same cancellation distinction. Keep unknown dispatch/acceptance status pending read-only native receipt reconciliation instead of labeling it canceled or automatically replaying it. A genuinely new dispatch requires current source authority even when the candidate is unchanged. No source world-mutation or authorization lock is held over remote work.

### One destination commit, recoverable source status

Give Start a durable source operation record before dispatch, containing the approved immutable candidate reference and target identity. The destination receives the bounded complete initial candidate through its native intake, validates the actual content against the pinned profile and prepares it without making it live. At activation, its one repository writer extends the existing transaction boundary to claim the exact target generation, assert complete emptiness and current validation/authority, insert the world records and initial account ownership/grants, and write the activation receipt atomically. Reuse the current record/history writers and authority provisioning; do not create a second save format or installer. A database-enforced unique target activation plus request identity prevents two source processes from winning. The target host keeps its ordinary single-writer lock throughout awaiting-creation, activation and runtime adoption.

The destination receipt binds source installation identity, source authoring operation, target ID/generation, candidate digest and created world ID. Same identity/body returns that receipt; changed-body reuse or another winning activation refuses. No source-world command/invention receipt, private memory, payer credential or live lease travels. The first world is paused and has fresh timeline/control admission; the canonical initial RNG and authored content are the reviewed values.

There is no distributed transaction pretending to commit source and target databases together. Destination receipt is authority for world creation; the source status is a recoverable reference. If the source loses acknowledgement, resolve that exact permitted receipt before any new mutation. If the source's authoring grant is later revoked, native reconciliation still records the actual operation outcome for operational correctness, while disclosure follows current audience permission; revocation never rolls back a world already committed. If no receipt exists and current authority no longer allows Start, refuse without publishing.

Prepare is cancelable before activation begins. Once Start is committing, cancellation means resolve its actual outcome; do not present a cancel button as a guarantee of no world. A failed transaction leaves the target empty. A successful transaction followed by host failure yields **World created; host unavailable**. Recovery never buys new generation, repeats first-world grants or creates another world. Changing targets after failure is an explicit new reviewed operation and does not retarget an uncertain request.

### Startup and restoration integration

Extract the necessary fresh startup preparation from `WorldService.initialize` so the reviewed initial state and first durable commit agree. Definition/state validation, initial perception/conditions, actor-role checks and explicit opening grants must precede publication; they cannot append an unrelated bundled scene afterward. The normal startup reader may rebuild derived state but must not allocate new authored identities, awards, biographies, physical stock or invention credits.

Creation project records, target registration and activation receipts are operational data outside gameplay rewind. Include them in current-format operational backup/recovery under their existing stores. Gameplay save/load preserves the resulting world with ordinary current-format validation; it cannot make an occupied target empty or authorize creation again. No development-save migration, legacy candidate reader, automatic deletion or whole-world replacement is introduced.

## Performance and growth

Cost grows with candidate entities/geometry, explicit definitions, required action/material checks, retained revisions and configured targets; it does not need recurring work proportional to the source world's history or every account's creations. Select permitted targets before hydration. Reuse a candidate's compiled definitions and geometry across its rows/checks rather than revalidating every visible object independently. Candidate construction and checks happen after explicit edits/check/start, never every simulation tick or keystroke.

Use [WC-L01–WC-L05](../limits/world-creation.md#wc-l01--reference-starting-population-and-place), [WC-L13's prepared-empty-target boundary](../limits/world-creation.md#wc-l13--prepared-empty-creation-targets), existing authoring payload/history/traversal limits, spatial preparation and host-work admission. The first reference is a locality with the selected supported cast; the current baseline's full wilderness population is not automatically an accepted generated payload. An oversized candidate or incomplete check stops honestly with retained work. Existing world/authoring storage admission constrains retention; there is no invented promise of unlimited revisions or background creation queue.

Measure cold construction, reused readiness, layout invalidation, full Start commit and host adoption separately, including visited entities/definitions and candidate bytes. Exercise the largest admitted supported opening and a rejected excessive candidate through the real callers. Record source-world responsiveness during preparation, target transaction duration, restart recovery and retained-memory behavior. Do not infer hosted capacity from a small native builder benchmark or require a new population simulator.

## Delivery, decisions and reconciliation

Implement OC01 → OC02 → OC03 → OC04 → OC05 within one assignment; host-lifecycle preparation may begin once OC01's initial-state contract is settled. The estimate and risks are in the [feature allocation](parallel-batch-07-playable-world-creation-feature-spec.md#stages-effort-and-acceptance). Complete integration and review fixes are owned here, including any narrowly necessary adaptation of the existing startup paths. No unanswered developer decision is required for this selected scope. A genuinely new law, population promise, publication policy or authority expansion remains outside it.

The consequential choices are: creation begins in an existing authorized session; the bundled family supplies the first supported profile; a complete fresh state is built rather than deleting/cloning a live world; only configured empty targets can receive it; the destination owns the exact receipt; normal entry grants control separately; and optional illustration/rehearsal does not delay a ready opening. These choices exchange general provisioning and arbitrary-law breadth for an actual independently deliverable creator experience while preserving the later profile/host adapter seams.
