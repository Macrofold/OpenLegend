## 1. Scope, authority and baseline

This design supplies the implementation contracts for the [Cognition Lab feature specification](cognition-lab-feature-spec.md). It is a developer workspace at `/cognition` for testing characters through the ordinary game implementation using independent scenario data. The feature specification owns screen composition, control behavior, content hierarchy and user journeys. This document owns runtime composition, request and record meanings, mutation/dispatch boundaries, persistence, extension seams and qualification.

The inspected baseline is `Macrofold/OpenLegend` `main` at `795dae71d1cf6a2e846ebfaaeb7c70342bc01f66`. The following are proposed additions, not descriptions of an installed lab. Existing source evidence is cited in the owner table. The [situation-aware context project](situation-aware-cognition-context-feature-spec.md) and the emotion proposal on `codex/design-stealth-02-emotions` contain compatible targets; the lab must expose their delivered capabilities when present without requiring those entire projects to finish first.

The lab changes no game law merely because it has a privileged editor. Perception, memory retrieval, judgment/routing, action offers, generation, output admission, native effects, memory recording and ongoing work use their ordinary owners. It does not call providers from the browser, emulate a character with a second prompt pipeline, invent actions from text, or run the rendered game client as a prerequisite.

The [development compatibility policy](../../AGENTS.md#development-save-policy) applies. Lab data is disposable development data. Implement the current format and reject incompatible data; no legacy reader, migration service, versioned protocol family, compatibility adapter or historical code replay is part of this project. A source commit or prompt/model identity stored with a result explains that result; it does not promise that the application can execute obsolete code.

## 2. Selected composition and isolation

### 2.1 One lab runtime beside the game runtime

The same server process owns the ordinary game and one lazily opened lab runtime. Each runtime consists of its own `WorldService`, `SqlGameRepository`, `AiDirector`, `CognitionExecution`, navigation preparation, ordinary mutation lane and lifecycle handles. They use shared constructors and shared semantic code.

Use one dedicated PostgreSQL database and one dedicated data directory for the lab. The current repository has singleton active-world state, explicit `open_legend` and `mind` schemas, and repository-owned operational rows. A different world ID in the gameplay database is insufficient isolation. A separate database avoids a repository-wide multitenancy refactor.

Standard development setup provisions the lab database alongside the gameplay database and exposes its URL through server-owned configuration. A configured lab database must differ from the gameplay database after resolving connection identity; the lab directory must not resolve to the gameplay directory. Missing or invalid lab configuration produces one actionable unavailable state. Never silently reuse the gameplay store. Connection strings and provider credentials are never sent to the browser or saved in exported scenarios.

The app opens without a configuration wizard when development setup is valid. On first use, initialize through the same current starting-world initializer as the game, with a new lab world identity and the installed authored rules. Do not copy a half-constructed live world or replace the normal opening with a hidden cognition-only definition set. Initial characters and objects are subsequently editable within the lab.

Exactly one scenario is active in the lab at a time. Saved scenarios, checkpoints and completed runs support serial experiments and side-by-side inspection; simultaneous live A/B worlds are not required. This constraint does not limit the number of characters in a scenario. It is a small development composition, not a new hosted simulation tenancy system. [Constraint owner](../limits/cognition-lab.md).

### 2.2 Shared runtime extraction

Extract the runtime construction currently embedded in `apps/server/src/http.ts` into a narrow shared factory, proposed `apps/server/src/world-runtime.ts`. It owns constructing and disposing the existing service, director, execution capacity, navigation and world-clock wiring. Ordinary game startup and lab startup call this same factory; there is no copied initialization function.

The runtime factory receives an existing repository, server-owned effective configuration and optional lab control/capture hooks. It returns the existing service/director accessors, one clock driver, and one close/drain operation. HTTP routing, authentication and static asset delivery remain host concerns. The lab consumes none of the PlayCanvas scene, entry artwork preparation, camera or render-frame loop to run cognition. Installed definitions, geometry and sensing required by the simulation still load normally.

Do not mechanically extract unrelated World Agent, public asset, invitation or hosting machinery into a generic container. Preserve their existing game startup ownership. Add only the second caller's required composition seam, and qualify normal game startup through that same factory.

### 2.3 Runtime and tab scope

Every lab endpoint is under `/api/cognition-lab`; it resolves the lab runtime explicitly. Existing gameplay endpoints resolve the gameplay runtime. Never select the destination store from a client-supplied arbitrary path, database URL, world name or actor label.

Server identity for a lab mutation is the authenticated principal plus the lab workspace, active world, timeline and expected scenario revision. Entity and record IDs retain their existing native scopes. Display names do not route requests. A second browser tab may inspect the same active lab; edits use the expected revision and return a concrete conflict rather than silently overwriting another edit. This is the existing one-writer model with revision checks, not a collaboration platform.

Reuse the authenticated host principal, but resolve its current native request scope from the lab authority store, lab world/timeline and admitted player binding before ordinary player intake. Never reuse a game-world scope, replace its actor with a picker value, or treat the lab's physical participation binding as play/control authority. Other selected actors use the explicit operator-authoring intake in §8.1. This reuses current authority owners rather than adding another authentication system.

Opening or operating the lab must not change gameplay pause, selected/controlled character, game save, autonomous actors, model configuration or request budgets. The game and lab may share process-level provider/network capacity; expose waiting caused by shared capacity rather than implying physical isolation of CPU or provider quota. The lab's own spending limits still apply.

## 4. State model and identities

### 4.1 Independent selections

The client keeps these values separately:

1. `inspectedActorId`: whose current editable information is displayed on the left.
2. Composer `actorId`: who submits the next Say/Act.
3. Composer target binding: exact person/object/location references required by the selected operation, or an explicit ambient/no-addressed-target choice.
4. `selectedTraceId` / `selectedStageId`: which captured processing is inspected on the right.

The run policy also stores an explicit `focalActorId`, initialized once from the initial inspected actor and then independently selected. The run strip shows it. Changing inspection, composer actor, targets or historical selection never silently changes that response boundary.

Changing item 4 never replaces item 1's current values. Changing item 1 does not transfer control, change the composer actor or mutate autonomy. A deliberate “Inspect this person” navigation changes inspection only. Targets use exact IDs, not the current inspector selection as an implicit fallback.

The left pane consumes the current lab projection with `scenarioRevision`. The right pane consumes immutable run/trace records with their captured time and source revisions. A link from a historical memory to its current source labels the destination as current; it does not silently update the recorded input.

### 4.2 Lab records

| Record          | Required meaning and fields                                                                                                                                                                                                   | Lifetime                                                                                              |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Workspace       | Stable lab ID, owner, active scenario/checkpoint references, current runtime generation, last confirmed save status                                                                                                           | One configured lab store; no cross-game alias.                                                        |
| Scenario        | Name/description, current-format full initial-world checkpoint reference, authored event sequence, chosen autonomous participant set, experimental context fields, effective run settings, optional evaluation notes          | Reusable starting situation. Saving a new starting situation does not preserve live request handles.  |
| Run             | Run ID, scenario/checkpoint origin, status, simulation and wall start/end, exact effective nonsecret configuration, stimulus occurrences, interventions, roots/stages/outcomes, accounting/completeness, optional annotations | Inspectable experiment, independently retained from rolling diagnostics.                              |
| Checkpoint      | Existing game-save identity plus lab name, scenario/run origin and capture instant                                                                                                                                            | Resume native state and accepted history using the current native save contract.                      |
| Prepared call   | Opaque handle, run/root/stage, world/timeline/generation, scenario revision, purpose, request kind, immutable original request, server bindings, gate status                                                                  | Process-local and single-use; never resurrected by loading.                                           |
| Evaluation note | Expected behavioral qualities or required result, selected source evidence, operator annotation                                                                                                                               | Outside all actor/model inputs unless explicitly copied into a separately labeled experimental field. |

Use native IDs for game records and application-issued opaque IDs for lab records. Composite keys preserve their components, following [identity and references](../identity-and-references.md#contract). A recorded source reference includes record kind and observer where applicable; matching only a shared event ID is not sufficient.

A source-reference projection carries native kind, world/timeline, exact native source ID, owner/observer actor where that kind requires it, the captured source revision and an optional retained-artifact identity. Follow the native kind's real identity contract rather than assigning every source the same fictional schema. `/sources/:id` uses an opaque server-issued binding to this complete reference; it cannot accept an unscoped event ID and guess a private perspective. Actor/entity references used by the composer are native IDs scoped to the current runtime, not source-reference handles.

`sourceCommit`, installed definition identity, model, prompt/rubric identity and adapter identity are explanatory provenance. Store current identifiers already provided by their owners. Do not build an old-code loader, global schema registry or version-negotiation protocol.

### 4.3 Current data and saved evidence

The active world and its complete relevant history remain in the ordinary lab repository. The left pane does not become a second persisted character object. A run captures the exact inputs/outputs it needs to explain an experiment, plus references into an immutable run checkpoint when requested; it must not depend exclusively on a rolling diagnostic cache.

Manual scenario edits are interventions. Retain their concise structured differences inside the run when they occur during an experiment. This is experiment evidence, not a development revision diary. At the start of each new run, capture one coherent native origin from the actual current applied state before its first stimulus or time advance; reference that exact checkpoint from the run. This includes unsaved applied edits and must not silently reference an older named scenario. Reuse an already captured checkpoint only when its native state and effective settings still match. Required origin capture uses the ordinary snapshot owner and CLL07 storage admission without a naming dialog; if capture fails, retain the draft and show the actionable setup/storage failure before dispatch. Continue and later stimuli in the same held episode reuse this origin and record their ordered stimuli/interventions. Do not capture another whole world per utterance, model call or keystroke.

## 5. Control of simulation and cognition

### 5.1 Distinct controls

| Operation                   | Effect                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stop following live updates | Client selection/scroll behavior only. Server simulation and paid work are unaffected.                                                                                                                  |
| Hold                        | Close new lab admission and stop native time at a safe boundary while admitted work settles; retain a consistent undispatched prepared call when one exists. This is the ordinary toolbar pause intent. |
| Native manual pause         | Advanced/internal control through the shared owner; resulting job cancellation/deferral remains explicit. It is not the ordinary toolbar Hold action.                                                   |
| Lab breakpoint              | A deliberate experiment hold before a selected operation or at a completed run boundary. It is not implemented by toggling ordinary manual pause.                                                       |
| Cancel request              | Cancel the exact admitted request through its owning controller. Already accepted effects and paid/uncertain work remain recorded.                                                                      |
| Stop run                    | Close further run-scoped admission, drain or explicitly cancel outstanding work as described below, then publish a terminal run result.                                                                 |

The shared runtime's clock driver accepts a lab hold that stops offering new native elapsed time and drops time accumulated while held. It does not change the underlying world's ordinary paused flag, cancel background work through the ordinary pause path, run native ticks at zero time to manufacture opportunities, or accumulate catch-up time for resume.

`WorldService.paused` currently includes manual pause, maintenance/storage holds and absence of a participating connection. Add one narrow runtime-driver liveness input for the authorized lab controller: it satisfies the operational away gate while an explicit finite lab run or prepared hold exists, without synthesizing a browser connection, taking control of a character or changing `pauseWhenHidden`. Gameplay keeps its existing presence behavior. Storage, manual and maintenance holds remain authoritative. First open is a lab-held boundary with no simulation debt; install the lab admission/clock controls before starting its director or host wake so initialization cannot dispatch a paid request before the hold exists.

Clock liveness does not establish physical participation. The current `WorldService.tickBatch` calls `reconcileParticipation`, whose `participatingHumans` derives presence from authenticated game connections/heartbeats; a renderer-free lab would otherwise begin the default speaker's exit. Extend this shared participation owner with a small, server-authorized runtime-participant input. The lab's declared participation set initially covers the authorized human-bound actors already active in the initialized/imported scenario. It is independent of inspection, composer actor, focal actor, autonomy and long-lived control. Capture the set with scenario/run settings; do not fabricate accounts, game connections or permissions.

Supply trusted lab participation configuration to the shared runtime/service at construction. Resolve its initial actor set after native world/authority initialization but before the first participation reconciliation; the current initializer calls `reconcileParticipation(!!existing)` before `service.ready` resolves. Installing bindings after readiness would already be too late. Derive the set from the authored/restored pre-reconciliation active state, preserving genuine saved exits.

The lab binding prevents absence caused solely by the missing game renderer. It remains in force across ordinary Hold, prepared editing and browser disconnect while that isolated runtime is held. Before resuming or installing a restored scene, revalidate the exact actor, timeline, current operator authority and native eligibility. At each participation reconciliation, contribute a lab binding only while its native actor is still active; prune stale bindings before the existing participating-actor branch, which can otherwise return an exiting/inactive actor. Existing exiting/inactive/departed/dead states are not silently returned or revived. An explicit participation experiment withdraws the relevant binding before invoking the ordinary departure owner; a return uses that owner's admitted return operation. Native death, removal and genuine departure still retire the binding and their normal work/evidence consequences. Scenario replacement drops the old generation's bindings and establishes only the selected new scene's declared set; disposal clears them. This is a lab-scoped source of operational participation, not a new world law or a second participation state machine.

The run owner gates new cognition admission at the shared director boundary and checks that gate again at the shared pre-dispatch wrapper for every model attempt, including a later child stage of an already-admitted task. A closed gate blocks new dispatch; it does not cancel or pretend to finish an undispatched continuation. Settling covers already-dispatched attempts and accepted publication/commit work in progress, not held undispatched continuations or a native action's future completion. It must not dispatch unrelated work while the operator is examining a breakpoint. Both gates belong to the lab runtime only. The game runtime remains active.

### 5.2 One-stimulus default

Default Submit performs this finite workflow:

1. Check the typed intention, current authority, expected revision and cheap known preconditions before expensive capture or model work; reserve the operation's required retained metadata.
2. For a new run, obtain the exact applied origin required by §4.3; later intervals reuse that episode's origin. Bind the returned capture revision/generation to source admission. If the applied scenario changes during capture, refuse as stale before executing rather than pairing the stimulus with a different origin.
3. Commit the ordinary source event or action request once through its owner, rechecking current admission after awaited preparation.
4. Identify the focal actor and that actor's actual opportunity/disposition associated with the committed occurrence.
5. Let the ordinary cognition pipeline perform its relevant immediate stages, including dependent judgments and required output admission.
6. Stop after that focal immediate decision reaches a terminal disposition and its accepted effects are durably published.
7. Close further admission for this run, settle already-dispatched work, and hold at the resulting current world. Show the exact stop reason.

A decision may complete by continuing current work, declining to intervene, or failing; it need not produce speech. “No perceived stimulus” and “no new decision admitted” are terminal explanations, not an infinite wait for a reply. The source association is not derived from message wording.

The default does not wait for an action's future completion, every bystander's later reply, memory consolidation, reflection or all possible consequences. Started native work remains started in the held scenario. The UI shows that state. Separate explicit stop conditions support a selected action's completion, a chosen actor's next decision, a particular event/condition or an elapsed simulation duration.

An already-dispatched child that finishes before the hold becomes quiescent keeps its actual outcome. A future independent opportunity remains pending/eligible under the shared scheduler and is visible when relevant; it is not falsely recorded as completed or automatically dispatched to make the trace look tidy.

### 5.3 Correlation and finite disposition

Attach lab observation identity to native admitted work outside model input: run/interval, source occurrence IDs, focal actor and actual opportunity/decision IDs. Add passive hooks at perception publication, opportunity disposition, job admission and final publication. The native producer supplies cause/dependency references; the lab does not infer causality from similar text or temporal proximity.

If a focal character did not receive the stimulus, the actual perception result closes that interval as not perceived. If native opportunity evaluation elects to continue work, defers, combines a stimulus into another decision or admits nothing, capture that disposition and its actual reason/boundary. Do not force an opportunity merely to produce a call. A decision already in flight before the source arrived counts as the response only if the native owner actually consumed/combined that source; otherwise it is a separate concurrent result. The finite run guards resolve missing/unrecorded progress without inventing a no-decision reason.

The run observer is a small correlation/boundary consumer of these callbacks. It never chooses actions, calls providers, implements scheduling priority or polls every actor for a fictional response. All newly admitted supporting/background attempts contribute to the interval's guard/accounting even when they are not the focal response.

### 5.4 Continuous and stepped execution

Continuous Run repeatedly offers elapsed time and ordinary admission until an operator stop, selected stop condition, configured run spending limit or real error. It does not create a new model call merely because a UI interval elapsed.

Advance-time and run-until use the same clock driver/native boundaries as normal play. A step crosses one defined semantic boundary (selected event, stage or decision), not an assumed number of 50 ms host wakes. The recorded step specifies which boundary was crossed. Provider waiting time, simulation time and operator breakpoint time remain separate measurements.

The selected autonomous participant set is a lab admission policy, not a transfer of human control and not a changed personality. A scripted event authored for a character remains labeled operator-authored. Actual directly controlled-character psychology follows its owning policy; the lab does not resolve the emotion branch's separate SA-D01 decision by selecting a person in a dropdown.

### 5.5 Bounded stopping

Do not wait for abstract “global quiet.” Stop at the selected identity-bound condition. Existing request deadlines, execution capacity, context limits, native work budgets and spending admission continue to bound work. Every run has a visible cost allowance derived from and no larger than its operator-authorized allowance; there is no hidden lab budget multiplication.

If the stop condition cannot be reached because the selected operation was refused, the actor disappeared, a required capability is unavailable, or a request has an uncertain external outcome, terminate with that specific disposition. A completed useful action is not required to call the run finished. Unknown external completion stays unknown until the existing receipt owner resolves it.

## 6. Prepared-call inspection and one-shot overrides

### 6.1 Hook position

The shared stage wrapper offers a prepared-call hook after the exact typed application request and server-owned reference/source bindings exist, but before cost reservation, dispatch intent and the provider call for that stage. This must be an ordinary shared dispatch boundary used by attention, routing, action scoring, generation and other supported stages—not a separate lab implementation of those operations.

The current `AiDirector.call` wrapper accepts a closure that dispatches the request. Refactor that boundary into a typed prepared request plus an execution function where necessary so the hook can inspect the actual request, not infer it from a log. Existing judgment/generation callers continue through the same attempt reservation, source validation, settlement and publication paths. Equivalent hooks are required for independently dispatched embedding or reflection/harness operations the UI offers to inspect/edit; an unsupported hook must be explicitly unavailable, never approximated with a fabricated payload.

Offer a held hook before acquiring the selected call's scarce execution slot or cost reservation. Never keep a world/SQL mutation lock across the operator wait. Any already-existing parent reservation remains visible under its native accounting owner; the lab cannot silently release or duplicate it. Revalidate source/authority, acquire capacity and reserve the actual selected request only when dispatch is explicitly resumed.

No debug hook is enabled for the gameplay runtime. With the lab hook disabled, ordinary callers receive the same inputs, route choices and outcomes, without diagnostic deep-copy work.

### 6.2 Request kinds and editable material

The discriminated request kinds are the existing judgment, generation, embedding and supported harness/tool request types; derive their schemas from their actual transport owners. The editable envelope contains all model-facing fields accepted by that kind: state/context, instructions, questions/options, supported model/effort settings, response schema and supported tool declarations/results.

The following remain server-owned: request/attempt IDs, principal and permission context, world/timeline/control bindings, secret credentials, endpoint URL, abort signal, actual execution deadline, real spending reservation, tool execution authority, and the captured reverse map from model references to native identities. Display safe identity and accounting summaries beside the editable envelope; do not serialize protected execution material into an editable JSON blob.

An operator may remove, replace or invent fictional information inside the request, including deliberately false or contradictory context. This is the point of the experiment. The run identifies the override. The normal response parser and native admission remain in force: adding a person's name, action string or invented reference token does not grant an executable target or capability. Structural validation failures report their path and preserve the draft rather than silently rewriting it.

### 6.3 Handle state machine

A prepared-call handle moves through `prepared → submitted → consumed`, or from `prepared` to `invalidated` or `cancelled`. The server issues it after preparation and accepts it exactly once. It binds an immutable original request and the exact scenario revision/generation. A duplicate Submit returns the same accepted submission outcome; it never makes a second provider request.

Only the payload modal's Submit sends its replacement envelope with that handle. Ordinary composer Submit has no override parameter and always prepares from the current scenario. Closing the modal discards its override draft and leaves the call visibly held. It does not dispatch or leave a persistent hidden override. Continue original submits the unchanged prepared request; Stop cancels it through the shared owner. Applying a left-panel edit invalidates prepared handles before further dispatch and visibly disables their Submit action. Restore, scenario load, principal change and runtime replacement do the same.

Provide Restore original and an original/edited difference view. The server retains original and actually submitted requests separately. A run's summary states whether it used ordinary inputs, model-only context additions, a stage override or several explicit interventions.

Invalidation never means repeating the accepted source. A native same-source retry is exposed only when its owner reports exact eligibility and rechecks it on execution. The existing interactive chat `submit(..., retryOf)` can reuse the latest failed speech job only when it has no accepted effects and its speaker, target and source still satisfy the owner's checks. It is not a general re-preparation API for cancelled calls, action/event sources or consumed opportunities. An eligible retry creates fresh attempt/preparation evidence under that native owner, may stop at the requested supported gate and counts its actual new cost. An ineligible case offers explicit restoration/rerun from the run origin or a deliberately new composer stimulus. Never invoke `prepareAndHold` merely to rebuild an invalidated request, resurrect a consumed decision, or add a generic historical-pipeline replay engine. Newly applied edits are carried into a whole-scenario rerun only as explicit declared variant differences.

### 6.4 Human wait and deadlines

A breakpoint is reached before dispatch of its selected call. No provider call is suspended mid-request. Operator editing time must not consume that call's provider timeout. Existing calls already in flight keep their real deadlines and settlement semantics.

When a lab gate holds a prepared operation, the shared decision timing owner records the start/end of the operator hold and suspends only that undispatched decision's pending immediate/expiry timers. The current [AiDirector](../../apps/server/src/ai-director.ts) installs `immediateTimer` and `expiryTimer` using `fastPublishBy` / `fastPublishByMonotonic` and `usefulUntilWall` / `usefulUntilMonotonic`; merely shifting those fields after editing would leave a timer free to defer or abort the request during the hold. Enter the hold through the same owner transition, first reject already-expired work, record the remaining intervals and clear those timers. Already queued timer callbacks must consult the current hold/generation before deferring or aborting. On Continue, shift the corresponding wall and monotonic deadlines by the measured hold interval and re-arm the remaining owner timers; on cancellation/invalidation, discard held timing state without re-arming. Preserve any deferral or expiry that occurred before the hold. Every matching preparation/publication expiry check uses that same adjusted timing state.

Introduce this one explicit timing operation on the existing decision owner; a normal game request never invokes it. Do not patch `Date.now`, `performance.now`, global timers or provider clocks, and do not clear or extend any already-dispatched provider request's timeout. Operator time is an explicit experimental intervention, not evidence that a normal production request would have met its original latency budget.

This is an explicit timing intervention, captured in the run, and therefore cannot qualify ordinary production latency. No already-expired operation is revived; cancellation, changed evidence or actual in-flight expiry still invalidates it. If another admitted operation changes a dependency while the selected call waits, invalidate the handle and offer only §6.3's eligible native retry or explicit rerun/new-stimulus choices. Do not silently recompute the request under the old handle.

### 6.5 Replay and rerun

Replay displays previously captured inputs, outputs and effects without inference or mutation. Rerun request creates a new, explicitly paid request comparison using the captured application input and chosen compatible settings. It uses the normal provider adapter and response validation, but does not publish actions, speech, memories or other native effects into the active world. Its result is labeled Request comparison, not a new character decision that happened in the scenario. Never edit the old run.

Continue from checkpoint is available only when an actual coherent checkpoint was captured at that held decision boundary and the current runtime can reconstitute its native prerequisite bindings. A process-local handle itself is never serialized. On restore, re-prepare those bindings through the normal owner and verify the recorded request/dependencies before allowing continuation; changed dependencies make the continuation unavailable. Store only a declarative supported-gate descriptor beside the checkpoint: native stage purpose, actor and originating source IDs, exact request artifact, required source/reference proofs and prerequisite stage-answer artifacts. The normal owner creates a new decision job, attempt and publication claim in the restored generation from that descriptor, then checks the reconstructed required input/bindings before dispatch. Do not serialize request-owned callbacks, `RetainedDecisionPreparation`, an old abort controller or a prior `DecisionPublication` claim; [decision preparation](../../apps/server/src/decision-preparation.ts) remains request-owned. A stage advertises checkpoint continuation only when its owner can reconstruct these prerequisites; otherwise offer Run scenario again. No old receipt is replayed as a new execution. Do not capture a full world before every model call merely to provide this action.

Run scenario again restores the saved starting checkpoint and executes perception and every earlier selection again. The active scenario then contains this new execution's real effects. Complete-scenario reruns and request comparisons neither promise identical remote-model answers nor substitute a recorded answer for a new model call without an explicitly labeled intervention.

If the captured request or checkpoint is incompatible with the current runtime, explain why execution is unavailable and permit ordinary recorded inspection where readable. Do not add an obsolete-code loader or compatibility engine.

### 6.6 Preparing from an idle composer

Opening Edit next input reads the supported stages and opens a preparation sheet. It must not commit the stimulus, advance time or call a model. Prepare and hold is the explicit executing action: it submits the source once, then allows necessary earlier native processing until the next matching actual prepared call. Its incurred calls and source occurrence remain in the run even if the operator later cancels.

The default match is the next actual decision/judgment/generation call belonging to the chosen focal reaction; it excludes preceding embeddings and other support calls. Show the selected purpose/category before Prepare and hold. An advanced stage selector can deliberately target a supported embedding, reflection or harness operation. A specific purpose filter matches a reported stage capability, not a mandatory pipeline position. If that response never needs the requested call, finish with its actual no-call or terminal disposition. Do not generate a dummy request. The sheet states that preceding work may incur cost; the held modal shows the resulting exact application input.

## 7. Scenario authoring and mutation contracts

Each mutation carries the current runtime generation, expected scenario revision and the existing owner-specific concurrency tokens. Reuse stronger existing checks: person editor base values, memory source hashes, installed manifest revision and body policy pin. A disagreement returns the current field values and a stale outcome without partially applying the draft. Do not replace the existing field-level/native checks with a single weaker UI counter.

When a field group spans several owners, the server prepares/validates all groups first and applies them under one admitted service operation. If the current service cannot provide atomicity for that group, separate its Apply actions visibly by owner; do not present multiple partially successful writes as one atomic edit. ### 7.2 Supported value holds

Hold during this experiment is available only for directly writable fields whose native owner advertises a hold capability. The owner applies the authored value at its actual scheduled mutation boundaries and reconciles dependent conditions through its ordinary rules. Each hold records the field, value, starting/ending boundary and that it is an intervention. It does not create natural immunity, explain away ordinary depletion or imply that a held reaction is spontaneous.

Do not repeatedly overwrite arbitrary JSON from a UI timer or repaint a constant over a changing native value. Derived fields cannot be held. A native field whose owner lacks this capability remains visibly unavailable for holding; CL03 adds the narrow owner hook where needed. Releasing a hold leaves the current accepted value in place and resumes ordinary evolution from it; it does not replay missed decay or restore a stale pre-hold value.

### 7.3 Speech history, memories and coherent retcons

The editor distinguishes what happened, what a particular person perceived, what they remember now, and what they believe. These are different editable sources with different consequences. Choosing a speaker and writing a past sentence is insufficient to imply that every nearby or current character heard it.

A new history authoring operation accepts an exact source kind, source time/order, actor/subject references, actual event content and explicit observer perspectives where the native model permits them. It validates temporal references and source links against the loaded scenario. It uses the existing creator-history preparation/commit owner, extended to admit insertion if insertion is not currently supported. This extension is CL03 work, not existing functionality inferred from the JSON viewer.

A prospective edit preview names the selected source and the affected actors/derived records. The existing history correction path hydrates the complete selected dependency closure, including cold SQL history; its recall candidate limit must not truncate this maintenance work. It can clear existing appraisals for affected actors. Show that consequence before Apply and refresh the left projection after the durable commit. Do not hide this by leaving stale private feelings painted on screen.

Changing a source inside a completed run never rewrites that run's evidence. The operator creates or edits a new starting scenario, then reruns. A current-run retcon is permitted as an explicit intervention when the run is held, with before/after source references; its label makes the experiment's edited history clear. Backdating an utterance is not replaying an actual earlier provider request.

### 7.4 Declared model-only fields

A custom field record has an application ID, label, datatype (`text`, `number`, `boolean` or a labeled numeric `meter`), description, value, subject scope, enabled flag, recipient actor IDs and supported input placement. A meter may declare display bounds/unit; these describe only its experimental display. Subject scopes are person, directed relation, object and scene. A directed relation binds exact `fromActorId` and `toActorId`; the direction is never inferred from display order.

Recipient actor IDs are explicit. A person field defaults to that person's private input; a directed-relation field defaults to its `fromActorId`. Object and scene fields require selecting whose input receives the experimental information. Adding another recipient is an intentional, recorded injection; it is not presented as natural perception. The editor offers source labels such as private belief, observed description and story premise to explain the experiment, but those labels alone do not install knowledge or physical facts.

The shared decision-context assembler accepts a lab-owned extra-context section with a clear experimental provenance marker. Only applicable fields for the actor whose actual request is being prepared and that stage's declared context capability are included, independently of the run focal actor, current inspector and composer selections. Other autonomous participants receive only their own explicitly scoped experimental fields. Stages that cannot accept contextual additions advertise this and are not silently patched elsewhere. The normal state/context envelope carries this section; it is never converted into provider/system instructions or tool authority. An embedding, response schema or judgment question is not modified just because a field is enabled.

Installed native fields and model-only fields must have different descriptors and mutation endpoints/operation kinds. A model-only `fear`, `hunger`, `blessing`, `knows_secret` or `can_fly` does not install an actual emotion, satisfy a resource, create knowledge provenance or grant flight. If a matching native capability later exists, the operator can deliberately author that native state through its owner. Do not auto-promote custom names into mechanics.

Custom-field transport/storage bounds and the deliberate absence of an extra count quota belong to [CLL08](../limits/cognition-lab.md#cll08). A rejected field remains in the editor draft with a validation message. No silent truncation, coercion to a string, or hidden exclusion is allowed. The recorded right-hand input includes the exact submitted fields and placement, so an operator can verify that a change affected the request.

### 7.5 Typed capability descriptors

Workspace bootstrap returns the fixed shell/runtime/run summary, supported capability kinds and category availability/counts. It does not enumerate every actor, installed definition, custom field or selectable reference. Obtain field descriptors and values in one bounded batch for the requested actor/category page through the existing current-projection owner; the opening Overview may use that same bounded read. No per-field requests or whole-character preparation are needed to paint the shell.

A selected field descriptor carries identity, label, datatype, native versus model-only meaning, editability, owning mutation and unavailable reason, with units/bounds where meaningful. Reuse immutable definition metadata separately from current actor values. Small fixed enums can carry inline options; large or growing choices expose a scoped searchable paged choice source and the currently selected exact binding, even when that value is outside the current page. Long prose/structured values supply their permitted preview and selected-detail reference rather than their entire contents in bootstrap. Prefer installed descriptors and add only missing projections; this is not a general plugin/schema framework.

The UI selects controls from the datatype: compact numeric input plus an appropriate bounded slider; checkbox/switch for boolean; searchable select only for genuinely long option sets; multiline editor for prose; full modal for complex structured content. Unknown structured native fields remain inspectable and clearly read-only until an owner exposes a validated editor. An advanced JSON editor may edit a declared supported JSON field, not arbitrary properties of a world object.

## 8. Stimulus, run and settings contracts

### 8.1 Submitted stimuli

Every executing stimulus has `commandId`, `expectedRevision`, `focalActorId`, a discriminated stimulus body and requested run policy. The authenticated principal and destination runtime come from server routing. The command ID deduplicates repeat submission of this same intention; it does not identify a new run when retried after an uncertain HTTP response.

| Kind  | Body                                                                                                      | Execution and evidence                                                                                                                                                                                                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Say   | `actorId`, text, supported native `volume` and optional exact `targetId` (absent means ambient address)   | Ordinary player-to-NPC directed speech uses the shared interactive conversation intake; ambient or explicitly operator-authored speech uses the native source/event owner. Preserve actual hearing, exact source identity and the selected intake's job/receipt ownership. |
| Act   | `actorId` and either a supported command intention or a prepared native action choice with exact bindings | Use the shared command/grounding binder and native admission through the appropriate player or explicit operator-authoring authority. Preparation and execution bind the same exact actor; a preview is not a successful effect.                                           |
| Event | A supported owner-authored event intention, its native subject/target references and required typed data  | Apply through the corresponding creator/domain owner. Selecting an Act does not imply that arbitrary source text is a supported native action. Existing generative grounding may propose a mapping; it must still resolve to the shared catalog and pass admission. Distinguish input accepted, interpretation pending, interpreted choice, command admitted, action started, action completed, refused and unavailable. If the game needs a clarification, preserve that result in the lab; do not manufacture a successful command.

The ordinary game `/api/chat` route calls `AiDirector.submitInteractive` and its `submit` owner. That owner commits speech once through `WorldService.say`, checks actual target hearing and associates the exact occurrence with a durable interactive chat job; autonomous intake excludes speech already owned by that job. The lab's ordinary directed player speech must reuse this complete path, including its priority, evidence, cancellation and retry rules. Calling `say` separately and then submitting chat would duplicate the utterance; calling only `say` would choose a different autonomous path. Capture the actual intake kind and source/job relationship. The independently selected focal actor controls observation/stop only, never inserts a second target decision. Ambient speech and explicitly operator-authored NPC speech preserve their native opportunity routing rather than impersonating a human-controlled chat.

For authoring speech/actions as another scenario actor, bind the authenticated operator and the exact acting character separately at one shared admitted intake seam. Existing `WorldService.command` resolves its actor from the supplied player scope, `AiDirector.submitAction` likewise uses its authority actor, and `godAct` only supplies specific operations such as revive/enable-cognition; none is a general arbitrary-actor executor. Extend the shared intake/binding owner with an explicit operator-authored intention, retaining current creator authority, target permissions, source freshness, native body/work prerequisites, ordinary interpretation and final command admission. Reuse the binder and executor used by gameplay; do not forge a player scope, omit authority to bypass it, change a controller or write a lab action executor. Record the selected authoring route as an intervention, so forcing Ada to act cannot qualify Ada's independent choice.

The operation receipt distinguishes native source acceptance from the later focal decision/action outcome. Return the accepted occurrence/command identity as soon as durable acceptance is known; publish later progress through the same operation/run identity. The client clears only that accepted draft revision even if cognition later fails. Before source acceptance, refusal preserves the draft and uncertainty reconciles the original command ID. Response retry does not repeat the source. This receipt meaning is shared by Submit and Prepare and hold.

The operator may submit a stimulus as one character while inspecting a different character and focusing the response on a third. The request records all three bindings. The focal actor is whose immediate response defines One response; other autonomous actors retain their actual eligibility and captured outcomes within the chosen run policy.

The Action picker and right-hand evidence distinguish all installed definitions, the actor's known/possessed capabilities, currently eligible choices, choices actually offered to a particular judgment, the proposed selection and the finally admitted result. All installed is a searchable developer catalog view with unavailable reasons; it is not the list the model was given. Selected-call Options shows the complete captured offered set with actual scores/output when available. It must never fill a missing offered set from today's catalog. Source-defined action families/variants remain searchable without rendering hundreds of persistent buttons.

### 8.2 Run policies and guards

A run policy contains mode (`oneResponse`, `untilCondition`, `forDuration`, `continuous`), focal actor when required, a typed stop condition, autonomous participant IDs, requested simulation duration, active-wall guard, maximum newly dispatched model calls and current authorized spending allowance reference. The policy is validated and displayed before work begins. The run records the requested and effective values plus any constraint that reduced them.

[CLL06](../limits/cognition-lab.md) owns proposed numerical defaults and their qualification status. Its time, call-count and active-wall guards are different from monetary spending authority and per-provider deadlines. Reaching a guard ends with Run limit reached; it must never be represented as an actor choosing silence. Already admitted work settles or cancels through its owner, and no new work is dispatched after the stop gate closes.

Continue explicitly opens a new displayed guard interval on the same retained run. It does not reset paid accounting, erase previous interventions, refund calls or recursively continue by itself. Run until stopped is a deliberate continuous mode with visible bounds, not a hidden unbounded loop. Advance time uses the ordinary clock path and tells the operator whether autonomous cognition is enabled during the interval.

### 8.3 Effective inference configuration

The lab uses an explicitly configured standalone provider allowance under the existing spending owner; it never copies the gameplay world's remaining balance as a new entitlement. Run/interval guards constrain that real allowance and cannot mint additional funds. Restores leave operational spending intact. No new cross-database billing platform is required.

Run configuration is a nonsecret snapshot derived from the ordinary installed settings. It includes model/provider route per supported purpose, requested model identity, effort and output settings, escalation policy, actual judgment/rubric/instruction identity, relevant context inclusion settings, prompt template identity, native seed/state origin, active capabilities and the run guards. Capture both requested and actual reported model/deployment identity where the adapter exposes them.

Changes apply to the lab run or named variant, never the live game's global config. A request's supported settings are validated before its existing cost reservation. A model/provider choice must resolve through configured server routes; no arbitrary endpoint, API key, hosting credential or permission override is accepted from a payload editor.

For `JudgeRequest`, the captured application input includes `state` and the complete typed `questions` map, including each question's instructions, choices/criteria and answer kind. For `GenerateRequest`, it includes `task`, `instructions`, `context`, `schema`, `schemaName` when present, model/effort/output bounds and supported execution/output-mode choices. Effective adapter settings omitted from these typed objects are captured alongside them. The reference tables actually included in state/context are part of the captured request; their executable reverse bindings remain server-owned.

Retain both the editable application request and any actual provider input/output capture emitted by the adapter. Label an adapter capture unavailable when it does not exist; never call a reconstructed prompt exact wire input. Neither receipt output nor UI explanation includes hidden provider chain-of-thought. Record actual supplied rationales and application deliberation only.

### 8.4 Serial experiments and native randomness

A serial A/B experiment restores the same full starting checkpoint before each variant, then applies that variant's declared settings or scenario edits and runs the specified stimulus/episode. Each result records its origin and exact differences. The final variant's resulting state remains the current lab state, visibly labeled; restoration afterward is an explicit action.

Preserve the native saved RNG continuation, simulation clock and current work state when cloning/restoring an origin. Reusing a seed alone does not prove equal state after different preceding events. Remote-model answers and completion ordering may vary despite identical captured inputs; comparisons show observed differences rather than claiming determinism or causal statistical significance from one pair.

Expectation notes, quality tags and operator scores do not enter character inputs automatically. Episode evaluation can include explicit repeated runs and the existing evaluation project's separate qualification workflow. No automatic extra paid judge is dispatched for a single speech test or for opening a comparison.

## 9. Capture, causality and historical inspection

### 9.1 Actual graph, flat presentation

Store the actual operation graph: a root for the stimulus/decision, stable stage/attempt IDs, parent/dependency IDs, actor, purpose, kind, start/finish/held times and terminal disposition. A judgment, generation, memory retrieval, action admission, publication or maintenance step may appear only when it actually occurred. The UI renders the graph as a flat ordered list with relationship badges and filters; storage identity must not force a recursive tree UI.

Do not hard-code a mandatory attention → routing → action → speech sequence. A missing stage can mean not needed, not admitted, not captured or unavailable; expose the actual reason when known, and preserve unknown when it was not recorded.

The root summary joins the submitted occurrence to perceived stimulus, selected response/disposition and accepted native effects. It remains understandable without expanding every call. A historical selected root or stage reads only captured records and never re-executes context builders against the current actor.

### 9.3 Retention and costs

A run record retains its bounded exact request/response evidence independently of the transient diagnostic log. Reuse existing receipts and log identifiers; do not create a second financial ledger that can disagree with settlement. Aggregate each unique actual attempt once across root, stage and run totals. Retries, embeddings, reflection/harness work and uncertain completion remain attributable when dispatched in the run.

Unknown cost is not zero. Estimates retain their pricing basis. A cancelled display row does not erase a provider request that may have executed, and a rewind does not refund or redispatch it. A request comparison adds new cost to its own result and the current allowance, never to the old recorded run.

Loading older evidence is read-only and free of model work. Annotation saves update only annotation records, not captured inputs/outcomes. Immutable evidence here means the app does not silently rewrite an experiment; it does not require a tamperproof archival subsystem or indefinite storage.

No persistent live synchronization.                                                         |
| `retainRun`                          | Run ID and optional name                                                                                                                           | Retain bounded evidence with truthful completeness; no world mutation/inference.                                                                                                         |
| `rerunRequest`                       | Captured stage ID, optional edited envelope/config variant, requested allowance                                                                    | New request-only result; does not execute a character effect in today's world.                                                                                                           |
| `continueCheckpoint`                 | Actual captured checkpoint ID, stage binding and compatible requested variant                                                                      | Fresh preparation/validation before new native continuation; unavailable without real checkpoint/bindings.                                                                               |
| `runComparison`                      | One saved origin, ordered named variants and authored episode, explicit guard/allowance policy                                                     | Serial restore/run under §8.4. Each variant has separate evidence; no hidden parallel runtime.                                                                                           |
| `annotateRun`                        | Run/root/stage ID, annotation text/tags or expected-behavior note                                                                                  | Metadata only, excluded from every model input.                                                                                                                                          |
| `removeSaved`                        | Exact selected saved IDs/kinds                                                                                                                     | Remove selected descriptors under §11.2’s shared-reference check; delete physical bytes only after the last eligible reference. Active state is not replaced as an implicit side effect. |

Hiding a payload modal or changing tabs needs no server dispatch operation. Its held handle persists until an explicit continuation, cancellation, invalidating edit or runtime close. A client may discard only its local override draft without destroying the original handle. Reopening Edit input reads that same valid handle; it is not another `prepareAndHold` operation. The modal retains normal background inertness/focus isolation, so other panes are available after closing it.

### 10.4 Execution state machine

A run consists of one or more explicit execution intervals. Each interval has the requested policy, guard counters and terminal disposition; Continue opens another interval without resetting the run's accumulated receipts. A finalized run's captured intervals are immutable. Ordinary submitted follow-up stimuli can extend the current held episode intentionally; starting a new experiment or loading another origin finalizes the previous episode.

| State    | Allowed transitions                                                                                                                                            | Required publication                                                                                                    |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Ready    | Submit/Prepare/Run → Running; load/import/save/edit remain Ready                                                                                               | Current scenario, applied revision, no active dispatch.                                                                 |
| Running  | Matching pre-call gate → Held before stage; response/guard/stop boundary → Settling; real failure → Settling                                                   | Actual progress with any currently in-flight requests and pending next boundary.                                        |
| Settling | Already-dispatched attempts and accepted publication/commit work durably resolved/cancelled → Held or Ended; externally uncertain work → Held with uncertainty | Close new admission immediately. Do not wait forever or relabel an unknown external outcome as successful cancellation. |
| Held     | Continue/Step/Submit follow-up → Running; Save/Edit/Retain/Inspect remain Held; Stop/finalize/load → Ended                                                     | Exact stop reason, completed interval, pending native work, actual prepared handle if one exists.                       |
| Ended    | Read/retain/annotate; new experiment → new Run                                                                                                                 | Final disposition and actual completeness. No previously admitted result may change a replacement scenario.             |

A held pre-call stage is not a completed model call. A response boundary may complete useful work while leaving a physical action in progress. Advanced native manual pause invokes shared pause/cancellation semantics and results in an explicit held/cancelled disposition; Stop following is never a server-state transition.

Known domain/validation errors are typed results with code, message, field path where relevant, current revision, and permitted next actions. Examples include stale draft, unsupported field/capability, invalid payload/schema, missing evidence/checkpoint, no perception/opportunity, unavailable provider, exhausted run/capture allowance, storage failure, cancelled and uncertain external completion. Preserve the original draft and accepted prior work. Unexpected exceptions keep a diagnostic identity and a concise UI error; they do not trigger a paid retry or return fabricated empty results.

## 11. Persistence, loading and lifecycle

### 11.1 Small current-format records

Use native game tables for the active lab world. Add a small lab metadata schema/table group for scenario descriptors, runs/intervals, captured stages/artifact references, annotations and operation receipts. Keep lab metadata outside the native checkpoint table set so restoring a world cannot rewind spending, erase prior runs or revive a used handle.

Use ordinary indexed SQL rows for summary/searchable fields and ordinary bounded files under the lab data directory for large exact request/response/checkpoint artifacts. Store artifact byte length/content type and an integrity identity provided by the current storage owner. A run refers to a single captured payload artifact rather than copying it into every event/section. Do not add content-addressed version trees, global deduplication services, event-sourced world reconstruction or an archival vault.

Useful indexes are the exact workspace/scenario/run/time ordering, run/root/stage identity and actor/source identity already needed by the read paths. Search uses the relevant text fields under that scope before cursor paging. Add a specialized search service only after measured queries justify it; it is not a prerequisite.

Store captured collection summaries and exact source/item identities in these indexed metadata rows once, so paging a memory-candidate/option manifest does not repeatedly parse or scan its complete artifact. The artifact remains the exact retained request/evidence; rows are derived inspection data, never another writable mind. Update run counts and derived cost/completeness summaries when their source records durably change, deduplicating by the real attempt/receipt identity. A cost reconciliation updates only the affected aggregate; a status refresh does not rescan every interval or receipt. Rebuild derived totals at startup/recovery only when necessary. Use the existing PostgreSQL adapter's read lane for scoped SELECTs and explicit read transactions, not new lab-specific connection machinery.

Retained evidence has explicit completeness. A failed artifact write means the call/run cannot be described as fully retained. [CLL07–CLL09](../limits/cognition-lab.md#cll07) owns byte allowances, reservation and payload-chunk values. No age-based cleanup silently removes saved scenarios or retained runs. Remove/export/increase allowance are deliberate developer operations.

### 11.2 Whole-state save and restore

`GameSaves`/checkpoint streaming owns a coherent native capture, including complete required cold event/memory rows and installed dependencies, with its existing consistency/admission controls. Do not save only the in-memory hot `World` JSON or just the selected person's form. Do not hold the world mutation lock while streaming a whole export.

A new run automatically captures its actual applied origin once under §4.3; that origin includes applied edits not yet saved as a named scenario. Reset means explicit restoration of the selected run origin or named scenario start, with that destination shown; New uses the current initializer instead. A scenario save captures a reusable starting state plus settings/sequence. A checkpoint captures a specific continuation state including native clock/RNG/work according to current save ownership. Retain run stores evidence and metadata; a run without a checkpoint cannot resume a world. One artifact may be referenced by more than one lab descriptor when it is genuinely the same capture; no generalized versioning system is needed.

Removing a saved scenario/checkpoint/run removes only the selected descriptor and its references. Before invoking the native save/file deletion owner, use an indexed lab-reference lookup: retain the bytes while another descriptor, active run/origin or active read/write still needs them. Physical cleanup follows the last eligible reference and settled writer; release the corresponding stored-byte charge only after deletion succeeds. The current `GameSaves.delete` removes the file outright and does not know lab references, so the lab metadata owner must perform this check first. This is one scoped reference check, not a version tree or archival subsystem. Removing a named scenario must not break two retained runs that share its origin.

Load/import first validates the candidate's current format, structural integrity, installed definition/asset dependencies and native world invariants without destroying the active state. After explicit installation is accepted, close admission, settle/cancel native operations through their owner, rotate runtime/timeline authority and restore through the current service/save path. Existing save recovery behavior remains shared; the lab does not create another recovery framework. Return to a held state without automatic paid work.

Streamed capture does not imply streaming or constant-memory restore. The current shared load owner reconstructs complete history/candidate state and clones the installed world; memory and synchronous preparation grow with the saved state. Its pre-load recovery capture also retains an authoritative restore barrier. Qualify this complete path for imports and repeated comparison restores in the shared game/lab process. If that supported workload stalls the game, improve the shared load/checkpoint owner: move eligible candidate reads/preparation outside the mutation lane, process growing work in bounded/yielding batches where consistent, and revalidate at installation. Keep the native recovery and authority transition intact; do not add a lab loader or claim that an async function alone moves CPU work off the event loop.

Historical captures preserve their own identities when the active world changes. Client selections referencing replaced current entities clear or re-resolve only through exact returned identity; they never bind to a namesake. Old prepared handles remain invalid permanently. Pending provider receipts retain their original operational identity and settlement outside the rewind.

### 11.3 Game import and current-format bundles

Import from game is explicit. The gameplay side supplies a coherent point-in-time snapshot through its existing capture owner; the lab validates/copies that artifact into its own storage. Record origin and native capture time. The game continues according to its normal capture semantics. Subsequent gameplay edits never synchronize to the lab, and lab writes never synchronize back.

A bundle has a selected kind (scenario, checkpoint or run), current application format marker, metadata, native checkpoint/dependencies where that kind requires them, exact retained artifacts and completeness. Use the existing native format identifier and validation; do not invent independent backward-compatible versions for each field. Reject unknown/incompatible data with a direct reason and offer ordinary rebuild from the current initializer.

Export omits credentials, access tokens, live request controllers, arbitrary server paths and unrelated gameplay data. Imported source authority is validated against the present authenticated installation; saved account/permission claims never grant current rights. Validate archive paths/sizes with the established file/save owner and stream bounded data. Do not add a special in-app migration or import-repair wizard.

### 11.4 Browser and server lifecycle

A browser reload reconnects to the existing active lab and reads its actual status. It never replays the composer submission. If the last lab connection disappears during a running interval, request a safe lab hold, close new admission and settle/cancel existing work through the normal owner. Preserve a held prepared original in memory while the runtime remains alive; reopening shows Held before stage with no automatic dispatch.

Losing a browser does not pause the game runtime. A server restart loses process-local prepared handles; it restores only current supported saved/native state and captured evidence, returns held and labels interrupted work honestly. Existing receipt recovery may reconcile an uncertain paid call; this cannot automatically begin a new lab model request. There is no promise to resume arbitrary in-process callbacks from a saved file.

Closing/replacing the lab runtime unregisters its clock, stream subscriptions, navigation jobs and hook instances and drains its own resources once. Shared host/provider facilities are closed only by their normal process owner. Do not close a shared network client merely because the lab tab closed.

## 12. Client composition and stable interaction

Use the existing client app, router, shared light-theme design system, form controls and diagnostic renderers. A direct `/cognition` URL opens the developer shell before any PlayCanvas/game-scene initialization. It still authenticates through the normal server session. Avoid embedding the full game in a hidden frame or mounting a second UI framework.

The shell is a viewport-sized grid with fixed header/run strip and the feature specification's three columns. Each column separates fixed navigation/actions from a single primary scrolling content region. Use explicit grid/flex minimum sizing (`min-width: 0`, `min-height: 0`) so long content cannot expand its pane and push sibling controls away. Growing collections own their search and one list scroller; expanded detail replaces that region or opens the designated modal. A nested collection does not create a second embedded scroll well.

Extract reusable structured content from `diagnostics.tsx` into shared renderer sections, accepting a read-only captured view and explicit navigation callbacks. The existing diagnostic accordion navigation is not copied wholesale. Right-side top-level sections open by direct command; a selected memory/source detail replaces the region with a short breadcrumb and Back action. Full payload editing/search uses the focused modal. Feature/CLL05 owns exact geometry, type sizes and navigation budgets.

Keep state ownership explicit: current editor/drafts, composer drafts, run policy, current world subscription, captured selection/detail cache and comparison view are separate. Draft keys include workspace/scenario/timeline, subject ID and editor kind. Historical selection keys include run/stage/evidence identity. A shared generic selected-person object must not feed both current and historical values.

Use revision/status notifications to invalidate or update the necessary projection; do not broadcast every meter/current field as its own subscription. Cancel an obsolete read when search/selection changes. A late response may enter the correctly scoped cache but cannot replace the visible selection. Search updates the list beneath its stable toolbar; selection and scroll anchors remain stable where the exact row still exists.

Following live results is a view preference. Explicitly selecting history turns follow off. Incoming rows preserve the current scroll/focus and show a compact new-result indicator. Follow latest/jump is explicit. Streamed text may grow inside its content area but cannot resize header/navigation/composer controls. Long raw text must remain fully accessible via search/copy/export without mounting every payload simultaneously.

Do not optimistically pretend an edit committed or an action executed. Retain the draft until a durable accepted result; show a compact pending state and returned error. Native events or receipts are the source of accepted outcomes. Keyboard/IME behavior, tooltips, focus return and icon names follow the feature specification and shared UI handbook. Opening a details panel cannot capture the next composer Enter press or change actor/control selection.

## 13. Feelings, maintenance and extension boundaries

The lab exposes installed capabilities in their actual categories: bodily condition/reaction, private interpretation/appraisal, externally observable expression, derived consequences and behavior. Similar labels do not establish identical variables. Qualitative grief can retain cause, target, source and lifetime without inventing a global numeric grief axis. Several current reactions can coexist; use the installed aggregation/selection owner instead of summing a dashboard's sliders.

The separate [emotional-physiology feature proposal](https://github.com/Macrofold/OpenLegend/blob/codex/design-stealth-02-emotions/docs/projects/emotional-physiology-feature-spec.md) and [technical proposal](https://github.com/Macrofold/OpenLegend/blob/codex/design-stealth-02-emotions/docs/projects/emotional-physiology-tech-design.md) are external implementation dependencies. Their existence does not make all emotional mechanics installed on this baseline. The lab descriptor reports available, read-only, model-only or unavailable precisely. The directly controlled human-character interpretation decision SA-D01 remains that design's open decision; choosing an inspector/focal actor does not settle it.

Reflection, recall maintenance, consolidation, higher cognition and existing harness work keep their native scheduling, context, time/cost and source validation. Provide explicit inspect/advance-to-boundary/run-maintenance controls only for supported owner operations. An existing native owner may already have a developer trigger; use it. Where none exists, add a bounded explicit request to that owner instead of calling its model directly from a lab route.

A scheduled future operation is visible as pending and can be reached with bounded time/condition controls. A run ends without waiting for all recurring maintenance to become globally quiet. Effects that arise later link to the originating sources while preserving their actual later time. Restore/reset cannot leave a callback with the authority to publish into a new scenario.

This capability approach also handles unusual repertoire ideas: different sensory bodies, alternate expression, shared senses, borrowed forms, object testimony and looping worlds require installed native rules. The lab can author clearly marked model-only premises to explore a voice, but those experiments do not qualify physical/sensing/memory-continuity mechanics. See the [all-catalogue review](cognition-lab-repertoire-review.md#catalogue-coverage) and [episode cards](cognition-lab-repertoire-review.md#repertoire-derived-episode-cards).

## 14. Bounded work and performance

### 14.1 Capture admission

The lab must not trade fast ordinary decisions for unlimited diagnostic copying. One lab retention owner accounts for serialized lab metadata, checkpoint/artifact bytes and reserved in-progress writes under CLL07/CLL09. Admit every record-producing operation, including native-only stimuli, execution intervals, no-call outcomes, annotations and saved descriptors, before it creates retained work. Reserve the finite receipt/terminal-status space needed to finish already admitted work, so a full allowance cannot erase why an operation stopped. Existing native world history and authoritative spending records retain their own owners and limits; this is not a total PostgreSQL disk quota or a second financial ledger.

Maintain committed usage and outstanding reservations incrementally under that owner, reconstructing them at startup/recovery when necessary rather than scanning every file/run on each Submit. Release bytes only after the corresponding write cancellation or physical removal is confirmed. Reserve model capture before dispatch using the provider's actual request/response limits and [CLL09](../limits/cognition-lab.md#cll09), not a guessed character/token ratio.

For a candidate dispatch:

1. Validate and serialize the complete actual application request using the ordinary request owner. Account for its exact encoded bytes and original-versus-submitted artifacts when different.
2. Reserve the complete normalized application response using the selected route's enforced native response/transport bound. Expose that owning bound where necessary; do not assume a requested model output-token count is a byte cap. Optional provider-wire input/output artifacts are included only when the adapter actually exposes a bounded capture. Missing or unbounded optional wire capture is marked unavailable and does not block an otherwise valid ordinary Say or application-level retained request/response.
3. Add the bounded stage/receipt metadata and reserve that total against the interval/run's remaining capture capacity and the shared lab storage allowance. Already stored artifacts are counted once, and identical original/submitted envelopes can reference the same local artifact.
4. After explicit continuation/Submit, revalidate freshness and acquire the existing execution/cost admission. If capture capacity cannot cover the attempt, stop before provider dispatch with Capture capacity reached and preserve the current draft/run.
5. Persist completed or failed evidence and convert the reservation to actual serialized bytes. Release unused capture capacity only after its owning write is resolved. A partial/failed write retains its actual completeness and diagnostic identity.

This byte reservation is a small lab capture counter, not a second financial reservation system. It cannot grant model spending. Normal transport errors, response overflows and invalid schemas remain genuine failed attempts with whatever error/partial evidence exists; the UI must not call a truncated response a complete accepted model result.

Call, active-wall and simulation guards are checked before the corresponding new work is admitted. The run observer closes admission once any guard fires, without spinning another background call to explain that it stopped. Receipt reconciliation of already dispatched work can complete later under its normal owner and remains linked to the run.

### 14.2 Read and publication cost

List/search endpoints apply world/actor/run scope, search predicates and cursor/page bounds in SQL before hydration. This includes run children, stage manifests, field descriptors and dynamic choices; a detail endpoint is not permission to embed an unbounded collection. Project only visible summary fields and use exact indexed identity for a selected item, without walking prior pages. Match indexes to the actual search/order predicates and verify query plans through the production adapter on the qualified growing-history workload; a result LIMIT alone does not bound database work. Counts show maintained/actually recorded totals, or loaded results with more available when no full filtered count was obtained. Do not scan all history or enumerate omitted candidates merely to fill a badge. Source/detail requests load one selected artifact or native source, not all candidate memories. Payload chunks use the exact stored byte offset and identity; do not reparse/reformat a complete large request to return its next chunk.

Publish small revision/status/event summaries at existing native change boundaries and coalesce redundant render notifications. Field typing, hover descriptions, tooltip opens, historical selection and cost refresh are free of model work and world mutation. No per-character polling timer continuously computes all private context, and no whole-world JSON copy runs on every tick or keystroke.

Use one exact request snapshot per actual preparation. Other views reference its artifact/section identity. A record's source material is copied when needed to preserve exact past input, not repeatedly at every UI selection. Full native checkpoints occur at explicit scenario/checkpoint/required origin captures, never automatically before every call.

Keep list DOM bounded using the shared list/paging conventions and windowing only where a measured growing collection requires it. Retain the current selection and accessible focus across page updates. Do not eager-mount all payload renderers behind hidden tabs. Comparison renders bounded summaries for its selected runs and loads one requested detail at a time.

### 14.3 Shared runtime fairness

Lab control scopes are independent of the game's control scopes, but both use the same process and may compete for provider/CPU/database resources. Preserve existing cooperative yielding, native execution lanes, network ownership and request deadlines. Where an existing capacity owner is process-wide, both runtimes consume it; where it is runtime-specific, the lab has its own bounded instance. Do not duplicate an underlying provider allowance by cloning a counter.

Do not introduce a mutation lock across provider calls, human editing or slow client downloads. Ordinary checkpoint export releases the native lane after establishing its coherent snapshot. The existing authoritative restore/recovery barrier described in §11.2 is a distinct shared-owner operation whose duration must be measured and reduced there where safe; merely reusing streamed capture does not remove it. Required state reads use the owner's bounded snapshot/fence pattern. Avoid a shared lab/game mutex, and qualify synchronous candidate construction as well as lock duration because both runtimes share the event loop.

Measure ordinary game with lab closed, lab open/held, lab running and lab inspecting a large retained run. Include first run-origin capture, current-format import and repeated serial comparison restores with growing cold history. Report complete operation time, peak process memory, native-lane/event-loop delays, game responsiveness, query work and artifact bytes, separating preparation/capture/restore from remote inference. Increase unrelated actors/custom fields, intervals within one run and evidence items within one stage independently; opening the shell/header/page must not hydrate those entire populations. The proposed limits become qualified only through CL11 evidence; add workers or additional queues only for a measured shared-owner bottleneck.

Qualify the shared intake and participation seams through ordinary paths: keep the game's renderer closed, speak as the default player, and advance beyond the native absence/departure boundary while the declared lab participant remains active. Changing inspection must not change that set; an explicit departure must still take effect. Compare directed player speech in game and lab, including its exact speech/job association, an unheard target, ambient speech and a bystander focal actor. Force a supported and a freeform action as an autonomous character while the player controls someone else; verify exact attribution, unchanged controller and visible intervention. After a source is accepted, force a later response failure and verify the draft is not falsely unsent. Reopen a held request without dispatch, then invalidate it and exercise both a genuinely eligible native same-source retry and an ineligible case that must not repeat speech/action effects.

Qualify retained-data boundaries independently: grow unrelated character fields/options, intervals in one run and items in one stage, then open the shell/header, search, page and load one exact item without whole-collection hydration or repeated artifact parsing. Include actual production query plans and complete-caller work, not only returned page length. Near the retention allowance, mix native-only intervals, annotations and model captures; accepted work must retain its terminal receipt while the next unsupported growth refuses clearly. Remove one scenario descriptor shared by two retained run origins, then the final eligible references; remaining consumers must stay valid and bytes are released only after real deletion. Measure first origin capture, import and serial restores with cold history and concurrent gameplay as specified in §14.3; no unmeasured claim of constant-memory or nonblocking restoration satisfies CL11.

A useful episode is more than a pleasing isolated line: the participants remember the right evidence, have distinct priorities, can refuse or reinterpret, and can carry choices into actual later activity. The lab should make those interesting differences easy to discover and repeat. It must also make mundane waiting, calm company and a response that does not escalate into drama understandable and valid where the native design permits them.

## 17. Decisions, open dependencies and non-goals

The selected architecture, screen/current-history boundary, single-active-scenario storage, one-response semantics, exact stage editing, request-only historical rerun and current-format policy are decided. Their numerical defaults and usability/performance outcomes are proposed constraints to qualify, not unresolved choices that require a setup conversation before implementation.

Open external dependencies are explicit: delivered context manifests/omission evidence; native editors or history insertion that the existing owner does not yet support; actual unusual action/perception/world rules; installed emotional physiology/maintenance capabilities; and emotional design decision SA-D01 for directly controlled human characters. Their owning projects make those decisions and implementations. None requires delaying the isolated ordinary-speech slice or inventing substitute mechanics.

The lab does not include a second simulation, provider client in the browser, parallel scheduler, repository-wide multitenancy, simultaneous live comparison worlds, full world checkpoint for every call, old-code execution, schema migration/version compatibility service, generalized search/queue platform, immutable archive infrastructure or automatic extra evaluation calls. It provides the smallest shared seams needed to make the complete selected experiment workflow real and understandable.
