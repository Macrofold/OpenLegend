## The main recommendation

Aim to remove **whole categories of repeated work**, rather than keep making individual database requests or calculations slightly cheaper. The code exposes three particularly important patterns:

1. **One character's change can cause calculations for many other characters.** A creature checking its territory or reaching a movement boundary can make the game prepare everyone's bodily changes and future deadlines again.
2. **Saving can rediscover changes that the game already knows about.** The game can change one record, then walk a much larger retained collection to identify that record for storage.
3. **One experience produces work in several places.** A person's account of an event is represented for the live world, historical display and memory search. The command waits for much of that work before it finishes.

These are source-level observations, not percentages of total running time. They justify specific experiments. They do not establish which change will have the largest measured benefit, nor that all proposed changes should be combined.

**Start with the existing changed-record information, cheaper handling of genuinely new observations, and local recalculation of affected characters.** Then test the sight, material and display work that still repeats. Keep larger changes to saved information and continuous values as deliberate architectural options. If exact optimizations cannot provide enough headroom, the proposed changes to routine memories, background activity and visual detail give us explicit compromises to evaluate.

## What success means for the player

The player clicks to walk and sees prompt, confirmed movement while residents travel, work, eat, rest and react around them. Forty animals and the added objects and buildings remain meaningful parts of the scene. Requested 3× runs continuously through busy periods, without building up delayed game time or depending on a quiet sleeping period to catch up.

Fast animation, a fast average clock and a fast command response are different requirements. All need to pass. The existing [performance budgets](../maintainers/performance.md#acceptance-budgets) remain the owner of exact latency targets; the [original expanded-scene project](three-times-scene-performance.md) retains the long-play goal. A predicted walking animation cannot be counted as a confirmed move.

The current evidence does **not** establish the normally launched game's performance at the level of the best private prototypes. The recent near-3× graphical result used private changes, still had slow walking and contained a long drawing gap. Other recent private comparisons varied widely. Read these as clues to investigate, not a reliable capacity specification or a promise that stacking their percentages reaches 3×.

## Changes to gameplay are legitimate experiments

There are three explicit compromise families in this batch:

- **Memory detail:** first give optional recall an episode of routine work while retaining exact personal history and required reactions. A later, separately evaluated reduction in captured routine accounts could lose exact incidental chronology; important events and actual speech remain separately represented. Grouping without removing other work can add cost, so even the first slice must earn its place.
- **Background detail:** a supported quiet activity progresses through meaningful stages, with detailed simulation restored before an interaction. Incidental paths and encounters can differ. Being off the player's screen alone does not make another character irrelevant.
- **Visual detail:** distant cloth and small models use cheaper animation. Movement, reach, collision and the world's elapsed time do not change merely because rendering is cheaper.

The continuous-value proposal also requires an explicit arithmetic decision: a new calculation can change rounding or threshold timing even if its formula looks equivalent. That difference must be specified and tested rather than hidden as implementation detail.

These are proposed choices. This document does not adopt them or weaken the accepted feature specifications. Fictional policy belongs to the selected world; efficient scheduling, storage and rendering belong to their existing engine/server/client owners. Identity, permissions, privacy, truthful outcomes and acknowledged durability remain protected.

## How we will avoid accumulating regressions

Each candidate starts with one causal question and a recorded expected reduction in work. Under the current authorization, check each changed operation for correctness and compare the combined running game in at most five ordinary full observations before compromise experiments. Include the costs added by indexes, caches, queues, allocation and recovery. Compare the combined build again after accepted changes.

A result can be **adopt**, **keep investigating**, **reject**, or **inconclusive**. “Fewer requests” and “lower native CPU” are useful findings, but neither is an automatic pass. A gameplay compromise needs both a performance result and an honest account of what became less rich or less precise. The full procedure and the limitations of the old results are in [evaluation instructions](performance-overhaul/evaluation.md).

No finite source proof or benchmark can guarantee “performance cannot possibly get worse.” The achievable discipline is to remove demonstrably unnecessary work, test the affected workloads, reject unexplained regressions, preserve a reversible implementation path and report the remaining uncertainty.
