## 1. Scope, decisions and existing behavior

The primary proof is the same-account sling round trip; the second is the already supported manufactured-cord → woven-container dependency. A third physical journey lets a maker leave a method sheet which another person independently learns and uses. A recipient-account round trip adds free distribution without a marketplace. Each ends in a useful ordinary action. See [feature §15](world-creation-feature-spec.md#15-dg12-expansion--a-useful-invention-follows-its-creator) and [bundled rules](../worlds/base/invention-reuse.md) for player intent, contents, tuning and acceptance.

Selected design decisions:

| ID | Decision and consequence |
| --- | --- |
| LIB-D01 | One configured operator library, using a current PostgreSQL repository and explicit trusted installation/account mappings. Each existing world keeps its own authority, simulation writer and database. No new public identity service or arbitrary-URL transport. |
| LIB-D02 | One supported recipe root and complete finite dependencies per retained artifact/release; exact supported native families/policies must already exist in the destination. The transfer cannot install code, laws, remote media or arbitrary item effects. |
| LIB-D03 | Install-only admission uses `installRecipe` plus the new imported-origin branch and local import receipt. It does not call `admitDeclaration`, fabricate an inventor or teach a character. Existing genuine invention and creator recipe Apply retain their present semantics. |
| LIB-D04 | Unchanged transfer, explicit trusted reference binding and a new adapted method are distinct. Recompile every installed candidate under the exact destination family. Source compiled outputs are comparison evidence, never execution authority. |
| LIB-D05 | Actual player/NPC learning stays with `learnRecipe` and delivered record inspection/learning. The maker's new method-writing activity consumes supplies and time. Import has no physical result unless a separately reviewed creator endowment explicitly creates one method sheet. |
| LIB-D06 | Same-author reuse needs sufficient retained content/use authority; release additionally needs the actual applicable redistribution grant and publisher mandate. Existing terms can support the first recipient proof. The application creates no default licence, compulsory contribution terms, complete-free-world badge or guessed coauthor agreement. |
| LIB-D07 | Library artifacts/releases, acquisition and account authority are operational records outside gameplay rewind. Installed local definitions, their import provenance, actual knowledge, physical records and active work are gameplay state. |
| LIB-D08 | Optional native work is demand-driven and bounded. Browse/reopen/search/exact reuse makes zero model calls. No tick scanner, automatic updates, automatic dispatch retries, NPC library access or generated executable text. |

## 2. Ownership and authority before data flow

### 2.1 One library on the configured operator

Select one existing OpenLegend installation as the operator library endpoint. Its current PostgreSQL database owns library operational tables through a new `InventionLibraryRepository`; it does not need a new deployment framework. Other configured source/destination hosts use a narrow server-held client to that endpoint. A single-host setup calls the same repository/service in process. A world may be offline while its already retained library artifacts remain available.

Configuration supplies a stable `operatorLibraryId`, library installation identity/address, trusted installation credentials, and explicit installation-account ↔ library-account mappings. Reuse the existing root HTTPS/loopback-HTTP address validation and server-held intake credential pattern. Never accept a client/model supplied connection string, remote URL, filesystem path, arbitrary issuer/account mapping or service credential. Reconfiguring a mapping/trusted installation advances its generation and fences new work; it does not rewrite historical credit.

Authenticate the account on the library endpoint using the existing verified identity owner. `LibraryScope` contains authenticated library account, login session identity/revision and library registration generation; it has no character or world permission. A host proxy may delegate one exact account-scoped read/write only through its configured mapping and current source account session, binding operation kind/body/registration generation. The library never accepts an unverified `accountId` in place of that scope. Account-only library routes occur before the current HTTP requirement for a world character; no empty actor fallback.

An account can list its own retained entries without source membership. A reference-only entry yields only retained permitted metadata until a current source read succeeds. Lists use approved public origin metadata or **Private source world**; they do not batch-fetch private source-world names. A deliberate **Open source** read uses the source's current permission fence, and no success at the library makes that source read permitted.

### 2.2 Authorities are separate predicates

| Operation | Native authority and boundary |
| --- | --- |
| Read own library / favourite / private nickname | Current library account session and ownership of this entry. No destination world grant required. |
| Capture contribution metadata | Authenticated configured source installation, exact committed source contribution identity/body and the server-derived owner accounts. Browser/model authorship claims are invalid. |
| Keep a reusable copy | Current account entitlement to retain this contribution plus current authorised access to the exact source closure or another already permitted retained copy; complete grants and storage admission. Historical ownership alone cannot reveal a private dependency. |
| Prepare for destination | Current destination `create` and `inspect`, exact library-copy entitlement, configured library/host mappings and supported family/role permissions. Preparation grants no world mutation. |
| Install reviewed copy | Existing creator authoring authority, applicable current player-origin invention policy, exact review/plan, destination timeline and registration, current pins/rights and atomic world publication. Do not invent a new ordinary-player lock override. |
| Write a physical method sheet | Embodied actor's current play/control admission, known exact method, installed writing activity, actual tool/material/custody/body/work eligibility. Account ownership of the method is irrelevant. |
| Learn/craft/use | Existing actor-owned native commands and current world knowledge/resource/access rules. Import or record custody is not a knowledge command. |
| Place an authored teaching copy / initial knowledge | Separately selected creator operation, exact affected location/actor/quantity and current world/creation authority. Defaults off and has a distinct receipt from definition installation. |
| Publish / acquire a free release | Current library account, eligible exact artifact, actual publisher mandate and redistribution terms; the known named recipient's own account/session performs acquisition. No recipient world's authority is inherited. |
| Unpublish / delete retained bytes | Current publisher/retainer authority for that exact record and current dependency/reference checks. No installed-definition mutation. |

World creator authority and historical account ownership are not interchangeable. Characterless library access is useful; the first destination installer keeps the current creator-workspace audience and does not require a new characterless world editor. Ordinary player-directed authoring remains under its existing lock; autonomous NPC invention remains independently locked/funded. Imported definitions never relabel a player delegation as an autonomous NPC request.

### 2.3 Exact boundaries across hosts

No transaction can atomically cover source, library and destination databases. Each accepting owner writes a durable operation/receipt before acknowledgement. Source current authority is checked before its one exact dispatch; destination/library current authority is checked again at their own commit. Revoking source permission stops subsequent dispatches but cannot retract an operation already accepted under the earlier exact dispatch. The UI must not promise stronger cross-database revocation than exists.

Before an install dispatch, the library issues one exact server-held `LibraryInstallAuthorization` through its own transaction: account, exact destination operation ID/body fingerprint, artifact SHA-256, destination installation/world/timeline/registration, approved plan SHA-256, applicable grant versions, authorization ID, issue time and a 60-second real-time expiry. Only this one exact reviewed install is authorized; it is not a reusable account/world grant. Its authorization ID and body are immutable and uniquely attached to that destination operation. The destination persists the authorization ID in its existing operational authoring receipt with a unique library/authorization constraint, so a different operation ID cannot replay it; receipt lookup remains read-only even if gameplay later rewinds. The destination receives/verifies it through configured trusted transport and rechecks its own current authority/pins plus this unexpired exact authorization at commit. Library withdrawal before issuance prevents the new dispatch; withdrawal after issuance does not pretend to atomically retract that already accepted one-operation authorization. Grant evidence requiring stronger immediate cross-host revocation is unsupported by this profile. Status reconciliation remains possible after expiry under current read authority, but cannot execute an expired operation.

Use explicit operation IDs and body fingerprints, current registration generations and bounded existing host-work/HTTP deadlines. A repeated same operation/body is read-only receipt recovery. Reuse with changed body is an idempotency conflict. Unknown acknowledgement remains uncertain and blocks replacement mutation until exact receipt reconciliation proves completion/refusal/absence. There is zero automatic redispatch of a user retention, install, publication, acquisition or paid adaptation. A fresh user operation after proved non-admission needs current authority and, for install, fresh valid review. The deterministic source contribution outbox has the narrower delivery exception in §3.4: repeating its exact minimal historical metadata/body cannot grant rights or mutate gameplay.

## 3. Data contracts and one source of truth

All new records use strict versioned schemas and application-allocated safe IDs. Reference tuples include operator/library/source installation, source world and definition kind where relevant; display names never bind. Use unambiguous tuple encoding and existing identity validators. Preserve exact native pins; `artifactSha256`, `bodySha256` and `reviewSha256` are new 64-lowercase-hex fingerprints computed server-side over canonical UTF-8 JSON, never overloaded native `digest` fields.

### 3.1 Portable artifact

The current-format file is canonical UTF-8 JSON with extension `.ol-invention.json`, media type `application/json`, format `openlegend-invention-v1`. No archive, compression, binary, base64 attachment, external fetch, embedded HTML or executable text. Raw transport and decoded definition/manifest text each fit WC-L07. Admission also limits parsed nesting to 32 levels and JSON values/keys to 16,384 total nodes before recursive validation; count these with an iterative scanner. These are operational parsing limits, not allowed arbitrary content schemas. Parse only after the raw bound; account decoded UTF-8 strings/objects as well so escaping cannot conceal expansion. Reject duplicate JSON object keys, unknown schema keys, invalid numeric values, unsupported formats and unsupported required dependency kinds. Text remains inert display data.

```ts
interface PortableRecipeArtifactV1 {
  format: 'openlegend-invention-v1';
  operatorLibraryId: string;
  artifactId: string;                 // application identity, never a caller authority
  originContributionId: string;
  root: ScopedDefinitionPin;          // kind: 'recipe', source installation/world + native pin
  definitions: PortableDefinition[]; // complete bounded set; exact source bodies
  edges: RequiredEdge[];              // derived by trusted kind adapters, verified on import
  presentation: ApprovedMetadata;     // name, purpose, permitted credits/origin, native appearance
  grantReferences: ExactGrantRef[];   // actual terms/mandate versions; no bearer credentials
  ancestry: ExactArtifactRef[];        // zero or one direct parent in this selected profile
}
```

After bounded parse and iterative depth/node checks, require a canonical round-trip identical to the supplied artifact bytes before recursively validating it. This also rejects duplicate keys, noncanonical unknown formatting and ambiguous encodings without relying on a second permissive interpretation. The repository stores the canonical bytes and computes `artifactSha256` outside that body; no self-hash field circularity. A release envelope carries that fingerprint, release identity and exact immutable release metadata alongside the artifact. A bare own-retained artifact references its existing library artifact identity; it cannot forge a free release. Uploaded files from this operator are re-resolved against the authoritative exact artifact/release/grant records. Unknown origin or changed bytes remain an unsupported local file with a refusal, not a new trusted publisher. A future cross-operator verifier needs its own selected identity/rights protocol.

`PortableDefinition` names one supported kind and source pin plus the full native definition/candidate bytes needed by that adapter. The first allowlist is recipe, its owned output item, native material/reference item, selected recipe-family definition and selected item-handling policy. Recipe-family and policy entries are required support references/comparison bodies: the destination must already install the exact supported implementation. They are not requests to register a host. Manufactured output entries preserve the producer link and positive material interface. No live object, invocation, person, memory, goal, claim, account grant, payer secret or world checkpoint is included.

`RequiredEdge` distinguishes actual dependency from an owned output's backlink. A recipe includes its output payload; `output.recipeId` is a reciprocal ownership link, not an instruction to recurse back into the producer as a dependency. The material dependency graph still rejects a true production cycle. A typed edge's kind, role, exact source/destination pin and requiredness are verified from the source candidate/family/compiler; an uploaded edge table cannot omit something the compiler reads.

Index contribution-owner lookup by `(account_id, contribution_id)`; library entries by `(account_id, sequence DESC, entry_id)`, keeping bounded permitted search text in the entry summary; artifact refs by `(artifact_id, kind, source_scope, definition_id, version, native_digest)`; reverse retained/release/operation references by artifact ID; operation receipt by its complete unique key; pending source delivery by status and stable sequence. Store complete identities in constraints even if an index can safely omit a single-valued operator field under this repository's constraint.

Library names/purposes retain the selected recipe schema's 80/700-character bounds; private nicknames are at most 80 Unicode code points, and permitted credit labels at most 120. At most 65 historical owner-credit entries follows the existing 64-world-creators-plus-player attribution envelope; the selected same-author proof uses one. Library preferences never rewrite those historical accounts. All decoded metadata, grant references and public notice text count under the one-artifact envelope rather than bypassing it as an attachment.

No new library data belongs in `WorldState.recipes` until actual installation. No favourites, account licences or paid records enter a gameplay save. No whole source declaration receipt is copied into the destination to impersonate local invention. No unbounded growth collection is put in every `GameView` or authoring prompt.

### 3.3 Imported local provenance and derivation

Add `ImportedRecipeProvenance` to the recipe union with `source: 'imported-library'`, local `importReceiptId`, exact `artifactRef`, source scoped root pin and direct binding/adaptation ancestry reference. It contains no local inventor actor or fake `authored-world` profile. `validateInventionAttribution` branches by provenance and verifies that a local import receipt accounts for the exact recipe/mapping, while the existing actor/authored branches keep their current checks.

When exact candidate mechanics already exist locally, return the existing local recipe without changing its original provenance or creating new invention ownership. The import receipt may record a legitimate acquisition/use association to that method. New local IDs from remapping are application-allocated and collision-checked through the existing owner; they do not alter the immutable source artifact. Preserve source→local mappings in the receipt. Recipe candidate/compiled output digests and pins are recomputed after any mapping because local reference identity participates in meaning.

A creator-side adaptation carries parent artifact and exact candidate revision, not `derivedFrom` pointing to a foreign recipe ID which the present actor-invention validator cannot resolve. A later **genuine local actor invention** derived from an actually known local imported method may use the normal local `derivedFrom`; it gets a real new actor receipt only if that ordinary invention action actually occurs. Cosmetic account nicknames never create either kind of derivation.

### 3.4 Contribution capture and reconciliation

On each successful native `admitDeclaration` commit, append a small operational source outbox entry from the committed receipt and server-derived attribution. Do not wait for the library, buy model work or copy the whole closure in that world transaction. One source worker selects at most 32 pending identities in a batch, resolves only those bodies, sends exact entries sequentially through existing finite host-work admission, and marks delivery only after the idempotent library receipt. It yields the ordinary work lane between batches, stops on unavailable admission/service, and starts on committed-outbox/startup/resume signals rather than a world-tick poll. An uncertain metadata delivery first reads its exact receipt; this derived metadata outbox may redeliver the same stable identity/body after proved non-admission on a later recovery signal, but may never widen its owner list/body, grant rights, buy generation or install content. User retention/import/release operations retain zero automatic redispatch. Source/library downtime leaves **Library sync pending** with actual source evidence; the admitted invention still works.

For prior contributions, run one explicit cursor-based reconciliation of retained canonical source contribution records. Save source cursor and coverage, page the owning source reader in at most 32-record batches and publish idempotently under that same worker. New committed entries continue through the outbox. A library list may say **This source's older contributions are still being indexed**; it cannot show an empty list as proof no older contribution exists. Do not perform a full world-history scan each time My inventions opens. A restored old gameplay save does not delete previously captured contributions or reset the operational cursor; reconcile by stable source contribution identity/body, not current simulation time.

Reference-only entries do not promise unavailable source bytes. Source root/dependency versions still required by its valid contribution/history remain under the existing definition-retention owner. Keeping an independent copy must resolve and durably retain every eligible dependency now. A missing/retired unretained source, absent grant or unavailable source read yields a precise reference-only/blocked result, never a synthetic reconstruction from prose.

## 4. Retain, close dependencies and bind

### 4.1 Retention algorithm

1. Authenticate the account and selected exact contribution/artifact. Resolve current source read/retain authority or an existing retained provider. Capture the source's relevant exact pins and permission/registration revision; private failures use a generic permitted missing-dependency explanation.
2. Start the existing bounded host-work preparation outside world/library writer transactions. Use the recipe adapter's required references, selected family and item-handling policy. Maintain a visited map keyed by complete scoped definition pin and a visiting stack keyed by causal producer identity. Count every distinct reference and decoded payload byte before admitting more work.
3. Resolve each required item/material/family/policy exactly. For manufactured inputs, require the original producer/output link, producer family/material interface and positive consuming-role proof, then traverse its actual native dependencies. Do not broaden the current native-only producer or other family's material policy.
4. Validate reciprocal output links without treating them as causal cycles. A true cycle, missing pin, changed meaning, unsupported kind, private/ungrounded dependency, work exhaustion or >32-reference/>1-MiB closure fails completeness. Never activate/retain a partial object labeled complete.
5. Canonicalize the complete artifact, compute its SHA-256 and run independent native validation. Assemble source credit, approved safe metadata and actual grant references separately from mechanics. Recheck authority/current source pins before admitting a new source copy; immutable existing retained bytes need their own current entitlement check, not live source membership.
6. In one library transaction, lock the account operation/quota row, check same-body idempotency and current grants, verify exact complete bytes, reserve actual admitted storage, insert/deduplicate the artifact and account retention, and write the receipt. Return **Retained copy** only after commit. Lost acknowledgement recovers this exact operation.

Copies share exact bytes where valid, while the account's independent entitlement remains explicit. Quota accounting charges the operator's actual retained unique bytes plus record overhead according to its current storage owner, not the UI's hypothetical total; account-level allowances, if configured, use the same transaction. Do not count a shared blob twice or treat an absent configured allowance as unlimited.

### 4.2 Destination binding preparation

`prepareRecipeImport(destination, artifact, explicitBindings)` is a pure adapter operation over a read-only destination view and already permitted retained bytes. It returns complete proposed local candidates, the source→local mapping, exact host/policy/native pin requirements, compiled facts/deltas, unsupported requirements and bounded work demand. It does not know account credentials, save the world, schedule actions or call a model.

Process producer recipes before consumers. Reuse exact installed native/family/policy pins; allocate missing recipe/output identities once for this plan. Existing `installRecipe` remains the final compiler/identity deduplicator, so preparation and commit must agree on allocation/deduplication. Extract its matching-ID preparation into a shared helper if needed; do not reimplement a divergent client or import compiler. Recheck candidate/ID collisions at commit and reprepare on a changed meaning.

Explicit binding supports only ports declared by the selected trusted family: direct ingredient roles and declared parameter definition references. Expose required role, semantic interface/version, units, accepted native/manufactured origin, bounds, binding phase, required/default status and contributed dependencies from that owner. The first profile permits installation-time reference binding; it has no invocation-time arbitrary callback or runtime-rebind port.

For the first native-alias proof, use an installed world-owned `native-material-alias-v1` descriptor containing exact scoped source item pin, exact destination item pin, exact allowed consuming family pin, role/declared-reference port, and adapter implementation version. Both items must be native (no `recipeId`, manufactured certificate or producer output). Its deterministic proof requires complete definition equality after removing only `id`, `name`, `description` and `icon`; every other field, including version, material/effect/custody/packing/consumption/characteristic metadata, remains equal. Names/appearance may differ and are shown. No arbitrary ignored-field list or new comparator function can come from the uploaded artifact. Run ordinary family compilation, current material eligibility, any real resource-source prerequisite and full output/dependency validation after remapping; the comparator alone never admits a candidate. A broader semantically different adapter is unsupported until separately implemented and qualified. This compares relevant material/consumption/handling behaviour under the real family, not just tags or `unitsPerItem`. Family/policy implementation versions remain exact; missing proof makes the candidate an explicit adaptation or unsupported case. The baseline simple round trip needs no alias: both worlds use the exact same native family/material pins. The contrasting binding qualification installs an explicit alias adapter in the test world's authored profile; it cannot be supplied by the uploaded artifact or inferred by a model.

For a material-changing adaptation, reuse the existing recipe editor and supplied-candidate native path. Save one new draft revision referencing the retained parent artifact, select permitted destination materials/parameters, recompile and derive a fresh closure. Show actual capacity/output/work/material differences using family-authored units. A family may reject the change; leave the original and the last valid draft intact. Unsupported physics is not represented as an unimplemented parameter. Do not silently select a named recipe from a canned catalogue when the user asks for a new invention.

### 4.3 Exact review and atomic installation

Add a `recipe-import` authoring adapter/kind beneath `world-authoring-kinds.ts`, consuming an immutable retained artifact reference and bounded explicit bindings/adaptation reference. It uses the same `WorldAgentStore` session/draft/check/plan/review operations. Its payload is a reference plus bounded choices, not the complete 1-MiB artifact forced through the existing 24,000-byte candidate or 28,000-byte tool-argument ceiling. Those limits remain unchanged. Exact technical inspection can page/read the retained artifact under separate library authority.

The plan records destination world/timeline/registration generation; current `create`/`inspect` and applicable player-policy revision; artifact SHA-256 and entitlements/grants; draft revision; family/policy/material pins; adapter versions/bindings; actual additions/reuses; local allocated IDs; compiled result fingerprints; actual storage/work demand; and review acknowledgement identity. The later one-use library authorization binds this exact approved plan, rather than broadening its permissions. The review summary leads with purpose, effects and remaining character prerequisites. Technical fields support inspection but are not the main button labels.

## 6. Immutable free releases, rights and deletion

### 6.1 Grant evidence without inventing terms

The service accepts only rights/mandate evidence established by the operator's selected actual agreement/component notice or explicit rightsholder-controlled grant process. It records the exact terms version/fingerprint and scope. A plain-text claim inside a package, an AI confidence score, current world-creator role or zero price is insufficient. The first same-author proof uses one account as inventor and sole world creator; every dependent component still needs its actual retention/use basis. A free release additionally needs sufficient redistribution/recipient-use permission for each included component. Modification/binding scope is checked for an adaptation; mere compatible operation does not imply modification rights.

The technical operation `recordExistingGrant` is an operator/rightsholder-authorised administrative intake of already selected evidence, not an ordinary model/browser permission grant. Its schema records issuer, terms document, covered exact component/version set or explicit future-version scope, allowed operation set, permitted recipient/operator scope, effective/cessation rules and publisher mandate. The application rejects a supplied evidence issuer not authenticated/authorised for the covered contribution. Additional coowners require an actual applicable mandate; deduplicating owners cannot choose it. Default unknown operations to ungranted, not false legal conclusions about unrelated uses.

Current repository first-party notices may be recorded by exact component path/revision/notice under `LICENSING.md`; independently created world data, linked art and third-party assets require their own applicable evidence. The design adopts no new legal text or universal licence, makes no legal determination about arbitrary uploaded content, and grants nothing by being merged. D44/INV-8.3 remains open for complete-world free-use contribution terms. If selected proof content lacks sufficient existing evidence, mark its release **Needs grant** and obtain that actual grant before the dependent release qualification; no engineering workaround fabricates it.

### 6.2 Publish, acquire and unpublish

**Prepare release** resolves one exact retained artifact, current publisher/mandate/grants and one recipient from the operator's explicitly permitted known-account mapping. The picker shows only allowed known recipients and stable account identity; it is not a public account-search service. The preview includes purpose, exact version, whole closure count, readable materials/behavior, approved public credits/origin, zero package price and granted recipient operations. Public metadata must be separately approved safe values; do not copy private world names or inventor background by default.

**Publish exact release** rechecks that preview, grants/mandate, recipient and storage inside the library transaction. Insert an immutable release body plus its initial publication-control revision and exact receipt. Sharing is by copyable direct link or downloaded current-format file. The operation sends no message and creates no acquisition. No blanket bearer token in the link grants any account the copy: an authenticated selected recipient must acquire it. A future public release changes audience policy explicitly rather than disabling the recipient predicate.

**Acquire** checks the current recipient session, exact release/artifact/grants and current publication-control revision in one library transaction. It creates the unique acquisition plus retained entitlement and receipt atomically. No destination world is read or changed. Same release/account acquisition returns the existing result; another account is refused. The recipient later prepares an installation under its own destination authority.

**Unpublish** uses expected publication-control revision and publisher authority. It prevents a new acquisition committed after unpublish. Acquisition and unpublish serialize on the same release control row, making the winner unambiguous. An already committed acquisition remains recorded and follows the actual acquired terms; it is not rolled back merely because discovery closes. Exact acquired-copy reads follow that entitlement, not current publication state. UI distinguishes **No longer available to acquire** from **Your acquired version**.

Later versions have new release identities/fingerprints and explicit parent lineage. No background synchronisation or Update all. Preparing a later version runs the same current destination review and may produce an additional distinct recipe; a live replacement or retirement requiring state migration routes to INV-5. The first consumer is additive and cannot silently remove old items, recipes, knowledge or active work.

### 6.3 Retention and removal

Separate preference changes, account-copy deletion, public availability and live-world definition removal. A favourite/nickname write uses the entry preference revision and changes only that account view. Hiding an entry leaves historical ownership and acquired terms intact. A request to delete retained bytes examines current artifact references from account copies, published releases, acquisitions and accepted unresolved operations in one transaction. Deleting one account's unneeded entitlement does not delete bytes required by another. Deleting the last required copy is refused with permitted dependency counts/explanations or requires the existing independently authorised retention/removal process; do not implement an unreviewed cascade.

Retained source versions do not disappear when source world membership closes. Newly resolving reference-only private bytes does require current source access. The source's ordinary deletion/unpublish event is distinct from exceptional operator rights/privacy/security action. Record an exceptional restriction explicitly and honour its actual scope at future read/dispatch boundaries without rewriting past receipts as if the action never occurred. Existing world retirement/operating policy handles installed content; the library cannot retroactively edit a live world or promise legal irrevocability.

Account permission/source-redaction checks are separate from mechanics cache and cannot inherit a cache's old authority. Source closure is computed only when needed; delete/reference counts use explicit indexed membership rows.

Operational storage requires a configured positive finite byte allowance from the current operator storage profile; absent allowance disables new independent retention/publication with a readable reason, not ordinary play or already-installed execution. No fixed lifetime invention-count/automatic deletion is introduced. Retained blobs, grant/release/account metadata and pending records all count under their actual owning storage admission. Configuration can grow after complete-caller capacity qualification; never loosen WC-L07 or existing HTTP/SQL/native-work bounds solely to make an oversized case pass.

Before LIB09 completes, measure the actual page/search/detail/retention/preparation/commit/restart path with empty and growing account histories, an absent match and a common match, many unrelated accounts/worlds, shared dependencies, the maximum admitted closure and over-limit refusal, simultaneous ordinary world commits, pending delivery/recovery and many old terminal operations. Include p50/p95/p99/max, timeout/error rate, SQL plans/rows, bytes, CPU/allocation/RSS where relevant, writer waits, cold-start versus genuinely warmed qualification, configuration and workload identity. No universal latency/population/storage capacity is selected by this paper design; results must show the optional consumer does not create unbounded routine work or mislabel incomplete results.

## 13. Open decisions and release boundaries

No unresolved game-design choice blocks implementing the selected bounded consumer. The world-owned sheet rule, initial families, same-operator topology, additive import, voluntary-record path, recipient audience, formats, exact state boundaries and implementation order are selected above. Existing compatible grants can support the free proof; sufficient actual evidence is an admission prerequisite for each particular artifact/release, not a licence invented by this design.

D44's general contribution/reuse/complete-world free-use terms and public naming remain owner decisions. Broader coauthor mandates/ownership transfer, commercial catalogues/revenue, public recipients and cross-operator trust remain with INV-8/PACK. Larger storage/query/closure capacity, broader family semantics and genuinely new worlds require their actual owner/qualification. Preserve these as open routes; do not label ND12's whole long-term ecosystem implemented or all generic EWF11 construct cases designed by this one recipe consumer.

Fun, balance and autonomous choice quality need evidence after implementation. Native success can show the bag carried a real prize; it cannot prove that another person cared or that a player wants a larger library. If the complete first round trip requires a long interview or produces no useful new option, improve the chosen practical setup/affordance using the existing family rather than add folders, rankings or forced resident admiration.
