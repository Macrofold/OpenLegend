## Why this batch emphasizes architecture

The concrete current path is:

1. A host tick, player command or character decision obtains its existing ordered world-change ownership.
2. Native execution prepares and updates bodily state, actions, movement and permitted observations. Some local changes discard preparation shared by many participants.
3. Publishing the world materializes pending changes and completes an immutable snapshot.
4. A synchronous command save prepares record differences, saves current data and personal history, updates searchable experiences and related outcomes, then completes the transaction.
5. The service installs/confirms the command; public projection, patch creation, delivery, client application and drawing have their own work and schedules.

This explains why several individually sensible changes can fail to improve walking. A command can still wait for saving after CPU work becomes cheaper; a native tick can still wait behind a command transaction; a larger immutable collection can become more expensive as the game creates items. A high average draw rate can coexist with a rare freeze. These dependencies are visible in [world-service.ts](../../apps/server/src/world-service.ts), [store.ts](../../apps/server/src/store.ts), the native kernel and public view owners; the precise remaining shares require future measurement.

The main design bets therefore remove multipliers or shorten a demonstrated dependency:

| Cost shape                                                                   | Candidate mechanisms                                                    | Where the gain may disappear                                                                                                      |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Unrelated participants × mechanical recalculations                           | Local dependencies, prepared effects, active/due subsets                | Almost everyone changes; dependency maintenance becomes larger than avoided work.                                                 |
| Retained collection size × local saves/publications                          | Exact changed keys, stable order, persistent entity storage             | Full replacements, lookup overhead or incomplete lineage force frequent rebuilds.                                                 |
| Routine events × witnesses × stored representations                          | One personal account, append-specific reconciliation, explicit episodes | Required distinct witnesses remain; read indirection or reduced memory usefulness outweighs savings.                              |
| Visible entities × updates × viewers                                         | Dependency-local sections, small field changes, dirty scene work        | Dense motion, broad permission/geometry changes or bookkeeping invalidate most results.                                           |
| Thinking characters × host ticks; large-context trimming in verified callers | Affected-character intake and incremental context size accounting       | Many genuine thought opportunities, required large contexts or provider latency dominate; an unused helper's cost does not count. |
| Many indexed writes before a command can finish                              | Deferred derived search; ultimately a durable transition journal        | Background backlog, immediate-read overlays, recovery or total storage throughput become limiting.                                |

These are hypotheses about work, not benchmark results. No percentage speedup is predicted, and no total is formed by adding old measurements.

## Engine, world and recovery boundaries

- The domain remains deterministic and free of I/O and wall-clock decisions. Actor-local work is still coordinated against one coherent world time and saved randomness.
- Derived indexes, changed-key records and cached preparation accelerate existing authority. Their lifetime follows the actual mutation owner; incomplete coverage rebuilds rather than guessing that nothing changed. Drafts are not immutable cache keys.
- The world chooses what routine experiences can merge, which activities support coarse progression and any changed biological timing/precision. Generic engine code must not hardcode the stag, hunger, a particular work recipe or an “NPCs matter less” rule.
- Every public or model-bound result retains exact observer/perspective permissions and freshness checks. Moving work after commit must not delay revocation or disclose cached private facts.
- A new runtime representation updates current readers, writers, validation and restore together. Apply the [development save policy](../../AGENTS.md#development-save-policy); do not add old-format compatibility as part of these proposals.
- A background search queue or transition journal needs bounded growth, backpressure, cancellation/recovery and truthful incomplete states. No command may be acknowledged as durable merely because it was queued in memory.

## Ideas not promoted to a new primary task

| Idea                                                                                   | Reason to hold or narrow it                                                                                                                                                                           |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Remove all animals, needs, sightings or bystander memories                             | Useful ablations, poor finished gameplay. The new cards replace specific repeated work or explicitly define a smaller compromise.                                                                     |
| Align quiet wander times, freeze worlds earlier, batch more intervals indiscriminately | Prior trials failed and at least one causal premise was disproved. A retry needs a different verified mechanism, not a new label.                                                                     |
| Remove indexes wholesale or just make their keys smaller                               | Lower write work can create growing search work. Index changes belong inside a complete read/write design, not an independent promise of faster saves.                                                |
| Group every ready resident decision into one save                                      | The private comparison removed many saves without a dependable whole-game gain. Real AI results may not arrive together; added waiting/fairness matters. Revisit only for measured concurrent demand. |
| Omit decision completion details                                                       | The diagnostic lost useful information and did not demonstrate dependable benefit. Consolidating complete information at its owner is a separate possible refinement, not permission to drop it.      |
| Another generic worker or more asynchronous syntax                                     | Database I/O is already asynchronous; it still has ordering dependencies. A long-lived simulation worker remains PF10 if residual main-thread blocking warrants its copy/recovery cost.               |
| Predict walking locally as the throughput fix                                          | PF10 can improve apparent response, but predicted pixels cannot pay game-time debt or count as durable confirmation. It remains a separate responsiveness option.                                     |
| Upgrade the editing library and assume the problem is solved                           | An existing private candidate deserves qualification only as itself. It does not remove world-wide invalidation, storage or browser freezes.                                                          |
| Tune one-row SQL or small lookup caches before broad repeated work                     | Possible later refinements, but current evidence and source suggest larger opportunities. Do not make 23 proposals into 23 mandatory micro-optimization projects.                                     |
