## What this experiment changes

Eligible commands first save an exact, ordered description of their accepted changes; ordinary query tables can update afterward. The game confirms only after PostgreSQL durably saves those changes and the command's result. Unsupported families retain the synchronous table transaction. Restart applies saved changes; it never repeats the command or purchases another AI answer.

This remains an implementation experiment with incomplete capacity qualification. Current full-game evidence still fails smooth 3×. Focused durable-boundary and recovery checks do not establish complete game capacity.

## Compact evidence storage

The existing record codec stores temporal receipts and shared received values in immutable suffix segments, sealed at save preparation. Appending writes only the new suffix; correction and reclamation replace affected segments while preserving identities, ordinal gaps and exact chronology. Logical temporal chunks span timestamps up to their existing byte allowance, and expiry removes the exact old prefix even within a partly retained chunk. Logical retention charges and authored defaults are unchanged.

Receipt segments own indexed subjects, source aliases, local individuals and exact value references. Mutable parent headers retain scalar ranges, counts and physical byte totals. Cold selectors filter indexed segments before hydrating the selected closure; a full-chunk read reconstructs ordered logical unions. Hydration admission includes segment-index bytes. Current-format decoding validates coverage, totals, derived SQL columns and each page's provenance against its actual source closure, so a valid aggregate union cannot hide aliases assigned to the wrong page.

Admission counts at most 512 distinct unresolved canonical/position probes, with a separate 512-summary-dependency preparation bound. Exact codec-owned append ranges, children of proven new parents and surviving parents from this repository's accepted predecessor need no redundant membership query. Schema-declared complete resident collections also prove new identities absent: current perception collections and capture watermarks qualify; cold history and shared-value pools do not. The proof requires immutable collections and that exact accepted baseline; a foreign frozen world or caller flag cannot grant it. Pending identities, final positions and ancestor deletions remain checked even without SQL. Unknown identities, physical parents and mutable authority retain their actual checks. Only complete current/cold/pending ownership proof permits ordinary unowned-payload reclamation to defer; semantic correction/forgetting retains synchronous treatment. Recovery fully validates durable bytes without transient proof.

Pending entries retain compact changed records, source plans and revision metadata, not whole-world roots. The 32-revision/32 MiB debt, one-worker and eight-revision online-batch bounds remain; encoded debt is not a bound on decoded buffers or heap. [Scoped verification](../../verification/attention-and-memory-core.md#current-format-storage-and-development-readiness--october-29-2026) covers exact storage, admission and reduced encoded writes. The [runtime design](../attention-and-scenes-runtime-design.md#6-append-storage-and-a-short-durable-command-barrier) and completion gates below retain broader failure and capacity qualification.

## Selected implementation and cost

Reuse the existing canonical record changes, one world revision, PostgreSQL authority, history/memory owners and ordered service publication. Journal data contains typed canonical row changes, exact changed event bodies and their personal evidence, not SQL or instructions to rerun gameplay. The journal identifies the world, durable generation, predecessor and successor revision. Query tables have an explicit applied revision. A separate bounded application transaction can write those tables without holding the command-append connection for its entire duration; one game-server reservation protects the primary and every application connection; independent game servers still require exclusive acquisition.

Cost grows with changed records/evidence, pending bytes/revisions and recovery work. Preparation is shared with the existing record/history codec; online application reuses its compact prepared records, while durable journal bytes remain recovery authority. Replacement, restore, unsupported transitions and uncertain constraints use synchronous application through the same revision contract. No revision or evidence coalescing is allowed. One online application transaction handles up to eight consecutive already accepted prepared revisions, applying each in exact order with its own revision metadata. Recovery remains one entry per transaction. Keep at most 32 unapplied revisions or 32 MiB of encoded changes; before admitting more, apply accepted work. A single transition larger than 32 MiB uses synchronous application rather than bypassing the bound. These are provisional debt limits, not limits on world population or retained history.

Read fencing waits through a captured committed revision, checks the durable generation, then lets the existing consumer read one consistent applied snapshot. Current live simulation reads its committed immutable world. Exact database readers wait rather than silently see older history. Operational authority and receipt reads do not wait for unrelated searchable tables. No process-local queue is the durable source of acknowledged changes.

Estimated runtime scope: 900–1,800 lines across the journal, PostgreSQL connection owner, repository commit/application split, canonical reconstruction, history preparation and checkpoint/read fences. Required checks: current type/build checks; actual disposable PostgreSQL append/apply/reopen, forced rollback and ambiguous acknowledgement; private history and same-version checkpoint coverage; finite backlog-bound exercise. Keep failed trials. No provider work is needed.

## Reader revision and wait matrix

The database facade used by existing repositories owns a conservative table-read fence. Journal append/application use the underlying connection explicitly; they cannot recursively wait on themselves. Unknown table access waits conservatively. A read transaction fences before opening its repeatable snapshot, never halfway through it.

The service publishes the live world immediately after durable acknowledgement. Deferred application separately notifies the service when committed memory metadata or retained history rows change, so its cached views and existing SSE transport also advance memory/place revision tokens in a quiet or paused world. Clock-only application sends no second notification. This notification grants no gameplay effect, starts no polling and does not delay the original acknowledgement. The service releases its subscription with its runtime resources.

### Deferred admission proof selected before integration

The initial prototype ran the complete current-world validator before every append; the first cost comparison exposed its growing-history cost. The October17 continuation instead prepares the exact changed memory/observation metadata through the existing source writer and shares that preparation with application. Complete current-format validation remains mandatory on loading and restart reconstruction. Physical changes in this first family are limited to existing identities and world-root placements; canonical identity, required columns, finite coordinates and SQL ownership/uniqueness are checked before acknowledgement. Updates to an already existing item component also qualify: its unique item identity is derived from the unchanged canonical entity path. Item creation/retirement and reparenting remain synchronous. Verify created record identities and required parents against one bounded, parameterized union of indexed canonical lookups plus the exact pending journal overlay. The head compare-and-set and immediate authority/receipt writes stay in that same append transaction. Defer neither physical entity creation/removal/reparenting, new unique learned methods, destructive/edited evidence, policy/definition edits, story nomination, operational callbacks nor durable AI completion. Those transitions first drain accepted application and retain the existing atomic transaction, advancing committed/applied together. They still share the new revision/read/recovery contract; this first eligibility is not completion of every possible deferred family.

Ordinary local movement and native progress may include new actions, plan steps, work records, exact observations, memories and summary links. Their required SQL fields use the existing canonical column extractors and source writer; observer evidence uses its existing validator. Summary links count toward the 512-row deferred-preparation allowance, so one summary cannot hide unbounded dependent work. Unknown schema constraints select synchronous application. New-source cross-family identities are checked rather than presumed unique. The journal applies original changes through the existing history/memory/canonical owners. During application they receive the applying revision explicitly through the owned database transaction context, so later committed entries cannot make earlier source work claim a future revision. Every local or worker application connection holds the same shared database reservation as the original primary. Independent game-server startup still requires the exclusive hold, so old application cannot outlive its reservation and overlap a replacement writer.

Current `TEXT[]` and `BIGINT[]` index columns are validated element by element before scalar type checks, preserving text encoding, safe integers, dense arrays and column nullability. Existing world-root placements also admit their optional `motionContinuityRevision` under the spatial owner's current rule: a nonnegative safe integer no greater than the placement revision. The [focused native-source recovery proof](../../verification/attention-and-memory-core.md#current-array-metadata-and-journal-admission--implementation-plan) covers actual movement and these current fields without qualifying broader worker failures, complete service speed or capacity.

Exact read transactions drain through a captured head before opening their snapshot, then independently require equal committed/applied heads inside that snapshot. A concurrent new append can require another bounded wait; return unavailable on the existing interactive read bound rather than return stale success. Operational-only session/grant/receipt/accounting reads retain their current narrow path. This read cost and changed-record preparation cost must be included in the experiment; faster append alone is insufficient.
