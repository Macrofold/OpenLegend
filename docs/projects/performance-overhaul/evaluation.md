## Treat previous results as leads

The earlier investigation contains useful controlled comparisons and unusually explicit failures. It also contains different code versions, different workloads, variable host conditions, incomplete comparisons, corrected measuring tools and private changes that never entered the normal game. A reported number is evidence about its recorded run, not an unquestionable description of today's game or a guarantee about a proposed change.

This analysis inspected source and reports; it did **not** recompute the original raw measurements, certify all the earlier tools or rerun their checks. Use three separate statements in every proposal:

1. **Source fact:** what the current code demonstrably does, with its owner and callers.
2. **Historical clue:** which recorded experiment suggests that work may matter, including its limitations.
3. **Prediction to test:** which work should disappear and why the complete game might improve or regress.

Do not turn a sample count into CPU seconds, an overlapping wait into an additive cost, or a correlation into a cause. Conversely, a noisy negative game comparison does not disprove a sound reduction in work; it leaves its practical benefit unestablished. Record both facts.

## Before each implementation slice

Use the existing PF17 entry and relevant original subsystem task. Write a short experiment note in the existing [performance evidence folder](../../verification/performance/README.md) before changing executable behavior. Reuse a relevant report for a direct follow-up; do not create a new report for every command or check.

Record:

- Exact parent revision, inherited private changes, affected owners and the one main hypothesis.
- What makes the cost grow; which work will disappear; shared preparation; what invalidates it; the complete caller being improved.
- Intended behavior and any deliberate differences, including affected characters and concrete gameplay examples.
- The smallest discriminating comparison, a refusal/interruption or recovery case where relevant, and the expected result that would make us reject the idea.
- The primary outcome, relevant regression limits, acceptable behavior differences and planned comparison order/replication, chosen before seeing results. Name which existing budgets apply and what benefit makes this particular change worth keeping.
- Which existing evidence still applies and which changed assumptions require new checks.

Keep the implementation through its current semantic owners. Do not create a new profiling framework, second mutation authority or broad replacement engine as a prerequisite to every experiment. The [performance workflow](../../../.agents/skills/openlegend-performance/SKILL.md) and [verification policy](../../../.agents/rules/verification.md) remain the shared owners; this file specifies this project's comparison decisions.

## Compare one change, then the combination

1. **Check the mechanism.** Verify that the intended work actually disappears through the production caller: fewer unrelated actors forecast, fewer unchanged fields copied, fewer observations hydrated, fewer repeated encodings, or fewer required writes. Include cold preparation and invalidation. A local counter improvement is necessary evidence for that hypothesis, not sufficient evidence of a faster game.
2. **Check behavior appropriate to the change.** For exact optimizations, compare outcomes, ordering, evidence and saved continuation. For intentional gameplay changes, specify allowed differences first, preserve integrity, and compare useful completed activities. Do not require identical random trajectories after an explicitly changed random policy; do require deterministic continuation within that policy. Avoid repeating unaffected checks just to make a long checklist.
3. **Measure fixed work.** Use the same valid starting state and input sequence for the before/after versions. Include relevant full costs such as preparation, publication and saving. Keep CPU, elapsed time and memory separate. Instrumented diagnosis and ordinary timing are separate observations.
4. **Measure real play.** Reuse ordinary server, storage and browser paths. Compare command confirmation, actual visible movement, busy-period clock debt, drawing gaps, accepted workload, errors and memory growth. A memory-search optimization needs searches; a presentation change needs actual drawing; a growth optimization needs older worlds.
5. **Repeat enough to distinguish a useful effect from variation.** Alternate or balance comparison order and retain all valid results. If variance is as large as the claimed gain, call it inconclusive and reconsider the hypothesis or environment. Do not keep repeating until a favorable sample appears. Report individual runs and counts; a mean of p95 values is not a pooled p95, and a tiny run does not qualify p99.
6. **Decide and update the tracker.** Use the dispositions below. Remove rejected prototype code from the candidate intended for integration; retain the explanatory record. Mark only the completed substep, not the entire smooth-game task.
7. **Recheck the combined build.** Establish a new baseline after an adopted change. Once several candidates are combined, compare that exact combination against the previous accepted build, including interaction and memory costs. Savings overlap; multiplying percentages is invalid.

| Disposition        | Required meaning                                                                                                                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adopt              | Relevant behavior passes and a reproducible, useful complete-path benefit is established without an unexplained material regression in the tested envelope. Explicitly accepted gameplay changes are recorded. |
| Keep investigating | Structural work falls, but complete-game benefit or a required behavioral case is still unresolved. This is a private candidate, not a shipped improvement.                                                    |
| Reject             | The mechanism does not remove the intended cost, introduces an unacceptable behavior change, or makes the complete relevant workload worse without a justified tradeoff.                                       |
| Inconclusive       | Noise, coverage, workload differences or a tool defect prevents a useful decision. Preserve the failure and identify the one missing fact.                                                                     |

No finite test can prove that performance can never regress on any machine or workload. The practical requirement is stronger engineering discipline: sound reduction in work, a declared supported workload, measured before/after outcomes, explicit tradeoffs and an easy way to reverse a failed experiment. Do not claim universal non-regression.

## Scenarios that prevent false wins

Use only the scenarios relevant to the candidate during development; the final combined game needs the complete requested acceptance. Keep the existing [PF acceptance budgets](../../maintainers/performance.md#acceptance-budgets) and PF00/PF16 long-play requirements as the numerical owners.

| Scenario                                                                           | What it catches                                                                                                                       |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Fresh expanded world: seventeen people, forty animals, added objects and buildings | The original task, with ordinary walking and real resident travel/work/food.                                                          |
| Working, resting and waking intervals                                              | Averages that hide overload when residents resume activity; invalid sleeping counts.                                                  |
| Older world with the same nearby activity                                          | Whole-history scans, collection copies, index maintenance and growing items.                                                          |
| Sparse map versus one crowded area                                                 | Whether filtering removes distant work or merely shifts unavoidable close interaction.                                                |
| Few changes in a large quiet world versus many changing bodies                     | Whether an index/cache saves work only in its easy case and explodes during invalidation.                                             |
| Multiple independent viewers, permission changes and slow consumers                | Repeated projections, disclosure mistakes, queue growth and publication fairness. This is separate from a one-player capacity result. |
| Combat, brief encounters, resource exhaustion, interrupted work, edits and restore | Missing causal boundaries concealed by routine scripted activity.                                                                     |
| Optional panels closed/open and ordinary versus detailed graphics                  | Preparation that leaks onto the frame path and quality reductions that merely move cost.                                              |
| Scripted plans, local thought preparation and real AI separately                   | What is actually being optimized; provider calls require their existing authorization and budget.                                     |

Successful completion means sustained requested 3× on the named reference setup, prompt confirmed walking, smooth drawing, meaningful activity and no growing backlog across the existing long mixed-action acceptance. Report remaining device/scale limits. Immediate predicted motion, fewer accepted inputs, sleeping residents, forgotten evidence or a slower world clock cannot stand in for those outcomes.

## Reporting template for future results

Keep a short reader-facing table first: **idea; exact version; before; after; activity performed; behavior lost/changed; decision; remaining uncertainty**. Follow it with the necessary technical evidence and links. Always distinguish implemented changes from private experiments and proposals. Do not place source hashes or internal task shorthand in the explanation in lieu of plain language.

This proposal creates no new population, history, inference, queue or gameplay cap. Relevant limits remain with [native work](../../limits/native-work.md), [persistence](../../limits/persistence.md), [memory](../../limits/memory.md), [cognition](../../limits/cognition.md), [spatial behavior](../../limits/spatial.md), [interface](../../limits/interface.md), [3D presentation](../../limits/3d-pixel-art.md) and [product scalability](../../limits/product-scalability.md). A later choice to change one belongs in its existing inventory with its gameplay cost.
