## PF17.17 — Public projection dependencies

**Priority/status:** next; a source-grounded extension of existing caches. **Scope:** medium-to-large. **Intended behavior:** unchanged public information.

**Code fact.** `projectView` in [view.ts](../../../apps/server/src/view.ts) has cached sections, but visible-entity discovery and inventory preparation depend on the entire entity directory. An entity's description preparation depends on its full entity object. Ordinary movement or bodily changes can invalidate information whose actual facts did not change.

**Implementation.** Separate dependencies for membership, stable descriptions/appearance, physical pose, bodily indicators, inventory and requested action details. Keep the existing observer-owned cache and permission checks. Reuse participant-independent preparation once in the current permitted projection; do not share observer-specific facts by global entity identity alone.

**Invalidation.** Definitions, recognition episodes, inspection, knowledge/forgetting, possession, body/appearance, permissions, timeline replacement and restore can change displayed facts. Countdown/status descriptions also depend on simulation time and their next meaningful display boundary. Spatial membership cannot be cached merely because the player's body stayed still.

**Why it could help / test.** Cost multiplies across visible entities, updates and viewers. Move one resident among many stationary objects and count membership queries, inventory preparations and descriptions rebuilt. Compare complete views after knowledge/permission/content changes, then measure multiple independent observers and actual browser play. Reject stale information, missing immediate updates or reuse maintenance costing more than preparation. This is not a proposal to remove actual perception or lower every publication rate.

### Implementation route and first slice

The live route is `WorldService.notify/subscribe` → `publish/currentView` in [http.ts](../../../apps/server/src/http.ts) → `projectView` → `projectPatch`. `currentView` caches a complete view for one `scopeKey` and version; `scopedCache`, `memoizer` and `optional` in `view.ts` own derived sections and their asynchronous completion. Keep the existing 20 Hz publication ceiling, projection lane and final scope checks.

Start the dependency audit with these verified reads; this is a minimum, not permission to omit other fields reached by a helper:

| Displayed fact and current reader                                                                                                                                              | Inputs that can change its answer                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name permitted for this observer: `observerName` in [base/knowledge.ts](../../../packages/domain/src/worlds/base/knowledge.ts)                                                 | Observer/subject identity, given-name record and authored flag, matching perception encounter, subject species/name grammar, and a remains record's source identity. A body can inherit the source person's name, so inspect that referenced person's dependencies too.                                          |
| Description: `describeEntity` in [entity-description.ts](../../../apps/server/src/entity-description.ts)                                                                       | The permitted name; remains and item definitions; threat policy/mode/relinquishment and strike windup; resource/cast definition and quantity; authored descriptions; life and animal danger; fire lighting and fuel. Apply the helper's branch order rather than assuming every description has the same inputs. |
| Public effects: `projectStatusEffects` in [status-capabilities.ts](../../../packages/domain/src/status-capabilities.ts)                                                        | Installed status definitions, subject effects, disclosure and contribution counts, fixed expiry versus simulation time, and source-sustained contributions' source existence/life/retirement and enclosing object's participation. The subject's own unchanged effect record is insufficient.                    |
| Recovery/status wording: `observedCombatActivity` in [base/combat-views.ts](../../../packages/domain/src/worlds/base/combat-views.ts), followed by `view.ts`'s status branches | Current action/preparation, combat recovery deadline and rounded remaining seconds, life/remains policy, observer sight, projected effects and selected-world action labels. Encounter-bound identity and time-bound status are different dependencies.                                                          |
| Visible attack motion: `actionAnimation` in [action-animation.ts](../../../apps/server/src/action-animation.ts)                                                                | Current action stage/phase/time, selected strike/tool definition, own heading/position, and target existence/position/visibility while tracking. A target can move without changing the attacking entity.                                                                                                        |

1. Record, for each returned entity field, which current helper reads it. Begin with `observerName`, `describeEntity`, `bodyProfile`, `projectAttributes`, `projectStatusEffects`, `actionAnimation` and assembly/interaction controls. A field being called a description does not make it static: [describeEntity](../../../apps/server/src/entity-description.ts) reads threat mode, life, remaining resources and fire fuel. Record these dependencies before removing any current cache dependency.
2. First split one entity projection into separately prepared description/appearance, bodily display and current pose/action blocks, assembled into the **unchanged** `EntityView` contract. Reuse `projectStatusEffects` once in that projection instead of independently rebuilding the same list for the list and status wording. Keep interaction, inventory and membership on their existing conservative dependencies until their own read audit is complete. This first slice establishes a safe pattern; it does not finish PF17.17.
3. Store these blocks under the existing observer cache and entity ID. Keys must retain world/timeline/authority scope; the dependency values must cover the exact definition and subject/observer facts. Do not retain draft objects. Bound entry lifetime by current cache eviction, entity removal and viewing-scope retirement. Failed async preparation cannot install an old block into a replacement scope.
4. Next narrow membership preparation using the existing permitted spatial/visibility owners and complete change information. A stationary observer still needs changes from moving targets, blockers, senses, recognition and definitions. An unavailable query or incomplete change set must take the existing conservative path; it is not an empty visible set.
5. Finally audit inventory preparation through [inventoryItemSummary](../../../apps/server/src/inventory-view.ts). Changes to carried lots alone do not cover access, inspected recipe text, equipped counterparts, learned methods, declared ownership or body equipment ports. Reuse only a block whose complete reads are covered. Keep action admission current even when the displayed explanation is reused.

**Checkpoint before narrowing a dependency:** the experiment note must contain a field-to-reader-to-invalidation table for that block, and a list of current mutation owners that produce each invalidation. If any owner is unknown, retain its broader dependency and report the remaining cost. An unchanged object identity at the outer level is not sufficient proof of immutable nested definitions.

### Finite verification and completion

Use the actual projection caller and relevant existing [private-history](../../../apps/server/src/private-history.test.ts), [conversation-view](../../../apps/server/src/conversation-view.test.ts) and [spatial HTTP](../../../apps/server/src/spatial-http.test.ts) fixtures as starting points. Add a small focused scenario only where these do not exercise the changed dependency.

| Scenario                                                                                      | Required result                                                                                              |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| One moving resident, ten stationary objects, two consecutive public projections               | Positions update; unchanged reusable blocks are reused; complete public values match the uncached reference. |
| One clock-only advance crossing a displayed recovery-second boundary                          | The countdown changes without an unrelated entity mutation; untimed blocks remain reusable.                  |
| Target enters/leaves sight while the observer stays still; then a blocker or sense changes    | Membership and permitted detail change in the same publication as the reference.                             |
| Change a resource quantity, fire fuel, threat mode, body form or installed definition         | Every affected description/status/appearance updates; no classification based only on field name hides it.   |
| Inspect/forget/correct information, change equipment or transfer a carried lot without moving | Relevant inventory/knowledge facts change immediately; unrelated private facts remain absent.                |
| Hold an async read, then replace control, revoke access or restore the same world             | Old private results cannot publish; the fresh projection uses the new scope/timeline.                        |
| Two observers know different names/details for one person                                     | Neither observer receives the other's cached description.                                                    |

After each block passes, measure cold preparation, unchanged reuse and invalidation-heavy updates separately. Complete the card only after the targeted entity, membership and inventory blocks have a disposition, multi-observer disclosure/fairness is checked, and the actual browser workload demonstrates the benefit. Report unconverted blocks explicitly; do not mark the whole card complete after the first local cache.

## PF17.18 — Small public changes and dirty scene updates

**Priority/status:** after or alongside PF17.17 at the same semantic boundaries. **Scope:** large server/protocol/client change. **Intended behavior:** unchanged.

**Code fact.** `projectPatch` in [view.ts](../../../apps/server/src/view.ts) compares complete entity objects and includes the whole object when changed. Patch application in [api.ts](../../../apps/client/src/api.ts) reconstructs entity collections. `WildernessScene.setView` in [scene.ts](../../../apps/client/src/scene.ts) revisits visible entities, appearance signatures and related scene preparation.

**Implementation.** Separate stable public descriptions/assembly data from frequent position/action updates, or introduce explicit changed fields in the current patch contract. Propagate changed identities/sections to the existing scene owner, so unchanged models skip appearance preparation and settled stationary entries leave the motion-update set. Update current producers and consumers together; no legacy protocol adapter is needed.

**Why it could help.** Reduces comparison, allocation, transferred bytes and client processing per changed entity. Smaller messages alone do not remove server projection work, hence the dependency on PF17.17. Large public assembly descriptions and many viewers make the opportunity larger.

**Future decision test.** Replay the same permitted sequence through both complete and incremental paths. Compare removals, supports, selection, captions, reset/reconnect, stale revisions, inspection loss and observer replacement. Count entities/fields processed, bytes and allocations alongside real frame/input tails. Reject if delta bookkeeping is more expensive in ordinary small scenes, or partial updates can combine facts from different authorized snapshots. One client state owner remains authoritative for presentation.

### Selected contract and implementation order

The current wire owners are `GameView`, `EntityView` and `GamePatch` in [protocol/index.ts](../../../packages/protocol/src/index.ts); producers are `projectPatch` and HTTP channel/reset delivery; the consumer is `applyGamePatch` in `api.ts`, followed by `acceptView`/stream handling in [main.tsx](../../../apps/client/src/main.tsx) and `WorldRenderer.setView` in [world-renderer.ts](../../../apps/client/src/world-renderer.ts).

1. First implement entity field patches while keeping renderer behavior unchanged. Recommended contract: complete entities for additions; `{ id, set, remove }` for changes to an existing entity; removed IDs; optional complete order. `id` is immutable within an update. Nested arrays/objects are replaced as complete field values in this first slice, rather than inventing arbitrary recursive patches. Missing means unchanged; a field in `remove` is deleted; `null` remains a value. Update the current schema discriminator and every current producer/consumer together as required by the actual contract; do not keep an old-format adapter.
2. `projectPatch` must compute updates only from two complete permitted `GameView`s for the same accepted scope/timeline. Keep reset behavior when those identities change. Apply an entire patch to a new client view before publication. Reject a missing update target, conflicting create/remove/update identity or mismatched base revision by requesting the existing full resynchronization path; never silently apply part of the patch or create an incomplete entity.
3. Preserve structural sharing for unchanged entities and sections. Keep entity order exactly as the full projection defines it, including insertion/removal without an explicit reordered list. HTTP patch retention/backpressure must still count the actual encoded bytes; a slow client must receive a valid chain or one full current reset, never a fabricated intermediate revision.
4. Only after wire equivalence passes, carry the changed entity/section information to the existing renderer boundary using plain data. Maintain renderer-owned sets for appearance changes, new/removing entities and active visual motion. The full reset still performs complete reconstruction/reconciliation. Do not create another public-view authority inside the renderer.
5. A settled position does not imply that all visual work can stop. Keep entries active for attack/recovery animation, departure fade, model/cloth motion, reveal transitions and other timed effects. Camera/floor/reveal changes can dirty many entries even without a network update. Re-entry, teleport, pause/resume and graphics restoration reset the appropriate preparation; selection and picking always read the latest permitted view.

**Prohibited shortcuts:** retaining omitted optional fields, treating entity IDs as valid across world/timeline replacement, hashing the complete view every frame to decide what changed, dropping intermediate committed speech/events as replaceable poses, or skipping privacy removal until the next animation frame. The extra transport structure must earn its cost against complete entity replacement.

### Verification gates

Start with [api.test.ts](../../../apps/client/src/api.test.ts), especially the actual producer/JSON/consumer optional-removal and entity-order/scope cases. The decisive assertion is `applyGamePatch(previous, JSON-roundtripped projectPatch(previous, next))` equals `next` for each supported patch; intentional full resets are compared separately. Include additions, deletion of the last entity, optional-field disappearance, nested replacement, reorder, duplicate/stale delivery and a missed revision. A rejected patch leaves the prior view unchanged and triggers ordinary resynchronization.

Then use [camera](../../../tests/browser/camera.spec.ts), [spatial-world](../../../tests/browser/spatial-world.spec.ts), [actions](../../../tests/browser/actions.spec.ts) and [conversation UI](../../../tests/browser/conversation-ui.spec.ts) scenarios for the changed renderer consumer. Exercise stationary attacks/fades, moving across raised supports, camera changes without network changes, control replacement while selected, and loss/recreation of graphics resources. Verify matching selection/picking/captions and no leaked entries. Measure transport and renderer stages separately, then the actual combined game using the existing profiling entry points. PF17.18 is complete only when both transport and scene work have an explicit retained/rejected disposition and no old current-protocol consumer remains.

## PF17.19 — Visual activity and quality tiers

**Priority/status:** explicit visual compromise; existing private cloth reduction is a useful starting point. **Scope:** medium renderer/asset work.

**Code fact.** `WildernessScene.update` and `updateModelVisibility` in [scene.ts](../../../apps/client/src/scene.ts) visit retained models. Their eligibility considers observation, level and action/body state, but does not fully tier work by viewport size. `MercenaryActor.update` in [mercenary.ts](../../../apps/client/src/characters/mercenary.ts) runs cloth for wanted mercenary models; [mercenary-cloth.ts](../../../apps/client/src/characters/mercenary-cloth.ts) performs constraint passes and publishes mesh/normals. This cloth cost applies to the detailed mercenary appearance, not automatically to every resident or animal.

**Implementation.** Give the presentation owner full near-camera cloth, cheaper small/distant cloth or pose animation, and minimal offscreen model work. Keep smooth authorized position interpolation, current selection/captions and camera behavior. Use stable tier transitions to avoid repeated cloth resets at a viewport edge. Being stationary does not prove the skeleton or cloth is stationary; idle animation still matters. A remembered/ghost appearance must not absorb hidden current facts.

**Why it could help / evidence.** This removes per-frame work in proportion to the eligible detailed models. Report their actual count, on-screen count and selected tier; the total animal/person population is not the cloth workload. [Report 17](../../verification/performance/17-cloth-quality-and-cost.md) found a useful isolated solver reduction but mixed graphical results and unfinished appearance checks. The rejected callback/draw-skipping trial is not the same mechanism and should not simply be repeated.

**Tradeoff and test.** Distant motion may be less detailed and cloth less constrained. Compare close, far, crowded, hidden and camera-transition scenes, including pause, teleport and graphics restoration. Measure whole-scene CPU, GPU/draw gaps and actual appearance. Reject distracting transitions, leaks or no meaningful complete-frame gain. Renderer quality owns the policy; this does not change collision, needs or cognition.

### First visual experiment and later tiers

The exact route is `WildernessScene.update` → `updateModelVisibility` → `MercenaryActor.setVisible/update` → `CapeCloth.update/step/publish`. Creation is limited to the `mercenary-model` appearance. `setVisible` can request a cloth reset, and `MercenaryActor.update` spreads the existing sixty settling steps across updates while retaining the sprite. Read that lifecycle before adding a tier; merely toggling visibility at a camera edge would repeatedly pay settling.

1. Requalify the smallest existing private change first: four instead of eight constraint passes, keeping the 60 Hz integration, collision bodies, pin/seam order, reset/settle and mesh publication unchanged. Recover the exact report-17 candidate or reproduce its single policy change from current source; do not copy unknown private dependencies. Inspect close garment motion before choosing it as a lower tier.
2. If that change is useful, introduce a renderer-owned quality value on `MercenaryActor`, separate from whether the model is permitted/visible. [A3D20](../../limits/3d-pixel-art.md#a3d20--experimental-cloth-quality-tiers) owns the proposed experiment's pass counts, projected-height thresholds, initial state, boundary retention and unavailable-projection fallback. Follow that complete rule; it keeps selected/large characters detailed and reduces work for small unselected models. Height means the model's height in the displayed viewport, not its fixed internal model render target. Compute it with the current camera/canvas scale. The proposed values are neither numerically optimal nor quality-qualified; report and evaluate them. They are presentation settings, not world laws or adopted defaults. Preserve existing visibility eligibility in this slice; offscreen suspension is the later separate experiment below.
3. Keep both tiers at the same 60 Hz cloth integration initially. Lower update frequency and replacing cloth with skeletal animation are separate changes and need separate motion/asset qualification. The old source garment is not a free fallback: report 07 records stripped skin bindings and a larger original mesh. Do not enable it and assume equal resource cost or correct deformation.
4. Only after the visible tiers are qualified, evaluate offscreen suspension. Use a conservative projected bound covering the model and cloth, not just its foot. On return, use the existing reset/settling and sprite fallback without replaying an unbounded hidden-time backlog. This visibly changes cloth history; specify and inspect that transition. Keep authorized position, support, captions and interaction state current while expensive decorative simulation sleeps.
5. Preserve lifecycle ownership: destroy model resources once, clear tier history on timeline/appearance replacement, reject late asset completion after disposal, and restore current quality after graphics-context recovery. World pause must not accidentally become a per-model permanent freeze.

### Finite visual checks and decision

Use [report 17](../../verification/performance/17-cloth-quality-and-cost.md) for the previous numerical/appearance cases and [report 07](../../verification/performance/07-cape-and-shadow-experiments.md) for rejected alternatives. Private helper paths are historical artifacts, not guaranteed installed tools. The existing [browser profiler](../../../scripts/performance/profile-browser.mjs) and [server profiler](../../../scripts/profile-server.ts) provide actual-game entry points; inspect their current accepted arguments rather than invent a cloth flag.

Compare one detailed model at close range, the same model at both threshold boundaries, a camera sweep across the viewport, ordinary walk/idle turns, a large position jump, sleep/wake, pause/resume, timeline replacement and graphics loss/recovery. Expected: finite meshes; pinned points remain pinned; no new visible seam/body/ground failures accepted silently; selected/close detail returns; no repeated settling while hovering between thresholds; the sprite/model handoff is coherent. Compare zero, one and several **actually instantiated** detailed models so unrelated population does not inflate the claimed saving. Record CPU, GPU, draw gaps, resource counts and close images/video separately. Finish by selecting or rejecting each tier and updating presentation limits/quality documentation only for retained settings; a four-pass isolated win alone does not complete the tier project.

## PF17.20 — Incremental landscape resources

**Priority/status:** scenario-specific: editing and expanding worlds. **Scope:** medium-to-large renderer resource lifecycle. **Intended behavior:** coherent current scenery and picking.

**Code fact.** `WildernessScene.setView` includes the spatial revision in its landscape key. A change can call `buildLandscape` in [scene.ts](../../../apps/client/src/scene.ts), disposing resources, repainting the full map canvas and recreating landscape geometry/scenery. A small structure edit can therefore have a whole-map presentation cost.

**Implementation.** Separate terrain texture, support/blocker geometry and scenery-instance ownership. Rebuild affected definitions/instances by their existing IDs/revisions and retain unchanged meshes/materials. Begin with one edit family, such as a structure instance whose change does not alter terrain paint. If large preparation remains unavoidable, prepare a bounded replacement and publish it coherently; cancel superseded work on edits, restore or shutdown.

**Why it could help / limits.** Removes map-area/resource reconstruction for local edits. It is not established as a steady-state walking bottleneck or the cause of the recorded rare freeze.

**Future decision test.** Add, edit and remove one building on a larger unchanged map. Compare picking, supports, cutaways, same-revision restoration, disposal and repeated edits against full reconstruction. Preserve unchanged procedural terrain and water decorations: the current builder consumes a shared seeded sequence, so restarting partway can rearrange untouched details. Measure edit-frame stalls and retained resources. Reject stale selectable geometry, resource leaks or replacement preparation that only shifts an equally large pause to publication. Any changed decoration or temporary loading treatment must be explicit presentation behavior.

### Resource contract and implementation order

`setView` currently calls `buildLandscape` when its map key changes. That builder owns terrain paint, ground/surround meshes, blocker boxes, non-terrain support meshes/seams, scenery batches and liquid glints. `applyLevelFocus`, picking and shadow presentation consume those resources. Preserve the [spatial renderer contract](../../spatial-world.md) while separating their lifetimes.

1. First extract unchanged terrain/ground/glint resource lifetime from structural geometry lifetime without changing output. Keep the original full seeded terrain/glint construction together; do not restart its random sequence independently per edit. World/timeline, seed, dimensions, tile data or terrain-definition changes still rebuild that complete group. An unclassified map change falls back to full rebuild.
2. First incremental family: non-terrain support surfaces and blockers. Use renderer-owned maps keyed by record kind and its exact ID, storing the source fields needed for the resource, its node/meshes, shared-material ownership and disposal function. A global spatial revision says something changed; it does not identify which surface. If no per-record revision exists, compare the finite geometry/material fields once at the map-update boundary. Never compare them every frame or assume an ID alone proves unchanged geometry.
3. Derive create/replace/remove sets from the new complete permitted map. Construct replacement resources before publishing them. After construction succeeds, switch the resource maps, current map used by picking and cutaway/shadow inputs coherently, then release superseded resources. On preparation failure, use the existing error/recovery path; never leave new picking geometry paired with old visible geometry. If a staged loading state is chosen, block affected picking explicitly rather than accepting stale destinations.
4. Extend to scenery by its existing batch key/instance identity. One changed instance may require rebuilding its batch, but not unrelated batches or terrain. Retain current material/mesh sharing and destruction ownership; a local node must not destroy a shared material still used elsewhere.
5. A later bounded asynchronous preparation must carry world/timeline and the exact desired map token. A new edit, restore, destroy or graphics reset invalidates its install; dispose its unused prepared resources. Do not retain an unlimited sequence of abandoned rebuilds. Splitting work is worthwhile only if final installation remains cheap.

**Checkpoint before incremental publication:** list every consumer of `geometryNodes`, `geometryMeshes`, `landscapeCards`, `landscapeBuffers`, `animations` and `landscapeMaterials`. Specify which owner removes each reference and whether the old node participates in picking, reveal or shadows. Confirm IDs can coexist across record kinds before selecting a key; do not rely on concatenation with an ambiguous delimiter.

### Finite checks and completion

Use [spatial-world browser scenarios](../../../tests/browser/spatial-world.spec.ts), [camera scenarios](../../../tests/browser/camera.spec.ts) and [world-camera unit cases](../../../apps/client/src/world-camera.test.ts) as entry points. Start with a map containing ground, one raised timber surface, one ramp, two blockers and two scenery groups. Add one support, resize/material-edit it, remove it, edit one blocker and edit one scenery member. After each step compare the complete resource geometry and actual screen/picking behavior to fresh full reconstruction. Unchanged terrain/glints and unrelated resource identities must stay unchanged.

Then restore different geometry with the same saved spatial revision, replace the world, and destroy during a deliberately held preparation. Expected: no stale install, no selectable removed support, correct cutaways/shadows, and every abandoned resource released exactly once. Repeat the finite edit sequence ten times and compare retained resource counts after teardown; growth is a failure to investigate, not proof of a useful cache. Finally measure larger-map single edits and a concentrated whole-map replacement. Complete the card after structural and scenery paths are qualified or explicitly rejected, full fallback remains correct, and actual edit stalls improve without moving the pause to publication.

## PF17.21 — Stable UI sections

**Priority/status:** after dependency-local public views; extend existing React work. **Scope:** medium client state/consumer change. **Intended behavior:** unchanged controls and information.

**Code fact.** [main.tsx](../../../apps/client/src/main.tsx) replaces the root view for each accepted update and runs scene-related effects when it changes. [nearby-entities.tsx](../../../apps/client/src/ui/nearby-entities.tsx) already memoizes individual rows. Removing unused panel shells previously did not establish a gain.

**Implementation.** Preserve stable section identities in the existing stream/state owner and notify consumers when their displayed facts change. Separate frequent scene pose updates from inventory, conversations, jobs and settings. Callbacks must resolve current authorized facts rather than hold an old complete view. Reuse existing subscription/helpers rather than add another application store solely for performance.

**Why it could help / test.** Avoids repeated unrelated component/effect work during frequent movement. Hold inventory or conversation open while many people move; count real component executions and allocations, then measure input and frame gaps. Test changes initiated elsewhere, access revocation, errors, focus, drafts and teardown. Reject missed UI updates or extra subscription complexity without a measured benefit. This is not a license to slow speech, action availability or error feedback.

### First slice and expansion

The current chain is EventSource handlers in `main.tsx` → `applyGamePatch` → accepted root `view` → `App` and the scene effect. The root state already receives structurally shared unchanged sections from `applyFields`; nearby rows already use React memoization. Do not add a second store before checking which remaining consumers actually rerun.

1. Choose one consumer shown to rerun under pose-only updates: the inventory panel is the initial candidate. Trace its props, handlers and effects from `App` to its connected component. Pass the smallest existing stable sections it displays, together with explicit access/action dependencies; do not construct a fresh wrapper on every parent render and then expect memoization to help. Keep the actual request/command owner unchanged.
2. Isolate that connected panel so its rendering work can be reused while its displayed inventory, access, pause, selected item and pending command state are unchanged. Keep its callbacks connected to the current accepted view or current command owner. A callback made stable by closing over an old view is a correctness bug.
3. Separate renderer updates using PF17.18's changed sections, or an equivalent exact scene dependency list, from unrelated UI sections. Clock changes still matter for pause, navigation preparation, timed effects and lighting. Do not declare a view scene-irrelevant merely because entity positions did not change.
4. Expand one measured consumer at a time to conversation, jobs and settings using its actual dependencies. Hidden panels already have lifecycle/visibility rules; preserve drafts, live receipts and explicit reading position instead of unmounting everything to suppress work. Keep one owner for each state value; avoid effects that copy current server state into redundant local state.

### Tests and stopping conditions

Start with [api.test.ts](../../../apps/client/src/api.test.ts), [actions](../../../tests/browser/actions.spec.ts), [conversation UI](../../../tests/browser/conversation-ui.spec.ts) and [design-system](../../../tests/browser/design-system.spec.ts) browser scenarios. In a focused actual browser case, leave inventory open while one resident moves through twenty accepted updates: unchanged inventory component work should fall, but its content remains identical. Then transfer a lot, equip an item, inspect a record, change the known recipe, receive a command failure and pause: each relevant display/control changes immediately without requiring another movement update.

For conversation, retain an unsent draft and reading position during motion, receive a real reply-status change, then replace control while a request is held. Expected: the draft follows its existing private-owner policy; no old reply or action targets the new person; error/status updates remain visible. Cover keyboard activation, focus restoration, narrow-screen panel switching and close/reopen. Use existing allocation/CPU observers only for attribution; compare ordinary frames/input without those samplers separately. Complete each consumer's dependency audit and decision, then measure their combination. A decrease in render count without lower complete-path cost is not sufficient retention evidence.

## PF17.22 — Affected-character cognition intake

**Priority/status:** meaningful for larger thinking populations; extension of an existing change-fed scheduler. **Scope:** medium-to-large server scheduling work. **Initial behavior target:** same meaningful opportunities and fairness.

**Code fact.** Host ticks can call `AiDirector.considerThought` in [ai-director.ts](../../../apps/server/src/ai-director.ts). `ActorWork.refresh` in [actor-work.ts](../../../apps/server/src/actor-work.ts) still visits memory-bearing characters and obtains inputs; `ready` scans tickets and sorts candidates. `ThoughtIntakeInputs.read` in [interests.ts](../../../apps/server/src/interests.ts) prepares character/module tokens. [cognition-maintenance.ts](../../../apps/server/src/cognition-maintenance.ts) performs related refresh and expiry preparation.

**Implementation.** Feed affected-character notifications and next meaningful deadlines into the existing owner. Prepare shared installed-policy tokens once, maintain ready membership and the earliest future deadline, and preserve urgency/aging order. Unknown mutation coverage, changed definitions and restore trigger conservative rebuilding. Coalesce repeated notices about the same current opportunity, not distinct speech or required evidence.

## PF17.23 — Bounded preparation for actual model-context callers

**Priority/status:** focused candidate for invention/world-assistant and large-context workloads; not established as an ordinary-walking cost. **Scope:** narrow-to-medium request preparation. **Intended behavior:** preserve exact allowed context and selection order.

**Code fact and corrected inference.** `buildContext` in [context.ts](../../../apps/server/src/context.ts) repeatedly encodes its whole context while removing optional records. This is reachable through `buildStoredContext` from [invention-service.ts](../../../apps/server/src/invention-service.ts) and [macrofold.ts](../../../apps/server/src/macrofold.ts); those callers already supply selected memories. Production decisions use [prepareDecision](../../../apps/server/src/decision-context.ts), which already passes its initial observation to action/planning candidates and refreshes after asynchronous work.

An initially attractive duplicate observation/recall path in `cognitionContext` proved reachable through tests and a verification script, not the normal decision coordinator. Its cleanup is not a demonstrated running-game optimization. The analysis explicitly withdraws that premise rather than promoting it on appearance alone.

**Implementation.** Begin with the live context builder's repeated encoding. Encode/count each optional record once, preserve the existing trimming order, select within the existing byte/character allowances, and perform one final exact encoding check. Account for JSON separators/escaping, Unicode, changing coverage fields and fixed required content. Keep the existing request-owned observation reuse in production decisions; do not remove freshness reads after waits. A later purpose-specific builder may avoid unwanted fields, but changing which fields count against a budget can change which other information survives. Treat that as a separate context-selection change, not exact equivalence.

**Why it could help.** Changes repeated trimming from roughly removed-records × full-context bytes toward preparation proportional to considered records and one final encoded result. It helps only callers and inputs that reach this preparation. The source establishes repeated encoding, not its fraction of game latency or provider wait.

**Future decision test.** Small and near-limit inventory/memories, Unicode and all required fields through actual invention/world-assistant callers. Compare complete provider-bound context, surviving optional fields, their order and coverage claims. Preserve relevant correction/forgetting and permission checks across asynchronous reads. Measure CPU/allocations through the real caller; a fixture that never invokes it cannot establish a gain. Reject if the exact optimization changes selected content, or if a later selection change is concealed as a byte-counting refactor.
