## PF17.1 — Save new observations without repeating the full edit path

**Priority/status:** first experiment; new refinement of an existing optimization. **Scope:** medium, memory repository and its commit caller. **Intended behavior:** unchanged.

**Code fact.** `writeSources` in [memory-repository.ts](../../../apps/server/src/memory-repository.ts) computes initial eligibility while inserting new rows, but adds every inserted source to `affected`. `reconcile` then evaluates eligibility/dependencies and vector-indexing work for the affected set. Initial eligibility and batching already exist; this proposal must not claim them as new.

**Implementation.** Replace the one undifferentiated affected set with owner-produced categories: genuinely new source, replacement, removal, privacy/correction change and changed dependency. Start with new awareness only. Reuse its insertion eligibility and omit operations meaningful only for a previous version. Still find and reconcile older episodes or summaries referencing that source; a newly arrived observation can supersede older evidence. Queue new eligible sources only for registered embedding models. Keep corrections, forgetting, replacement and unknown cases on the complete path.

**Why it could help.** New observations are common, and the full edit/revocation machinery is more general than their ordinary requirements. [Report 55](../../verification/performance/55-memory-write-plans.md) records selected reconciliation calls visiting rows while changing no eligibility. [Report 35](../../verification/performance/35-memory-catalog-write-counts.md) found genuinely new information, not identical old-body rewrites. Neither proves that every new row is independent.

**First slice and decision.** Compare pure append with an older related episode, a dependent summary, forgotten identities and an active embedding model. Count rows visited, reconciliation operations and queue writes; compare complete stored results and immediate recall. Then measure a busy actual game. Reject if proving independence requires an equally expensive broad query or misses any dependent invalidation. Identity includes world, observer and source family; a same-looking ID does not prove a new source.

### Implementation packet

**Start here.** Trace `WorldService.commit` → `SqlGameRepository.commit` → `MemoryRepository.project`, `WorldRecords.write`, `MemoryRepository.writeSources`, `MemoryRepository.reconcile` and `reconcilePlaces`. In [memory-repository.ts](../../../apps/server/src/memory-repository.ts), read `MemoryChanges`, `sourceKey`, `sourceEligibility`, `refreshQueue`, `registeredModels`, `pending` and `publishVectors` together. `project` sees removals/replacements before writes; `writeSources` currently knows insertion eligibility; `reconcile` owns dependent sources, vectors and pending indexing. The first slice is **new awareness rows only**, with all other kinds using the present complete path.

1. Replace only the internal change description, keeping its owner in the memory repository. Record new exact source keys separately from sources requiring full reconciliation; preserve actor-wide invalidation and changed-place information. Classification must use the canonical row change's creation status and the exact world/actor/family/ID, not a textual ID alone. If a transaction both creates and changes/removes a source, promote it to full reconciliation.
2. Keep the existing insertion-time eligibility calculation, lexical encoding and source revision. Carry its result into the new-source path instead of recomputing it. The proof is transaction-local: no cache may reuse eligibility after another commit, forgetting or correction.
3. For each new awareness ID, find existing memories referring to its event and summaries referring to its source. Pass those dependencies through the complete existing reconciliation. Do not remove these dependency lookups merely because the new row itself has no previous version.
4. For the new row itself, omit only obsolete-version cleanup that cannot apply. Queue eligible new revisions against the transaction's registered models with the existing vector/attempt exclusions and conflict semantics. An in-process model set is not sufficient proof that the durable model rows are unchanged. Preserve `reconcilePlaces` for new place observations.
5. Keep a bounded combined SQL operation for many new observers. Do not turn one batched statement into one query per observer. On rollback discard the transaction-local classification; retry/recovery begins from the actual committed baseline.

**Checkpoint/output.** Before editing reconciliation SQL, write a small truth table in the experiment report: new awareness / linked old episode / linked summary / forgotten event ID / same textual ID in another family / replacement. For each, list required eligibility, vector deletion, queue insertion and place update. The existing vector queue and vector identities do not contain every source-family field used by `recall_sources`; explicitly establish that the proposed fast path cannot cross that boundary. If it cannot, retain the full path for that case and track the identity change with its existing owner instead of assuming IDs never collide.

## PF17.2 — Carry known record changes into saving

**Priority/status:** first, especially older worlds; new extension of existing change tracking. **Scope:** medium and staged by collection. **Intended behavior:** unchanged.

**Code fact.** `WorldRecords.prepare` in [world-records.ts](../../../apps/server/src/world-records.ts) uses `entityChangesBetween` for some entity changes. Other changed map collections build all old entries and traverse all current entries to find differences. The persistent command-result collection avoids some runtime copying, but its `indexed-map` persistence path can still enumerate retained records. [world-record-schema.ts](../../../apps/server/src/world-record-schema.ts) explicitly marks unordered record identities.

**Caller qualification.** Ordinary HTTP gameplay receipts are removed from the world's retained receipt collection by `WorldService.transition` before commit and saved through the separate command repository. Therefore this scan is not automatically a per-walk cost. Trace an actual native operation or other growing collection that changes in the target workload before selecting the first slice.

**Implementation.** Extend the existing mutation/delta lineage to carry touched keys, insertions and deletions into the existing record codec. For a genuinely changing retained native-result collection, appending one result should visit that key and its actual changed path. Do not create a second writable collection or accept an unproved caller hint. Keep full traversal for a missing predecessor, construction, restore and actual reordering. History eviction must remain distinct from deletion.

**Why it could help.** With H retained records and k changes, ordinary preparation can approach k relevant lookups rather than H entries. It removes work before SQL without changing required rows. [The command-tree trial](../../verification/performance/18-command-record-layout.md) does not settle this separate persistence scan.

**First slice and decision.** Identify the real changing collection/caller, then append, change and delete through its actual native/save owners in a large retained collection. Check visited-entry counts, preparation CPU, allocations and full command latency. Include duplicate replay, forks, discarded prepared saves, rollback and reopening. Reject a purported shortcut if it still scans H to verify its own change list, retains unbounded predecessor chains, or cannot detect a nested change. Genuine bulk replacement may remain full-set work. If routine walking never pays the scan, qualify this as a growth/caller improvement rather than a walking fix.

### Implementation packet

**Start here.** Read `WorldRecords.prepare`'s `map` and `indexed-map` branches, its `visit` encoder, and `WORLD_RECORD_SCHEMA`. Compare [draft.ts](../../../packages/domain/src/draft.ts)'s `finishWorld`, `entityChangesBetween` and `entitySuccessors` with [ordered-record.ts](../../../packages/domain/src/ordered-record.ts)'s `orderedRecordSet`/`orderedRecordEntries`. Persistent-tree writes change internal paths; generic draft patches do not automatically identify their logical record keys. Read `SqlGameRepository.prepareCommit`/`commit` and `WorldService.transition` before choosing a receipt example.

**Selected first slice.** Use the inner unordered `mind_exposure` map: `world.perceptionEpisodes[observerId]`, declared as `perceptionEpisodes.$` under `mind_exposure_owners`. Its entries are subject ID → perception-episode ID strings. In [kernel.ts](../../../packages/domain/src/kernel.ts), `updateEncounters` inserts/removes bindings as visible people/objects change, and `retirePerceptionEpisodes` deletes bindings when participation ends; [living.ts](../../../packages/domain/src/living.ts)'s `reconcileBody` can replace one observer's map with an empty map. Trace these real paths through `finishWorld` and saving. This first slice skips unchanged bindings inside a changed observer map; it does **not** remove the outer observer-map scan or claim growth with all historical receipts. If a later baseline finds that this active-visibility collection is too small/infrequent to matter, close the slice as low-value instead of building generic infrastructure. The next separate option is logical-key tracking at the ordered-record owner for a demonstrated native-receipt caller.

1. In `finishWorld`, recognize patches beneath `perceptionEpisodes / observerId / subjectId` and collect changed subject IDs per exact observer map. These values are strings, so insertion, replacement and deletion cover its entry mutations. Replacement of the root or entire observer map invalidates that map's incremental proof rather than enumerating it just to build a key set. Preserve no-op identity.
2. Publish bounded, process-local predecessor/successor metadata using the existing entity-lineage pattern. It certifies one exact immutable predecessor and successor; serialized copies, forks, missing/collected links and overlong chains return “unknown.” Do not serialize this metadata or keep strong references to whole predecessor worlds.
3. In `WorldRecords.prepare`, request the proof for the exact accepted baseline and candidate. For each touched key, use the existing `visit` function on previous/current values, including insertion and deletion. Permit this only where the schema says order is irrelevant; retain current position/order behavior everywhere else.
4. Keep the complete traversal for unknown lineage, construction, restore, bulk replacement and unsupported collections. Missing a proof costs time, never correctness. Distinguish removal from hot memory from deletion of the durable record according to the existing history-retention owner.
5. If extending to `OrderedRecord`, have its mutation owner record logical keys and exact old/new roots. Explicitly invalidate on untracked/root replacement or any permitted nested mutation. Only then consume that proof through the same codec. Do not add a second general diff engine or parallel collection authority.

**Checkpoint/output.** The report must confirm the named schema child and writers remain current and show actual visibility entry/exit in the selected workload. Include a table of patch shapes → observer/subject key or fallback, including `reconcileBody`'s map replacement. If that table cannot cover all legitimate writers, keep fallback for the uncovered cases; do not label the fast path complete. Report active bindings per changed observer separately from retained historical records.

## PF17.3 — One durable personal account with several read views

**Priority/status:** larger architecture candidate after the cheaper append-path work. **Scope:** large; canonical record, history, memory and recovery owners. **Intended behavior:** unchanged knowledge and history.

**Code fact.** Awareness is represented in [world-record-schema.ts](../../../apps/server/src/world-record-schema.ts); `HistoryRepository.project` in [history.ts](../../../apps/server/src/history.ts) serializes personal historical evidence; `MemoryRepository.writeSources` extracts text and search metadata into another representation. These have different consumers and are not simply interchangeable duplicate rows.

**Implementation.** Give one durable personal account ownership of the observer's exact evidence, wording, source links and lifetime. Let hot awareness, historical display and search reference that account, with only the indexed columns their reads require. References bind the exact world, observer, source family, identity and revision. Keep required prior versions; editing one current account must not silently replace every historical reference. Current correction/forgetting rules still govern disclosure. Keep global event facts separate from personal perspective. Two witnesses must retain different permitted accounts even when they saw the same event. Start with one new awareness family; avoid redesigning every history family at once.

**Why it could help.** This can remove repeated encoding, repeated text bytes and maintenance across several tables. It addresses the volume of genuinely new accounts identified in [reports 23](../../verification/performance/23-witness-record-removal.md) and [35](../../verification/performance/35-memory-catalog-write-counts.md). It does not eliminate the real number of witnesses: cost can still grow with events × recipients.

**First slice and decision.** One event with several different perspectives, hot-tail eviction, immediate history/recall, correction and forgetting. Compare stored/serialized bytes, write work, complete save time and old-history read cost. Keep source ownership after hot eviction and revoke dependent access atomically. Reject if read joins/hydration or retained lifetime cost outweigh the write reduction. This is representation consolidation, not shared omniscient memory or deletion of precise historical evidence.

### Implementation packet

**Start here.** Trace [events.ts](../../../packages/domain/src/events.ts) `recordEvent` → [event-observation.ts](../../../packages/domain/src/event-observation.ts) `observeEvent` → [experience.ts](../../../packages/domain/src/experience.ts) `acquireEventAwareness`. Then follow `prepareHistory`, `HistoryRepository.project`, `MemoryRepository.project`/`writeSources`, `hydrate`/`current`, `WorldRecords.prepare`/`load`, and `SqlGameRepository.releaseHistory`/`adoptHistory`. The same event can produce detailed, partial or private accounts; shared event identity does not make their bodies equal.

**Proposed contract.** For the first awareness family, one immutable durable account version owns the exact captured observer evidence and personal wording. Its key is `(world, observer, source family, source ID, revision)`; a separate current-source reference selects the current version. Distinguish current history-display references from evidence explicitly bound to a prior version. `HistoryRepository.project` currently updates the displayed `history_perspectives` account when awareness is edited and revokes dependent stories: preserve that behavior by advancing the display reference. Only references whose existing contract binds a prior version keep it, subject to current disclosure rules. Search metadata may duplicate indexed fields, but must resolve its body through the required exact account. Global event facts remain separately authoritative. Hot awareness remains the current domain representation and materializes from the same account on load; it is not another independently editable durable body.

1. Inventory the actual fields read from awareness, history's `StorySource`/`eventEvidence`, the consumers in [perceived-events.ts](../../../apps/server/src/perceived-events.ts), recall rows and retained source versions. Produce a field map assigning each to the canonical account, global event or a rebuildable projection. Preserve historical display time/order/type and story-selection metadata even where they are not part of the evidence body.
2. Introduce the account version and references in the current schema and record codec together. Insert each account version once within the existing commit transaction, before dependent references. Use the repository's exact revision encoding; do not replace an observer-specific revision with a global event revision.
3. Switch `HistoryRepository.project` and the awareness branch of `writeSources` to references plus their required indexed columns. Hydration must batch exact keys for a page/context; avoid one query per displayed memory. Private read caches include the exact version and remain subject to current disclosure fences.
4. Make replacement create a new version and update current-source and current history-display references atomically, preserving existing dependent-story revocation. Explicit prior-version evidence references remain bound to their version only where the current contract requires it; do not freeze all history displays at their original text. Forgetting and correction revoke both relevant source and event identities; retained bytes are not permission to reveal them.
5. Define retention from actual owners: hot-tail eviction alone cannot delete accounts needed by durable history, summaries or required decision evidence. Account garbage collection may remove only versions with no remaining legitimate retention owner and no required audit/correction obligation. Do not place cleanup on every ordinary save.
6. Update current-format restoration, checkpoint table coverage and validation before integrating the first family. No legacy reader or parallel old schema remains solely to preserve development saves.

**Checkpoint/output.** Complete the field map, exact foreign-key/reference graph, current-versus-historical revision rules, and a consumer matrix covering history display, recall/context, private inspection, correction/forgetting, checkpoint and restore. For every old body copy, state which consumer now hydrates it and in how many queries. This is the reviewable design gate; unknown consumers cannot be postponed until after deleting a representation.

## PF17.4 — Prepare search projections after durable source saving

**Priority/status:** larger architecture option; changes what the command waits for. **Scope:** large, storage plus every affected search consumer. **Initial behavior target:** immediate correct evidence remains available.

**Code fact.** `SqlGameRepository.commit` in [store.ts](../../../apps/server/src/store.ts) performs source projection, writes and reconciliation before the transaction finishes. Search indexes in [memory-repository.ts](../../../apps/server/src/memory-repository.ts) add write work. Background vector generation already exists; the rest of this search preparation is not thereby asynchronous.

**Implementation.** Keep exact source records, command result, revision and a compact durable pending-search record in the canonical transaction. Move one derived projection, initially lexical search, to bounded processing after commit. Pending work binds the world generation and exact source revisions; publication rechecks them and rejects obsolete work. Readers must merge indexed results with the committed pending suffix, or explicitly await the required revision. Forgetting, correction and access revocation take effect immediately through current fences, regardless of worker progress. Do not label missing preparation “no memory.”

**Why it could help.** This shortens the command's critical path and can combine superseded derived updates. Merely moving work does not reduce total CPU or sustainable throughput. Test whether search maintenance is really the limiting dependency before expanding the design.

**First slice and decision.** Save an observation, immediately search it, correct/forget it before background processing, restart midway, and compare all permitted answers. Let old work finish after restore, source replacement or forgetting and prove it cannot republish obsolete entries. Measure confirmation latency, total CPU/I/O, oldest pending revision, pending bytes and worst catch-up. An expanding queue is a regression. The selected first contract keeps exact evidence immediately available but lets lexical search wait or truthfully report temporary unavailability; this timing tradeoff must be measured and reported. Successful stale/empty search is never a substitute. Reuse the current durable work owner where it can express these dependencies.

### Implementation packet

**Start here.** In `SqlGameRepository.commit`, distinguish canonical records, disclosure/eligibility changes, lexical preparation and vector queue work. In `MemoryRepository`, inventory `context`, `conversationSources`, `entry`, `page`/`readPage`, `commitments`, `browse`, `knownPlaces`, `maintenanceBatch`, `selectContext`, `hydrate`, `current` and vector publication. `knownPlaces` reads `search_text` and applies `matchesSearch` when terms are supplied; it is also a lexical consumer. Then follow each reader's `WorldService` caller and its post-await privacy checks. Current vector background work does not supply a safe lexical-read contract automatically.

**Selected first contract.** Defer **lexical document/index preparation only**. Keep canonical source versions, current eligibility, revocations, command receipts and required evidence usable in the committing transaction. Bind durable work to `WorldRecords.head().generation` / `world_head.generation` and its committed revision. The separate `WorldService.generation` is process-local and changes on restart; it cannot identify resumable durable work. A lexical read explicitly waits for projection coverage of its required durable generation/revision, then verifies coverage in the actual read snapshot; direct exact-source evidence reads continue from canonical storage. A wait that exceeds the caller's existing bound returns an explicit preparation-unavailable/stale outcome through that caller's contract, never an empty answer interpreted as “the character remembers nothing.” Pending-source merging is a possible later alternative, not a second first implementation.

1. Separate lexical derived fields from the canonical source/eligibility owner so canonical insertion can avoid the lexical index work being deferred. Define a durable pending item containing world generation, committed revision, exact source key/revision and operation (prepare/remove). Insert or supersede it atomically with the source. Do not copy whole worlds into jobs.
2. Process bounded groups through the existing database write authority. Read the exact committed source body, produce the same lexical representation, then recheck source revision, generation and current eligibility in the publication transaction. An obsolete item is completed/discarded without publishing its old body. Queue ownership must prevent two workers from treating the same item as independently current.
3. Advance a projection watermark only when every required earlier item for that world generation is resolved. A later completed item cannot hide an earlier hole. Coalescing superseded work must mark the superseded revisions as resolved while retaining the current exact source revision.
4. Route lexical consumers through one readiness operation before their read transaction; do not hold the writer lane or a database snapshot while waiting for work that needs that lane. Within the actual read snapshot, check its durable generation, committed revision and lexical coverage together. If a newer change committed after the first wait, release the snapshot and await the newly required coverage within the caller's original bound, or return explicit unavailability. Join lexical documents to exact canonical source revisions so obsolete text cannot match a replacement body. Cached selections also need coverage/generation binding: rechecking only selected rows does not prove newly searchable rows were considered. After readiness, retain each caller's current authority/evidence check. Search may wait longer than walking; that cost is part of the comparison.
5. Keep immediate forgetting/correction/access checks at canonical read and publication boundaries. Deleting an old lexical document later is cleanup, not the privacy mechanism. Reopen resumes durable pending items; restore changes generation so pre-restore workers cannot publish into restored data.
6. Bound each worker batch and total pending bytes using an explicit admission/backpressure rule. Proposed rule: stop accepting further projection debt at the selected bound and use the existing explicit busy/persistence behavior, without acknowledging and silently dropping evidence. Select and document the bound from later sustained-load measurements; no arbitrary limit is adopted here.

**Checkpoint/output.** Before changing the transaction, produce a read-surface table with “exact read” or “requires lexical revision,” the existing caller timeout/refusal outcome, and post-wait fence. Also produce the pending-item schema, watermark algorithm, same-writer scheduling order, crash/retry state table and selected backlog rule. If an existing consumer cannot truthfully report temporary unavailability, update its contract as part of this slice before enabling deferral. A worker that can indefinitely starve commands or itself does not satisfy this design.

This architecture and PF17.8 are alternatives to evaluate separately before combining.

## PF17.5 — World-authored episodes for routine observation

**October17, 2026, 13:07 EDT disposition:** the real source-preserving grouping trial is rejected for the zero-provider target workload: optional choices shrink, but extra summaries/links increase saving and indexing work, and that workload never consumes the optional-model saving. No automatic policy is adopted. [Order-balanced results and exact scope](../../verification/performance/overhaul-compromises.md#result-grouping-preserved-sources-but-added-saving-work). The original packet below remains a future alternative for a different measured workload, not current behavior.

**Priority/status:** explicit gameplay experiment; potentially reduces work at its source. **Scope:** large, event/awareness policy through memory and ordinary character behavior.

**Code fact.** `HistoryRepository.project` expands event audiences into individual accounts, and `writeSources` makes those accounts searchable. Domain/world event production determines how many accounts exist before storage can optimize them. Removing all bystander accounts in [report 23](../../verification/performance/23-witness-record-removal.md) removed useful behavior and was not a finished solution.

**Implementation.** Extend the existing episode/awareness owners for one world-declared routine activity. ## PF17.8 — A durable change journal before table materialization

**Current implementation status — October17,2026:** the general journal is implemented for eligible changes, with ordered application, read fencing, bounded debt and recovery. Narrow contained-item creation also passes finite checks. Other families remain synchronous, including the currently investigated character-decision completion records. Complete throughput benefit and smooth3× remain unproven; this is partial PF17.8 delivery. Follow the [current journal contract](journal-contract.md) and [saving results](../../verification/performance/overhaul-storage-implementation.md).

**Historical October16 disposition:** the earlier restricted existing-payload-only variant was rejected after12real walking/route/native transitions; only the two already-background route-preparation changes qualified. At that time the general journal was an unimplemented alternative. The [earlier source/caller inventory](../../verification/performance/overhaul-implementation.md#pf178--journal-feasibility-and-rejected-restricted-variant) records that narrower rejection, not the current general implementation.

**Priority/status:** high-risk architecture under implementation and evaluation. **Scope:** very large, changes a central persistence contract. The following packet records the original proposal; the current contract above owns implemented details.

**Code fact.** [store.ts](../../../apps/server/src/store.ts) already represents prepared exact changes and coordinates a single ordered commit. Today's table writes and derived maintenance are part of that commit. Existing [background saves](../ordered-async-saves.md) do not make command acknowledgement independent of those writes.

**Implementation option.** In the existing PostgreSQL authority, durably append a complete ordered transition record with its accepted result, exact changes, required events/evidence, randomness and applicable authorization dependencies. Query tables become materialized views of the journal through a known revision. Commands are acknowledged only after the durable append. Do not record just a command that would require rerunning AI or guessing changed world state during recovery. This is not a second local database or an unprotected in-memory queue.

**Why it could help.** It changes the critical path from many indexed row updates toward a compact append. Later application may combine replaceable current values while retaining every distinct event, receipt and meaningful effect. Total work and payload size may still be substantial, and some immediate integrity updates must remain synchronous.

**Required design before code.** Resolve canonical reads from the committed overlay, transaction/foreign-key validation, head conflicts, external accounting, privacy revocation, bounded journal growth, checkpoint coverage and safe pruning. Restoring must reproduce acknowledged outcomes exactly, never execute them twice or regain obsolete permission. This revisits the existing durability/storage-placement decision; the current catalog-based contract remains in force.

**First slice and decision.** Only after a separate complete recovery design, implement one transition family and test failure after every append/apply/acknowledgement boundary. Compare durable command delay, total work, backlog, restart time and older-world reads. Reject if overlay/recovery complexity or continuously growing application debt defeats the gain. This is an alternative to some smaller storage architectures, not a mandatory final layer added to all of them.

### Implementation packet

**Start here.** Read `WorldService.mutate`/`runMutation`/`commit`/`saveProgress`/`commitProgress`, `SqlGameRepository.prepareCommit`/`commit` and its after-commit/rollback hooks, `WorldRecords.advance`/`write`/`load`, `CommandReceipts`, and [GameSaves](../../../apps/server/src/game-saves.ts)/[checkpoint](../../../apps/server/src/checkpoint.ts). The present accepted revision is a table-backed world revision. This proposal must replace that meaning coherently, not leave ordinary readers using the old meaning while commands acknowledge a newer one.

**Proposed durable contract.** PostgreSQL remains the single durable authority. A world has a durable generation and two explicit revisions: **committed**, whose exact changes are durable and may be acknowledged, and **applied**, through which query tables have been updated. Extend the persisted `world_head` / `WorldRecords.head()` contract for these heads; the process-local `WorldService.generation` is not a recoverable journal identity. Each journal row uniquely identifies `(world, generation, next committed revision)`, names its expected predecessor, and contains the complete validated record changes, exact event/personal evidence changes, saved randomness/sequence consequences and accepted command result. Data required for recovery is encoded in the row or referenced by immutable durable identity in the same transaction. Mutable process objects and instructions to rerun a command are not recovery data.

1. Keep one ordered writer. Within one PostgreSQL transaction, check the expected committed head and current authorization/control dependencies, append the exact transition and advance the committed head. Persist command identity/result and any required nonrewindable operational/accounting changes atomically where their existing owners require them. Only after this transaction commits may `WorldService` install/confirm the outcome.
2. Validate everything needed to ensure the accepted change can later be applied **before acknowledgement**. Reuse domain/current-format validators and enumerate remaining table constraints that currently protect references or uniqueness. The proposed first slice excludes external paid effects and requires the design to prove each affected constraint against the committed world plus journal changes. “Let materialization discover a broken foreign key later” is not an acceptable contract.
3. Apply journal entries strictly in revision order. For one revision, perform its exact changes and advance the applied head in one transaction. Reapplying an already applied revision is a no-op; a gap or wrong predecessor refuses. Initially do not coalesce revisions: prove exact recovery first. Any later coalescing may combine only replaceable current values, never distinct events, receipts, spending or irreversible effects.
4. Establish a single read revision. The live service's committed immutable world supplies current simulation decisions. Exact persistent-record reads use a bounded overlay of committed journal changes on applied tables; reads that cannot implement a correct overlay explicitly await application through their captured revision. No read can mix current world facts with older permissions or quietly treat unapplied history as absent. After any wait, recheck current disclosure/authority.
5. Keep revocations and nonrewindable authorization/spending at their existing immediate durable owners; journal lag cannot revive access. On restart, load applied tables and replay exact committed changes through the head before accepting new commands. Replay installs results and randomness, not commands, models, purchases or notifications. Ambiguous acknowledgement resolves by durable command identity/result.
6. For the first checkpoint implementation, wait until applied equals a captured committed head, then capture one consistent database revision using the existing checkpoint owner. Admit no checkpoint claiming newer coverage than its captured tables. Restore establishes a new generation and invalidates obsolete materializer/read work; it preserves current nonrewindable accounting and revocation rules. Prune journal entries only after a validated checkpoint/recovery policy proves they are no longer required for exact recovery or retained audit.
7. Bound committed-but-unapplied bytes and revision count. Proposed overload behavior is to stop admitting more deferred debt and finish applying existing accepted work before accepting another transition; return the existing truthful busy/persistence outcome when the request bound expires. Never drop journal rows or acknowledge changes whose recovery bytes were not committed. Choose measured limits before production adoption.

**Checkpoint/output required before runtime code.** Produce one reviewed contract table covering every write currently inside `SqlGameRepository.commit`: journal payload, immediate atomic operational write, later applied write, or explicitly unaffected. Produce a reader table identifying overlay versus wait and its exact revision/fence; a constraint table proving pre-acknowledgement validation; and a recovery state table for the boundaries below. Name checkpoint/pruning coverage and overload behavior. These artifacts instantiate the proposed contract, expose remaining caller-specific choices and determine whether this architecture is feasible. A missing row in any table is unfinished design, not permission to rely on process memory.

**Narrow first implementation after that checkpoint.** Use one ordinary deterministic local movement transition with no provider work, while journaling **all** of its resulting changes, including generated observations and its durable command result. Its first shadow comparison can build/validate a journal record without changing acknowledgement; that measures encoding/size and correctness only. Switching acknowledgement to the append requires the complete recovery/read behavior for that transition, not merely a faster insert. Unsupported transitions must synchronously bring applied tables to the committed head and use a single coherent authority contract; they must not alternate between incompatible definitions of the durable baseline.
