## 1. Intended play and evidence

[Sections 12–14](#12-command-receipt-admission-and-operational-reads) specify the BK28 source conversion, implemented November 7, 2026; connected checks and conditional adoption remain open in BK28.

[Section 11](#11-history-intent-and-metadata-read-repairs) specifies the installed repairs exposed by the [reviewed-runtime investigation](../verification/performance/bookkeeping/2026/2026-11-06-reviewed-runtime-isolation.md), plus the unadopted conditional batching of real edits. Its requirements extend the owners below; [current connected evidence](../verification/performance/bookkeeping/2026/2026-11-06-shared-confirmation.md) qualifies the asynchronous save/read cases independently of earlier passes.

People should move and respond while storage catches up within a bounded allowance. A witness can remember the order of an encounter, recognize someone later without retaining their old walking coordinates, keep a promise's actual terms, and compare a personal recollection with an independently acquired historical record. Different witnesses can honestly disagree. These are the useful capabilities this work protects; it adds no compulsory model call, omniscient replay, narrative episode classifier or new sensory producer.

The [query-level assessment](../verification/performance/2026-10/bookkeeping-simplification.md#november-1--query-level-assessment) owns measurements. Its completed two-minute trace contains 16,935 database calls: 6,781 retention preparation/proof calls, 898 derived-quota enumerations returning 206,204 metadata rows, and 117.09 MB of standalone current-contact parameters. No LLM cognition turn or embedding generation ran. Native evidence ingestion and saving create the work independently of cognition. The earlier 20,293-call capture lacks query-level detail; do not present the newer breakdown as its reconstruction or an optimization gain. CPU, driver elapsed, writer waiting, bytes, row changes and calls are different units.

There is already one ordered writer, one accumulating save buffer, an independent read lane, grouped SQL, background native saves and physical garbage collection. Extend these owners. No second journal, message broker, evidence store, generic event bus or duplicate cold catalogue is selected. The implementation should first remove unnecessary operations, then batch remaining work. Moving an unchanged query to another thread is not a work reduction.

## 2. Ownership and change information

| Existing owner                                        | Target responsibility                                                                                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Domain reception/current/temporal owners              | Actual received changes, independent detail timing, exact recent sequence and native pool counters; no SQL or wall clocks            |
| Recognition, knowledge, experience and action owners  | Admit meaningful lasting accounts and their minimum support, preserve original acquisition and source-correction identity            |
| `WorldRecords`, existing append/changed-key lineage   | Carry proved create/update/remove intent and touched fields to storage; pure preparation, no writes to inspected live state          |
| `WorldService` and `WorldStore` / `SqlGameRepository` | Accept one coherent transition, capture an immutable save cut, combine pending changes and publish/save in order                     |
| `RetentionMetadata` and existing retention owner      | Select maintenance from due/pressure actors; prepare bounded cold work outside simulation mutation; publish an exact eligible result |
| `ReceivedValueOwnership`                              | Apply actual owner/value set differences and collect unreachable stored values                                                       |
| Memory repository / lexical owner                     | Exact source eligibility, current recall and batched optional search preparation                                                     |
| Authority repository                                  | Current session/grant/control generations and durable changes to them                                                                |
| History repository / player-view projection           | Personal history and player-only narration; no narrator-to-cognition feedback                                                        |

Extend existing typed change results with only information these consumers need: certified fresh identity; changed contact groups and metadata; appended receipt range; exact removed/rewritten receipt ranges; new/released support; owner/value additions/removals. These are finite transition-local inputs, folded into the existing pending buffer and discarded after settlement. They are not a new saved event log.

One typed pending-write entry identifies the existing canonical record key, creation proof when available, changed column mask, captured final values and actual logical removals. Coalescing takes the union of masks and newest values; a deletion replaces a pending current-row update. A fresh insert followed by deletion can disappear only if no retained event, receipt or support needs that identity. Historical appends are separate ordered suffixes and never collapse into the current-row entry. Owners emit these results; for proved lineage the writer must not rediscover them by diffing whole worlds or querying SQL.

Creation proof comes from the identity-allocating mutation and its unchanged lineage. Appending to a partially loaded list, seeing no resident predecessor, or an empty SQL lookup is not proof. Unknown lineage, imported replacement and true edits retain the scoped comparison path. Use complete `(world, actor, source family, source identity, revision)` keys; namespaces and punctuation inside IDs are valid. A metadata-only contact update cannot be recast as a new acquisition.

## 3. Separate event history, recent detail and learned knowledge

### 3.1 Retention purpose, not a movement blacklist

The installed world owns event importance, admission and memory lifetimes. The engine provides typed retention operations. Preserve the current base targets in [recent history and lasting memory](../worlds/base/attention.md#recent-history-and-lasting-memory); no engine-wide rule says every movement is trivial or every spoken sentence permanent.

Learning that an earlier claim was false is new personal evidence, not an editorial source deletion: the character can still remember hearing the claim. Likewise, revising an impression need not erase the experienced event. The existing source-correction/explicit-forgetting owner handles actual withdrawal; ordinary disagreement, changed belief and fictional deception do not gain that authority.

| Record purpose                                                   | Availability and storage consequence                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current perception                                               | Latest actually received state plus independent freshness/availability. Replacement does not by itself create lasting memory.                                                                                                                                             |
| Recent detailed observations                                     | Finite chronological buffer; age and selected pressure boundaries determine access. Movement, activity and other changes use the same mechanism.                                                                                                                          |
| Lasting personal knowledge / exact account / fallible impression | Own admission, significance, reinforcement and retention. Minimum necessary support is owned independently of the original recent chunk.                                                                                                                                  |
| Active required account                                          | Preserve required terms/support until its native obligation ends; optional pressure cannot evict it.                                                                                                                                                                      |
| Exact ordinary speech                                            | Its existing separate finite tail; understood words and attribution remain exact while available.                                                                                                                                                                         |
| Admitted world event archive                                     | Continue the existing event/history owner's archiving. Personal forgetting or zero personal references is not permission to delete a historical world event. This project adds no automatic archive deletion and no new promise to record all simulation changes forever. |
| Search/index/scheduling helpers                                  | Rebuildable or replaceable; no independent power to retain or reveal knowledge.                                                                                                                                                                                           |

An unreferenced shared payload is storage garbage only after the legitimate retaining owners have released it. An archive entry either owns its complete body or registers its actual shared-value uses; a personal reference count cannot stand in for archive ownership. Reference count is not a gameplay importance score. A route that matters can support a retained account under existing policy; coordinates are not made permanent merely because another actor or the global archive still stores related information. This preserves historical investigation without giving an NPC access to unreceived world history.

### 3.2 Independent support at admission

When a learned name, recognition association, Known place, learned method, exact summary or obligation is admitted, its existing owner installs the smallest sufficient support in the same native transition. Small necessary facts are copied once into the existing support capsule; substantial immutable received values retain exact owner links. Record source kind/identity/revision and ranges for later correction. An exact quotation keeps its actual words. An impression explicitly lacks exact quotation/path authority. Do not retain the source's whole recent chunk, and do not recreate evidence from today's world state.

Existing BK03 capsules and source-version support are reused. Audit every consumer before removing routine survival queries. A candidate that needs cold support prepares it outside the mutation turn, then rechecks the exact sources before admission. No half-installed knowledge is published. Optional material that cannot fit its existing allowance is declined; a required operation must reserve its support before effects are accepted. There is no summary/model call at expiration.

Exact summary dependencies and correction propagation remain indexed and source-specific. The source body may reside in the summary's owned support after its original recent receipt expires. Metadata identifying the origin does not grant the deleted receipt's broader content. Ordinary history retirement must not remove an independently supported name, promise or place.

### 3.3 Recent-only individuals and aliases

Do not scan cold history to decide whether every formerly seen individual still has a reference. Extend the existing local-individual owner with its newest retained recent-reference locator/time, and use existing current-contact and independently retained support links. Update the newest locator once per changed acquisition/subject, not per field; unchanged ordinary reads do nothing. A locator exists only for an admitted actual reference.

Recent-prefix expiry compares this locator with the actor's canonical retention frontier and age cutoff. An individual still used by a current contact or independent lasting/required owner remains. Otherwise an expired recent-only individual can become unavailable and its allocation can be reclaimed by scoped maintenance. These stamps are liveness metadata only: they never prove a true identity, learned name, recognition, relationship or additional sensory reception. Recognition/familiarity continue to use their selected semantic owners.

This optimization relies on ordered recent admission. A sparse correction/deletion that removes the newest qualifying reference uses one batched targeted survivor lookup for affected individuals, or an existing independently valid support. It cannot assume no earlier surviving reference exists. Parent/actor deletion remains explicit. Do not add a lifetime alias count table or per-field dependency ledger. Rebuild the bounded metadata from eligible sources during cold activation/validation, then update it incrementally; inactive actors are processed on activation or a selected cold request, not polled every tick.

### 3.4 Expiration and preparation

Age eligibility is evaluated from the supplied game-time cut and existing retained-prefix boundary, without a database write per expired receipt. Current-detail freshness has its own clocks and is not a recent-history retention timer.

Maintain the existing native counters and next due time. An actor becomes a maintenance candidate only when age crosses a relevant boundary, a pool reaches its target, or an actual account edit/removal changes dependencies. Coalesce candidates by actor in the existing scheduler. Deadlines for fictional aging use game time: stop while paused and recalculate the next host wake when speed changes. Save and physical-cleanup deadlines use monotonic real time. A due actor remains marked while preparation is running; combine new dirty causes and recheck before clearing the mark so a change during an await is not lost. No recurring all-actor scan or permanently immediate timer replaces save-time preparation.

1. Capture actor/life/epoch, retention frontier, relevant source revisions and native totals. Read bounded selected headers at one database revision through the existing read lane, outside the game mutation queue.
2. Select the oldest eligible prefix from headers. For ordinary whole-prefix retirement, do not hydrate segment bodies, collect every alias, query all lasting-account tables or run generic summary/source-version closure.
3. Under a short native transition, validate the exact selected prefix and sources. Appends beyond that prefix do not invalidate the plan. Use current counters minus the exact removed charges; new suffixes retain their own charges. A modified selected chunk/source invalidates only its affected plan.
4. Advance the canonical frontier and update native totals once. Persist that change with the next save. Physical chunks can remain until collection; no reader may treat their physical presence as personal access.
5. Continue due/pressure work in bounded slices. A historical read pending during expiry rechecks current eligibility before new disclosure. An already admitted finite thought retains its detached input under the distinct [BK24 pending-capture contract](bookkeeping-simplification-tech-design.md#meaningful-knowledge-identity-and-delayed-interpretation); explicit correction/forgetting and current action authority still fence publication.

Recent history and replaceable optional accounts gain bounded maintenance headroom as specified in BKS-L06: target sizes and age rules stay unchanged, but pressure retirement may finish after the target is crossed. At the hard admission ceiling, stop adding optional detail with explicit missing coverage; never stall physical time or delete required support to pretend the optional buffer fits. This is overload behavior, not acceptable normal performance. Ordinary exact speech has its own 25% maintenance headroom in the installed world profile; it does not borrow optional capacity or silently drop required words at its hard ceiling. Its target remains 512 sources / 8 MiB. Required-account limits remain strict at creation. Lasting knowledge and its independently owned minimum support also keep the original target ceiling; they have no pressure-eviction owner. No parent task can pass by routinely exhausting headroom.

Required accounts retain their strict admission ceiling. Pressure cleanup of unprotected aftermath starts at `(1 - maintenanceHeadroom)` of that ceiling (75% in the base world), leaving room for new required outcomes while preparation runs. Active obligations and independent learned support remain protected. A prepared plan preserves newly raised required pressure, and missing accounting installs only from complete canonical totals. Recent and account slices share a transient fair actor selector over the existing deadline index; an actor remaining due cannot monopolize the first 32 positions. A plan invalidates native Known-place preparation only when its exact selected place sources changed; non-place aftermath/deadline work preserves the complete index. Native cold installation uses that owner’s place-specific token alongside existing life/privacy/generation checks.

Unknown/corrected dependencies still use a scoped closure. Batch all requested actor/family/source/person keys in one statement per bounded input batch, returning the captured revision even when no matches exist. Select relevant live pages first, then evaluate exact requested memberships. Do not cross join each candidate against every retained page or expand unrelated page arrays. Pending replacements/removals are part of the query input. Reuse unchanged cold inputs across closure rounds; never reuse a negative proof after a relevant dependency changes. The writer performs one final expected-revision check for its complete save, rather than each helper opening its own revision transaction.

## 4. Write only the data that changed

### 4.1 Current contacts

Within the existing current-perception tables, separate stable group content columns from small timing/availability/recording columns. Keep a single native authority; this is a persistence mapping, not a second current-state store. Stable content includes actual received value references and membership/declaration identity. Metadata includes independent checked/measurement times, unchecked/availability state and recording cursors; do not merge independent clocks merely to reduce columns.

For `mind_perception_current`, retain one row per contact. `payload` holds contact/field order, originals and immutable received grants/typed fields; `metadata` holds sight, independent freshness scopes and compact last-recorded-content/coverage continuation. Recording stores no carried binding or predecessor proof dictionary. The exhaustive current codec keeps freshness-only writes independent of content encoding; scoped typed readers address actual current values directly.

The current-record encoder consumes the typed received change and emits one of: insert a contact, replace its affected content and metadata, update metadata only, remove the contact. Batch equal column shapes. Metadata-only writes do not serialize stable descriptions or rebuild value-reference arrays/index projections. SQL upserts may be used for unknown existing identities, never to hide a collision of a certified fresh immutable identity.

In the pending buffer, keep the newest current state per key and union its changed-column set. Preserve all admitted chronological operations separately in original order. Multiple confirmations may become one current-row update, but any retained historical check times remain in their existing packed sequence. Don't substitute a last position for an attended route. A genuinely unchanged result emits no write.

### 4.2 Canonical accounts and derived work

For an uncertain history-event replacement, retain the exact predecessor lookup; a confirmed missing row skips empty derivative/perspective/event cleanup. A real rewrite or removal still invalidates its actual narration and dependencies. Certified new memories/awareness/summary records insert directly and install their known dependency set. They skip old-body SELECTs, old-source DELETEs, version-archive probes and old-vector reuse. A source identity collision fails the existing creation boundary. Prepared direct expiry without a surviving replacement uses its exact native source identity and prepared actor-version scope, with no old-row discovery. Uncertain replacements/corrections read validated scalar retention class/revision once per batch and retain exact private archive/dependency checks; source bodies are read only by consumers needing their content. Independent artifact invalidations and actor compaction keys use the existing bounded batch owner.

Apply logical removal intent to history permissions. Extending a physical segment has no removal intent and cannot call `retireTemporalStoryAccounts`. Actual sparse removal supplies exact receipt ranges; whole-chunk retirement removes its personal grants in bounded chunk-key batches while its frontier enforces immediate eligibility. Each temporal grant retains the original `receivedAt` and native `chunkOrder` beside its exact locator, allowing age/frontier filtering before cold body preparation and selection limits. Decode and restoration verify those scalars against the actual receipt/chunk. History readers enforce source eligibility even before physical pruning. Preserve current world-event archives and meaningful action outcomes. Audit completed internal work rows: an entry whose only purpose is scheduling and that can be derived from saved cursors/current state should be transient, with one startup reconstruction; action identity/outcome, randomness, deadlines, permissions and obligations remain saved.

### 4.3 Shared values and SQL batches

The value-using owner emits new/released value IDs at group/chunk/support boundaries. Combine per-owner additions/removals across the pending save and cancel pairs only when the final owner set and all retained chronological owners permit it. Recent append adds genuinely new chunk/value pairs using the existing chunk membership structure; unchanged pairs never reach SQL. Partial correction alone may rebuild an affected chunk's bounded uses.

Reuse `SqlWriteBatch` and `sqlRowBatches`, retaining existing parameter/byte bounds. Encode each body once. Group independent deletes/retirements as well as inserts; flush only for a true data dependency or bound. Projections that need inserted data should consume the incoming typed rows or explicit returned keys, without rereading the same canonical rows. Sibling modifying SQL operations must not depend on unspecified execution order or invisible sibling effects; the repository operation makes that dependency explicit. One statement may contain many operations; metrics must distinguish calls, fragments and affected rows.

## 5. Background helpers with bounded work

### 5.1 Search and derived storage

Exact recent/required reads work from canonical permitted sources regardless of optional search-index lag. A source mutation notifies the existing lexical/derived owner once per actor/source/revision. Coalesce repeated changes to the newest eligible source, retaining removal intent. No event or timer starts a model call simply to maintain storage.

Maintain exact charged usage through the existing derived owner: each actual insertion/replacement/removal supplies its charge delta, with batched SQL RETURNING for unknown cold old sizes. Publish usage only after the owning transaction commits; rollback invalidates that attempted update, and counts come from actual affected rows, not attempted inserts. Reconstruct on initialization/restore, not per tick. It is an accounting projection, never another memory store. Below the target, no eviction-candidate query runs. Above target, retrieve a bounded priority/age-ordered candidate page, delete enough to reach the low watermark, update the same usage total, and yield. Include lexical, vector, cache, queue, text and annotation paths; no writer bypasses accounting. Unknown usage first runs one aggregate query, not full body/row enumeration. Selected policy replacement schedules affected actors once; a zero allowance disables optional artifacts without removing canonical sources.

Use BKS-L06 soft/hard limits for replaceable artifacts. Optional indexing pauses admission when its hard ceiling is reached; it cannot pause simulation. Exact lookup remains available. Vectors are reused only for changed eligible source/model/revision keys for which matching cached work can exist; a certified fresh identity has no previous-source cache. Scope fulfilled-queue deletion to those keys. Indexed recall may await bounded preparation outside mutation, use canonical/recent fallback, or return explicit incomplete optional coverage; it must never return revoked or misattributed evidence. Deliberately skipped/evicted lexical coverage leaves an actor-scoped omission marker in the existing progress owner; queue draining cannot clear it or fabricate completeness. Pending sources likewise cannot use older indexed coverage. Literal browse/known-place reads decode missing cached text from canonical sources. Required facts keep exact source fencing and completeness independently of optional artifacts.

### 5.2 Physical cleanup

Logical availability changes in the native/retention owners; physical deletion does not decide gameplay. Keep the existing collector and reverse-use check. Coalesce notifications and run one bounded slice only when its next permitted maintenance opportunity arrives. A nonempty slice does not immediately requeue an unlimited drain. Give due foreground persistence first turn; reserve finite cleanup service so permanent foreground activity cannot starve it. BKS-L07 owns cadence/work limits and debt escalation.

Rows retired only in an unsaved cut cannot be physically collected yet. Every new pending reference is either backed by a still-eligible durable owner or is a new value held by the pending buffer. Commit additions/replacements and released uses together. Payload caches cannot reacquire an otherwise unowned value. Read complete finite closures in one bounded snapshot, then release the connection and recheck authority on consumption. No temporary pins or per-reader durable reference rows.

Measure deletion throughput, retired bytes, oldest debt and index/table growth. If debt grows under normal load, the implementation fails sustained acceptance even if the world keeps moving. Storage exhaustion retains an explicit failure boundary; asynchronous deletion is not a claim of unlimited capacity.

### 5.3 Sessions, controls and story display

Reuse AuthorityRepository's existing session/grant/control maps and publication generation. Establish token-to-session identity on first use, retain only bounded unexpired entries and invalidate through every actual authority mutation. Routine request checks compare the current owner-held session/grant/control values and expiration; commands recheck after waiting. Unknown entries load through one combined indexed query and share an in-flight lookup. Never rerun external login for ordinary requests.

Before this conversion, enumerate all writers: logout, account replacement, grant edits, control transfer, operational setup and restore. Normal writes must flow through this owner; an out-of-process administrative write requires existing coordination/invalidation or must be offline. If any supported concurrent authority writer cannot notify this owner, retain the current database check for that path. Do not invent distributed invalidation infrastructure to save 469 queries. Protected access mutations themselves remain durable and atomic.

**Implemented BK24 boundary:** ordinary service-owned commands enter the world mutation lane at their actual admission turn. `/api/command` and `/api/input` use service-owned entry points; cold receipt and Known-place/trade preparation remain outside the lane. Current authority, writer health, request identity and gameplay dependencies are rechecked immediately before accepting effects. Other routes retain their existing guards; converting them requires their own admission/disclosure proof. Do not relax `authorized` globally or invent a new route-classification framework.

| Stage                                    | Owner and required mechanics                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare outside the world mutation lane  | HTTP parses input and carries explicit scope/capability/control through the existing authority context. Service readiness, first-use authority lookup, cold receipt lookup and Known-place/trade preparation may await here. For input, move `await this.ready` before `updateWorldInput`'s mutation turn. Preparation cannot apply gameplay or hold an inherited mutation context.                                                                  |
| Enter the existing service mutation turn | Recheck committed session/grant/control values, current wall-time expiry, timeline/generation, writer health and prepared evidence dependencies. Recheck recent command receipt/epoch or input sequence so simultaneous preparations cannot apply twice. Evaluate the proposed action against current world mechanics.                                                                                                                               |
| Accept the effect                        | In shared `acceptProgress`, recheck current authority/ownership immediately before pending-buffer admission and publication after any intervening await. A refusal installs neither the candidate world nor a success receipt and rolls back temporary reservations. Operational-only input writes use the same guard before their first accepted input mutation because they bypass `acceptProgress`. Keep this final check and effect synchronous. |
| Reply and save                           | Receipt replay and private egress check current disclosure rights. Ordinary accepted effects join the existing scheduled save; later expiry of their originating session cannot reject that save. Protected commits, spending and access/control changes retain their transactional SQL authority fences and durable acknowledgment.                                                                                                                 |

Reuse one service guard over the existing authority maps and writer-health owner at these actual boundaries. Do not duplicate the joined SQL query, cache permissions on a timer, strip the protected operation's authority context or substitute a preparation-time check for acceptance. Waiting for unrelated database reads then delays the command's preparation, without preventing native world updates from taking their own turns. A command still waits for its actual serialized world change; the design does not allow concurrent conflicting mutations.

The shared guard checks request authority when present; autonomous native progress retains its existing internal authority and does not acquire a player-session requirement. Writer failure refuses new gameplay, while the existing failure/pause reporting path remains able to report the stopped state.

Reuse `PostgresDatabase`'s existing exclusive writer connection/advisory lock and failure latch for a synchronous live-admission guard: startup, closed or failed ownership rejects admission. Surface that owner state through the existing store and latch unexpected socket end/error or close; do not introduce a second lease, expiry cache or polling query. This covers known connection/ownership failure, not arbitrary unsupported online SQL. Verify delayed receipt/preparation plus logout, control transfer, expiry, timeline replacement and database disconnect: native time may advance during preparation, while stale commands cannot take effect or disclose cached receipts. Verify duplicate requests yield one effect/receipt, a second supported writer cannot acquire the database lock, a protected effect still reaches its SQL fence, and an accepted ordinary effect can save after its originating session expires. Removal acceptance: ordinary command/input preparation contributes zero held `assertFence` database calls and owns no world mutation turn while waiting for a cold read. The [AWS attribution](../verification/performance/bookkeeping/2026/2026-11-05-runtime-ablation.md#what-holds-advancement-while-the-thread-is-not-computing) establishes the held boundary. The [subsequent removal matrix](../verification/performance/bookkeeping/2026/2026-11-05-subsystem-ranking.md#cleanup-authority-and-native-scheduling) shows no demonstrated throughput gain in these cuts from skipping that query or moving it outside ownership; naive preflight worsens command latency. Reuse existing admission fairness and measure ready-command latency/skips alongside clock progress; an empty held-query span alone does not qualify the conversion.

The queue boundary must remain simple and fair: cold preparation owns no mutation slot; once ready, its single actual admission joins the existing FIFO mutation lane. Native continuation observes pending foreground work and yields at its next coherent prefix under the existing 8 ms cooperative/32 ms publication targets, rather than draining all owed game time first. Do not add a priority broker or let prepared commands bypass earlier admitted effects. Preserve the current queue/count/age limits and explicit busy outcome. A command whose inputs became stale refuses or follows its existing bounded preparation behavior; it cannot recursively reprepare while holding ownership. `updateWorldInput` similarly prepares readiness outside the lane, then admits its operational mutation once with current sequence/authority. The isolated E4 comparison must include a deliberately slow cold read plus a subsequently ready command: native progress continues during the read, the ready command gets a bounded queue opportunity, and completing the older preparation does not backdate its effect. No fixed wall-time latency guarantee is claimed for an indivisible slow native operation.

Cache the latest story result, including null, by world/timeline, player principal and the history owner's relevant banner/source-eligibility revision. Invalidate actual banner changes and relevant privacy changes; an unrelated game/view/history update is not a banner change. Share one in-flight fetch. A read completing after invalidation cannot repopulate the new cache. Narrator prose stays player-only and never enters a character's cognition, personal memory or new semantic trigger.

## 6. Live acceptance and ordered saving

**Selected by Mike November 1, 2026:** ordinary gameplay may be acknowledged before disk, targeting one-second saves and allowing at most five seconds of unsaved progress before backpressure. Ordinary gameplay follows this live acceptance contract; protected effects retain their existing durability. It does not authorize weaker spending/access accounting. BKS-L08 owns operational limits. A crash may lose the accepted unsaved suffix for every participant together; no client continues authoritative simulation during an outage.

### 6.1 Classify by side effect at the existing admission boundary

| Operation                                                                                                               | Acceptance and persistence                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary physical actions, speech, inventory transfers, native progress and accepted gameplay portions of NPC responses | Validate and atomically accept in server memory; publish result with its command receipt; batch complete effects and evidence into the ordered save stream                                                                                        |
| Provider dispatch/reservation, charged outcomes, access/grant/control changes, external irreversible effects            | Existing durable owner and idempotency before the external effect or durable success acknowledgment; no volatile spending/access mode                                                                                                             |
| Checkpoint, restore, timeline replacement, authoring/world installation, explicit durable export                        | Establish the required complete durable cut before reporting success; ordinary native execution is not used to run a database transaction                                                                                                         |
| Correction/explicit forgetting                                                                                          | Immediately fence affected sources and pending disclosure, prepare selected dependencies asynchronously, then atomically publish the complete correction and durable privacy ledger; do not freeze unrelated physical advancement while preparing |

Do not create a classification framework or per-world command whitelist. The existing command/operation owners declare whether they touch protected operational effects or a persistence barrier; ordinary native gameplay is the default. Mixed operations retain the strictest actual dependency, not an accidental helper's database call. An NPC response's model bill remains durable even if its later ordinary gameplay result is in an unsaved suffix; restart never automatically buys the response again.

Ordinary commands that need cold information still prepare it before admission: known-place movement, retained trade disclosures and speech availability are concrete existing callers. Capture scope and exact dependencies, await their bounded reads outside mutation, then recheck them and apply the complete command in one short turn. Pending preparation does not occupy `pendingOperations` or block native saves/advancement. Do not silently convert an unavailable preparation into permission, absence or a synchronous save. Protected operations retain the existing strict commit path; their final atomic barrier may briefly exclude world mutation, but their preliminary I/O does not. Pause takes effect in memory immediately and requests the final flush without waiting to stop movement; graceful shutdown stops admission and awaits that final cut within its existing shutdown deadline.

Permission and gameplay-source checks authorize the **live acceptance** of an ordinary effect. Its later save checks server writer ownership, expected database revision and storage integrity, not whether that original player's session is still valid. Session expiry cannot retroactively reject already published gameplay. Authority changes fence new affected admissions immediately and order their durable settlement after the preceding accepted cut; later actions use the new authority. New disclosure and paid dispatch still recheck current rights. Do not pass one request's SQL authority fence over a multi-actor pending batch. This changes the acceptance boundary, not who may act or read.

Correction success is reported only after its durable privacy barrier. A failed preparation/write does not silently lift the affected-source fence or report successful forgetting. The existing correction/storage owner resolves the failure; unrelated work remains eligible subject to the same pending-save limits. This preserves immediate non-disclosure without making a partially prepared correction a second writable world. Internal native place preparation may use the still-accepted knowledge cut under the [existing native-index contract](../memory-architecture.md#personal-perspective-and-acquisition); it grants no player/model disclosure and is invalidated atomically when the edit is accepted.

### 6.2 Accept, buffer, save

1. Authenticate against the authority owner; after entering the short mutation turn, recheck current control, timeline, ordinary preconditions and exact command identity. Existing recorded outcomes are returned without execution. Check bounded pending admission before mutating.
2. Apply the operation to an isolated candidate, including native RNG, received evidence, meaningful personal accounts and its result receipt. Verify final pending charges before publishing; an estimate made before execution cannot authorize an oversized result. Publish one immutable accepted world and append its existing change intent to the pending buffer. Resolve the command from that acceptance; there is no SQL await in this ordinary turn. A rejected candidate publishes no partial effects.
3. Extend the existing service sequence/waiter mechanism to number **accepted world cuts**, rather than only saves. Advance this process-local acceptance sequence once per atomic accepted publication; the durable sequence is the greatest covered acceptance sequence. A save captures a fixed through-sequence, oldest acceptance time and expected database revision. Database revision still advances once per transaction and is not this acceptance sequence. UI-only notifications advance neither. Pending changes consist of coalesced current records plus ordered admitted occurrences/receipts; retaining the latest world snapshot alone is insufficient because older unsaved history may leave the resident tail.
4. At the one-second opportunity, or an explicit checkpoint/protected-operation flush, detach one immutable prefix. Later arrivals do not reset its timer. Paid cognition and ordinary cold readers waiting for a captured cut join the scheduled batch; registering a durability waiter does **not** request an extra early save. The fixed wait consumes the existing urgent inference budget; an expired request defers under its existing policy, without extending the deadline or purchasing another attempt. Prepare/encode only deltas outside mutation, using captured bounded inputs and the existing cooperative preparation budget. Merely wrapping synchronous encoding in an async function does not move CPU work off the event loop; yield between bounded batches and measure the indivisible largest row. The writer commits canonical records, original history, necessary support, privacy changes belonging to that cut, command outcomes and revision together. Later live changes accumulate independently.
5. On success advance the durable-through sequence and release only that saved prefix. Coalesce the existing publication/diagnostic notification; no SQL poll per client or command. A protected consumer waits for its captured sequence, not for an ever-moving latest world.
6. On failure stop new ordinary admission and preserve the accepted pending suffix in RAM; do not silently revert already published gameplay while clients remain connected. Keep the existing latched storage-failure behavior, without a new automatic retry/replay protocol. Recovery resolves uncertain completion through the existing revision/receipt; it does not re-execute native actions or paid work. Restart chooses the last complete durable cut.

Elapsed time is accounted by the existing native clock owner; saves never report attempted time as advanced. The five-second limit uses the oldest accepted unsaved change's monotonic acceptance time, not the current write's start. A successful partial flush must not reset the age of a still-pending older suffix. Check before accepting another native slice/ordinary command, and cap the next cooperative slice against the admission deadline. A single indivisible native operation can overrun that deadline; report its measured overrun rather than claiming hard real-time scheduling. The rule stops admitting more play; an unresponsive database may remain unavailable longer than five seconds.

Use the existing pending buffer, adding incremental byte/count accounting rather than repeatedly serializing it to check size. Record codecs own conservative charges from already encoded/admitted payload sizes, cached unchanged content sizes and bounded changed metadata; an unknown-size payload is prepared once before acceptance and its encoded result reused. Coalescing releases a superseded current entry's charge, never an in-flight or retained chronological entry. BKS-L08 defines the finite byte ceiling and oversized-operation behavior. Reserve 64 KiB inside the 64 MiB ceiling for emergency Pause; ordinary admission cannot consume that margin. At a cap, the host yields and waits for storage; it does not discard accepted history, silently shorten the route or let the client grow an unbounded command queue. Emergency pause stops new advancement promptly. Backpressure is not ordinary memory consolidation and must remain visibly classified as storage pressure. Existing debt handling applies while the running process waits; a fresh process does not simulate offline elapsed wall time.

Detached pause flushes, save/retention timers and shutdown saves clear inherited mutation ownership and request authority before entering the existing queue. They cannot re-enter an awaited command as nested work or adopt a durable baseline while newer progress is unsaved. The ordinary pause acknowledgement and protected flush guard retain their existing meanings. A save callback refused **before it starts** preserves its accepted prefix and reuses the single save timer with a one-second admission delay; this does not reset unsaved age, raise limits or retry an executing write. Failures after admission retain the existing fault latch. Closing gameplay admission keeps accepted saves draining for shutdown durability waiters; resource release cancels the timer and fences already queued callbacks. A refused post-durable residency turn waits for the next save or explicit flush: the committed cut remains durable and placement does not become forgetting.

### 6.4 Disconnect, restart and restore

Clients render the accepted server state and send bounded intentions; their prediction/input buffers are never a recovery log. Ordinary acknowledgement means accepted in the live world, with durability tracked separately in protocol/service state, not an extra gameplay menu. After a crash, reconnect replaces client predictions with the restored world and does not replay old pending intentions automatically.

Resolve retries from the bounded current-process pending/recent outcome map first. For an unknown command identity, batch the existing durable-receipt lookup outside the world mutation queue before admission, then recheck the live outcome map inside the turn to close concurrent-duplicate races. A map miss alone is not proof that an old command is new. This may still delay that request; it must not stop other actors or native time. Receipt writes join the same world save, not an extra transaction per command.

Use the existing command epoch/control-generation mechanism, rotating the acceptance epoch on every process activation and timeline replacement. Persisted old receipts remain recoverable under current disclosure rights. An old-epoch request with no durable receipt is explicitly unconfirmed and cannot be executed as a new command; a fresh intentional retry needs a new request in the current epoch. Saved ongoing actions continue from their native state independently of this client-input epoch. This prevents a lost acknowledgement from duplicating a transfer across restart without persisting every HTTP response separately.

Restore validates one complete current-format cut and independent native pool/use totals, reconstructs ephemeral attention-work queues, caches and scheduling, and installs current authority/privacy overlays before exposure. Explicit correction/forgetting and real spending remain protected across older checkpoint restoration. A checkpoint request awaits its selected durable cut, then uses the existing bounded streaming snapshot exporter. No new journal, save migration, whole-world clone per tick or parallel persistent head is introduced.

Other observers keep their existing policy and can never inspect private command/goal/method data for classification. Preserve the initial exact result, agency result pointers/fallbacks, prepared-threat result triggers, current perception, required recent receipts, attended paths, native reactions, required aftermath and finite request captures. This stage does not skip an action-result writer or shorten its horizon.
4. When the existing retention owner selects an eligible exact account, branch on the stored after-release decision. Discard removes that account through existing expiry/source-version owners without constructing an impression, its conversion-only provenance, a new memory row or later impression-index/weakening work. Existing protected obligations, learning, source references and current private captures remain effective. Deleting an account can still require its body for canonical revocation/cleanup; do not claim every body read disappears.
5. Deliberate retention and warranted summaries/model interpretations remain explicit independent acquisitions; do not discard them because one supporting event involved movement. `acceptConsolidation` currently copies a source's entire retention value: convert that caller so an authored summary/interpretation receives its own selected retention decision, including a same-ID summary replacement, never an inherited `afterRelease` from one source. Its required exact source support remains independent. A retained derived account can still require the exact old source revision. Names, familiarity, Known-place support and command receipts keep their separate owners. Meaningful escape, injury, completed goals or resource consequences use their existing supported evidence; there is no daughter/cliff/hunting special handler.

**Removal/acceptance:** count actual predicate matches, exact accounts retired, impressions created, source versions, rows/bytes/index work and retained heap. The observed 1,524 impressions are a potential affected population, **not** a guaranteed removal count or CPU saving. Compare recent ordered movement and own results through real cognition/player consumers before/after; near-quota pressure, a stopped/replaced route, a genuinely consequential/goal-bound movement, deliberate retention, mixed routine/meaningful-source consolidation, an intentionally retained all-routine recollection, another observer, pending correction and cold restoration must keep their stated meanings. Check that a summary/fallback does not recreate the discarded record elsewhere. Qualify the gameplay tradeoff separately from clock/CPU: ordinary movement may have no lasting recollection after exact support releases, while useful outcomes survive.

**Further acquisition reduction is unselected.** The diagnostic omission of `endActivity` accounts suppresses 769 admissions but stalls progression at game time 11,060; its faster command replies are not a valid gain. This is not a clean measure of account-birth cost or proof that an absent result reference directly blocks time. The existing result/cognition consumers independently require a complete replacement before that admission can be removed. The same `RecordingReason` currently gates event intake, required temporal capture and automatic account admission. Merely returning `none` for movement could drop needed recent evidence; skipping `endActivity` memory can cause `agency.finishPlanAction` to recreate it. If initial routine account creation remains materially expensive after this experiment, separate recent receipt requirement from automatic account admission at the existing decision owner and convert events, acquisition, agency/context, recording and persistence together. That requires its own complete consumer design and measurement; it is not covered by the after-release stage. No new cognition loop, summary generator or duplicate episodic store is proposed.
