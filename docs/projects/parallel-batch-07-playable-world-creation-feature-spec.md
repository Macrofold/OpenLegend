# Batch 07 — Create a world and play its opening

| Status      | Current progress                                                                                                              | Last updated |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------ |
| In progress | Main and solo starts pass native creation, reload and browser preview; generated-tool play and parent acceptance remain open. | 2026-10-14   |

## Purpose and selected scope

**October 14 supplied-start revision, authorized by Mike:** offer **Main world** and **Solo testing ground**. Main world contains the current integrated camp residents, survival/crafting, shelter, fishing, practice, expeditions, missing-belonging investigation and distant Broken Watchpost rivals through the same authored initializer as ordinary startup. Rivals are outside the ordinary opening view; exploring discovers their actual location and circumstances. Solo testing ground has one controlled person, basic supplies and making opportunities, with no residents or encounters. Custom supported openings remain available through authoring. These are starting circumstances, not scripted goals, guaranteed autonomous behavior or claims that every diagnostic world-law variation can coexist. See the [implementation plan](parallel-batch-07-playable-world-creation-tech-design.md#main-world-and-solo-testing-ground--october-14-implementation).

Let an authorized creator describe a small world, preserve the parts they care about, inspect what someone can actually do there, and enter that exact opening on an operator-prepared empty host. Creation succeeds when the person plays a useful activity, not when a model finishes describing a place.

This allocation implements the first supported creation journey in [world creation §§2–11](world-creation-feature-spec.md#2-boundaries-inherited-from-the-project). That document remains the product behavior owner. The work covers one existing supported world family, retained proposals, meaningful clarification, concrete preview, readiness, exact start, recovery and first play. Its [technical design](parallel-batch-07-playable-world-creation-tech-design.md) selects the missing initial-world assembly and empty-target integration. OC01–OC05 are internal stages of **one assignment**, not five parallel tasks.

The familiar reference contains one human-controlled character, one autonomous resident, a useful locality, reachable finite supplies and an activity with a payoff. The creator can choose a supported solitary or harsh variation; the software must not secretly add a resident or emergency resources. The reference population is a bounded release profile, not a universal world law. Broader communities retain their existing qualification.

## Why this work now

The player can already manufacture admitted inventions, learn physical methods, explore, fish, barter and build the supported shelter. Those available mechanisms make it possible to create an opening with real choices rather than a scenery editor that promises future play. Existing World Agent questions, drafts and review provide the authoring foundation. The remaining gap is assembling a new initial world and making the reviewed result enterable without replacing an existing world.

The repertoire ranks the [authored first-session boundary and rehearsal](../repertoires/automation-creators.md#world-contracts-and-selected-modes) (ACR-122/ACR-135) and [a visitor's complete activity](../repertoires/automation-creators.md#creator-challenges-and-complete-experiences) (ACR-192) **1 Core**. [A personally proposed useful tool](../repertoires/actions.md#def-deliberate-invention-and-owner-authoring) (DEF-01) is also Core. These ranks support a playable creation consumer, not a universal world compiler.

Batch 06 already owns purposeful opposition, new ranged combat, evasion, combat help and its contested destination; duplicating them would neither create independence nor fill a new experience. DG12's cross-world invention library is useful but separate: packaging (DEF-10) is Specialist, and carrying a recipe to another world does not supply this opening. Ordinary social and exploration work can proceed independently. Larger populations, commercial hosting and general invented laws would multiply cost before this smaller creator journey proves useful.

This priority remains a hypothesis. The strongest contrary evidence would be creators preferring the prepared game because authoring takes too long or produces no meaningfully different activity. Acceptance therefore records the complete journey's effort and useful differences, not just valid definitions or shorter prompts.

## The complete creator and player journey

1. From an existing authorized creator session, choose **Create a world** or use a ready supported opening. Describe the idea in ordinary language. Choosing a prepared opening needs no new model call.
2. Keep the original idea and consequential answers. Show a compact proposal: place, people, actual first opportunity, meaningful payoff, known laws, initial knowledge/supplies, limitations and target operating profile. Ask only for a missing consequential choice; optional polish does not delay an already ready opening.
3. Inspect the proposed place through a permitted preview and readable equivalents. Change supported layout, cast descriptions, starting supplies or knowledge without losing unrelated chosen work. If an essential requested mechanic is unavailable, preserve it as an unresolved requirement and retain the draft.
4. Review the exact opening and a currently eligible empty target. The review explains what will be created, who will control the first character, the known ongoing configuration and any deliberately harsh conditions. **Start this world** authorizes only that candidate and target. No existing world is replaced.
5. Follow the confirmed entry route, authenticate normally and enter the created character through existing control admission. A committed world may still be waiting for its host; the UI distinguishes those facts and recovers the original receipt after a disconnect.
6. Pursue the chosen activity. In the familiar proof, genuinely request a supported new tool, gather its actual inputs, make it and use it in the current hunting/food loop. A dependable known method remains available. A resident responds through ordinary cognition to permitted events; no authored success script makes them agree or provide a reward.
7. Leave at a worthwhile stopping point, reopen and find the actual created world and consequences intact. The player can use the gained capability again. No replay of world creation, free items or fresh paid generation is needed to restore it.

The contrasting supported opening is solitary gathering and making: it deliberately omits the resident, offers a finite accessible resource and an existing supported container or tool activity, and preserves a different selected layout. It must use the same initial assembly contract. This is an authored scenario variation, not evidence of arbitrary new physics or autonomous goal formation.

## Boundaries and meaningful failure

Use supported definitions and ordinary actions from the starting base. New host mechanics, a general map generator, arbitrary creature/body authoring, cross-world libraries or packs, public discovery, automatic host provisioning, travel between live worlds, larger-community simulation, custom media generation and changes to Batch 06 combat are outside this allocation. Character description and initial circumstances are included; personality development and removal of people from a running world are not dependencies.

The creator prepares the new opening from an existing authorized authoring surface. This does not silently grant characterless visitors new tools. The operator must have prepared the target's independent database, data directory, host address and account policy. Implementing the empty-target intake and handoff is this assignment's work; installing a cloud provisioning platform is not.

| Situation                                                       | What the person sees and what remains true                                                                                                |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| A useful supported opening is ready                             | Play is offered; no required decorative generation, simulated history or extra interview.                                                 |
| The premise depends on unavailable mechanics                    | The essential idea remains in the retained proposal, with a concrete unsupported requirement; no silent substitution or misleading Start. |
| The creator deliberately chooses scarcity or solitude           | The actual choice survives review and entry, with its practical consequence explained.                                                    |
| A required route, ingredient, definition or grant is missing    | Readiness identifies the blocking opportunity and repair; a pretty preview is not a pass.                                                 |
| The target is occupied, unavailable or no longer authorized     | The candidate remains retained; no overwrite, reset, deletion or automatic retry.                                                         |
| The person changes the proposal during review                   | The old review cannot start the changed world; unchanged work remains available.                                                          |
| Start commits but the browser or source process loses its reply | The same start identity resolves to the same world and entry route, without a second creation.                                            |
| The target commits but its runtime fails to start               | Show the committed world and unavailable host separately; runtime recovery opens the same world.                                          |
| Optional presentation fails                                     | Use faithful existing native presentation where available; required missing representation remains a blocker.                             |
| The resident declines or chooses another activity               | Preserve independent behavior; first play remains possible without compulsory help.                                                       |

## Stages, effort and acceptance

OC01 establishes the supported initial-world contract and extraction from existing authored content. OC02 integrates retained natural-language creation with the current World Agent. OC03 supplies native readiness and creator preview. OC04 implements the exact empty-target handoff and entry lifecycle. OC05 owns the complete first-play, failure, recovery and documentation qualification. Every stage belongs to the same worker; implementation order is internal.

Initial estimate: **5,000–9,000 production-logic lines and roughly 18–30 engineer-days**, excluding tests. These are planning ranges, not a delivery deadline or measured AI-agent productivity. The principal uncertainties are separating startup from auto-seeding, target admission, extracting fresh-world construction without changing the existing start, and usable preview integration. Reassess against the actual source before implementation.

Completion requires the [technical acceptance matrix](parallel-batch-07-playable-world-creation-tech-design.md#complete-acceptance) and all [OC01–OC05 exits](../maintainers/parallel-batch-07-playable-world-creation.md). A scripted journey proves that the feature works through its real surfaces; it does not establish uncoached enjoyment, calibrated balance, larger-population capacity or general natural-language quality. Report those distinctions and retain failed cases.
