# Profiling the stand-alone Rust game server

The opt-in profiler lets a developer follow the server's work from a gameplay run down to actual calls and the amount of work they did. CPU samples explain what was running. The timeline explains what the player waited for. Both must describe a world that continued to play and save correctly. [Implementation and qualification status](../../maintainers/profiling-controls.md#stand-alone-rust-server)

## 1. Establish the clean case and its identity

1. Reuse the [clean Rust gameplay case](../../benchmarks/native-runtime-foundations/2026/2026-11-18-rust-game-server.md#clean-publication-timing). Its worker manifest is `workers/campaigns/f3816cae-1af5-4a5f-8cd3-170e9061441b/manifest.json` under the private Open Legend verification directory. Resolve `driver`, `tools` and `language` from that manifest. Beside it, `inputs/<archiveSha256>.json` lists each member's byte count and SHA-256. Verify the selected files under each plan input root, or retrieve the pinned archive and verify its archive and member hashes. Use the driver's `direct` arm. PC11 must make this reproducible from a clean checkout plus pinned inputs. Promote the necessary driver source or reference the retrievable, checksum-verified bundle. A developer's working directory is insufficient.
2. Extend the reference `scripts/performance/profile-campaign.ts` plan/case/summarize interface with a Rust case adapter. Keep offline planning and reporting separate from the case that starts the game. Resolve case IDs from the frozen plan in both the runner adapter and the report reader. The reference tool hard-codes its numbered discovery and detail groups. Keep its artifact containment and checksum checks when adding Rust cases. Use the [existing case schema](../../performance/hierarchical-profiling.md#concrete-plan-and-case-interface) and managed runner. Freeze the game, tooling, driver, authored release, Cargo.lock, toolchain/target/features, machine, PostgreSQL settings, worker width, seed, schedule and allowed work variation. Record the **actual executable** and matching symbol hashes per arm. The pair shares the frozen workload and lists its one permitted build or observer difference. Reject any other difference. Record each arm's full identity even when its executable is intentionally different.
3. Run the known opening with one player, ten active human NPCs, ten deer, five hares and 1,246 scenery records. Use ten real seconds of warmup and 180 real seconds of steady play, the installed 60:1 clock, 2 GiB profile and one-second background saves. Require all 34 scheduled walks including warmup, both held steering gestures, the two controlled replies applied and saved once, observed reactions, a live permitted stream and clean shutdown. Count the actual steady work separately. Keep a browser display witness distinct from HTTP acceptance, stream receipt and durable acknowledgement. Separate cold reopen, reconnect and administrative restore into their own windows.
4. At the steady window boundaries, collect CPU deltas for the server process (including Tokio and Rayon), the exclusive PostgreSQL process group and the separate client/driver. Report any external sampler's CPU separately. Prove ownership across backend exits. Missing counters yield an unavailable delta. Sample concurrent memory during the window for the observed peak. Endpoint RSS and admission reservations answer different questions. Report measured progress and identify whether the scheduler exposed actual debt.

## 2. Measure CPU, then select direct probes

Start with one external CPU sampling experiment against the owned, optimized release on the standard worker. Verify available permissions, process/thread coverage, unwind quality and symbolization on the actual image before planning repetitions. Cover threads already running and threads created or retired within the window. Record lost samples, unknown frames, kernel/unavailable time and unattributed libraries. Keep one exclusive instruction bucket per sample and a separate inclusive caller view. For example, allocation inside attention is visible in both views. Count its CPU once. Keep the code address and inline call site when optimized Rust gives multiple sites the same symbol. Express any translation from samples to core usage as an estimate, with the sampled CPU population and its coverage. A userspace-only sample cannot allocate kernel CPU to gameplay features.

Check the frozen November 20 diagnostic inputs before selecting a sampler. Managed campaign `32b916bf-aa32-49bd-a00b-a34930cc0ef3` includes a disposable Linux thread CPU timer, address-only stack collection and offline symbolization. Use the collected results only after their checksums, complete gameplay and sampling coverage have been verified. Its signal handler writes a record per sample and thread creation is intercepted. Those are distinct overhead and failure risks. Keep this sampler confined to diagnostic runs.

Use the release's existing line tables first. Sample instruction addresses or address-only call chains scoped to this process. Exclude raw process memory, stack contents, argument values and system-wide collection. If the worker cannot collect usable call chains within those controls, retain flat symbols/unknowns and use direct probes for the missing caller. A build requiring frame pointers, different inlining or an allocation sampler is its own overhead experiment. Never weaken worker security to obtain a profile. [Linux perf access and data exposure](https://docs.kernel.org/admin-guide/perf-security.html)

Use the [S00–S16 inventory](../../performance/simulation-inventory.md#reading-and-maintaining-the-hierarchy) for categories and units. The tool registry owns each executable metric's stable ID, unit, timing kind, finite caller/outcome classes and the hash of the exact source binding. Reuse an ID across runtimes only when its meaning and unit agree. The Rust probe identifies its site. Resolve enabled sites to numeric handles once when arming. Check the binary's site list against the frozen bindings, reject missing or ambiguous sites and report unselected or unexercised sites separately. A category collects related measurements and has no duration of its own. Select one family per diagnostic pass. Short paths below are relative to the named crate's `src/` directory.

## 3. Add one bounded Rust recorder

**Build and ownership.** Add a non-default `profile-campaign` Cargo feature to the server and forward it to the participating host and simulation crates. The normal release compiles out probe calls and optional argument evaluation. A probe-capable binary with nothing selected opens no channel, creates no recorder and performs no diagnostic preparation. Leave the original game operation and its success, refusal or cancellation in the existing control flow. The host owns selection, clocks, storage and output. World rules emit finite tags and already-known counts. No recorder state enters a save, authorized view or decision input. [Rust conditional compilation](https://doc.rust-lang.org/reference/conditional-compilation.html)

For an enabled case, pass its validated plan through an operator-only inherited channel at spawn. Arm before releasing the input schedule. Map the driver's start and cutoff into the recorder's monotonic clock before the steady window begins. Classify by those timestamps, even if an edge notification is late. Record mapping uncertainty and actual resource-read times. A missed handshake, a dropped control channel or an unalignable window fails the affected measurement. Teardown releases capture state independently of the game's shutdown.

Keep the small probe interface in a feature-gated simulation module and implement it in the server. Begin/end brackets one logical operation. Resume/suspend brackets its actual execution segments. Only instrumentation receives the token. The pool uses the same interface. Install a worker-local binding only for a synchronous call and restore it on return. Build the stock server and Node bridge separately from the profiling server to check feature isolation.

**Invocation lifetime.** A selected operation carries only a numeric capture generation, slot and slot generation. Keep any task-owned logical token distinct from the execution thread. Time a synchronous block at entry/exit. Across an await or simulation yield, keep logical latency open but close active time. Bracket the existing synchronous resume or worker body at its real caller. A token can cross threads, a thread-local active stack cannot. Pass the association explicitly at queue submission and resume. Never leave a thread-local guard installed while a future is pending. Observe the outcome at its existing match arm. On early return, cancellation, unwinding or thread retirement, account what was observed and preserve the original result, drop order, poisoning and cancellation behavior. Do not poll a future again to learn its result. [Rust future contract](https://doc.rust-lang.org/std/future/trait.Future.html)

Keep game data out of tokens. Observe permission, selection and serialization inside the existing disclosure owner. Never hold an authorized view, buffer, lease or world to complete a timing.

`try_submit_world` charges the size of its submitted closures to gameplay. Keep job correlation in a bounded diagnostic table keyed by the existing per-job cancellation allocation. Register **after admission and before scheduling** because the worker can finish before submit returns. Store the capture generation in that allocation's existing padding. The weak key preserves allocation identity without keeping the job alive. Clear the tag when the worker takes or cancels the job, and discard the table entries at capture teardown. A missed lookup counts against the capture that registered it, even when queue timing was unselected. Never export a pointer. The dispatcher still decides whether to run or cancel a job. A recorder failure disables the affected capture, while an actual worker panic still takes the existing world-poison path in `WorkAdmission::run`.

**Storage and loss.** Preallocate the selected series and slots within [OB03](../../limits/observability.md#ob03--hierarchical-campaign-measurement). Its cap covers the entire process, including worker storage and any capture still exporting. Use one capture-owned table. Check the observation window before trying its nonblocking lock, then check the capture and slot generations under the same guard that writes the record. A busy recorder drops an eligible observation immediately and increments a separate capture-local atomic loss counter. A missed terminal write leaves the token outstanding until bounded teardown. Report affected counts as incomplete and exclude the affected distributions from qualification. Treat bounded worker-local aggregation as a separate experiment when a high-rate capture loses material coverage or exceeds the overhead gate.

Keep eligible calls, timed calls, outcomes and work units distinct. Use the shared histogram bins, underflow/overflow, count/sum/min/max and tail rules. Merge compatible bins before computing pooled quantiles. Report per-run results separately. Timed active segments include preemption. For sampled leaves, use the fixed measurement seed and probability ladder, independent of gameplay randomness. Label extrapolations. Reject arithmetic overflow and loss of integer precision across Rust, JSON and the report reader.

**Ending a window.** Clip active segments to the steady interval, including work already underway. The optional trace records operations that start in steady play. Keep carry-in in the clipped aggregates and reserve trace capacity for steady work. Follow in-window operations to settlement or the frozen drain deadline. Report carry-in, unfinished, censored and omitted work separately. Maintain ordinary clock, saves and stream presence. Under the update guard, detach the table, record its stop time and invalidate its generation. Cleanup cannot extend the recorded window, and a late finish cannot touch the snapshot or the next capture. Serialize the detached data outside gameplay locks. Count it against the cap until released. Control loss, export failure or a full recorder leaves the original gameplay outcome intact. [Window and drain accounting](../../performance/hierarchical-profiling.md#window-edges-and-incomplete-operations)

**Allocation pass.** Begin with the existing game memory owners' admitted, retained, pending-save and released bytes, and sampled process RSS. They answer different questions. An allocation-site profile needs a separate backend and run. Before adopting one, demonstrate that it observes the actual allocator, bounds sampling and export memory, does not allocate recursively or expose payloads, and still permits a held reader and a correct admission refusal. Otherwise report allocation-site coverage as unsupported. Never infer allocation rate from RSS or reclaim live data to improve the observation.

## 4. Qualify each instrument through its real caller

| Order                                     | Required check and decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Prove the controls                     | Build the ordinary release before and after adding the feature. Identical executables share the untouched control. A different default executable needs its own gameplay and overhead comparison with untouched. Build the probe-capable release once and use that exact binary for both disabled and enabled runs. Check feature-off and runtime-disabled paths skip optional evaluation. Through the real caller, verify visible movement, both permitted NPC inputs, exactly-once saved replies and cold continuation.                                                                             |
| B. Deliver one clock turn in the report   | Join scheduled advance → turn acquired → worker steps, including a yielded host question → accepted game time. Drive a fixed sequence through the real simulation/service owner. Compare admitted inputs, ordering, saved randomness, debt, rollback and durable effects. Exercise an admission refusal and retry, cancellation before execution, recorder failure versus worker panic, worker retirement, stop/restart with an outstanding token and loss at recorder capacity. The report must distinguish a wait from a step and a refused attempt from an executed job.                           |
| C. Explain selected costs                 | Measure the parent, choose expensive children using the frozen selection rule, then freeze their IDs before dispatch. Include one enclosing span to explain the same-pass remainder. Isolate every new probe family, sampler, SQL/allocator mode, future wrapper or storage strategy with its own correctness check and off/on comparison before relying on it for ordinary-play costs.                                                                                                                                                                                                               |
| D. Verify privacy, storage and the reader | On fixed-work cases compare the actual permitted request and accepted effects from the controlled provider and persistence owners. Normalize only documented transport-only differences. Publish pass/fail and finite reasons. Exercise withdrawn evidence, cancellation during a held reply, revocation before disclosure, blocked/disconnected streams, save refusal/retry and cold reopening. Verify an independently held reader sees its original snapshot. Feed missing, corrupted, unexercised and lossy captures to the offline report. None may appear as measured zero or qualify overhead. |

Freeze a finite case list, price, remaining authorization and stop rule. Use the standard 16 GiB worker with independent databases and three matched pairs per overhead claim in A–B, B–A, A–B order. Compare untouched with disabled, then disabled with each enabled selection. For an external sampler compare the same release with sampling off/on. If compiler flags must change, isolate that build change while unsampled. Share controls only where identity and interleaving match.

In fixed-work replays require exact input order and outcomes. In timed play require all discrete promised actions and their effects. Normalize each arm's CPU by its **actual completed game-seconds**. Use the opening driver's checks and freeze tolerances for clock-boundary uncertainty and internal work before dispatch. A tolerance cannot excuse a missed walk or reply. The reference `qualifyOverhead` checks work-unit equality unconditionally. Adapt that check for real-time measurements while retaining exact equality for fixed work. Never round game time to force a match. Apply [OB03](../../limits/observability.md#ob03--hierarchical-campaign-measurement) to the median paired CPU increases for server and server plus PostgreSQL separately, and to command p95 in **each** applicable pair. Missing proof, changed cognition input or incomplete gameplay prevents qualification. A diagnostic can still locate work. Its timings stay out of release speed claims.

## 5. Produce the answer

Reuse the verified local artifact layout, CSV/JSON and static HTML of the [hierarchical procedure](../../performance/hierarchical-profiling.md#8-artifacts-and-output-contract). Generalize only the fields consumed by both runtimes, such as server CPU and thread role. Report startup, steady play, drain, reconnect and recovery separately. The first page answers four questions.

- **How much of a core, at what game speed?** Show server and PostgreSQL separately, completed/offered game time and debt, client/driver separately, median/mean/p95 with units and sample populations. One core is 100%. Show supporting combined CPU per completed game-second, actual memory and reservation headroom.
- **What delayed the player?** Separate command response, first stream receipt, first browser display and durability. Join on existing operation and accepted-cut evidence inside the private fixture. Report an ambiguous join as unobserved. The public protocol needs no profiling field. Use same-clock intervals or a measured clock mapping with uncertainty. An unsent frame, coalesced view or failed command is an outcome. Do not infer display from server handoff.
- **Which mechanic and which technical work?** Give disjoint sampled CPU groups, inclusive call paths, work per completed game-second and per call, plus the unresolved remainder. For example, “an observer checked sight 20 times, requested two geometry batches, and changed one memory” would distinguish an expensive check from a useful new observation. Compare parent and child only within a compatible pass. Subtract only nonoverlapping active intervals of synchronous children on the same execution lane.
- **Why so many database calls or bytes?** Summarize caller × finite query family, size probe versus body, lane wait, rows, prepared/application bytes versus measured wire bytes, WAL, growth and exclusive PostgreSQL CPU. Use existing group counters at boundaries. If available on the owned database, take filtered statement-statistics deltas in a separate mode, checking resets and evictions. Elapsed SQL time includes waits. Query counts do not allocate database CPU among features. Never log parameters, prompts, saved rows or raw SQL carrying private values. [PostgreSQL statement statistics](https://www.postgresql.org/docs/current/pgstatstatements.html)

Show unsupported/unselected/not exercised, censored, sampling loss and unqualified overhead beside the affected rows. Give the checked local report path, source/input identities, actual run count, spend and cleanup. A recommendation to check sight less often or retain fewer observations must say what the player or NPC could miss. Changing an authored rule or optimizing game code is a subsequent decision.

Match the exact plan bytes against the managed claim and bind each capture to its arm and stop receipts. Parse evidence from the bytes checked against its seal. Check both resource sample edges against the frozen allowance for clock uncertainty. For CPU stacks, compare stored records with the sampler's own shutdown counts and verify the executable identity. Take SQL wire snapshots beside the resource readings, before awaiting database statistics. Check both wire edges against the same clock allowance and require ordered snapshots with no partial frames or observer failure. Keep counts with evidence gaps available for diagnosis and label their coverage explicitly.

The offline report looks for `ownership/safety/<comparisonId>.json` in the campaign directory. The checksum envelope contains `sha256` and a `proof` with schema 1, the comparison ID and frozen identity, and a `repetitions` array with an explicit repetition number on each replay record. Each replay identifies the control and candidate source, executable SHA, mode, probe IDs and sampling probability. It records the admitted-input and canonical-effect SHA values for both arms and whether admitted order, saved randomness, durable effects, private inputs and cold continuation matched. A replay qualifies only its matching timed binaries and selections.
