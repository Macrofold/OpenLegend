# Profiling the stand-alone Rust game server

**Proposed implementation · November 20, 2026.** A developer should be able to start with “where does the server spend a core while I walk?” and follow the evidence down to an operation, its real caller, and the amount of useful work it did. A slow walk also needs a timeline. CPU samples explain what was running. The timeline explains what the player waited for. Both must describe a world that continued to play and save correctly.

## 1. Establish the clean case and its identity

1. Begin outside the server. Reuse the frozen RGS08 opening, release builder, input schedule, controlled HTTPS provider and ordinary database setup from the [stand-alone comparison](../../benchmarks/native-runtime-foundations/2026/2026-11-18-rust-game-server.md#required-work-and-evidence). In the offline `plan` command, locate the case from its collected manifest. Verify the hashes of the driver and everything it loads. Import only shared tool functions that the Rust case uses. Keep one game driver and one worker runner.
2. Freeze the game and tools commits, Cargo.lock, toolchain/target, build flags and features, release assets, source/patch, executable and matching symbol-file hashes, worker and PostgreSQL identity/settings, worker width, seed, schedule, instrumentation, capture limits and cost ceiling. Verify the **running executable** against this manifest. Qualification keys also include the probe set, sample probability, machine, phase schedule and useful-work criteria. Build `case` inputs for the existing runner. Keep `plan` and `summarize` offline. A source or fixture change starts a new comparison.
3. Run the known opening with one player, ten active human NPCs, ten deer, five hares and 1,246 scenery records. Use ten real seconds of warmup and 180 real seconds of steady play, the installed 60:1 clock, 2 GiB profile and one-second background saves. Require all 34 scheduled walks including warmup, both held steering gestures, the two controlled replies applied and saved once, observed reactions, a live permitted stream and clean shutdown. Count the actual steady work separately. Keep a browser display witness distinct from HTTP acceptance, stream receipt and durable acknowledgement. Separate cold reopen, reconnect and administrative restore into their own windows.
4. Emit the existing case artifacts before adding an in-process probe. At both boundaries read server process CPU (all Tokio and Rayon threads included), exclusive PostgreSQL group CPU, separate client/driver CPU, concurrent actual memory and database counters. Verify ownership and counter continuity across backend exits. Missing cutoffs, reset counters or an incomplete backend roster yield an unavailable delta. Report reservations separately from RSS. Where the runtime does not expose debt, distinguish an external progress observation from a direct scheduler measurement.

**Reason for this order.** In three clean runs of the retained November 19 build, median server CPU was 62.74% of one core, PostgreSQL 8.14% and game speed 100.000% of intended. A different four-area diagnostic located 9.909 CPU seconds inside the ordered driver in 15.131 seconds on the clock worker. It did not divide the heavy opening's 62.74% among deer, perception and saving. Use these observations to pick the first drill-down. ## 2. Measure CPU, then select direct probes

Start with one external CPU sampling experiment against the owned, optimized release on the standard worker. Verify available permissions, process/thread coverage, unwind quality and symbolization on the actual image before planning repetitions. Cover threads already running and threads created or retired within the window. Record lost samples, unknown frames, kernel/unavailable time and unattributed libraries. Keep one exclusive instruction bucket per sample and a separate inclusive caller view. For example, allocation inside attention is visible in both views. Count its CPU once. Keep the code address and inline call site when optimized Rust gives multiple sites the same symbol. Express any translation from samples to core usage as an estimate, with the sampled CPU population and its coverage. A userspace-only sample cannot allocate kernel CPU to gameplay features.

Check the frozen November 20 diagnostic inputs before selecting a sampler. Managed campaign `32b916bf-aa32-49bd-a00b-a34930cc0ef3` includes a disposable Linux thread CPU timer, address-only stack collection and offline symbolization. Use the collected results only after their checksums, complete gameplay and sampling coverage have been verified. Its signal handler writes a record per sample and thread creation is intercepted. Those are distinct overhead and failure risks. Keep this sampler confined to diagnostic runs.

Use the release's existing line tables first. Sample instruction addresses or address-only call chains scoped to this process. Exclude raw process memory, stack contents, argument values and system-wide collection. If the worker cannot collect usable call chains within those controls, retain flat symbols/unknowns and use direct probes for the missing caller. A build requiring frame pointers, different inlining or an allocation sampler is its own overhead experiment. Never weaken worker security to obtain a profile. [Linux perf access and data exposure](https://docs.kernel.org/admin-guide/perf-security.html)

Use the [existing S00–S16 inventory](../../performance/simulation-inventory.md#reading-and-maintaining-the-hierarchy). Bind each selected row to a path, Rust symbol and unique block, input/output unit, timing kind, bounded caller/result classes and an actual caller witness. Hash that source in the frozen manifest. Fail planning on an ambiguous or missing site. Record every other selected item as unexercised, unsupported or awaiting a binding, as applicable. Rebind an ID only when it measures the same operation and unit. Select one family per diagnostic pass. Crates are under `native/`. Short paths in each row start in the corresponding crate’s `src/` folder.

## 3. Add one bounded Rust recorder

**Build and ownership.** Gate diagnostic call sites with a non-default Cargo feature forwarded only by the participating build. Compile optional arguments and work-count expressions out of the ordinary release. In a probe-capable binary, check selection before evaluating those expressions or reading a clock. A disabled run opens no control channel. Every mode executes the original game operation once. The game-server host owns configuration, clocks, optional storage, output and teardown. The simulation emits only finite operation tags and already-available scalar counts through a diagnostic-only seam. World rules cannot read the recorder, change their result based on its availability or persist a token. Validate selection, numeric bounds and output destination before the case starts. Start with one campaign per process. The operator supplies a private local case at process launch with a fixed window. For an enabled capture, pass a private, inherited control channel from the driver at spawn. Have the recorder acknowledge arming before the driver releases its schedule. Send window edges against that schedule, record the actual local cuts and alignment uncertainty, then stop and export after drain. The stock binary uses the same external workload without this channel. Players, world data and provider responses cannot select or read a capture. [Rust conditional compilation](https://doc.rust-lang.org/reference/conditional-compilation.html)

The recorder needs a begin/end pair for a logical operation, a resume/suspend pair for each active segment, and already-known work counts at their owning site. Begin returns an optional token to the probe adapter only. End takes the token once with a finite outcome. Keep the sink interface in a diagnostic-only module of `simulation`. Implement the storage and clock in `game-server`. At synchronous simulation entry install the sink for the current worker for that call, restoring the prior binding on exit. The worker-pool crate needs only submit/start/finish notices at its existing dispatch boundary. Put no server dependency in the simulation or pool. Compile both the stock executable and the Node bridge to catch unintended feature propagation.

**Invocation lifetime.** A selected operation carries only a numeric capture generation, slot and slot generation. Keep any task-owned logical token distinct from the execution thread. Time a synchronous block at entry/exit. Across an await or simulation yield, keep logical latency open but close active time. Bracket the existing synchronous resume or worker body at its real caller. A token can cross threads, a thread-local active stack cannot. Pass the association explicitly at queue submission and resume. Never leave a thread-local guard installed while a future is pending. Observe the outcome at its existing match arm. On early return, cancellation, unwinding or thread retirement, account what was observed and preserve the original result, drop order, poisoning and cancellation behavior. Do not poll a future again to learn its result. [Rust future contract](https://doc.rust-lang.org/std/future/trait.Future.html)

Keep game data out of tokens. Observe permission, selection and serialization inside the existing disclosure owner. Never hold an authorized view, buffer, lease or world to complete a timing.

One concrete trap is `try_submit_world`, which charges the size of its submitted closures to gameplay. Adding even a token to the closure can change a genuine capacity decision. For this handoff, use the existing per-job cancellation allocation to identify the job in a bounded diagnostic table. Register **after admission and before scheduling**. The worker can finish before submit returns. Use a weak reference to the per-job `requested` flag to preserve its allocation identity through retirement. The host-wide close flag cannot distinguish jobs. Retire the association on every completion or at capture teardown. Never export a pointer. If correlation cannot be admitted, record the omission and run the original closure once. No recorder may block under a world, disclosure, database or admission lock.

**Storage and loss.** Preallocate the selected numeric series and token storage before warmup. Use the [OB03 limits](../../limits/observability.md#ob03--hierarchical-campaign-measurement) for the entire Rust process, including all thread shards, tokens and scratch. Start by testing one capture-owned table with short, nonblocking updates and an independently readable loss counter. If an update cannot be recorded, let gameplay continue, count the omission and reclaim the slot safely at completion or bounded teardown. A contended recorder can systematically miss busy periods. It cannot qualify a distribution with unexplained or biased losses. Experiment with bounded per-worker aggregation only if the simple recorder fails. Do not multiply the allowance by the pool width.

Keep exact eligible/completed/failed/timed counts and work units distinct. Use the common histogram boundaries, count/sum/min/max, explicit underflow, overflow and clock resolution. Active segments measure monotonic elapsed time, including preemption. Only thread or process CPU counters and CPU sampling measure execution. Merge integer bins from compatible shards/runs before deriving pooled quantiles. Report per-run values and label small or censored tails. For hot leaves use the existing seed/probability ladder independent of gameplay randomness. Report the actual timed subset and label any extrapolated total. Arithmetic overflow invalidates the metric. Check numeric precision at export so Rust counts survive a round trip through the JavaScript report reader.

**Ending a window.** Admit attribution before warmup. At the measured start mark already-open operations as carry-in. Clip active segments to the measured half-open interval. Separately follow starts inside it through the frozen drain deadline, preserving the original ordinary clock, saves and stream. Record unfinished/censored operations, lower bounds, dropped observations and actual times of boundary reads. On stop, close admission for this generation, harvest all worker contributions including retired workers, invalidate handles and release the diagnostic storage. A late completion cannot write to a recycled slot or a later capture. Perform serialization, symbolization and checksum collection outside gameplay locks and measured callbacks. Missing output fails the capture, never the player's operation.

**Allocation pass.** Begin with the existing game memory owners' admitted, retained, pending-save and released bytes, and sampled process RSS. They answer different questions. An allocation-site profile needs a separate backend and run. Before adopting one, demonstrate that it observes the actual allocator, bounds sampling and export memory, does not allocate recursively or expose payloads, and still permits a held reader and a correct admission refusal. Otherwise report allocation-site coverage as unsupported. Never infer allocation rate from RSS or reclaim live data to improve the observation.

## 4. Qualify each instrument through its real caller

| Order                          | Required check and decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Driver and controls         | Verify the untouched production release and the normal build after adding the compiled-out seam. Then compare untouched with the probe-capable binary running disabled. Keep provenance for both binaries. Prove disabled mode creates no recorder, clocks, scans, workers, database reads or output solely for profiling. Verify an actual command reply, visible move, both private NPC request witnesses and one saved application per request with a cold continuation.                                                                                   |
| B. One joined parent           | Start with clock turn → dispatched driver step → accepted advance, including a real wait and yielded provider question. Use a focused fixed-work replay to match ordered input, saved randomness, debt, rollback and durable effects. Exercise return/error, busy refusal, cancellation, worker retirement and a later successful retry. Stop/restart with an open token. Fill or disable the recorder and prove the same gameplay still completes. This first slice must reach the offline report before adding more families.                               |
| C. One diagnostic at a time    | Compare a selected parent set with disabled. Select expensive children from that result and freeze the next set before dispatch. Add one enclosing span for a same-pass residual. Separately qualify each new probe family, CPU backend, SQL collection, allocator observation, future wrapper or sharded recorder against the otherwise identical build without that change. Match real inputs and compare resource cost as well as correctness. Keep higher-cost results explicitly diagnostic.                                                             |
| D. Privacy, storage and report | In fixed-work checks compare private permitted inputs and effects at the real preparation/application owners using the existing controlled fixture. Retain only equivalence outcomes in public evidence. Exercise correction/forgetting, cancellation while a reply is held, revocation before disclosure, slow/disconnected streams, save refusal/retry and cold reopening. Verify independent readers retain their original snapshot. Verify missing cases, late completions, bad hashes, lost samples and unexercised families stay visible in the report. |

Use the standard managed 16 GiB worker, fresh independent databases and three interleaved repetitions per arm (A–B, B–A, A–B) for each overhead claim. Compare each affected real caller with the same observer disabled before combining families. A prior pair can supply a shared control only when its identity and interleaving satisfy the new comparison. In particular, cost a newly selected child pass together with its disabled control before dispatch. Predeclare the cost, authorized case count, selection rule, stop condition and available balance. Start with one worker configuration. Qualify the dormant build before expanding. For each instrument, apply OB03 independently to **server** and **server plus owned PostgreSQL** CPU per completed work unit and to applicable command p95. Exact fixed-work semantic equivalence and complete real-time gameplay are required passes. A low overhead percentage cannot override a changed cognition input or a missing save. For a new sampler, compare the same executable with sampling off/on. If its build flags must change, qualify the unsampled build change separately. If a mode fails, split its selection, sample or retain an explicit gap within the frozen budget. Never mix diagnostic timings into a claim about a faster release.

## 5. Produce the answer

Reuse the verified local artifact layout, CSV/JSON and static HTML of the [hierarchical procedure](../../performance/hierarchical-profiling.md#8-artifacts-and-output-contract). Generalize only the fields consumed by both runtimes, such as server CPU and thread role. Report startup, steady play, drain, reconnect and recovery separately. The first page answers four questions.

- **How much of a core, at what game speed?** Show server and PostgreSQL separately, completed/offered game time and debt, client/driver separately, median/mean/p95 with units and sample populations. One core is 100%. Show supporting combined CPU per completed game-second, actual memory and reservation headroom.
- **What delayed the player?** Separate command response, first stream receipt, first browser display and durability. Correlate on existing operation/accepted-cut identities inside the private fixture. Use same-clock intervals or a measured clock mapping with uncertainty. An unsent frame, coalesced view or failed command is an outcome. Do not infer display from server handoff.
- **Which mechanic and which technical work?** Give disjoint sampled CPU groups, inclusive call paths, work per completed game-second and per call, plus the unresolved remainder. For example, “an observer checked sight 20 times, requested two geometry batches, and changed one memory” would distinguish an expensive check from a useful new observation. Compare parent and child only within a compatible pass. Subtract only nonoverlapping active intervals of synchronous children on the same execution lane.
- **Why so many database calls or bytes?** Summarize caller × finite query family, size probe versus body, lane wait, rows, prepared/application bytes versus measured wire bytes, WAL, growth and exclusive PostgreSQL CPU. Use existing group counters at boundaries. If available on the owned database, take filtered statement-statistics deltas in a separate mode, checking resets and evictions. Elapsed SQL time includes waits. Query counts do not allocate database CPU among features. Never log parameters, prompts, saved rows or raw SQL carrying private values. [PostgreSQL statement statistics](https://www.postgresql.org/docs/current/pgstatstatements.html)

Show unsupported/unselected/not exercised, censored, sampling loss and unqualified overhead beside the affected rows. Give the checked local report path, source/input identities, actual run count, spend and cleanup. A recommendation to check sight less often or retain fewer observations must say what the player or NPC could miss. Changing an authored rule or optimizing game code is a subsequent decision.
