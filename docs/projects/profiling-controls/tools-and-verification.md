Each script owns its one stop handle in an outer `try/finally`. Finish capture only after owned workers/server work stop, and take needed final snapshots before that. If cleanup throws, still detach observers and stop capture in a nested `finally`. Preserve the original failure plus existing cleanup reporting; do not add a generic multi-error framework.

In off mode, do not install application-duration listeners, domain counters, command-span context or additional per-operation traces. Existing optional CPU, allocation, native-count and detailed tracing selections that contradict this comparison mode must produce an early clear configuration error. Readiness/final metadata must state each active instrument separately; `appProfiling: 'off'` is not shorthand for “nothing measured this process.”

Report optional phase attribution as disabled when off. Never calculate a speed ratio, percentage or saving from absent counters. Use simulation timestamps from existing permitted state reads and successful command receipts for the comparison's independent progress measurements. Preserve the difference between wall-time achieved speed, admitted-time speed, pauses and pending debt. Read-only observation can still cost work; use the same read cadence in both modes.

Current sample/trace/export limits remain in force. No tests call providers or alter the user's development save. Use the existing disposable database/scenario mechanisms; preserve output-path refusal and teardown. A new flag must not weaken those safeguards.

## PC05: browser tool

1. Add `--app-profiling=on|off` to `scripts/performance/profile-browser.mjs`, default on, with strict duplicate/value handling. This chooses scene collection only. Read and report the server mode from its readiness manifest separately; it never controls the server through the browser.
2. When on, retain `profile=1` and the existing scene API workflow. When off, remove that query parameter, do not wait for the global scene API and never call its start/stop/snapshot/model methods. Retain ordinary scene-ready and visible-page checks. Missing scene data is explicit `null` plus its disabled status, not a zero-filled report.
3. Keep the independently injected browser animation-callback and HTTP receipt observations in both comparison modes, at the same cadence and retention bounds. Their optional calls into the scene collector must remain optional. Gate pose/scene-dependent movement watches when the scene report is unavailable. Report click-to-scene-position or completion evidence as unavailable, not successful or instantaneous. Do not make the profiler-off result pass a full movement-completion gate it cannot observe.
4. Preserve the ordinary fixed-coordinate move/cancel workload used by the non-survival path. It does not need the ground-inspection callback. Use the same inputs for both members of an overhead comparison and compare actual accepted commands, not just attempted clicks.
5. Reject `--app-profiling=off` combined with `--survival`, `--near-start` or `--wait-for-resume` before opening the browser: those workloads currently depend on the scene's inspection callback. Do not silently select a different workload. `--selection-sweep` and `--blur-off` may be used only identically in both comparison modes. Reject CPU/trace combinations with off mode for this minimally instrumented comparison.
6. Update report generation and every current report consumer to tolerate intentionally absent scene data. Include server mode, scene mode, domain counters, runtime monitor, external browser callback sampling, CPU sampling, trace and any remaining WebGL instrumentation. Do not retain old report schema aliases.
7. Final cleanup stops the driver's own callback/long-task collection and any explicitly started DevTools capture on success or failure, independently of scene cleanup. Preserve existing resource and export bounds. Capture start/stop request times and acknowledged times remain distinct.

Keep the disposable world paused while selecting speed, reading startup reports and arming collection. Resume through the ordinary control only after both collectors are ready, then write the server marker. Report the resume interval separately: preparing an on-mode collector while the game already runs can change the initial gameplay and invalidate the comparison. Console diagnostics retain bounded observation times and sanitized same-origin paths so request failures can be separated from teardown; do not include query strings or credentials.

This narrower off-mode comparison qualifies application profiling overhead on the fixed-input scenario; it does not qualify the survival soak or absolute “no observer” performance. Supporting that additional workload without a scene collector is an explicitly deferred tooling extension, not a reason to expose hidden world data or treat missing movement observations as a pass.

## PC06: measure overhead honestly

First pass static checks and these focused scenarios. Use the repository's existing formatter and TypeScript check after implementation, and required build/CI checks selected by actual impact. Reuse existing tests where relevant; do not create a large mirrored test suite for optional counters. Implementation verification follows the agreed run allowance; this project does not reset it.

Later compare one integrated implementation in both modes using identical host, build, scenario, admitted activity and observation cadence. Keep fixture creation, reset, source fingerprinting and export outside measurement. Use separate fresh fixtures/processes per comparison so changing caches, growing history and old workers do not contaminate the result.

1. **Focused cost comparison:** exercise the same finite native/server workload with profiling off and on, first cold and then warm. Record elapsed time, CPU, memory and completed operations outside the measured callback. A collector microbenchmark can explain overhead, but cannot qualify the game.
2. **Matched server/browser comparison:** use the existing expanded scene, requested 3× speed, the same fixed-input browser path and bounded duration. Use the same public reads and external callback observations. Run off/on and reverse the order for a repeat when the agreed run allowance permits. Avoid concurrent noisy benchmarks. Record host load and order. This is a proposal for bounded comparison, not permission to reset another project's run allowance.
3. **Interpretation:** use external simulation progress, accepted command counts, real elapsed time, frame-delivery tails and errors. Off/on ratios of absent internal metrics are invalid. If one run generated substantially less gameplay work, report the pair as inconclusive. If enabled sampling changes cooperative yield timing, report that difference rather than attributing all cost to one sampled function.
4. **Retention:** retain the architecture only after the off path avoids the specified work and correctness passes. Report enabled overhead numerically. An unexplained material regression in comparable complete-caller cost remains open; do not mark it complete because timings can be displayed. Tiny differences within observed host/run variation are inconclusive, not a win. Do not invent a universal percentage acceptance threshold from this unmeasured design.

Create one focused runtime evidence report under `docs/verification/performance/` when execution actually occurs, then link it from the existing verification index and PC tracker. Do not create an empty report now. Use the following readable table, followed by source revision, machine, instrument settings, actual workload, durations, count coverage and limitations:

| ----------------------------------------- | ------------- | ------------ | ------------- | -------------------------------------------------------------------------------------------- |
| Finite native/server workload             | Pending       | Pending      | Pending       | Same admitted simulation work required                                                       |
| Whole-server progress and command latency | Pending       | Pending      | Pending       | Same successful activity and observation cadence required                                    |
| Browser frame delivery                    | Pending       | Pending      | Pending       | External callback observation remains in both; display presentation is not directly measured |
| Retained memory and cleanup               | Pending       | Pending      | Pending       | Distinguish current retained data from peak process memory                                   |

Final 3× acceptance remains the parent performance project's separate criterion. A faster disabled collector does not establish that the game now meets it.
