# Mechanics that context must explain

**Source inventory for the proposed context design; not a new mechanical specification.** Baseline and project scope are in [the project packet](README.md). Values in examples describe that inspected world version; production packets must read current owners. The [technical design](../world-agent-context-tech-design.md#3-mechanical-descriptions) owns the proposed description shape.

## Objects and identities

| Thing                         | Meaning for the agent                                                                                                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Item/material definition      | Describes properties and native behavior; does not establish that anyone possesses an instance or knows its recipe.                                              |
| Recipe and candidate revision | Specifies a finite crafting transformation. A saved candidate is neither an installed recipe nor a crafted object.                                               |
| Live item/lot                 | Has identity, quantity, definition pins, placement/access and revisions. Splitting or equipping can change selected instance identity.                           |
| Entity/body                   | Receives native actions, bound attributes and status instances according to its capabilities. An actor is a kind of entity, not the only possible effect target. |
| Resource source               | Supplies a finite typed resource. A source's remaining quantity differs from a material's definition and from inventory.                                         |
| Attribute definition/value    | Definition supplies meaning, unit/range and implementation; a binding supplies a value on a particular entity. Definition alone does not bind it.                |
| Status definition/instance    | Definition supplies conditions/operations; an admitted instance has exact receiving/source/target bindings, state and lifetime.                                  |

[Persistent objects](../../../packages/domain/src/objects.ts), [domain types](../../../packages/domain/src/types.ts), [world modules](../../../packages/domain/src/world-modules.ts) and [status effects](../../../docs/status-effects.md) own these distinctions. Custody, access, control and legal ownership must not be inferred from one another.

The executable status family is wider than the current hand-written authoring guide. A new generated guide must include actual supported contribution fields or declare its incomplete coverage; copying the current prose is not proof of complete schema support.

## Relationships and future mechanics

The [initial foundation](initial-foundation.md) derives a candidate graph from these same owners for context, validation and review. It also checks the design against the harder [action repertoire](../../repertoires/actions.md): multi-person roles, continuing actor/device processes, ordered physical prerequisites, attributed observations and identity/topology/time constraints. These cases require honest requirements and missing-capability findings now; they do not authorize new execution families. Preserve their distinctions when extending the common description shape rather than forcing every action into a subject/source/target triplet.

## Worked context selection

### Sling

Include eligible cord/prepared-fiber definitions and properties, swing field meanings/ranges, crafting consumption/completion and the native hunt consumer. Explain finite stone use, chance and target/reach limitations. Include a short statement about work using ordinary energy; only expand physiology if the request depends on it. Omit global entity lists, unrelated custom attribute schemas, NPC memories and filesystem instructions.

The schema's `accuracy` is not a promise of guaranteed hits. A larger `workSeconds` does not automatically raise accuracy; these are candidate parameters chosen to meet the request and bounded by validation. Narrative “homing” in a description does not add a homing consumer.

### Reed-gathering tool

Include exact eligible rigid-and-flexible body/binding materials, resource definition, total yield, finite source/non-stacking behavior and craft work. Both body properties are required by the current role/family checks. The output remains useful without weapon or status-policy schemas. Native source debit and inventory credit must describe the same typed resource and amount.

### Faster-restoring bed

First distinguish the requested object from the existing sleep policy. Read the sleep effect's receiving entity, entry/exit rules, energy rate and capability restrictions; include native fullness drain and separate awake expenditure as relevant interactions. Explicitly report missing item-to-effect binding, bed recipe/output family and any placement/use adapter rather than inventing them.

A world owner may separately choose a wider sleep-policy revision. That proposal must show who is affected and preserve or explicitly review every other policy definition. Current policy submission is whole replacement: omitted definitions are removals. A compact edit template must not silently change this contract.

### Charge without a source

A custom reservoir definition and body attachment do not create a battery item, supply or charging mechanism. Native drain continues during replenishment. Gross transfer comes from finite compatible stock; away from bounds and other effects, equal drain/replenishment rates maintain the recipient value while consuming stock. Work duration bounds transfer time, not net gain. Context must identify the compatible source/transfer owner or say it is missing. A reviewed direct value edit is an owner intervention and can create/remove fictional quantity; it is not ordinary replenishment. A future mechanical adapter is justified by the missing operation, not by adding another descriptive field.

## Extension test

A coherent world may have machines without hunger, different clocks or non-human senses. The assembler should request that world's actual capability descriptions and relevant values. It must not prepend wilderness survival rules universally. Adding a real family requires purpose/support, typed fields, dependencies, lifecycle, disclosure and native verification under the existing semantic owner; this project does not add an unused plugin loader or arbitrary rules interpreter.
