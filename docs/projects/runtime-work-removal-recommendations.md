# Recommended removal of routine simulation work

| Status      | Current progress                                                                                                                         | Last updated |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| Not started | Source review is complete; the recommendations below are proposed changes, not installed behavior or performance-qualified improvements. | 2026-11-08   |

## 1. Recommendation and evidence boundary

Remove unnecessary event and personal-account creation at its source, then remove repeated preparation of unchanged receiving state. Preserve meaningful physical consequences, personal knowledge, useful recent chronology and independent characters. Do not begin by shrinking attention, weakening privacy, or deleting flight. Those choices would discard valuable behavior while leaving shared overhead intact.

This is a decision report, not another implementation specification. It recommends changes to the existing [BK29 design](bookkeeping-simplification-tech-design.md#21-proposed-pressure-and-preparation-work-removal) and identifies additional removal targets. Accepted changes belong in that design and its [tracker](../maintainers/production-data.md#bk29--pressure-and-preparation-work-removal-proposed). The separately selected [native-core design](native-simulation-core-tech-design.md) owns resident-state conversion and its adoption experiments. Do not create competing event, memory, scheduling or persistence systems from this report.

**Source inspected:** `codex/stealth-runtime-01-evidence`, initially `aac9e438da22e4d80ddf9066e71d90dff69ac828`, with documentation reconciliation through `d092d52989d4fd5e0dc0bf4342cd9f9408ce6d00`. The `apps` and `packages` source trees at the reviewed head have no diff from measured runtime `330da6405d49a4069c2536893a646f9ec3fc966d`. Review covers the production paths identified below and their important consumers; it is not a claim to have audited every repository file. No game execution, benchmark, cloud resource or model call was run for this report.

### What the existing measurement establishes

The [BK29 investigation](../verification/performance/bookkeeping/2026/2026-11-07-bk29-profile.md) measured the standard opening: seven people, twenty animals and seventy-four other physical roots. After a 60-second warmup, a six-real-minute run accepted 768 scripted commands at the unchanged 60:1 game clock. Models were disabled. The driver replaced movement commands every 500 ms with additional bursts and requested full state at 4 Hz; this is aggressive input, not an idle opening or an exact reproduction of the real client's SSE-driven requests.

- The clean run achieved **100.006% normal clock**, **95.95% of one main CPU core**, and **180.26 ms p95 / 482.90 ms maximum command latency**. It did not reproduce one-second latency. Its collected main heap was 430.8 MiB and cold-validated checkpoint 88.6 MiB; neither number is peak allocation or a CPU attribution.
- A separate late CPU diagnostic assigned 17.25% inclusive samples to encounters/perception, 7.20% to attended-history reconciliation, 7.08% to attention, 6.90% to status preparation, 9.40% to event recording and 9.58% to player projection. These overlap. Direct record/draft/Immer utility samples were 30.34%, with another 5.14% in garbage collection. These categories cannot be added to predict savings.
- The clean checkpoint contained 1,659 animal-response events, including 1,575 generic escape announcements; one bird produced 1,545 of those announcements. Across five witnesses, animal responses generated 5,983 recent occurrence entries and 5,983 pooled values. Their value payloads occupied about 4.56 MB, and compactly reserialized occurrence entries about 7.08 MB, before page/index overhead. These totals include warmup and final capture.
- Flight-choice admission occupied 6.13% inclusive sampled time, predominantly its emission chain (5.86%) and witness acquisition (4.89%, overlapping). This does **not** establish the total cost of physical flight or predict a 6.13% saving from removing flight.
- Later reader/counter attempts failed to produce complete measurements. They establish neither a successful optimization nor a gameplay failure. The current rate and occupancy of account-retention queries remain unqualified; older reader measurements are not measurements of this head.

The strongest immediate evidence is excessive work _created by announcements_, plus source-confirmed repeated preparation. Savings for the proposals remain unmeasured. Fewer rows alone do not prove a faster complete game.

## 3. Remove narration-driven work

### R1 — Remove generic animal-response announcements entirely

**Current path.** [The response controller](../../packages/domain/src/native-response-controller.ts) emits `animal-response` from `beginNativeAlarm`, settling/routine transitions and `admitNativeFlightChoices`. [The kernel's `nativeMovementTransition`](../../packages/domain/src/kernel.ts) also emits it for ground escape. The flight emitter runs after an accepted finite leg, even during continuing escape. Retained routes already have continuity/hysteresis; this is not proof of repeated random selection of an unchanged route.

Each emission enters [`events.emit` / `recordEvent`](../../packages/domain/src/events.ts): choose audience, create occurrence identity/time/text, prepare each observer's permitted references, acquire evidence where needed, capture attended history, update attention cues, finalize immutable data, and offer history to persistence and display. Animal responses have presentation classification in [the base event vocabulary](../../packages/domain/src/worlds/base/event-presentation.ts). They are not actual sounds. [`nativeResponseReceiver`](../../packages/domain/src/native-response-controller.ts) consumes actual harm/projectile/attack-preparation families, not these announcements; the announcements do not cause the escape. The native appraisal owner likewise does not turn every announcement into an emotional update.

**Recommendation.** Delete the generic explanatory announcements from this world's native animal controller, including onset and settling prose, rather than merely deduplicating escape legs. Keep the controller's private state, motion, actual physical reactions, RNG choices, collisions and genuine sensory occurrences. Do not add a corresponding received `fleeing`/`alert` field, a replacement onset event, an AI inference, or another retention store merely because the announcement disappeared. A hunter needs the animal's permitted position/visibility and usable range to decide whether to pursue. Private intention is not a prerequisite for that decision.

Real vocalization, impact, attack preparation and material interaction retain their source owners. If a selected future behavior actually depends on an observable posture or alarm sound, implement that physical cue for its concrete consumer. Do not infer a sound from this event's name. Check generic event-dependent commitments as well as literal event-type callers before deleting a family: [`advanceCommitments`](../../packages/domain/src/commitments.ts) supports data-declared completion conditions. A required completion must have an explicitly retained meaningful source, or the removed event-based condition must be retired from the supported authored vocabulary; never leave it silently impossible.

This changes the bundled world's outward behavior, not an engine law forbidding other authored realities from defining meaningful alarm sounds or observable actions. Remove unused emission/vocabulary paths together; do not leave a default-disabled duplicate pipeline or hardcode species exceptions in the engine.

**Tradeoff.** Lose generic log sentences, their extra event-time position samples and repeated mild attention emphasis. Ordinary sight and attended motion remain. Someone can miss a brief onset between sight samples; no synthetic replacement sample should conceal that deliberate loss. A later observer cannot be told when an earlier escape began.

**Removal target / acceptance.** Zero generic animal-response occurrences, witness values and history rows from those producers, with no compensating state-label pipeline. In isolation preserve physical routes, random choices and native consequences, while comparing IDs semantically because removed event allocation changes numbering. Exercise first alarm, continuing legs, blocked movement, settling, renewed harm, unknown/late witnesses and cold restore. Broader actor attention may intentionally change because repeated artificial cues are gone; record that difference rather than demanding identical attention.

This recommends replacing BK29-E1's proposed requirement to preserve received fleeing/alert meaning. It requires adoption; it is not an already changed contract.

### R2 — Remove routine walking announcements, without removing action semantics

**Current path.** [The command/complete-action owners](../../packages/domain/src/kernel.ts) emit `action-started` for ordinary movement and `moved` on arrival. These are action boundaries, not each coordinate. Actual native locomotion already skips ordinary movement announcements. Failure uses `action-stopped` and sometimes a separate private reason. These records enter the same audience/evidence pipeline as consequential occurrences.

**Recommendation.** For successful, standalone, unconsequential walking, stop publishing departure/arrival prose as witnessed events. Use received current motion and its admitted recent sequence for witnesses, and the actual action result for its performer. Do not replace each sentence with another independently stored movement event. Ordinary repositioning needs no automatically narrated destination or motive.

Classify departure using the bindings and observable cues already known at admission, not a prediction that the walk will succeed. Classify the eventual outcome from its actual effects. A later obstruction, injury or other meaningful outcome can produce its own necessary evidence even when departure was quiet; never backfill a start observation that nobody received.

Do **not** remove `action-started` globally: attack preparation and other meaningful work use it. Preserve interrupted production, injuries, obstruction, resource changes and deliberately bound work. Keep plan/goal/method/cooperation/commitment-linked outcomes unless the corresponding consumer is converted explicitly. [`basePreparedThreatResponses`](../../packages/domain/src/worlds/base/threat-responses.ts) also considers `moved` and `action-stopped` for known encounter participants; preserve its needed received state/sequence through its existing evidence owner before suppressing those sources. This is a caller conversion, not a text or event-type blacklist.

**Tradeoff.** Less routine log noise and no extra event-time arrival sample between scheduled sight checks. An observer retains the route they actually sampled, not guaranteed exact departure/arrival instants. The performing character still gets truthful completion or failure immediately.

**Steering boundary.** [`player-steering`](../../packages/domain/src/player-steering.ts) and [`world-input`](../../apps/server/src/world-input.ts) already provide ongoing direct input without manufacturing a command per steering sample. Keep them. The profiled workload repeatedly submits discrete move commands; do not call that proof that all real controls cancel/restart movement. Further click-to-walk retargeting is not selected here: first remove the account/announcement cost, and separately measure actual control use before building another action identity protocol.

**Removal target / acceptance.** Eligible travel produces no external start/arrival wrapper or duplicate personal account; collision, final outcomes, cancellation identity, threat consumers and bound activities still work. Keep a precise private failure result when navigation fails. Check an attended walk with a turn, an interruption, a move fulfilling a commitment, and an attack preparation that must still be noticed.

### R3 — Use one personal source for routine outcomes

**Current path.** [`endActivity`](../../packages/domain/src/action-experience.ts) writes the actual execution outcome, then ordinarily creates an `episode` memory and assigns `resultMemoryId`. [`finishPlanAction`](../../packages/domain/src/agency.ts) can recreate a missing account. [`baseRecordingReason`](../../packages/domain/src/worlds/base/attention.ts) classifies own consequences as required; `baseAccountAfterRelease` already says eligible routine travel should later be discarded. Thus some data is created, charged, indexed, selected for cleanup and deleted despite never warranting a lasting recollection. Skipping `appendMemory` alone is unsafe.

**Recommendation.** Implement [BK29-D's complete typed result-source conversion](bookkeeping-simplification-runtime-design.md#bk29-d--one-personal-source-for-routine-results). Store the small exact actor-owned outcome in the existing recent receipt stream once. Use one result reference/resolver for its actual consumers. Do not create an additional autobiographical account, support capsule or pin merely because it is the latest result. Keep execution/learning records and network retry receipts for their distinct purposes; neither grants unlimited personal recall.

Convert agency result pointers, required-outcome/context selection, threat result handling, learning/inspection, correction/forgetting, pending reads, codecs and cold restoration together. Retain independent exact support only when an actual learned fact, promise or deliberate recollection requires it. The eligibility predicate stays world-owned and excludes effects, outputs, spending and meaningful bindings. Do not extend a successful narrow movement conversion to all action families without auditing their consumers.

**Tradeoff.** Ordinary unbound results use the existing six-game-hour recent horizon and pressure policy instead of a preferred one-day automatic account. Under the current clock, those six game hours are six real minutes at normal speed. Trivial details can disappear without a summary; a remaining pointer does not extend retention. Meaningful outcomes and independently retained knowledge keep their contracts. Expired personal evidence is unavailable, not a failed physical action and not recoverable from hidden execution history.

**Removal target / acceptance.** Zero routine-result account insertion, account-index admission and account-aging work on the eligible path. Preserve actual outcomes, required context outside attention slots, correction of retained support, cold retrieval, and continued progress when an old result has expired. Reject the conversion if per-result capsules/pins/queries recreate the cost in another form. The earlier omission experiment that stalled time is not successful evidence for this recommendation.

## 4. Remove repeated preparation

### R4 — Private clocks must not invalidate sight and attention

**Current path.** The response controller's `changed()` always calls `recordAnimalClockWrite`, `recordSensoryChange` and a general `behavior` notification. It is called after pure review-deadline refreshes, including pending navigation and retained-flight continuations. [`recordNativeChange`](../../packages/domain/src/native-change-feed.ts) then feeds sight work and invalidates observer preparation for behavior changes. [`reconcileNativeDangers`](../../packages/domain/src/native-response-danger.ts) also includes global sensory/state revisions in its short-lived reuse proof. Unrelated broad notifications can therefore defeat other preparation.

**Recommendation.** Implement BK29-E2 at the actual mutation owner. A timer-only write updates the existing timer/queue. Actual pose, body capability, exposure, public activity or relevant native-decision changes notify their actual consumers. Reuse the pattern already present in [`setForagingReviewAt`](../../packages/domain/src/worlds/base/foraging-state.ts), rather than introducing another change bus.

Audit the entire operation before calling it timer-only: an earlier danger reconciliation can have changed real facts. Do not merely set `outwardChange: false` and assume every consumer honors it; perception preparation, status/rate forecasts, behavior and sight have distinct dependencies. A private destination can affect execution without becoming a new outward observation. Unknown writers retain conservative invalidation.

**Removal target / acceptance.** A pure private review changes no sensory revision, observer candidate set or unrelated status input. Real danger, movement, capability and visibility changes still take effect at their required boundaries. Measure reduced downstream work, not just fewer notifications. Routes, deadlines and RNG remain unchanged in this isolated stage.

### R5 — Remove the per-event global observer inventory

**Current path.** [`externalAudience`](../../packages/domain/src/event-audience.ts) calls `worldRootEntities(world, true)`, gathers scalar inputs from all eligible memory-capable receivers and compares the complete list with its prior index before a local query. It reuses geometric buckets, but ordinarily rebuilds the list that proves they are reusable. `withStableAudience` avoids that only in a narrowly fixed phase. Admission to detailed personal evidence happens later in `recordEvent`.

**Recommendation.** After R1/R2 reduce event count, make surviving events query a receiver inventory maintained from actual membership, position, range and participation changes through the existing spatial/change owners. Known direct/felt recipients use exact identity access; external witnessing still uses conservative candidate selection and exact occurrence-time visibility. Reuse only a compatible phase's prepared receiver inputs. Do not turn an old visibility grant into proof of a new event or introduce a second independently writable spatial index.

For an event whose recording policy permits only existing detailed attention, intersect legitimate receiver candidates with that existing attention eligibility before preparing names, rich references and wording. This optimization cannot gate real speech, physical reaction, actual harm or required evidence on attention slots. The current late rejection already skips much rich materialization; retain it as a fallback, not as proof that audience preparation is free.

**Growth / acceptance.** Remove the `events × all physical roots` inventory cost; target changed receiver maintenance plus nearby exact candidates per surviving event. Actual witness fan-out is still required and can be large. Qualify mixed radii, moving receivers, appearance/disappearance, occluder/participation changes and direct harm by an unseen attacker. Include index maintenance and cold rebuild cost. If maintaining a new structure costs more, extend existing spatial preparation rather than adding caches to rescue the experiment.

### R6 — Select detailed-sight contacts before enumerating them

**Current path.** [`reconcileVisualEvidence`](../../packages/domain/src/perception-evidence.ts) begins its support/loss pass with `currentContactEntries(state).sort(...)`, then skips contacts outside `measuredSubjects`. [`currentContactEntries`](../../packages/domain/src/perception-current.ts) materializes the collection and, inside a pending contact batch, merges it into a new map first. The kernel's detailed-sight callers already supply the exact selected subject set. A ten-subject check can therefore prepare every visible contact before rejecting almost all of them.

**Recommendation.** In the explicitly scoped path, fetch selected contacts with the existing `currentContactGet`, including pending writes, then preserve their authoritative order. Examine all prior/current contacts only for genuinely complete broad acquisition or global invalidation that requires it. Selected lost contacts must be checked even when absent from the newly visible subject list; use the requested selection, not just successful measurements.

**Growth / acceptance.** Change the scoped contact pass from materializing/sorting all `C` contacts to selecting `K` requested contacts and ordering those, where `K` is the actual detail set. No new persistent index is needed. Exercise detail-only loss, pending deletion/replacement, same-time broad/detail phases, channel/life replacement and global perception loss. Do not falsely claim that broad first exposure or downstream contact work has become constant-time.

### R7 — Let received changes drive recent-history work

**Current path.** [`reconcileAttendedTemporalEvidence`](../../packages/domain/src/perception-evidence.ts) prepares prior/final cohorts, selected-track sets and current groups. [`captureTemporalCurrent`](../../packages/domain/src/temporal-evidence.ts) partitions members against prior recording marks, constructs content comparisons and then skips unchanged content. Unchanged sightings already produce no new historical receipt; the remaining target is the work performed to reach that answer. This path accounted for 7.20% inclusive sampled CPU, not 7.20% proved removable CPU.

**Recommendation.** Feed the existing capture owner the actual changed current groups plus attention entry/exit, loss/unchecked transitions, identity correspondence changes and genuine recording-repair work. The existing receiving phase and current-group owner know these causes. Do not rebuild all selected group inputs merely because another sight opportunity completed. Leave latest independent confirmation times in current evidence; capture a terminal using its actual final check when coverage ends.

Keep baselines for entrants and the outgoing subject's triggering change. A prior capacity refusal may become recordable when capacity improves, even without a value change; explicit repair must still run. Required events remain independently ordered. Contact/familiarity credit and terrain acquisition keep their own actual due conditions rather than being accidentally suppressed with history work.

**Growth / acceptance.** Target changed groups plus genuine lifecycle work instead of all attended fields per opportunity. This is an experiment because stale-detail and coverage semantics are subtle. Verify stationary confirmation writes no history and does no full capture preparation; then verify changed pose, independently stale appearance, same-time unequal frames, loss, reentry, correction, pressure refusal/recovery and restore. Reject a shortcut that fabricates continuity across a gap or silently drops required changes.

### R8 — Keep valid attention preparation across ordinary continuations

**Current path.** [`workingNativeWorld`](../../packages/domain/src/kernel.ts) starts a new `beginAttentionPreparation` lease. [`annotationCatalogue` and `attentionCandidates`](../../packages/domain/src/attention.ts) rebuild on a cold lease. Within a lease the code already reuses selections and refreshes changed sources; pose-only changes can reuse descriptions. The remaining candidate loss occurs across invocation/publication boundaries. Warm ranking/grouping can still traverse candidates; ten selected entries do not bound that population.

**Recommendation.** Implement the bounded exact-successor reuse in BK29-B if attribution confirms enough cold rebuilds to justify it. Keep scalar descriptions/scores and existing dependency identities through the owning continuation; never retain mutable bodies, authorization results or entire previous worlds. Update changed/due candidates, and rebuild on correction, unknown writers or incompatible forks. For the native-core route, keep the equivalent preparation resident under the same owner rather than porting a TypeScript-specific token mechanism unnecessarily.

**Tradeoff / acceptance.** No intended change to attention selection, discovery, familiarity, slot count or acquisition timing. Retained preparation consumes bounded current-scene memory and requires exact invalidation. Count complete cold builds, descriptive reads, transferred/copied entries and actual ranking work. Reject per-publication full-map copies, whole-world fingerprinting or a retained chain of old worlds. Do not add an independent ranking tree or deadline scheduler without a remaining measured need.

## 5. Remove maintenance and ambient work at their cause

### R9 — Batch real account pressure instead of repeatedly preparing tiny retirements

**Current path.** [`experienceMaintenanceTarget`](../../packages/domain/src/remembered-impressions.ts) uses 75% of the required-account ceiling both to trigger early work and to select the retirement target. [`prepareAccountRetention`](../../apps/server/src/account-retention.ts), [`RetentionMetadata`](../../apps/server/src/retention-metadata.ts) and the saved deadline machinery use that boundary. A small new ordinary outcome can make another selection/closure/transaction necessary shortly after a previous retirement. The current head's actual frequency is not measured by the failed diagnostic.

**Recommendation.** Use BK29-A's single-owner start/stop experiment after reducing account creation. Its concrete initial policy starts at 448 records / 3.5 MiB and retires toward 384 records / 3 MiB, preserving the 512-record / 4 MiB hard ceiling. Retain natural due-time cleanup, exact ownership, fair scheduling and protected obligations. All scheduling/admission/metadata/application callers must agree on which threshold they use. A pressure pass with only protected material must settle until something relevant changes, not spin.

**Tradeoff.** The proposed start leaves less spare space for a sudden burst than today's early trigger. It can cause new admission refusals if preparation cannot keep up. Do not raise quotas or drop protected data to hide that failure. Fewer initial accounts may make this tuning less valuable; remeasure after R3.

**Acceptance.** Count useful retirements per preparation, no-op/stale work, reader occupancy, command waits, debt and rejected required operations. Include a simultaneous burst and delayed save/read. Keep only a complete-path improvement without new normal-play refusals or growing debt. Exact logical expiry and deletion later remain separate; do not replace them with a new cleanup service.

### R10 — Stop generating movement solely to make idle wildlife look busy

**Current path.** [`nativeWanderRoute`](../../packages/domain/src/native-response-controller.ts) chooses a random supported move of 0.4 m after the base profile's 120–239 game-second wait: roughly every 2–4 real seconds at normal speed while eligible. [The kernel](../../packages/domain/src/kernel.ts) excludes animals with an active episode, territorial role, foraging state, flight or other work. These impulses already avoid ordinary movement announcements, but still change physical/sensory state. [The starting bird](../../packages/domain/src/worlds/base/world.ts) also installs an automatic flight loop. [Ecology installation](../../packages/domain/src/worlds/base/ecology.ts) gives selected species genuine need-driven behavior; that is a different path.

**Recommendation.** Run two separate world-policy experiments: disable the default fallback random shuffle, and stop starting the opening bird on automatic laps. Leave idle animals resting while preserving authored foraging, hunger, pack/territorial behavior, threats, flight escape and actual interactions. Keep flight capability and refuges. Do not make a visible huntable bird secretly decorative, and do not remove unrelated useful starting content.

Use the existing world/controller seam, with no new scheduler or generic ecology framework. Disabled idle behavior must have no recurring wander deadline; merely making its distance zero would retain the useless wakeup and can violate current validation. Update the installed current-format definition and callers together. Ordinary visual idle animation may provide atmosphere but must not move the authoritative collision body or invent heard footsteps.

**Tradeoff.** Less incidental motion and fewer purely accidental wandering encounters. These are recommended product simplifications, not behavior-preserving optimizations. A quiet animal must still flee, feed, hunt or respond when its existing rules require it. Some animals already never reach fallback wandering, so removing it may save little; count actual eligible moves. The bird's measured expense is predominantly escape announcements, so disabling its passive loop is not a substitute for R1.

**Acceptance.** Measure each change separately with actual travel, needs, encounters, feeding, reactions and deaths reported. A different RNG/distance/event history is expected; compare playability and complete cost, not exact old trajectories. Revert a negligible or worse tradeoff instead of removing more living behavior to force a gain. Keep these content-policy results separate from equal-behavior native-core comparisons.

## 6. Remove representation overhead without removing integrity

### R11 — Keep private execution resident; capture only at real boundaries

**Current path.** [`draft`](../../packages/domain/src/draft.ts), [`records`](../../packages/domain/src/records.ts), current-contact finalization, native continuations and [server record preparation](../../apps/server/src/world-records.ts) maintain immutable publication, previews, persistence changes and safe deferred reads. These are real duties. The profile identifies substantial utility CPU, but does not prove that the entire world or old history is copied every step. Already certified/frozen descendants are shared, and `immutableDataSnapshot` already combines copying and certification for its owned output.

**Recommendation.** Use the selected [NSC01–NSC03 complete pipeline proof](../maintainers/native-simulation-core.md) to replace repeated private draft/graph reconstruction with one resident authority, compact changes and bounded snapshots at actual consumer boundaries. Keep current required status/rate forecasts and eliminate repeated proof/preparation of their unchanged inputs; do not remove hunger, bodily state or condition effects because `NativeStatusPreparation` has a large sampled stack. Private rollback, nested response outcomes and hypothetical previews still need their explicit checkpoints. Saving and model/player reads receive immutable selected cuts, not the mutable resident authority.

Do not undertake a wholesale Rust port or distributed execution before the proof. Compare against the specified compact TypeScript control so representation effects are not automatically credited to language. Do not build a parallel TypeScript resident engine or a second save writer in this recommendation. Carry accepted R1–R10 semantics equally into both arms. The existing core design already supplies the ownership, host bridge, rollback and restoration plan; this report adds no competing framework.

BK29-C is an interim option only where object-identity attribution shows a real repeated freeze/proof traversal that its existing owner can combine. Do not add universal eager certification just because some later callers might ask for it. Do not simultaneously enlarge that interim machinery and port it away without a demonstrated reason.

**Acceptance.** Compare complete movement → receiving → attention/history → permitted consumption → actual PostgreSQL save/restore, including bridge copies, queues, Node CPU, native CPU, allocation and command latency. A fast native movement loop with missing observation/storage work fails. A prototype that removes checks by exposing shared mutable data fails. Rust and parallelism remain experiments; moving the same work off the Node thread is not proof of less total work.

## 7. Keep these features and avoid duplicate projects

| Tempting cut or rewrite                                                   | Recommendation and source-based reason                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Remove flight entirely                                                    | Keep the supported capability initially. The 6.13% stack is predominantly announcement work, not an isolated flight-physics measurement. R10 can remove passive laps without deleting escape/hunting interactions.                                                                                           |
| Slow sight again or shrink attention                                      | Keep broad/detail defaults at 60/30 game seconds (1/0.5 real seconds at normal speed), the current change-driven scheduler and default ten detail allocations. Quiet unchanged worlds already have no ordinary sensory deadline. Removing repeated preparation is the selected first change.                 |
| Keep only the last position of an attended subject                        | Reject. Received turns, interactions and ordering support tracking, testimony and the promised reliable recent sequence. Compressing away meaningful turns is a real loss, not a free optimization.                                                                                                          |
| Delete all coverage endings                                               | Reject. Loss, unchecked support and attention exit are different. Keep compact boundaries so history cannot falsely bridge an unseen interval; remove prose/duplicate processing, not the needed distinction.                                                                                                |
| Make everything visible only if it wins a detail slot                     | Reject. Broad awareness and received terrain stay separate. A daughter, fifteen pursuers and a cliff must not depend on squeezing every relevant object into ten subjects.                                                                                                                                   |
| Give every animal a lighter replacement mind                              | Do not create another system: `hasMemory`, native command admission and receiving already exclude ordinary native animals from human autobiographical/detailed-attention work. Audit exceptions, preserve this boundary and remove their unnecessary broadcasts instead.                                     |
| Introduce yet another change-only history or shared-value store           | Reject. Current history already skips unchanged content; shared received values, compact contacts and independent freshness are installed. R7 removes repeated preparation inside those owners.                                                                                                              |
| Rebuild direct steering                                                   | Reject as a default project. It already exists. Any remaining discrete-command retargeting needs its own demonstrated workload and benefit.                                                                                                                                                                  |
| Permanently remember every passerby                                       | Already not required: body-only roles can be temporary; lost individuals have scoped pruning and familiarity is bounded. Do not introduce another forgetting store. Preserve genuinely learned identity/name support.                                                                                        |
| Remove correction, private-source checks or exact support universally     | Reject. Preventing hidden knowledge and honoring promises/learning are central gameplay and integrity requirements. ## 9. Implementation order, experiments and stop conditions

1. **Adopt the behavior decisions explicitly.** R1/R2/R3/R10 change parts of the current game. Reconcile their feature/world contracts, activity/result and generic commitment consumers before editing runtime. In particular, replace BK29-E1's compulsory activity-label target if R1 is accepted. No schema compatibility layer or old-format reader is needed.
2. **Finish the first selected removal, then compare it.** Implement R1 with all actual producers/consumers. Compare alone on the standard managed 16 GiB AWS worker. Do not combine it with physical-flight removal and attribute the difference to event overhead.
3. **Convert routine travel as one coherent path.** Complete R2/R3 through action outcomes, cognition, player history, commitments, correction and persistence. Retain intermediate source boundaries to distinguish omitted announcement work from account work in isolated comparisons; do not leave permanent production switches.
4. **Remove shared repeated preparation.** Qualify R4, R5, R6, R7 and R8 individually, finishing each implemented stage before its comparison. Reuse the existing owner/change feed. A pure scope reduction can preserve complete outputs; event removal intentionally changes only its declared evidence/presentation behavior.
5. **Retune residual maintenance, then evaluate idle wildlife.** Apply R9 only to the remaining account stream. Compare R10's two world-policy variants separately, reporting changed behavior and actual work. Keep these separate from equal-policy engine benchmarks.
6. **Run the existing complete native-core proof.** R11 is the architecture experiment already tracked by NSC. Adopt wider conversion only after its complete-path gate; do not keep a second production backend merely to preserve an experiment.

The minimum useful measurement for a stage combines an unsampled complete workload with bounded attribution for its removal target. Use the same source/control, opening, inputs and timing; report actual movement, reactions, completed commands and meaningful outcomes. Use an unchanged-policy control for implementation removals. For deliberate product cuts, report both the reduced work and lost behavior rather than claiming exact equivalence. A short native scenario can establish a specific invariant but cannot qualify service latency or population scale.

Count event births and recipient preparation, current contacts visited versus selected, actual changed versus captured groups, cold attention/status preparations, account births/retirements per pass, required refusals, rows/bytes, reader occupancy, main/whole-process CPU, retained memory, progress and command/SSE behavior. Select counters relevant to the stage; do not build a permanent exhaustive telemetry system. Do not add overlapping stack percentages or infer storage savings from only one table.

**Stop/reject conditions:** privacy or chronology failure; missing native reaction; stalled time; refused ordinary work caused by reduced headroom; lost pending data; rising cleanup debt; total cost shifted to support/index upkeep; or an isolated result with no worthwhile complete-path gain. Revert an unsuccessful optional mechanism instead of raising limits, hiding consumers or retaining both implementations. Existing normal-clock, cold restore, mature-memory and population acceptance remain unchanged; passing the small opening does not qualify hundreds of richer characters.
