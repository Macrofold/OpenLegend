## 1. Owners and architecture

Extend `scripts/verification-workers/`; retain one source packager, transport, bootstrap, supervisor, artifact owner and infrastructure template. [Feature behavior](verification-campaigns-feature-spec.md) and [current worker contracts](../technical/verification-workers.md) remain distinct: native SQL/isolation evidence covers 25 hosts with the recorded control/measurement limits; §6 is implemented and qualified; §7's Lab adapter is implemented with corrected managed qualification pending. The old two-slot controller's global serialization must not become the 128-worker request path.

Use the existing DynamoDB table for immutable job metadata, conditional leases and funded allocations; S3 for immutable sources, inputs and outputs; EC2/SSM for the existing native process execution. Add query indexes and a campaign scheduling owner, not Redis, a second queue ledger or another provider implementation. A best-effort asynchronous Lambda wake follows committed enqueue/completion changes; the scheduled reaper remains recovery fallback. Duplicate wakeups are harmless because conditional job/worker transitions, not notification delivery, authorize execution. Experiment dispatch is never an automatic message retry.

Keep one logical mutation owner with two paths in the same controller modules:

- **Point operations:** concurrently process exact worker/job heartbeats, start/report/capture/release calls under DynamoDB conditions. No global lock, pool scan, wait for boot, artifact loop or model execution on this path.
- **Scheduling:** a short fenced allocator lease selects eligible campaigns and available workers in bounded pages. Persist each allocation/operation before EC2/SSM. Release/yield without waiting for readiness. A late allocator must still satisfy per-row generations/conditions; the allocator lease alone cannot authorize a write or exceed capacity.

Refactor existing helpers along these owners; do not copy the current controller into a parallel controller. The paid-attempt owner in §6 stays outside cloneable/resettable Lab databases. This separation is development infrastructure, with no domain/world dependencies.

## 2. Current-format input and commands

Replace the current run schema once, updating all maintained callers/examples together; keep `pnpm verify:worker run PLAN.json`. One current schema has `jobs[]`, even for a single job. `concurrency` is mandatory; configured pool capacity defaults to two independently of that request. Do not retain an old-plan reader, aliases or a second executor. A job contains existing ordered `cases[]`; cases select source and ordered `steps[]` instead of a growing set of special seed/build/test fields.

```json
{
  "taskId": "assigned-task",
  "cloudAllocationId": "assigned-task",
  "deadlineSeconds": 1800,
  "lifetime": "durable",
  "concurrency": 1,
  "inputs": [{ "id": "seed", "root": "/absolute/fixture-root", "paths": ["spec.json"] }],
  "jobs": [
    {
      "id": "native-seeded-scene",
      "mode": "batch",
      "timeoutSeconds": 300,
      "cases": [
        {
          "id": "sample",
          "source": "EXACT_40_CHARACTER_COMMIT",
          "inputs": [{ "id": "fixture", "bundle": "seed" }],
          "databases": ["fixture"],
          "steps": [
            {
              "id": "seed",
              "database": "fixture",
              "argv": [
                "node",
                "--import",
                "tsx",
                "scripts/seed-fixture.ts",
                "{inputs}/fixture/spec.json"
              ]
            },
            {
              "id": "measure",
              "argv": [
                "node",
                "--import",
                "tsx",
                "scripts/profile-fixture.ts",

              ]
            }
          ],
          "requiredArtifacts": ["profile.json"]
        }
      ]
    }
  ]
}
```

This is the native schema specimen; the illustrative seed/profile entrypoints, exact source and existing fixture root must be supplied by the caller. Each real step names a reviewed entrypoint present in its source. Jobs may differ in every supported field; no cognition row IDs/model names belong in the generic runner. Source manifests, immutable input digests, public env, deadlines, output/disk allowances, acceptance kind and supported toolchain identities retain their current owners. `steps` is a finite sequential list, never a shell string or workflow expression.

| Level           | Required meaning                                                                                                                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Campaign        | `taskId`, `cloudAllocationId`, unique `jobs[]`; hard `deadlineSeconds` defaults to 3,600, `lifetime` defaults to `attached`, required `concurrency` declares the requested simultaneous job count. `durable` is explicit.                                                                         |
| Job             | Stable `id`, `mode` (`batch` or `browser-session`), explicit `timeoutSeconds` covering boot/preparation/work/cleanup, and ordered `cases[]`. A browser campaign claims the submitting physical device through the shared capture owner; no caller-supplied device identifier bypasses that claim. |
| Paid job (VW08) | Optional `paid` declares `limitMicroUsd`, `maxCalls` and permitted lane IDs from the configured shared service. Absence means native/zero paid spend. Admission derives the immutable child grant ID; callers cannot supply another job's grant/capability.                                       |
| Case            | Exact `source`, input bundle references, public `env`, database aliases, ordered `steps` and required relative artifact paths; job-level output/disk allowances and acceptance apply. Source/settings remain fixed through its steps.                                                             |
| Step            | Unique case-local `id`, literal executable `argv`; optional `database` selects a declared case alias through protected `PG*`/`DATABASE_URL` environment, without a shell or credential-bearing argv. System install/source/binding guards are outside this editable list.                         |

No field contains provider credentials, signed download URLs or grading answers. Validate cross-field totals and all composition limits before reservation/activation; supported individual fields do not make an oversized combined plan valid.

Expose `plan`, `run`, `status`, `cancel`, `collect`, `resume`, `recover` and `retire` through the same CLI. `plan` validates and returns sources/input deduplication, required changes, effective parallelism, resource needs and separate compute/provider/storage reservations without starting anything. `run` saves its capability privately and stages/activates one campaign. `resume` observes the existing campaign and resumes safe staging/collection; it never replays running, dispatched, completed or uncertain work. A new attempt requires an explicit new identity linked to its original and fresh spending admission. Existing single-run users become one-job manifests.

Trusted recipes may expose Node, pnpm, Python and PostgreSQL tools actually installed on the worker. Review each allowed executable family through the existing process/network boundary. Future languages require an explicit recipe update, not `bash -c`, an online installer supplied by a plan or arbitrary generated execution. Public env cannot replace database ownership, source, provider credentials, budget, accounting or lifetime controls.

Cut over only after existing claims and control commands are terminal; do not cancel another agent's work to deploy. Preserve financial records and required exports, then reinitialize disposable coordination/private-run state for the new schema or retire old hosts safely. Update validator, controller, supervisor, CLI and all maintained examples/callers together. Old experiment evidence remains historical data; no old-plan adapter, save conversion or mixed-protocol execution is required.

## 3. Isolation, inputs and seed ownership

One job owns one host from preparation through clean export. Each case gets fresh source/home/results and fresh requested database aliases; ordered steps within that case share those databases. Inject job-owned connection handles through protected environment/file bindings, never credential-bearing argv. Centralize creation/drop in the existing disposable PostgreSQL owner with a job/attempt namespace and alias lookup. Allow seeding one or several databases without giving a seed script another job's or a financial database's administrative URL.

Stage each distinct source archive once per campaign/source hash and each distinct input bundle once per content hash. Reuse the existing archive descriptor (bytes, archive/file hashes and relative paths); a bundle reference must resolve to an explicitly admitted campaign input, never an arbitrary bucket key. Keep shared private input blobs outside broadly readable source prefixes. The controller copies only the declared immutable bundles into the assigned worker/run prefix before launch. Existing per-slot IAM then grants their reads without a URL signer or broad private-input bucket access. Original archives upload once; server-side copy is bounded to four bundles per control operation. Permanent manifests contain content hashes and unsigned references. Root-owned private blob caches are not readable by unrelated jobs. The same cache owner verifies archives on reuse and bounds retained blobs to 4 GiB/256 entries, pruning outside measurement; permissions are checked against the current job before consulting it.

Worker downloads stream into bounded local files and verify both bytes and manifest. Inputs mount/extract read-only; writable fixtures live in the owned case directory/database. Reject path escapes, links and missing hashes before executing. Cache package content and verified immutable blobs, never mutable worlds, current Lab selections or workspace links. Prune only idle/claimed preparation outside capture and retain required sole copies.

Use current Lab/save export/import owners to produce portable origins. Do not copy a live database, local login cookie, provider credential, old financial journal, `.data` directory or historical saved-ID reference as a fixture. Import yields a local saved-ID mapping while retaining original artifact/source hashes. Scenario/world rules and native authoring remain in their existing engine/world owners; the runner knows only input references and database aliases. Seed-only jobs must publish their requested export before cleanup; downstream use is another explicitly staged campaign.

A data-only PostgreSQL fixture may use SQL. A game/Lab world seed uses its authored initializer, normal mutation/import owners and current-format validators; a generic seed step does not authorize bypassing them.

Install dependencies and run binding/source guards through existing owners before declared steps. Preserve selected instrumentation, startup, game warm-up, exact requested measurement, drain and cleanup boundaries. No test/capture can silently change clock speed, episode wall/call bounds or native mechanics to improve throughput. Browser jobs retain the existing real-browser path and attached ownership, claiming the submitting physical device exclusively through the same owner as direct browser-profiler calls. A busy device refuses before cloud admission; uncertain browser closure retains the claim for explicit verified recovery. One browser job per device is supported; no device fleet is introduced. Cognition episodes use their existing native/HTTP caller without opening a browser per row. A hundred CPU workers are not a hundred representative graphics devices.

## 4. Persistent queue and scheduling

Do not put all jobs in a DynamoDB campaign item. Store the immutable manifest in S3 and these compact rows:

| Row         | Authority and lookup                                                                                                                                                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Campaign    | Assigned task/origin, manifest fingerprint, capability hash, deadline/lifetime, cloud/provider escrow references, requested parallelism, activation state and derived counts.                                                                   |
| Job/attempt | Campaign and declared job ID, immutable spec/hash, input/source refs, cost grant, pending/running/terminal state, worker/generation/operation identities, deadline, artifacts and outcome. Explicit fresh attempts have distinct IDs and links. |
| Worker      | Existing slot/instance/environment, generation, lease/job/case, pending cloud intent, retention class and due time. Allocating, stopping, retiring and quarantined slots count as occupied.                                                     |

Use structured tuple digests for composite identities and retain the admitted request fingerprint through storage; decoded object key order is not an original request. Public status exposes no capability. Terminal cancellation/heartbeat requests observe the original terminal state; pending cancellation is projected from the parent as not-started without rewriting every queued row. Exact row IDs remain authoritative; indexes are derived candidate selectors.

Cloud campaign states are `staging → running → completed`, with terminal `cancelled` where appropriate; interrupted or failed jobs remain explicit in its roster; a completed campaign can contain failed jobs. Physical jobs progress `staging → starting → preparing/dispatching → running → releasing → finished` (browser export may await the client), with terminal outcomes `completed`, `failed`, `interrupted`, `not-started` or `uncertain`. Setup/measurement/cleanup/acceptance dispositions remain separate fields. Preserve the original cloud-operation or paid-attempt identity across uncertain transitions; a new delivery cannot reset a terminal job to pending.

Use one sparse `group-order` index for active campaign ordering, image work and due workers. Maintain worker due keys at the shared mutation boundary. Confirmed stopped caches have no idle polling before storage expiry. Job pages derive exact tuple-digested `(campaign, ordinal)` keys in groups of 25; no job-history index is needed. Read the bounded 128-slot registry only for capacity preflight/admission, prefer existing prepared hosts, and create empty-slot metadata without creating instances. Timers select at most 25 due workers per slice; strongly read and fence selected rows. Do not scan completed runs, enumerate all slots for each request, or decode all job manifests for one heartbeat. Page campaign jobs/results; update display counts only with an exactly-once terminal transition, and permit reconstruction from job rows.

Admission reserves the native campaign's conservative physical occupancy, outputs, recovery and incremental selected-host storage once. Compute is bounded by the smaller of concurrent campaign occupancy and summed job timeouts, with idle/stop headroom; parent settlement never duplicates child estimates. Declared provider commitments follow §6. Publish job rows in bounded transactions (at most 20 jobs, within DynamoDB item/transaction byte limits), tracking staging progress by the manifest fingerprint. Workers cannot claim a partially published campaign. Activation requires the exact expected job count/hashes and valid reservations. Failed staging is resumable; never double-reserve on duplicate submission. Retain conservative complete-campaign charges at terminal settlement rather than refund estimates based on partial observation; uncertainties retain funding. The reported amounts are charged estimates, not AWS invoices.

Before staging, reserve the complete requested `concurrency` as one admission boundary. Insufficient quota, funding or available pool capacity blocks the campaign before any job starts; never reduce it silently. Recovery visits active campaigns in admission order; each campaign assigns its oldest pending jobs automatically. This is best-effort admission between campaigns, not a strict FIFO guarantee. One short pool transaction reserves the entire requested slot set before staging; unrelated jobs do not contend on that pool row for heartbeats, reports or receipts. Callers declare jobs, never job-to-instance mappings. The initial wave assigns distinct reserved slots and acquires all requested physical instances before any experiment dispatch. A definite creation rejection cancels that wave rather than running less concurrency. Thereafter each freed worker immediately takes the next pending job, without waiting for the slowest initial job. A claim checks the active campaign, reserved worker and assigned immutable job under campaign/worker locks with transaction fencing. The dispatch intent transaction additionally checks parent capacity readiness, cancellation, deadline and attached lease. No running job is preempted merely because another campaign arrived; surplus capacity becomes available to other campaigns immediately after this campaign has no pending jobs. Record skipped jobs blocked on provider capacity rather than filling hosts with waiting processes. Prepared workers are preferred, then already-owned idle capacity, then funded burst creation. EC2 creation tokens bind the exact slot/generation; unknown delivery retains ownership. SSM launch remains fenced/idempotent at the supervisor, with exact command reconciliation after an uncertain send.

Wake scheduling after successful enqueue/release/capacity changes; timers serve only due work and outage recovery. Bound one scheduling invocation to eight assignments and a 15-second start-work window, with explicit settlement headroom. No lease spans a boot wait, package install, model call or artifact transfer. Controller callbacks use point keys and can run concurrently; initially configure 16 Lambda executions, qualifying actual heartbeat/service latency before claiming fleet capacity.

## 5. Fleet, preparation and lifecycle

Configured capacity defaults to two and supports 1–128 slots. Keep deterministic per-slot IAM role/profile policies scoped to that worker's lease/artifact prefixes; do not replace them with whole-table or whole-bucket permission. Generate only the configured capacity, not 128 roles for every installation. This deliberately uses the existing security model rather than introducing a credential-vending service. Raising capacity requires an infrastructure update and preflight; it does not itself start instances.

Upload larger CloudFormation templates privately to S3 and pass the template reference. Derive deterministic scoped role/profile names from pool and slot instead of emitting a profile map: controller configuration stays fixed-size in the CloudFormation-owned environment, avoiding another configuration store/read. Generated templates must remain below CloudFormation resource/byte limits, IAM inline-policy size and Lambda environment limits; local measurements are recorded with qualification, never treated as deployed IAM/quota acceptance. Verify the generated resource count/template bytes and applied IAM, EC2 vCPU, subnet IP, EBS, Lambda and SSM quotas before activation. For example, 100 four-vCPU workers require **400 available vCPUs**, excluding any other project resources. No quota increase or cross-Region workaround is automatic. AWS [EC2 quotas](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-resource-limits.html), [template limits](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-limits.html) and [Lambda environment limits](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html) are current preflight references, not assumed project capacity.

Maintain two reusable warm-cache slots by default; additional slots are temporary burst capacity. Burst instances terminate after verified cleanup and durable export, while required S3 results remain protected until collection. Warm instances stop after the existing idle interval. Failed upload/cleanup quarantines and stops compute, retaining the sole disk copy for funded recovery. Burst storage is reserved for the declared run plus a default 24-hour recovery allowance, rather than automatically funding seven-day warm retention for every host. Never delete sole required evidence or financial records to fit budget; unresolved retention remains visible and funded.

The maintained `image prepare TASK CLOUD_ALLOCATION EXACT_SOURCE_COMMIT` operation uses the existing bootstrap recipe on a fresh empty registered slot, never a cached experiment host. Its $2 conservative cloud reservation includes preparation and seven-day image retention; failed preparation stops compute, exports console evidence and retains its disk for one day before retirement. Images expire through the existing reaper; they do not silently become the selected pool image. Explicit deployment selects an available image. A recipe-specific tools stamp skips OS/tool downloads on restored clean images while first boot regenerates slot configuration. Record image/recipe, OS/architecture, Node/pnpm, PostgreSQL/extensions and lockfile seed-store identity. Before image capture, remove job state, private inputs/blob caches, instance/slot configuration, credentials, SSM/cloud-init/machine/SSH identity and transient launch markers. Seed only pinned package content with install scripts disabled; require an exact sanitization receipt and confirmed stopped state before capture. First boot binds the actual slot and starts with admission closed until reconciliation. Images contain tools/package content only. Pin and fund image/snapshot retention; do not build an automated image factory or use a dirty post-experiment machine as an image. Retain ordinary bootstrap as the bounded cold path, not another runner.

In durable lifetime, cloud admission owns the immutable roster until deadline; laptop loss does not cancel it. Supervisor heartbeats prove worker liveness, not permission to extend the campaign. In attached lifetime, the submitter's existing lease remains required; a supervisor's job capability cannot renew that operator lease. Keep distinct campaign/operator and job/supervisor capabilities. Both modes keep job/case generations, independent host deadlines, cancellation before further dispatch, scoped cleanup, uncertain-command quarantine and actual power-state reconciliation. A lost lease never grants a successor immediate ownership. Paid uncertainty prevents automatic fresh execution.

## 6. Shared paid-execution boundary

VW08 implements the [current shared-execution contract](../technical/verification-workers.md#shared-paid-execution). The same extracted `AttemptRepository` performs reservation and receipt settlement for game execution and the dedicated service; its persistent PostgreSQL database sits outside all resettable Lab/worker namespaces. Task/campaign escrow reserves nonoverlapping job grants, while original provider attempts remain the only paid journal. The parent cloud allocation includes these same grants once; it does not add another copy of attempt charges. Captured source/input publication and private grants precede experiment dispatch.

Each grant binds task, campaign, job, admitted cases/source hashes, service/model lanes, amount, call count and the original assigned run/deadline. The worker receives a narrow capability rather than provider/control credentials. The service exposes funding/admission to its privileged operator and execution, original-receipt observation, cancellation and closure to the exact permitted scope. Native jobs retain `AI_BUDGET_USD=0`; paid consumers explicitly load the supervisor-owned capability and use the existing typed client interface. No direct-key fallback exists.

Per-stage spending reads use exact indexed job-budget bindings; they never sum every campaign attempt in each worker. Request identity hashes the grant, case and native request ID before admission. Matching duplicates observe the original work; changed content refuses. Results retain both native and service attempt identities, case/source bindings, actual provider receipts and uncertainty. Resetting/importing a world, losing a submitter or restarting the service cannot refill money or resubmit an original attempt. Cancellation is durable per attempt, including before admission, and uses the same bounded call record rather than another queue/store. It consumes one call slot before dispatch without reserving money. Dispatch, atomic result settlement and post-wait receipt delivery share the current permission fence; cancellation acknowledgement performs no provider I/O. Repeated unchanged closure preserves existing rows and task balances. Once hardware is confirmed quiescent, financial-only monitoring ends at the original campaign deadline plus the existing cleanup allowance; unresolved obligations remain held outside the active index. Authenticated `resume` reconciles the original financial record and has a fresh bounded collection window, without renewing experiment/model deadlines.

Provider admission bounds service-wide and per-lane active requests plus rolling-minute admissions; campaign preflight checks configured lane capacity. Queue/refusal/timeouts are reported separately from reasoning quality and never enlarge the episode’s original bounds. The typed service currently admits judgment, structured generation and embeddings. Native world-tool harness execution retains its existing game/permission owner and is refused by this model-only interface. A separately hosted available service is required for paid campaigns to survive loss of the submitting machine; no permanent host fleet is provisioned implicitly.

Unknown provider execution/pricing retains its original obligation. Confirmed local process/SSM cleanup can release EC2 independently; uncertainty does not require paying for an otherwise clean host. Exact supported receipt observation may reconcile original costs without inference. If service configuration, credentials, grant enforcement, financial state or capacity is unavailable, affected paid jobs remain blocked/refused with their original records; no fabricated paid pass, historical allowance or automatic retry substitutes for this boundary. VW08 qualification is recorded in the [paid-execution evidence](../verification/performance/2026-10/verification-paid-execution.md).

It adds no scheduler or provider pipeline. [VW09](../maintainers/verification-workers.md#delivery-order) remains open until the adapter's [native and funded managed-Lab qualification](../verification/performance/2026-11/verification-lab-adapter.md) is complete.

An explicit declaration selects the complete matrix, exact per-row execution records, immutable current-format origin exports and actor mappings, canonical authored profiles, model revisions/settings, seed/replicate, original call/simulation/wall limits and funded lanes. The planner verifies selected source contains the maintained executor/runtime and exact input hashes, then freezes one stable ID per `(scope, condition, model, replicate)`. Execute mode keeps each mutable episode's native action/conversation steps serial, establishes required arrival/work/injury before dependent stimuli and captures primary results before declared zero-inference postludes. Action bindings come from authored world data. Setup, missing-opportunity, provider and observation failures remain distinct outcomes.

Paid judgment, structured generation and normal embeddings use the shared typed execution/accounting owner in §6. Server availability reads granted capabilities; worker credentials contain no provider keys. Paid plans supply the native Lab allowance and explicit public model-price settings, including auxiliary summaries; derived cache-rate and default judgment estimates remain labeled in provenance rather than treated as provider quotations. Native request IDs, service attempts, receipts and uncertain obligations remain outside resettable worlds. Recovery observes the existing episode and original attempts, never starts replacement inference. This typed facade does **not** run the full deliberation/world-tool or reflection harness; provenance records those unsupported paths, and model-only qualification cannot establish them.

Aggregation consumes the managed collector's verified artifacts, verifies worker-run/source/spec/origin/seed/order identities and emits complete CSV/JSON with raw result references. Failed, blocked, unobserved and uncertain positions remain in the denominator; mismatched evidence is retained with an error. Collection can resume against the same campaign without replay. Episode receipt costs and the authoritative shared-grant closure budget are overlapping snapshots, never additive; the closure can include work settled after episode capture or when episode output is missing. Closure coverage, held uncertainty and unknown totals remain explicit. Report worker preparation/queue/collection/cleanup, episode work and provider intervals separately, with provider-reported costs distinct from estimates and missing receipts. Generic fleet qualification and plan-only coverage do not establish Lab/model throughput or character quality.

### 7.1 Ordinary-runtime comparison

**Implemented under CL13/CTR08; [bounded qualification and remaining observer/behavior limits](../verification/cognition-context/2026/2026-11-05-readiness-and-admission.md) are recorded.** The [isolated adoption gates](combat-and-threat-responses-tech-design.md#isolated-before-and-after-adoption-gates) require unchanged-Lab before/after and ordinary-runtime observer-overhead comparisons before this runner supplies timing evidence. An explicit `runtimeTarget: 'lab' | 'game'` is carried through the current episode declaration, planner, validator, runner and provenance/aggregation. Use distinct existing scope/condition identities for the two targets; recovery must reject a mismatched target rather than reuse a Lab result as game evidence. The game target runs the existing `createWorldRuntime`/host with no `labControl`, normal native clock progression and ordinary participant/control/funding rules. Prepare its declared current-format starting state through existing native setup/save owners before enabling cognition/time, then use actual player intentions, source-bound observation and normal effect admission. Keep the same world rules, identities, seed, model, native stimuli and ordinary participant/autonomy setup; the intentional difference is the Lab's processing holds. Use a declared isolated origin with the selected autonomous participants through normal authoring/control, rather than relying on a Lab-only actor whitelist to suppress otherwise eligible people. Retain and account for any incidental nonfocal calls; different actor populations or eligibility policies invalidate a claimed clock-only comparison. During the measured interval, a passive observer must not call `holdBoundary`, pause the game for export, or wait for model completion before allowing native time to advance. At the declared end or guard, stop only the owned runtime through normal cleanup and label any interrupted work; terminal collection is outside the measured gameplay interval.

Reuse `campaign.ts`, `contracts.ts`, `episode.ts` and their shared native-step/observation and accounting owners. Common preparation/export stays shared; only runtime/control entrypoints differ. No new product mode, provider client, credential path, database authority or retry/recovery system is selected. Persist that target with the current episode contract, update its planner/validator/aggregation and callers together, and leave ordinary Lab behavior unchanged. Do not add legacy readers. Each game case still has its own runtime/database/output and shared spending ledger. Qualify zero-model setup, genuine actor participation, native time advancing across a held provider response, cancellation and failure-time participant export before the four live game positions in the [focused delivery panel](combat-and-threat-responses-tech-design.md#focused-experiments-after-readiness). Label a fake/delayed provider as a clock-mechanics check, not live responsiveness. Missing game-path support is a delivery blocker, not permission to report a Lab run as ordinary gameplay.

Both targets use the same paged field reader, declared prelude defaults and native arrival proof; an arrival-only step needs no focal model reply. Keep attempted phases and their acquired source evidence on failure. Start cleanup ownership as soon as the replacement runtime exists, and retain its actual live/fixture execution provenance. Separate measured work from primary snapshot I/O, original provider settlement, postlude and export collection. Finite Lab advancement must respect processing/capture holds before admitting cognition, as automatic advancement already does.

## 8. Bounds, measurement and implementation

| Initial setting             | Target/rationale                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Default configured capacity | Two; explicit configured ceiling through 128, counting all occupied/quarantined slots. No host sharing for performance comparisons.                                                                                                                                                                                                                                              |
| Campaign parallelism        | Required explicitly by every caller, never above configured funded capacity; no implicit default or silent reduction.                                                                                                                                                                                                                                                            |
| Manifest                    | Up to 4,096 jobs and 16 MiB encoded metadata; at most 64 KiB per job. Large fixtures/prompts are admitted bundles, not metadata. Reject the complete oversized composition before effects.                                                                                                                                                                                       |
| Per job                     | Up to 16 ordered cases, 32 steps per case; current output/disk guards and pinned toolchain. All current callers use this one schema.                                                                                                                                                                                                                                             |
| Control                     | 25-item job/due-worker pages, 20-item staging transactions, eight assignments per scheduling slice, 16 concurrent point handlers initially; preserved lease/deadline checks and settlement headroom.                                                                                                                                                                             |
| Campaign/job time           | Campaign hard deadline defaults to one hour, at most the existing eight-hour bound. Each explicit job timeout must be below the campaign window and starts on assignment; launch only if it fits the remaining campaign allowance. Otherwise retain `not-started/campaign_deadline`, without shrinking measurement bounds. Queue wait burns no claimed-host execution allowance. |
| Recovery storage            | Warm retention remains current policy; burst run/storage plus 24-hour recovery funded separately. Required sole copies cannot expire because an allowance ended.                                                                                                                                                                                                                 |
| Failure                     | Continue unrelated jobs by default; pause affected service on accounting/source/infrastructure integrity failures.
