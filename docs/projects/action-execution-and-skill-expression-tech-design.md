## Behavior-to-implementation contract

Deliver the [ND38 player feature](action-execution-and-skill-expression-feature-spec.md) through **ordinary admitted actions**, not a second minigame result engine. A human chooses a permitted action; its physical preparation remains native; an optional input exercise yields bounded **action-specific execution evidence**; one trusted family derives any permissible effect; the actual world owner commits the effect, receipt and disclosure. A resident chooses through its ordinary controller and executes through the same physical owner using character competence, not simulated cursor input.

The connected demonstration is ordinary versus animated timed ranged/melee attacks while walking, observing and choosing targets or points. Ordinary crafting remains unchanged. Include no second combat solver, item-quality store, universal stats or per-frame model call.

[Existing engine/world boundary](../engine-and-world-boundaries.md#5-a-repeatable-boundary-decision) remains controlling: stable identities, authorization, resource accounting, ordered native effects, safe observation, restoration and data-driven admitted definitions are reusable; the selected game's weapons, skills, injury/evasion law, ring tuning and names are **replaceable world policy**. Other coherent worlds can omit any mechanism. A supported family may be compiled native code without becoming universally installed.

### Engine-owned versus world-owned computations

**Engine and reusable native services:** exact action/resource/receipt ownership, bounded normalized input assessment, immutable admitted meaning, current-format continuation, observer-scoped projection. The assessor returns a finite assessment; the action's trusted native family interprets its contribution and commits through the existing physical owner.

**Server control policy:** input epochs, ordering, renewal, expiry and revocation belong to the existing WorldService control/presence and clock owners. The live input scope advertises their current operational values. Installed fictional definitions cannot extend that authority. A policy change invalidates/reissues input scope; it does not reinterpret a weapon, recipe or completed item.

**Client input and settings:** keybindings, tap/hold classification, animated timing, reduced-motion preference and focus routing belong to the shared device controls in §6. They govern how a player submits an admitted choice, not the world's mechanical definitions or proof that a human supplied it.

**World-owned authored decisions:** which installed action permits timed release; visible ring bands and period; supported competence/condition contributions; weapon work/recovery, projectile/strike and avoidance laws; contribution bounds and their labels. An invented item, label or arbitrary world data cannot register a property-mutating callback, executable formula, raw stat path or security grant.

## 1. Player input and shared attempt lifecycle

### 1.1 One native preparation, one release, exact recovery

**Implemented mechanism; evidence and remaining independent player acceptance are tracked in ASE.** The client owns only `idle → candidate-tap → manual-hold → submitted/cancelled` presentation. `ActorComponent.action` remains the sole primary physical work owner. A pointer gesture, movement lease or local ring is not another Action, physical plan, resource reservation or position writer.

In attack mode, valid primary pointer-down immediately requests **one beginning of the exact chosen native attack**, capturing the displayed action/definition, tool, ammunition choice, initial permitted intended subject or point, and current input scope. Native preparation, reservation, windup, interruption and later recovery remain with the existing ranged/strike owner. A hold changes how that same preparation will be released; it never starts a second attack. Unavailable sources remain visibly unavailable, with no silent substitution of another weapon, ammunition lot, Speak, Move or target-bound method. A melee hold introduces a release-ready state in the existing strike progression: reaching the windup deadline while still holding does not automatically impact. Ordinary explicit menu/NPC strike routes retain their own native approach and one-shot progression.

A valid absent optional descriptor retains the ordinary route. For the first bundled **knife and Punch**, which have no held-execution profile, pointer-down captures only the exact ordinary choice; pointer-up invokes that one ordinary native action after any required review. Holding does not start a timed/held-ready strike, and cleanup never invokes it. These actions keep their existing native work and menu/NPC behavior; a long hold neither repeats nor grants a bonus. The explicit ordinary Attack button remains available. An invalid present descriptor is a refusal, not this absence path. A ranged weapon without the optional descriptor uses the existing one-shot native action, including its normal preparation, automatic release, ammunition debit and recovery, rather than entering an indefinite manual aim. Its installed ranged policy selects exact physical point fire or the permitted observed-subject route; the client never claims point-fire support from a weapon label.

**A Begin that requires lethal review admits no preparation before confirmation.** The existing review owner first prepares the exact proposed attack read-only; it creates no action, ammunition reservation, equipment change, cost, recovery or random outcome. Receiving that review finishes the old pointer gesture and discards any queued pointer-up release, held keys and ring phase. Present the world-authored confirmation as **Prepare attack**. Explicit confirmation admits only the reviewed native preparation under current authority and returns its action ID/profile; it never interprets the old button-up as Release. The admitted confirmation starts a fresh local hold-toggle session when its profile is displayed, with a new phase origin and the selected presentation, rather than inheriting old pointer elapsed time. Continue through the visible Release/Attack normally/Cancel controls or a fresh eligible deliberate input. Confirmation cannot resume held WASD, start an animation from an abandoned clock or fire automatically because windup is already ready.

Classify a pointer-up by monotonic elapsed time from its down event. A release below the [client hold threshold](#61-one-owner-visible-state-and-selected-bindings) is ordinary score zero. Crossing that threshold allows the optional ring only after the exact admitted input profile has actually arrived. Start its phase origin once at the later of those two boundaries. Before admission, show local pending feedback without a usable green promise. A release before the admitted profile was displayed is ordinary, even when network delay exceeded the threshold; it is never scored against an unseen phase. After display, use one fixed admitted profile for the attempt. Rendering stalls cannot turn a long hold into a tap merely because a timeout callback ran late.

The ring uses monotonic **real elapsed time**, independent of date changes, graphics frames, world simulation speed, server publication and provider jobs. Phase is computed from the admitted period; frame updates draw locally. Send no recurring pointer/phase samples or paid-model work. The real-time input lease below renews control availability, not a score. Native movement, windup, recovery, resources and impacts use the selected world's simulation clock. Waiting for release does not pause the world.

Pointer-up captures **one immutable release intention**: final subject-or-point choice, ordinary/timed input and displayed phase. If begin has not returned an action ID, retain that intention locally only while the same live gesture remains authorized. If native preparation is not ready, the admitted action retains one pending release record; its receipt says **release requested**, not **released**. The native ready boundary can consume it once while its current foreground input authorization remains valid. Do not recalculate timing, replace the selected physical life, update an exact point from a later target, spend ammunition at request acceptance, queue another attack or fire repeatedly during a long hold. Subject aim resolves its current permitted body anchor and observed-motion lead at native release.

At actual release, validate current actor/tool/method, relevant installed pins, readiness, body recovery, actual geometry, retained intended subject and release-review dependencies. Use the then-current native launch anchor and the retained subject-or-point choice under §3.1. A genuine accepted melee reach miss consumes native recovery under the strike owner; a refusal before an attempt commits does not. Ranged post-release handling uses the selected new native body recovery deadline described in §3; ring period never substitutes for weapon recovery.

Cancellation names only this gesture and its unfinished admitted action. Mode Off, deliberate self-region entry, Escape/Cancel, pointer cancellation, lost capture, tab blur, unrelated modal entry, pause, connection/control/life loss or rejected capability clear local held input and disarm future automatic release; cleanup never sends Release. Cancel before begin acknowledgement establishes a terminal marker for that exact begin, so a late begin cannot prepare an unwanted action. **The sole modal exception is this attempt's own exact lethal-review dialog:** it preserves only the existing review's frozen uncommitted choice and, for release review, its already admitted native preparation. It suspends movement and automatic release, not the world, and grants no continuing pointer/keyboard authority. User Decline, Escape or close drops that review and cancels only its matching unfinished preparation; closing never submits the choice. The same bounded review retains its exact confirmed native action through its existing expiry, including ordinary attacks without an execution profile, so a late Decline can resolve a Confirm race without touching replacement work. Actual accepted strike/shot events mark release; no historical scan or second review store is needed. An already released projectile/committed strike remains real. If release won at the server before cancellation arrived, report the actual released result rather than claiming cancellation.

Native preparation can remain inspectable only where ordinary participation/interruption permits it. Reconnect, reload or Resume restores explicit native **Release/Cancel**, never held keys, a local phase or an armed automatic release. A saved pending-release record retains its exact evidence as needed for the receipt/history owner but restores **unarmed**. Deliberate recovered Release uses the current visible subject-or-point choice and a fresh neutral release request against the exact surviving action, after resolving any uncertain original release receipt.

### 1.2 Finite request, receipt and input-order contract

Keep the existing authenticated `/api/command` envelope, `commandId`, `commandEpoch`, `X-OL-Client`/`X-OL-Scope`, `WorldService.command`, command binding, native transition and durable `commandReceipt` recovery. Extend the current protocol declarations, `apps/server/src/command-input-schema.ts`, `WorldService.bindCommand`, catalogue descriptors, `command-request.ts` and `ui/aim-controls.tsx` together. Do not introduce a second attack executor or persisted gesture database. `ApiResult.actionId` is already the native action identity; it is distinct from the request's command ID and catalogue option ID.

The following are the finite wire fields for this integration. Use existing validated reference/pin types when implementing them; never expose raw actor life or accept an actor ID as authority.

```ts
type AttackInputIdentity = {
  inputEpoch: string; // common current controller/world/life scope
  attackInputToken: string; // current server-issued attack-lane incarnation
  gestureSequence: number; // positive safe integer, increasing in this incarnation
};
type AttackGestureIdentity = AttackInputIdentity & {
  beginCommandId: string; // original /api/command identity, never regenerated on retry
};
type AttackReleaseInput = { kind: 'ordinary' } | { kind: 'timed-release'; phase: number };
type AttackExecutionControl =
  | ({ operation: 'begin' } & AttackInputIdentity)
  | ({ operation: 'release'; input: AttackReleaseInput } & AttackGestureIdentity)
  | ({ operation: 'confirm-review' } & AttackInputIdentity)
  | ({ operation: 'cancel' } & AttackGestureIdentity);
```

The existing top-level `lethalReviewId` identifies the one actor-scoped review. The command repeats its required native attack fields unchanged; `confirm-review` supplies fresh operational authority and no new release sample. The server obtains the frozen input/profile and original execution stage from this exact review record, requires every repeated target/point/source/action field to match, and reconstructs the reviewed semantic choice for validation. Unknown or conflicting gameplay fields refuse; omission of a new sample cannot choose ordinary or rescore the old one. The existing review binds whether it is **begin preparation** or **release existing preparation**, its original begin command identity, and any exact native action reference. A confirmation cannot choose its own stage or another action. A fresh gesture sequence, strictly greater within the current attack-token incarnation, identifies this deliberate continuation; the server binds the original begin identity and returned/current native action to that sequence. Its outer command ID is a new explicit confirmation request, retained unchanged for retries. A confirmed initial Begin creates one preparation only. A confirmed release can commit once if ready or arm one pending release under the new current lease. Ordinary release/cancel identity checks are not weakened for commands without this exact current review.

`execution` is accepted only on the supported native attack begin/release/scoped-cancel command forms. It cannot register a new action or arbitrary effect. The current `aim` and `strike` bindings gain deliberate held preparation when `execution.operation` is `begin`; absent that payload, their existing ordinary routes keep their meaning. `release-shot` continues to name its native aim through `aimId`. Add the finite native `release-strike` variant with `expectedActionId` for the held-melee ready state; it uses the existing strike impact owner, not the ranged executor. Update native types/binders/support classification alongside that state. The native command names its action exactly once: `release-shot.aimId`, `release-strike.expectedActionId`, or `cancel.expectedActionId` when known. The existing binder resolves that reference and checks it against the gesture binding; the optional execution payload carries no second action-ID spelling. Before acknowledgement, a scoped Cancel can omit the native action reference and identify only its original begin/gesture. Confirmation obtains the action reference from the exact reviewed native form. This keeps invalid combinations out of the supported request shape rather than making every consumer reconcile duplicate identities.

At most **one bounded current attack-gesture slot** belongs to a live controller. It stores the highest accepted gesture sequence, original begin command identity, bound action ID and phase: `open`, `release-requested`, `cancelled`, `released` or `ended`. It coordinates input only; action state, ammunition and effects stay native. A matching cancellation is terminal even if it arrives before begin or confirmation. Lower sequences cannot revive work; a higher deliberate begin cannot silently replace an unresolved gesture or unrelated work. A reviewed continuation can attach a fresh sequence to the same exact native preparation only through its existing review record. Native release marks the slot `released`; refusal, cancellation or other terminal work marks it `ended`/`cancelled` with the actual cause. Retain the sequence watermark while permitting the next deliberate gesture; a finished action cannot leave an unresolved slot blocking subsequent input. Duplicate command lookup precedes fresh eligibility checks; conflicting content under one command ID refuses. Late HTTP results update neither abandoned gestures nor another actor's UI.

The existing `commandEpoch` is a retained retry epoch, not a transient restart fence. Publish an opaque common `inputEpoch` from the existing server generation and current world/timeline/control/life authority. Pause/suspension, load/restart, handoff, detected control loss and shared input-policy invalidation reissue that scope and revoke its operational inputs. Under it, the same control owner advertises exactly two server-issued incarnation tokens: `movementInputToken` and `attackInputToken`. Each fences fresh authority-granting packets for its existing input lane, including a previously unseen higher sequence. Issuing a token does not start a lease: only active steering or an armed automatic pending release receives the renewable time window. A held native preparation alone has no new total-hold timeout. Expiry retires that lane's window and rotates only its token; a still-live independent lane keeps its meaning and authority. Native interruption, replacement or loss of an uncommitted pending release likewise retires the exact attack token once, allowing the existing scope acknowledgement to clear an obsolete local gesture even if its Begin reply was delayed. A committed release event remains terminal and cannot be inferred away from later action absence. This is fixed control state, not a registry, historical token-alias table or saved permission. Durable receipts retain their separate recovery scope, and no token attests human timing or mouse input.

The projected `WorldInputScope.revision` orders scope acknowledgements monotonically within one server generation. A late acknowledgement cannot replace a newer common epoch or lane token. The client first fences the existing server-generation portion of `historyEpoch`; a restart may reset this revision. The revision orders control descriptions only: it grants neither input authority nor elapsed time.

### 1.3 Movement alongside preparation and the live input lease

WASD captures the camera basis when an eligible movement-key combination changes and transforms its normalized ground-plane direction once to finite world `(x,z)` intent. Hold that world direction until the next eligible key change; camera orbit, rendering and unchanged renewals do not bend the route. It carries no client position, speed, distance travelled or elapsed simulation time. The existing body/support movement owner consumes finite steering segments while idle or while the selected ranged/melee preparation or committed weapon recovery explicitly permits steering. Movement remains available after release; a recovering strike still owns its same Action/deadline while the shared movement owner consumes steering. Recovery blocks incompatible new combat work, not ordinary legal retreat. It uses the existing `moveAlongPath`/`setSpatialPosition` and support-walk transition owners; collision, floors and elevation remain native. `ActorComponent.action` is still the sole physical work slot. Guard, craft, another weapon preparation and unrelated manual work remain incompatible. An ordinary move/evade/menu action uses ordinary replacement admission. Unsupported bodies/tools expose refusal, not generic parallel work.

Use a narrow authenticated input-control update within the existing WorldService control/presence owner, not a durable gameplay Action or receipt for each heartbeat. Direction changes/stop and renewal are separate finite messages; all are scoped by current `inputEpoch` and controller authority:

```ts
type WorldInputUpdate =
  | {
      kind: 'steer';
      inputEpoch: string;
      movementInputToken: string;
      movementSequence: number;
      direction: { x: number; z: number };
    }
  | {
      kind: 'renew';
      inputEpoch: string;
      renewalSequence: number;
      movement?: { movementInputToken: string; movementSequence: number };
      pendingRelease?: {
        attackInputToken: string;
        gestureSequence: number;
        beginCommandId: string;
        actionId: string;
      };
    };
```

Movement, gesture and renewal sequences are positive safe integers. Movement/gesture watermarks belong to their respective current lane tokens. The client increments one `renewalSequence` within the common input epoch; the server keeps a separate accepted renewal watermark for each current lane, so a later movement-only renewal cannot suppress an earlier valid release-only renewal. A strictly higher movement sequence can change steering; a strictly higher renewal sequence for a named lane can extend its expiry. Direction is a finite normalized vector or exact zero for Stop. A renewal must name at least one lane and exactly its accepted nonzero movement or still-armed pending release; it cannot create a window or revive stopped/expired work. After common authentication/schema checks, validate each named token, sequence and current intent independently. A stale movement claim cannot renew movement or prevent a valid release claim from renewing. Acknowledgements report current scope/tokens and per-lane acceptance, not fabricated gameplay receipts.

Process due monotonic expiry at every input/command receipt and coherent continuation, before validating a fresh claimed token or accepting another sequence; do not wait for a timer callback to rotate the token. Account elapsed time under the previous coverage clipped at its actual deadline. Refuse an old token before it can affect current watermarks, even when its packet has a higher sequence. Receipt lookup for an exact already-recorded command still precedes new execution eligibility; an old token neither hides a committed result nor grants a new effect. Reset only the counters owned by a replaced scope/token. Explicit withdrawal/cancellation retains its existing exact native authority and pause exception.

When a token is replaced, the client clears only that lane's local held/armed input and uses the advertised replacement only for a fresh deliberate input. It never retries an old steer, held key, frozen release or rejected packet under the replacement token automatically. Common lifecycle revocation clears both lanes. Thus an expired steering token rejects a delayed higher-sequence direction while an independently renewed pending release remains valid; its converse also holds.

The existing **server control/presence owner** supplies the initial **100-real-ms renewal target** and **250-real-ms lost-input expiry**, advertised with the current input scope. Renew only while movement is held or an exact early release remains armed. These are selected initial operational defaults, independent of fictional definitions and simulation speed; the recorded workload measurements do not establish optimal values for every device or network. The five-second general presence heartbeat remains separate and cannot meet this deadline. An unchanged valid renewal updates this narrow control state without full world preparation, navigation, save publication, aim/phase sampling or resource work. A host policy change invalidates/reissues input scope instead of changing mechanical definition pins.

**A short real-time lease must not authorize old simulation debt.** `WorldService.tickBatch` can retain elapsed-time debt while navigation is blocked and offer a large native interval when work resumes. Checking expiry only between batches is insufficient. Its existing clock/control owner therefore retains a finite, unsaved authorization window `{startsAt, endsAt}` in native game time for each of its two kinds of live intent: at most one latest steering intent and one exact armed pending release. Keep their identities and windows independent; a direction change cannot drop or re-date an accepted release.

At receipt of a new intent, first account ordinary active real elapsed time through that receipt once in the existing clock owner. Use one unsaved monotonic **accounted-through cursor** shared by input admission and host ticking; admit only an uncovered suffix so a later overlapping tick cannot charge the same real interval twice. Set both window bounds to the admitted-time frontier: current committed simulation time plus all admitted, unadvanced debt, including any reserved unadvanced prefix. Earlier owed game time is outside this new intent's window. Grow `endsAt` only as that owner subsequently admits real intervals actually covered by the still-current lease, converting each covered interval once through the existing base ratio and selected speed. Clip coverage at expiry and settle the old conversion before changing speed. Renewal extends the named intent's real expiry; it grants no future game time, cannot claim an uncovered gap and cannot reset the end to `simTime + another full allowance`.

Coverage requires the clock owner's actual monotonic interval, not just a duration supplied to `tick`. An unattributed duration can remain ordinary owed simulation time, but first disarms affected continuous-input windows so later coverage cannot bridge an unproved gap. Apply existing genuine-suspension/pause exclusions before assigning coverage; their clock policy remains controlling. These checks add no second world clock, saved wall timestamp or input-interval history.

The existing native interval owner receives only finite game-time bounds and exact current intent, never a wall-clock query. Split offers at each applicable window start/end as well as ordinary physical/work boundaries. A zero-length window grants no automatic work. Reaching the currently credited end is not lease expiry: the next covered clock admission can extend it without rotating the input epoch. A preparation ready exactly at the end of a positive covered window may release while its current lease and native prerequisites remain valid. Before a steering window starts or after it ends, that new steering is absent; pending release requires its own admitted covered window. Native preparation and other ordinary work continue under their normal rules. The host rechecks current scope and monotonic expiry before each coherent continuation and when accepting its input-dependent result.

Use the existing `tickBatch` / `advanceWorldSlices` candidate boundary concretely: retain the last complete immutable world before an input-bearing candidate and recheck authorization before accepting its returned world or counting its elapsed seconds. Publish a valid input-bearing candidate promptly through the existing `acceptProgress` / `saveProgress` / `commit` owner, with the final authority check at that acceptance boundary; do not accumulate earlier unaccepted input effects behind a check of only the last interval. If authority expired, discard that entire unpublished dependent candidate, including events and RNG, disarm only invalid input and retain its elapsed seconds as debt for a coherent continuation. Operational expiry is ordinary disarming, not `advanced.outcome.ok = false`: that existing error branch stops the world as a required-work/storage failure. Once authorized acceptance has begun, later expiry cannot retract its commit. Never surgically delete a shot from a dependent draft, rewind published motion/RNG or discard debt to repair input expiry.

A direction update can replace/coalesce only unconsumed steering, giving the new direction its own receipt-time frontier; it cannot apply the new direction to the older window. A release has its separate frozen choice. Stop, expiry and revocation disarm affected unconsumed input immediately at the next coherent boundary, while committed effects remain real. Keep no historical queue of key changes. Under substantial catch-up, an intent may expire before simulation reaches its window and therefore have no effect: expose pending/expired control honestly, never compensate with extra movement or an old automatic shot.

Camera orbit never changes a held world direction or creates a movement command. A fresh eligible key-combination change samples the current camera basis and uses the bounded input cadence, with immediate Stop. Integrate these boundaries once through the shared native interval owner rather than advancing the entire world per packet. Use the actual shared movement preparation for projectile bounds and swept contact, including compatible steering; an approach-only predictor cannot treat a steering body as stationary. There is no queue of repeated move-to destinations or client collision bypass.

Server monotonic expiry is operational state outside saved domain time. Pausing or invalidating input first disarms leases/automatic release before further world continuation. Under the existing manual-pause exception, exact cancellation remains possible; new movement/begin/release is unavailable until Play and fresh input. The browser clears held keys on blur, blocked UI/modifiers, pause and control loss and does not reconstruct them on reconnect or modifier release. A network partition has no instantaneous remote cancellation guarantee: the finite lease bounds unobserved input, and any already committed effect is reported honestly.

For melee, the human must move into actual reach; green never auto-approaches or grants a point-only hit. Existing NPC and explicit-menu navigation remain intact. For ranged, valid steering changes the eventual launch anchor. Exact-point aim retains its frozen XYZ; subject aim retains its exact life and resolves its permitted anchor and observed-motion lead at release. Derive actual facing from the admitted action under supported body rules, not camera orbit; ND38 does not need a universal turn-speed mechanic.

### 1.4 Attack mode and qualified personal notices

Attack mode is visible local player-control state, not native hostility, permission, knowledge or a second engagement list. Selected defaults are unmodified WASD, exact **Shift+T** toggle, plain **T** equipped target, **Shift+W** world-agent panel, and retained **Shift+A/Shift+S** Act/Speak. Exact modifier dispatch resolves the current W and Shift+T collisions. Narrow remapping belongs to the current settings/input owner; completing all ND13 remapping is not a prerequisite. A new controlled character/tab starts neutral. The combat pair table still chooses Command-click's preferred Speak/Attack; explicit secondary/contextual actions keep their semantics.

Auto-entry consumes a typed controlled-player notice produced by existing native offense/personal-observation evidence, not a client guess from event text. Add a compact `GameView.player.attackModeNotice` containing `noticeSequence`, `occurrenceId`, `occurredAt` (simulation time), and `kind: 'own-offensive-action-admitted' | 'personally-experienced-assault'`; optional source reference/label must already be permitted by that evidence. Bind it to current input scope and carry it through the public patch producer and `applyGamePatch`. Generic conflict categories, HP changes, testimony, environmental harm, proximity and hidden intentions are insufficient. No world-wide hidden attacker search is needed.

The initial view consumes the current sequence without entering; fresh later qualifying evidence enters once. Manual Off consumes the latest notice and cancels the matching gesture. Repeated publication, reconnect, old events and retained threat grace do not re-enter. A fresh assault can update mode while a modal is open, but cannot close it, steal focus, start an attack or turn a dismissal into a shot. An unidentified personally experienced assault can qualify without revealing its source. Store no private threat fact merely to explain the toggle.

### 1.5 Physical pointer aim, consequence review and cancellation

The plain-data `WorldRenderer` aim picker intersects permitted displayed body/scenery/surface geometry using the current camera projection and transform. It returns finite XYZ plus the existing opaque body reference or support/shape basis and exposed body facts. The installed ranged policy's projected `targetRule` determines which living bodies are eligible; the renderer does not invent world combat rules. An eligible body chooses subject aim. ## Open decisions, dependencies and current-format constraints

The chosen first slice intentionally makes **no promise of competitive browser timing trust**, general hitbox animation, genuine fluid/wind ballistics, universal crafted durability or already installed Dexterity/Focus. Those need separate demonstrated benefits and authorizations. Keep ring/weapon mechanical tuning in the [base-world profile](../worlds/base/skilled-action-execution.md), input lifetime in the server owner (§1.3) and device defaults in the client owner (§6). Inventory their tradeoffs in [ASE limits](../limits/action-execution-and-skill-expression.md); do not scatter anonymous fallback literals.

The numeric profiles are selected initial world values, not measured balance. Further charge, defense, animation or craft-skill features need separate useful scenarios and authorization; none blocks this combat correction.

No older-save migration or API compatibility wrapper is permitted under [AGENTS.md](../../AGENTS.md#development-save-policy). Same-version saved aim/work, authoring pins, exact current validator and release continuation must be verified. Do not discard current saves unless they are truly incompatible development data under the explicit root policy; preserve useful starting-world content when replacing the default starting world. Invalid profiles/records refuse at their boundary rather than silently treating broken state as a legendary or ordinary result.
