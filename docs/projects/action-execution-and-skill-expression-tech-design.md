## Behavior-to-implementation contract

Deliver the [ND38 player feature](action-execution-and-skill-expression-feature-spec.md) through **ordinary admitted actions**, not a second minigame result engine. A human chooses a permitted action; its physical preparation remains native; an optional input exercise yields bounded **action-specific execution evidence**; one trusted family derives any permissible effect; the actual world owner commits the effect, receipt and disclosure. A resident chooses through its ordinary controller and executes through the same physical owner using character competence, not simulated cursor input.

The first complete connected demonstration is (a) quick versus optional timed ranged/melee attacks while walking, observing and tracking real animals/opponents, and (b) optional **point-placement fit** during real woven-container manufacture, yielding an item-specific effective storage capacity. The first pouch has no categorical grade; optional meaningful grades remain supported for later families. Include no general scripting interpreter, second combat solver, second item-quality store, nominal 'equipment quality' modifier ignored by use, universal stats, or per-frame model call.

[Existing engine/world boundary](../engine-and-world-boundaries.md#5-a-repeatable-boundary-decision) remains controlling: stable identities, authorization, resource accounting, ordered native effects, safe observation, restoration and data-driven admitted definitions are reusable; the selected game's weapons, skills, injury/evasion law, ring tuning, material fit, item facet, names, and quality grades are **replaceable world policy**. Other coherent worlds can omit any mechanism. A supported family may be compiled native code without becoming universally installed.

## 1. Player input and shared attempt lifecycle

### 1.1 One native preparation, one release, exact recovery

**Selected implementation target; not current runtime behavior.** The client owns only `idle → candidate-tap → manual-hold → submitted/cancelled` presentation. `ActorComponent.action` remains the sole primary physical work owner. A pointer gesture, movement lease or local ring is not another Action, physical plan, resource reservation or position writer.

In attack mode, valid primary pointer-down immediately requests **one beginning of the exact chosen native attack**, capturing the displayed action/definition, tool, ammunition choice, initial permitted intended subject or point, and current input scope. Native preparation, reservation, windup, interruption and later recovery remain with the existing ranged/strike owner. A hold changes how that same preparation will be released; it never starts a second attack. Unavailable sources remain visibly unavailable, with no silent substitution of another weapon, ammunition lot, Speak, Move or target-bound method. A melee hold introduces a release-ready state in the existing strike progression: reaching the windup deadline while still holding does not automatically impact. Ordinary explicit menu/NPC strike routes retain their own native approach and one-shot progression.

Classify a pointer-up by monotonic elapsed time from its down event. A release below the [world-owned hold threshold](../worlds/base/skilled-action-execution.md#concentric-release-interaction) is ordinary score zero. Crossing that threshold allows the optional ring only after the exact admitted input profile has actually arrived. Start its phase origin once at the later of those two boundaries. Before admission, show local pending feedback without a usable green promise. A release before the admitted profile was displayed is ordinary, even when network delay exceeded the threshold; it is never scored against an unseen phase. After display, use one fixed admitted profile for the attempt. Rendering stalls cannot turn a long hold into a tap merely because a timeout callback ran late.

The ring uses monotonic **real elapsed time**, independent of date changes, graphics frames, world simulation speed, server publication and provider jobs. Phase is computed from the admitted period; frame updates draw locally. Send no recurring pointer/phase samples or paid-model work. The real-time input lease below renews control availability, not a score. Native movement, windup, recovery, resources and impacts use the selected world's simulation clock. Neither stepping the ring nor waiting for a release pauses the world.

Pointer-up captures **one immutable release intention**: final physical point where applicable, ordinary/timed input, displayed phase and manual/assisted provenance. If begin has not returned an action ID, retain that intention locally only while the same live gesture remains authorized. If native preparation is not ready, the admitted action retains one pending release record; its receipt says **release requested**, not **released**. The native ready boundary can consume it once while its current foreground input authorization remains valid. Do not recalculate timing, update the point from a later target, spend ammunition at request acceptance, queue another attack or fire repeatedly during a long hold.

At actual release, validate current actor/tool/method, relevant installed pins, readiness, body recovery, actual geometry, retained intended subject and release-review dependencies. Use the then-current native launch anchor and the frozen endpoint. A genuine accepted melee reach miss consumes native recovery under the strike owner; a refusal before an attempt commits does not. Ranged post-release handling uses the selected new native body recovery deadline described in §3; ring period never substitutes for weapon recovery.

Cancellation names only this gesture and its unfinished admitted action. Mode Off, deliberate self-region entry, Escape/Cancel, pointer cancellation, lost capture, tab blur, true modal entry, pause, connection/control/life loss or rejected capability clear local held input and disarm future automatic release; cleanup never sends Release. Cancel before begin acknowledgement establishes a terminal marker for that exact begin, so a late begin cannot prepare an unwanted action. A released projectile/committed strike remains real. If release won at the server before cancellation arrived, report the actual released result rather than claiming it was cancelled.

Native preparation can remain inspectable only where ordinary participation/interruption permits it. Reconnect, reload or Resume restores explicit native **Release/Cancel**, never held keys, a local phase or an armed automatic release. A saved pending-release record retains its exact evidence as needed for the receipt/history owner but restores **unarmed**. Deliberate recovered Release uses the current visible point and a fresh neutral release request against the exact surviving action, after resolving any uncertain original release receipt. Craft's retained ready-to-finish work follows its own §4 lifecycle; transient mouse cancellation does not invent an automatic ordinary/excellent completion.

### 1.2 Finite request, receipt and input-order contract

Keep the existing authenticated `/api/command` envelope, `commandId`, `commandEpoch`, `X-OL-Client`/`X-OL-Scope`, `WorldService.command`, command binding, native transition and durable `commandReceipt` recovery. Extend the current protocol declarations, `commandInputSchema`, `bindCommand`, catalogue descriptors, `command-request.ts` and `ui/aim-controls.tsx` together. Do not introduce a second attack executor or persisted gesture database. `ApiResult.actionId` is already the native action identity; it is distinct from the request's command ID and catalogue option ID.

The following are **selected fields for this narrow integration**, not descriptions of existing wire support. Use existing validated reference/pin types when implementing them; never expose raw actor life or accept an actor ID as authority.

```ts

  inputEpoch: string;
  gestureSequence: number; // positive safe integer, increasing per current controller
  beginCommandId: string;  // original /api/command identity, never regenerated on retry
};
type AttackReleaseInput =
  | { kind: 'ordinary' }
  | { kind: 'timed-release'; phase: number; mode: 'manual' | 'assisted' };
type AttackExecutionControl =
  | { operation: 'begin'; inputEpoch: string; gestureSequence: number;

  | ({ operation: 'release'; actionId: string; input: AttackReleaseInput }

  | ({ operation: 'cancel'; expectedActionId?: string }
```

`execution` is accepted only on the supported native attack begin/release/scoped-cancel command forms. It cannot register a new action or arbitrary effect. The current `aim` and `strike` bindings gain deliberate held preparation when `execution.operation` is `begin`; absent that payload, their existing ordinary routes keep their meaning. `release-shot` continues to name its native aim through `aimId`. Add the finite native `release-strike` variant with `expectedActionId` for the held-melee ready state; it uses the existing strike impact owner, not the ranged executor. Update native types/binders/support classification alongside that state. Require `execution.actionId` to match `aimId` or `expectedActionId`, respectively; the duplicate spelling cannot select two different actions.

At most **one bounded current attack-gesture slot** belongs to a live controller. It stores the highest accepted gesture sequence, begin command identity, phase (open, release-requested or cancelled) and bound action ID. It coordinates input only; action state, ammunition and effects stay native. A matching cancellation is terminal even if it arrives before its begin. Lower sequences cannot revive work; a higher deliberate begin cannot silently replace an unresolved gesture or unrelated current work. Existing explicit replacement admission still governs such choices. Duplicate command lookup occurs before fresh action/gesture eligibility checks, as the current receipt owner already requires; a conflicting payload under the same command ID refuses. Durable command receipts keep their own recovery scope. A current epoch does not attest human timing or mouse input.

### 1.3 Movement alongside preparation and the live input lease

WASD supplies a normalized **camera-relative ground-plane direction**, transformed to finite world `(x,z)` intent. It carries no client position, speed, distance travelled or elapsed simulation time. The existing body/support movement owner consumes finite steering segments while idle or while the selected ranged/melee preparation explicitly permits steering. It uses the existing `moveAlongPath`/`setSpatialPosition` and support-walk transition owners; collision, floors and elevation remain native. `ActorComponent.action` is still the sole physical work slot. Guard, craft, another weapon preparation and unrelated manual work remain incompatible. An ordinary move/evade/menu action uses ordinary replacement admission. Unsupported bodies/tools expose refusal, not generic parallel work.

Use a narrow authenticated input-control update within the existing WorldService control/presence owner, not a durable gameplay Action or receipt for each heartbeat. Direction changes/stop and renewal are separate finite messages; all are scoped by current `inputEpoch` and controller authority:

```ts
type WorldInputUpdate =
  | { kind: 'steer'; inputEpoch: string; movementSequence: number;
      direction: { x: number; z: number } }
  | { kind: 'renew'; inputEpoch: string; renewalSequence: number;
      movementSequence?: number;
      pendingRelease?: { gestureSequence: number; beginCommandId: string;
        actionId: string } };
```

Both sequences are positive safe integers. Direction is a finite normalized vector, or exact zero for Stop. A newer movement sequence replaces current steering; old/equal movement packets cannot change or renew it. A renewal names the currently accepted nonzero movement sequence and/or exact pending release; it never recreates stopped movement or an expired/cancelled gesture. Discrete attack sequencing is independent: a newer WASD packet cannot drop a release, and a release cannot revive stale movement. Input acknowledgements return the current epoch and accepted sequence so the client can discard obsolete state without fabricating a command result.

The [world input table](../worlds/base/skilled-action-execution.md#concentric-release-interaction) owns initial renewal/expiry values. Renew only while movement is held or a still-authorized early release is pending, with **100 real milliseconds** as the initial renewal target and **250 real milliseconds** as the server expiry. These are unqualified test defaults, not measured latency claims. The existing five-second general presence heartbeat remains a separate service; it cannot serve this deadline. An unchanged valid renewal extends only the operational lease and avoids full world preparation. No aim positions, ring samples or native resources are rewritten on renewal.

On a direction-change or expiry boundary, finish the already admitted simulation segment under the previous direction, then apply the new direction or stop. Coalesce unsimulated redundant updates to the latest valid intent without dropping already committed movement. Integrate boundaries once through the shared native interval owner, never by advancing the entire world per input packet. Capture actual piecewise body tracks for `projectileBoundary`/`advanceProjectiles` candidate bounds and swept contact, including compatible steering; the current approach-only prediction cannot silently treat a steering body as stationary. There is no queue of repeated move-to destinations and no client collision bypass.

Server monotonic expiry is operational state outside saved domain time. Pausing or invalidating input first disarms leases/automatic release before further world continuation. Under the existing manual-pause exception, exact cancellation remains possible; new movement/begin/release is unavailable until Play and fresh input. The browser clears held keys on blur, blocked UI/modifiers, pause and control loss and does not reconstruct them on reconnect or modifier release. A network partition has no instantaneous remote cancellation guarantee: the finite lease bounds unobserved input, and any already committed effect is reported honestly.

For melee, the human must move into actual reach; green never auto-approaches or grants a point-only hit. Existing NPC and explicit-menu navigation remain intact. For ranged, valid steering changes the eventual launch anchor without moving the frozen endpoint. Derive actual facing from the admitted action under supported body rules, not camera orbit; ND38 does not need a universal turn-speed mechanic.

### 2.2 Deterministic evaluation and presentation

The timed-release evaluator accepts a phase and the admitted profile; it does not read rendering frames, a hidden opponent or current wall-clock time. The client advances phase from monotonic real elapsed time after both hold eligibility and receipt/display of the exact admitted profile, with the phase origin fixed by §1.1. One full period traverses outward and back. For the selected triangle waveform, normalized white-ring radius is `r = 1 - abs(2 * phase - 1)`. For authored target center `c`, green half-width `g`, ordinary half-width `y` and maximum radial distance `D = max(c, 1-c)`, let `d = abs(r-c)`:

```text
if d <= g: score = 1 - d/g
else if d <= y: score = 0
else: score = -min(1, (d-y)/(D-y))
```

The installed profile must satisfy finite `0 < g < y`, `0 < c < 1`, `y <= min(c,1-c)` and `y < D`, with a positive finite period. This prevents empty bands and zero divisors, rather than validating incidental conventions. Use the same pure evaluator for permitted UI prediction and authoritative interpretation. A shared boundary scores exactly zero: project it as ordinary; positive is strong, zero ordinary and negative weak. Do not color a zero result as a promised improvement. The [base-world timing profile](../worlds/base/skilled-action-execution.md#concentric-release-interaction) owns exact initial values; the [limits](../limits/action-execution-and-skill-expression.md#ase-l02--ring-pace-and-visible-timing-bands) own their restrictiveness and tuning status.

An ordinary tap, explicit skip and NPC action without human input contribute exactly zero. An accessible skilled alternative may reach the same positive maximum through the same admitted family. It is an input route, not an automatic hidden reward or a lower item class. The precise controls are in §6; competitive acceptance is separately restricted in §5.

World-installed character/condition/weapon-familiarity contributions may alter the admitted bands or period. None is a mandatory engine Dexterity/Focus field. The initial base-world slice installs no new focus, intoxication or clothworking statistic. If a future installed contribution changes the active challenge's meaning, invalidate that sample and offer a fresh permitted preparation; do not keep displaying an old curve while secretly scoring a new one. Unrelated simulation ticks do not invalidate a profile. Physical handling/condition is evaluated by its normal native owner at the relevant preparation, release or contact boundary; changing the ring never changes native windup or recovery.

Browser phase, monotonic timestamps and coordinates remain **untrusted input claims**. Deterministic recalculation prevents fabricated score/stat fields; it does not prove human timing, actual pointer motion or freedom from automation. No server challenge database or trusted competitive clock is selected here.

For point placement, evaluate distance in the admitted workpiece's local frame, never pixels or device resolution. The same signed pattern uses the family's positive radius, ordinary radius and finite penalty-tail width. Exact guide construction and first-slice numbers have one owner in [fitted woven containers](../worlds/base/skilled-action-execution.md#the-chosen-noncombat-proof-fitted-woven-container). The workpiece does not share the combat ring's animation, target position or timing law merely because both produce a bounded scalar.

### 2.3 Family-owned contributions

Let `b` be the native baseline **after** the existing tool, character competence and applicable condition calculation; `s` the evaluated input; and `p,q` the exact family's excellent-improvement and poor-reduction coefficients. The common relative arithmetic is:

```text
factor(s) = 1 + p * max(s, 0) + q * min(s, 0)
result    = nativeChannelClamp(b * factor(s))
```

Definition admission requires finite nonnegative coefficients and a nonnegative resulting factor over the supported score range. The [base-world weapon table](../worlds/base/skilled-action-execution.md#weapon-specific-consequences-selected-initial-testing-profiles) selects its actual coefficients; these are initial balancing inputs, not measured fun or a universal 25% multiplier. A hypothetical 75% baseline with a 25% relative excellent coefficient becomes 93.75%, not 100% and not 100 percentage points. Apply existing sling competence once before this contribution, never once at aim and again at contact.

Contact quality affects only a legitimate physical opportunity under §3. It cannot create collision, make a body intangible, steer the ray, bypass shielding or add a second random miss after injury. A body with no feasible evasive clearance remains collidable even when source handling is poor. Injury scaling occurs before the existing defense/susceptibility/health-clamp owner, with actual inflicted quantity recorded after clamping. Do not round a probability as though it were whole-point health.

Only an actually supported native critical mechanic could consume a future critical channel; this slice creates none. A future charge or spell gesture needs a useful supported family, not speculative channels now. Manufacturing uses its own material-derived baseline and integer packing rule in §4; no generic engine item-quality scalar is introduced.

## 3. World physical contact and the evasion reconciliation

### 3.1 One exact released ray and retained source facts

The current bundled `releaseShot` calls `baseShotDirection` and spends randomness on trajectory deviation. The selected bundled shot family replaces that law for **every** admitted route through that family: ordinary tap/menu shot, held manual shot, practice/hunt and resident/NPC action. ### 6.2 A complete finite accessible attack route

Provide **Animated timing** (default) and **Step timing** in the same action-input preference. Both use the exact admitted profile, character baseline, native preparation/costs/recovery and final evaluator. Step timing is explicit noncompetitive assistance; it changes the displayed exercise, not world time, target knowledge or physical outcome authority. The ordinary route is always useful and exact score zero.

1. **Attack** performs one ordinary native attack at the current explicit aim. **Prepare** begins the same deliberate held preparation without requiring a continuously held mouse button. While preparing, expose **Release**, **Attack normally** and **Cancel** in the shared active-action group. Ordinary Tab and Enter/Space button semantics suffice; add no competing global letter listener. Pending admission/ready/refused/release-requested/released are distinct visible states, with current native disabled reasons and a receipt-based **Check result** when uncertain.
2. Select an already perceived subject through **In view** or the existing target chooser to initialize one reticle at its currently displayed point. This is a one-time point selection; later movement never tracks the subject automatically. A focused **Aim** control moves the reticle in screen axes with arrow keys, coarse **16 CSS pixels** and fine **Shift+arrow 1 CSS pixel**, through the same physical aim picker as the pointer. The focused control owns those keys instead of camera arrows; visible camera controls still work. Invalid aim stays visibly unavailable. No numeric world-coordinate form or hidden-target list is introduced.
3. In **Step timing**, after admission/hold eligibility the ring initially shows phase zero. A labeled **Timing position** slider changes phase in **0.01-cycle steps**, with Home=0 and End=0.99 and equivalent directional controls. It freezes only the white ring's displayed phase; native windup, other characters and the world continue. Phases 0.25 and 0.75 are exactly selectable, so the selected center-green maximum remains attainable. Choose **Release** explicitly; moving the slider never fires and crossing green never auto-releases.
4. **Animated timing** also supports the Prepare/Release hold-toggle route. Reduced motion can select Step timing directly; do not secretly slow game time or submit at green. **Attack normally** skips input with score zero, whereas assisted skilled input retains the same permitted noncompetitive score range and maximum. The competitive boundary in §5 neutralizes the entire optional score at an actual human-owned contact, including its negative side, without exposing that ownership.

The [world input table](../worlds/base/skilled-action-execution.md#concentric-release-interaction) and ASE limits own the selected numeric defaults and their unverified status; this section names their exact initial behavior rather than installing another set of constants. They require actual keyboard, reduced-motion and assistive-technology qualification. This first desktop slice does not claim touch/controller parity merely because buttons accept focus.

## 7. Performance, cadence, and bounded work

**Growth:** local frame drawing is O(1) per active gesture, never O(number of entities); native body-contact candidate work grows with local collider density and released flights (existing spatial index/work budget); available-action preparation grows with applicable tools/methods and targets only at an actual request; item quality resolution is O(1) per owned exact item; no world-wide scan per tick. **Sharing:** immutable installed profiles/geometry descriptors reused within their stable definition pins; current permitted target/tool preparations reused only in the owning current unchanged read. **Invalidation:** actor life/control, body/condition/competence, equipment and profile pins, current visibility/geometry, actionable work, time deadline and held gesture/receipt epoch. **Measurement:** sample browser input-to-cue and release-to-request latency, end-to-end release-to-observed flight, physics during pending model jobs, projectile first-contact candidate count, ordinary versus skilled manufacturing and projected item capacity under the same device/world/clock, including sparse and concentrated cases.

Do not send 60 network writes/second for pointer tracking or WASD if an interval- or change-based intent channel with a bounded renewal can carry the same actual movement. Retain the current single-writer authoritative transition and existing 50-ms publication only where it is actually appropriate; client graphics smoothness is separate. A client drag sampling interval does not spend simulation time. Bound native continuation by actual meaningful contact/work deadlines and the existing work budget; if full collision preparation cannot complete, preserve a truthful unfinished/technical state rather than simulating no contact.

**Required critical cases:** release exactly once across duplicate HTTP/receipt replay; evade/body/solid ties with canonical ordering; multiple bodies along one ray; moving bodies across sparse interval boundaries; shooter gone after release; 500 simultaneous active but unrelated characters without global per-frame rescoring; many registered irrelevant tools with one selected action; current-format restore of held aim and selected craft; reduced-motion/manual/assisted parity; fast time acceleration does not create 8× browser callbacks.
