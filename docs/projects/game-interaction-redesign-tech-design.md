## Whole-interface implementation boundaries

The following boundaries are implemented in the current whole-interface candidate, grounded in the [58-group source map](../ui-ux/interface-coverage.md). ### Keep the application, reorganize its task entry

Retain React for interface state, PlayCanvas behind `world-renderer.ts` for scene presentation, and the current native/application owners for knowledge and effects. The main integration seam is `apps/client/src/main.tsx`: `panelInfo`, `content`, `show`/`fit`, selected-object context, task entry and modal/editor mounts. Reuse `design-system/components.tsx` `Panel`, `Launcher`, `Toolbar`, shared controls and `ui/hud-layout.ts`; do not introduce another shell, routing framework or UI package.

Implement the product specification's navigation hierarchy through focused assemblies of existing surfaces. A player task, creator workspace and operations console can share controls without sharing authority or becoming one enormous menu. Keep `ApplicationScope` and `OperationsConsole` as the actual characterless/operator route. Selecting a category or opening a panel stays read-only. An in-world action retains its initiating object, while a deliberate independent workspace can expose broader search.

Extract a small connected component from `main.tsx` only when a specific slice needs clearer ownership—for example its time controls or Settings/help sections. Preserve the existing view/subscription owner; avoid a second synchronized copy of `GameView`. Do not replace every panel at once or build a metadata-driven universal menu. The inventory coverage map supplies the scope accounting; subsystem specifications continue to own behavior.

## Interaction state and data flow

An inventory interaction has a controlled actor, world/access/timeline identity, an optional external object, two collection locations, and local presentation state. Each collection retains its own query, sort, continuation, scroll anchor, selected item and read revision. The external object is an exact reference originating in world selection, not a display name or a list row index.

The state progression is:

1. **Selected exterior.** The player knows the object through the permitted world projection. Selection/hover is read-only.
2. **Opening.** Explicit Open requests the object's permitted direct contents. Display loading without temporarily reusing another chest's rows.
3. **Open and usable.** Both collections are tied to exact locations and access state. Item selection and inspection remain reads.
4. **Transfer pending.** The initiating gesture submits an exact native intention. Mark affected rows pending; retain source and target context.
5. **Committed or refused.** Apply the actual receipt/projection, restore useful focus and show any refusal locally.
6. **Unavailable/closed.** Loss of access removes protected contents; hiding closes presentation according to the current lifecycle without reopening, retrying or mutating anything.

Loading, empty, filtered-empty, incomplete, stale, refused and disconnected are separate states. Do not use an empty grid as the visual meaning of all seven. Source revisions and stable identities fence async replies. Switching from chest A to chest B cannot let A's late response populate B. A changed search does not prove a missing selected item was removed.

Opening now uses a small permitted exterior/access projection followed by the existing native direct-contents read. It does not create a globally accessible container session. The client retains the selected world root and its placement while open; a changed root or lost permitted hint makes that interaction unavailable until explicitly reopened. Native access still decides whether any contents may be returned.

## Direct transfer without weaker authority

Resolve the exact source item, source location, destination location and quantity at the player's commitment. Drag/drop, quick-move, keyboard action and explicit Move button call the same client intention helper and native admission route. They are interaction alternatives, not four mutation implementations.

A routine move needs no additional human review because the two endpoints and item are already visible. It still needs server checks for actor/control identity, custody, permission, supported handling, reach, obstruction, current quantity/capacity, reference validity, containment cycles and applicable equipment constraints. Bind the destination when the gesture starts/commits according to a documented drag contract; a projection update must not redirect a pending move to another pane.

The implemented ordinary inventory-handling command path captures and retains the exact `{commandId, commandEpoch, command}` request before sending. It requires the server-issued `commandRecoveryScope`; it does not fall back to a different draft or connection namespace. If browser storage cannot retain that request, the send is refused before execution with an explanation that nothing was sent. Until a result is known, duplicate handling remains blocked and no optimistic item becomes usable at both locations. The separately entered God ownership/access editor retains its existing owner-write path; it is not a gameplay receipt-recovery client.

**Check result** submits that exact original envelope to `/api/command/receipt`, which only reads the native receipt and never executes the command. The execution fingerprint remains unchanged. The separate recovery fingerprint omits only connection and control generation, while preserving account, session and session revision, grant revision, actor, world/timeline, audience and exact input. Current access is revalidated before a result is returned. This permits same-owner recovery after a control resume without letting a new owner or changed payload claim the old result. The request label is local presentation, not an extra field sent to the strict receipt endpoint.

A timeout, unavailable receipt or lost connection remains unresolved; counts, hiding/reopening and a fresh command ID cannot prove or retry the earlier outcome. A resolved native refusal is a known result. Completion and storage cleanup must match the still-pending request identity so a late result cannot clear a newer command. Real client/server recovery, changed-input rejection and late-result qualification remain required in J06/J08; focused owner checks alone do not close them.

Amount edits preserve the target object but invalidate quantity-dependent eligibility. Native revalidation can refuse changed capacity without sending the player back to choose the same chest. Quantity draft, selected target and eligibility evidence are distinct pieces of state. Quick-move now submits the exact inspected available quantity, with current item, placement, contents and destination revisions as applicable. It leaves reserved units behind and never silently expands to all-at-admission semantics. A stale amount retains the player's text and endpoint choice while requiring fresh facts; changed availability is not zero and does not select a different stack.

Visual grouping and local order never merge domain objects. Use native split/merge actions where that is the player's intention, preserving individual identity, history, names and state. A generic cell count cannot replace world-defined capacity. A world's slots, volume, mass or other capacity can be presented only through its supported facts.

For bulk transfer, add a native batch contract before claiming a single atomic action. Decide atomic versus explicitly partial semantics, bounded candidates, protected-item rules, result receipts and retry of only the remainder. A front-end loop over all loaded rows cannot promise Take all across unloaded contents. This is a later stage with its own UXL09 gate.
