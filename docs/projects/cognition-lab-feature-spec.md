# Cognition Lab — feature specification

| Status      | Current progress                                                                                          | Last updated |
| ----------- | --------------------------------------------------------------------------------------------------------- | ------------ |
| In progress | Design complete; runtime implementation and usability/behavior qualification remain open under CL01–CL11. | 2026-10-24   |

## 1. Purpose and product outcome

Cognition Lab is an owner-only development workspace at `/cognition` for making Open Legend's people more particular, expressive, independent and consistent through actual situations. It runs the game's existing simulation, perception, memory selection, cognition, action discovery and execution against a separate editable scenario. A developer can speak to Ada, change one relevant circumstance, repeat the interaction and understand the difference without launching the rendered game.

Standard development setup provides one dedicated lab data store and one active lab scenario through a second instance of the same runtime. Saved scenarios and recorded runs are selectable; comparison variants execute serially in that lab runtime. No extra database/setup wizard appears in the ordinary page flow. The game runtime remains independent.

The ordinary task is immediate: open the page, choose a person, type something and see what that person says or does. Deep inspection is available beside that task. A developer must not assemble a model experiment, traverse a tree of implementation objects or manage five scrolling panels before trying one line of speech.

The lab's creative value is discovering a person worth encountering in play. Particular interests, jokes, loyalties, disagreement, competent action, quiet pleasure and remembered consequences should survive outside the lab in the same game implementation. The tool must help uncover those qualities rather than optimize everyone into generic helpfulness, compulsory emotional display or an answer prescribed by the test author. [Character authorship](compelling-characters-feature-spec.md#character-authorship-and-changing-personality) and [whole-episode evaluation](compelling-characters-feature-spec.md#judge-a-life-not-an-isolated-response) remain the behavior owners.

This is a design-only deliverable. The linked technical design defines the implementation contracts; the maintainer tracker distinguishes design completion from unimplemented capabilities and unqualified usability. No model-quality or gameplay evidence is claimed by this specification.

## 2. Accepted scope and non-negotiable behavior

1. **Same game implementation, independent data.** The lab uses the same installed world rules, scenario initializer, character authorship, perception, memory/context preparation, supported decision routes, action options, admission and effects as the game. No second personality engine, lab-only action interpreter or client-side imitation of perception is allowed.
2. **The rendered game is optional.** The normal game can remain open in another tab, but its renderer and live world are not needed to use the lab. Scenario edits, pauses, restores and deletion never affect that game.
3. **Left is current; right is historical.** The left panel always represents the currently selected character in the current editable lab scenario. Selecting any old event, request or comparison never rewinds, substitutes or freezes the left panel's character values. The right inspector shows the exact captured values used by its selected decision.
4. **Focus is not control.** Inspected person, event actor, event target and autonomous participants are independent selections. The run policy also names its own focal actor, initialized once and thereafter independent. Inspecting Ada does not transfer human control, suppress cognition, change her interpretation policy or silently choose whom the experiment waits for.
5. **Full authoring freedom is explicit.** Character prose, traits, beliefs, experiences, speech history, surroundings and custom input fields can be edited freely within the isolated scenario. A descriptive addition does not silently install native decay, triggers, abilities or physical effects.
6. **One-call overrides are one-call overrides.** Only Submit in the prepared-input modal uses its edited request. Ordinary Submit always prepares from the current scenario. Left-panel edits invalidate prepared input; an override is never a hidden persistent setting.
7. **Read does not run.** Opening, searching, refreshing, inspecting, copying or replaying recorded results does not send another model request or alter the world. Commands that advance the experiment are distinct.
8. **Technical truth remains inspectable.** Perception, testimony, belief, model proposal, accepted effect and completed action are distinguishable. Silence, deliberate continuation, unsupported action, missing capture and unavailable AI are not rendered as successful empty replies.
9. **Large desktop is the primary target.** The layout prioritizes Mike's ability to read and manipulate many values at once on a large screen. Small-screen adaptations must not reduce desktop density, introduce automatic pane replacement or expand ordinary controls.
10. **Current development data is disposable.** Save/load supports valid current-format scenarios and runs. No legacy adapters, schema migration service, historical engine runtime, branching storage platform or preservation of incompatible development experiments is part of delivery. Follow the [development policy](../../AGENTS.md#development-save-policy).

## 3. First useful interaction

### Default opening

Opening `/cognition` restores the last selected compatible lab scenario when available; otherwise it creates a scenario held at a ready boundary from the current selected world's normal starting definitions. It does not clone a currently running game silently. The page opens with the existing starting character Ada selected when that authored character is available; otherwise it selects the first eligible named character and shows the ordinary picker. This is a bundled-world default, not an engine requirement for an Ada identity.

The selected scenario supplies the normal participating characters, physical surroundings, histories and installed rules needed for a coherent opening. The character picker lists characters in this scenario; Add/import character is explicit. Selecting another person never imports an unbound body, history or acquaintance by name alone. The lab keeps its declared, already-active human participants present without requiring a game renderer. Merely inspecting or speaking as someone does not change participation; deliberate departure/return experiments use the native participation controls and are recorded as interventions.

The center composer opens on **Say**. Its actor defaults to the normal initializer's actual player-character binding (Mike in the base world), and its target to the initially inspected character. The lab does not invent a new speaker or change long-lived control. Actor and target remain independent thereafter: inspecting another person does not silently retarget an already drafted message. Volume defaults to the world's normal supported speech volume. The input is focused only on initial ready entry, never on every refresh. **Wait for: Ada** initially identifies the One response run policy; its actor is initialized from the opening inspection once and then persists independently. Inspecting a different person does not change the stopping condition.

The developer types a sentence and selects **Submit**. The default **One response** mode admits the event and runs until the focal character's immediate decision has published its accepted result or reached an explicit no-decision/failure disposition, then holds at a safe boundary. It closes new admission and settles already-dispatched dependent work; it does not wait for all autonomous characters, background reflection or a newly started physical action to finish. An action that only started is shown as started, with **Continue** or **Advance to outcome** available. [CLL06](../limits/cognition-lab.md#cll06) owns finite progress bounds. Reaching a guard displays **Run limit reached**, never a fictional decision to remain silent. The event appears in the center with actual speaker, target, volume and game time. The focal person's accepted speech, action or deliberate lack of intervention appears in the same chronology. The right panel automatically selects this newly submitted experiment's root while in Follow latest mode and shows its result summary. Existing deliberate inspection disables that automatic selection without stopping the experiment; a fixed new-result indicator offers a direct jump without replacing the record being read.

There is no mandatory setup wizard, test rubric, save dialog, configuration form, tree expansion or raw-payload inspection in this journey. Missing AI configuration is an inline, actionable state beside Submit; the text remains editable. No automatic send occurs after configuration becomes available.

### The first explanation is visible

With Follow latest enabled, the new experiment opens its Overview immediately. The fixed result strip identifies the person, time, disposition and a short outcome; the body below shows the full accepted speech or action status, then compact facts for trigger/perception, choice/admission and consequential changes. These facts require no click or accordion. A failure or no-action reason occupies the same ordinary result view. Long replies scroll only in that existing body; the 88 px strip is not expected to contain the entire reply or every causal fact. Technical request details remain one deliberate step away.

## 4. Desktop workspace and spatial contract

### Fixed shell

The browser viewport contains one full-height workspace. The workspace document itself does not scroll. Use a compact fixed header, a fixed experiment strip and three resizable panes. Headers, pane navigation, collection searches, composer controls, apply/cancel controls and payload-modal actions remain outside their relevant content scrollers.

At default UI scale use the existing 4 px token rhythm: 8 px workspace inset, 8 px column gaps, a 40 px header and a 32 px experiment strip. The panes take the remaining height. These are selected lab presentation defaults, not changes to ordinary game panels; [CLL05](../limits/cognition-lab.md#cll05) owns their rationale and qualification.

| Reference viewport | Left pane | Center pane | Right pane | Expected use                                                                       |
| ------------------ | --------- | ----------- | ---------- | ---------------------------------------------------------------------------------- |
| 1920 × 1080        | 420 px    | 734 px      | 734 px     | Ordinary authoring, speech and full structured inspection simultaneously.          |
| 2560 × 1440        | 480 px    | 1024 px     | 1024 px    | Larger prose, side-by-side facts and richer comparisons without enlarged controls. |

The widths exclude the workspace inset and two column gaps. Pane splitters preserve user choices per device. Reset layout restores these defaults. The selected character, composed text, collection queries, active record and scroll anchors survive resizing. Growing the screen adds readable content space; it does not increase button sizes or impose wider padding.

The header contains the lab title, current scenario/name and dirty state, scenario picker, save actions and settings. The experiment strip contains execution controls and live state. Neither repeats the selected character's name in a large title. A pane header is 32 px; ordinary toolbars use one 32 px row. The left Apply/Discard footer reserves 36 px even when clean, displaying a quiet saved/current status instead of appearing and shifting content. The center composer reserves 160 px: two 32 px control rows, 80 px for the four-line input and 16 px total spacing; expanding text within that allowance cannot shrink the timeline. The right result strip reserves 88 px for a bounded summary and direct links; selecting a longer result opens its full content in the body. These baseline measurements are qualified together in CLL05; they are not permission to clip important text at larger user font sizes.

The large-desktop reference target is at least 1600 × 900 available CSS pixels at the user's chosen scale. Smaller windows retain explicit pane-focus controls; implementing a mobile product or phone-specific drawer system is not a delivery prerequisite. A deliberate focus-pane action temporarily gives that pane the available workspace and has a fixed return control. It never happens automatically during a normal desktop interaction. Browser zoom and larger text still preserve reachable controls and ordinary keyboard operation.

### Scroll ownership

| Region              | Fixed content                                                                        | Scrollable content       | Search                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| Left                | Person selector, category rail, current category title, Apply/Discard when dirty     | One category body        | Fixed search for Memories, History, Relations, Possessions, Surroundings and other growing collections. |
| Center              | Timeline filter strip, actor/target/mode controls, composer and Submit               | One event timeline       | Fixed timeline search and compact filter controls.                                                      |
| Right list          | Inspector header, trace search, filters, follow control                              | One trace list           | Always available; filters do not replace search.                                                        |
| Right detail        | Back/breadcrumb, trace/call selector, result strip, subsection tabs, payload buttons | One selected detail body | Fixed search when the detail body is a collection or long payload.                                      |
| Payload modal       | Stage/snapshot header, editor toolbar, footer actions                                | One payload editor       | Editor find, with next/previous matches.                                                                |
| Focused text editor | Subject/field title and Apply/Cancel                                                 | One text editor          | Find for long text.                                                                                     |

Never put a separately scrollable memory list inside the scrolling left category or a scrollable question table inside the scrolling right body. The owning collection is the body. Item selection replaces that body or opens the specified focused editor. A fixed finite row of view/filter options uses compact buttons rather than a scrollable selector.

A scrollbar is not a browsing strategy. Growing collections expose search from their first use, visible known totals or loaded/more counts, clear-filter action, stable ordering and explicit empty-versus-no-match states. A fixed small set such as Say/Act/Event or Input/Output/Full request does not gain search or scrolling. Long individual prose is allowed to scroll in its focused editor; it is not forced into a table row.

### Density and icons

Use existing UI and utility typography, with 13 px interface labels, 14 px readable prose and approximately 20 px prose line height at default density. Compact rows are 28 px high; icon controls use a 28 × 28 px rectangular hit region even when their glyph is round. Utility glyphs are normally 16 px. Do not use tiny unlabeled targets, reduce body copy below 12 px, or shrink the entire page to fit. Exact accessible contrast, hit regions and focus treatment remain shared-control requirements. [CLL05](../limits/cognition-lab.md#cll05) tracks these presentation defaults.

Use icons for familiar repeatable utilities: search, clear, add, remove, edit, copy, save, back, expand/focus pane, play, pause, step, pin, filter and settings. Use the shared semantic catalogue, not arbitrary emoji. Each icon has an accessible name and hover/focus description; toggles expose pressed state and a non-color selection treatment. A tooltip includes a shortcut when supported. Destructive actions identify the exact subject in their accessible name and remain spatially separated from frequent actions.

Keep short labels for unfamiliar or consequential primary choices: **Submit**, **Apply**, **Discard**, **Compare**, and the active category title. This is not a rule to label every repeated utility. A row of anonymous icons whose meaning is required to understand the task fails acceptance even if each has a tooltip. Errors and blocking reasons never exist only in hover help.

Frequently used actions are visible in their fixed toolbar or beside the selected field. Hover is for description, not for discovering that editing or inspection exists. A selected row can expose less frequent actions in one labeled menu; it must not require drilling through nested menus. Repeated record rows do not each need a large button bar.

Related icon controls use a labeled toolbar with one Tab stop and arrow-key movement; entering/leaving the toolbar must not trap focus. Tab order follows header, experiment strip, left, center, right. A toolbar preserves the active item when focus returns. Tooltips appear on keyboard focus as well as hover, can be dismissed with Escape, and do not cover the control being described. Plain Enter submits only from the intended primary-action context; **Ctrl/Cmd+Enter** submits a composer draft when that composer has focus. Escape closes the topmost temporary surface or discards an uncommitted field edit, never the entire scenario. No global letter shortcut consumes ordinary typing.

### Shallow disclosure and direct access

The workspace shows outcomes and frequently edited information immediately, detail in the same pane on request, and raw payloads in a focused modal. It does not use recursive object trees as the normal presentation.

From a visible reaction summary with a unique recorded source call, the exact model input, questions/options, selected memories, or state changes are reachable with one direct action. A selected memory's full content is at most one further action away. When a root has several calls and no unique primary source, choosing the actual call adds one explicit selector action; the UI must not invent an aggregate request to meet a click target. The right panel may preserve a longer breadcrumb for orientation, but those breadcrumbs must not impose sequential navigation: relevant tabs, record selectors, result links and back navigation can jump directly. [CLL05](../limits/cognition-lab.md#cll05) owns the access-depth requirement.

The result strip therefore supplies a direct **Memories** count/link to the relevant captured collection, rather than forcing Inputs → category → collection traversal. Existing Input, Choices and Changes controls provide the other direct actions; do not duplicate identical toolbar buttons. These links resolve from the actual selected result's source bindings. A result with no corresponding model call shows the true unavailable/native-only explanation. Multiple calls remain separately named in the fixed call selector; the UI never merges their inputs to manufacture one request. After a call is selected, Input/Output/Full request refer to that call unambiguously. A memory row selection opens its complete text in the body immediately; a source-provenance view is optional supporting detail.

Use ordinary sections and compact tables when values benefit from comparison. Do not hide each field behind an accordion. Long collections can replace the detail body; fixed category switches remain visible. Back restores the exact query, selected row and scroll anchor. No new popout window or modal is needed merely to read one memory.

## 5. Current-character editor — left panel

### Stable structure

The person selector remains at the top. Below it is one fixed row of compact category icons with hover/focus names; the active category's short title is always visible. Categories are **Overview**, **Person**, **Body**, **Feelings**, **Relations**, **Work**, **Possessions**, **Surroundings**, **Memories**, **History** and **Custom**. A larger row can wrap once into a reserved second line without scrolling or displacing content unpredictably; the desktop layout reserves its full navigation height from initial render.

Overview is the initial category and contains compact summaries of currently installed body meters, active feelings/concerns and current work. It uses one body scroller only when those actual facts exceed the available height. Pinning a field places it in the Overview rather than creating another permanent floating panel. Pinned fields are references to existing editors, not independently writable copies. A name/value row can open or directly edit its known field; a Details icon reaches the full owning category.

All left values are current scenario values, even when the right side shows an earlier run. A persistent small **Current** label beside the person selector and historical time on the right communicate this. Comparing an earlier value never changes the left panel's meaning. Restoring a checkpoint is an explicit scenario command and therefore changes current values normally.

### Field and category behavior

| Category     | Required editable or inspectable content                                                                                                                               | Important distinction                                                                                                                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Person       | Name, authored description, biography, personality, traits, values, interests, preferences, current accepted self-understanding and beliefs                            | Biography, present circumstances and chosen intentions are distinct. Descriptive traits do not automatically grant mechanical effects. |
| Body         | Applicable health/energy/fullness/spirit or world-authored equivalents, units/range/direction, injury, pain/discomfort, wake/sleep, posture, senses, active conditions | Use actual installed definitions. Lower fullness means more hunger in the base world. Unknown is not zero.                             |
| Feelings     | Every active permitted feeling, its source/target, qualitative or numerical value, lifetime, last change and proposed/accepted update                                  | Bodily reaction, interpreted feeling and calculated gameplay consequence are separate.                                                 |
| Relations    | Directional personal notes, known name, recognition/acquaintance binding, beliefs about the person, actual supported commitments                                       | A relationship word does not establish reciprocal feeling, consent, recognition or native promise state.                               |
| Work         | Current goals, selected and suspended plans, current action, remaining work, blocked steps, commitments and consequences of interruption                               | A scenario-seeded goal is labeled an intervention; it is not an independently chosen intention.                                        |
| Possessions  | Inventory, equipment, quantities, resources, usable tools and learned methods                                                                                          | Saying someone is skilled or owns a weapon in prose does not install the method or physical item.                                      |
| Surroundings | People, animals, objects, placements, facing, relevant physical conditions and current personal sensory evidence                                                       | Scenario truth and the selected person's perception have separate labeled views.                                                       |
| Memories     | Raw experiences, retained shared-event awareness, summaries, source/perspective/time, certainty, selection/index status and actual dependencies                        | A heard claim, inference, imagination and observed fact retain their meanings.                                                         |
| History      | Authored past speech/events, speaker/actor, target, volume, actual or authored hearers, times and dependent experience                                                 | Rewriting visible text alone is not a coherent history edit.                                                                           |
| Custom       | Freeform text, named concerns, traits and numeric/qualitative fields with chosen input placement                                                                       | Model-input-only information has no native mechanic unless the installed engine supports one.                                          |

Numerical controls pair a compact slider with an exact-value field, authored units, meaningful endpoints and reset. Keyboard entry and step controls remain available; dragging is never the only route. Preserve incomplete numeric drafts. A slider previews during movement and stages its final value on release; it does not dispatch cognition on each pointer movement. Fixed or derived values are labeled and link to their actual contributors instead of presenting a misleading writable total.

Text fields keep short inline previews with a clear edit affordance. Opening a large text field gives it a focused editor within the current pane or one explicit editor modal when simultaneous context is valuable. It does not push the category navigation or Apply controls offscreen. The full value remains searchable, selectable and copyable; preview truncation is not storage truncation.

Traits and installed definitions use editable comboboxes or named searchable pickers according to the shared control contract. Freeform entry remains available as an explicit **Use custom text** choice when it is descriptive information; it cannot silently create an installed executable capability with a similar name.

### Dynamic editor contract

Installed field descriptors supply label, value type, units, range/options, writable or derived status, help and native owner. The UI renders those descriptors rather than hard-coding a special form for every possible feeling or body. It must not omit an installed field because its name is unfamiliar. An unavailable native editor is a visible capability state, with its actual value inspectable and a source link where available.

| Field shape                                   | Default compact control                                              | Disclosure and validation                                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Bounded number                                | Slider plus exact input                                              | Units/endpoints visible; native validation and missing/unknown state retained.                               |
| Unbounded number or duration                  | Exact input plus unit/clock selector                                 | No arbitrary slider ceiling; simulation duration is distinguished from real time.                            |
| Boolean                                       | Small named toggle                                                   | On/off meaning and inherited/unknown status are explicit.                                                    |
| Fixed enum                                    | Compact segmented control for a small set; combobox for a larger set | Current value remains visible; no scrolling strip of fixed options.                                          |
| Tags or references                            | Searchable multi-select with short chips/count                       | Typed identity bindings, not name-only strings; full selected set is reachable directly.                     |
| Short text                                    | Inline input                                                         | Preserve draft until apply; no change on blur if the enclosing transaction is not committed.                 |
| Long text                                     | Readable preview and focused editor                                  | Full content is editable/copyable in one action.                                                             |
| Growing record collection                     | Searchable table/list in the category's one body                     | Add/edit/remove with a stable field schema and explicit affected record.                                     |
| Structured value without a specialized editor | Labeled advanced structured editor                                   | Preserve complete supported content; field-path errors retain the draft. Never silently flatten or truncate. |

Custom entries have a name, type, value, explicit subject/scope, recipient actors and supported stage placement. Scopes are this person, a directed relationship, an object or the scene. Person and directed-relation additions default to the owning actor only; object and scene additions require chosen recipients. Nothing defaults to every actor. The editor shows where the addition will enter model input, or why the selected call will not include it. The persistent **Model input only** label distinguishes a custom fear, skill claim or invented concern from an installed effect. Exact inputs on the right show whether it was actually included. Source labels such as story premise, private belief or observed description explain the experiment; they do not grant physical truth or native perception. Deliberately adding another recipient is a recorded intervention. A custom number need not have a decay rule, and a qualitative attachment need not have a number. Removing a custom input removes that input; it does not reverse unrelated native effects.

### Drafts, application and invalidation

Related left-panel edits are staged in named Apply groups that the owning mutation can commit atomically. **Apply** and **Discard** appear in a reserved fixed footer without moving the category body. Switching categories retains the draft. The footer names its subject/group and changed-field count; it never silently applies hidden drafts for other people. Groups without a shared atomic owner have separate visible Apply actions and results. Applying reports actual resulting values and dependent changes and invalidates affected prepared input.

An edited field is visibly marked Draft until application; its accessible description distinguishes the last applied value from the proposed value. The left panel's Current label names the scenario it edits, not a claim that an unapplied number is already active. The footer's dirty count remains visible while another category is open.

Changing inspected character preserves that character's staged draft; a compact elsewhere-dirty count opens its named groups and subjects. Commands use applied values. Before current-world Submit/Prepare/Continue/Step/Run/Advance or Save scenario/checkpoint, any scenario/settings drafts trigger one compact review: **Apply edits and continue**, **Use applied values**, or **Cancel**, with the exact affected groups shown. A single Apply-and-continue is available only for a supported atomic group; otherwise show each owner's Apply and enable continuation after the selected groups succeed. Accepted groups remain visible if another fails, and the pending command does not execute. Do not infer draft relevance by running perception or cognition. Recorded inspection, retention and annotations need no such prompt. Replacement identifies drafts that would be discarded; navigation alone never asks. Conflicts show affected fields against current values without silent overwrite.

If an experiment is active, the developer can read current values and prepare edits. Apply explicitly reaches the normal safe Hold, settles admitted work, revalidates the affected fields and commits or reports a conflict; the run remains Held. Only an explicitly selected Apply-and-submit continues the selected intention after successful edits. Show what is waiting and keep Stop/cancel reachable. Ordinary live ticks and status updates do not make an untouched draft or the Stop control stale; actual changed-field/source conflicts still matter. The technical design owns those separate revision checks.

A normal edit changes the value once. An explicit **Hold during this experiment** field-menu option is available only for supported directly writable fields and is marked as an intervention in run settings/results; it does not pretend to be natural game decay. The native field owner must implement a truthful hold at its actual mutation boundaries. Unsupported holds show unavailable rather than repeatedly overwriting arbitrary state on a timer or repainting a fake constant. Holding a calculated value is unsupported. Reading the field or opening its slider does not hold it.

### Memory, history and world authoring

The developer can fabricate starting experiences, alter past speech, add/remove memories and set a mistaken belief deliberately. Existing actor-scoped editing/forgetting owners handle supported operations and invalidate dependent summaries/feelings/search material where required. The editor displays the affected scope before application when the edit changes more than its own record.

Creating a revised starting situation is distinct from rewriting a completed run's recorded evidence. Substantial authored-history changes create a revised current scenario or continuation with the intervention recorded; previous completed run results remain what actually happened. There is no requirement to retain incompatible development saves or build a general historical reconciliation system.

Changing a world fact does not automatically rewrite personal knowledge to agree. Removing an attacker can leave Ada uncertain about where they went. Conversely, editing Ada's belief does not move the attacker. Surroundings editing keeps these two operations explicit.

### Emotion presentation

Present bodily reactions, private feelings and derived consequences in separate compact subsections. Every feeling row shows its readable meaning/target, value where applicable, current status and a direct source link. A selected row exposes cause, sources, creator/model origin, lifetime/recovery rule, last accepted change and pending reassessment. Several fears or concerns can coexist; a qualitative grief record does not gain a fabricated numerical meter.

Effective totals follow the installed emotion owner. Under the referenced proposal, effective fear uses the strongest contributing fear, not the sum of every fear record; the derived bar links to contributors and is not freely editable. A physiological arousal value, a particular fear and qualitative grief must not collapse into one mood score. The lab exposes the installed aggregation and decay rules without inventing a new formula or treating the proposal as implemented.

The referenced [emotion proposal](https://github.com/Macrofold/OpenLegend/blob/codex/design-stealth-02-emotions/docs/projects/emotional-physiology-feature-spec.md) is a dependency design, not delivered physiology. Unsupported emotion definitions show a clear unavailable/native-support distinction while custom descriptive input remains usable. One native startle can end while interpreted fear remains; calm speech does not establish absence of fear. The lab must expose those differences without requiring a review operation to invent a fictional thought.

## 6. Event timeline and composer — center panel

The center is a chronological event timeline, not a synthetic two-person transcript. It presents actual speech, attempted/started/completed/interrupted actions, authored private character thoughts, environmental events and optional internal changes. Technical operations never become invented dialogue or thoughts.

Each row has a compact type icon, actor or subject, short content, outcome and game time. Target, volume, hearers and detailed attribution are directly available on row selection and concise hover/focus detail. A speech's intended addressee is not its set of hearers; partial heard text remains partial for the selected observer. An explicit perspective control chooses **Scenario events** or **What this person perceived** without changing any character's knowledge.

The default feed emphasizes speech and actions. Thoughts, internal changes and technical events have fixed small filter icons with counts and pressed states. Failure and rejected-attempt markers remain visible when their parent event is shown. Search, clear, filters, Follow latest and result count stay in the timeline toolbar. New content does not steal the reading anchor; the existing new-events affordance returns to the bottom.

### Composer

The composer is fixed below the timeline and has a reserved, compact height. Its top row contains **Say / Act / Event**, actor, target and applicable parameter controls. The text field begins at one line and grows to four visible lines; beyond that the text field itself scrolls while actor/target and Submit remain fixed. This is the center's only nested input scroller, not an additional content panel; a focused-editor action gives longer writing full space. The timeline height does not change on each incoming event.

**Say:** actor, optional target, installed speech volume and text. Normal directed player speech uses the game’s actual conversation route, including its real hearing and response eligibility. Target can be none/ambient when supported. Another character may be the speaker through explicit operator authoring without transferring long-lived human control; the resulting source remains labeled as an intervention.

**Act:** actor, typed supported target(s), searchable installed action or freeform text, and only parameters needed by that selected action. The picker exposes Available and All installed views, with known blocked reasons. A separate inspectable comparison shows which actions the character's actual decision received. The lab uses the game's exact interpretation, proposal review where required, availability and execution. Unsupported freeform text remains editable and produces the real unsupported result, not fictional success.

**Event:** supported native scenario events or explicit authoring of personal experience. The editor names whether it changes scenario reality, supplies perceived evidence or adds a private belief/experience. It cannot silently convert arbitrary prose into physical effects or disclose it to every character.

An action/event with more parameters than fit the reserved composer uses one **Details** action to replace the center's content body with its form, retaining the fixed mode/actor/target and Submit controls. A fixed Back to timeline control restores the timeline anchor. It does not grow the composer, append another scrolling panel or nest a modal inside a picker. The selected action summary shows any missing required parameters before submission. A picker with a genuinely growing option set uses one transient searchable list; opening a picker never creates a second permanent panel.

The primary action is **Submit**. The adjacent **Edit next input** utility opens the prepared-call flow without running it. Stop/cancel remains in the fixed experiment strip, not substituted for Submit while a read is pending. Drafts are scoped by scenario, composer mode, actor and target; changing a selection never submits. Confirmed native acceptance of the speech/action/event clears only the exact submitted draft revision. A later failed character response does not make that accepted stimulus unsent. Refused source submission preserves the draft; uncertain source acceptance retains it while reconciling the original command, with new submission blocked until that outcome is known. A native **Retry response** action, when actually eligible, reuses the accepted source and never speaks or acts again. IME confirmation, combobox Enter and modal Enter do not accidentally submit the outer composer.

## 7. Decision inspector — right panel

Before an experiment is selected, the inspector shows its compact chronological trigger list. With Follow latest enabled, a newly submitted experiment opens its Overview and result strip directly; the list remains one Back action away. Each detected meaningful opportunity remains inspectable even if no model call ran. The list gives actor, trigger sentence/type, response summary, result and time; supporting technical calls are children of their actual root, not numbered peers.

Selecting a root replaces the list with its detail. Selecting a call or context collection replaces the detail body, preserving the fixed inspector controls. Use Back and breadcrumbs, never stage accordions as the primary navigation. A fixed root/call selector supports jumping directly among neighboring roots and stages. The developer can pin an inspector selection while subsequent events continue; this freezes only the inspected record.

### Result summary and sections

The persistent result strip names the character, trigger, captured game time, actual disposition and capture completeness. It displays the most useful immediate output or failure. Below it, fixed section controls select **Overview**, **Inputs**, **Choices**, **Changes**, **Calls** and **Timing/cost** when applicable. The controls do not move when body content expands. Unavailable sections remain discoverable with an explanation rather than vanishing and shifting other controls.

Overview shows the causal facts at readable scale: stimulus, actual perceived content, decision/no-decision outcome, proposed versus accepted response, and consequential changes. Native action progress links to the actual activity outcome; successful speech cannot make a failed action look successful.

Inputs organizes the selected call's captured context into direct sections: character identity/self-understanding, needs/body, concerns/feelings, surroundings, goals/current work, possessions/techniques, relations/commitments, recent events and memories. A section's visible header shows included/omitted/unavailable counts where actually captured. Selecting the section opens its collection directly. Full selected memory content appears directly in the row detail; source provenance is supporting detail, not an obstacle to reading the content.

Choices presents the actual question, offered choices, returned ratings and selected route/action together. A rank, relevance score or answer probability is labeled by its actual meaning; it is not a calibrated probability that the behavior is psychologically correct. Show mechanically available, retrieved, offered, proposed and accepted choices as distinct statuses where captured.

Changes presents before/after values and links each to its recorded cause and accepted operation. A proposed value, rejected value and current live value never substitute for the historical accepted value. This view does not write back to the left panel.

Calls presents the actual dependency order and parent links, including parallel or background work where present. It does not draw a fixed invented pipeline. Every recorded call is shown once, with model/configuration, purpose, state, request/response and applicable usage. Reflection and later reconsideration link to their originating run and retain their own time/status.

Timing/cost separates simulation progress, preparation, queue wait, provider duration, acceptance and real elapsed time. Show known actual charges, estimates and unknown/pending usage distinctly, including supporting and background work attributable to the run. Refreshing billing is read-only; it does not rerun cognition.

### Missing decisions and incomplete evidence

The inspector differentiates: not perceived; no qualifying opportunity; native-only handling; inputs combined; deliberately continued; deferred; cancelled; stale; invalid; unsupported; rejected; failed; uncertain; budget/service unavailable; and capture missing. Display actual recorded reasons, never a generated retrospective explanation passed off as causal evidence.

A record not selected may be unexamined, ineligible, outdated, unavailable, excluded by actual selection, or omitted because of an explicit bound. The UI must not label all missing records irrelevant. Search coverage, index lag and missing captures remain visible. Complete captured game steps and exposed provider outputs are the inspection goal; provider-internal hidden reasoning is not promised and is separate from fictional private thoughts.

### Payload access

Fixed **Input**, **Output** and **Full request** actions open a focused modal with readable formatting, find, wrap, copy and optional original/edited comparison. Full request names the actual operation and includes submitted instructions, context, questions/options, references and output/tool schema. Supplemental model-readable inputs, such as a reflection's accepted mind files, are directly accessible within Inputs and counted in completeness; a JSON context alone is not their full input. Application-prepared and provider-transformed input stay separately labeled. Sanitized, partial, expired or unavailable content says so explicitly, including current disclosure restrictions; no credential is displayed.

The fixed call selector always names the call these actions address. Selecting a root initially chooses its recorded primary response stage when unambiguous: the generation that produced the accepted response, otherwise the decision/routing stage that owns the recorded disposition. This is derived from captured result ownership, not array order or the most recent supporting request. If no unique primary exists, the same control shows **Choose call** with the actual named stages and purposes. Choosing one is the only extra navigation step; no new pane or accordion opens. A root with no model call has a visible native-only/no-call explanation and no fabricated payload.

## 8. Prepared-input editing

There is no single static payload representing every possible call after a Say/Act. The modal targets one actual prepared call. Opening **Edit next input** from an idle composer shows a preparation sheet with actor, supported stopping point and an explanation of any preceding native work; opening it does not submit or spend. Its default is the next focal character's decision/judgment/generation request for this reaction, not the first supporting embedding or query-preparation request. The selected stage rule and purpose are visible before **Prepare and hold**; the actual resolved call/stage is named at the gate before its own dispatch. An advanced stage selector can deliberately target other supported calls, including embedding or reflection, without making that the ordinary speech path.

**Prepare and hold** explicitly submits the source event once and runs the ordinary game preparation until the selected call is ready. Required earlier paid preparation remains visible in the run and is not described as a free preview. A no-perception/no-decision/native-only result terminates truthfully rather than inventing a model request for the modal. An idle context preview, if provided, is labeled an estimate and cannot masquerade as the exact prepared request.

The modal header identifies actor, stage, captured scenario/time and whether this is a **Held live call** or **Recorded request rerun**. Original input is retained for comparison. Editing is fully freeform within the supported model-facing request contract; malformed or unsupported structure yields a precise validation result and retains the draft. The editor does not grant new native entity references, tool authority, credentials or execution permissions. The normal response parsing and native checks still apply after a live model response returns.

**Submit this input once** is the only action that sends the edited payload. Closing or cancelling the editor discards its override draft and leaves the real call **Held before [stage]**. It does not dispatch the original, cancel the entire run, erase an already accepted source event or discard unrelated composer text. The fixed **Edit input** action reopens that same valid held call without preparing or submitting anything. **Continue original** deliberately dispatches the unmodified prepared call; **Stop** applies the native cancellation semantics and invalidates its handle. Ordinary composer Submit is never redirected to override text.

Applied scenario edits invalidate the held request. Its view shows the actual reason and preserves any open override text only as a stale draft for comparison/copy. **Retry response** is offered only when the native owner reports an eligible same-source retry; it revalidates current evidence and explicitly incurs any new preparation/call cost, without repeating the accepted speech or action. Otherwise offer **Run scenario again** from the captured origin or **Return to composer** for a deliberately new stimulus. A whole-scenario rerun identifies the origin and recorded sequence it will restore, including whether a newly applied edit is selected as an explicit variant; it never silently discards that edit or claims to retry the same live call. There is no generic Prepare again action that resubmits an already accepted source.

The selected execution boundary holds the scenario consistently while the request is being edited. The payload editor is a true modal: its background is inert and focus stays within it. Close it to read or edit other panes while the original call remains held; reopening uses that same handle unless an applied edit has invalidated it. The technical design owns cancellation and continuing pending work; the UI must not emulate a breakpoint with ordinary game pause if that changes the work being inspected. Operator hold duration is displayed separately and excluded from ordinary production-latency interpretation. The game in the other tab remains independent.

Historical actions have distinct labels and guarantees:

| Action                   | What it does                                                                                                                     | What the result means                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Replay recorded run      | Displays captured events, requests and outcomes without dispatch or mutation                                                     | Evidence of the original run.                                                                                         |
| Rerun request            | Submits a fresh request from recorded input, with current provider/schema validation; defaults to request-only comparison        | New output for that captured input. No claim of fresh perception/retrieval, native action execution or world effects. |
| Continue from checkpoint | Continues a fresh call result through normal native admission from an actually captured compatible checkpoint at that breakpoint | A new scenario continuation with new accepted outcomes; the old result is untouched.                                  |
| Run scenario again       | Restores the selected coherent origin and executes the full event/preparation/decision sequence again                            | New whole-scenario behavior, including whatever context the normal game selects now.                                  |

**Continue from checkpoint** is unavailable when no actual breakpoint checkpoint was captured. Its inline explanation offers **Run scenario again**; the UI never reconstructs executable history from a request alone. Request-only rerun and live one-shot override are therefore visibly different modes. No historical action receipt is executed merely by replaying a recorded result.

## 9. Experiment controls and saved work

The experiment strip provides compact **Run / Hold**, next-event/next-decision step, run-until selector, game-time advance, **Stop**, autonomous-participant chooser and current experiment status. Hold requests the lab's safe execution boundary; it is not the native manual pause operation that may cancel work. Native pause is an advanced operation with its actual cancellation semantics explained. The normal interaction uses the default response boundary without configuring these controls. Keyboard focus and shortcuts do not enter the world while typing.

The compact **Wait for: [person]** picker remains beside the run-until condition. Its focal actor determines which immediate response One response waits for; it does not select the left editor, change the speaker/target or grant autonomy. When the addressed person differs, keep the chosen waiting condition visible and provide a small **Wait for [addressee]** utility; do not silently retarget or require a confirmation. A targetless ambient utterance or an Act/Event submission retains this explicit focal actor. If that person cannot perceive the stimulus or is ineligible for autonomous consideration under the native policy, the run reports that real disposition rather than choosing another person or waiting indefinitely. Manually directing the focal actor to perform an action remains a forced source action, not evidence of an independent choice. Autonomy defaults to the ordinary scenario's eligible participants; limiting that set is an explicit recorded intervention.

The run-until selector names its actual stop condition: One response, Next event, Next decision, Selected action outcome, Chosen simulation time or Until stopped. Unsupported conditions are explained rather than approximated. The selected focal actor and any target action remain visible. Each mode uses the finite allowances in CLL06 and shared spending rules. **Continue** renews the displayed allowance explicitly within the same retained run; there is no automatic loop when a guard is reached. A continuous experiment retains a reachable Stop control even when a read or model request is pending.

One response completes an interval and leaves the run **Held**, preserving a natural conversation. Another submitted stimulus or explicit Continue can add to the same episode; it does not rewrite finalized stages. **End run** closes a held episode; **Stop** closes an active run after native cancellation/settlement. Reset/load also closes the prior episode before replacing its scenario. The visible lifecycle is Ready, Running, Held and Ended, with the actual held/stopped reason beside it. While admitted work settles, show **Finishing current work**, or **Stopping** after Stop, before reaching Held/Ended; this is the technical design's Settling state, not another state owner. The developer need not create, name or retain a new run for each sentence.

Time advance uses simulation time and the installed world clock, with normal-play duration labels when appropriate. Real model latency never becomes an emotion's duration or unrequested world catch-up. Reading an old run or stopping follow does not freeze the world. Cancelling a pending request is distinct from pausing simulation and preserves the actual outcome/usage uncertainty.

Starting a new run automatically captures its actual applied starting state once, without a name/save dialog, so unsaved applied edits are included in Run scenario again and matched comparisons. A later utterance or Continue in the same held episode reuses that origin and records the ordered stimuli/interventions; this is not a full-world copy per utterance or model call. Failed origin capture preserves the draft and exposes the concrete storage/setup error before execution. **Reset** names and restores the selected run origin or saved scenario start; **New** initializes a fresh scene from the current world definitions.

Save operations distinguish **Scenario** (a fresh reusable starting setup), **Checkpoint** (a coherent running situation to resume), and **Run** (actual recorded inputs/results/diagnostics). Each action has a named destination and truthful saved/failed status. A coherent starting/continuation save includes the native people, objects, histories, relationships and work together with that moment's custom inputs, supported value holds, autonomy/participation and model/run settings. Reset/rerun restores this combination before declared variant changes, rather than keeping later custom inputs attached to an earlier world. It never rewinds spending, current permissions or paid-call receipts.

New opens a compact scenario picker with the current world's standard starting definitions, saved scenarios and explicit one-time copy from an authorized current game. Creating a custom small scene uses the same source definitions and shared scenario authoring. The source game is unchanged. No ongoing synchronization is configured.

Restoring a checkpoint is explicit and changes current scenario values. It does not silently resume paid work, replay accepted effects or restore a live provider session. A completed run can be viewed without a model call where current source permissions still allow it. **Run again** requests fresh responses; **Replay recorded run** displays recorded outcomes. **Rerun request** is available only when the actual operation and all supplied inputs can be reproduced without native or shared-workspace effects; otherwise explain the missing capability and offer a supported scenario rerun. Same native randomness does not guarantee identical fresh model text.

The save menu offers **Save scenario**, **Save checkpoint**, **Retain run**, **Export** and **Import** with short descriptions of these different objects. Save uses the current applied state; if drafts exist, the choice is explicit. A proposed name is editable, with no mandatory metadata form. The searchable saved-work picker shows kind, name, originating world, creation/update time, short scene/run description and compatibility or capture-completeness status. Opening a run is read-only; loading a scenario/checkpoint explicitly replaces the active lab scenario. These actions do not silently affect game saves.

Export writes the selected current-format scenario/checkpoint/run bundle with the native dependencies and captured evidence required by its kind; it excludes provider credentials and unrelated gameplay data. Import validates kind, structure, required definitions and current compatibility before replacing anything. It shows the selected item's name and relevant included people/objects or run count, reports concrete missing dependencies, and rejects incompatible data without a migration wizard or lossy fallback. Imported recorded evidence remains recorded evidence; importing it does not execute a request. Partial or unavailable captures retain their status in exported and imported results.

Lab settings open from one fixed header action. The initial view contains active run policy, autonomy, installed model/routes and spending/stop limits. Deeper model, prompt/question or request-setting experiments are grouped by their actual stage and searchable where the collection grows. Apply at Ready/Held takes effect for the **next response or run interval**, including a follow-up sentence in the same episode; Running first reaches the normal safe Hold. Applying settings alone starts no work and renews no allowance. Distinguish Draft, accepted next-interval settings and a selected result's actual settings. Record changes as interventions, invalidate affected prepared input, and retain earlier intervals' settings. Named variants use the same behavior. No extra End run step is required. Game settings, credentials and already-dispatched requests stay with their owners; unsupported combinations report the real validation error.

## 10. Comparison and character-quality workflow

The developer can save a starting situation, run an interaction or short authored event sequence, restore it, change one factor and compare the resulting episodes. Compare opens a dedicated workspace in the center/right area while the current-character editor remains current and clearly labeled. A fixed comparison header identifies the two runs, their starting situations, configuration and interventions. Returning preserves normal pane selections and drafts.

Variant execution restores the same complete origin before each serial run and applies only its declared differences. When the final variant finishes, the active scenario remains at that variant's actual resulting state; the left label identifies the variant/run. **Restore starting checkpoint** is explicit. Merely opening A/B comparison changes no scenario. Adding a third variant uses the same named comparison selection rather than opening more permanent panes; two chosen results are visible at once.

The comparison shows the effective starting inputs, not just a shared save name. If current native forgetting/privacy rules remove evidence after that save, identify the difference before executing and offer an explicitly unmatched run or a new comparable origin. Retained input cannot be used to bypass those rules. Accepted saved mind files can seed a fresh supported reflection; old provider sessions and hidden remote history are not replayed as equal starting state.

Match events by authored sequence position/actual relation, not by assuming identical output counts. Side-by-side timelines may scroll together when matching anchors exist; unmatched events stay visible and labeled. A selected comparison shows speech, actual actions, accepted changes and later behavior, with direct access to each run's exact input. It must not silently place the historical comparison value into the current left editor.

Optional evaluator notes and expectations are saved with the run, outside model input. Useful labels are In character, Inconsistent, Unclear and a freeform note attached to evidence. A memorable joke, decisive act, pleasing silence or useful refusal can be marked at its actual event and found again through saved-run search; this is an annotation, not a new score or reward system. A required product behavior can be an acceptance criterion without becoming a hidden prompt instruction. For the specified able, informed Ada after an unprovoked punch, the existing requirement for independent counterattack remains distinct from a manually forced attack.

The creative coverage set includes a meaningful invitation/refusal, a personal interest or joke, real help with competing work, a credible threat and aftermath, mistaken or partial information, an ordinary enjoyable interval, and a later encounter where memory can matter. More vivid expression is not always more words: quiet delight, dry humor, decisive action and silence can be the characterful outcome. The [repertoire-derived episode cards](cognition-lab-repertoire-review.md#repertoire-derived-episode-cards) are a searchable authoring/reference bank, not twelve mandatory shipped presets, a new forced behavior taxonomy or a reason to install every repertoire mechanic. Existing CE/CTR/evaluation flows own behavioral acceptance. Only a materialized scenario whose dependencies are installed can appear as a runnable preset.

The most useful creative experiments hold recognizable human meaning constant while changing one consequential fact. A remembered terrible song can be a welcome recurring joke with one friend and baffling noise to a newcomer; a declined loan can coexist with an invitation to dinner; a sad song can be chosen pleasure rather than a problem to solve. Those examples already exist in the [catalogue coverage](cognition-lab-repertoire-review.md#catalogue-coverage). Their lab value is quick access to particular history, actual perception and later independent behavior, not additional sliders for universal friendliness or happiness.

The comparison retains actual model/route settings, prompt/question variants, authored rules, starting state and manual interventions. Evaluate one relevant difference at a time, preserve unsuccessful runs and keep acceptable alternatives visible. A model's eloquent self-explanation is not proof of why its earlier action occurred. Full cost includes failed/deferred/supporting work; no single pleasing line establishes sustained character quality.

## 11. Common state and recovery rules

Initial loading uses the shared delayed loading treatment without fabricating scenario values. After a same-scenario view is populated, refresh preserves layout and readable content. Empty, filtered-empty, unavailable, partial, stale, failed, pending and completed states have distinct wording. No unknown meter becomes zero and no missing trace implies that nothing happened.

| State                                             | Visible explanation                                                                                           | Available next action                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| New compatible scene                              | The current person and ready composer; an empty feed says no lab events yet                                   | Type and Submit; no onboarding gate.                                                                                    |
| No records in a category                          | The category's real empty state, such as No memories yet                                                      | Add where supported, or continue the experiment.                                                                        |
| Search has no matches                             | No matches for the visible query; any known unfiltered total stays available                                  | Clear query/filter.                                                                                                     |
| No eligible actor or missing starting definitions | The concrete unavailable actor/definition, without placeholder meters                                         | Choose/add a compatible actor or resolve the named definition.                                                          |
| Waiting for native/provider work                  | Actual stage and wait reason; elapsed time/cost status where known                                            | Inspect other evidence; Stop where supported. Do not claim the character is thinking unless a fictional thought exists. |
| Held at a prepared call                           | Held before the named stage                                                                                   | Edit input, Continue original, or Stop.                                                                                 |
| No response                                       | The actual recorded distinction: unheard, no decision, continued work, rejected action, or other owner result | Inspect the directly linked evidence; modify the scene or continue deliberately.                                        |
| Guard reached                                     | Run limit reached with the actual exhausted allowance                                                         | Continue with the displayed renewed allowance, change bounded settings, or End run.                                     |
| Incomplete capture                                | Which request/input/stage is unavailable and why, when known                                                  | Read remaining evidence or run a fresh experiment; never infer missing values from current state.                       |
| Request/save outcome uncertain                    | The known confirmed portion and the unresolved operation                                                      | Reconcile the existing operation before a fresh retry.                                                                  |
| Connection lost or revision conflict              | Last confirmed values labeled stale; explicit affected draft/operation                                        | Reconnect/reload current values or resolve that conflict; no speculative successful mutation.                           |
| Incompatible saved item                           | The current-format or missing-definition reason                                                               | Choose another item or create a fresh scene; no compatibility wizard.                                                   |

These are meaning requirements, not a vocabulary list to expose internal enum names. Apply the [player-facing language standard](../ui-ux/player-facing-language.md) to this developer surface: name the actor, operation, actual result and useful next step in plain language. Technical detail belongs where it helps the experimenter act.

Each mutation has one owner, one explicit commit and one truthful result. An uncertain network result reconciles the original request before offering a fresh duplicate. Selection, searching, hover and pane resizing never commit. Cancel remains meaningful and available at the owning operation where supported. A routine reversible edit does not need repeated confirmations; replacing the current scenario or deleting a named saved item has an explicit consequence.

Live updates preserve selection, focus, text selection and reading anchors. They do not reorder the row under a pointer or clear a new draft when an earlier request completes. Losing scenario authority clears protected detail and blocks commands. Browser Back is navigation, not simulation rewind. Private input and hidden character information do not enter sharable URLs.

Light mode is local to this developer workspace, using the existing design system's semantic controls, spacing, icons and focus behavior. Neutral light surfaces, dark readable text and restrained existing accents support density. No decorative card grid, large marketing headings, illustrative art or theme-production dependency belongs in the ordinary lab workflow.

### Accessibility basis and qualification boundary

The selected 28 px controls exceed WCAG 2.2's 24 CSS px minimum-target dimension, subject to its actual criterion and exceptions; that does not by itself establish accessible rendering. The [WCAG target-size explanation](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) informs the compact-target choice. The [WAI-ARIA toolbar pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) informs the grouped keyboard navigation. The [tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/) is explicitly a work-in-progress supporting pattern; it does not certify this design. Open Legend's shared controls and CL11 qualification still own actual focus, semantics, contrast, zoom, clipping and assistive-technology behavior. None of these sources establishes that the chosen density is optimal for Mike; that must be evaluated with the real task.

## 12. Acceptance journeys

The final implementation must be qualified through the connected tasks and concrete UI checks specified in the maintainer tracker. A typecheck, fixture payload or attractive screenshot does not establish usability or autonomous character quality. All journeys must retain the independent inspected person, event actor, target and autonomous participants, plus the explicit focal actor in run policy. A view selection must never silently change any of the other roles.

| Journey                          | Required visible outcome                                                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Open and speak                   | A compatible default scene reaches a ready Say composer without a setup wizard; one submission produces an attributable event and response/no-response explanation.                  |
| Inspect history while running    | Selecting an earlier decision displays its captured inputs on the right; the left continues to display current values and remains an editor for the current scenario.                |
| Change a need and repeat         | Stage/apply a numeric change, reset or branch deliberately, rerun the same event and compare actual behavior; the meter's authored direction and native consequences remain visible. |
| Edit personality and recognition | A freeform trait edit and an acquaintance binding remain distinguishable; the character's actual input identifies only the names they know.                                          |
| Observe emotion sources          | Bodily reaction, interpreted feeling and derived effect remain separate; qualitative feelings retain qualitative presentation.                                                       |
| Explain silence                  | Hearing failure, deliberate continuation, native-only handling, unavailable service and rejected result are distinguishable without reading an undifferentiated log.                 |
| Inspect one missing memory       | Search reaches the memory, its content and its actual inclusion/exclusion/coverage status with at most the selected shallow access path.                                             |
| Override a prepared request      | Only modal Submit uses edited input; original/difference are retained; a left edit invalidates the request; normal Submit uses current scenario information.                         |
| Author past speech               | Changing words, attribution or hearers updates the intended scenario through the owning history/experience rules and reveals relevant dependent invalidation.                        |
| Compare an episode               | The same starting situation and event sequence support a one-factor comparison with later consequences, separate expectations and recorded-versus-fresh replay.                      |
| Use a large dense workspace      | At 1920 × 1080 and 2560 × 1440, fixed controls remain visible while long collections/text scroll in their one owning body. No control moves because a record expands.                |
| Use keyboard and long content    | Long names, multiline text, no results, disabled actions, popup boundaries, focus, IME and enlarged text preserve the same task without accidental submission or clipped controls.   |

### Required end-to-end qualification details

1. **Ordinary speech has no setup detour.** From the standard ready scene, leave every default unchanged, type one greeting and Submit. The source event appears once, the focal result's Overview becomes visible without opening a modal, and the response boundary holds. The full accepted words/action status and actual no-response/failure explanation appear in the body beneath the compact status strip, with no extra navigation or clipped reply. No rubric, variant, checkpoint or raw input is required. A later response failure leaves the already accepted utterance visible and does not restore it as an unsent draft.
2. **Inspection cannot alter the experiment's identities.** Speak to Ada with Wait for: Ada selected, inspect another person, select an older Ada decision and let current work continue. The left shows the newly inspected person's current values; the right retains the older captured values; speaker, target, autonomy and focal actor remain unchanged. A targetless next utterance still uses the displayed focal actor. Select a historical call with several siblings and verify the payload header identifies the actual chosen stage.
3. **The next useful fact stays shallow.** From a reaction result, open its Memories link, select one memory and read its full content. Return once and retain the query and row anchor. Open Choices directly and see the actual question/options/ratings. Switch to Changes and verify recorded before/after values rather than current left values. If there is no unique call, the one explicit call chooser is the only added step.
4. **A draft is never a hidden experiment parameter.** Change a need, add a custom private belief and move to another category. Both drafts remain marked and the count persists. Submit must resolve whether to apply drafts or use applied values. A clean application records only the intended fields, shows model-input-only versus native effects, and invalidates any existing prepared-call handle. A hold on a derived or unsupported field is unavailable with its native reason.
5. **One-shot editing is exactly one shot.** Opening Edit next input sends nothing. Prepare and hold submits the source once and stops at the first matching focal decision call, not a supporting embedding. Edit text, close the modal and verify no dispatch; reopen the same handle, then Continue original sends the original. In another held experiment, close the modal, apply a left edit and verify the old payload cannot submit. An eligible native Retry response reuses its source; an ineligible case offers the explicit whole-scenario rerun or a new composer stimulus and never duplicates the old source. A valid held call's Submit this input once retains original and edited input, then later ordinary Submit uses current state. If no matching call occurs, show that actual terminal disposition.
6. **Request rerun cannot impersonate game execution.** Select a historical call without a breakpoint checkpoint and Rerun request. Its new model output is inspectable, but no native action or world mutation is claimed. Continue from checkpoint explains why it is unavailable and offers a full scenario rerun. A separate case with a real compatible checkpoint continues through normal admission and produces separately attributed accepted effects.
7. **An action can begin without being finished.** Submit a source event that yields a real durative action. One response ends its interval at decision publication and shows Started/Pending with the actual action link. Advance to outcome uses the native clock. A guard hit says Run limit reached and requires explicit renewed allowance; no automatic loop or invented silence occurs. Stop remains available while provider work is pending, with uncertainty/settlement reported truthfully.
8. **Comparison preserves the life around the line.** Run a short interaction, intervene in one saved factor and execute a second variant from the same complete origin. Compare actual speech, physical behavior, changes and a later encounter. Expectations and annotations do not enter either model input. A/B run serially; after B, left Current identifies B's actual ending state. Opening A's captured inputs does not restore A. Restore starting checkpoint is a separate explicit command.
9. **Dense content does not move essential controls.** At both reference viewports, populate long histories, many memories, long traits, numerous current concerns and a large payload. Search and all execution/editor controls remain reachable in their fixed regions. Scroll each collection once through its own body; no inner record list traps a second wheel scroll. An input editor's own scrolling is confined to editing. Pane focus, resizing, text zoom and return preserve drafts and selection. Tooltips are discoverable through focus without being the sole source of essential meaning.

The qualification report must record observed behavior and unresolved failures. These are acceptance journeys to implement and exercise, not claims that the current application already passes them.

## 13. Delivery shape and boundaries

Deliver a useful vertical slice through CL01–CL02 plus the minimal CL04 ordinary-speech intake, CL05 result summary, CL06 finite One response/hold controller and CL08 actual applied-origin capture: isolated current-engine scenario, three stable panes, ordinary speech and a readable result that stops predictably and can be repeated from its real starting state. The first slice does not require advanced stepping, arbitrary breakpoints, the complete saved-work manager or import/export. Continue through the complete selected lab scope: CL03 editors/custom fields; full CL04 Say/Act/Event semantics; full CL05 captured inspection; full CL06 execution control; CL07 exact one-call editing; full CL08 scenario/checkpoint/run persistence and import/export; CL09 serial comparisons and annotations; CL10 installed emotions/background maintenance; and CL11 usability, performance and shared-engine parity qualification. CL00 records design completion only. Staging implementation does not weaken the accepted product contract or relabel unfinished requested capabilities as optional.

The lab does not itself implement the broader emotion, speech-streaming, combat, personality-development or context-selection projects. It consumes their shared capabilities as installed and exposes truthful unavailable states. Missing shared instrumentation or narrow scenario-control seams needed for this lab are implementation work in its technical design and tracker, not permission for a second cognition framework. Broader gameplay feature gaps stay with their established owners.

## 14. Decision status

The selected layout, light palette, current-left/historical-right boundary, shallow disclosure, isolated data, prepared-call editing and current-format-only storage are product requirements. Default widths, density and initial run behavior are reversible design selections to qualify with Mike's actual workflow, not measured usability claims.

Direct human control's emotion policy on the referenced emotion branch remains an external unresolved decision. This lab does not settle it: event authorship and inspection do not transfer control. An extension that deliberately tests direct-human-control cognition must use the eventual owning policy rather than inventing a lab exception.

Any remaining question that actually blocks an implementation decision must be recorded in the canonical decision owner and resolved before dependent work. Browser/runtime/model-quality acceptance is unperformed implementation work, not an unresolved product-choice label.
