# Reusable verification workers — technical design

| Status      | Current progress                                                                                      | Last updated |
| ----------- | ----------------------------------------------------------------------------------------------------- | ------------ |
| Not started | The operational contract is designed; infrastructure, runner and lifecycle qualification remain open. | 2026-10-31   |

## Owners and minimal architecture

The [feature specification](verification-workers-feature-spec.md) owns intended behavior; [agent procedure](../../.agents/rules/verification-workers.md) owns use. Add one maintained runner under `scripts/verification-workers/`, with modules for source packaging, controller requests, remote execution and report collection. Keep infrastructure/bootstrap beside it and expose one package-script entrypoint. Reuse the existing native/server/browser profilers, disposable PostgreSQL helper and workspace-resolution guard. Do not put cloud coordination in domain, game server, AI or world packages.

Use one small IAM-invoked Lambda controller, one DynamoDB coordination table, SSM for remote commands/private tunnels, private S3 prefixes for source/results, and an EventBridge Scheduler wakeup for recovery. The controller has reserved concurrency **one**: lifecycle operations serialize for this small pool without another queue/service. It returns after bounded control operations without waiting for boot or game completion; game execution never runs in Lambda. An instance-local supervisor owns child processes. The independent scheduled recovery and host watchdog cover loss of the developer's laptop and controller failures respectively. No Kubernetes, continuously running coordinator, fleet autoscaler or agent-specific shell harness is needed.

DynamoDB stores only development leases, run metadata and compute reservations, not game state. Game checks continue using PostgreSQL exclusively. The atomic lease table is necessary because local lock files, EC2 tags and separate worktrees cannot arbitrate a stopped worker across hosts. Tags provide discoverability, never authority. Deployment records exact resource IDs in one pool configuration, separate from secrets; use the project/Region owner in [AWS guidance](../../.agents/rules/aws.md).

## Operational defaults

These are initial replaceable development settings, owned by the pool configuration and emitted in every run manifest. Change them for measured need within authorization; they are neither game limits nor measured capacity claims.

| Setting   | Default and reason                                                                                                                                                                                                                                                                                                                                                            |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pool      | Provision one worker initially; maximum two managed slots, counting quarantined/stopping machines. Add the second only for real concurrent demand and admitted cost.                                                                                                                                                                                                          |
| Machine   | On-demand, non-burstable x86-64 Linux, 4 vCPU / 16 GiB RAM, 64 GiB encrypted gp3 EBS. Resolve the available family/image and current price at deployment; record CPU/storage details. No Spot interruption or CPU-credit dependence in ordinary comparisons.                                                                                                                  |
| Claim     | Entire host exclusive. One admitted experiment or sequential comparison per claim. Claim only after inputs are ready.                                                                                                                                                                                                                                                         |
| Liveness  | Runner heartbeat every 30 s; lease expires after 180 s without a successful renewal. Host checks every 30 s; scheduled controller recovery every minute. These are watchdog targets, not guaranteed AWS response times.                                                                                                                                                       |
| Deadline  | Require a complete run deadline, at most 60 min by default, including setup/results/cleanup. Reserve a final 120 s for cleanup; refuse a plan that cannot fit. Explicit longer admission requires a new cost reservation before extension. Heartbeats never extend the hard deadline.                                                                                         |
| Waiting   | Busy callers retry after 5 s with jitter, at most 10 min per request, then report busy. No worker reserved while waiting; no durable FIFO queue initially.                                                                                                                                                                                                                    |
| Idle      | Stop after 5 min idle, using EC2 stop and instance-initiated shutdown behavior `stop`. No hibernation. Reserve the idle tail and stopping allowance in the releasing run's estimate; a new claimant can assume subsequent occupancy.                                                                                                                                          |
| Retention | Automatically retire unclaimed workers after seven days without use, after required artifacts are preserved. Pool creation reserves that storage lifetime; renewal requires renewed budget. Source/results in S3 expire after seven days unless explicitly preserved elsewhere or extended with cost admission. Never expire financial records or the only required evidence. |
| Disk      | Enforce a 10 GiB dependency-download cache cap, a declared per-run source/output/database allowance and at least 10 GiB free-space headroom. Reject an oversized plan or admit a larger worker explicitly; stop an over-budget capture with an incomplete result, not silent data loss.                                                                                       |

There is no free standing pool budget. [Task spending](../../.agents/rules/verification.md#spending) includes compute, EBS while stopped, image snapshots, control services, logs, transfers and artifact retention. Reserve conservatively using current prices and the deadline plus idle/stop allowance. Register an authorized task ceiling once; sibling agents share it. The controller transactionally reserves cloud commitments against that task, subtracting other reported/uncertain task spending. This is not a replacement for provider accounting: native runs set `AI_BUDGET_USD=0`; any live-model experiment needs separate existing admission under the same aggregate ceiling. Do not accept a fresh task ID as a way to reset the allowance.

Keep upper-bound reservations until reconciliation, distinguishing estimates from settled charges. Watchdogs reduce runaway cost but cannot promise an absolute bill ceiling during an AWS outage. An unknown stop remains a financial uncertainty and blocks further admission that depends on those funds. Account for the full pool storage commitment before creating the second slot. Retiring a slot deletes only its registered disposable resources after export; never discover deletion targets by a broad tag match.

## Claim and execution contract

Proposed runner operations are `plan`, `run`, `status`, `cancel`, `collect` and `release`; these are interfaces to implement, not commands available today. `run` performs admission, source staging, claim, execution and release in `finally`. Status/collect survive loss of the initiating CLI. Explicit claim/heartbeat internals are shared by interactive browser sessions. Requests carry structured arguments, not interpolated shell strings.

Persist these small records in the coordination table. Admission/status queries inspect the bounded slot registry and exact run/task keys, never scan run history:

- **Worker:** exact instance/volume IDs and environment identity, lifecycle state, monotonically increasing claim generation, current run ID, lease/hard deadlines, last clean receipt and any pending control operation.
- **Run:** unique ID, task/agent and original absolute worktree, claim-secret hash, source and plan hashes, worker/generation, timestamps, command IDs, phase/outcome, artifact prefix/manifest and cost reservation. Human branch labels are diagnostic; content hashes determine source identity.
- **Task:** authorized ceiling/provenance, settled estimates and outstanding reservations, including other known task spending. Preserve uncertainty instead of refunding a lost receipt.

State transitions are `available → leased → releasing → available`; stop uses `available → stopping → available` only after EC2 reports stopped. A leased machine may be booting, preparing or running; those are run phases. Failed recovery enters `quarantined`, unavailable until repaired or retired. Never mark a machine available merely because its lease time passed.

1. **Admit:** transactionally create the run/reservation under its unique request ID and task ceiling. Package/upload source without occupying a worker. Repeated requests return the existing run, not another reservation. Abandoned staged runs retain only their incurred storage/accounting commitment.
2. **Claim:** select from the bounded registered slots. A conditional transaction requires `available`, no unresolved control operation, an admitted waiting run and a live reservation; set `leased`, increment generation and bind run/deadlines. A loser receives busy. An old read or a tag cannot win a claim. Create a slot only through the serialized allocator, within cap and budget; `RunInstances` uses an idempotency token tied to that allocation. Reconcile an uncertain create before allocating again.
3. **Prepare/start:** record the intended operation before calling EC2/SSM. Each remote operation includes worker ID, generation, run ID, operation ID and expiry. The supervisor takes a host-local lock, strongly reads the lease and refuses expired/mismatched claims before installing inputs or starting a child. Persist operation IDs locally so duplicate SSM delivery cannot execute an experiment twice. A started-but-unfinished operation is uncertain, never automatically rerun.
4. **Execute:** use an unprivileged per-run process group/systemd unit with a hard runtime limit; database and output paths contain the run ID. Its PID group, command IDs and database names belong to that run manifest. A supervisor heartbeat updates observed phase, but **cannot renew the agent's lease**. Every renewal requires the current worker/generation/run and an unexpired lease. Worker loss, cancellation or deadline stops subsequent dispatch and initiates cleanup.
5. **Release:** conditional transition to `releasing` closes dispatch. Stop/await all owned children, cancel and reconcile pending SSM commands, close/drop only run-owned databases, finalize/upload artifacts and delete owned workspace/temporary secrets. The supervisor acknowledges cleanup under the same generation. Only a verified clean receipt with no pending operations permits `available`; retain tools/cache. Failed cleanup quarantines. Repeated release is idempotent; a stale release never affects a later run.
6. **Recover/stop:** the serialized controller also handles scheduled recovery. For an expired lease, close dispatch and terminate the old generation; never transfer it directly. Delayed SSM commands must be terminal or expired and fenced by the supervisor before reuse. Unknown processes/control outcomes require quarantine or a verified stop/reboot and clean preparation. A control request recorded before a controller crash is reconciled from actual EC2/SSM state, not blindly resent. Pending stop/start operations block claims until their outcome is known. No new generation begins while a prior controller invocation or host shutdown can still affect it.

The host watchdog terminates its owned process group on lease loss even if the controller is unavailable. It uses the same local lock/generation checks for cleanup; stale callbacks cannot act on a new claim. At the hard deadline it blocks further launches and requests instance shutdown with verified `stop` behavior. Mirror the idle-stop deadline on the host too, so controller failure cannot leave an unclaimed machine running indefinitely. Once local shutdown begins, launch admission stays closed; the controller reconciles actual power state before resuming any concurrently acquired claim. Boot starts with launch admission closed until the supervisor reconciles its journal and current lease. Preserve source/results on EBS when upload fails and quarantine for recovery; stop compute rather than wait indefinitely for transfer. Once the machine is clean, the controller may stop it without deleting evidence.

The runner creates a random 256-bit claim secret before admission and saves it outside Git/logs in private task state; the controller stores only its hash. Mutations require the secret as well as matching generation/run. Status exposes no takeover capability; SSM commands carry only the controller-authorized operation identity, never that secret. Idempotent request recovery uses the same saved secret. Operator recovery is explicit and closes the old claim before acting.

Use DynamoDB conditional transactions, not TTL deletion, for correctness: TTL is eventual garbage collection. Active worker rows and uncertain accounting never expire through TTL. AWS documents [conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [atomic transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) and [delayed TTL removal](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html). Keep all state and mutations in the selected Region; do not introduce a distributed multi-Region lease protocol.

## Prepared environment and source fidelity

Bootstrap from one maintained, pinned recipe: OS, Node/pnpm selected by repository pins, PostgreSQL/pgvector and the worker supervisor. Store its recipe/image hash and installed versions. Reuse the EBS-backed installation across stop/start; prepare a new environment only when its required identity changes. Apply updates/reboots during idle preparation, never during a measured run; suppress competing maintenance and record unavoidable system load/CPU steal. A baked AMI can reduce replacement time after the recipe stabilizes; automated image pipelines are not a first-stage requirement.

Key dependency download caches by lockfile, Node ABI, pnpm version, platform/architecture and relevant install settings. Run the frozen-lockfile install in the run workspace with the shared download store, then verify it. Never copy macOS `node_modules` to Linux, share another checkout's workspace symlinks, or treat cached build output as proof of the current source. Start with fresh builds when needed; add build caching only with measured benefit and exact inputs. Prune unused caches only while the host is unclaimed; no cache maintenance during measurements.

Use EBS-backed `/var/lib/openlegend-verification/` for supervisor state, `cache/` and `runs/<runId>/{source,results}`. Bootstrap logs belong in `/var/log/openlegend-verification-bootstrap.log`; each run retains its own stdout/stderr and timeline. Return these paths and the artifact URI from status, so diagnosis never depends on an agent remembering a temporary filename. Stream source/output byte limits and monitor free disk with cheap filesystem statistics; database growth guards are observed limits with headroom, not an invented hard PostgreSQL quota. Disclose monitoring overhead.

The source packager streams a compressed archive and manifest from an exact commit by default. It includes maintained runtime/tooling files and pinned dependency/configuration files, excludes credentials/private saves/generated output, and records archive bytes and SHA-256. If checking uncommitted work is needed, explicitly label a content-addressed dirty snapshot with its base commit and included changed/new files; do not claim it is the base commit. Reject escaping paths/symlinks and missing workspace files. Required external assets retain the existing asset-storage contract and exact selected release; an archive is not permission to copy private payloads.

Upload once to a private run/source prefix; verify the archive and extracted manifest on the worker and before/after execution. Reject links resolving workspace packages outside that source root using the existing guard. Prefer a source manifest accepted by the profiler rather than reconstructing synthetic Git objects just to satisfy provenance checks. If a tool genuinely needs Git, use a real exact detached checkout. Reconcile existing profiler source checks in VW03; do not weaken provenance or pretend a copied directory is a Git checkout. Any manifest/tooling replacement needs actual mismatch-refusal evidence.

SSM is the default control path, targeted to an exact instance ID. S3 handles compressed source/results; do not tunnel large logs through command output. SSH/SCP remains an explicitly owned fallback, with task-scoped credentials, exact host verification and identical claim enforcement. No public PostgreSQL/game listener, broadly open SSH port or copied developer AWS session. The controller alone changes lifecycle/claims; instance roles are limited to required SSM, lease reads and owned artifact access. Run source code without the supervisor's credentials or instance-metadata access. Secrets needed for a separately authorized experiment use the existing scoped secret mechanism, not archive/environment dumps or plaintext SSM arguments; [SSM's guidance](https://docs.aws.amazon.com/systems-manager/latest/userguide/running-commands.html) explains that command parameters are logged.

## Measurement and artifacts

Keep one top-level `run.json`, source/environment manifests, stdout/stderr, phase timeline and optional existing profiler outputs. The runner wraps existing tools; add phase hooks at their actual boundaries rather than scraping prose or inventing a second simulation. Each phase records start/end, elapsed time, outcome and relevant byte/count/cache-hit facts. Use monotonic clocks within a process, UTC plus run/phase IDs across machines; record clock uncertainty and nesting. Do not sum overlapping parent/child phases.

Capture: local packaging/compression → source upload → wait/claim → instance start/readiness/bootstrap if needed → download/extraction/verification → dependency preparation → required build → PostgreSQL/database preparation → cold world startup → saved-world reopen when selected → warm-up → measured activity → drain → artifact upload/download → cleanup/release → actual stop. Capture controller admission and failures as events. Distinguish stages skipped through reuse, phases still running and unavailable timestamps. Separate human/agent idle time from automated overhead. Report cold and warm end-to-end totals, not just the profiler's requested duration.

Inside a standard five-minute experiment, preserve the existing actual workload evidence: actors and active actions, accepted/refused commands, speech, achieved game time versus requested speed, debt/backlog, pauses/recording blocks, event-loop delay, CPU, memory and storage growth. Preserve the profiler's available samples; if its timeline is insufficient, add a low-volume one-second progress sample in the shared reporting owner, with collection cost disclosed. Include startup and final drain separately so a fast unfinished run cannot pass. CPU/SQL detail captures remain separate from minimally instrumented throughput runs with the same workload. A fixture with idle NPCs is not evidence of active hundreds-of-actors capacity.

For browser work reuse `scripts/performance/profile-browser.mjs`: record frame interval percentiles/stalls, actual command acceptance and first rendered response, server-to-client updates and visible movement continuity. Record browser/OS/GPU, headless/software versus hardware rendering, viewport/pixel ratio, quality, asset release, network/tunnel topology and competing host load. Browser callbacks and renderer submission timestamps are not physical display presentation measurements. An AWS CPU-only browser can check UI behavior; qualify graphics on a representative device. Keep server loopback throughput distinct from real-network responsiveness. Report a measured result against the task's existing target; do not invent a universal FPS/device gate here.

Before release, upload outputs under `runs/<runId>/`, publish an immutable experiment checksum/size manifest and verify object receipt. Download/verify to a task-owned path outside Git, or record the exact private durable artifact location and retention deadline when the laptop is unavailable. A separate completion receipt references that manifest and records later cleanup/release/stop and accounting outcomes; it never changes sealed experiment bytes or rewrites failure as a pass. `collect` returns both when available and labels an unfinished receipt pending. Do not publish private URLs or logs as public assets. Necessary evidence must be copied to its approved longer-lived home before expiry. Quarantine preserves the only copy when transfer fails. Ongoing storage and unfinished cleanup remain explicit. Remove closed run metadata after its evidence/receipts have been preserved; retain the task's financial record and all uncertain operations.

No prior run established the complete setup-stage timings. Historical one-off bootstrap or profiler durations are not promises for this workflow. [AWS stop/start](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html) retains EBS but can change host/public address; a restarted machine is not necessarily the identical physical benchmark host. Record measured hardware and environment on every claim and use fresh matched comparisons when that matters.

## Implementation and review boundaries

Deliver the narrow lifecycle first, then reuse/caching, then complete profiler/browser reporting; [VW01–VW04](../maintainers/verification-workers.md) own dependencies and acceptance. Native controller/runner logic can be exercised without launching AWS; actual IAM, stop/start, crash recovery and graphics remain separate live evidence. Required measurements may expose poor overhead; do not relabel them as passes or add an unbounded optimization campaign.

Before delivery, walk through two simultaneous claims, a stale owner releasing after reassignment, interrupted upload, changed lockfile, mismatched workspace link, duplicate command delivery, controller crash during start, laptop loss, failed database drop, failed artifact transfer and idle stop racing a claim. The single mutation owner must handle each; no agent-specific repair script or manual claim deletion is an accepted path. Use disposable owned resources and the smallest adequate existing checks/scenarios; this design does not request a new unit suite.
