# Reusable verification workers — technical design

| Status      | Current progress                                                                                      | Last updated |
| ----------- | ----------------------------------------------------------------------------------------------------- | ------------ |
| Not started | The operational contract is designed; infrastructure, runner and lifecycle qualification remain open. | 2026-10-31   |

## Owners and minimal architecture

The [feature specification](verification-workers-feature-spec.md) owns intended behavior; [agent procedure](../../.agents/rules/verification-workers.md) owns use. Keep this tooling under `scripts/verification-workers/`, exposed through `pnpm verify:worker`. `contracts.mjs` owns plans/results and boundary validation; `cli.mjs` owns preparation, heartbeats and collection; `controller.mjs` owns cloud admission/claims/lifecycle; `supervisor.mjs` owns host processes and cleanup. Source packing and artifact transfer are helpers shared by those callers, not separate services. Keep one infrastructure template and bootstrap recipe beside them. Reuse existing native/server/browser profilers, the disposable PostgreSQL helper and workspace-resolution guard; no cloud coordination belongs in domain, game server, AI or world packages.

Use one small IAM-invoked Lambda controller, one DynamoDB coordination table, SSM for remote commands/private tunnels, private S3 prefixes for source/results, and an EventBridge Scheduler wakeup for recovery. The controller has reserved concurrency **one**: lifecycle operations serialize for this small pool without another queue/service. It returns after bounded control operations without waiting for boot or game completion; game execution never runs in Lambda. An instance-local supervisor owns child processes. The independent scheduled recovery and host watchdog cover loss of the developer's laptop and controller failures respectively. No Kubernetes, continuously running coordinator, fleet autoscaler or agent-specific shell harness is needed.

DynamoDB stores only development leases, run metadata and compute reservations, not game state. Game checks continue using PostgreSQL exclusively. The atomic lease table is necessary because local lock files, EC2 tags and separate worktrees cannot arbitrate a stopped worker across hosts. Tags provide discoverability, never authority. Deployment records exact resource IDs in one pool configuration, separate from secrets; use the project/Region owner in [AWS guidance](../../.agents/rules/aws.md).

## Operational defaults

These are initial replaceable development settings, owned by the pool configuration and emitted in every run manifest. Change them for measured need within authorization; they are neither game limits nor measured capacity claims.

| Setting   | Default and reason                                                                                                                                                                                                                                                                                                      |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pool      | Provision one worker initially; maximum two managed slots, counting quarantined/stopping machines. Add the second only for real concurrent demand and admitted cost.                                                                                                                                                    |
| Machine   | On-demand, non-burstable x86-64 Linux, 4 vCPU / 16 GiB RAM, 64 GiB encrypted gp3 EBS. Resolve the available family/image and current price at deployment; record CPU/storage details. No Spot interruption or CPU-credit dependence in ordinary comparisons.                                                            |
| Claim     | Entire host exclusive. One admitted experiment or sequential comparison per claim. Claim only after inputs are ready.                                                                                                                                                                                                   |
| Liveness  | Runner heartbeat every 30 s; lease expires after 180 s without a successful renewal. Host checks every 30 s; scheduled controller recovery every minute. These are watchdog targets, not guaranteed AWS response times.                                                                                                 |
| Deadline  | Require a complete run deadline, at most 60 min by default, including setup/results/cleanup. Reserve a final 120 s for cleanup; refuse a plan that cannot fit. Explicit longer admission requires a new cost reservation before extension. Heartbeats never extend the hard deadline.                                   |
| Waiting   | Busy callers retry after 5 s with jitter, at most 10 min per request, then report busy. No worker reserved while waiting; no durable FIFO queue initially.                                                                                                                                                              |
| Idle      | Stop after 5 min idle, using EC2 stop and instance-initiated shutdown behavior `stop`. No hibernation. Reserve the idle tail and stopping allowance in the releasing run's estimate; a new claimant can assume subsequent occupancy.                                                                                    |
| Retention | Retire unclaimed workers after seven days without use, after required artifacts are preserved. Reserve that storage lifetime; renewal requires renewed budget. Source and disposable output retention is seven days; required results become eligible only after verified collection under the artifact contract below. |
| Disk      | Enforce a 10 GiB dependency-download cache cap, a declared per-run source/output/database allowance and at least 10 GiB free-space headroom. Reject an oversized plan or admit a larger worker explicitly; stop an over-budget capture with an incomplete result, not silent data loss.                                 |

There is no free standing pool budget. Before registering a task, allocate a finite cloud amount from its remaining [task spending allowance](../../.agents/rules/verification.md#spending), after all other settled, reserved and uncertain spending. That allocation stays unavailable to sibling/provider work until explicitly returned. The controller enforces only this cloud sub-budget with integer micro-USD reservations; it does not query or replicate provider ledgers. All agents on that assigned task share its stable task ID/allocation. Increasing it requires additional existing task headroom or Mike's authorization; a new run/worktree/task alias never resets the ceiling. Native checks set `AI_BUDGET_USD=0`; paid-model experiments remain outside these delivery tasks.

Reserve current-price estimates for compute, stopped EBS, public IPv4, control/log/transfer services and artifact retention, including idle/stop allowances. Pool creation charges its finite storage lifetime to the creating task; another task pays only an explicitly admitted renewal, with no overlapping ownership of the same commitment. Claims on an existing pool must renew its storage deadline before their run can exceed it. Keep a task's allocation reserved until its unsettled cloud commitments are reconciled; this avoids a cross-provider accounting framework or falsely atomic aggregate guarantee.

Keep upper-bound reservations until reconciliation, distinguishing estimates from settled charges. Watchdogs reduce runaway cost but cannot promise an absolute bill ceiling during an AWS outage. An unknown stop remains a financial uncertainty and blocks further admission that depends on those funds. Account for the full pool storage commitment before creating the second slot. Retiring a slot deletes only its registered disposable resources after export; never discover deletion targets by a broad tag match.

## Claim and execution contract

### Runner input and output

The following is the interface to implement, not available commands. `pnpm verify:worker plan PLAN.json` validates and estimates without mutation. `allocate TASK_ID --usd AMOUNT --authorization-ref REF` registers an explicitly reserved cloud sub-budget; it cannot silently increase an existing allocation. `run PLAN.json` admits, stages, claims, executes and releases in `finally`. `status RUN_ID`, `cancel RUN_ID`, `collect RUN_ID DESTINATION` and `release RUN_ID` resume from private task state; operator `recover WORKER_ID` uses the same cleanup owner and cannot steal a healthy claim. `run` owns heartbeats independently of agent tool polling. Busy/throttled control requests can retry within bounded waits using the same operation ID; experiments are never automatically replayed. Initial controller deployment uses existing task spending admission and records its setup commitments before allocating the first worker.

| Plan field                                              | Contract                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `taskId`, `cloudAllocationId`                           | Existing assigned task and admitted cloud sub-budget, never an implicit fresh allowance.                                                                                                                                                                                                                                                                                                             |
| `cases[]`                                               | Ordered, nonempty cases; each has a unique ID, exact source commit or explicitly selected dirty snapshot, optional build `argv`, and check `argv` with public tool settings. One ordinary run has one case; comparisons run sequentially under one claim, each with a fresh workspace/database and source/result manifest. No shell interpolation, implicit branch update or general workflow graph. |
| `mode`, `environment`                                   | `batch` or `browser-session`; machine class, pinned bootstrap identity and declared instrumentation. Compatible hardware can be prepared for a changed toolchain under its claim; an old cache is not grounds to silently run another version.                                                                                                                                                       |
| `deadlineSeconds`, `outputLimitBytes`, `diskLimitBytes` | Whole-run wall deadline, combined capture-output cap and observed run-disk budget. Defaults: 3,600 s, 256 MiB and 16 GiB, subject to free-space/headroom checks; explicit larger diagnostics need admission. The final cleanup allowance is unavailable to measured work.                                                                                                                            |
| `requiredArtifacts`, `acceptance`                       | Artifact names that must be collected before expiry; the existing task's required pass versus measurement and actual-work indicators. Default required artifacts are the result, source/environment manifests, timeline and completion receipt; profiles/logs are retained too and can be promoted to required for diagnosis. No new universal game-performance target.                              |

Validate the plan once at admission; freeze its hash, source manifests and exact command/configuration per case. An execution change requires a new run. Public overrides follow the tool's supported settings and cannot replace the owned database or enable paid AI; credentials use separate secret references, never plans/logs. Each response includes run/worker/generation, phase, deadline, outcome (`completed`, `failed`, `interrupted` or `not-started`, absent while running), artifact locations and estimated/reserved/uncertain cost. Preserve check, setup, transport, timeout, resource-limit and cleanup failures distinctly. A completed process is not an acceptance pass: report acceptance separately as passed, failed, measurement-only or unassessed. Busy expiry before claim is not-started and releases unused compute reservation while retaining actual staging/storage costs.

Persist these small records in the coordination table. Admission/status queries inspect the bounded slot registry and exact run/task keys, never scan run history:

- **Worker:** fixed slot ID, exact instance/volume IDs and environment identity, lifecycle state, monotonically increasing claim generation, run/active-case ID and admitted plan reference/hash, lease/hard deadlines, last clean receipt and pending control operation.
- **Run:** unique ID, task/agent and original absolute worktree, claim-secret hash, source and plan hashes, worker/generation, timestamps, command IDs, phase/outcome, artifact prefix/manifest and cost reservation. Human branch labels are diagnostic; content hashes determine source identity.
- **Task allocation:** authorized cloud sub-budget/provenance, charged estimates and outstanding cloud reservations. Other task spending remains with its existing owner; preserve uncertainty instead of refunding a lost receipt.

State transitions are `available → leased → releasing → available`; stop uses `available → stopping → available` only after EC2 reports stopped. A leased machine may be booting, preparing or running; those are run phases. Fixed pool slots also support `empty → allocating → leased` and `available/quarantined → retiring → empty`. Allocating/retiring slots remain occupied for the pool cap; deletion must be confirmed before reuse. Failed recovery enters `quarantined`. Never mark a machine available merely because its lease time passed.

1. **Admit:** transactionally create the run/reservation under its unique request ID and task allocation. Package/upload source without occupying a worker. Repeated IDs require the identical plan/secret hashes and return that run; changed payloads are refused. Abandoned staged runs retain only their incurred storage/accounting commitment.
2. **Claim:** select from the bounded registered slots. A conditional transaction requires `available`, no unresolved control operation, an admitted waiting run and a live reservation; set `leased`, increment generation and bind run/deadlines. A loser receives busy. An old read or a tag cannot win a claim. Create a slot only through the serialized allocator, within cap and budget; `RunInstances` uses an idempotency token tied to that allocation. Reconcile an uncertain create before allocating again.
3. **Prepare/start:** record the intended operation before calling EC2/SSM. Each operation includes worker ID, generation, run/case ID, operation ID and expiry. The supervisor takes a local lock, strongly reads its lease and checks the admitted plan/current case before installing inputs or starting a child. Hold that lock only for transitions/launch, never while awaiting the child or uploading, so watchdog cleanup cannot deadlock. Persist operation IDs so duplicate delivery cannot execute twice. Started-but-unfinished is uncertain, never automatically rerun. Advance cases only after preceding processes/commands and cleanup finish; delayed first-case commands cannot modify the second case.
4. **Execute:** use an unprivileged per-run process group/systemd unit with a hard runtime limit; database and output paths contain the run ID. Its PID group, command IDs and database names belong to that run manifest. A supervisor heartbeat updates observed phase, but **cannot renew the agent's lease**. Every renewal requires the current worker/generation/run and an unexpired lease. Worker loss, cancellation or deadline stops subsequent dispatch and initiates cleanup.
5. **Release:** conditional transition to `releasing` closes dispatch. Stop/await all owned children, cancel and reconcile pending SSM commands, close/drop only run-owned databases, finalize/upload artifacts and delete owned workspace/temporary secrets. The supervisor acknowledges cleanup under the same generation. Only a verified clean receipt with no pending operations permits `available`; retain tools/cache. Failed cleanup quarantines. Repeated release is idempotent; a stale release never affects a later run.
6. **Recover/stop:** the serialized controller also handles scheduled recovery. For an expired lease, close dispatch and terminate the old generation; never transfer it directly. Authenticated cleanup of that generation remains permitted after expiry, but new preparation/work does not. Delayed SSM commands must be terminal or expired and fenced before reuse. Unknown process/control outcomes require quarantine or a verified stop/reboot and clean preparation. Reconcile interrupted requests against actual EC2/SSM state, not blind resend. Pending cloud stop/start operations block claims; a claim racing host-local idle shutdown waits for reconciled readiness. No new work begins while an old operation can still stop it.

The host watchdog terminates its owned process group on lease loss even if the controller is unavailable. It uses the same local lock/generation checks for cleanup; stale callbacks cannot act on a new claim. At the hard deadline it blocks further launches and requests instance shutdown with verified `stop` behavior. Mirror the idle-stop deadline on the host too, so controller failure cannot leave an unclaimed machine running indefinitely. Once local shutdown begins, launch admission stays closed; the controller reconciles actual power state before resuming any concurrently acquired claim. Boot starts with launch admission closed until the supervisor reconciles its journal and current lease. Preserve source/results on EBS when upload fails and quarantine for recovery; stop compute rather than wait indefinitely for transfer. Once the machine is clean, the controller may stop it without deleting evidence.

The runner creates a random 256-bit claim secret before admission and saves it outside Git/logs in private task state; the controller stores only its hash. Mutations require the secret as well as matching generation/run. Status exposes no takeover capability; SSM commands carry only the controller-authorized operation identity, never that secret. Idempotent request recovery uses the same saved secret. Operator recovery is explicit and closes the old claim before acting.

Use DynamoDB conditional transactions, not TTL deletion, for correctness: TTL is eventual garbage collection. Active worker rows and uncertain accounting never expire through TTL. AWS documents [conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [atomic transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) and [delayed TTL removal](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html). Keep all state and mutations in the selected Region; do not introduce a distributed multi-Region lease protocol.

## Prepared environment and source fidelity

Bootstrap from one maintained, pinned recipe: OS, Node/pnpm selected by repository pins, PostgreSQL/pgvector and the worker supervisor. Store its recipe/image hash and installed versions. Reuse the EBS-backed installation across stop/start; prepare a new environment only when its required identity changes. Apply updates/reboots during idle preparation, never during a measured run; suppress competing maintenance and record unavoidable system load/CPU steal. A baked AMI can reduce replacement time after the recipe stabilizes; automated image pipelines are not a first-stage requirement.

Reuse pnpm's [content-addressed package store](https://pnpm.io/10.x/symlinked-node-modules-structure), not a duplicate store per lockfile. A fresh workspace uses the pinned `pnpm install --frozen-lockfile --prefer-offline`; [pnpm fetches missing packages](https://pnpm.io/10.x/cli/install). Lockfile, Node ABI, pnpm version, platform and install settings identify the installation, not a reason to redownload unchanged content. Rebuild native dependencies as required; never copy macOS `node_modules` or another checkout's workspace links. Keep current repository install-script permissions. Build outputs start fresh when needed. Use pnpm's own pruning only under an exclusive claim during preparation/cleanup, when pressure warrants it; pruning every release would erase useful reuse. No install, upgrade or cache maintenance runs during measurement.

Use EBS-backed `/var/lib/openlegend-verification/` for supervisor state, `cache/` and `runs/<runId>/cases/<caseId>/{source,results}`. Bootstrap logs belong in `/var/log/openlegend-verification-bootstrap.log`; runs retain their own stdout/stderr/timeline. Status returns those paths and artifact locations. Stream source/output byte limits and monitor free disk with cheap filesystem statistics; database growth guards are observed limits with headroom, not an invented hard PostgreSQL quota. Disclose monitoring overhead.

The source packager streams a compressed archive and manifest from an exact commit by default. Include maintained runtime/tooling files and pinned dependency/configuration files; exclude credentials/private saves/generated output, and record bytes/SHA-256. For a dirty snapshot, freeze an explicit changed/new-file selection with its base commit; detect files changing during capture and refuse the mixed snapshot. Preserve its archive as required evidence. Reject escaping paths/symlinks and missing workspace files. Required external assets retain their existing storage contract and exact selected release; an archive grants no permission to copy private payloads.

Upload once to a private run/source prefix; verify the archive and extracted manifest on the worker and before/after execution. Reject links resolving workspace packages outside that source root using the existing guard. Prefer a source manifest accepted by the profiler rather than reconstructing synthetic Git objects just to satisfy provenance checks. If a tool genuinely needs Git, use a real exact detached checkout. Reconcile existing profiler source checks in VW03; do not weaken provenance or pretend a copied directory is a Git checkout. Any manifest/tooling replacement needs actual mismatch-refusal evidence.

### Network and execution boundary

Use the selected project's suitable subnet with outbound internet access; the default is a public IPv4/Internet Gateway route and a dedicated security group with **no inbound rules**, not a new NAT gateway or endpoint fleet. Record and budget IPv4 cost; reuse an existing qualified egress arrangement when available. SSM initiates [outbound HTTPS connections](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-create-vpc.html); allow required HTTPS, DNS and time synchronization, use HTTPS package mirrors, and keep game/PostgreSQL listeners on loopback. Do not change shared network rules to make setup work. The deployment template must explicitly supply this connectivity rather than assume a private subnet has internet access.

SSM targets an exact instance; S3 transfers compressed source/results, not command-output blobs. SSH/SCP is a diagnostic fallback with scoped credentials, host verification and identical claims. The controller alone mutates lifecycle/leases; per-slot roles read their own lease, the sanitized pool source prefix and `workers/<slotId>/runs/` artifacts. The lease's admitted plan reference supplies the supervisor's execution authority; no whole-table permission is needed. Run trusted project code unprivileged, without supervisor credentials or instance-metadata access; this is not a hostile-code or multi-tenant sandbox. Never copy developer AWS sessions or put secrets in [logged SSM parameters](https://docs.aws.amazon.com/systems-manager/latest/userguide/running-commands.html).

### Remote browser integration

The existing browser driver consumes `READY.json`, requires loopback HTTP/PostgreSQL metadata, writes a local `startMarkerPath`, and launches headless Chromium with a Metal option. `scripts/profile-server.ts` supplies that marker and waits for it; `scripts/performance/profile-server.mjs` is the separate headless server workload. Do not treat these as interchangeable runners.

For a browser session, use the owned browser fixture on the worker and one [SSM port-forwarding session](https://repost.aws/knowledge-center/systems-manager-session-manager-connect) to a local ephemeral loopback port. The runner verifies run/case/source identity and prepares local ready metadata for that origin; retain loopback, authentication and database ownership checks. Keep production client assets served by the worker, with API/SSE on the same tunneled origin; no separate public listener or proxy framework.

Make the existing browser measurement implementation callable with an injected `signalCaptureStart()` hook. Its local CLI keeps the local marker path; the worker runner supplies a fenced supervisor operation that writes the worker's registered marker exactly once and awaits the fixture's capture acknowledgement. The browser still performs the ordinary Resume action; the hook signals instrumentation, never resumes gameplay again. Record browser resume, marker send/receipt and actual server/browser capture bounds; report overlapping windows and relay/clock uncertainty, not identical starts. Update all current callers together; do not fake a shared filesystem or copy the driver into a remote variant.

Add an explicit representative-device mode using a visible browser and its native graphics backend; retain headless mode for diagnostics. Do not send Metal flags to Linux or infer hardware acceleration from launch options. Record actual renderer/GPU/backend and keep uncertain/software results labeled. The runner holds the lease and tunnel until browser capture and server cleanup finish; tunnel loss interrupts the run, never starts a replacement or replays inputs.

## Measurement and artifacts

Keep one top-level `run.json`, source/environment manifests, stdout/stderr, phase timeline and optional existing profiler outputs. The runner wraps existing tools; add phase hooks at their actual boundaries rather than scraping prose or inventing a second simulation. Each phase records start/end, elapsed time, outcome and relevant byte/count/cache-hit facts. Use monotonic clocks within a process, UTC plus run/phase IDs across machines; record clock uncertainty and nesting. Do not sum overlapping parent/child phases.

Capture: local packaging/compression → source upload → wait/claim → instance start/readiness/bootstrap if needed → download/extraction/verification → dependency preparation → required build → PostgreSQL/database preparation → cold world startup → saved-world reopen when selected → warm-up → measured activity → drain → artifact upload/download → cleanup/release → actual stop. Capture controller admission and failures as events. Distinguish stages skipped through reuse, phases still running and unavailable timestamps. Separate human/agent idle time from automated overhead. Report cold and warm end-to-end totals, not just the profiler's requested duration.

Inside a standard five-minute experiment, preserve the existing actual workload evidence: actors and active actions, accepted/refused commands, speech, achieved game time versus requested speed, debt/backlog, pauses/recording blocks, event-loop delay, CPU, memory and storage growth. Preserve the profiler's available samples; if its timeline is insufficient, add a low-volume one-second progress sample in the shared reporting owner, with collection cost disclosed. Include startup and final drain separately so a fast unfinished run cannot pass. CPU/SQL detail captures remain separate from minimally instrumented throughput runs with the same workload. A fixture with idle NPCs is not evidence of active hundreds-of-actors capacity.

For browser work reuse `scripts/performance/profile-browser.mjs`: record frame interval percentiles/stalls, actual command acceptance and first rendered response, server-to-client updates and visible movement continuity. Record browser/OS/GPU, headless/software versus hardware rendering, viewport/pixel ratio, quality, asset release, network/tunnel topology and competing host load. Browser callbacks and renderer submission timestamps are not physical display presentation measurements. An AWS CPU-only browser can check UI behavior; qualify graphics on a representative device. Keep server loopback throughput distinct from real-network responsiveness. Report a measured result against the task's existing target; do not invent a universal FPS/device gate here.

Before release, upload case outputs under the registered worker/run prefix, seal their checksum/size manifest and verify receipt. A separate run completion receipt references those manifests and records cleanup/financial outcomes; stop may initially be pending. `run` returns after verified cleanup and artifact receipt, **without waiting through the five-minute idle tail**. Later status records either the stop or reuse by the next run, without changing experiment bytes or claiming unknown charges settled.

`collect` verifies downloaded checksums outside Git and records destination/manifest acknowledgement; an approved durable archive can acknowledge collection instead. Required artifacts are excluded from automatic expiry until acknowledged; optional output and staged source can expire after seven days. Use [tag-filtered lifecycle eligibility](https://aws.amazon.com/blogs/storage/simplify-your-data-lifecycle-by-using-object-tags-with-amazon-s3-lifecycle/), not unconditional bucket expiry. Adding eligibility to an already old object can make it expire immediately; preserve the destination first. No Object Lock, old-save migration or indefinite retention of every trace is needed. Missing required collection retains its cost commitment and a visible recovery item; stop compute, preserve the sole copy, and resolve retention before its reserved storage term ends. Delete EBS only once required payloads are verified elsewhere. Keep financial receipts/uncertain operations; retire other closed metadata with collected evidence. Never commit signed artifact URLs or private payloads; public documentation/source links are unaffected.

No prior run established the complete setup-stage timings. Historical one-off bootstrap or profiler durations are not promises for this workflow. [AWS stop/start](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html) retains EBS but can change host/public address; a restarted machine is not necessarily the identical physical benchmark host. Record measured hardware and environment on every claim and use fresh matched comparisons when that matters.

## Implementation and review boundaries

Deliver lifecycle, then reuse, then profiler/browser integration under [VW01–VW04](../maintainers/verification-workers.md), the sole owner of fault cases and acceptance. Pure controller/runner checks do not qualify live IAM, stop/start, recovery or graphics. Use existing checks and controlled disposable scenarios, not a new test suite or agent-specific repair script. A poor measurement needs attribution, not a claimed pass or unbounded optimization campaign. No migration of temporary task wrappers/environments or production game deployment is required.
