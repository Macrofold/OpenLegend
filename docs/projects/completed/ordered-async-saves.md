## Problem

`WorldService` saves simulation progress about once per real second (LA171). Before this project that save was synchronous: it ran `store.commit` inside the world mutation queue, so native time, commands and reads waited for the whole PostgreSQL transaction. The worst recorded 3× scene hitch overlapped a 327 ms save; one save took 2.54 s under host load. After the write, `commit` installs its captured, history-released world as the live world. Releasing the queue around the existing call would let newer progress be overwritten by that install, or let two writes diff against the same baseline.

## Ordered persistence design

Terms: a **background save** writes simulation progress while the game keeps running; a **synchronous save** holds the mutation queue until its write finishes and only then shows its effect ([canonical definitions](../../save-and-load.md#background-and-synchronous-world-saves)). Player commands, AI characters' finished actions and replies, pause/resume, editors and loads use synchronous saves; simulation progress uses background saves except in the rule 4 fallback. In code a background save is `WorldService.saveProgress` with `backgroundSave` in flight; a synchronous save is `WorldService.commit` or the synchronous branch of `saveProgress`. The **live world** is `WorldService.saved`, the one authoritative in-memory world. The **durable baseline** is the repository's last committed state (`acceptedState`/`acceptedRevision`), which the next commit diffs against. A **snapshot** is a frozen `SavedWorld` taken from the live world inside the mutation queue.

### Ordering rules

1. **One writer, snapshot order.** At most one world write runs at a time. A background save's snapshot is taken only inside the mutation queue when no write is in flight. Every synchronous save (commands, AI results, pause/resume, editors, restore, `flush` inside the queue) first waits for the in-flight background save's completion handle, which settles only after its bookkeeping or failure latch, then re-checks `storageError`, then writes. Revisions therefore commit in the order snapshots were taken.
2. **Descent.** The live world always descends from the most recent snapshot, and each snapshot descends from the durable baseline. The repository diff (`WorldRecords.prepare`) and its proven-append fast paths therefore stay valid.
3. **Prepare before release, once.** Record preparation (`prepare(baseline, snapshot)`) runs synchronously when the snapshot is taken, before history release, because only preparation assigns canonical list/map positions that release then reuses. Preparation and release are computed once per snapshot and reused on every path; release is not idempotent (its memoization would skip a second compaction). The transaction consumes that exact prepared change set and refuses a token whose baseline or revision changed. The hot-event dependency compaction that precedes preparation is never installed as the release.
4. **Evict only durable records.** Hot-event trimming and history release remove records from memory. A background save may evict a record only if the durable baseline holds the identical object at the same path (reference equality), i.e. SQL already has that exact value. If any eviction would drop a record created or changed since the baseline, that snapshot is saved synchronously instead, with the same prepared change set and release (today's order: write, then release). This keeps the invariant “not resident implies already in SQL” for every SQL reader during the write window. The collection that forced each synchronous save is recorded for PF00 attribution.
5. **Two outcomes once the release is live.** After a background save's released world becomes live, its prepared change set is the only valid successor of the durable baseline. It either commits, and the released world becomes the durable baseline (`adoptHistory(snapshot, released)`) together with the durable bookkeeping in the same continuation, or `storageError` latches with no further world commits. A refusal before `BEGIN` (writer queue busy or full) re-submits the same prepared change set after pauses of 0.5, 1 and 2 s, four attempts in total, because nothing ran and the baseline is unchanged; it never prepares a new snapshot against the old baseline, which would delete every record the release evicted. A synchronous save of simulation progress (rule 4) makes one attempt, since it holds the queue; on refusal nothing is installed, its computed release is forgotten so the next tick releases again, and that tick retries. As a backstop, the repository refuses to reload-and-diff after a rolled-back commit until an explicit reload (restart); a load refused before its transaction starts restores the released baseline it replaced, so a later diff never deletes history that is not resident.
6. **Bounded pending work.** One background save may be in flight; when the next is due while one is still writing, new simulation progress stays in memory (these snapshots are cumulative and replaceable). If the in-flight background save has been outstanding for 4 s, native time waits for it before advancing again, restoring today's backpressure. The wait delays native time without discarding it, so unsaved simulation progress is bounded by the previous write's full duration plus about 4 s of the in-flight write, not by 4 s.
7. **Admission without holding the queue.** Top-level operations that are not simulation progress (commands, AI results, reads through the queue) wait outside the queue for an in-flight background save, so a command never holds the queue for another operation's I/O. One 5-second admission budget covers that wait and the queue wait (then `busy`, as today). While any such operation is waiting or queued, no new background save starts (up to 5 s of unsaved progress); its synchronous save, if any, carries the simulation progress. Native ticks and computed-route publication do not wait. Nested operations keep their re-entrant behavior. Exception: when the 5-second cap starts a background save while operations are already queued, a queued command's synchronous save waits for that background save inside the queue for the rest of its write (as simulation-progress saves did before this project), and operations behind it may get busy; avoiding that would mean giving up the cap.
8. **Durability waits.** `flush()` keeps its synchronous in-queue semantics (hydration, history edits, capture and restore need `live === baseline`). `flushMemorySources()` outside the queue first takes one queue turn, so an earlier forget/correction commits before its check, then waits outside the queue for the first snapshot that covers the live world as it was at call time: the in-flight write only if nothing changed since that snapshot, otherwise a follow-up snapshot. State read after the wait may be newer than what is saved.

### Publication boundary

Unchanged: explicit commands, AI and other background-job results, editors, pause/resume and restore still use synchronous saves: they return only after their own durable commit, and their effects become live only after that commit. Simulation progress remains visible before it is durable, exactly as before (`acceptProgress`, formerly `acceptRoutine`). Journal/history refresh signals, transcript epochs, story-job wakeups and job outcomes continue to follow the durable commit (the repository's after-commit hooks plus settle-time bookkeeping).

### Failure behavior

- **Failed background save (transaction error):** the PostgreSQL transaction rolls back. `storageError` latches, the world pauses with the existing storage message, no later snapshot or commit is written, and no durable mark is emitted. The live world keeps its unsaved simulation progress in memory but is never written; restart reloads the last durable revision. Queued commands are not applied. A failure during `COMMIT` itself may still have committed; restart reconciles from SQL.
- **Every latch rejects waiters:** `storageError` is a setter, so any assignment from any module rejects all durability waiters and drops pending snapshot requests. A lost follow-up request (queue admission expired) rejects its waiters with `busy`.
- **Crash during a write:** the database keeps the previous revision; unacknowledged commands are not applied; simulation progress since the last completed save is lost. The loss window grows from about one second to about one second (up to 5 s with a rule 7 deferral) plus the previous write's full duration (the cadence restarts when a write finishes, and backpressure delays rather than discards time) plus up to about 4 s of the in-flight write. A crash after `COMMIT` but before settle recovers the new revision at startup (existing narrator/job recovery).
- **Guard fallback:** a synchronous save (the previous behavior) for that snapshot only.
- **Shutdown (stage 7):** stop intake, await the tick, wait for the in-flight background save within a deadline; if latched or past the deadline, skip the final flush and report the last revision confirmed durable and its simulation time; always attempt to close the server and store (a close past the deadline is reported and `main.ts` exits one second after the report).

### Durable notification (EPR05 seam)

`WorldService` exposes the latest durable mark `{revision, generation, sequence, nextId, eventSequence, simTime}`, `onDurable(listener)`, `whenDurable()`, `durabilityTicket()` and `isDurable(ticket)`. Marks are emitted after every successful world commit, synchronous or background, in revision order, after the PostgreSQL COMMIT and its existing after-commit publication hooks; listeners run from a root context (never as nested queue work or with a request's authority). `generation` is process-local: it changes on restart and on load. A consumer that observes new or changed evidence records `durabilityTicket()` and treats it as saved once `mark.sequence >= ticket` in the same generation. For records created at or before a cut, awareness/memory `sequence <= nextId` and event `sequence <= eventSequence` are also saved; revisions or removals of older records need a ticket. A load rejects waiters from the abandoned timeline and publishes exactly one mark for the restore revision under the new generation. The producer is integrated. [EPR05](../../maintainers/events-perception-and-reactions.md#epr05--change-fed-actorwork-and-one-reaction-intake) still owns consumer-side durability gating; this project did not change perception/reaction code, and no additional branch merge is a prerequisite.

Known consumer gap: `AiDirector.considerThought` persists a “seen evidence” watermark from live (possibly unsaved) awareness sequences. After a crash, `nextId` rewinds and newer evidence below the stored watermark is ignored until ids pass it. The window already existed (about one second) and now also spans the in-flight write. Proposed fix for the perception owner: clamp the stored watermark to `world.nextId` when reading the schedule, or cap it at `durable.nextId` when writing.

## Decisions, risks and open questions

- The crash-loss window for simulation progress grows by the previous write's full duration and up to about 4 s of the in-flight write; recorded as a limit change (LA171, SV19). Starting the next snapshot as soon as a slow write finishes would shorten it but keep storage continuously busy under slow I/O; not done.
- The guard fallback keeps rare synchronous saves of simulation progress; measure frequency before adding a read fence or finer eviction.
- Commands and AI results keep synchronous saves because their effects must not be published before durability; moving them to background saves needs durability-gated view publication (out of scope, recorded in PF05).
- A supported way to load when the pre-load checkpoint cannot be created (SB13 bypass) is a policy decision; this project makes failure safe and documents operator preservation, without adding a bypass.
