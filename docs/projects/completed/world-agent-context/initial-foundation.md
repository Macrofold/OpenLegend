The first version must carry a supported invention through real draft, dependency, validation, presentation-readiness and review records into the existing activation/knowledge/use boundaries. Describing those stages in a prompt is insufficient. Keep the finite recipe path small, but make its records and projections useful to other existing authoring kinds.

Presentation adequacy may block claiming an invention usable without blocking storage of its draft. If the requested activation needs presentation that is missing, do not prepare an activation-ready review by hiding that blocker. A purely administrative policy can have no new visual artifact requirement while still needing truthful explanation/current observation behavior. An optional prettier icon cannot hold a supported recipe hostage or authorize paid art.

## 3. Three structures with different jobs

1. **Semantic relationship graph:** what definitions, candidates, resources, interfaces and evidence depend on or affect. It is a typed multigraph, not necessarily a DAG.
2. **Creation work plan:** which native checks or deliberately admitted jobs must complete before review/publication. A small list with prerequisites is enough initially; it is not a second workflow engine or a physical-action scheduler.
3. **Freshness dependencies:** which definition, value, membership, geometry, authority or deadline changes make a result stale. Reuse [native dependency types](../../../../packages/domain/src/dependencies.ts).

They share exact references but not authority or cycle semantics. A `requires` definition edge does not mean “perform this action first.” A pipeline prerequisite does not reserve physical resources. An invalidation token is not a human-readable mechanical explanation. Do not collapse these into an untyped `dependsOn` list.

## 4. Small shared candidate graph

### Current reader reused

[Protocol relationships](../../../../packages/protocol/src/relationships.ts), [definition extraction](../../../../apps/server/src/world-graph.ts) and [indexing](../../../../apps/server/src/relationship-index.ts) already supply exact references, typed source-backed links, immutable incoming/outgoing adjacency and paging. Current source coverage includes recipe materials/output/base/family, attribute/sense hosts, status conditions/rates and cognition's dream-status reference. Live/evidence projections remain separately scoped.

[Trace](../../../../apps/server/src/relationship-trace.ts) supplies bounded BFS paths and unfinished frontiers. It deliberately omits previously seen alternative/cycle edges. Use it to explain a route; **never use its witness tree as a complete candidate dependency closure, cycle proof or validation result**. Current page coverage explicitly says `impact: not-evaluated`. [Authoring impact](../../../../apps/server/src/world-authoring-kinds.ts) has meaningful selected status/body checks but returns a `none` token for other kinds; that is not proof of no interactions.

### Candidate overlay and extraction

Build an immutable overlay for one submitted draft revision using the same reference/edge/index semantics. The draft and proposed output are visibly proposed, with no installed/instance identity. Extend closed reader/projection types deliberately for candidate/report references; do not pretend the current definition-only registry already reads them. Existing repositories retain authority; the graph is reconstructable derived data, with no arbitrary edge-write endpoint.

Missing or unavailable required endpoints remain unresolved requirements tied to their candidate field; they are not fabricated versioned nodes or dangling indexed edges. Graph extraction must preserve the invalid candidate and actionable findings rather than fail before draft retention.

Each selected kind's trusted adapter supplies:

- Exact required definitions/materials/interfaces, an inspected base if present, and governing policy/source revisions.
- Actual supported reads, contributions and resource consumption/production, with owner, role, quantity/unit and timing where meaningful.
- Relevant native consumer/interaction obligations and known reverse consumers for the requested change.
- Explicit unresolved requirements and links to the corresponding native validation evidence/findings.

Start with recipes and a distinctly different existing kind: a selected owner status-policy revision. Preserve current vocabulary such as `requires`, `produces`, `derives_from`, `implements`, `contributes_to` and `governed_by`; add canonical `reads`/`consumes`/validation or presentation relations only when a real extractor and consumer need them. [The canonical vocabulary](../../../invention-graph.md#3-relationship-vocabulary) controls meaning; this is not permission for arbitrary relation strings or for implementing every future relation now. A planned `produces` edge means what successful crafting would produce, not that an output already exists.

Edges retain exact `sourceRecord`, assertion basis and bounded qualifiers; source references identify their revision. Native extraction of a candidate's requested fields is `compiler-derived`, not proof that the candidate is admitted. Native contract descriptions may be `host-enforced` only within their actual supported behavior. A hypothetical interaction remains a separately labeled, attributable hypothesis and cannot satisfy a required dependency.

### Coverage and frontiers

Retain three separate facts:

- **Projection coverage:** complete/page/unavailable for a named authorized source/query and snapshot.
- **Mandatory-check coverage:** complete/pending/unsupported for the selected family's stated obligations.
- **Broader interaction coverage:** explicitly not evaluated or a named evaluated scope; never silently promoted by either of the first two.

A frontier identifies an authorized root/query, reason and continuation: missing adapter, stale source, work/page bound, or unresolved required binding. A hidden dependency can yield a permitted blocker without exposing its label/count. Missing data, forbidden access, unsupported computation and an empty result remain distinguishable where disclosure permits.

The finite recipe path can satisfy its existing native-family obligations while broader interaction analysis remains unevaluated. It need not wait for a universal solver. However, a new requested guarantee outside that envelope remains unresolved; a truncated required closure never passes. For a status-policy edit, required active-episode/dependency checks must use the actual status/impact owners; a complete list of status nodes is insufficient.

### Algorithms, invalidation and presentation

Use exact source reads, adjacency maps and a visited worklist; retain all relevant edges for checks, not only shortest-path witnesses. Classify cycles by actual relation/operation semantics: unsupported recursive expansion and zero-time scheduling fail; supported temporal feedback can be legal; a resource cycle needs its native source/loss contract. If a required cycle class has no analyzer, return unsupported/pending rather than accept it or reject every cycle indiscriminately. No all-pairs paths or full-world Cartesian validation.

Bind reports to candidate digest, generation, source/family/validator versions, grants, relevant policy and query membership. Existing native freshness dependencies are reused where applicable; conservative immutable-collection fingerprints remain until finer coverage is established. A newly matching consumer invalidates previous negative evidence. Source/index readiness must match before required analysis can pass. Restore rebuilds derived graphs and fences old continuations/approvals through existing authority.

The context builder renders only the required facts and short dependency explanations from this shared analysis. Human review uses the same refs and findings in an accessible expandable relationship list; the agent can inspect further pages through the same service. No full graph serialization is added to every model call. A visual node canvas remains deferred.

## 5. Small native work plan and readiness projection

Extend existing draft/review/operation records where necessary; do not create another project identity system. The first slice may use existing request/root/session lineage with one selected draft. Cross-session project creation beyond that supported mapping stays explicit rather than silently treating a Macrofold session as the project.

Persist bounded requirements with stable local IDs, source message/reference, hard constraint/preference classification, accepted changes and unresolved decisions. Model suggestions about fulfillment remain suggestions until native checks or an explicit human decision establish the relevant claim. Free-text constraints that cannot be verified mechanically remain clearly reviewable; never label inferred intent fidelity a deterministic pass.

The native validation record references the candidate/graph snapshot and stores required check IDs/versions, prerequisite check refs, outcomes/findings, coverage, assumptions and applicable evidence. Existing validators choose obligations; the model cannot omit a check or certify itself. Structural errors are cheap; required missing mechanics stop before optional enrichment. Reuse existing qualified family evidence only when its versions, parameters and assumptions apply. A static shape check does not establish physical behavior.

Most initial checks are synchronous unpaid functions composed inside save-for-review. Keep transaction/snapshot/replay semantics from the [technical design](../world-agent-context-tech-design.md#6-submit-completion-and-recovery). If an applicable required check cannot complete in the bounded native slice, retain the candidate with pending analysis and a continuation; do not hold a transaction or paid harness open. The first release may refuse unsupported long analysis with a precise blocker; a general job executor is not required to claim the supported finite path works. Any enabled asynchronous stage uses existing durable attempt/eligibility/funding records and publication fences.

Expose independent readiness facets derived from actual records: candidate saved, required checks, review decision, installation receipt, presentation adequacy, knowledge and instance/use outcomes. No giant overall status enum combines all of them. A short player label such as draft/blocked/awaiting review/ready to craft is derived conservatively. “Ready to craft” means an available learned technique under its stated conditions, not guaranteed ingredients or completion; current craft admission still checks them.

Store no live filesystem-generated artifact as authoritative design. Provider outage, cancellation or supersession preserves native records; missing optional art never undoes accepted mechanics. Real spending, privacy and revocation stay outside fictional rewind.

## 6. Concrete first-version proof

The initial implementation gate includes all of the following; a blank graph interface or future-only TODO is insufficient:

1. **Sling:** inspect exact materials/family; project draft → required materials/family/proposed output; run recorded native checks; show saved review and separate not-installed/not-crafted facts. Graph/context/review references agree.
2. **Gathering tool:** project a real finite resource/yield dependency and native consumer consequences, proving the extraction is not keyed to weapons. Unsupported quantity or resource binding produces a retained finding.
3. **Owner sleep-policy revision:** project attribute reads/rates, affected capabilities, separate expenditure/fullness interactions, dream linkage and relevant active episodes through existing owners. Retain exact whole-policy semantics; omission/removal remains explicit. No bed behavior is invented.
4. **Failure and refinement:** changed material/definition, missing required source, stale frontier, new query member, invalid cycle, allowed temporal dependency, duplicate/lost-response submission, cancel/restore and reduced grants. Preserve unrelated applicable evidence and expose blockers.
5. **Presentation:** one actual adequate existing recipe representation, a no-new-asset policy change, and a synthetic required-representation failure. Optional polish remains unstarted with no purchase.

[Candidate graph example](examples/candidate-graph.yaml) and [pipeline/readiness example](examples/pipeline-state.yaml) are illustrative projections, not executable schemas or claimed runtime results. Graph/report bodies remain server-side; the agent usually receives the short summary, blockers and exact refs.

## 8. Completion boundaries and work ownership

WW18 now includes the candidate graph and shared scoped analysis; WW19 includes retained requirements/checks/readiness in save-for-review; WW22 includes lifecycle/evidence continuity and broader existing kinds; WW23 includes the concrete first-version proof and harder design witnesses. The same task IDs remain. INV-11 owns larger mandatory validation, INV-15 graph expansion, INV-12 presentation generation, INV-17 composition and INV-20/AC repertoire execution. DI owns invalidation correctness.

This changes the earlier recipe-first optimization plan: graph/validation/pipeline foundations are required initial deliverables, not optional later investigation. It retains the small model-facing interface. Generic graph databases, new orchestration services, full graph editing, arbitrary recursive recipes, paid art and exotic-world execution remain deferred. A first-version component is complete only when its supported path works or its unavailable branch is truthfully represented; empty abstractions are not completion.
