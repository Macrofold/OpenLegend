## 1. Experiment and dependency boundary

**Hypothesis:** two well-made MetaHuman foundations can become a small reusable OpenLegend kit, with continuously adjustable identity/body shapes, independent presets and modular clothing, while preserving attractive results and ordinary browser performance.

Use MetaHuman to supply the difficult anatomical foundation. Use Blender and the existing character-family machinery to prepare and evaluate a bounded set of shapes. Do not reconstruct MetaHuman's full identity solver or embed its editor, DNA evaluator or cloud services in the game. Exported assets retain their licenses even when the software is no longer required at runtime.

Implementation is authorized as a standalone private proof. The dedicated branch starts from the integrated local main; preserve the existing pilot and do not reset, stop or commit another task’s work. Use an isolated external Unreal project and art workspace. No game database reset, ordinary starting-world replacement, production release selection, provider generation or art-skill edit is required for the POC.

The [feature specification](metahuman-foundation-poc-feature-spec.md) owns the replacement recommendation and user-visible scope. Current [people authoring](people-from-parts-authoring-contract.md), [world appearance](../worlds/base/people-appearance.md), [art direction](../../art-direction/decisions.md#current-direction-at-a-glance) and [storage](../asset-workflow.md) remain authoritative outside this experiment.

## 4. Execution sequence

Each gate produces reviewable evidence before the next expensive step. An implementation can report a failed hypothesis without being allowed to claim success. Apply [MHP limits](../limits/metahuman-poc.md) and the current spending/verification rules. The installed engine's `Engine/Plugins/MetaHuman/MetaHumanCharacter/Content/Optional/` must include nonempty texture-synthesis archives (`*.ar` under `TextureSynthesis/`, including subfolders) and body textures (`BodyTextures/*.uasset`). Follow the installed plugin's own optional-content check if the layout differs. [Epic setup instructions](https://dev.epicgames.com/documentation/en-us/metahuman/getting-started-with-metahuman-creator). If only 5.7 is usable, first record a version-specific export/API smoke result; do not mix 5.8 instructions with guessed 5.7 calls or create a multi-version compatibility layer.
3. Create a blank external Unreal project and enable MetaHuman Character and Python scripting; restart when prompted. Use the operator's authorized Epic account; texture acquisition/auto-rig may require its cloud access. Do not reuse Higgsfield credentials or assume website login is editor login. Installation checks alone do not establish working cloud access or export. No provider image generation is needed.
   Keep its project name at most 20 characters and absolute project/output paths shallow: native TextureGraph cooking rejects paths longer than 260 characters. Use the [pricing and license guide](../../art-direction/research/3d-pixel-worlds/tool-and-license-notes.md#price-thresholds) for corporate-group revenue, authoring seats and the distinction from Unreal-runtime royalties; zero game users does not itself establish an exemption. Keep proprietary assets/code separate from the AGPL repository; copying Engine/plugin code into it is not part of this plan.
5. Record private-evaluation permission before asset use; resolve public browser distribution/customization-kit rights before publication/adoption. This requested POC selects a licensed candidate for private evaluation, not a permanent exception to the normal CC0/CC-BY source policy. If the applicable terms are unclear, keep the result private and ask the owner a specific licensing question; do not assert either blanket prohibition or blanket permission.
6. Verify existing private asset authority and preservation access using the [shared authority procedure](../asset-workflow.md#shared-asset-authority). Do not alter cloud permissions or publish publicly as a shortcut. Account for settled and outstanding charges under Mike's task-specific $100 ceiling, including earlier work and unresolved commitments; additional software/seats/compute need approval before exceeding it. Earlier main-thread spending approvals are not new POC allowances.

**Exit:** one supplied preset can be opened and saved, the selected versions and lawful evaluation path are recorded, and an export destination is ready. A hardware/auth/license blocker is an actual blocker, not permission to redesign the experiment around a different source.

### Gate 1 — one attractive complete person survives export

1. Start with the adult masculine foundation, chosen from a supplied preset close to H02. Review a neutral front, both profiles and three-quarter view before editing. Use MetaHuman's own face/body tools, not a new image-generated graft. Aim for a fit adult with coherent shoulders/chest, natural neck and a strong but believable jaw. Keep reference screenshots beside the viewport.
2. Make one bounded adjustment toward the approved athletic references using the existing physique controls and compare matched views. Prefer a recipe adjustment within the exported range; do not pursue a perfect production body or start a sculpting loop. Height, fat and muscularity are correlated parameters; pin the measurements intended to stay fixed and inspect the result. A slider name does not guarantee an isolated deformation. [Body Params](https://dev.epicgames.com/documentation/metahuman/metahuman-creator-body-params-tool-in-unreal-engine).
3. Save the neutral identity before making samples. Remove source outfits and verify that chest, abdomen, pelvis, back and thighs exist underneath. Retain complete anatomy; add separate opaque fitted linen coverage for all review captures. Clothing opacity/double-sided rendering must not conceal a missing torso.
4. Request the necessary textures and rig once. Normal full-rig creation opens the Epic login flow; texture download alone only checks existing authentication. Export **geometry** plus the DCC/source package. Require the DCC completion manifest and actual baked head/body/eye maps as well as DNA: a positive-size ZIP can be a failed DNA-only partial export. Raw material-source textures are shader inputs, not finished skin. A completed DCC ZIP is still not a browser-ready GLB. Geometry Export creates Unreal skeletal meshes, including a full-body option; export those through the supported skeletal-mesh interchange path into Blender. Material instances also need conversion. [Export tools](https://dev.epicgames.com/documentation/metahuman/metahuman-creator-export-tool-in-unreal-engine), [FBX skeletal-mesh pipeline](https://dev.epicgames.com/documentation/en-us/unreal-engine/fbx-skeletal-mesh-pipeline-in-unreal-engine).
5. Start from one consistent mesh LOD. Compare source LODs visually and select the highest-quality one that can plausibly meet the character profile after preparation. Do not independently remesh samples or assume the full cinematic rig will fit the browser. Keep the original high-quality export for comparison.
6. Prepare the single neutral through §§5–7, export an ordinary GLB and load it in the existing art inspector. Inspect clay first, then material finish. Match neutral expression, view angle, framing and lens when comparing source and export. Look at front, both profiles, three-quarter, back and neck close-up. Compare under daylight and warm/fire light, then at the default game camera.
7. Record source → Blender → browser screenshots with the same pose. Identify whether a defect first appears in source geometry, conversion, materials or lighting before fixing it. Do not spend time sculpting anatomy to compensate for a colour-space error or incorrectly placed eyeball.

**Exit: required pass.** A complete, attractive covered person works in the browser and fits the geometry/material/size profile. Motion and required clip checks remain pending Gate 4; label them pending rather than claiming a strict full-character pass at this stage. Record Mike’s body/head selection, or his explicit delegation of that selection, before making wardrobe or the full sample batch. Delegation does not supply final browser acceptance. If the source itself looks wrong, choose a better supplied preset; do not start another unguided head repair project. If conversion fails, try one focused fix or one evaluated exporter shortcut, document its result, then stop that path for a decision.

1. Hold safely preserved hair work. Resolve backward elbows before further garment or hair work: compare the original source, retargeted export and actual shared actor to locate the first defect. Reuse exact accepted Idle/Walk/Run sources and the existing retargeter. Export stable in-place clips with the motion metadata expected by the actor. Do not generate motion just because the skeleton changed. Fix the source-to-target mapping, rest pose and joint orientation before altering the clip itself.
   Different arm rest bends need the mapping's explicit `alignRest` selection for both upper arms, forearms and hands, using the actual target bone names. Forearm-only alignment can leave the upper-arm direction and hand compensation wrong; copying turns from unlike rests can reverse elbow flexion. Compare the original source and transferred elbows, wrists and palms, including bends between keys. For a limited source-track repair, verify complete local rest frames, hierarchy and timeline before preserving unrelated channels. Exact export readback alone can retain a bad intermediate; a fixed world-axis sign is not an anatomical bend test when the shoulder rotates.
2. Use a known-good permitted premade garment compatible with the selected body/rig as the control. Preserve its source geometry and carry its actual package information, including any authored body visibility maps, through the existing conversion and part owners. Inspect complete anatomy and an unmasked garment/body diagnostic separately; qualify the intended package on one body through export/reimport, Idle/Walk/Run and transitions in the shared actor. Verify visibility-map linkage, UV interpretation and exact canonical coverage before applying it. ## 5. Geometry, topology and rig preparation

### Coordinate and identity contract

Normalize once into the existing glTF-axis/metre family convention; retain the source-to-family transform in the manifest. Unreal centimetres must not become metre-scale giants. Use anatomical crown/sole landmarks for height, excluding hair, shoes and attachments. Apply height exactly once to mesh positions, joint positions and parts around the sole. Keep head proportions and foot placement consistent with the selected source.

For every mesh sample verify the same vertex IDs, triangle ordering, UV correspondence, material partition and anatomical meaning. Equal vertex count alone is insufficient. Split UV/normal vertices must preserve a mapping to shared anatomical source vertices. The neutral supplies the index buffer and remapping for all shapes; do not run independent decimation, remeshing, triangulation or nearest-position matching per endpoint.

Native serialization may reorder faces or control points without changing topology. First accept an unchanged selected-LOD triangle/UV layout directly. Otherwise recover canonical IDs through exact, unique material-partition/UV-face/corner matches, covering every source face/corner/point and retaining the neutral’s canonical ordering. Extra native control-point copies may share a canonical vertex only when their positions and complete named skin weights are exactly identical; never average differing copies or infer identity from nearby positions. After this lossless normalization, canonical vertices remain bijective: missing, ambiguous, conflicting or merged anatomical points refuse. Native muscle-low lip copies demonstrate this distinction; the full sample set and posed result still require qualification. Higher source LODs with different anatomy/UV topology cannot substitute for the selected corresponding LOD.

Use an existing suitable LOD if possible. If reduction is necessary, derive a single retained topology and source-surface correspondence from the neutral, then evaluate that same map on every sample. Protect eyelids, nostril boundaries, lips, ears and the neck seam. An exporter that cannot preserve/recover reliable IDs has not passed the kit gate; do not patch it by matching every character independently.

Prefer the complete source's matched head/body. If runtime face selection needs a separate head mesh, split it at one fixed mapped boundary across every sample. Neck seam pairs must share evaluated positions, compatible normals and weights in every pose. Never remap an arbitrary CC0 head onto this body merely to preserve the previous pipeline. Test eyes/teeth/mouth interiors as geometry, not painted details.

### Reduced runtime skeleton

Preserve the original source rig externally. Compile a recorded, parent-first retained joint map under the current character joint/influence budget. Keep the locomotion chain and the head/neck/eye/jaw joints needed by the chosen representation; helper/twist/finger reductions are explicit losses to inspect, not silent improvements. This proof qualifies locomotion and rest hands, not all finger gestures.

For removed joints, map weights to the selected retained deform ancestor, then retain the strongest permitted influences and normalize once. Reconstruct retained local transforms from evaluated world transforms when intermediate ancestors are removed; simply deleting nodes changes animation. Use source rest matrices and sampled joint head/tail landmarks to populate the existing rest-hierarchy contract. Recompute inverse binds for each evaluated body through that owner; never reuse one body's inverse binds on another.

Check exported source joint orientations against the existing landmark-based evaluator. If a retained change of bone roll cannot be represented, constrain the sampled controls or report a contract gap before changing generic runtime math. Do not claim exact reproduction of MetaHuman joint/corrective behavior from positions alone. The source rig can use more bones and nonlinear correctives than the browser kit.

Gate rest pose, raised arms and bent knees against the source, then the actual locomotion. Reduction fails if it produces collapsed shoulders, reversing knees, neck cracks or visibly different silhouettes. Do not raise shared budgets or ship the full source rig as an unmeasured shortcut.

## 6. Portable shapes and recipes

Use **two independent families** for this proof. Shared topology is required within each, not between them. This avoids inventing a cross-sex anatomical morph and makes any future decision to merge families evidence-driven. The family cannot encode gender identity or game statistics.

| Control     | Study definition                                                                                                                                                                        |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Height      | Male 1.70–1.95 m, reference 1.80 m; female 1.55–1.80 m, reference 1.65 m. Uniform stature scaling, not limb proportion editing. These are proposed proof ranges, not engine/world laws. |
| Muscularity | Normalized 0–1, neutral 0.5; approved lean-fit and muscular endpoints. Keep stature and fullness as stable as the source permits; record residual coupling.                             |
| Nose width  | Normalized 0–1, neutral 0.5; bounded anatomical change, preserving nostrils and surrounding features.                                                                                   |
| Jaw width   | Normalized 0–1, neutral 0.5; bounded anatomical change, preserving mouth interior and neck transition.                                                                                  |

Height displayed as 75% means `minimum + 0.75 × (maximum − minimum)`; it never means 75% of a person's current height. Store actual units/values as required by the existing family definition. A non-height bipolar slider uses the existing neutral convention: `negative = max(1 − 2s, 0)` and `positive = max(2s − 1, 0)`. Geometry is neutral plus weighted endpoint-minus-neutral offsets. Do not make a second implementation of this formula.

The existing compiled schema requires frame, stature and age controls. For each single-frame adult study family, frame is fixed at 0 and age at 30 using equal minimum/maximum/default bounds; use identical frame endpoints/zero deltas and one age sample where the schema needs them. Do not display these as working sliders. In `packages/domain/src/appearance.ts`, allow equal bounds in family validation, define a fixed control's fraction as 0, and retain rejection of any recipe value different from its fixed value. Percentage resolution must yield that fixed value; range calculation must return the single allowed point. Numeric/percentage consistency checking uses absolute difference for a zero-width range, as the native resolver already does, rather than division by zero. Reuse the existing non-draggable UI treatment, hiding these fixed fields in the study's control selection rather than fabricating variation. Check fixed frame/age, invalid off-value input and unchanged ordinary sliders through both native assembly and browser admission. Do not add fake age targets or a compatibility adapter to avoid this small current-format contract correction.

Use one neutral face entry per family and saved recipe combinations for the initial face presets. This proves bounded face variation, not a large library of unrelated identities. Hair/coverage/eye selections use the existing selection roles. Material palettes and dependency landmarks must be expressed in the actual current format, not extra fields a runtime silently ignores.

The private study uses one `character` presentation group for its complete character presets, including body, face and selected parts. Presets remain group-local patches under the existing validator; no cross-group exception or second recipe format is introduced.

Save two additional feminine presets at low/high in-range height and different nose/jaw weights. Keep all presets visibly adult and fit. They are authored examples, not restrictions on other coherent bodies after adoption.

**Nonlinearity experiment:** for each family evaluate all eight corners of the three bipolar shape controls, the neutral, the three presets and two new intermediate recipes. Height endpoints can be checked on the already evaluated minimum/maximum silhouettes. Compare reconstructed endpoints to their prepared source samples on the same retained topology; target maximum anatomical position error is 0.1 mm before height scaling. This measures reconstruction, not fidelity to the unreduced cinematic surface. For two representative combined settings per family, also author a source combination and compare silhouettes, eyes, lips and joint placement. These four source combinations are validation oracles, not substitutes for runtime interpolation.

Do not expect a linear sum to reproduce MetaHuman's nonlinear solver exactly. If an otherwise valid range has one problematic interaction, allow one paired corrective per family using the existing corrective mechanism: store the combined source minus the uncorrected sum and activate it continuously using the same participating weights. Recheck corners and intermediates. If more extensive solving or ongoing manual per-character repair is required, report the independent-kit hypothesis unsupported at this scope. Do not secretly narrow the advertised range; a proposed narrower range needs the visual selection decision recorded before acceptance.

## 7. Material finish, eyes, hair and facial movement

An Unreal material instance is not a portable PBR material. Prepare base colour, normal, roughness/metalness and permitted opacity using existing browser material support. Keep colour textures in sRGB and data maps in linear space; verify normal orientation and tangents through the actual exported mesh. Do not bake directional scene lighting into skin. Share sensible atlases and preserve enough face texel density; cinematic maps are source material, not mandatory player downloads.

The current compiled family supports colour/normal maps, scalar roughness/metallic values, palettes and tint masks; it does not expose Unreal's complete shader graph. Start with those supported fields. Mask eye-colour changes to the iris so the pupil and sclera retain their authored colours. Record losses from simplifying skin/eye materials and judge them in the browser. If adequate quality needs an unsupported material feature, demonstrate that specific gap before proposing a scoped material-owner change; do not silently add ignored texture fields or recreate a cinematic shader system.

The experimental shared [cutout contract](people-from-parts-authoring-contract.md#skin-age-and-material-production) adds standard `MASK` and two-sided cards, with actual native packing evidence but live-family/performance qualification still open. Native groom tangent RGB encodes strand direction, not an ordinary normal map; do not connect it as one. Ordinary-PBR brown is an authored approximation. The current inspector can play a named diagnostic without Idle/Run and isolate a local model; these capabilities do not relax game-actor requirements or qualify the kit.

Inspect eyelid contact with the eyeball, iris depth, sclera exposure, highlight placement and shadowing. Do not approximate every Unreal eye-occlusion layer with a flat opaque dark mesh. Check nostril cavities, lip volume, mouth interior and teeth from both profiles. A neutral face must pass before adding makeup, hair or brighter lighting. Finish should match the grounded, believable game direction; photorealistic pores alone do not establish style fit.

Hair remains a separable mesh with a stable scalp attachment. Test only one existing natural-looking premade card style after animation/clothing; use the mapped scalp surface and existing material owner. Check hairline, silhouette, highlights, transparency and moving-camera stability from several angles, then report usable results and material limits. The earlier geometric-hair studies remain preserved and unselected. Do not refine them, author a hair system or expand the library. Skin/eye colour and hair choice should not modify facial topology.

**Facial-export exploration — required measurement, not a complete expression-system pass:** export left/right blink and a modest jaw opening from each neutral foundation into a standard GLB diagnostic using the source's evaluated rig. Prefer an evaluated existing exporter before writing a rig solver. Play those clips in the current inspector, and compare open/half/closed lids and the mouth to source frames. Record missing shape correctives, teeth motion and whether output contains usable bones or morphs. Expression poses are not identity targets and must not be added to the player face sliders.

The [free Fab head exporter](https://www.fab.com/listings/88fa82af-3210-42e1-81f0-9a613da436ef) advertises glTF/ARKit shapes; evaluate its exact version/license and source/target topology on one head. The [MetaHuman-to-GLB project](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/README.md) describes a Sequencer bake followed by Blender extraction, and discloses missing fine correctives and eye/material issues. Its approximately 40 MB example is not evidence that our payload budget passes. Use these as bounded exporter candidates, not accepted black boxes or reasons to add their viewer, orchestration or public hosting.

If a converter supplies standard expression shapes, preserve a minimal diagnostic subset rather than hundreds of source morphs. Record the exact bake/remapping path and licensing before reusing code. A full facial rig, expression transfer across all mixed identities, expressive gameplay and speech remain adoption work; neutral sliders and this diagnostic cannot certify them. If even convincing blink/jaw export is unavailable, the final recommendation must state that consequence prominently.

## 8. Clothing and modularity

Each family retains a complete body mesh. Underwear, premade garments, hair and the rigid accessory are separate parts. A premade control includes its verified authored visibility data: source-defined always-covered faces may be hidden through the existing exact-topology `hiddenRegions` contract. Preserve unmasked diagnostics and inspect every opening and supported pose; additional ad-hoc masks cannot excuse visible fit or conversion defects. Removing a garment restores underlying coverage immediately. Do not remove anatomy from the editable source or replace it with a garment shell. Any native shrink/corrective behavior not carried by the current contract remains an explicit qualification gap.

Fit once on the family's neutral body, then use the current surface/bridge/rigid part binding contract. A close-fitting vertex binds to a declared anatomical region's triangle with barycentric coordinates and an offset in its local frame. Body-derived garments retain that source-triangle correspondence through cuts, relaxation and thickness; discarding it and rebinding nearby opposing surfaces can assign cloth to the wrong leg. Thickness copies share their attachment and skin weights. Binding is an authoring operation, not an unrestricted nearest-surface search on every character edit. Sleeve/armpit/hem vertices need appropriate bridge or garment-shape treatment rather than projection onto the nearest thigh or opposite arm.

For native wardrobe intake, verify the selected item's visibility map and rest rig, not just its FBX shell. A combined source mask stays with its compound part unless independent per-piece coverage is authored; separate meshes alone do not establish independently removable coverage. When the retained rig's body and garment deform differently, test a weights-only transfer from the actual canonical body/head field through existing surface helpers. Limit eligible support by garment bounds and anatomical side; include the lower head/neck for a collar without admitting the face or hands. A compact nondrawn support may copy only referenced source triangles, retaining their explicit source IDs, shape targets and reviewed weights. Compare the ordinary compiled normals visually: this compiler recomputes them rather than retaining native custom corner normals.

Evaluate the shaped body first, then the garment against that shape, then apply the same wearer rig/motion. Reuse transferred and reviewed skin weights. Fit loose hems with sufficient clearance and a real silhouette; do not shrinkwrap every surface into body paint. Use the existing paired fit corrections or bounded variant support only for observed failures, never a hidden manually fitted outfit per recipe. Inspect elbow/shoulder/hip motion and layer intersections before accepting.

The rigid buckle/pendant follows an authored attachment frame derived from stable landmarks/binding, with scale rules recorded; it must not stretch with a muscular chest. This proves the rigid attachment mechanism, not necklace-chain simulation or arbitrary armour fitting. A premade design can have distinct bindings to the two families; garment asset identity and material design stay shared while those bindings are explicit data.

Acceptance includes underwear-only and dressed views, static extremes and all four motion cases. Small unseen intersections can be recorded; visible body breakthroughs, floating shoulders, cardboard coverage, closed openings or missing anatomy fail. No physics cloth, auto-tailoring service or new armour taxonomy is needed.

## 9. Verification and performance evidence

All implementation mechanisms are **experiments until measured**. Reuse earlier valid checks only for unchanged code/assets; no claim of 100% safety or visual quality follows from source inspection. This proof does not call cognition, alter prompts or change world data. If implementation starts touching those paths, stop and rescope rather than claim they are unaffected.

| Complete anatomy and coverage | Underwear-only, isolated body/garment and back/side views; no hollow torsos or cardboard pelvis covers. Required pass.                                                                                                                |
| Sliders and presets           | Both families, all endpoint/corner cases and held-out intermediates; same-pose comparisons, no snapping/tearing and no vendor requests. Required pass.                                                                                |

Use the game's default camera plus a close portrait; a flattering fixed close-up is insufficient. Keep camera, light, pose, outfit and resolution constant in comparisons. Include a neighbouring ordinary person/reference height for scale. Each repair gets the same views before/after and the relevant affected check; do not regenerate unrelated evidence merely to accumulate screenshots.

Include the latest preserved SAM/MHR + CC0 candidate in the visual comparison when its exact asset can be recovered, using the same framing and light. Show the concept beside both candidates, with explicit notes about silhouette, eyes, nose/lips, jaw, neck, musculature, hair and material finish. Do not modify or finish the main candidate to produce this baseline. This is an art comparison; differing geometry/materials make it unsuitable as an isolated evaluator-performance baseline.

### Controlled performance experiments

Use the same machine/browser, fixed canvas resolution/DPR, camera, lights, exact assets and motion. Record versions, thermal/background conditions and timing method. Do not compare a bare old head to a fully dressed textured new person and attribute the difference to the evaluator.

The private comparison’s `profile=1` frame-capture controls use `ScenePerformance`, including its CPU histograms, optional GPU queries and resource estimates. Start/save captures through the visible controls after the prescribed warmup; exported reports include exact recipes/compiled references, browser/module identity, start/end framebuffer/DPR and configuration/visibility changes. Reject mixed or hidden workloads. CPU brackets cover update through render submission, excluding frame wait; 0.25 ms histogram buckets are not exact raw percentile samples. Ordinary scene recording still requires its permitted world projection; the private study explicitly opts into rendering-only records. Recipe and capture JSON share the existing local-download behavior. Actual capture/drag/baked-baseline/lifetime evidence remains required.

Edit capture records event timestamps, requests replaced before presentation, unresolved work and at most 1,024 submitted updates. Whole-call CPU samples qualify only when warm materials commit evaluation/fitting/mesh installation synchronously; asynchronous material rows are separate. Event-to-submission is a software timing proxy, not physical display latency. Resource capture retains at most 64 scene teardown receipts with existing owner/texture/mesh counters before and after destruction; driver/GPU heap memory remains unavailable. These controls observe actual manual study use and do not automate or replace its required journeys.

1. **Baked vs adjustable:** render the same evaluated character once as a baked mesh/rig and once through the family actor, matching materials, joints, triangles and clips. Measure one wearer, then the four-character comparison scene. Warm each case for 10 seconds; collect three alternating 30-second samples. Report CPU frame-time p50/p95, GPU timing only if the platform provides it, draw calls, actual payload, decoded estimates and live resource counts. Source conversion time is a separate metric, never runtime latency.
2. **Dragging:** run 20 deliberate sweeps across the same control range. Measure recipe evaluation/mesh update p95 and input-to-visible-update p95. Proposed study thresholds are ≤16 ms p95 CPU update and ≤100 ms p95 visible response on the recorded development machine. One pending update per frame replaces superseded drag work; do not accumulate a queue or rebuild unchanged texture/rig resources.
3. **Idle cost:** after a recipe settles, shape/part evaluation must stop. There is no per-frame MetaHuman solve, wrapping or full-body refitting. For baked vs adjustable steady rendering, investigate p95 CPU regression greater than `max(1 ms, 10% of baseline)`; unresolved regression fails the current POC performance target. Report both absolute timings and the comparison; these thresholds are provisional acceptance targets, not measured capacity guarantees.
4. **Lifetime:** switch presets/families and create/destroy the preview 20 times. Live owner/resource counters return to their baseline after teardown; memory must not grow monotonically through those cycles. Report unavailable GPU memory rather than inventing a measurement. Shared immutable family data and each wearer's mutable buffers/rig must have distinct ownership.
5. **One-change diagnosis:** if applying a corrective, material simplification, exporter replacement, rig reduction or contact fix, compare before/after with only that variable changed. Reuse existing renderer timing/resource diagnostics; add minimal diagnostic fields to their owner only if absent. Do not build a benchmark framework or run paused automated suites.

Pass the existing `art-tool.py report --profile character --strict` for every completed full-character review GLB and assess the **aggregate family/parts dependency payload** separately. Static intermediate exports and head-only expression diagnostics are labeled incomplete/diagnostic rather than falsely passing the full-character clip contract. A GLB pass alone cannot bound a larger loaded kit. Current checker values include 40,000 character triangles, 2,048-pixel texture edges, 8,388,608 total base-level texture pixels, 8 materials, 64 joints, 4 influences and 16 MiB encoded output; [A3D limits](../limits/3d-pixel-art.md) own the shared constraints. Verify actual current tool values at execution, report any mismatch and do not silently increase them. Full-quality authoring sources remain external and are not loaded into the browser.

These workloads answer the four-character proof. They do not establish crowd scale, low-end mobile performance, production creator completeness or cognition regression coverage.

## 10. Operator commands and implementation checks

The experimental offline adapter is `scripts/art/metahuman-study.py`; `--help` describes its pinned conversion manifest. Actual-source preparation, compilation and visual/rig qualification remain required. It fails on missing required source artifacts and writes fresh output directories. Record the working source-export command after Gate 0 rather than inventing a universal Unreal command line.

Implement two adapter operations: `prepare --samples <manifest> --out <fresh-directory>` writes the Blender master and authoring descriptor; `compile --master <blend> --descriptor <json> --reference <exact-reference-json> --out <fresh-directory>` delegates to the existing compiler and packages its outputs. Paths are external. The sample manifest names each family, neutral and six endpoint IDs, their files/checksums, source state, LOD and conversion settings. It is conversion input, never a second runtime appearance definition.

The descriptor omits its own reference and compiled digest to avoid a hash cycle. Offline compilation can use the real exact reference computed by `assets prepare` from the frozen descriptor manifest; keep the candidate explicitly unpublished. Publication still commits the descriptor before its dependent artifacts; browser admission requires the currently permitted published closure. The live study passes a valid `PersonAppearance` with recipe, compiled artifact reference, permitted `compiledPath`, parts and matching definition. Keep private masters out of browser dependencies. Do not forge catalogue approval, bypass `admitPersonFamily`, edit the production lock or install a world family merely to open the study. Gate 1 can inspect a local GLB before private publication; Gate 3 needs valid permitted descriptor/artifact references. Mark unavailable preservation/access as blocked, not published.

## 11. Stop conditions, adoption and extension

Stop dependent work on unresolved rights/access, unusable export, broken correspondence, unacceptable neutral anatomy or budget failure. Allow one focused repair per failed gate; a second substantial workaround needs an explicit decision rather than silently becoming another custom character system. Preserve failed artifacts and their explanation. Correct routine wiring mistakes within the experiment, but do not solve a failed source assumption by adding a new renderer or full facial solver.

On success, propose a separate adoption change: select the source-license exception, finalize the supported controls/family decision, finish expression/hand/contact qualification, integrate the source adapter into the existing people route, and replace only the affected source foundation. Retain useful source-agnostic motion, part-binding, actor and inspection improvements. Do not add migration support for old development characters; no real users require it. Preserve source/study assets and useful decisions through the existing archive, independently of disposable development saves.

Staging preserves private study assets and records exact qualified inputs for that later decision; it does not install them. The current [appearance installer](../../apps/server/src/appearance-installation.ts) requires a published runtime release with **public runtime descriptors and compiled JSON**. A private study index or restricted runtime wrapper cannot satisfy that contract. Public runtime rights, adoption and publication therefore remain separate prerequisites; this proof does not create a private installer, grant access, publish publicly or edit the game’s asset selection.

Expansion uses the same seams: more authored face entries/targets, independent fullness and regional controls, body shapes, fitted wardrobe parts and animation clips are data plus qualification. New controls need corresponding eyes/joints/garment effects, plausible ranges and interaction checks; adding a slider label alone is not implementation. The description-to-recipe step can later use the game's existing AI boundary, but must choose supported parameters rather than invent topology or execute code. Broader expression behavior is a separate missing capability, not a reason to mix identity and animation weights.

Report reuse against the actual qualified outputs, not a promise that every future body fits:

| Later change                                               | Reuse and rebuilding                                                                                                                                                                                                                                  |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Another recipe inside the tested envelope                  | Reuse source meshes, topology, UVs, rig IDs, part bindings, source visibility maps and motion sources. Re-evaluate fitted geometry/rests and export as needed; check the new combination's openings, hair fit and contacts. No vendor call is needed. |
| Athletic base or endpoint edits with the same topology/UVs | Reuse tooling, original garments/cards/maps and source clips. Rebuild the body kit and affected fits, skin/rest calibration and derived exports; requalify coverage and motion. Stable IDs alone do not prove the old fit still works.                |
| New topology, UV layout, seam or rig                       | Re-author affected surface bindings, canonical face masks, skin mappings and retarget profiles. The original art and source clips remain reusable inputs; compiled arrays and previous fit evidence cannot be carried over blindly.                   |
| Production visual polish                                   | Separate art work after this feasibility proof. One checked card style is not a hair library, and plausible prototype anatomy is not a finished production body.                                                                                      |
