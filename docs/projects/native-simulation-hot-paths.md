# Rust simulation and player-view preparation

| Status      | Current progress                                                                   | Last updated |
| ----------- | ---------------------------------------------------------------------------------- | ------------ |
| Not started | Implementation steps and isolated adoption checks are designed and await approval. | 2026-11-20   |

During a walk, residents and the player should see the same permitted facts, hear the same speech and get the same reactions. The AI panel should show the same totals a fresh read would return. Save recovery should return the same accepted changes, and an NPC should receive the same decision input and apply its reply exactly once. These designs target repeated preparation for those journeys. What bystanders should notice or remember is a separate open product decision. ## How to run the experiments

Perception and attention accounted for 31% of sampled Rust CPU, save preparation for 8.17%, NPC decisions for 8.68% and player views for 6.42%. These category totals rank where to look. They do not estimate the savings from any one change. The detailed work recorder missed events, so use its counts to locate candidates and rerun focused counts to make decisions. Each lettered change below is an **experiment** with its own control. Begin with the first eligible change in each family. Carry any adopted change into both sides of the next comparison. Remove candidate-only code when a change is rejected or inconclusive.

1. Recheck the named callers against the selected source and freeze the affected outputs and failure cases. Run the narrow work-count diagnostic before expensive comparisons. Record actual removed work and any scans, synchronization, charges or queries it introduces. Confirm that the workload exercises the changed path. An arm that rarely encounters eligible work stops after this screen.
2. Verify the real callers using fixed inputs and the same clock, random state, authority and durable contents. Compare identities, order, exact encoded or decoded outputs as specified, effects and error outcomes. Exercise failure and retry before timing. Separately observe live visibility, reply and save behavior under the normal clock. No new test suite or permanent experiment switch is needed for these checks.
3. For materially exercised arms, use the [ordinary stand-alone comparison](../limits/native-simulation-core.md#nsc-l10--stand-alone-rust-server-comparison), with three interleaved pairs and fresh databases on the managed 16 GiB worker. Use the 26-actor opening, actual player stream, ordinary clock and one-second saves, both controlled replies, unchanged 2 GiB allowance, and existing controlled HTTPS fixture. Use ordinary movement with the AI panel closed. Add the smallest matching visible-panel, held-reader or dense-observer case only where a changed boundary needs it. Freeze inputs, allowed work variation, decision metric and applicable gates before dispatch. Keep work-count diagnostics out of clean timing.
4. Lead with server and PostgreSQL CPU as percentages of one logical core and achieved game speed. Compare combined CPU per completed game-second. Report median, mean and p95 with sample counts, clock debt, actual memory, reservations and SQL work. Separate command response, stream receipt, browser display and durable acknowledgement. Use the existing browser check when a display target affects the decision. A database change can earn its place with a repeatable material reduction in SQL work and no material cost elsewhere. A gain inside normal repeat spread is inconclusive. Require equivalent completed gameplay, privacy, save continuation and the applicable [timing and durability targets](../maintainers/native-simulation-core.md#applicable-multiplayer-timing-policy). Preserve failed evidence. [Comparison method](../performance/measurement.md#planning-comparisons)

These are local changes to existing owners. Native reception and record changes serve both Rust hosts and must keep mixed-host callers working. The player-view and NPC formatter experiments start in the stand-alone application. The browser wire, saved format and bridge contracts stay current and common. World definitions continue to own sensing, attention and cognition policy. A second observer using another installed channel or life must still receive their own facts; shared immutable definitions confer neither observation nor permission.

## 3. Separate expensive display work from motion

The browser uses preferences for rendering, job results for actions and conversation, and selected speech for captions and reply status. The Node-hosted server also consumes the pause-when-hidden preference. The browser's action composer uses displayed budget values to trigger a fresh interaction check. Actual spending is enforced by the server. Older personal stories and world events already have their own scoped pages. Count the repeated SQL aggregate first, and begin with the simpler event lookup if the aggregate is cheap or lacks a safe reuse boundary. ## 4. Prepare fewer storage and decision products

The present path journals actual changes, funds the output before acceptance and publishes one complete cut. The PostgreSQL writer batches the detached rows and retries the same immutable prefix. A newer accepted mutation can still prepare the next suffix and readers may hold an older input independently. The application likewise holds original and fresher NPC reads for distinct reasons. These experiments remove conversions within those owners.
