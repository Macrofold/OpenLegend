## 1. Scope and working rules

Use the [feature specification](runtime-unification-feature-spec.md) for behavior, baseline and the selected Q1–Q3 decisions. The source paths below are relative to the repository root; symbols, not historical line numbers, locate the work. Recheck them against the implementation branch before editing because the parent implementation is active.

For each conversion: trace its writers and actual readers; preserve required behavior in the selected owner; update current validators/storage/protocol/callers; prove the replacement through those callers; then remove the old path. A deleted type or lower helper count alone is not completion. Do not build both production paths behind permanent flags. A disposable comparator may evaluate the same immutable input twice during verification, never perform the effects twice.

Engine mechanisms own permitted evidence, deterministic changes, queries, scheduling, reference integrity and durability. Installed world owners choose what is conspicuous, how speech creates an obligation, sensory rates, retention and recognition policy. Policy content remains in `worlds/base/` where currently selected; no person/animal/item-name exceptions enter the generic scheduler or index.

## 3. Shared implementation contract

### 3.1 Change coverage without a new framework

Reuse `dependencies.ts`, `draft.ts: entityChangesBetween`, `native-change-feed.ts`, `entity-index.ts`, record-change preparation and the existing service publication lifecycle. Native draft changes are not committed notifications: consume them inside their owner, and publish consumer hints only after the appropriate accepted transition/durability boundary.

Each changed/due query returns either a complete affected set or **unknown coverage**, never an empty set for unknown history. A first read, mutable unaudited builder, restore/fork, missing ancestry, policy replacement or overflow uses the existing conservative rebuild. Track fallback counts and reasons with current diagnostics; a fallback on every ordinary publication fails the conversion. Do not attach an ever-growing event log to worlds.

Derived indexes hold IDs, revisions and necessary scalar metadata, not duplicate entity bodies or old worlds. Weak identity reuse is valid only for immutable inputs; request-local preparation must be released before unrelated waits. Rebuild indexes on restore without replaying acquisition, model dispatch or effects. Removal changes membership; a partial changed set never means omitted actors were removed.

### 3.2 Time and asynchronous work

Keep actual simulation deadlines in existing native boundary/ActorWork owners. Use their current condition crossings, sleep episodes, protection expiry, action completion and reminder deadlines. For a time-dependent predicate without complete dependency/deadline coverage, retain its conservative check on the smallest actual participating cohort until the owner can certify skipping it. Do not invent a general future-event predictor or infer that an unchanged object means an unchanged elapsed value.

Wall-time cooldowns remain wall-time; game-time deadlines respect pause/speed changes. Notifications coalesce pending work and preserve changes arriving during an inspection. Acknowledgment advances only the captured generation. Optional formatting/retrieval/AI stays outside the writer; ordinary physical effects and mandatory acquisition retain their phase boundaries.

## 4. RU01 — Read acquired surroundings once

**Files:** `apps/server/src/interests.ts`, `ai-director.ts`; domain perception current/grant readers, `perception-evidence.ts`, `attention.ts`, `entity-index.ts`.

1. Enumerate what the thought-input tuple actually consumes: received membership/classification, native condition eligibility, current goals/plan and personal evidence revisions. It does not need a freshly computed line of sight.
2. Add/reuse a small read-only domain selector over the existing current perception owner. Return permitted current subject IDs and the classification/change token needed by intake, with unknown/incomplete coverage represented. Read received classification, not hidden current `kind`/resource metadata from raw entities.
3. Reuse unchanged owner identity/revisions across publications. If classification can change without membership, include its acquired-change revision. Unknown identity remains a local subject; disclosure of a name is independently owned.
4. Replace `ThoughtExposure`'s geometry inputs, `spatialQuery`, `entityVisionQuery`, copied IDs and live classification `JSON.stringify` in the scheduler. Do not move that geometry into another server helper.
5. Drive refresh from acquisition/withdrawal and the existing state/condition causes. A held sample stays the same sample between permitted acquisitions; physical action admission still checks present geometry.
6. Update verification comparisons to use the same finite acquired cut. A delayed verification must not advance awareness watermarks or discard evidence that arrived during the wait.

**Proof:** repeated nonphysical publications and scheduler reads cause zero new sight queries/acquisitions; real entry/loss/classification changes, sense blocking, correction and restore reach the scheduler. Player/NPC context agrees about the received cut. Work is proportional to changed permitted rows; native sensing still pays for actual receivers.

2. Separate changes to value, confirmation time, availability and description. Unchanged confirmations refresh support without becoming semantic outward-change events. Keep each originally received timestamp and frame; no synthesis of unseen intermediate states.
3. Translate only already received changed facets through the installed world's existing semantic event policy. Preserve outward injury, incapacity, burning/resource/action changes currently represented by `visibleFeature`; do not blindly classify every XY sample as an event. Preserve exact supported cause/detail when the existing policy actually emits it.
4. Use the same change result for attention novelty and relevant reaction hints. Their acknowledgment watermarks remain separate because a queued description can be considered later than a movement sample.
5. Remove `sensoryProgress.features` and its per-observer scan only after all its detected changes have a mapped source facet or owner-specific change signal. On re-entry, actual acquisition and the existing recognition policy decide continuity; history reads cannot refresh the grace. The world owns semantic significance and grace, while generic acquisition supplies received changes.
**Proof:** arrival/departure, brief occlusion, reacquisition beyond grace, blocked perception, visible injury/fire, unattended animal, attention rotation and cold restoration. Compare supported facts and narrative availability under Q1, not byte-for-byte duplicate envelopes. Physical source change while unseen cannot produce an acquired notice.

## 6. RU03 — Refresh pending and due actors, not the whole world

### Navigation

1. Replace `NavigationCoordinator.reconcile`'s `worldRootEntities` population with `pendingNavigationEntityIds(world)`. This owner already includes action navigation, assembly exits and animal refuge/foraging proposals; retain all four.
2. Keep exact request identity, timeline, map, body/origin and current request validation. First simplify to iterating pending IDs, not a second queue-membership index. Reuse prior queued tasks by identity and preserve order/age, the 64-task bound and active-worker exclusion.
3. Skip reconciliation when world/request membership and task dependencies are unchanged, even if `WorldService.notify` only changed telemetry. On map/restore reset, terminate obsolete work through the existing lifecycle and rebuild once. Never suppress worker completion/failure wakeups.
4. If candidate data changes while its membership set is unchanged, process changed pending actors; membership identity alone is insufficient. Cancelled, dead or replaced subjects must retire tasks.

### Thought, maintenance and memory indexing

1. Extend the existing `activeIntakeChanges`/owner-change readers to identify actors changed by evidence, mind, goal, possession, capability, condition, acquisition or policy. Consume source revision changes from their real publication owner instead of calling `sourceRevision(id)` for every actor every time.
2. Preserve existing `ActorWork.refresh`/`refreshAffected`, ready IDs, fair order and deadline indexes. Retire the full-roster native predicate comparisons only for inputs with complete change/due coverage under §3.2. Global installed-policy changes legitimately select all affected participants once.
3. Keep maintenance-specific eligibility and learning actors that lack ordinary mind entries. Retain backlog changes, sleep/dream completion, resource pauses and resume. A global capacity change can wake existing pending tickets without reparsing each mind.
4. For `RecallService.indexMemories`, preserve model registration first: the existing `pending` call registers a model and seeds its queue, so a pending-only query alone would miss a newly eligible actor. Register newly eligible NPC/model pairs once in bounded batches on creation/model change/startup; then obtain pending actor IDs in a bounded batch from existing eligible source/index-attempt metadata, using its current revision/model identity. Do not copy bodies just to find NPCs, and do not issue an empty pending-source query for every NPC on each round. Merge committed source-change actors with startup/resume backlog; filter current NPC eligibility at dispatch.
5. Retain one batch per eligible actor per round, failed/uncertain-attempt semantics and funding checks. A dirty notice is not a durable job: startup reads canonical pending state, notifications follow commit, and a change during a run remains pending afterward. No new paid retry or periodic empty SQL polling.

**Proof:** telemetry-only notifications do no root enumeration or actor preparation; one actor change refreshes that actor and actual dependents; time-only need/sleep/deadline transitions still wake; map replacement, lost wakeups, cancellation, late worker results, failure/resume and restore remain correct. Measure CPU before async fan-out, not just the 64 returned tickets.

## 7. RU04 — Incremental history dependencies and due placement

**Files:** `hot-events.ts`, `history-residency.ts`, `world-service.ts: prepareSnapshot/installWorld`, `world-records.ts`, `retention-metadata.ts`, domain experience/temporal boundary owners.

Keep three meanings distinct: hot residency (where data is loaded), logical retention/permission (whether it remains usable), and physical reclamation (when storage is removed). Existing retained-source metadata is not automatically an exact index of hot event dependencies.

1. Centralize extraction of hot event references from awareness, memory/obligation and knowledge records. Preserve current aliases: event ID, obligation evidence and fulfillment event, and knowledge evidence. Use reference counts, not a boolean set: removing one owner cannot release another owner's requirement.
2. At the existing accepted record/publication boundary update a derived per-owner reference summary only for changed records/owners. Integrate it with existing record-change/retention metadata where meanings match; do not create another saved lifetime table. A cold loader has its own placement view and must rebuild the same summary for the exact records it loads.
3. Maintain the recent event tail and pinned-event membership incrementally. When references change, re-evaluate affected eviction candidates. Avoid filtering an unchanged whole event list on every save after the threshold, especially when fewer than the current eviction batch can be removed. Preserve event order and `archivedEventCount`; eviction never means forgetting.
4. Plan history placement once from changed owners and due deadlines. Reuse the plan for the pre-save hot-event decision and post-commit release; preview must not mutate the accepted index or mark discarded work complete. Clone only owner maps that actually change. Keep existing row/byte limits, agreement pins, occurrence positions and append proofs.
   Canonical list ordinals are finalized by storage preparation after preview selection. On release, rebind selected rows to those final positions and propagate them to the actual normalized arrays; a preview cannot assign future append addresses.

5. Maintain earliest sensory expiry per awareness owner and a derived global due index through the existing experience mutation/array tracking owner. Read the minimum without enumerating every actor at every native boundary; expiry visits due owners. Preserve exact logical expiry, accounting/revocations, cold sensory handling and saved continuation. This is not a slower forgetting cadence.
6. Extend the same changed/due placement selection to ordinary memories, summaries and action-occurrence tails. Their different retention rules stay with their owners. No serializing an unchanged row to discover its size; reuse existing immutable record size metadata.
7. On failed save, rollback, unknown lineage or restore discard the candidate plan, preserve the previous accepted summary and rebuild conservatively as needed. Use BK’s coherent live prefix and direct transaction’s durable cut; do not restore a separate journal/application stage. Add neither foreground whole-history SQL hydration nor another cleanup service.

**Proof:** shared references, fulfilled/cancelled commitments, knowledge pins, correction/forgetting, newest-tail retention, more than 768 resident events with fewer than 256 evictable, cold reload, expired sensory prefix, rejected save and direct-commit recovery. In a fixed-active-work workload growing old unrelated history must not grow ordinary-save visits. Full checkpoint/load remains proportional to saved content and is measured separately.

Build a lightweight selection of self/current evidence, required item/method/subject references, admitted inspection page and optional candidates. Exact ID lookup comes first. All current callers choose a deliberate complete or selected query; no silent default that rehydrates the old full inventory in ordinary decisions.
2. Extract current action/queued-plan bound item IDs into one helper used by observation and recall. Include equipped items and required cooperative/committed-work dependencies using their existing binding owners. Preserve supported command fields and declared bindings; do not replace them with heuristics about item names.

Compute it lazily only when a supply/carrying consumer needs it. Cache only when all those dependencies are certified; otherwise a compact quantity scan is honest necessary work. Never claim absence from incomplete coverage.
5. Select learned-method IDs/dependencies before copying full recipe bodies. Preserve required known methods, recent guaranteed choices, current action pins and ordinary inspection/discovery. Use existing knowledge/recall indexes for optional retrieval, not another embedding store or model call.
6. Remove `candidateSet`'s whole-note body-byte prepass after replacing it with admitted-metadata/selected-body accounting. Add that narrow canonical-document adapter, not a second note store. Hydrate/render only selected rows. Preserve local individual versus live-body bindings, corrected/forgotten filtering, note revisions and read-only place/map annotations. Expose identity/revision/subject/byte metadata from `mind_knowledge_documents` through its existing codec and actor-scoped read owner; use canonical IDs/revisions to join the existing `recall_vectors` scope before hydrating selected bodies. Retain the current optional ranking/Jev and embedding-admission policy. 7. Replace one Known-place query per supply candidate with an exact multi-place method on `MemoryRepository`. Deduplicate the bounded requested IDs, select newest eligible supported capsules per place, batch correction/source metadata and hydration in one read snapshot, and map results back in caller order. Missing/corrected/unretained places stay unknown. Use bounded SQL parameter chunks and the existing read lane; do not just launch unbounded `Promise.all` over the old method. 9. Prepare finite permitted data before waits, and retain current source/revision/authority rechecks after waits. Let complete required support overflow refuse/narrow through existing outcomes; never truncate it to make a request fit. Preserve optional incomplete versus empty results.

**Proof:** small inventory produces the same available choices; large inventories preserve inspection and bound tools; inaccessible containers and reserved stock cannot yield false supply claims; required personal notes and methods survive optional selection; multiple known/unknown/corrected places share the batch without leakage; one large pile does not clone its full contents for sixteen references.
