# Desktop access, release and hardware reach

**Target.** Two friends, one on Windows and one on an Apple Silicon Mac, can install Open Legend, enter the same hosted world if admitted, and return to the same characters, possessions and changes. The download is a game for players. Neither friend needs Unreal Editor, an Epic developer account, a console, a second operating system or a local AI model. Both need a supported device and a connection to that world.

## Which experience is available where

| Person or device | Promised experience |
| --- | --- |
| Windows player | A native downloadable game with ordinary keyboard and pointing-device play, full character control and the supported game journeys. Windows is the first internal integration target. |
| Apple Silicon Mac player | A native macOS game with those same journeys and access rules. It can use less expensive lighting or foliage. A Windows virtual machine, remote Windows workstation or streamed video does not qualify the Mac player. |
| Friend following an invitation in a browser | A legible landing page that identifies Open Legend and explains how to play on the visitor’s system. Offer the appropriate available download or a way to open the installed game. Show other supported downloads so automatic detection cannot trap the visitor. Display published requirements, approximate download size and release availability before the visitor commits. |
| Creator, researcher or operator in a browser | Independent access to the tools their role permits, including the Cognition Lab, world authoring and operations. They can inspect or work without a local Unreal installation where the tool does not require a live playable view. A handoff into the game must say what needs the game and preserve authorized context. |
| Browser-only, Intel Mac, Linux, mobile or console player | No native consumer release for these devices is promised by this specification. Tell visitors what is available. A future browser game, streamed session, offline edition, or console port has a separate product decision and its own access, cost and qualification requirements. |

Windows and Mac are product targets. Publishing dates, the precise supported operating-system versions, installer channel and tested device floors belong to [the decision register](README.md#decisions-and-needs-design). Each public channel describes what its players can actually install that day. A Windows-only internal build or public preview must describe its scope accurately.

## From an invitation to a return visit

1. **Receive.** Opening or forwarding a world invitation can suggest a destination. Display only information available to the visitor. Redeeming a valid offer grants the account its specified role after the world’s access checks. Character control is acquired separately. A revoked, expired or exhausted invitation leaves the visitor free to select an accessible world or request a new offer. [World access invitations](../../glossary/access-and-participation.md)
2. **Install and sign in.** Offer the correct release, show progress and explain how to recover from an interruption, missing files, low disk space or an unsupported device. Reuse a compatible installation. Keep editor tools, credentials and private studies out of the download. Shared maps, placement seeds and asset downloads may contain public scenery. Inspecting them must not disclose a camp’s location or an occupant’s identity beyond what the recipient is permitted to know. Installation alone cannot select a character or redeem an invitation. After sign-in or an account change, open the intended destination if permitted. Otherwise offer an accessible world or explain why entry is unavailable.
3. **Enter.** An admitted returning player can resume their eligible character on either platform. Handle a world that is paused, full under its published admission policy, unavailable or newer than the client with a distinct explanation and appropriate action. Never create a replacement character or world silently. After sign-out, the game, launcher, recent destinations and support views on a shared machine must expose only the new user's permitted information. A revoked asset cannot be served again by the game from its cache. Previously delivered files or knowledge cannot be recalled from a recipient.
4. **Leave and return.** Quitting, uninstalling, switching devices, an interrupted update and a laptop sleeping do not erase committed world changes. Rejoining reacquires current permissions and control. If a player switches from Mac to Windows while still signed in on Mac, the control rules of the world govern both sessions. Menus, installs, retries and offline waiting cannot create a second copy of a committed action. The [play chapter](play-and-perception.md) defines recovery when the outcome of an action is uncertain.
5. **Update or recover.** Tell the player when an update is required and what to do. A failed or partial update leaves either a known compatible build that may play or a recoverable update screen. When an older build is incompatible, refuse entry before the player can issue actions. A corrected or reverted client release reconnects to the current permitted world. Restoring a world timeline is a separate, authorized operation. An absent optional art update uses the approved fallback. Missing required data that makes controls, disclosures or physical boundaries unreliable blocks the affected play and explains the recovery.
6. **Manage local settings.** Make display, readable interface scale, audio, captions, camera motion and input settings reachable before entering a demanding scene. Keep usable local preferences on relaunch. Give the player a way back to safe display settings if a choice makes the game hard to read or too slow. Display, device and focus changes must release held input. Sleep, switching away or restoring a window cannot send a stale action. Players may leave or sign out even when the host is unreachable.

Ordinary hosted play uses the player's computer for drawing and the hosted world for shared decisions. Losing the connection cannot turn a cached valley into a second playable timeline. A world configured for a single participant still follows its hosting and pause rules. Sharing a household or joining the same session gives each participant their own authorized perspective.

## Creator and operator journeys

| Situation | Observable result |
| --- | --- |
| A creator opens browser tools | Show the operations allowed for this account and role. In an authorized World Agent conversation, a creator can save an answer without taking control. Continuing from that answer requires an explicit request, the required character control and an admitted spending allowance. Within their grants the creator can inspect, approve or refuse a proposal. Opening the tool or saving an answer starts no paid work. Report the actual result of applying an approved change. |
| An operator manages access or restores a checkpoint | Each operation requires its own grant. The restored world opens paused. Desktop clients discard requests and views tied to the superseded timeline. Work recorded in the checkpoint, such as an unfinished walk, follows the world’s continuation rules under current permissions. Opening the console never takes character control or counts as player activity. An unauthorized account receives a safe refusal. [Save and restore](../../save-and-load.md#spatial-state) |
| A researcher examines character behavior or an artist reviews a scene | The Cognition Lab and asset studies show only material authorized for that use. Study results remain separate from actions in the shared game world and private NPC recollections. Where the answer depends on how Unreal actually draws a scene, link a playable preview or moving capture identified by the selected release, viewpoint and settings. Other browser tool tasks work independently. |

If the player crosses from the installed game into a privileged tool, say what the tool is for, recheck identity and permission in that tool, and provide a way back to ordinary play. Signing out, switching worlds or losing permission invalidates the handoff. Support reports and general logs may identify a release, error and affected operation without exposing credentials, private speech, memories, raw saves or protected media. ## What a modest laptop may change

An M2 MacBook Air and a modest Windows laptop are **design targets**. Seeing the world at a comfortable pace should not depend on premium graphics features. Device generation by itself is insufficient to promise support. Memory, graphics, display resolution, thermal limits and the released game all matter. The richer setting should reward stronger hardware with better light, depth, surface detail and movement in the landscape. The modest setting must still deliver the game's invitation to explore.

| May differ by device or setting | Must agree wherever the world gives the same facts |
| --- | --- |
| Fine shadow edges, density of decorative undergrowth, cloud/fog detail, reflections, animation detail in the distance, display resolution | Time and weather state, walkable ridges, a door or bridge's position and condition, travel distance, reach, cover and the world’s sight/hearing rules |
| Surface detail of a cloak, hair strands, background figures’ cosmetic detail | Who and what a player is permitted to identify, useful equipment cues and which action was accepted |
| Keyboard labels, local display preferences, accessibility treatment of motion, effects or sound | Character identity, available actions, shared possessions, remembered knowledge and durable consequences |

For example, two friends at the same gate may see different shadow softness. Each viewer can identify an approaching friend only to the extent their character recognizes them. A quality setting, caption or map cannot disclose a concealed person’s location beyond what the viewer could otherwise sense. Equally, expensive ornamental grass cannot be the sole indication that a field boundary blocks a cart. The world owns whether an obstruction or hazard matters.

Keyboard and pointer are the desktop input baseline, including an alternative to hover-only information and an accessible way to inspect, select, confirm and cancel. Design focus and action names so directional navigation and a future controller can serve travel, inventory, conversation and construction. Complete gamepad mappings, TV layout, console certification, touch input, assistive-technology combinations and supported UI languages require explicit scope and evidence before being advertised. Basic scalable text, captions, reduced motion, clear contrast and focus are requirements on both target platforms. ## What qualifies a supported device

| Evidence | Workload and success |
| --- | --- |
| **Required functional pass, per advertised OS** | A friend starting from a clean machine finds the download, installs, signs in, joins a real shared world, completes ordinary play, updates and returns. Cover expired access, interrupted install, sleep/reconnect and an incompatible release. Pair a Windows and Mac player in the same changed settlement before claiming shared desktop play across both. |
| **Required measurement, per candidate tier** | Identify OS, processor/graphics, memory, power mode, display and internal resolution, game/content release and quality settings. Measure cold and repeat entry, then sustained play long enough to reveal heat-related slowdown on a fanless laptop. Walk through sunlit leaves, turn toward a distant valley, enter a crowded lit settlement, converse and edit a structure. Record typical and slow frames, worst visible pauses, input response, memory use, download/installed/patch size and time to resume. Measure hosted response separately from drawing. |
| **Required pass once the device promise is chosen** | On each advertised floor, the ordinary route and stressful scenes must meet the published settings, responsiveness and frame-time targets while preserving the cues above. Check text, focus, captions and construction at that resolution. An average frame rate, editor screenshot or test on a more expensive machine cannot qualify the floor. On failure, repair the experience or publish a narrower measured device claim. An unqualified platform remains labeled as such. |
| **Human acceptance** | At the modest setting an uncoached player can pick a destination, find the path, use a door, distinguish a heard cue from a visible source, identify a permitted site and understand a change on return. Record where they wanted to go and why. Keep this distinct from an art approval or a performance measurement. |

Thirty frames per second allows roughly 33.3 milliseconds per frame. Sixty allows 16.7. These are useful comparison points when testing modest and richer settings. Publishing a minimum requires named machines, resolution, sustained frame delivery and acceptable stalls. A claimed player count also needs a measured shared-world workload. Adding scenery or switching the engine supplies neither result. Test a busy meeting at one site separately from the same number of people spread across the map. At both settings, approaching a new region must not load the world's entire catalog before a player can act. When optional detail is slow, keep supported input, permitted nearby cues and physical boundaries usable. Signpost any missing essential state until it is safe to proceed.
