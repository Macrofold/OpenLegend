# Enable live AI locally

Open Legend selects Macrofold for backend features when `MACROFOLD_API_KEY` is configured; otherwise it uses direct Jev/OpenAI adapters. Configured custom deployments can use the separate `MACROFOLD_MODEL_API_KEY` without replacing that backend credential. Native play requires neither. Conversation uses compact level-2 inference with Jev escalation. Independent workspace reflection requires Macrofold and PostgreSQL; direct keys support immediate decisions and cleanup. See [memory architecture](memory-architecture.md).

## Macrofold, embeddings and PostgreSQL

Use the settings in `.env.example`: `MACROFOLD_BASE_URL`, backend key, model/harness, billing mode, optional provider/Jev connection IDs, model-run cap, owner-selected `MACROFOLD_WORKER_ID` for native execution and per-agent monthly `AI_BUDGET_USD`. The backend key authenticates catalog inference and Runs; configured deployments can use the optional model key below. BYOK defaults to the configured OpenRouter connection for both Contributor and Jev; connection IDs select server-stored credentials, never raw keys in prompts.

Full native agent/harness execution requires a nonzero monthly agent allowance and an authorized existing Worker. OpenLegend does not provision or renew shared compute; its owner manages Worker limits and credit separately from the agent's Run budget. Direct inference needs no Worker. For local Docker, the API and `pnpm worker:docker` are separate processes; native Runs need that dispatcher. It also reconciles shared hosting, so its owner must coordinate startup. Enabled/sleeping metadata alone does not qualify Worker execution. Follow [Worker setup and coordinated cutover](ai-providers.md#shared-worker-setup-and-cutover), including `workers:use` permission and preservation of uncertain operation identities. September 20 live BYOK inference, embeddings and workspace publication are historical evidence for the previous caller, not Worker deployment qualification. See [pending Worker acceptance](maintainers/macrofold-worker-api.md#mw04--remaining-deployment-and-qualification-gates).

`MACROFOLD_RUN_MEMORY_MIB` optionally selects the memory allowance for every native Run, including continuations. Unset preserves Macrofold's default; a larger Host alone does not enlarge that allowance. Select a value that fits the approved offering after platform headroom. Larger allocations can reduce concurrency or increase paid compute costs; immediate inference is unaffected.

Macrofold normally listens on port 3210; OpenLegend's example configuration uses `PORT=3211`. The game and AI service need separate listening ports. Follow the lifecycle below to discover the actual Macrofold address. For Auth0, set `OPEN_LEGEND_PUBLIC_ORIGIN` to the actual game origin and register that exact origin's `/auth/callback` URL in the Auth0 application.

Restart after configuration changes and inspect the selected backend. A configured label is not live acceptance. Current model/effort requests and unverified compatibility are described in [AI providers](ai-providers.md). Set `OPEN_LEGEND_DATABASE_URL=postgresql://mzw@127.0.0.1:5432/openlegend` for this local database (adapt username/database elsewhere). To enable semantic vector recall, configure an OpenAI embedding key even with Macrofold: `OPENAI_EMBEDDING_API_KEY` falls back to `OPENAI_API_KEY`. Missing embedding credentials disable vector indexing and semantic queries; immediate decisions can still use structured recall. Install pgvector for your PostgreSQL major version and enable `CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public` in the game database (the server also performs this additive setup when its role has permission). Check the actual installation with `SHOW server_version` and `SELECT extversion FROM pg_extension WHERE extname = 'vector'`; a previously tested host does not establish this database's extension availability. All runtime storage requires PostgreSQL with this extension; unavailable embeddings retain structured recall. Defaults are `text-embedding-3-small`, 512 dimensions; explicit embedding reservations count against the same actor cap. SQLite support and its import tool have been removed. Use current-format PostgreSQL backup/recovery tools with the server stopped; never point two writers at one database.

### Use existing model deployments for decisions and replies

Select hosting in Macrofold, grant the game principal access, then configure the existing `OPENLEGEND_MODEL_TARGETS_JSON` setting. Native judgments use `judgment`; chat replies use `npc_response_fast` and `npc_response_complex`, with the complex target also supplying higher decision generation. Either protocol submits immediate inference through the existing adapter without a Worker, sandbox or agent harness. Missing purposes retain current provider settings. A supplied target requires the Macrofold adapter; malformed settings fail startup instead of selecting a different model.

Set `MACROFOLD_BASE_URL` and a server-only `MACROFOLD_MODEL_API_KEY` authorized for deployment discovery, inference and original-Run recovery. When that optional key is absent, deployment calls use `MACROFOLD_API_KEY`; other backend features keep the existing key. Never put either key in target JSON, the browser or a world save. Supply trusted workspace/deployment references; the [current follow-up](projects/custom-models-implementation-plan.md#current-configured-service-follow-up--october-25-2026) owns Mike’s supplied IDs and current workload-suitability decision, while these UUIDs are illustrative:

`judgment` requires a SystemOne deployment. It submits the same permitted state and independently named Choice, Score and Noul questions; no chat prompt substitutes for a scoring head. Score may be fractional and Noul is a probability, not a boolean. Existing consumers retain their own thresholds and native action checks. Native targets accept an optional output reduction but reject `structured_output`; they do not stream. `AI_JEV_ONLY` can use this native route while continuing to disable generation and embeddings.

Chat targets require an OpenAI-compatible deployment. `auto` selects supported JSON Schema or JSON-object output. Explicit `json_schema` and `json_object` require those capabilities. Select `prompted_json` explicitly for a text-only runtime; it receives schema-derived instructions and the same strict local validator. Invalid JSON/actions are withheld without another paid call or format fallback. Optional `max_output_tokens` only reduces the current caller/runtime allowance. Existing supported private preview can stream; a completed-only chat deployment remains usable. Public progressive speech retains its separate release requirements. Optional chat-only `chat_template_kwargs:{enable_thinking:false}` requires that exact advertised capability. For Qwen3, the revision selects the `qwen3` reasoning parser and this native boolean disables thinking; a `/no_think` prompt is not reliable. Omission preserves the model default, arbitrary template options are rejected, and reasoning text never substitutes for missing final content. Required character context and local schemas remain intact when a small model reports context overflow.

Mike has ruled the original Kev 8,192-token and Huihui 4,096-token configurations unsuitable for the measured current character requests, approximately 19.9k judgment and 29.4k generation input tokens. Retain their deployment references and grants. Larger configurations remain separate qualification work: Kev 65k has encoding/accounting evidence only, and Huihui 32k is declared capacity without qualified caller execution; both larger service windows ended before inference admission. Preserve required evidence when selecting or qualifying a configuration.

Add `deployment_revision_id` inside a target's `model_binding` to pin a serving revision UUID. This is distinct from a Hugging Face source commit. Otherwise Macrofold selects the serving revision when accepting each request. Earlier accepted answers retain their original revision; ordinary recovery, credential rotation and equivalent worker replacement do not independently invalidate them. Warm compatible work adds no hosting metadata poll. Unavailability or an operator-stopped service does not cause the game to start hosting or replay inference. Later new requests can discover repaired capabilities through bounded shared preparation. Restart OpenLegend after changing its local target settings.

These targets leave player-expression interpretation, embeddings, reflection and full harnesses on their existing routes. Higher decision generation uses the configured complex target unless an explicit model is selected through `DECISION_ESCALATION_MODEL` or Cognition Lab. Namespaced catalog IDs use the existing Macrofold inference adapter and backend key; unnamespaced direct IDs retain OpenAI Responses. Changing a held higher request across these transports requires selecting the model in settings and preparing a fresh stage. Its policy, current decision schema and one-call entitlement remain unchanged; choosing a deployment does not grant another model call.

Keep `AI_BUDGET_USD`, per-request limits and no-call controls enabled even on prepaid capacity. Configured deployment request fees and native reservations are zero; zero allowance still prevents a call. Shared hosting is separately funded, and missing token usage remains unknown telemetry. These game budgets do not cap idle/GPU/storage charges. Closing the game never destroys shared hosting. No study manifest or model-comparison campaign is needed; optional tools retain their [existing generation-comparison scope](../scripts/decision-benchmark/README.md#custom-generation-experiments).

### Catalog output format

The exact Macrofold catalog model `meta/muse-spark-1.3-contributor` defaults to `prompted_json` without additional configuration, based on the [response-reliability qualification](verification/cognition-context/2026/2026-11-03-response-reliability.md). Other models retain `json_schema`. Ordinary and higher replies, independent voice and other immediate catalog callers use the same policy; model selection, credentials and billing remain unchanged.

`catalog_structured_output` in the existing setting remains an explicit override. For example, this deliberately selects strict schema output for a Contributor diagnostic:

```dotenv
OPENLEGEND_MODEL_TARGETS_JSON={"schema_version":1,"catalog_structured_output":{"meta/muse-spark-1.3-contributor":"json_schema"}}
```

JSON-object and prompted-JSON modes supply the exact schema in system instructions, counted inside existing input/cost allowances. Every mode retains local schema validation and native action checks without automatic retries. A catalog-only setting needs the normal backend credential or a matching shared lane, with no deployment workspace/key. Shared execution advertises its granted format before preparation; a local override must match it. Newly configured catalog lanes use the same Contributor default when their format is omitted; existing explicit lane formats remain authoritative. Deployment settings, direct OpenAI, embeddings, judgments and full harnesses retain their contracts. Restart the affected server/executor after changing code or configuration.

REST equivalents are `GET /v1/model-deployments?workspace_id=...` and `GET /v1/model-deployments/{id}?workspace_id=...`. These reads do not buy capacity or invoke a model. Inspect protocol/capabilities, serving revision, `state`, `admission_open`, retirement and observed capacity; a display name alone cannot establish a usable target. Managed capacity must have a positive loaded-worker proof; imported endpoints can have null replica observations. For local discovery, first register borrowed server use under the lifecycle below. Do not restart another checkout's preview. A discovery HTTP 403 means this application key cannot establish current access; it does not prove that no service exists. Have the deployment owner correct the intended key's scopes/grant rather than borrowing a neighboring project's private fixture credentials.

The deployment key needs `runs:write`, `runs:read`, `model-deployments:read` and `model-deployments:use`, plus an active deployment grant for its trusted workspace. The separate owner/admin credential manages hosting and grants; the game receives neither `model-deployments:write` nor upstream credentials. ### Local Macrofold server lifecycle

When an authorized development or verification task needs local Macrofold, ensure it is available yourself: **reuse an existing server; start one only when none is running; clean up task-started services when their users finish**. Do not wait for Mike to start it or ask for another confirmation just to start this dependency. Provider calls still require the existing [spending authorization and accounting](../.agents/rules/verification.md#spending). This procedure concerns local development, not changing a deliberately configured hosted deployment.

1. **Discover before creating.** Check the configured local `MACROFOLD_BASE_URL` and any shared server record, then inspect local TCP listeners in ascending port order for an existing Macrofold server. Identify the service using its process/checkout and `/health` JSON, not an HTTP 200 alone: the current endpoint reports `status`, `mode` and `configuration_ready`. Reuse an existing compatible server regardless of its port. A server still starting or reporting a database/configuration problem already exists; wait or diagnose that problem instead of launching a duplicate. Leave unrelated listeners alone.
2. **Serialize startup across agents.** Every agent uses the same per-user directory, `/tmp/openlegend-macrofold-<uid>/`, substituting the numeric result of `id -u`; worktree/task identifiers must not change that path. Acquire its `lock/` directory atomically with `mkdir`, and keep shared server and task-use records beside it. Record the lock owner's PID and process start time, keeping that owning process/session alive until the operation releases the lock; reclaim a stale lock only after verifying that exact owner is no longer running. Under this lock, repeat discovery before starting anything. If no server exists, try **3210, 3211, 3212, ...** and choose the first free TCP port. If another process wins the bind, repeat discovery and port selection. Keep the startup record visible until readiness or confirmed failure, so another agent waits rather than creating a second server.
3. **Use the existing Macrofold installation.** Read that checkout's applicable instructions and current startup documentation. Start only missing required dependencies, preserving their configuration and data. Do not run fresh setup, reset databases, replace credentials or edit the companion checkout just to start it. In the currently inspected checkout, an already prepared web application can be started from its repository root with `pnpm --filter @platform/web exec next dev -p <selected-port>`; recheck the installed command before using it. Start a Worker only when the requested native execution needs one; immediate decision inference does not. A missing installation or unusable configuration is a concrete blocker to report, not permission to substitute a different backend.
4. **Verify and share the actual address.** Use a bounded readiness wait and confirm database/configuration readiness through `/health` before dispatch. Record the endpoint, checkout, exact owned PID/start time or managed session identity, creator task and any dependencies this task started in the shared record. Set `MACROFOLD_BASE_URL` for this task's calling processes to that endpoint; do not rewrite a shared `.env` or another agent's configuration. Tell Mike which server was started or reused and which port it uses. A healthy local service alone does not establish working provider credentials, credit or live model acceptance.
5. **Protect concurrent users during cleanup.** Under the same lock, each agent registers its use before connecting and unregisters when finished. Mark a pre-existing, externally owned server as borrowed: never stop or restart it during cleanup. For an agent-created server, the creator owns cleanup. If other agents still use it, record an explicit cleanup handoff: the server remains running until the final registered user finishes, and that user may stop it only under the creator's recorded cleanup authorization. Recheck active users and exact process identity under the lock before shutdown; never kill by port number alone. Restore only dependencies started for this server that are no longer needed by anyone else. Preserve saved data and outstanding financial records, remove only this server's coordination records after confirmed shutdown, and report cleanup or the continuing shared use in the handoff.

Discovery, registration and shutdown must share the same lock: finding a free port alone does not prevent duplicate startup, and process ownership alone does not make shutdown safe after another agent begins borrowing the server. Release the lock after recording each coordination operation's outcome, including failures; do not hold it throughout model calls or gameplay. Keep credentials out of coordination files and logs. This is an agent operating procedure; the benchmark itself checks readiness but does not manage server processes.

The following direct-provider steps apply when the Macrofold key is absent and do not supply file-reflection harness execution.

## 1. Get a Jev key

Sign in at [TypeSafe’s API keys dashboard](https://console.typesafe.ai/keys) and create a key for Open Legend. The [official quickstart](https://docs.typesafe.ai/introduction/quickstart) links this dashboard. TypeSafe’s [home page](https://typesafe.ai/) currently offers a waitlist; if your account cannot access the console, complete that access process first. A key for an unrelated AI gateway cannot be substituted into the current direct TypeSafe adapter.

## 2. Get an OpenAI API key

Sign in at the [OpenAI API keys page](https://platform.openai.com/settings/organization/api-keys), select the project you want to use, and create a secret key for Open Legend. Ensure API billing is enabled for that account/project. The server uses the Responses API, so a restricted key needs permission to create responses. See the official [key setup guide](https://developers.openai.com/api/docs/quickstart#create-and-export-an-api-key) and [billing/key guidance](https://developers.openai.com/api/docs/guides/production-best-practices#setting-up-your-organization).

Copy keys directly into the local file below. Do not put them in a game message, a screenshot, a shared issue or a commit.

## 3. Edit the local environment file

Open `.env` at the root of this repository in a text editor. An existing installation already has this file; preserve its other settings. For a fresh clone only, copy `.env.example` to `.env` first.

Set these three values, replacing the placeholder keys:

```dotenv
TYPESAFE_API_KEY=your_typesafe_key
OPENAI_API_KEY=your_openai_key
AI_BUDGET_USD=1
```

Here, `1` is a $1 ceiling per agent per UTC calendar month. Configuration accepts $0–$100, with a $50 default, and atomic reservation honors the configured ceiling. The former hidden $50 reservation clamp is removed. Zero disables paid dispatch. Reservations and uncertain calls consume the admitting agent's allowance, which persists through restarts and cannot be rewound by world restore. See [the accounting contract](architecture.md#monthly-agent-spending).

Keep the existing `JEV_MODEL`, `OPENAI_MODEL`, and price settings for the initial test. The checked-in defaults are `jev-1.13.0` and `gpt-5.6-luna`. A different model needs matching explicit price settings; see [AI providers](ai-providers.md).

## 4. Restart the server

Environment changes take effect at server startup. If you started the server in a terminal, press **Control+C in that terminal**, then run this from the repository root:

```sh
pnpm run dev
```

For the built client, use `pnpm run build` followed by `pnpm start` instead. Do not run both servers on the same port. If Codex is running the current server, ask it to **restart Open Legend** after saving `.env`; it can restart the existing process without resetting the world. Do not delete `.data` to resolve configuration or port errors.

## 5. Refresh and inspect configuration

Refresh [the local game](http://localhost:3211/), using your selected port. With Auth0 or a custom host, open the exact `OPEN_LEGEND_PUBLIC_ORIGIN` configured above; `localhost` and `127.0.0.1` are different hosts, and the server refuses a different host in Auth0 mode. Then open **Game → Intelligence & allowance**. The ordinary panel shows intelligence availability and the controlled character’s allowance. In an owner-enabled god-mode session, **Connect intelligence** lists Jev and Language model as **Configured**, and **Monthly agent allowances** shows each character’s funds. A configured label means the server received a nonempty key; it does not prove authentication, model access or successful inference yet.

## 6. Make a first live request

With immediate inference configured and spending explicitly authorized, resume the world, move near Ada, select Talk, and send a short greeting. Observe the request status and the character’s actual reply, then review **Game → Intelligence & allowance**. Owner-enabled god mode additionally exposes call counts under **Execution details**. While the world is running, autonomous NPC thinking can also use the actor’s allowance. Pause when you finish the test.

If a request fails, inspect its recorded reason before sending again. Missing or rejected credentials, inaccessible models, insufficient provider funds, insufficient agent allowance, timeouts and invalid output are separate problems. The application does not silently retry paid requests. Live quality remains a separate acceptance check; follow [verification](verification.md) for the full playtest.
