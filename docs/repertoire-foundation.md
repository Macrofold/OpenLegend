# Repertoire-driven invention foundation

**Status: accepted target integration and staged implementation specification.** This is the integration owner for the [action repertoire](repertoires/actions.md), the [invention foundation](invention-foundation.md), live relationships, information artifacts and social arrangements. The [action capability contract](action-capabilities.md) remains the sole owner of grounding, invocations, activity control and participation. The graph, presentation, declaration, agency, memory and spatial specifications retain their semantics. Current delivery belongs to Architecture; tasks belong in INV/AC/EWF, with regression work in maintainer TODO.

## 1. Target behavior and scope

The repertoire is a design/evaluation catalogue, not the runtime capability registry. Its concept keys are not installed interfaces. Supporting an example requires supported host behavior, a compatible installed definition, legitimate invocation authority, adequate evidence, and actual native consequences. None follows from recognizing the sentence.

| Witness                                                  | Intended route and proof                                                                                                                                |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BLD-01 / OBJ-12: place a plank as a crossing             | Existing placement/support makes a useful arrangement. No compulsory bridge invention. Traversal still checks actual support and the actor's body.      |
| OBJ-11 / COM-08: ring a pot as the dinner signal         | An acoustic interface produces sound; permitted receivers may interpret a known convention. No compulsory new pot definition and no forced NPC summons. |
| COOP-01–04: hold, fasten and carry together              | Real role acceptance/readiness, overlapping contributions, shared instance identity and withdrawal; not sequential commands with fabricated helpers.    |
| ECO-03/04: borrow and return the same keepsake           | Custody, ownership, normative terms and exact instance identity differ. Equivalent materials cannot silently replace the keepsake.                      |
| ART-03 / KNO-07: draw a map or label a jar               | The information represents its author's evidence/claims. Drawing reveals no unexplored geometry; a label does not change contents.                      |
| SEC-09 / MAG-09: disguise or illusion                    | Render admitted observer-relative sensory evidence, not an omniscient truth icon. An apparent bird need not have a physical bird body.                  |
| FIR-03 / AUT-08: tend a fire, then use a feeder          | Actor labor becomes unnecessary only if a real machine-owned process supplies the work and energy.                                                      |
| BLD-05 / CBT-03: brace before removal; stop at surrender | Ordering and maintained constraints span an activity. Dependent steps use actual receipts and perceived evidence.                                       |
| LAW-01–12: promise, negotiate and establish a custom     | Communication/acceptance can establish terms or voluntary practice without installing enforcement physics.                                              |
| COL / TMP / SYN: unusual bodies, clocks and topology     | The common interfaces retain extension seams, but do not claim new solvers, cloning, time travel or graph-world traversal already exist.                |

The first implementable foundation is a usable relationship reader, shared world-level inspection and safe MCP access to existing native capabilities. It is not a new physics engine. Subsequent releases prove unlike domains rather than implement hundreds of named verbs.

## 2. One route for use, another for definition change

The World Agent routes to the existing action-capability/agency service for parameterized use and retained activities, and to INV for changing reusable behavior. Goal planning is not disguised as interpretation. A retained route or personal routine need not become a definition. Promoting a successful method to a reusable template is a deliberate separate operation.

The shared tool service must eventually support discover/inspect/prepare/start/status/cancel for an activity using the same typed calls, constraints, output ports and authority as player/NPC inputs. `ol_action` must not be limited to the concrete suggestion shortlist. The current native command adapter may remain finite while AC delivers the general representation. Do not expose a placeholder generic action tool that accepts effects the host cannot execute.

A World Agent investigation is administrative and can read authorized world facts; an NPC method executes using that actor's actual knowledge and senses. The two scopes cannot be interchanged. Broad read access never grants actor control, authoring permissions, revelation to every player, or additional spending.

## 3. Definition, live arrangement and evidence views

Use the [relationship graph](invention-graph.md) as one projection protocol with three independently versioned layers:

- **Definition:** immutable recipe/material/module/interface dependencies, source and output bindings, constraints and potential consumers.
- **Live:** actual ownership/custody, support, containment, attachments, current actions, work sites and processes. These are paged neighborhoods or overlays, not an eagerly rebuilt copy of every entity each tick.
- **Evidence:** observations, interpretations, authored claims and validation reports under their existing access/retention owners. Evidence of an interaction does not install that interaction.

Relationships belong to their actual semantic owners. The graph has no unrestricted `add_edge` mutation. A visual wire editor edits a supported port on a candidate; moving a node edits only layout. Runtime feedback cycles are not the same as recursive definition expansion.

### Identifiable multi-party relationships

An attachment, trade, agreement or joint activity that has roles, state, terms or a lifecycle is an identifiable record, not a collection of independent pairwise edges. Its owner projects edges such as `has_participant`, `uses_instrument`, `affects`, or `governed_by` from that record. Qualifiers identify roles and exact source versions. This represents an n-ary relation in an ordinary typed multigraph without a hypergraph database.

For a stretcher interaction, the record identifies the one stretcher, passenger, carriers, accepted method revision and current phase. Readiness/withdrawal live in the shared-work owner. For a loan, the agreement references the exact lent instance and terms; custody and ownership remain distinct state. A graph query never infers a joint lift merely because two independent actions mention the same item.

### Extraction and completeness

A kind adapter projects only relations its authoritative source actually defines. Unknown or unimplemented relations remain explicit coverage gaps. A current item `ownerId` may be projected as the current inventory-owner relation, but must not be misrepresented as a fully modeled legal title or loan. A support surface is not proof of a structural load network.

The initial reader indexes exact recipe inputs/outputs, installed attribute/sense host bindings, and explicit base derivation. Live inspection projects current item/actor/action/support facts on demand. General read/effect graphs, shared load, agreements and information carriers require their real source owners before extraction. A complete page in this implemented projection is not complete interaction verification.

Snapshot keys separate definition changes from live sequence/time. Reuse immutable definition indexes across ticks; never hash all live entities to serve a definition query. Restore changes the scope generation even when bytes match. Incoming and outgoing adjacency avoid full-edge scans; bounded paging reports continuation and scope. No materialized transitive closure, all-path enumeration or all-inventions Cartesian product is required.

## 4. Activities, operators and autonomous processes

Composition must declare which owner supplies ongoing work. An invocation can start a process that outlives it, but actor-dependent work remains dependent on an available actor. The common descriptor must expose required participation and resource claims; metadata does not mint extra hands or attention.

Keep one physical lane now. Existing concurrent speech/private operations retain their current semantics. Richer concurrency is released with an actual family that supplies resource-channel arbitration and safe interruptions. The initial generic API must not hardcode a universal two-hand anatomy; channels come from the compatible body/service.

A future joint family uses AC's invitation/readiness/start/advance/withdraw protocol. A worksite owns shared accumulated progress and consumed inputs; participants own their choices and current contributions. Start may atomically acquire required readiness, but minutes of committed work are not one reversible transaction. Reserve only near-term necessary resources. Stable acquisition order and timeouts release abandoned readiness; cancellation does not fabricate continued support or refund work.

First proof: one person holds a part while another fastens it, including refusal, loss of grip, departure, rest and same-version restart. Joint carrying follows only after its actual load and movement interfaces exist. An ordinary timer/device configuration stays use; creating new trigger/effect behavior is INV.

## 5. Information artifacts

Information is not an image file and a statement is not world truth. Introduce a family-owned content record only with a concrete note/map/diagram consumer. It uses existing IDs, provenance and record storage rather than creating another memory system.

A minimal content revision identifies content kind, author/source, language/encoding, bounded text or structured marks, represented references/claims, evidence scope/uncertainty and presentation bindings. A **carrier binding** identifies the physical surface/item or permitted nonphysical channel, occupied portion, readability and copying/modification rules. Content, carrier and rendered bytes have separate identities. Copying content creates appropriate provenance and a new carrier/copy identity without necessarily inventing a new mechanic.

A native writing/marking action validates tools/materials/carrier, starts work, commits the content/carrier mutation and emits permitted sensory effects. Generating a prettier rendering is asynchronous and cannot create the written message before work finishes. Reading uses available senses, detail, literacy/decoding and access. It returns what was represented, attributed to its source; learning and belief appraisal use CR/AG. A false label remains false, and changing it never changes the jar's contents.

A map's structured locations and claimed connections derive from permitted author evidence. Unknown regions remain unknown. The administrative World Agent can validate or inspect more, but cannot pass that knowledge into an NPC-authored map or image brief. Layout/art refinement must preserve content and uncertainty. Document semantics never come from OCR of a newly generated texture.

Editing retains previous content revisions where referenced by evidence; defacement/damage affects current readability under the carrier family. Existing memories of a message do not change when someone later edits it. Independent copying, publication, inspection and learning require their own receipts. Source text is untrusted data and cannot alter tool instructions or permissions.

First slice: a bounded plain-text note on an already supported carrier, with write/read/copy behavior and provenance. Maps, diagrams, music and executable instruction media follow distinct adapters. Until physical carriers/actions exist, do not advertise note creation merely because a content schema has been added.

## 6. Agreements, obligations and fictional institutions

Preserve the existing memory-linked commitment/obligation owner. It describes attributed or personal commitments today; it is not already a multi-party settlement engine. Extend it only when accepted offers/terms have an actual consumer. Do not install a second mutable promise store in the graph layer.

An agreement revision identifies parties/roles, exact proposed terms, deadlines in the appropriate fictional clock, involved item/resource refs, evidence/acceptance requirements, amendment rules, termination and permitted disclosures. Distinguish proposal, communicated offer, each party's actual acceptance, effective agreement, fulfilled/breached/disputed/expired state and release. One party cannot approve another's role or unilaterally erase jointly accepted terms.

Separate three layers: **normative fact** (what was agreed or owed), **actual behavior/evidence** (what occurred and who knows), and **enforcement** (a supported escrow, institution or explicitly magical consequence). Ordinary promises influence cognition and appraisal, not force actions. In-world theft or breach can be possible; fictional illegality is not platform authorization. Real account boundaries remain protected in every world.

A trade can atomically validate the exact accepted offer revision and settle both current resource transfers through one native owner. A promise about a later delivery uses retained terms and evidence; chat success is not delivery proof. Loans retain custody/title distinction and exact-item obligations. Anonymity filters public attribution without erasing private authoritative provenance.

First proof: offer and acceptance followed by exact native transfer, then a deadline-based personal commitment; do not build a universal court or a general contract language. Use registered term/predicate interfaces and explicit unknown/disputed outcomes. Lawfully authorized release of a claim is not permission to delete all parties' records.

## 7. Observer-relative presentation

The invariant is **faithfulness to the admitted observation model**, not disclosure of every underlying physical fact. Creator inspection can expose the mechanism; embodied presentation follows observer/sense/recognition and the world's actual illusion/disguise/occlusion rules.

An undiscovered trap cannot use a public fallback that identifies it as a trap. An illusion may depict a bird without a bird body only if an admitted effect produces that sensory evidence. A disguise changes supported appearance/recognition inputs, not another actor's beliefs by direct assignment. A pretend duel emits performance/gesture events, not real attack receipts. Unsupported deception is not an excuse for arbitrary client-side invisible collisions or inconsistent worlds.

Separate the authoritative presentation requirement from the permitted observer-facing projection. Asset reuse keys include projection identity when appearances differ; never leak hidden entity IDs, meaningful names or private previews through shared cache metadata. Compatible observers can share bytes; this does not require one generation per observer. Prefer finite admitted states, procedural effects and view-valid fallbacks.

Art refinements preserve selected apparent features and content. Meaningful changes to occlusion, recognizability, light, anatomy or geometry re-enter their native/invention owners. The art generator cannot supply the missing mechanics. Player UI may show an authorized designer preview while embodied characters still see only the admitted projection.

## 8. Validation of methods over time

Consume AC's typed method constraints and result bindings rather than author a competing condition language. Separate hard constraints, preferences, desired outcomes and uncertainty. The original request and accepted weakening/substitution must remain traceable.

Validation has two points: candidate/method preparation checks ordering, output type, resource claims and supported predicates; execution rechecks current prerequisites and maintained constraints at declared boundaries. A guard plus effect requiring atomicity uses one native transition. A cached successful preparation cannot reserve every future resource or guarantee another actor's later behavior.

Examples: `brace receipt -> remove beam`; preserve exact keepsake instance through every transfer; never open the sealed carrier; stop upon actually perceived surrender; retain sight while retreating where supported. An unsupported guarantee returns a blocker or an explicitly accepted narrower method, not a cosmetic success label. Loss of evidence is distinct from a false condition.

Scenario runners exercise sequences, interruption, participant withdrawal, multiple resources and passive interactions. Existing independent invariants remain mandatory; candidate-generated tests are supplemental. A failed final stage retains previous valid design work. Revising true intent creates a new candidate; fixing a malformed output does not require a whole-world redesign.

## 9. Exotic worlds: preserve seams, do not fabricate implementations

World-specific location codecs may represent surface points, graph nodes, portals or other spaces. The present spatial provider remains XYZ/surfaces. Generic tool references carry kind/identity rather than force coordinates into every payload. No new topology is enabled merely by accepting an arbitrary string.

A mind, body, controller grant and population group are different identities. A future split/clone/merge family must define resource partition, memory/evidence lineage, controller authority, pending work, lifetime, obligations and conflict reconciliation. Immutable IDs and idempotent creation remain engine guarantees. Do not merge memories or duplicate inventories by generic object copy.

Simulation time, possible future local-clock domains and real provider/accounting time remain separate. A local-time effect needs cross-domain event ordering, transfer and scheduling semantics; changing `deltaTime` is not a complete implementation. Fictional rewind cannot undo charges, external receipts or current revocation.

Deformation, living buildings and detachment need qualified body/topology/support/occupancy operations. Record absent host capabilities as G3 requirements or future qualified G2 work. A partial representational interface is not a solver. These are future tasks, not dependencies of the graph/MCP foundation.

## 10. Foundation implementation boundaries

Implement the core projection/index and strict shared tool service against the current immutable native records. Add a disabled-by-default authenticated MCP adapter that exposes only implemented read/preview operations. Keep local browser inspection behind the existing owner boundary; remote inspection requires its own world-bound credential and never browser cookies.

Use the official pinned SDK for protocol conversion, fresh request-scoped servers, no model-controlled principal/world selection, bounded inputs/results and no automatic paid work. Read-only previews can function without a paid session; mutation/session context and native Macrofold provisioning remain their existing INV-16/18 work. Do not counterfeit a unified native harness by exposing a standalone endpoint.

No new saved-world fields are required for derived graph indexes. Define cache invalidation on exact immutable source identity and restore generation. Keep adapters and traversal separate so new real relation sources do not rewrite MCP or AI schemas. Do not create dormant unconsumed runtime stores for future social/physical families merely to mark a task implemented.

Implementation/acceptance are tracked under INV-20 and the existing AC/EWF owners. All architecture claims must identify the delivered projection coverage. The complete graph, joint physics, information carriers, institutions, generated art and live Macrofold integration require their stated follow-up consumers and qualification.

## 11. Technical extension contracts

The shapes below specify future owner records, not new runtime fields delivered by the read-only bootstrap. Use the existing identity, native mutation, serialization and reference codecs when implementing each consumer. The point is to preserve required meanings, not to establish a second public schema or require a class for every row.

### 11.1 Source adapters and identifiable relationships

Keep traversal independent of the source model. A source reader accepts an authorized snapshot, resolves exact records and projects nodes/edges with provenance. A new adapter for a worksite, agreement or content carrier must supply its revision, disclosure projection, bounded enumeration and relevant invalidation inputs. It cannot authorize effects by returning an edge. The initial concrete functions are simpler than a general plugin registry; add a common adapter interface when a real additional source needs it.

A multi-party relationship is an owner-managed record with its own identity, not a clique of pairwise edges. Its projection is the record node plus role edges to exact participants/resources/definitions. Preserve at least:

```text
Interaction identity and source revision
  kind / exact implementing definition
  participant roles -> actor/body/controller references as appropriate
  actual role acceptance and withdrawal receipts
  worksite/object/resource bindings
  preparation, active and terminal status under the owning family
  current committed contributions and retained progress
  relevant clock, cancellation and recovery rules
  disclosure policy and source evidence
```

The graph can collapse that node for display, but must retain its identity and roles for explanation and impact queries. Two people carrying one stretcher must share one stretcher identity and one load owner; two loans concerning one item remain two independently attributable records. A role edge does not make an actor willing, knowledgeable or physically present.

Definition extraction is invalidated by definition/manifest changes. Live overlays depend on selected state, connected records and applicable geometry; evidence overlays depend on their actual record and source references. Merely advancing `simTime` does not change an unchanged structural record. Growing sources eventually need indexed source enumeration rather than increasing synchronous caps indefinitely. Pagination freezes the query/source binding and never implies full interaction closure.

### 11.2 Information record and carrier implementation

A first note implementation should use three existing-owner records or components:

| Record                     | Required fields and boundaries                                                                                                                                                                                                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Immutable content revision | Content identity/revision, kind/encoding, bounded text or typed marks, author/source identity, optional original/copy lineage, represented references/claims, evidence/uncertainty, and permitted disclosures. A represented entity is not automatically physically present or named to every reader. |
| Carrier binding            | Carrier instance/part or admitted nonphysical channel, exact content revision, occupied area/slot, marking method, current integrity/readability and family-owned access/decoding requirements. Do not attach an unbounded transcript to every entity.                                                |
| Reading/copying outcome    | Actor, permitted carrier/content projection, actual action receipt, source revision and acquisition conditions. Existing observation and learning services determine resulting knowledge/belief; an `inspect` tool alone does not create that receipt.                                                |

Write flow: bind a supported carrier and materials -> validate the exact requested content under the actor's evidence scope -> perform native work -> commit carrier/content binding and consumed resources -> emit the actual sensory event -> project reading opportunities. A creator placing content uses a separately authorized creator operation, not an imaginary actor writing session.

Copy flow: inspect/read at supported detail -> retain the represented content and errors/uncertainty actually available -> consume the new carrier/work -> create copy provenance. A map copy must not gain missing geography; a false label can be copied faithfully without becoming true. Copying an immutable content value can reuse bytes, but carrier identity, ownership and copying evidence stay distinct.

First release may limit content to plain text and one actual carrier family. Proposed starting bounds are 8 KiB text and 32 represented reference/claim entries per revision; qualify these with actual UI/storage/reader costs. Use registered language/decoding policies, not an LLM-generated interpreter or arbitrary active document. No file/URL fetched from in-world prose, JavaScript embedded in a document, OCR-derived authority, or automatic character memory grant is permitted.

### 11.3 Agreements and commitments implementation

Do not redefine the current personal obligation as a signed mutual agreement. A new agreement family needs a separately identified accepted-terms record linked to the existing participants' memory/commitment projections:

```text
Agreement revision
  identity / exact term-definition and prior-amendment references
  parties with role-specific accepted terms and authenticated action receipts
  resource/instance commitments, recipient and fulfillment predicates
  effective condition and deadline in an admitted fictional clock
  amendment, withdrawal, expiry and dispute rules
  evidence sources and known / unknown / disputed resolution
  optional admitted enforcement binding
```

Term evaluation uses registered predicates over allowed evidence; it cannot evaluate arbitrary code, query all memories, or require every promise to have mechanically verifiable satisfaction. Subjective promises can retain personal appraisal. Public agreement state and what each participant believes about it can differ.

Implement offer creation and exact acceptance through NC/AG and the owning agreement mutation. Accepting revision R does not accept revision R+1. Recheck actual parties, required participation, current items and term version at settlement. An exchange may settle atomically; a long-term promise cannot reserve another actor's behavior or hold the entire world transaction until tomorrow.

Where enforcement exists, it consumes agreement/evidence through its admitted interface and emits ordinary accountable effects. Escrow owns its deposited resources; personal commitments own no imaginary copy. Deactivation/removal of an enforcement definition follows INV-5 with deposits, pending claims and participant records preserved or explicitly recovered. A rightful waiver changes only that party's claim; it cannot erase historical evidence or other parties' rights.

### 11.4 Shared work and temporal validation implementation

Use one current AG action owner per participant and one family owner for a shared worksite. Each participant's actual readiness binds a role, the exact shared method revision, necessary stance/channel/tool and a finite readiness lifetime. Acquire the necessary start resources in stable order at one simulation boundary. Do not keep an actor's lane indefinitely reserved while another participant is absent.

A work step computes the contribution from participants who are actually ready under the family's rules, resolves finite material/channel claims, then commits worksite progress and receipts once. Withdrawal stops future contribution at the declared safe boundary. Retained progress belongs to the worksite rather than a departing worker; some processes cannot pause safely and must expose that limitation. Native load/geometry support remains a required capability for lifts, stretches, braces and collapses.

Method-validation records must refer back to AC-owned constraint/predicate/result IDs. For each hard constraint retain its binding time, evidence requirement, scope and check boundary (pre-start, maintained, before irreversible effect, or terminal). Failure maps to supported stop/wait/reconsider dispositions; there is no generic rollback of completed work. Preferences influence method selection but never masquerade as enforced guards.

Preparing a method checks structural ordering and known invariants. Runtime checks use the current evidence and authoritative state at the required boundary. In `brace -> remove beam`, the second step depends on actual supported bracing, not merely an accepted command. In `do not open package`, no step may request opening as a hidden implementation detail. In `stop if noticed`, the guard needs admitted recognition evidence; the engine cannot expose the observer's private thought as a convenience.

### 11.5 Observation-to-presentation implementation

Keep three values distinct: authoritative subject/effect state; observer-visible appearance facts; renderer asset binding. The sense/recognition/effect owner projects the second from the first. The presentation adapter selects a compatible asset from the second. No asset can back-propagate anatomy, physics or a new belief into the first.

Projection identity includes the actual admitted appearance/effect revision, modality/detail and permission class where they change what can be shown. It need not include every observer ID when many observers share the same permitted appearance. Private source identities are not cache keys exposed to unauthorized clients. Reacquisition or dispelling an illusion updates the relevant observation/projection, not every unrelated asset.

The default scene can retain its current rendering until illusion/disguise/carrier families exist. Their acceptance requires player-view and creator-view examples, no hidden trap label in fallback, no fake bird collision, and a map preview that does not expose unknown terrain. A generated still alone does not implement any of these semantics.

### 11.6 Incremental delivery and expansion stop points

The read-only foundation can ship without new saved fields, paid models, a graph database, or parallel activity execution. The next meaningful increment is the native Macrofold connector/session/approval path under INV-16/18, using these existing readers and native recipe draft services. A real authenticated deployment and live harness qualification are required before claiming that connection works.

Thereafter select one unlike consumer at a time: note/carrier, exact offer/transfer, worksite hold/fasten, then a composed pot/bell/convention/request scene. Each demonstrates actual family behavior, graph extraction, cognitive projection, native use, interruption and current-format persistence. Do not call an unconsumed type declaration an implemented family.

Before exposing clone/merge, local clocks, graph-world travel or deformation, the respective host consumer must define its identity, collision/topology, resource, observation, scheduling and recovery semantics. Generic references and adapter boundaries leave room for them; the current runtime must continue to report them as unsupported. These are architectural extension points, not latent gameplay switches.
