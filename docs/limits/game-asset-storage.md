# Game asset storage — limits and constraints

[Feature](../projects/game-asset-storage-feature-spec.md) · [Architecture](../projects/game-asset-storage-tech-design.md) · [AS work](../maintainers/game-asset-storage.md) · [Inventory rules](README.md).

**Implementation in progress: 2026-10-17.** Mike selected external storage for all asset payloads and meaningful study preservation. Concrete defaults are implemented where stated; measured qualification remains separate. Correct reference identity, privacy, publication atomicity and retained-dependency integrity are requirements, not tunable limits.

## AST01 — Git and bootstrap assets

**Implemented and verified / Very safe:** Git permits **zero stored asset payloads**, with no per-file size exemption or media allowlist. Standalone media and SVGs, exported mesh/animation JSON, vector/icon bundles, editable art files, asset archives and embedded images remain external. Base64 and percent-encoded SVG data URLs in CSS or other source files are included. Code, shaders, JSX drawing code, small semantic authored data/catalogs, exact references, licenses and attribution remain source; the restriction does not classify all JSON or drawing code as media.

The former **64 KiB per-file / 1 MiB total** reviewed-media allowance is **removed** at Mike's explicit request for complete asset cleanup. That allowance retained nine editable UI SVGs and did not exclude other small exported geometry/vector payloads; size and editability do not make an asset semantic metadata. The tradeoff is that even a small illustration or icon bundle requires external publication and loading. Native depiction and loading feedback remain code-defined, without bundled media.

The Git/build guard rejects asset payloads rather than admitting exceptions; publication, exact references, semantic metadata checks and preservation gates remain independent controls. The initial AS05 cleanup removed substantial tracked media; its historical verification is not a zero-payload audit. Older reachable Git blobs remain a separate AS08 reclamation concern. AST01 does not cap world/game asset size or import qualification; A3D owns those. AS02/AS05 own consumer qualification and guard enforcement.

## AST02 — Storage boundaries and reuse

**Selected / Medium:** distinct library, studies, delivery, intake and recovery storage roles; separate production/nonproduction delivery. No per-world/per-asset bucket. Reuse identical files within a permitted boundary; allow documented copies across access, environment, study-independence and recovery boundaries.

This spends some extra storage to keep deployment/rights/retention independent. Global cross-private-domain deduplication is not a requirement and must not leak existence. Expansion to another content account or region changes deployment mapping, not logical references. AS01/AS03/AS04 own qualification.

## AST03 — Published dependency graph

**Implemented / Safe:** required immutable file/manifest dependencies form a directed acyclic graph. File descriptions, retention pins, optional lineage/navigation links and permitted public/private closures are distinct. Cycles in required dependencies fail publication explicitly; repeated dependencies share a visited identity. Descriptive study/model backlinks are not recursively expanded dependencies.

The configured publication envelope is **10,000 inspected revisions/edges, 20,000 inspected file members, 10 GiB of exact unique file bytes, depth 32 and 4 MiB per manifest**. Counting inspected members/edges also bounds repeated descriptions; unique-byte accounting does not pretend repeated graph work is free. Operation inputs must fit the existing checkpoint row encoding before transport. Named public projection keys are limited to 512 UTF-8 bytes, leaving room for recovery prefixes; physical S3 keys are limited to 1,024 bytes. Exact lookup does not scan the global library. These are admission limits, not qualified throughput; AS01/AS04 own runtime evidence, and A3D01–A3D05/A3D09/A3D10 retain shared format/rights envelopes.

The fully encoded nested logical identity is limited to **1,000 UTF-8 bytes** so composite dependency/pin indexes can hold two adjacent exact identities, their owner kind and record overhead without ambiguous truncation; authored spelling remains unrestricted within that bound. A PostgreSQL qualification found that the earlier 2,000-byte allowance could fail a complete publication with error `54000` when both identities occupied one index entry. Near-bound incompressible parent/child identities pass under the current allowance. Private named-page login checks at most **100 committed publications of that exact physical page** and refuses a larger candidate set. It does not scan or disclose the wider private catalog.

Admission also reserves room for each file's combined canonical/named transfer receipt within the existing **1 MiB encoded SQL-row limit**, including the supported 1,024-byte opaque S3 version identifiers and JSON escaping. Actual receipts are checked again before storage. A large alias set can therefore refuse before transfer even when its manifest fits; partition that publication deliberately rather than producing unrecoverable metadata. This is a derived byte bound, not a separate fixed alias-count setting.

## AST04 — Local cache and download work

**Implemented / Safe:** one configurable shared user cache outside worktrees, with a **10 GiB default disk budget, 20,000 entries and four concurrent transfers**, active-use pins and eviction of unused verified entries. Workspaces containing unsaved art are separate. If pinned content fills the budget, refuse new materialization with an explicit disk-capacity result. Processes sharing a cache must agree on its limits. These defaults are a starting developer convenience, not optimality evidence.

The budget includes partial files and cross-process in-flight reservations, not just completed entries. A file larger than the allowance requires an explicit allowance change or refuses; concurrent pulls cannot each spend the same free space. Editable copies need separate workspace-space admission and are never cache-eviction candidates. Cancellation releases only that reader's interest; another active reader retains its protection. Each cache acquisition, including waiting for an occupied transfer slot, uses the configured finite transfer budget from entry. Its observation owner reuses the existing reader/queue allowance and retains unsettled cleanup rather than adding transfer capacity. [NET-L02/NET-L05](bounded-network-requests.md) owns the shared lifetime defaults and accounting.

The browser schedules selected asset reads before the existing four-transfer owner. Its finite waiting allowance is the installed release's URL count plus the four active transfer slots; the total five-minute budget starts before waiting. This accommodates a legitimate first-scene burst without increasing transfer concurrency or retrying failed downloads. Per-scene model reuse and destruction cancellation remain controlling. The allowance bounds small read descriptions, not cached model bytes, and is not a measured browser-capacity claim.

Cache metadata allows at most `maxEntries × 4` reader relationships and `maxEntries × 4,096` encoded bytes; owners, verified files and pending transfers are checked before iteration. Dead-process recovery requires evidence that the recorded process ended; elapsed age alone cannot reclaim a live reader.

Per-instance transfer slots bound shared-admission polling, local readers await one owned transfer, and reader counts use exact-file lookup. Metadata validation still reads the admitted complete cache record; the entry ceiling is not a measured throughput guarantee. Qualify large retained caches and concurrent clients before raising these limits or adopting a server workload beyond the recorded developer-cache scenario.

Public HTTP cache transfers have a five-minute deadline, finite headers and exact declared/body lengths; redirects and compressed representations are refused. The cache verifies complete SHA-256 before granting a reader. S3 conditional transfers permit at most three fresh-stream attempts for bounded transport failures. No paid AI retry is introduced. Existing renderer owners retain decode/upload scheduling; no new automatic whole-library prefetch is enabled. AS02/AS04 qualify complete caller behavior. Warm cache hits do not establish cold latency or total browser memory.

The reviewed interface icon catalog is fetched once per page from its exact selected reference. The ordinary game bootstrap awaits it for at most **15 seconds**; failure or expiry preserves accessible letter symbols, without automatic retry. Standalone scene tools do not wait for optional icons. Immediate high-contrast loading text remains visible while ordinary bootstrap waits. Face geometry and cloth are prepared once per renderer owner; owner destruction cancels outstanding work and prevents late mesh allocation. Partial construction and upload failure also release resources before a completed owner can be installed.

## AST05 — Retained sources, releases and studies

**Selected preservation; no automatic age/count deletion / Too liberal for unattended growth without admission:** preserve published source/library revisions, pinned runtime dependencies and all requested meaningful study iterations, including rejected variants. There is no fixed artistic-history count cap. More exports/captures can grow storage indefinitely even though publication and browsing are bounded.

Monitor unique/copy bytes and configure the operating storage/spend envelope before unattended production. At capacity, refuse/pause new optional work; never discard retained dependencies to satisfy a local cache or generation budget. License/privacy withdrawal and explicit owner deletion remain separate controlling policies. AS06 owns recovery/pins; automatic retained-object GC remains disabled until its publication-race checks pass. No blanket archive-class transition or irreversible retention period is selected.

## AST06 — Temporary intake and previews

**Implemented with an operator-enforced grace / Safe:** disposable terminal intake runs have a **7-day cleanup grace** after successful completion. Record that completion time with the proof/receipt and keep the exact intake versions untagged for at least seven full days before reviewing them for the explicit disposable tag. Published/preserved outputs must already be copied and verified in durable storage, with no active or unpublished work depending on the intake copies. No automatic terminal tagging is enabled.

The S3 lifecycle rule applies only to explicitly tagged `runs/` objects. Its current-version expiry uses **7 days of object age**, and noncurrent expiry uses **7 days as noncurrent**; tagging itself does not start another grace period. The operator waiting step therefore protects the agreed post-completion grace. An older object can expire promptly once tagged, subject to asynchronous S3 processing. Incomplete multipart uploads are aborted after **7 days**. Untagged active work and durable prefixes do not expire. Request logs retain 30 days. The [cleanup procedure](../asset-workflow.md#create-and-verify-recovery-checkpoints) names the exact receipt/version checks; [AWS lifecycle semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html) define the storage timer.

Preview deployment expiry releases its own references; it never expires a study or source that refers to the same content. Preview duration is an operator-selected deployment setting, not a study-retention limit. No age-based S3 expiration rule applies to durable blob prefixes. AS01/AS06 own cleanup qualification.

## AST07 — Delivery and documentary URLs

**Implemented / Medium:** migrated documentation uses verified stable revision URLs on `assets.openlegend.ai`; access tokens and temporary provider/worker/local paths are not durable references. Specific evidence links pin iterations; current-selection links are labeled as navigation.

Public immutable delivery uses long-lived cache headers; controlled withdrawal removes the current origin object and waits for exact CloudFront invalidation while retaining old S3 versions privately. Previously downloaded files cannot be recalled. The future-private study portal issues a **60-second exchange ticket** and **15-minute signed cookies** for its explicitly curated scope. The hosted ticket can be exchanged again until its deadline, always retaining the original cookie expiry. The documented login checks current SQL access before and after issuance; direct IAM invocation remains a privileged operator capability. Already issued cookies retain their admitted window, but controlled withdrawal removes the selected origin copies and invalidates cached delivery. The local operator viewer has a separate one-use ticket and rechecks current SQL permission on every asset/source request, including cache hits. Existing [DEP07](production-deployment.md#dep07--asset-access-and-caching) owns the broader policy. AS03/AS04/AS05 verify direct blobs, CORS/CSP/ranges, expiry, takedown and corrected links. Active migrated links and retained study entries use verified hosted replacements; original repository paths remain provenance.

## AST08 — Global admission, catalog and recovery growth

**Implemented admission; capacity unqualified / Medium:** the current SQL owner admits at most **10 GiB of unique claimed physical destination addresses, 100,000 claim rows and 10,000 publication operations**. A second bucket or named mirror is a separately charged address. Terminal claims remain retained; retained objects have no automatic collector. This bounds admitted publication growth, not total billed bytes: old S3 versions, request logs and recovery copies are additional storage, and public request volume is not a hard spending cap. Eight bucket storage warnings and the study issuer's error alarm provide console visibility; they do not stop a cloud bill or delete retained work.

Recovery bounds are **32 MiB for current-authority metadata, 64 MiB per checkpoint manifest, 256 MiB captured metadata, 1 MiB per encoded SQL row, two million captured rows, 10,000 revisions, 100,000 exact file locations and 20,000 metadata files**. Checkpoints retain exact account/Region/bucket/key/version addresses, including named mirrors and environment copies. Restoration writes only to a private `recovery-*` intake namespace, verifies current independent authority and requires deliberate promotion before primary delivery. A missing/pending current-authority marker keeps recovered access quarantined. These finite envelopes are integrity/admission limits, not RPO/RTO measurements.

Authority mutations check the complete encoded result, including their durable outcome, against the existing authority and SQL-row limits before committing. Exceeding a limit rolls back the mutation and preserves unchanged complete coverage; an export limit cannot first be discovered after an irreversible permission change.

Administrative inventories and recovery remain outside native/render paths and process bounded batches. AS07 records actual transfer, retained bytes, recovery duration and cost estimates separately from these configured limits. One account/Region recovery cannot survive loss of that entire account/Region; Mike explicitly accepted separate buckets/roles in this deployment. No RPO/RTO, CDN bill or frame rate is promised from cloud product specifications. [A3D](3d-pixel-art.md), [DEP05/DEP09](production-deployment.md) and existing spending admission remain the shared owners.

Migration preparation accepts at most **32 explicitly selected refs, 20,000 unique historical objects and 250,000 historical path records**. HTML rewriting allows **16 MiB per source page and 32 MiB per snapshot**. Oversized inputs require a deliberately partitioned plan; they are refused rather than partially inventoried or silently omitted. These administrative limits do not constrain authored world population.
