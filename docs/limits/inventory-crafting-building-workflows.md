## ICB-L01 — Finite actor work, not a production service

**Proposed scope · Restrictiveness: Very safe.** The first crafting-list consumer compiles personally known, installed, qualified native manufacture into the existing finite invocation/sequence/repeat representation. Pending-suffix edits support only that generated craft-only structure, not arbitrary branch/watch plans. One existing physical work lane and existing active/suspended-plan rules remain; no background worker, indefinite production, automatic gathering/trade/research or new offline continuation is included.

Use [AEL01](action-experience.md#ael01), [AEL07](action-experience.md#ael07) and [AEL08](action-experience.md#ael08) as the sole owners of structural/execution/history budgets. At the inspected baseline AEL01 has a 64-node representation and bounded repeat/expansion work; the eight-entry active window is not a total-list cap. Explain shape exhaustion before submission and preserve the draft rather than truncate it. Counts and dependency expansion must fit the existing native structure; this proposal adds no separate maximum number of possessions or recipe definitions.

Reason: reduce repeated chosen work without a second scheduler or changed survival obligations. Expand only for a concrete additional supported process with full continuation/cost/output semantics. Implementation: ICB02.

## ICB-L02 — Bounded reads before detail

**Proposed new-reader envelope · Restrictiveness: Safe.** For the new task-specific recipe summary and alignment-candidate reads, return up to 40 summaries from up to 200 permitted candidate IDs examined per request, with continuation and explicit incomplete coverage. Reuse existing equivalent query helpers and shared configuration where semantics match; these values do not alter the existing complete action catalogue, native validity checks or world perception. Fetch full material/recipe detail only for the selected method, not for every candidate. Alignment candidates are optional aids; reaching their read limit does not prove no legal placement exists.

One construction workspace has at most one in-flight check and one replaceable latest pending draft. Identical scoped reads may share an in-flight request. Hidden workspaces stop optional reads; no server check is dispatched per renderer frame. Keep the existing inventory/destination limits in [IW01 and AP01](interface.md), not duplicate values under another authority. Result and candidate caps are starting choices, not measured optimal values.

Cold index preparation, the full relevant material assignment, final ancestor-capacity validation, required geometry/navigation preparation and global mutation/publication backlog are **not bounded by these display/read values**. They remain governed by existing [object](objects.md), [native-work](native-work.md), [spatial](spatial.md), [shelter](editable-shelters.md) and [persistence](persistence.md) owners. Do not claim that returning 40 rows makes all preparation constant work. Measure those growth paths in ICB07; exhaustion remains incomplete/refused work with a recovery route, never a false absence or partial commit.

## ICB-L03 — Immediate equipment exchange scope

**Proposed scope · Restrictiveness: Very safe.** One explicit exchange selects one incoming equippable unit plus all actually conflicting attachments and their chosen accessible destinations. The installed equipment/body owner determines conflicts; there is no hard-coded universal one- or two-slot grid. Native individualization may select one unit of a lot while retaining lineage. Only movement/equipment operations with supported immediate semantics can be combined in the first release; timed approach/pickup or unsupported equipment families remain separate ordinary actions with their actual costs.

No new global personal inventory cap or automatic junk/disposal rule is chosen. Actual container packing/capacity/depth and active-work restrictions remain with the [object inventory](objects.md) and [base-world item contract](../worlds/base/items.md). The final-state capacity proof cannot be bypassed or replaced by a temporary empty slot. This narrow scope avoids silently granting a timed action for free; expand only with a separately designed complete temporal exchange. Implementation: ICB04.

## ICB-L04 — Existing shelter family, assisted selection

**Proposed scope · Restrictiveness: Very safe.** Alignment and correction apply only to current admitted construction families, orientations, surfaces and contact rules. The initial consumer uses the delivered flat one/two-bay and single-bay lean-to, preserving the [SH inventory](editable-shelters.md), including its unsupported overlap and broader geometry boundaries. No new fixed snapping distance, arbitrary rotation, third bay, enclosure, walkable roof, demolition refund window or material-grade ladder is introduced.

The aid can be disabled or manually adjusted within the family's supported geometry. Uncommitted draft changes are reversible; committed construction changes use native material/work rules. This retains meaningful place choice without disguising unimplemented physics behind a preview. New shapes or behaviors require the existing world's scoped design and qualification, not expansion of the UI alone. Implementation: ICB05–ICB06.

## ICB-L05 — Draft lifetime and retained work

**Proposed draft policy · Restrictiveness: Medium.** Unsent work-list/placement drafts live in the active client's scoped task state and survive panel hiding, viewport changes and same-scope transport reconnection. They are not newly written to browser persistent storage or synchronized between devices. Reload may lose an unsent draft; the interface cannot promise recovery for it. Existing inventory/private-work persistence is not removed by this choice. Scope revocation or actor/world/timeline replacement invalidates affected private drafts.

Accepted lists/edits and actual results use the existing plan, occurrence and receipt owners with current-format database/capture support and their current retention limits. There is no second unbounded saved work-list history, inventory copy or browser receipt archive. Repeated list creation grows existing action history and is subject to AEL07 admission; this design neither evicts evidence nor raises its budget. A larger cross-device or long-lived unsent-draft feature needs an explicit privacy/retention design. Implementation: ICB01–ICB02, qualification ICB07.

## Review triggers

Revisit a proposed value only after observing a legitimate task that it prevents or excessive work that it allows. Measure complete cold/warm paths, not only final page sizes or a warm preview. Keep gameplay and query restrictions distinct. No backlog-wide limit removal, privacy relaxation or new paid experiment is authorized by this inventory; ICB07 owns the selected evidence and existing parent trackers retain broader performance work.
