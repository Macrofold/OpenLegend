# Creator edit propagation: limits and constraints

[Tasks](../maintainers/creator-edits.md) · [Design](../projects/creator-edit-propagation-tech-design.md)

## CE01

**Accepted target, not implemented — October 3, 2026.** No automatic semantic memory cascade. Mandatory deletions require explicit dependency proof and a complete approved preview. Optional associations are selectable. This protects coherent state without pretending semantic similarity is authority. Plan size, closure work and retained approval lifetimes have no selected numeric bounds yet; the implementation must choose and measure them before claiming complete coverage. Oversize or unsupported closure must block application, never truncate required deletions. Existing [invention bounds](inventions.md) apply where those services are reused.

### CE01-A — First supported removal consumer

**Proposed — October 11, 2026 · Restrictiveness: Very safe.** [Batch 09](../projects/parallel-batch-09-reviewed-content-removal-feature-spec.md) covers installed status-effect definitions, qualified through conditions deliberately authored by a creator. Required removals follow complete native status references; optional supporting conditions are explicitly referenced status definitions, kept by default. Body/dream-policy references and retained independent contribution pins, including cold ended records, block application. Recipe/material/stock deletion, semantic memory rewrites and other unsupported owners remain excluded. This restriction makes one real creator journey complete without inventing retirement laws for unrelated records. Expand only after another semantic owner supplies a lawful complete removal contract.

### CE01-B — Complete review and growing work

**Proposed; aggregate work and retention unqualified · Restrictiveness: Too liberal until qualified.** The retained plan covers the full selected definition, instance and activity set; pages display that plan without truncating approval. Reuse current authoring, record, page and transport envelopes where valid. Installed predicate edges, affected instances, retained plan bytes and cold contribution history grow independently; a small page or empty pin result does not bound preparation or database work. No new numeric allowance or lifetime deletion policy is selected here. [RD05](../maintainers/parallel-batch-09-reviewed-content-removal.md) must measure complete preparation, page and Apply paths and justify any required admission bound. Unsupported, excessive or incomplete coverage blocks application while retaining the unapplied proposal under existing retention rules. Approval validity follows actual dependencies, instance episodes, permission and timeline; unrelated clock advancement alone is not a new review lifetime. The [technical design](../projects/parallel-batch-09-reviewed-content-removal-tech-design.md) owns the complete behavior.

## CE02

**Later target, not implemented.** Search scope and result pages will reuse [memory limits](memory.md) and actual semantic lookup. No maximum batch, paid allowance or retention target is selected by this document. Large memory sets create vector-search, review and mutation costs; implementation must bound them, expose incomplete coverage and respect the account owner's explicit paid cap. AI suggestions require selected exact diffs and cannot apply automatically.
