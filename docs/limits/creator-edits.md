# Creator edit propagation: limits and constraints

## CE01

**Current qualified finite consumer; general target remains open — October 14, 2026.** No automatic semantic memory cascade. Mandatory deletions require explicit dependency proof and a complete approved preview. Optional associations are selectable. This protects coherent state without pretending semantic similarity is authority. Batch 09 implements installed-condition removal with the envelopes below; [RD05](../maintainers/parallel-batch-09-reviewed-content-removal.md) records its completed selected acceptance. Oversize or unsupported closure blocks application, never truncates required deletions. Existing [invention bounds](inventions.md) apply where those services are reused.

### CE01-A — First supported removal consumer

**Selected consumer qualified — October 14, 2026 · Restrictiveness: Very safe.** [Batch 09](../projects/completed/parallel-batch-09-reviewed-content-removal-feature-spec.md) covers exact installed status-effect roots. Required removals follow complete native status references; optional supporting conditions are explicitly referenced status definitions, kept by default. Body/dream-policy references and retained independent contribution pins, including cold ended records, block application. Incomplete historical physical-owner coverage or undisclosable ordinary affected records also block review. Recipe/material/stock deletion, semantic memory rewrites and other unsupported owners remain excluded. This restriction supplies a finite lawful consumer without inventing retirement laws for unrelated records. Expand only after another semantic owner supplies a lawful complete removal contract. [Native/PostgreSQL and actual browser evidence](../verification/reviewed-content-removal.md) qualifies cold pins, ordinary object coverage, exact review/Apply/recovery and the selected creator journey.

### CE01-B — Complete review and growing work

**Current envelopes; finite complete-path measurements recorded, broader scale remains open · Restrictiveness: Safe for retained detail, Too liberal for unqualified aggregate preparation.** Complete removal detail is admitted only within **96 KiB of serialized JSON**, leaving room inside the existing 128 KiB operational-record envelope. The full candidate policy also retains the existing **24,000-byte** authoring allowance. Neither bound permits truncating required rows; exceeding either returns capacity refusal before an executable review is retained. Detail pages contain **20 rows** from one immutable plan section; a cursor binds exact plan/draft/revision/digest, section, authority and timeline. The existing session retains at most 512 review plans, 64 drafts, 256 revisions per draft and 2,048 edit receipts under [shared authoring retention](inventions.md#reviewed-authoring-and-remaining-usage). These limits apply to retained refused reviews as well as successful ones. The new detail allowance is conservative storage headroom, not evidence that its exact size is optimal. A serialized character-count lower bound on required explanation paths now enforces that same allowance before copying a provably oversized set of paths. This adds no smaller membership or chain-depth limit; the final UTF-8 byte check still covers labels, instances and all other detail. Removal intentions accept at most **64 supplied root IDs** and **64 supplied optional IDs**, with each ID at most **200 characters**. These transport limits bound one submitted selection; the complete required dependent set can exceed 64. Oversize input refuses admission. They are conservative request limits, not measured world-capacity limits; expand after qualifying larger submitted selections within the candidate/detail and existing transport envelopes.

Installed predicate edges, affected instances and cold contribution history grow independently of retained bytes and page size. Native admission still requires complete condition-history materialization before replacing definitions, including no-pin cases. The storage owner batches at most **800 entity-parent IDs per query**, preserves complete maps/order, and refuses an omitted historical physical owner; this bounds parameters rather than total returned rows or database work. It loads no unrelated memories, appraisals or object history. [Five-sample measurements](../verification/reviewed-content-removal.md#condition-history-and-postgresql-qualification) reached 5,000 retained terminal conditions and 10,000 unrelated cold memories using two SELECTs, with a 20.466 ms median status-only hydration time on warm-cache loopback PostgreSQL. This qualifies that measured reader, not complete preparation, page disclosure, Apply, whole-server latency or a larger population. [Complete-call measurements](../verification/reviewed-content-removal.md#independent-complete-call-growth--october-14-2026) independently varied installed definitions/references, ordinary instances, terminal contributions and unrelated cold memories, including paging, optional revisions and Apply. The 5,000-terminal no-pin case took 50.710 ms for preparation and 55.709 ms for Apply in one warm-buffer sample; 5,000 pinned records refused approval after 199.157 ms preparation. These are finite observations, not percentile or aggregate capacity guarantees. The selected [RD05](../maintainers/parallel-batch-09-reviewed-content-removal.md) browser/full-path acceptance is complete; larger populations, multi-parent batches, cold disk, concentrated high-reference graphs and production responsiveness remain unqualified. Complete condition-history loading and current instance/pin checks still hold the existing world operation while they run; the largest recorded contribution workload is 5,000.

Removal disclosure also visits each distinct referenced subject’s existing bounded containment/attachment ancestry once per permission check, with no SQL for live subjects and no retained permission cache; results are discarded before any later read/commit check. Missing retained references need exact canonical custody preparation in batches of at most 256 IDs, using the existing entity and retirement indexes in one read snapshot. An active-turn reader reuses those exact facts across packet writes while checking current permissions again. Restores invalidate preparation; physical-membership changes invalidate proved absence, while immutable retirement facts survive unrelated membership changes. This batches parameters and repeated subjects rather than promising bounded total historical work; genuine historical absence is accepted only after that preparation succeeds. This does not bound total admitted review work independently of the existing retained-detail allowance.

A larger aggregate history envelope or finer indexed preparation needs a separately qualified owner contract that preserves native completeness, rather than inferring absence from a small query/page. No independent clock-based review expiry or historical deletion policy is added: relevant dependency, episode, permission and timeline changes determine approval validity. The [technical design](../projects/completed/parallel-batch-09-reviewed-content-removal-tech-design.md) owns the complete behavior.
