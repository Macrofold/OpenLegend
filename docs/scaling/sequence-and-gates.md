## Five gates, not three ambiguous deadlines

NOW/SOON/LATER describe when a dependency becomes necessary, not a calendar date. A task can have a small foundation needed now and a large implementation needed much later; those must have different child IDs and independent evidence.

| Gate | Stage | Trigger and intended outcome | Do not make this a prerequisite |
|---|---|---|---|
| G0: preserve the foundation | NOW | While building ordinary gameplay: stable identity, explicit authority, source/timeline/units, bounded query interfaces and attributable work. Remove a confirmed unwanted multiplier after a short relevant baseline. | A general benchmark platform, global database, distributed engine or complete public-auth deployment before a local feature can work. |
| G1: qualify a growing local/regional world | SOON, feature-growth gated | Before claiming long sessions, large learned libraries or the next supported population: independently addressable consumed records, efficient recall preparation, coherent recovery, bounded jobs and applicable-rule processing. | Full D3/MCP query tooling or every future schema before migrating a currently consumed record. |
| G2: qualify public shared play | SOON, release gated | Before strangers/independent humans share a hosted world: authenticated control, scoped views, human-private denial, queue fairness, security, cost/recovery objectives, browser/network and deployment evidence. | Voice, world-to-world trade, arbitrary scripting or a large fleet unless that feature is in the release promise. |
| G3: qualify regional distributed execution | LATER, deferred | When a named shared-world workload requires more than one owner: measured partition boundary, fenced authority, transfer and cross-boundary/time protocols, fault testing and safe rollout. | Treating independent-world sharding as completion of the accepted region-divided shared-world goal. |
| G4: specialized scale or new causal domains | LATER, conditional | When a named bottleneck or approved feature warrants it: specialized memory/search, geographic disaster recovery, dense-event design, advanced solvers, G2 runtime, media/global economy. | Adopting every researched technique, vendor or approximation. A negative experiment can close an evaluation without authorizing deployment. |

Gates supplement, not replace, P1–P7 product milestones and D0–D6 delivery phases. G0 spans current feature work; G1 consumes D1/D2 and PF; G2 consumes the relevant D3/D5 and multiplayer contracts; G3/G4 are conditional D6 or feature-specific expansion. Do not silently renumber product milestones or equate a local fixture with public release acceptance.

## Near-term dependency order

1. **Establish the measured problem and semantic boundary.** Reuse PF00 and the current audit. Identify the actual growing input, affected operation, evidence and existing task before adding a new one. A confirmed loop does not require a months-long benchmark project before a focused fix.
2. **Stabilize identity and invalidation first where a change depends on them.** Actor/session scope, source incarnation, time units and dirty-record identity support later records, queues and caches. Preserve the single writer. Contract extraction is not an excuse to defer a small independent hot-path fix.
3. **Migrate the consumed current records and queries in vertical slices.** D1/D2 own canonical entities, holdings, processes and memory/evidence. SC tasks supply focused gaps. Native simulation remains in memory; database selection precedes optional context text. Snapshot optimization remains transitional and cannot close D1/D2.
4. **Qualify the whole affected experience.** Include cold loads, old history, concurrent actions, required evidence, native speed, browser work and optional provider fixtures. Paid behavioral quality remains separately authorized. An optimization and its release qualification can have different completion states.
5. **Complete shared-hosting safeguards before public access.** Control/permissions, recipient replay, budgets, backpressure, erasure, deployment/recovery and operational support must exist before relaxing local-only protections.

No global rule requires all G0 work to finish before any G1 work. Follow the dependencies of the actual slice; do not create a serial waterfall across unrelated systems.

## Research provenance and task identity

Every newly added or substantially clarified research-derived task must include **Massive-scale research** with a relative link to the specific domain/stage chapter, and the SCA finding when one exists. Linking only this index is insufficient for a detailed task. A task may inherit that provenance from its immediately enclosing, explicitly named workstream when all child rows share it.

Give independently completable changes stable child IDs, a stage/trigger, one deliverable and a falsifiable exit. Keep the body in one owner. Existing PF/EPR/SW/CR/AG/INV/EWF/SL/D tasks remain their owners; add child detail or a scoped evidence extension there rather than duplicate them as new SC work. Indices and crosswalks link to the body and do not repeat checkboxes.

Preserve existing SC01–SC16 anchors and all checked states. Splitting a task does not complete it. A parent may be partially delivered while its scale/failure gate remains open. Reuse existing regression IDs for deferred test implementation; the research does not revoke the repository's separate verification policy.

## Promoting long-term work

Long-term work is **deferred**, not the default next-task queue. Promotion requires a named product need or measured saturation, a concrete workload/SLO, relevant policy decisions, dependency readiness, an owner and authorized implementation scope. Record the promotion and evidence in its existing task, then link it from current scheduling; do not copy the task into a second tracker.

For an experiment, specify the baseline, the comparison and a stop rule. For deployment, also require recovery/rollback, authority/privacy and cost evidence. A region prototype can be developed against fixtures without provisioning production infrastructure. A physical-storage shard is not a prerequisite to proving two simulation owners using one transactional store.

Independent worlds and a fleet remain supported alternatives with their own benefits. They do not supersede the accepted shared-world regional priority. A vendor change, ECS rewrite, WebSocket switch, actor framework or vector index is a candidate implementation, never a goal in itself.

## Invariants across every gate

Preserve legitimate event-time witnesses, native physical outcomes, source eligibility, protected commitments, human-private data and external accounting through restore. Missing capacity/coverage is not fictional impossibility. No hidden time dilation, dropped evidence, arbitrary lifetime content cap, automatic paid retry or changed offline policy is authorized by a scale task.

A retained record need not remain hot, but cold storage grants no new recall permission. Proposed cohort simulation, memory surrogates, global trade, runtime scripts and dense-crowd compromises require their own approval and evidence. Current D03 time/absence and D14 recall choices remain in their canonical owners.

## Completion evidence

Each handoff reports the child and parent IDs, baseline/current commits, changed behavior, actual checks and measurements, unresolved policies, remaining gate and next trigger. Update Architecture only for delivered runtime behavior and Verification only for actual executed evidence. Documentation completion establishes traceability, not performance or capacity.
