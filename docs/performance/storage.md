# Storage execution and transactional persistence

Part of the [performance contract](../performance.md). Read for the matching mechanism; historical results qualify only their recorded workload and revision. [Verification](../../.agents/rules/verification.md) selects checks.

## Compact transactional persistence

The [bookkeeping implementation](../projects/bookkeeping-simplification-tech-design.md) uses direct transactions, explicit append batches and scoped ownership queries. The custom journal/application stage, live-object evidence-layout bindings and global retention mirrors are removed. [BK](../maintainers/production-data.md#bookkeeping-simplification) retains operating and lifecycle acceptance; reduced bookkeeping alone establishes no capacity pass.

Each event/observer perspective retains history access, ordering and an exact family/body-hash reference to that observer’s permitted account; there is no duplicate audience table. Current awareness bodies live in their canonical records, replaced/removed versions in the existing source-version archive. Independently rephrased history accounts use that archive explicitly. Shared account resolution reconstructs complete permitted evidence without copying each full body into the history row or substituting mutable global event text. Indexed columns support character-reply identity, permitted dialogue participants, speech type and conversation-related actions. Participant pages merge limited indexed streams. Event string references have a GIN projection for creator deletion safeguards. These projections cost disk and write work; they avoid repeatedly parsing unrelated event JSON. Record indexes have stable descriptive names, with short hashes for PostgreSQL's identifier limit, and source families only keep relevant indexes. Deleting an actor's source collection uses its exact indexed parent ID.

Normal startup reads a transactionally maintained retained-event count. Checkpoint capture and full recovery still compare that count to physical rows; the integrity tradeoff is owned by [save/load](../save-and-load.md#current-history-capture-boundary).

Current canonical storage writes use typed compact row batches through the existing grouped writer, preserving complete byte/row admission, explicit columns, order, duplicate-create checks and dependency barriers. History and canonical record owners may share that bounded batch when no intervening consumer requires the writes; editing, forgetting, old-source reads, deletes and subsequent source joins keep their actual flush barriers. Recent character-result rows retain stable storage positions across ordinary rollover; true reordering and unsafe position exhaustion use complete renumbering. Exact changed entity/perception-binding lineage avoids rediscovering unchanged keys, with complete fallback for replaced, forked or unknown inputs. Read-only previews must not bind live storage positions, install codec layouts or stage mutations; a refused preview cannot change a later real write.

The derived full-text vector/index is prepared after source commit using durable exact-revision keys. Exact account bodies, source eligibility, displayed-text history search and latest-place reads remain synchronous. Indexed context search waits for revision coverage and checks it again in its actual read snapshot. [Memory architecture](../memory-architecture.md#implemented-retrieval-and-storage) and [MH15](../limits/memory.md#mh15--delayed-lexical-preparation) own correctness and operational bounds. This removes a dependency from ordinary source saving, not the total index work; sustained backlog and command tails must qualify together.

### Fast append and deliberate edits

Use the application's unchanged/append/diff intent together with the domain draft’s append proof; caller hints alone cannot certify an unchanged prefix. Carry that proof through encoding, metadata extraction and ownership projection: append-only SQL does not help if preparation still rebuilds the retained prefix. Encode each new source once and bulk insert its rows and actor-scoped access/evidence perspectives. Edits, forks and unknown predecessors retain complete comparison. Resolve current-format history readiness once at startup and cache it only after a successful transaction; this does not authorize converting an incompatible development layout. Duplicate IDs and receipt conflicts must still fail or reconcile explicitly; an append hint is not permission to overwrite retained history.

Existing event edits, source corrections, forgetting and deletions use a separate branch of the same repository entrypoint. Their dependent story revocation, audience changes, vector invalidation and forgetting ledger remain atomic. Do not obtain speed by leaving stale private prose or evidence readable after revocation. Batch the affected IDs and load dependencies together instead of traversing SQL relationships once per record.

Prepare immutable lookup/delta inputs before opening the transaction when committed readiness is known. For dense history bursts, do not retain a second full set of prepared payloads: encode each source once into a bounded row buffer, flushing sources before their dependent rows within the same transaction. This deliberately keeps bounded encoding in the transaction rather than trading shorter lock time for unbounded temporary memory. Buffer limits count UTF-8 SQL parameter bytes and portable parameter counts; a single oversized record retains the existing one-record behavior. Preparation never authorizes a different or mutable snapshot. Prepare other bounded payloads before opening the transaction. Bound bulk writes by rows, bytes and database parameter limits. Persist changed canonical records, the head/CAS check, required history, job outcome and accepted mind changes under the same atomic boundary. Combine compatible metadata writes rather than adding per-feature round trips. Keep any complex PostgreSQL-specific statement inside a typed repository operation. Query count should grow with bounded batch chunks, not one query per witness or event.

Current checkpoints stream complete canonical records through one owned read-only worker. A short revision barrier releases gameplay mutation ownership after the snapshot is established; the repeatable-read transaction remains open while records are read and checkpoint output is written. The [capture deadline and worker watchdog](../save-and-load.md#current-history-capture-boundary) bound that exposure and preserve the previous usable save on failure. File publication is atomic through the save owner, separate from the database transaction. Required event perspectives and source revocations retain their owning durability and privacy barriers. All gameplay table changes and receipts use the same direct atomic writer; readers use coherent database snapshots.

### Preserve order without one global database bottleneck

Record writes group new rows separately from updated rows within each table, retaining bounded batches and insert-only duplicate detection. Tables with secondary unique indexes keep their original row order. This avoids alternating new/updated visibility records producing separate statements for every observer. Parent tables still precede children; dependent history, source eligibility and the world head remain in one atomic transaction. Job identity and completed-status protection are checked by the same upsert that writes the job.

The observer/subject sight-episode map explicitly has no insertion-order meaning: consumers resolve identities by key. Its codec therefore writes neutral ordinals and only changed bindings; a bird leaving view does not renumber every still-visible object. Reload may enumerate those map keys differently, but preserves every episode identity and disappearance/reappearance boundary. Entity order, visible-subject lists and history order retain their existing semantics. New collections must opt in only when all consumers are order-independent.

Gameplay writes retain one ordered writer connection and the advisory ownership lock. The independent bounded PostgreSQL read lane is already implemented for optional inspection and other scoped reads; reuse it rather than proposing that separation again. Bookkeeping writes still use their existing transaction owners. Remove idle queries and redundant writes before adding another connection for a measured bottleneck. No auxiliary connection may acquire a second world-writer lock or mutate world state through a side door.

A second connection removes application head-of-line waiting, not database contention. Keep its transactions short, queries indexed and deadlines bounded; long scans, shared-row locks and large writes can still hurt gameplay. Required reservations and uncertain paid receipts remain durable before dispatch/settlement under their existing accounting contract. Provider calls run outside SQL transactions and outside the mutation queue.

Cross-connection reads use captured scope/revision tokens and reject stale results on return. Revocation and publication compare authoritative source versions; optional caches or indexes never expand permission. No read replica, generic task broker or large connection pool is needed for this stage.

The shared work queue captures each submitting operation's asynchronous context. Waiting work must not inherit request, diagnostic or transaction context from the preceding operation. Transaction owners still establish their own active lifetime and publication hooks; queue ordering alone does not provide context isolation.

### Committed cognition metadata

The store shares concurrent and repeated reads of committed interest, reflection-queue and semantic-schedule records. Only encoded immutable values are retained; each consumer receives a separately parsed value. Explicit transactions bypass this cache so they see their own writes or their original read snapshot. Writes invalidate before execution and again after commit/rollback; restoring a game clears the whole cache before installation and after settlement. Cache eviction returns to SQL without dropping records. [Inventory and bounds](../limits/cognition.md#cg03).

Conversation compaction uses separate SQL compare-and-swap writers and remains outside this cache. Accounting, authority and arbitrary integration keys also use their existing durable read paths. Adapters lacking transaction-state and publication hooks cannot enable shared metadata reads.

Unchanged committed memory/vector coverage counts return without opening a read transaction; transaction callers always query their own snapshot. Ordinary current-visibility/encounter-identity changes no longer invalidate retained-memory revisions or wake memory indexing. Actual awareness, memory, correction, forgetting, accepted-mind and restore changes retain their invalidation paths. These optimizations do not change what characters perceive or remember.

## Storage execution

When evaluating SQL batching or narrower reads, distinguish statement count, sequential database waits, commits, transferred bytes and time holding locks. Report the costs actually changed alongside complete caller latency; fewer waits can leave database execution and local encoding work unchanged. Compare shared and copied values using total payload, row/index, reference-update and cleanup costs, rather than JSON size alone.

World rows and their history audit share one database snapshot. Validation checks those independently captured values after releasing the reader; only a successful load can replace the durable baseline. A load failure cannot restore a previously lost baseline. Memory search checks its independent derived-index readiness inside the actual read view and waits outside that view when preparation is incomplete. There is no journal-alignment classifier or application fence.

Preparation belongs to one exact immutable save attempt; permissions, expected revision and receipt admission remain under its writer. Absence from a resident tail does not prove database absence. Insert-only creation requires a mutation-owner proof of a new identity or its absence from a complete canonical collection; unknown cold predecessors use the ordinary upsert path while immutable shared contents remain protected. Corruption, authority and storage errors fail without automatic replay. Earlier journal-specific [PSF01–PSF06](../maintainers/performance-safeguards.md) evidence does not reinstate removed save paths.

Before adding, widening or removing an index, identify both the reads it serves and how often its table changes. Each maintained index can add CPU, dirty pages and recovery-log writes even when a query returns few records. Measure representative inserts/updates and dependent reads, including absent-key and growing-history cases; report statement work separately from complete transaction and gameplay latency. For expiring high-cardinality keys, verify physical index reuse after deletion and vacuum; a bounded candidate-key filter with exact postchecks can avoid GIN retaining a growing dictionary of historical identities without recurring reindexing. Overlapping keys are a reason to investigate, not proof an index is redundant. Preserving every index is also not proof of preserving search cost: inspect the rows actually visited. An enforced single-value field may be omitted from a non-unique physical lookup key only while its owning constraints prove that premise; preserve complete identity and permission predicates and name the contract change that would invalidate it. [The fixed memory-write comparison](../verification/performance/59-fixed-memory-index-burst.md) demonstrates substantially less recovery-log work without a dependable complete-operation gain.

Describe the actual cache preparation behind storage measurements. Reading or hashing a complete table before a search warms that data; repeating a search before explaining it is also warmed evidence. A fresh database, connection or process alone does not establish cold database or operating-system caches. Preserve warmed correctness/search results and explicitly leave first-use behavior unqualified when it was not measured; do not flush shared caches or change global settings to manufacture a cold case.

Independent world-record table writes and history source/perspective inserts now share bounded parameterized write statements through the existing PostgreSQL transaction. The writer explicitly supplies independent writes; there is no universal deferred-write queue. A repeated table, 64 writes, 10,000 parameters or approximately 256 KiB starts another group. Original oversized single statements remain admitted alone. Re-parenting writes complete before record deletes, and memory-index reads/upkeep remain separate after preceding writes. Revision/authority checks and final commit retain their ordinary awaited boundaries. Transaction start and its local timeout travel together. The default is enabled; `OPEN_LEGEND_SQL_WRITE_GROUPS=off` restores separate waits for matched diagnosis. [PF16.7/PF15](../maintainers/performance.md#october-14-expanded-3-investigation) retains full-path performance/failure qualification; grouping implementation is not smooth-scene acceptance.

The final history group also updates the retained-event total from the complete explicit inserted/deleted count. This independent update does not read newly inserted event rows. The group checks exactly one returned total row before returning; a missing total refuses and rolls back the transaction. Intermediate bounded history flushes accumulate inserted counts, and only the single final flush applies their total. Initial total creation completes first. This changes request grouping, not retained history, count integrity or acknowledgement durability.

Key-only observer and correction dictionaries share publication-certified changed keys through canonical saving. Outer observer ownership and exact source-to-correcting-evidence maps carry no insertion-order chronology; ordered evidence and other ordered collections retain their existing order. Replaced maps, forks, mutable construction and missing/long weak lineage use complete comparison. The [October17 codec comparison](../verification/performance/overhaul-storage-implementation.md#reopened-changed-key-coverage--october-17-2026) removes full dictionary enumeration for a single edit in 10,000 corrections, without claiming a whole-game speedup.

New recall metadata is inserted with current eligibility rather than immediately updating that indexed value from zero. The memory owner shares its existing eligibility expression and bounded row batching; its [transaction ordering](../memory-architecture.md#implemented-retrieval-and-storage) preserves archival provenance and dependent-source/privacy reconciliation. The data-stress metric includes both archive preparation and the subsequent source insertion, excluding the intervening canonical record write as before. Matched four-case viewer measurements show a small, variable progress improvement, not complete 3× capacity; [the evidence](../verification/performance/01-interaction-and-early-server.md#initial-recall-eligibility-within-the-world-commit) separates SQL callback waits from database execution.

When a world commit finishes a durable character decision, the store merges its completion fields into that job in one parameterized update. Other diagnostic/request/invention fields remain intact, missing jobs stay absent, and a completed job still resists a later failed result. The returned stored and payload fingerprints retain the original integrity refusal within the same world transaction. Later meaningful AI diagnostic publication remains separate; this removes a read round trip without delaying or weakening the committed outcome. The first successful completion time survives later diagnostic updates. The operational jobs upsert retains any enclosing transaction and grants no gameplay or spending authority. [Scoped verification](../verification/performance/04-earlier-long-runs-and-cognition.md#durable-decision-job-completion).

Ordinary HTTP admission reads the current login session, world grant and control in one indexed SQL snapshot. Account/session-only routes keep their narrower read. There is no cross-request authority reuse: expiry, later disclosure and transactional commit fences remain. A read started before a committed authority change cannot repopulate the old session cache. [October17 evidence](../verification/performance/overhaul-storage-implementation.md#reopened-request-admission--october-17-2026) records two reads versus one, positive query-plan coverage and held-logout checks; no whole-game latency gain is claimed.

PostgreSQL is the sole backend. Independent bounded reader/writer lanes preserve transaction ownership and admission deadlines; an owned read-only checkpoint worker streams fixed-revision records. SQL batching, callback construction, JSON encoding and dense native work still require complete-path measurement. Main-isolate heap is not total process memory; process RSS includes worker memory and phase-end samples are not peaks. The previous SQLite writer/read-worker implementation was removed because there is no embedded/offline product requirement; historical measurements retain their original scope.

The [current PostgreSQL adapter](../../apps/server/src/postgres.ts) routes a prepared read outside an active transaction to its reader only when the SQL begins with a non-locking `SELECT`. Leading `WITH` or a SQL comment does not select that path; the same logically read-only query can otherwise occupy the ordered writer. Keep read-only CTEs inside an outer `SELECT`, or use the existing explicit read transaction when a consistent multi-query snapshot is required. Locking reads and writes retain their owning transaction. When adding or changing SQL selection/recovery work, verify the actual connection and transaction path as well as its query plan; `async` and a bounded result alone do not keep it off gameplay commits. [Creation receipt recovery](../../apps/server/src/world-agent-store.ts) uses the outer-select form while selecting records before hydrating retained candidate bodies.

### Shared entity queries and cognition work

Recipe readers share successful exact compiled-method validation for the same recipe object in a deeply frozen published world. Carried-material quantity reads build per-actor definition totals once from the existing accessible-possession iterator in that snapshot. Private weak caches retain no world or item authority: every new world snapshot starts fresh, mutable drafts/builders recheck, failed method validation is never cached, and record access, deliberate inspection, knowledge, command pins and native execution remain current checks. This removes repeated compilation and stock scans across physical records without storing duplicate balances or caching eligibility. [Expedition review evidence](../verification/rewarding-expeditions.md#requested-review--october-6-2026) records the 16-record and 1,023-carried-lot workloads; remaining complete-menu previews and wider capacity qualification stay with PF05/PF11.

The recipe's mechanical identity separately shares one immutable scalar result under its deeply frozen recipe-object key, including across publications that retain that definition. Mutable builders/drafts recompute, changed definitions have new keys, and callers cannot mutate a retained identity. This excludes attribution/admission time as before; it does not extend compiled validity across worlds. [Second-review evidence](../verification/rewarding-expeditions.md#second-requested-review--october-7-2026) includes 24 actual changed-world publications: each still compiles once, while the subsequent record page reuses that world's validation. Client detail refresh includes every supplied recipe detail, so another inspection or changed knowledge updates the selected screen without an unrelated tick.

`entity-index.ts` owns physical-root membership; `spatial.ts` owns nearby candidates; `queries.ts` adds bounded query results/dependencies; perception owns exact sensing. Known-ID lookup remains direct. `entityVisionQuery` binds observer sight once per read-only batch; cognition and observations share it while still checking each target’s current participation, position and body. It is never retained across a mutation or await. Encounter phases maintain privately owned scalar source bins and exact counted body maxima from complete phase-local changes. Narrowly audited draft writes certify coverage; unknown coverage, overflow, policy replacement and mismatched continuation ownership rebuild from authoritative roots. Changed source old/new neighborhoods select observers before exact sight/contact checks. The audit visits created draft records; observer settings refresh for changed observers, or all observers when rebuild/order/global contact dimensions require it. Affected observers query their complete relevant source population. Cold recovery and unknown structural changes retain complete rebuilds; current native batches reuse changed/due cohorts and publication-owned indexes under the [attention runtime contract](../projects/attention-and-scenes-runtime-design.md#43-lists-cohorts-and-downstream-reuse). [NP02 evidence](../verification/perception-reaction-intake.md#np02-sensory-preparation--october-3-2026) and [NW16](../limits/native-work.md#nw16) distinguish these costs; this is not a fully unified incremental visibility service. The current attention runtime owns delivered change-fed broad/detail reuse; PF09/PF12.3 retain their separately scoped work. Keep current visibility distinct from the [semantic encounter policy](../memory-architecture.md#encounters-sensory-detail-and-reminder-continuity); a routine animal reacquisition need not initiate reasoning.

The [3× scene report](../verification/three-times-scene-performance.md) separates throughput, cold/warm command/publication tails, post-GC heap and browser frames. Do not infer smooth play from average simulated speed or a renderer-only result.

## Design and review guidance

Before changing or reviewing database access, schemas or indexes, including new or expanded callers of existing repository helpers, read [Storage execution](#storage-execution) and trace the actual adapter connection/transaction path. For paged SQL, a result limit or application scan allowance does not bound database work. Inspect the actual production query plan, including expanded views/functions, rows, repeated loops and buffer reads, on representative data before manually refreshing statistics; fresh bulk and naturally aged data are distinct workloads. Scalar headers or bounded first queries can still expand aggregating views or multiply whole-history scans in later joins. Prefer indexed selection and batched related reads in the same snapshot when the plan demonstrates that problem. Prune in-memory revoked/forgotten IDs before SQL hydration, and skip empty allocations or no-op transactions when no eligible rows remain. Count statements across the complete observer/source batch, not only one observer. A timeout disappearing is not sufficient performance evidence.
