# Performance measurement and interpretation

Part of the [performance contract](../performance.md). Read for the matching mechanism; historical results qualify only their recorded workload and revision. [Verification](../../.agents/rules/verification.md#choose-the-execution-location) selects checks and requires AWS execution for speed tests using the [standard worker](../../.agents/rules/verification-workers.md#standard-speed-test-worker), subject to Mike's explicit exceptions. This includes the short diagnostics and browser measurements below.

## Reporting results

Lead performance summaries with **CPU usage as a percentage of one core** and **game speed achieved as a percentage of the intended rate**. Identify the measured window, workload/population and run count beside these results.

- **CPU:** `100 × CPU seconds / elapsed wall seconds` for the same window. Report server CPU (including Native and worker threads) and exclusive PostgreSQL CPU separately; identify client/load-generator CPU separately when measured, then give the combined total. Count each process/thread once. One core here means one logical CPU (vCPU); a value above 100% represents more than one core's worth of CPU, regardless of machine size. Whole-process server CPU already includes its threads.
- **Game speed:** `100 × completed game seconds / intended game seconds` over that window. For a constant intended rate, intended game seconds are elapsed wall seconds × configured game-seconds-per-wall-second, including the selected play-speed multiplier. Use the workload's declared schedule for planned rate changes or pauses. Unexpected pauses, stalls and unfinished work remain in the window. If intended progress is zero, report game speed as not applicable; if it is unknown, report the percentage as unavailable. Retain actual completed/intended time and accumulated debt so a percentage does not hide lost progress or later catch-up.
- **Distributions:** report the median (p50), arithmetic mean (average) and p95 together, with units, sample count and the population/window they summarize. This includes command response, first affected view/movement and durability latency. Distinguish individual observations from statistics across repeated runs; a median of run p95 values is not a pooled p95. Whole-window CPU and game-speed percentages are window averages: label them accordingly, and identify statistics across repeats separately. Sampled CPU/rate percentiles require actual interval samples and their cadence; unavailable statistics stay explicitly unavailable.

Keep CPU per completed game-second as supporting efficiency detail after these headline measures. Preserve complete-work qualification, repeated-run spread, failures and missing accounting; a stalled or incomplete run cannot establish a speedup. Keep steady play, setup, drain, reconnect, cold reopening and administrative recovery windows distinct, and retain the relevant latency, memory, database and storage costs.

Give before and after explicit column labels, or define an arrow as control → candidate and name the statistic order. Every value needs an unambiguous unit. Name workload conditions, such as ordinary play or a held NPC reply, separately from the compared implementations. Different experiments have their own baselines. For manually advanced workloads, label completed/offered time as completion and report wall duration and debt; an exhausted manual offer alone does not establish automatic game speed. Interpret CPU share alongside completed work and wall duration, since a lower share over a longer run can consume more total CPU.

## Planning comparisons

Use the existing task plan to identify the affected caller, complete-work criteria, candidate/control, workload, repetitions and decision before dispatch. Reuse applicable component evidence and choose the smallest experiment that answers the question. A bounded actual-caller diagnostic can screen an optional candidate by cost per call and observed frequency before a complete-server campaign. Complete-path claims still require representative complete work; existing required journeys, repetitions and adoption gates remain controlling. Reducing those obligations needs an explicit scope decision before new runs.

Keep independent candidates on a common repaired baseline so withdrawing one does not force unrelated candidates to be rebuilt and requalified. Apply a required common repair to both arms of each affected new comparison. Preserve older frozen results. Share controls only when source/build, workload, settings, instrumentation, worker conditions and measurement window match; declare the balanced interleaving in advance. Reusing one control cohort across comparisons does not create additional independent observations.

Inspect actual-work outcomes as runs complete. Declare any correctness-based early-stop rule before dispatch; frozen campaigns retain their original continuation rules. When that rule applies, preserve the failure, collect/clean up started work and hold dependent unstarted repeats. Continue independent experiments. A first pair may count toward planned repeats when executed under the same frozen plan; a passing pair does not justify skipping later repetitions. Never replace an unfavorable result with a favorable retry or select continuations based on their speed.

Use [parallel worker scheduling](../../.agents/rules/verification-workers.md#parallel-comparisons-and-reuse) for independent campaigns. Compare total development time using the existing phase timeline, separating builds, gameplay, transfer and cleanup. Monitoring waits and work performed while a campaign runs overlap that campaign's elapsed time. When recurring setup dominates, prioritize its demonstrated costs through the maintained worker owner rather than expanding the test matrix or building new infrastructure.

## Data foundation measurements

Canonical record commits, independent read/write lanes and SQL-first memory retrieval are implemented. [Recorded runs](../verification/data-foundation.md#data-foundation-runtime) separate structured/semantic retrieval, full local preparation, source indexing, cold extraction, native simulation, commit and recovery. Physical observation can omit memory preparation when its caller supplies SQL recall. Exact vector ranking remains the default; no arbitrary 20 ms limit or new searchable-history cap is imposed. Dense first exposure, active-history copying, checkpoint size and full browser/network/live-AI workloads remain qualification gates.

## Optional measurement

For a thorough campaign, use [hierarchical profiling](hierarchical-profiling.md): direct parent/child timings, per-unit distributions, three repetitions, overhead qualification, hardware comparisons and local artifacts. The maintained [simulation inventory](simulation-inventory.md) maps server/world components and candidate workloads; select its IDs or supply another explicit inventory. Its [default opening campaign](simulation-inventory.md#initial-run-plan) measures 27 runs, with expensive children detailed only on the standard machine; broader catalogue scenarios are deferred. Its new tooling is a target tracked by PC07–PC10, not a capability supplied by existing timing rings or CPU samples.

The complete-server harness, `scripts/profile-server.ts`, keeps its historical crowded comparison by default. Set `OPENLEGEND_PROFILE_STANDARD=1` to measure the authored opening without diagnostic additions; the report identifies that fixture explicitly. It cannot be combined with the expanded fixture. Compare like workloads and retain both ordinary-play and capacity results.

A disabled recorder must skip its preparation: optional clock reads, argument scans, peak statistics, arrays, timers and listeners. Keep the actual byte limits, deadlines and other facts needed for gameplay or safe resource use. Optional observation must preserve the operation’s execution and result; decoding a request for a report must not prevent the original request from reaching its authoritative validator.

Decide which optional diagnostic content is needed and admit its retained cost before copying or decoding it. Enforce source-text, encoded-byte and traversal allowances during preparation, rather than constructing a complete value only to discard it after serialization. Redaction or compression can shrink output without bounding the work needed to inspect its source. Reuse owned immutable preparation. Account for recent records, active captures, pending writes and active write batches together; a bounded pending queue alone does not bound retained data. Encoded-byte allowances do not establish peak JavaScript heap use. Retiring a capture drops its content references and closes interest even when abandoned transport work continues settling; check interest again before a later optional copy. Omitted diagnostics remain explicit, and authoritative accounting and required outcomes retain their existing owners.

Keep resource ownership, saved progress and failure handling independent of whether statistics exist. Bind asynchronous measurements to their exact recording session; Stop releases pending measurement resources and prevents late work from entering a later recording. Put cleanup around resources as soon as they are acquired, including later configuration, manifest and initialization failures. Attempt later independent cleanup even if an earlier drain fails. Disabled, missing, unavailable and omitted data are distinct from a measured zero.

For comparisons, verify the build and effective settings actually running in each sample, including inputs that activate the changed feature; a rebuilt output directory or updated browser route is not proof the candidate loaded. After authoring or changing a fixture, validate its world and definitions, including feature invariants, through their owning validators before timing; storage-only validation does not qualify a complete current-format cold reload. Finish observer preparation before releasing the paused or otherwise fixed workload. Record actual start/end and resume boundaries for each process. Matching clicks is not matching actions: verify successful work per participant, sustained input, interface obstruction and the visible scene through the measured interval. Keep console/HTTP failures attributable independently of optional timing. An unequal-work pair is inconclusive; it cannot become an overhead percentage or a smoothness pass. The [recorded comparison](../verification/performance/profiling-controls.md#expanded-game-comparison--october-17-2026-2352-edt) illustrates these limits; [current tool instructions](../projects/profiling-controls/tools-and-verification.md) own the concrete procedure.

## Rebased acquisition and full-server measurement

Keep native output correctness separate from implementation cost. Reuse unchanged observer/source relationships, seal owned experience copies through the shared domain finalization owner, and avoid whole-roster draft snapshots. Preserve generic status and knowledge semantics; never exchange actor-private evidence for a shared knowledge cache. Existing authoritative owners and deterministic transition order remain unchanged.

Measure the native kernel and actual server separately using the existing native profiler and the [bounded server workload](../maintainers/performance-profiling.md#full-server-workload). Real-time debt, successful/rejected commands, SSE/projection, persistence, event-loop delay and excluded clock gaps all matter. Cold acquisition occurs after normal server bootstrap; native cold profiles remain a separate cache-start workload. Phase maxima labeled cumulative are not per-phase latency percentiles. Implementation, evidence and residual gates remain in [PF](../maintainers/performance.md#perceptionevidence-and-burst-delivery) and [Verification](../verification/integration-summaries.md#rebased-action-and-perception-performance).

## Design and review guidance

For copied-source comparisons, verify tracked contents against the pinned Git revision and actual checkout-local workspace-package resolution through the existing profiling check. Matching source hashes alone does not establish which dependencies execute.

Preserve distinct sampled nodes and call sites when aggregating profiles: anonymous or transpiled callbacks can share function/file labels. Confirm a proposed expensive source site with bounded phase timings and work counts before redesigning it; a combined label does not isolate one constructor.

For work added to a shared execution path, estimate caller frequency × candidates visited × work per candidate, including nested queries. Include uneven relationships in relevant stress workloads: many invitations reaching one person can cost differently from the same number of disjoint pairs. A per-sender bound does not bound recipient work. Measure through the actual callers and mutation/publication lifecycle, preserving production cache eligibility (including mutable versus frozen state); an isolated helper benchmark cannot qualify that path. Count visited or recomputed items when timings alone do not explain the cost.

Keep correctness inspection from changing the measured caller's ownership or baseline. A load, current-value projection or complete re-encoding may replace reusable metadata even when it leaves gameplay fields unchanged. Inspect through a non-installing read or an independent copy outside timing, and verify that subsequent warm behavior remains representative. Cloning the timed production path itself is not a substitute. Match restored snapshots to the service’s resident data through its actual restoration/eviction owners; complete checkpoints can include cold records absent from live memory, and JSON loses process-local preparation metadata. Sampling overhead can itself trigger cooperative time-budget exits; rank CPU with sampling, but qualify retained changes through a matched unsampled caller. The [saving comparison correction](../verification/performance/overhaul-storage-implementation.md#whole-saving-architecture-control--october-17-2026-1452-edt) records this failure mode.

When stress is selected under [Verification](../../.agents/rules/verification.md), exercise the changed runtime path with the specified workload. Use disposable worlds and new private output paths. Include cold rebuilds and changes that invalidate reuse, not only warm cache hits. Verify that the stress driver continues delivering work to every intended participant after refusals or errors; an unchanged initial population can hide a dwindling active workload. Match the runtime's mutation/freeze behavior, cache lifecycle and cold/warm setup: frozen fixture definitions can hide repeated signature work in a mutable service world. Report isolated calculations separately from actual caller and whole-path timings, preserving repeated-run variance rather than selecting the favorable sample. Record matched before/after evidence and remaining bottlenecks; unavailable baseline or runtime access is a limit, not invented improvement. A timeout is incomplete, not a capacity pass. Do not require stress for unrelated edits or weaken behavior just to hit a timing number.
