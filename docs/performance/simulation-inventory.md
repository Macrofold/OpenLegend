# Simulation measurement inventory

This maintained inventory maps server/world work to direct measurements and reproducible workloads. Use it in full or select stable IDs and their descendants for a narrower campaign. The [hierarchical profiling procedure](hierarchical-profiling.md) defines collection, statistics, overhead, artifacts and execution; it also accepts inventories unrelated to this one. Do not duplicate its measurement machinery here.

**Source census:** Macrofold/OpenLegend, `codex/stealth-runtime-01-evidence`, commit `2a17fa7c42f777c5eefd3fba67c652ef2c5f54ec`, November 7, 2026. This is the selected gameplay source for the first campaign even if the branch moves. Current instrumentation is incomplete; rows below specify coverage to implement, not measurements already obtained. Code under `apps/server/src`, `packages/domain/src` and `packages/spatial/src`, plus the server's shared protocol/AI/network consumers, is in scope. Rendering, asset production/delivery benchmarks and external AI/embedding execution are excluded from this campaign. Server-side context, model-result validation/application and native reactions remain in scope with controlled inputs.

## Reading and maintaining the hierarchy

Each numbered heading groups real operations; its parent series brackets the actual entry points below. Each row is a child measurement with a specific unit and boundary. Dotted IDs identify children; sub-blocks listed in a row are separately timed descendants when the row contains a semicolon-separated sequence. In the tool registry give those descendants descriptive suffixes, e.g. `S05.04.people`, `S05.04.objects`, `S05.04.selected`; never collapse them into an unexplained total. Paths name semantic owners; functions locate boundaries, not an instruction to time every call with every probe enabled.

Unless stated otherwise, a function measurement brackets the real call including its early exits and exceptions. Distinguish `cold/rebuilt`, `reused`, `changed`, `unchanged`, `empty`, `refused`, `failed` and `stale` only where those branches exist. Work counts come from existing loop/results, not second scans. All measurements have mean, median, p95 and p99 under the procedure's observed/sample-size rules. Counters and gauges have totals/rates or time series, not fictional latency distributions.

`S00`–`S16` form a **coverage hierarchy**, not additive CPU categories: events can run inside movement and shared queries inside several categories. A trace may attribute one invocation to one actual parent; the human report must retain this distinction. In particular, do not sum `S05` + `S06` + `S07` + `S08` and call it total perception without checking nesting.

### Direct parent series

Use separate `entry` dimensions when a subsystem has several real entrances. Do not time the whole campaign and label it “all movement,” or synthesize a parent latency from its children. A folder containing independent operations has no single per-invocation latency; show its actual parent series and separately qualified CPU attribution.

Logical lifetimes with yields/awaits record both directly observed end-to-end latency and active segments. Scope variants remain distinct; a command's asynchronous total is not an actor interval's cost. For sight, the phase and observer parent series are required even when only its children are the question.

When code changes, update the affected rows and scenario assertions in the same feature change. Keep meaningful IDs stable. Before a complete campaign, enumerate HTTP routes, native command cases, interval phases, installed activity/status families, timers/workers and SQL writers against the frozen source. Classify new entry points here; classify data-only files with their consuming family. Emit `coverage.csv` containing each requested row, its bound source and positive scenario, plus explicitly excluded/unmapped entry points. A source file list is a coverage audit, not a requirement for a timer in every file. Significant sampled work with no row is added before claiming complete attribution.

### Useful denominator counters

Every case records actual game seconds, live/participating people and animals, controlled versus scripted actors, nearby/visible/attended subjects, actions admitted/completed/cancelled, successful displacement/work, events and recipient fan-out, current contact count, recent entries/pages, memory count, saves, database calls/rows and client connections. Capture whole-state censuses only outside timing; during timing maintain already-known counters or the existing low-rate bounded observations. Track per-actor activity counts for the fixed roster so hundreds of idle entities cannot masquerade as hundreds of active characters.
