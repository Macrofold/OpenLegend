### Mature-world tick profiling

Read-only inspection of the running local PostgreSQL game on Apple M1 Pro / Darwin arm64 / Node 22.23.2 found approximately 93% of one CPU core in use. This excludes initial freezing cost and does not establish long-session or editor/migration compatibility. That input-only experiment preceded the server ownership-boundary implementation described below.

Independent disposable SQLite HTTP servers loaded that same snapshot with explicit zero spending and no provider credentials. Over approximately ten seconds, 1× accepted 413 simulated seconds (41.27 per real second); 3× accepted 444 (44.37 per real second), versus required rates of 60 and 180. The 3× run recorded 4.257 real seconds excluded by the existing greater-than-two-second suspension rule and a maximum completed tick of 2,186 ms. CPU gauges approached 100% of one core. In-flight batches were still running at observation; native work counts therefore exceed accepted simulated time. These short runs used SQLite, not PostgreSQL, and shared the machine with the existing live game. They reproduce saturation and clock loss, not stable tail estimates or population qualification. The live game's speed/state was not changed.
