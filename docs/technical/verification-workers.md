# Reusable verification workers — technical design

Last used for implementation/review: `2026-11-01T00:09:20Z`.

## Owners and minimal architecture

The [feature specification](../features/verification-workers.md) owns intended behavior; [agent procedure](../../.agents/rules/verification-workers.md) owns use. Keep this tooling under `scripts/verification-workers/`, exposed through `pnpm verify:worker`. `contracts.mjs` owns campaign/job plans, results and boundary validation; `campaigns.mjs` owns the durable roster, assignment and aggregate escrow; `coordination.mjs` supplies short fenced metadata locks; `images.mjs` owns clean tool-image preparation; `cli.mjs` owns preparation, heartbeats and collection; `controller.mjs` owns cloud admission/claims/lifecycle; `supervisor.mjs` owns host processes and cleanup. Source packing and artifact transfer are helpers shared by those callers, not separate services. Keep one infrastructure template and bootstrap recipe beside them. Reuse existing native/server/browser profilers, the disposable PostgreSQL helper and workspace-resolution guard; no cloud coordination belongs in domain, game server, AI or world packages.

Use one small IAM-invoked Lambda controller, one DynamoDB coordination table, SSM for remote commands/private tunnels, private S3 prefixes for source/results, and an EventBridge Scheduler wakeup for recovery. The controller has reserved concurrency **16**. Short per-worker locks allow independent leases/reports concurrently; only slot-set admission and financial settlement use the pool/allocation locks. Every committed metadata transaction checks its held lock token/expiry. Definite effect-free transaction conflicts receive bounded backoff; conditional lock contention returns busy. Unknown writes and experiment execution are never retried by that mechanism. Locks never span boot, installation, experiment execution or bulk transfers. Finished-run collection updates its own metadata field under a separate lock, without delaying a successor host lease. It returns after bounded control operations without waiting for boot or game completion; game execution never runs in Lambda. An instance-local supervisor owns child processes. The independent scheduled recovery and host watchdog cover loss of the developer's laptop and controller failures respectively. No Kubernetes, continuously running coordinator, fleet autoscaler or agent-specific shell harness is needed.

DynamoDB stores only development leases, run metadata and compute reservations, not game state. Game checks continue using PostgreSQL exclusively. The atomic lease table is necessary because local lock files, EC2 tags and separate worktrees cannot arbitrate a stopped worker across hosts. Tags provide discoverability, never authority. Deployment records exact resource IDs in one pool configuration, separate from secrets; use the project/Region owner in [AWS guidance](../../.agents/rules/aws.md).

## Operational defaults

These are initial replaceable development settings, owned by the pool configuration and emitted in every run manifest. Change them for measured need within authorization; they are neither game limits nor measured capacity claims.

| Setting   | Default and reason                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pool      | Default capacity two; explicit configured capacity 1–128, counting quarantined/stopping slots. `concurrency` is required per campaign and never silently reduced. Two warm-cache slots; additional hosts are temporary burst capacity.                                                                                                                                                                                           |
| Machine   | On-demand, non-burstable x86-64 Linux, 4 vCPU / 16 GiB RAM, 64 GiB encrypted gp3 EBS. Resolve the available family/image and current price at deployment; record CPU/storage details. No Spot interruption or CPU-credit dependence in ordinary comparisons.                                                                                                                                                                     |
| Claim     | Entire host exclusive. One job, possibly containing ordered comparison cases, per claim. Claim only after inputs are ready.                                                                                                                                                                                                                                                                                                      |
| Liveness  | Runner heartbeat every 30 s; lease expires after 180 s without a successful renewal. Host checks every 30 s; scheduled controller recovery every minute. These are watchdog targets, not guaranteed AWS response times.                                                                                                                                                                                                          |
| Deadline  | Require a complete run deadline including setup/results/cleanup: 60 min by default, at most eight hours when explicitly planned and budgeted. Reserve a final 120 s for cleanup; refuse a plan that cannot fit. A new longer run needs its complete reservation; an active immutable plan cannot be extended in place. Heartbeats never extend the hard deadline.                                                                |
| Waiting   | Admission refuses an unavailable complete slot set. Admitted jobs queue durably by ordinal; no host is held for an unassigned job. Scheduling is best effort between campaigns, ordered within one campaign.                                                                                                                                                                                                                     |
| Idle      | Stop after 5 min idle, using EC2 stop and instance-initiated shutdown behavior `stop`. No hibernation. Reserve the idle tail and stopping allowance in the releasing run's estimate; a new claimant can assume subsequent occupancy.                                                                                                                                                                                             |
| Retention | Warm slots fund seven days of retained storage after the campaign window. Burst slots fund the campaign plus 24-hour recovery and retire after clean export. Only an extension beyond an existing funded storage deadline is charged; renewal requires admitted budget. Source and disposable output retention is seven days; required results become eligible only after verified collection under the artifact contract below. |
| Disk      | Enforce a 10 GiB dependency-download cache cap, a root-only immutable archive cache capped at 4 GiB/256 files, a declared per-job source/output/database allowance and at least 10 GiB free-space headroom. Reject an oversized plan or admit a larger worker explicitly; stop an over-budget capture with an incomplete result, not silent data loss.                                                                           |

There is no free standing pool budget. Before registering a task, allocate a finite cloud amount from its remaining [task spending allowance](../../.agents/rules/verification.md#spending), after all other settled, reserved and uncertain spending. That allocation stays unavailable to sibling/provider work until explicitly returned. The controller enforces only this cloud sub-budget with integer micro-USD reservations; it does not query or replicate provider ledgers. All agents on that assigned task share its stable task ID/allocation. Increasing it requires additional existing task headroom or Mike's authorization; a new run/worktree/task alias never resets the ceiling. Native checks set `AI_BUDGET_USD=0`; paid-model experiments remain outside these delivery tasks.

Reserve one campaign amount before any upload: the bounded compute/IPv4 window, incremental retained storage, a simple control/transfer margin and all declared paid-job limits. Child-job estimates are informational, never duplicate reservations. Admission captures a small aggregate summary and exact manifest fingerprint; immutable source/input/grant publication precedes staging/dispatch. The full manifest must match that summary. Resume checks the original executor binding and continues the same funded publication, never another experiment. There is no upload-charge API, per-package fee journal or second staging wallet. Paid closure accepts only the exact campaign and nonnegative safe integer amounts; malformed evidence retains the hold. Unchanged settlement polls do not rewrite rows or reread the allocation; changed monetary categories still refresh status without duplicating charges. After physical stop/reuse is confirmed, automatic financial monitoring ends at the original campaign deadline plus the existing cleanup allowance. Unresolved funds remain held, with `settlementMonitoringEndedAt` recorded and the row removed from the active settlement index. `resume` performs one authenticated reconciliation of that original record; it never reopens work. Unknown hardware remains actively owned/recovered until closure is established.

At execution completion release host ownership without waiting for idle stop. Budget settlement runs through its own bounded indexed group, so pending finance cannot starve active campaigns. Each campaign retains only its first claim and final run per used host; final lifecycle metadata supplies the earliest confirmed stop, termination or handoff to a successor campaign. Compute is an estimate from that observed interval and the configured rate, including the minimum billed interval. Required retained warm storage stays funded; confirmed burst termination releases unused storage allowance. Never turn an unknown power/cleanup result into a refund.

The allocation distinguishes its remaining reservation from estimated charges. After confirmation, release the unused compute hold; show compute, retained storage, operations margin and known paid amounts separately. Unknown/reserved paid obligations stay reserved after automatic monitoring ends and remain available for explicit reconciliation; completed known costs update the same allocation by delta, without double-counting. Estimates are not AWS invoices. Historical charged estimates and actual/uncertain provider receipts remain intact; simplification grants no authority to erase or reinterpret them. Watchdogs bound ordinary occupancy but do not promise an absolute AWS bill cap during an outage.

## Claim and execution contract

Idle stop and retirement publish their intent under the allocator fence, so a reserved but not yet claimed host remains occupied. A host-local stop may already be in flight when a claim arrives: wait for stopping to finish, then restart that same registered instance before dispatch. This power transition neither replaces the job nor replays its experiment.

### Runner input and output

The CLI uses one current campaign schema. `plan PLAN.json` validates and estimates without mutation; it does not verify live capacity. `allocate TASK_ID --usd AMOUNT --authorization-ref REF` records an existing task's cloud sub-budget and cannot silently increase it. An explicitly authorized increase uses `allocate ... --previous-usd CURRENT` with the exact prior amount; it retains all charges/reservations and appends the authorization adjustment. `run PLAN.json` packages, uploads, admits, stages, watches and collects a campaign. `status CAMPAIGN`, `cancel CAMPAIGN`, `collect CAMPAIGN DESTINATION` and `resume CAMPAIGN` use its private capability; resume observes original work and never replays an experiment. `retire SLOT` and `recover SLOT` retain the existing lifecycle fences. Private state lives under `~/.codex/verification/OpenLegend/workers/` (overridable by `OPENLEGEND_VERIFICATION_HOME`); it contains capabilities and must stay outside Git/logs.

| Level    | Contract                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Campaign | Existing `taskId`/`cloudAllocationId`, required `concurrency` 1–128 not exceeding job count, 1–4096 unique `jobs`, optional `inputs`, `deadlineSeconds` default 3600/max 28800, `lifetime` attached by default or explicit durable. Total encoded manifest ≤16 MiB.                                                                                                                                                        |
| Job      | Unique `id`, `mode` batch/browser-session, explicit `timeoutSeconds` ≥180 and below the campaign deadline, 1–16 ordered `cases`. Optional `paid: {limitMicroUsd,maxCalls,lanes}` authorizes only the shared service. Optional exact supported environment, `outputLimitBytes` (default 256 MiB), `diskLimitBytes` (default 16 GiB), relative `requiredArtifacts` and `acceptance` check/measurement. Job metadata ≤64 KiB. |
| Case     | Unique `id`, exact 40-hex `source`; packaging fills required cloud-side 64-hex `sourceHash`. Ordered `steps` (1–32), public string `env`, up to 8 unique `databases` aliases and 32 `inputs` mounts, optional case-relative required artifacts. Fresh source/home/results/databases for each case; steps share only that case's state.                                                                                     |
| Step     | Unique `id` and literal `argv` using installed node/pnpm/python3/psql; optional `database` names a declared alias and injects protected `PG*`/`DATABASE_URL`. No shell interpretation or inline installer. `{source}`, `{results}`, `{inputs}` substitute admitted paths.                                                                                                                                                  |
| Input    | Campaign declares unique bundle `id`, local `root` and explicit relative `paths`; case mounts `{id,bundle}`. Only referenced bundles are packaged; unused definitions cause no file reads. Capture rejects protected files, links, escaping/changing files, >50,000 files or >512 MiB data. Each job uses at most 32 distinct bundles.                                                                                     |

`OPENLEGEND_JOB_INPUTS` names read-only mounts; `OPENLEGEND_JOB_DATABASES` names an immutable alias-to-loopback-connection JSON file. Use normal authored initializer/import owners to create game state; data-only SQL is suitable for infrastructure fixtures. Public env cannot replace source, lifetime, database ownership, process settings, credentials or `AI_BUDGET_USD=0`. Paid settings are not admitted by this native framework.

One browser-session campaign is attached, concurrency one and one job/case. It reserves this physical developer device before cloud admission. `device status` inspects ownership; after the original process is gone, `device release OWNER [--confirmed-closed]` requires confirmation of actual browser closure if cleanup was uncertain. No timeout or alternate worktree steals a GPU claim.

Validate the plan once at admission; freeze its hash, source manifests and exact command/configuration per case. An execution change requires a new run. Public overrides follow the tool's supported settings and cannot replace the owned database or enable paid AI; credentials use separate secret references, never plans/logs. Each response includes run/worker/generation, phase, deadline, outcome (`completed`, `failed`, `interrupted` or `not-started`, absent while running), artifact locations and estimated/reserved/uncertain cost. Preserve check, setup, transport, timeout, resource-limit and cleanup failures distinctly. A completed process is not an acceptance pass: report acceptance separately as passed, failed, measurement-only or unassessed. A job that cannot fit its full timeout within the remaining campaign window is `not-started/campaign_deadline`; no silent shorter measurement or refund from incomplete observation.

Persist these small records in the coordination table. Admission inspects the bounded slot registry; job callbacks use exact keys. A sparse `group-order` index selects active campaigns, image builds and due workers; roster pages derive 25 exact ordinal keys, never scan run history:

- **Worker:** fixed slot ID, exact instance/volume IDs and environment identity, lifecycle state, monotonically increasing claim generation, run/active-case ID and admitted plan reference/hash, lease/hard deadlines, last clean receipt and pending control operation.
- **Campaign:** immutable S3 manifest/hash, private capability hash/dispatch capability, original worktree, staging cursor, next ordinal, bounded active job IDs, selected slot set, lifetime/deadline and aggregate reservation. Publish at most 20 job rows per transaction; no job launches before complete staging. Parent cancellation projects unassigned rows as not-started and closes counters without per-job rewrites; terminal parent requests cannot change the sealed outcome.
- **Run:** unique ID, assigned task, original absolute worktree and owning agent's claim-secret hash, source and plan hashes, worker/generation, timestamps, command IDs, phase/outcome, artifact prefix/manifest and informational cost estimate. Human branch labels are diagnostic; content hashes determine source identity.
- **Task allocation:** authorized cloud sub-budget/provenance, charged estimates and outstanding cloud reservations. Other task spending remains with its existing owner; preserve uncertainty instead of refunding a lost receipt.

State transitions are `available → leased → releasing → available`; stop uses `available → stopping → available` only after EC2 reports stopped. A leased machine may be booting, preparing or running; those are run phases. Fixed pool slots also support `empty → allocating → leased` and `available/quarantined → retiring → empty`. Allocating/retiring slots remain occupied for the pool cap; deletion must be confirmed before reuse. Failed recovery enters `quarantined`. Never mark a machine available merely because its lease time passed.

1. **Admit/stage:** package distinct sources/inputs locally and read applied EC2/EBS quotas, selected AMI, subnet capacity and registered availability. Under short pool/allocation locks atomically reserve the complete slot set and one conservative funding hold before uploads. Publish the immutable manifest and private paid grants, then stage immutable job rows in batches of 20. Repeated IDs require identical fingerprints/capabilities; partial publication resumes without a second reservation or execution.
2. **Claim:** assign initial jobs to distinct reserved slots automatically; acquire all requested initial instances before experiment dispatch. A definite creation rejection cancels this initial wave, rather than running less concurrency. Later freed hosts take pending jobs. Conditional writes bind assigned job, campaign, worker/generation, lease and deadline before EC2; creation tokens identify slot/generation and unknown creation retains ownership. No caller maps a job to an EC2 instance.
3. **Prepare/start:** record the intended operation before calling EC2/SSM. Each operation includes worker ID, generation, run/case ID, operation ID and expiry. The supervisor takes a local lock, strongly reads its lease and checks the admitted plan/current case before installing inputs or starting a child. Hold that lock only for transitions/launch, never while awaiting the child or uploading, so watchdog cleanup cannot deadlock. Persist operation IDs so duplicate delivery cannot execute twice. Started-but-unfinished is uncertain, never automatically rerun. Advance cases only after preceding processes/commands and cleanup finish; delayed first-case commands cannot modify the second case.
4. **Execute:** use an unprivileged per-run process group/systemd unit with a hard runtime limit; database and output paths contain the run ID. Its PID group, command IDs and database names belong to that run manifest. A supervisor heartbeat updates observed phase, but **cannot renew an attached campaign submitter lease**. Durable campaigns continue without that submitter; cloud scheduling renews job leases under the original parent deadline. Every renewal requires the current worker/generation/run and an unexpired lease. Worker loss, cancellation or deadline stops subsequent dispatch and initiates cleanup.
5. **Release:** conditional transition to `releasing` closes dispatch. Stop/await all owned children, cancel and reconcile pending SSM commands, close/drop only run-owned databases, finalize/upload artifacts and delete owned workspace/temporary secrets. The supervisor acknowledges cleanup under the same generation. Only a verified clean receipt with no pending operations permits `available`; retain tools/cache. Failed cleanup quarantines. A shared database-catalog check rejects unowned leftover databases before execution, between cases, at final cleanup and before image capture; never delete an unrelated database to make a host look clean. Repeated release is idempotent; a stale release never affects a later run.
6. **Recover/stop:** the per-worker controller also handles scheduled recovery. For an expired lease, close dispatch and terminate the old generation; never transfer it directly. Authenticated cleanup of that generation remains permitted after expiry, but new preparation/work does not. Delayed SSM commands must be terminal or expired and fenced before reuse. Unknown process/control outcomes require quarantine or a verified stop/reboot and clean preparation. Reconcile interrupted requests against actual EC2/SSM state, not blind resend. Persisted stop/retirement intent retries only the idempotent EC2 operation on its exact registered instance after reading its actual power state; it cannot replay a game check. Pending cloud stop/start operations block claims; a claim racing host-local idle shutdown waits for reconciled readiness. No new work begins while an old operation can still stop it.

The host watchdog terminates its owned process group on lease loss even if the controller is unavailable. It uses the same local lock/generation checks for cleanup; stale callbacks cannot act on a new claim. At the hard deadline it blocks further launches and requests instance shutdown with verified `stop` behavior. Mirror the idle-stop deadline on the host too, so controller failure cannot leave an unclaimed machine running indefinitely. Once local shutdown begins, launch admission stays closed; the controller reconciles actual power state before resuming any concurrently acquired claim. Boot starts with launch admission closed until the supervisor reconciles its journal and current lease. Preserve source/results on EBS when upload fails and quarantine for recovery; stop compute rather than wait indefinitely for transfer. Once the machine is clean, the controller may stop it without deleting evidence.

The runner creates a random 256-bit claim secret before admission and saves it outside Git/logs in private task state; the controller stores its hash and a distinct private job-dispatch capability on the parent campaign; public status strips them and the scoped paid-closure capability. Mutations require the secret as well as matching generation/run. Status exposes no takeover capability; SSM commands carry only the controller-authorized operation identity, never that secret. Idempotent request recovery uses the same saved secret. Operator recovery is explicit and closes the old claim before acting.

Use DynamoDB conditional transactions, not TTL deletion, for correctness: TTL is eventual garbage collection. Active worker rows and uncertain accounting never expire through TTL. AWS documents [conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [atomic transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) and [delayed TTL removal](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html). Keep all state and mutations in the selected Region; do not introduce a distributed multi-Region lease protocol.

## Shared paid execution

`apps/server/src/attempt-repository.ts` owns the existing attempt schema, reservation and receipt settlement for both the game repository and the dedicated service. Game actor/monthly limits retain their existing behavior. A fixed job grant uses the indexed exact job-budget binding, rather than scanning other actors/campaigns or inheriting a monthly reset. `shared-execution.ts` owns task/campaign escrow, job grants, lane admission and original-request identity; the HTTP wrapper is a narrow authenticated facade. No billing logic or provider credentials live in domain or worker code.

Run the maintained `pnpm verify:execution /absolute/private/service.json` entrypoint. Configuration contains a dedicated PostgreSQL `databaseUrl`, a random `adminToken` of at least 32 characters, optional loopback `host`/`port` (defaults `127.0.0.1:3231`) and explicit `lanes`. Each lane supplies `id`, `kind` (`judge`, `generate`, `embed`), `provider` (`jev`, `openai`, `macrofold`), exact `model`, `reserveUsd`, `concurrency` and `requestsPerMinute`. Supported pairs are Jev/Macrofold judgment, OpenAI/Macrofold generation and OpenAI embeddings; other pairs refuse startup. Optional output/timeout bounds default to 8192 tokens/120 seconds; absolute bounds remain 16384/300 seconds. Direct lanes require explicit prices sufficient for their supported input/output envelope. Macrofold uses its existing configured billing/connection defaults and per-call spending bound. An explicit lane `target` supplies the existing `{workspaceId,modelBinding}` pinned-deployment contract; optional generation-lane `outputMode` selects its supported output strategy for either a catalog model or deployment. Catalog Contributor defaults to `prompted_json` through the shared [provider policy](../ai-providers.md#current-macrofold-routes); other models and deployment targets retain their defaults, and explicit modes take precedence. `json_schema` supplies the formal response schema; `json_object`/`prompted_json` append the schema to system instructions and still validate locally. The same existing deployment clients/receipt checks run without catalog fallback. Provider keys come only from the service’s operator environment through the existing adapters; missing keys refuse service startup. The service database is persistent financial authority, not an ordinary resettable game database or another saved world. Initialization rejects game-owned storage by its actual schema marker, even when a URL alias bypasses the environment comparison; it preserves existing financial records while extending call metadata. Back it up independently of Lab fixtures; never replace it with an old experiment snapshot.

The facade admits a task cap once and reserves nonoverlapping child grants for a frozen campaign. Grants capture the non-secret provider/model/target/billing/price and execution-bound fingerprint; changed service configuration refuses execution under old grants rather than silently rebinding them. Re-admission returns the original grant definitions. Macrofold generation grants expose their captured `outputMode` through the typed client. Preparation uses that same trusted mode before fitting, capture and local spending admission; a local catalog-format map must agree. One shared selector resolves the actual unique lane for both preparation and dispatch without inventing a model default. Request-only comparisons assert their planned mode so a mislabeled lane refuses before creating a paid attempt. Operator control authorizes funding/admission; each short-lived job capability permits only its declared cases/source hashes, lanes, call count, amount and immutable assigned run/deadline. `judge`, structured `generate` and `embed` reuse existing typed adapters. Full native world-tool harness execution is refused here; these grants do not carry world-effect authority. Provider lanes independently enforce active requests and rolling-minute admissions, with a service-wide 128-request bound. Campaign preflight verifies declared lane capacity; transient contention is a truthful refusal, never an automatic paid retry or an enlarged experiment deadline.

The worker plan adds `paid: {"limitMicroUsd":250000,"maxCalls":2,"lanes":["selected-model"]}` only to jobs requiring models. The native default stays absent/zero. Private CLI configuration is installed with `execution configure PRIVATE_ENDPOINT.json` containing `url` and `adminToken`; only HTTPS origins are accepted for AWS workers. Server/control clients reject redirects. The controller activates the immutable run, copies only that job’s capability to its own private run prefix, and the supervisor supplies a case-specific `OPENLEGEND_JOB_EXECUTION` file. No sibling grant hydration, control key or provider key is needed on a worker. The file is excluded from exports. Programs load it once through `loadJobExecutionClient()` and inject the returned typed client after ordinary actor/source/permission admission. Maintained consumers are `node --import tsx scripts/verification-workers/execute-ai.ts judge|generate|embed INPUT.json OUTPUT.json` and the isolated [Cognition Lab episode adapter](../../scripts/cognition-lab/README.md). The Lab retains native action, conversation and episode authority; the shared facade supplies typed execution and accounting only.

Attempts use a structured hash of grant, case and native request ID, plus an immutable request fingerprint. Identical duplicate requests observe original results/uncertainty; changed content refuses. Receipt `requestId` maps back to the caller’s native ID; `sharedExecution` preserves the service attempt, campaign/job/case and source identity. The service stores the original receipt once through the common owner. Per-attempt cancellation is saved in the existing call record, even when it arrives before the original request. A cancellation before admission consumes one grant attempt slot and no money, bounding stored cancellation intents. Cancellation/deadlines fence new inference and late value delivery across restart. Cancellation acknowledgements record intent without fetching provider billing or claiming execution stopped; explicit observation owns receipt recovery. The client sends one bounded cancellation request and need not await that cleanup to withhold a value. Job cleanup closes its grant, independently of successful host cleanup. Missing service acknowledgement retains paid uncertainty without pinning otherwise clean EC2 compute. Campaign admission stores its scoped closure capability before uploads; cancellation can close even an as-yet-unadmitted service campaign. That closure prevents a delayed admission from opening new paid work.

`GET /grants/ID/attempts/ATTEMPT` is observation-only under that job’s token. It returns original results while permitted, pending evidence, a recorded cancellation or receipt-only recovery. Permission is checked again after asynchronous receipt recovery. Existing Macrofold exact-Run receipt observation may settle original costs; it never creates another inference. Other unknown provider outcomes remain held until exact evidence is available. Closed/expired grants expose receipt recovery while withholding newly adopted values. Resetting a Lab, restarting the executor, cancelling a campaign or replacing a source cannot erase spending, refill a grant or replay its attempt. A separately hosted available executor is needed for durable paid campaigns to continue after the submitting machine disappears; the runner does not provision another permanent fleet/service implicitly.

## Prepared environment and source fidelity

Bootstrap from one maintained, pinned recipe: OS, Node/pnpm selected by repository pins, PostgreSQL/pgvector and the worker supervisor. Store its recipe/image hash and installed versions. Both experiment and image launch wait for this instance's cloud-init completion; a baked installation receipt is not current boot readiness. Reuse the EBS-backed installation across stop/start; prepare a new environment only when its required identity changes. Apply updates/reboots during idle preparation, never during a measured run; suppress competing maintenance and record unavoidable system load/CPU steal. The maintained `image prepare TASK CLOUD_ALLOCATION EXACT_SOURCE_COMMIT` uses a fresh empty registered slot, never an experiment host. Its $2 reservation funds preparation and seven-day image retention. It installs the same recipe and seeds pnpm content from the pinned lockfile with scripts disabled. Before capture it removes job/input/cache payloads, configuration, AWS/SSM/cloud-init/machine/SSH identity and transient state; capture requires a stopped host and exact sanitization receipt. A tools stamp skips OS downloads on restore. Explicit deployment selects the returned image; reaping deregisters expired owned images/snapshots. This is an on-demand clean-image operation, not another execution runner or automated image factory.

Reuse pnpm's [content-addressed package store](https://pnpm.io/10.x/symlinked-node-modules-structure), not a duplicate store per lockfile. A fresh workspace uses the pinned `pnpm install --frozen-lockfile --prefer-offline`; [pnpm fetches missing packages](https://pnpm.io/10.x/cli/install). Lockfile, Node ABI, pnpm version, platform and install settings identify the installation, not a reason to redownload unchanged content. Rebuild native dependencies as required; never copy macOS `node_modules` or another checkout's workspace links. Keep current repository install-script permissions. Force the admitted Corepack preparation rather than letting a comparison source silently choose another pnpm. Build outputs start fresh when needed. Use pnpm's own pruning only under an exclusive claim during preparation/cleanup, when pressure warrants it; pruning every release would erase useful reuse. No install, upgrade or cache maintenance runs during measurement.

Use EBS-backed `/var/lib/openlegend-verification/` for supervisor state, `cache/` and `runs/<runId>/cases/<caseId>/{source,results}`. Bootstrap logs belong in `/var/log/openlegend-verification-bootstrap.log`; runs retain their own stdout/stderr/timeline. Status returns those paths and artifact locations. Stream source/output byte limits and monitor free disk with cheap filesystem statistics; inspect output every five seconds and run/database size every 30 seconds, outside game scheduling; database growth guards are observed limits with headroom, not an invented hard PostgreSQL quota. Disclose monitoring overhead.

The source packager streams a compressed archive and manifest from an exact commit by default. Include maintained runtime/tooling files and pinned dependency/configuration files; exclude credentials/private saves/generated output, and record bytes/SHA-256. For a dirty snapshot, pin its base before building the private index, freeze an explicit changed/new-file selection and refuse files changing during capture. Preserve its archive as required evidence. Reject escaping paths/symlinks and missing workspace files. Required external assets retain their existing storage contract and exact selected release; an archive grants no permission to copy private payloads.

Publish under a private source prefix keyed by commit and archive hash; reuse a verified staged object only when its retention covers the complete admitted run and wait allowance; verify the archive and extracted manifest on the worker and before/after execution. Reject links resolving workspace packages outside that source root using the existing guard. Prefer a source manifest accepted by the profiler rather than reconstructing synthetic Git objects just to satisfy provenance checks. If a tool genuinely needs Git, use a real exact detached checkout. Reconcile existing profiler source checks in VW03; do not weaken provenance or pretend a copied directory is a Git checkout. Any manifest/tooling replacement needs actual mismatch-refusal evidence.

### Network and execution boundary

Use the selected project's suitable subnet with outbound internet access; the default is a public IPv4/Internet Gateway route and a dedicated security group with **no inbound rules**, not a new NAT gateway or endpoint fleet. Record and budget IPv4 cost; reuse an existing qualified egress arrangement when available. SSM initiates [outbound HTTPS connections](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-create-vpc.html); allow required HTTPS, DNS and time synchronization, use HTTPS package mirrors, and keep game/PostgreSQL listeners on loopback. Do not change shared network rules to make setup work. The deployment template must explicitly supply this connectivity rather than assume a private subnet has internet access.

SSM targets an exact instance; S3 transfers compressed source/results, not command-output blobs. SSH/SCP is a diagnostic fallback with scoped credentials, host verification and identical claims. The controller alone mutates lifecycle/leases; per-slot roles read their own lease, the sanitized pool source prefix and `workers/<slotId>/runs/` artifacts. The lease's admitted plan reference supplies the supervisor's execution authority; no whole-table permission is needed. Run trusted project code unprivileged, without supervisor credentials or instance-metadata access. PostgreSQL services and case/image-fetch units share a systemd slice blocking both metadata addresses, including fixture SQL that starts server-side processes; this is not a hostile-code or multi-tenant sandbox. Never copy developer AWS sessions or put secrets in [logged SSM parameters](https://docs.aws.amazon.com/systems-manager/latest/userguide/running-commands.html).

### Remote browser integration

The shared browser driver consumes `READY.json`, requires loopback HTTP/PostgreSQL metadata and uses either its local `startMarkerPath` or injected remote start hook. Diagnostic mode is headless and requests Metal only on macOS; representative mode is visible and selects the native backend. Reports record actual Chromium GPU/backend information. The selected speed comes from fixture readiness; the fixture's default remains unchanged. `scripts/profile-server.ts` supplies that marker and waits for it; `scripts/performance/profile-server.mjs` is the separate headless server workload. Do not treat these as interchangeable runners.

For a browser session, use the owned browser fixture on the worker and one [SSM port-forwarding session](https://repost.aws/knowledge-center/systems-manager-session-manager-connect) on the same ephemeral loopback port registered by the fixture. Refuse an occupied local port; preserve existing Host/Origin authentication instead of rewriting requests or adding a proxy. The runner verifies run/case/source identity and prepares local ready metadata for that origin; retain loopback, authentication and database ownership checks. Keep production client assets served by the worker, with API/SSE on the same tunneled origin; no separate public listener or proxy framework.

Keep the existing browser measurement implementation callable with injected `signalCaptureStart()`, `signalCaptureComplete()` and `awaitServerResult()` hooks. Its local CLI keeps the local marker path; the worker runner supplies a fenced supervisor operation that writes the worker's registered marker exactly once and awaits the fixture's capture acknowledgement. The browser performs Resume through the ordinary Game menu; speed is already selected by the fixture, without God mode. The hook signals instrumentation and never resumes gameplay again. Start/finish signals live in the fenced lease record, not a second event store; duplicate signals retain the original timestamps. The fixture acknowledges capture start, records its measured interval, and keeps HTTP alive for at most 30 seconds awaiting browser completion before teardown. Browser completion follows its final frame/screenshot; remote publication is awaited through the controller rather than a local filesystem path. Local mode uses the same atomic readiness, acknowledgement and completion-file contract. Failed browser activity, diagnostics or cleanup rejects the shared driver call, rather than merely setting its process exit code. Record browser resume, marker send/receipt and actual server/browser capture bounds; report overlapping windows and relay/clock uncertainty, not identical starts. Update all current callers together; do not fake a shared filesystem or copy the driver into a remote variant.

Use the explicit representative-device mode using a visible browser and its native graphics backend; retain headless mode for diagnostics. Do not send Metal flags to Linux or infer hardware acceleration from launch options. Record actual renderer/GPU/backend and keep uncertain/software results labeled. The runner holds the lease and tunnel until browser capture and server cleanup finish; tunnel loss interrupts the run, never starts a replacement or replays inputs.

## Measurement and artifacts

Keep one top-level `run.json`, source/environment manifests, stdout/stderr, phase timeline and optional existing profiler outputs. The runner wraps existing tools; add phase hooks at their actual boundaries rather than scraping prose or inventing a second simulation. Each phase records start/end, elapsed time, outcome and relevant byte/count/cache-hit facts. Use monotonic clocks within a process, UTC plus run/phase IDs across machines; record clock uncertainty and nesting. Do not sum overlapping parent/child phases.

Capture: local packaging/compression → source upload → wait/claim → instance start/readiness/bootstrap if needed → download/extraction/verification → dependency preparation → required build → PostgreSQL/database preparation → cold world startup → saved-world reopen when selected → warm-up → measured activity → drain → artifact upload/download → cleanup/release → actual stop. Capture controller admission and failures as events. Distinguish stages skipped through reuse, phases still running and unavailable timestamps. Separate human/agent idle time from automated overhead. Report cold and warm end-to-end totals, not just the profiler's requested duration.

Inside a standard five-minute experiment, preserve the existing actual workload evidence: actors and active actions, accepted/refused commands, speech, achieved game time versus requested speed, debt/backlog, pauses/recording blocks, event-loop delay, CPU, memory and storage growth. Preserve the profiler's available samples; the shared server profiler retains one-second progress samples (actual callback timestamps, world time, pause/backlog/error state, CPU and RSS), without entity scans or per-sample I/O, and reports their collection cost. Include startup and final drain separately so a fast unfinished run cannot pass. CPU/SQL detail captures remain separate from minimally instrumented throughput runs with the same workload. A fixture with idle NPCs is not evidence of active hundreds-of-actors capacity.

For browser work reuse `scripts/performance/profile-browser.mjs`: record frame interval percentiles/stalls, actual command acceptance and first rendered response, server-to-client updates and visible movement continuity. Record browser/OS/GPU, headless/software versus hardware rendering, viewport/pixel ratio, quality, asset release, network/tunnel topology and competing host load. Browser callbacks and renderer submission timestamps are not physical display presentation measurements. An AWS CPU-only browser can check UI behavior; qualify graphics on a representative device. Keep server loopback throughput distinct from real-network responsiveness. Report a measured result against the task's existing target; do not invent a universal FPS/device gate here.

Before release, upload case outputs under the registered worker/run prefix, seal their checksum/size manifest and verify receipt. A separate run completion receipt references those manifests and records cleanup/financial outcomes; stop may initially be pending. `run` returns after verified cleanup and artifact receipt, **without waiting through the five-minute idle tail**. Later status records either the stop or reuse by the next run, without changing experiment bytes or claiming unknown charges settled.

`collect` verifies downloaded checksums outside Git with up to three concurrent transfers and records destination/manifest acknowledgements; an approved durable archive can acknowledge collection instead. Automatic collection shares the run deadline; a later explicit collection or resumed collection gets ten minutes and can resume preserved files. Server and browser artifacts have separate checksum acknowledgements under the same run, sharing one admitted output-byte allowance; release waits for both producers and cleanup. A browser export appearing during collection requires fresh download/acknowledgement before becoming eligible for expiry.

Expiry eligibility progresses in batches of eight concurrent object updates, at most 64 objects per controller invocation. Stop beginning batches after 15 seconds or sooner near its deadline; five-second tag/cursor requests retain settlement headroom. Persist a cursor tied to the exact acknowledged manifests; the CLI resumes pending acknowledgements. This prevents large comparisons from blocking other claims/heartbeats or repeatedly restarting collection. Later lifecycle metadata is a separate supplement, preserving sealed experiment bytes.

Required artifacts are excluded from automatic expiry until acknowledged; optional output and staged source can expire after seven days. Use [tag-filtered lifecycle eligibility](https://aws.amazon.com/blogs/storage/simplify-your-data-lifecycle-by-using-object-tags-with-amazon-s3-lifecycle/), not unconditional bucket expiry. Adding eligibility to an already old object can make it expire immediately; preserve the destination first. No Object Lock, old-save migration or indefinite retention of every trace is needed. Missing required collection retains its cost commitment and a visible recovery item; stop compute, preserve the sole copy, and resolve retention before its reserved storage term ends. Delete EBS only once required payloads are verified elsewhere. Keep financial receipts/uncertain operations; discard redundant local exports after matching the sealed S3 manifest; retain compact financial/operation records. Never commit signed artifact URLs or private payloads; public documentation/source links are unaffected.

The [worker acceptance record](../maintainers/completed/2026/verification-workers.md) links measured setup timings; historical one-off bootstrap/profiler durations are not promises for this workflow. [AWS stop/start](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html) retains EBS but can change host/public address; a restarted machine is not necessarily the identical physical benchmark host. Record measured hardware and environment on every claim and use fresh matched comparisons when that matters.
