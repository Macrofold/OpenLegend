# How cognition runs, from movement to memory

This is a walkthrough of the installed code, inspected on November 5, 2026 at `bec86d8af288e9c7f7a00e376c479403620063b1`. It explains behavior and work, rather than prescribing a new design. Numerical defaults below belong to the bundled world or current server configuration; another authored world can supply different rules.

The measurements come from the [completed November 5 investigation](../verification/performance/bookkeeping/2026/2026-11-05-native-execution.md). Its measured runtime was `72eea53fd43f82b8f6a915c0e90383b6557005cb`. This is a dated explanation of that implementation and evidence, not a measurement of subsequent runtime changes. No new game run or model call was made for this walkthrough.

The cycles: [world updates](#cycle-1-advance-the-world) · [reception and attention](#cycle-2-receive-something-choose-attention-and-record-changes) · [thinking opportunities](#cycle-3-decide-whether-an-npc-gets-a-thinking-opportunity) · [request preparation](#cycle-4-build-the-information-for-one-decision) · [model calls](#cycle-5-decide-what-to-do-and-make-model-calls) · [applying answers](#cycle-6-the-answer-arrives-while-the-world-keeps-moving) · [search indexing](#cycle-7-background-search-indexing) · [reflection and learning](#cycle-8-consolidate-reflect-and-learn-during-downtime) · [retention and saving](#cycle-9-retention-correction-saving-and-restoration). The [measured CPU explanation](#why-the-tiny-opening-still-consumes-so-much-cpu) follows the cycles.

## The important distinction

There is no single “think every tick” operation. Several loops run at different times:

| Loop                   | What it does                                                                                         | Runs without a model?                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Physical simulation    | Moves bodies, advances work and bodily conditions, resolves collisions and native responses.         | Yes.                                                                                        |
| Reception              | Determines what each eligible observer actually receives through its senses.                         | Yes.                                                                                        |
| Detailed attention     | Chooses which received subjects get more detailed sampling and recent change history.                | Yes.                                                                                        |
| Opportunity scheduling | Decides whether an NPC has a new reason to consider doing or saying something.                       | Yes. It can decline before preparing a model request.                                       |
| Context preparation    | Collects that NPC's current situation, required evidence, memories, knowledge and available actions. | Mostly. Some routes can pay for relevance judgments, embeddings or conversation compaction. |
| Decision               | Selects an offered action, generates a response, or deliberately continues.                          | Native responses need no model. Semantic judgments and generated responses do.              |
| Memory maintenance     | Retains useful accounts, consolidates eligible older accounts, reflects and updates search indexes.  | Some work is native; summaries, reflection and embeddings use models when admitted.         |
| Saving and delivery    | Saves accepted changes and sends each player their permitted view.                                   | Yes.                                                                                        |

**The expensive native loops continue when model spending is zero.** The tiny-world CPU measurement used here had zero external model calls. Its high CPU use therefore cannot be explained by LLM inference or by building an LLM request every few seconds.

“Async” means a caller can stop waiting while another job proceeds. It does not mean JavaScript preparation runs on another CPU core. Most preparation still uses the server's main JavaScript thread. Database and provider waits release that thread; synchronous scans, copies, sorting and encoding do not. Some geometry work has a separate worker boundary.

## What the game stores

These are different things. Treating them as one “memory store” hides why the same subject is handled several times.

| Information                    | Example                                                                                         | Purpose and lifetime                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Physical world state           | A deer is at a particular position and is moving.                                               | Authoritative reality. Other characters cannot read this directly into their thoughts.                                             |
| Current personal reception     | I last saw this deer here; I saw its appearance earlier; I currently have usable sight contact. | One observer's received facts. Position, appearance, identity and other parts can have different dates and availability.           |
| Attention state                | This deer is one of the subjects I am tracking in detail.                                       | A small selected set plus information used to compare it with other received subjects. Selection is not a new sensory observation. |
| Recent received history        | I saw this deer at A, then B, then C; detailed coverage ended afterward.                        | Ordered, bounded records of actually received changes. It is not the world's complete movement log.                                |
| Retained personal accounts     | I heard a warning, completed some work, or formed an interpretation of what happened.           | Recallable events, memories and summaries, with their supporting evidence and retention rules.                                     |
| Learned identity and knowledge | I recognize this individual; I know their name; I learned where a place is.                     | Useful acquired knowledge can outlive the detailed route that first supported it. It does not grant current sight.                 |
| Accepted self-understanding    | Personality, identity, beliefs and relationships expressed in the character's mind documents.   | Included in reasoning and revised through bounded, validated reflection. It is not an ever-growing transcript.                     |
| Operational records            | This request is pending; this amount is reserved; this answer was already applied.              | Prevent duplicate spending and effects. These records are not experiences the character remembers.                                 |

Shared storage can hold an identical received value once. Each observer still needs their own permission, timing and identity association. Sharing the bytes for “red coat” does not let another observer know who wore it.

## The clocks and limits used below

The normal bundled clock advances **60 game seconds per real second**. That conversion assumes the server keeps up and the world is running at normal speed.

| Setting                               | Current value                                                              | What it actually limits                                                                                                                                      |
| ------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Server wake opportunity               | Every 50 real milliseconds                                                 | An opportunity to process elapsed time. Not one complete simulation step, sensory sample or model call. A busy update is not started again concurrently.     |
| Ordinary broad sight                  | Aligned opportunities 60 game seconds apart: about 1 real second           | Processing of pending relevant physical changes. A clean scene does not require a fresh full sight pass merely because the interval elapsed.                 |
| Ordinary detailed sight               | 30 game seconds: about 0.5 real seconds                                    | More frequent sampling of selected received subjects. Recognition and other finite sensory work also have their own due times.                               |
| Contextual geometry and relation work | 20 game seconds: about one-third real second                               | Bounded work using received bodies and nearby physical features. This does not automatically buy a new broad body-sight pass.                                |
| Ordinary sight radius                 | 28 metres                                                                  | Spatial eligibility before visibility tests, not a maximum number of visible subjects.                                                                       |
| Detailed attention                    | Normally 10 subjects                                                       | Default Focus 50 gives 10. The world computes `round(5 + Focus / 10)`, giving 5–15 for Focus 0–100; an explicit actor capacity can override the calculation. |
| Attention stability                   | 120 game seconds: about 2 real seconds                                     | Ordinary selected subjects resist small priority changes. Strong urgent cues can interrupt; stability is not a promise of continued visibility.              |
| Recent detailed history               | At most 6 game hours, 8 MiB and 131,072 charged changes per actor          | Whichever limit binds. Six game hours are about 6 real minutes. This is not a promise that every observation is retained for six hours.                      |
| Normal save target                    | About 1 real second                                                        | Several accepted world updates can share one database save.                                                                                                  |
| Unsaved-progress ceiling              | 5 real seconds or 64 MiB of pending work                                   | Further ordinary progress is held when the buffer cannot safely admit more; a small margin is reserved for emergency pause.                                  |
| Immediate thinking pipelines          | At most 2 per world; at most 1 ordinary pipeline                           | An urgent pipeline may coexist with an ordinary one. One actor cannot have overlapping decisions.                                                            |
| Provider execution                    | 1 primary execution and up to 100 background operations per server process | Admission ceilings, not a claim that 100 active characters or requests are performant. Spending and per-world limits still apply.                            |

“Query” below can mean either an **in-memory lookup** or a **database query**. Each row states which. An in-memory lookup can still allocate objects, traverse several nested structures and repeat thousands of times.

A few recurring terms describe concrete safeguards:

- A **world-update lane** lets only one writer change the world at a time. Publishing means accepting those changes into the live world; saving them to disk is a later step.
- A **captured cut** or **prefix** means all accepted work through a particular point. A job waits for that point to be saved, not for the world to stop changing.
- A **source binding** maps a short label in the model request to an exact permitted observation, memory or choice. It lets the server check what the answer refers to.
- A **cursor** remembers how far a job got. A **generation** identifies the current loaded world, so an answer prepared before a restore cannot affect the restored world.
- **Cold history** is stored in the database rather than already loaded in memory. A **projection** is the permitted part of the world prepared for a particular reader, such as a player.

### How to read the measurements beside each cycle

Unless a note names a different specimen, counts and sample shares below come from one completed diagnostic: **7 people, 20 animals, 74 objects**, one walking controlled player, ordinary speech, actual wildlife and player event-stream output. It used the standard AWS **m7i.xlarge, four logical CPUs/two physical cores and 16 GiB**, with no subsystem removals or external model calls. After 30 seconds of warmup, 90 seconds of input plus drain produced **92.440 real seconds / 5,574.206 game seconds**. Approximate rates divide by those 92.440 real seconds; they are averages across the world, not per actor, per step or peak rates.

A **sample share** tells us how often a function or one of its descendants was on the sampled main-thread stack. All shares use the same 83,387 samples; a nested function's percentage is still of the whole sample set, not of its parent's percentage. They approximate where main-thread time went, not percentages of the entire machine or removable waste. **Do not add overlapping shares.** Attribution uses sample counts because the trace contains one negative timestamp delta. Operation counts measure frequency, not cost per operation; database waits include waiting and cannot be added to CPU time.

The [measurement report](../verification/performance/bookkeeping/2026/2026-11-05-native-execution.md#lookup-counter-semantics) retains the precise counter definitions. Where a counter covers several callers, the notes say so rather than assigning its whole total to one table row. Model preparation, inference and maintenance need separate evidence; a limit in their tables is not a measured workload.

## Cycle 1: advance the world

Picture the player walking past a deer. The server first has to advance physical reality. It cannot let the player walk through a wall while it waits for someone to think. It also cannot calculate one large jump that skips a hit, completed action or required sensory boundary.

The game advances until the next relevant boundary, handles it, then continues. It can process several internal intervals in one private edit. Other commands see a coherent accepted world, not a half-applied interval.

The immutable world is not a full deep copy on each wake. It is also not one shared mutable object that everyone can write while other readers use it. The implementation shares unchanged branches and copies/finalizes changed ones. Numerous small changes can therefore still cause considerable bookkeeping.

Animals add work even without human-style memory or model calls. A due native foraging choice can query nearby entities, test sight, assess food/prey or a remembered target, and prepare movement. Its saved review time determines when to reconsider that routine; actual mode, target, route and outward changes can affect physics and nearby observers. A clock-only renewal is now classified separately. This is different from the NPC thought scheduler and its paid decisions.

### Sending the accepted world to the player

After accepted changes, the server prepares the controlled player's permitted view, including visible rows and journal information, then delivers updates. This reads personal reception again, independently of whether any NPC thinks.

The diagnostic made **1,304 player projections**, about **14/s**, producing **49,214 rows** — roughly **38 rows per view**. Projection appeared on **8.83% of samples** and its longest measured operation was **117 ms**. Those rows are repeated output preparation, not new world objects or memories. Coalescing and reusable fragments already help, but preparing a view still contributes to the shared current-field reads described below. Browser rendering was not part of this workload.

## Cycle 2: receive something, choose attention, and record changes

Suppose someone enters a clearing containing several people and animals. The observer first gets a broad picture of what is visible. The game then chooses a small number of subjects for detailed attention. Current reception and detailed history have separate jobs: the observer can know there are more bodies nearby than fit in detailed attention.

None of this cycle asks an AI model what a sword, deer or relationship means. The native priority rules use received cues, current work, explicit focus and acquired familiarity. A personal interest such as blacksmithing is interpreted when thinking; there is no general native semantic classifier matching every novel object to that interest during sensing.

### What movement history actually means

If an attended person is received at A, then B, then C, those changed received samples can survive in recent history. The system does not have to call them “approaching the anvil” or invent an episode boundary. A later model can interpret the sequence using the received surroundings.

It does **not** record a continuous physical path between the samples. A brief detour entirely between samples may be missed. Entering detailed attention later does not grant the unobserved earlier route. Outside detail, current broad knowledge can update without retaining every intermediate change. That is a deliberate distinction between noticing presence and tracking a sequence.

## Cycle 3: decide whether an NPC gets a thinking opportunity

Suppose the observer hears “Watch out,” finishes a chosen task, or receives a newly meaningful physical relation. The server records a reason to reconsider. It combines repeated reasons for the same NPC rather than making one model job per event.

There is no required LLM call every three real seconds. There is also no general per-NPC cooldown for autonomous thought. New qualifying reasons can become eligible on the next pass, subject to durable evidence, capacity and money.

**Measurement boundary:** in the zero-budget opening, the autonomous director returns at step 1 before preparing ordinary thoughts. The large lookup totals above are not evidence of repeated model-request building. The remaining steps, and the paid paths in cycles 4–8, describe what admitted cognition can do; that opening supplies no per-step CPU or live-provider timing for them.

Direct player speech uses a separate admission path. It checks control, the chosen recipient, available response capacity and actual heard addressed evidence. The utterance is a real world occurrence; other eligible listeners can hear it. The recipient's direct job owns that exact speech turn. Autonomous scheduling does not create a second reply to it.

## Cycle 4: build the information for one decision

This is where the server turns personally permitted data into a request a model can use. For example, “Should I answer this stranger while continuing my work?” needs the actual heard words, the character's goals and body, some current surroundings, recent work results and relevant memories.

The code has an ordinary preparation mode and a **native-only preparation mode**. Native-only here means “do not buy extra relevance, embedding or compaction calls while preparing”; it does not mean the final decision uses no model. Current decisions admitted under the configured escalation policy use this cheaper preparation mode. Reflection and some other routes can use the ordinary paid preparation path.

There is a significant distinction between **the complete received scene captured for permitted expansion** and **the small scene actually sent to a model**. The latter is bounded. Building the former can still visit every currently received body and candidate. This is one reason small prompt limits alone do not make preparation cheap.

**Separate measured conversation specimen:** on the earlier `5f01a6451` checkpoint, one AWS check took **712.943 ms of Node-process CPU and 1,532.954 ms elapsed** from chat submission to entry into the first response-generation handler. It included preparation, admission/database waits and two injected judging stages; it excluded external inference and the subsequent held-provider wait. CPU includes Node worker threads but not PostgreSQL. This is a combined route measurement, not a sum of timings for the seventeen rows above or a universal cost per utterance.

That request contained **63,581 bytes of context text, 2,743 bytes of instructions and 31,687 bytes of compact response schema**. Even “Hello” can require substantial character, surroundings, evidence and choice preparation. These are three payload sizes, not three measured processing costs. The earlier check is separate from the 92.440-second diagnostic and does not establish preparation throughput after later changes.

### The recall subcycle, literally

For a character with years of history, the decision does not load years of memory bodies into JavaScript. It asks the personal indexes for candidates. However, a database can still examine many indexed rows to count or rank them, particularly for exact vector search.

## Cycle 5: decide what to do, and make model calls

Jev is the service used to judge supplied possibilities. A generative model writes speech, thoughts or proposals. They are not the same stage. “Level 1” can therefore cost a model call while producing no generated prose.

Several routes exist. A direct conversation is not mechanically identical to an autonomous danger response or reflection.

The normal immediate decision has a one-real-second dispatch window. Work can remain useful later, up to about 31 seconds from intake under the current root deadline; the higher attempt has a 30-second useful window from eligibility, bounded by that original deadline. The supplied-response strategy declares both dependent judgments up front and can finish them inside its original useful lifetime after the one-second immediate marker. These are operating deadlines, not extra fictional time added to the character's action.

With escalation enabled and eligible, a route asking for deeper reasoning can hand off to the higher attempt instead of executing every ordinary generative stage above. Therefore **“two judgments and one generation” is one observed path, not the universal call count**. A native continuation can use no generation, a supplied-response case can use two judgments, and preparation/compaction/query branches can add calls only where enabled and needed.

## Cycle 7: background search indexing

An embedding is a numerical description used to find semantically similar text. It is not a memory itself and does not confer knowledge. Indexing should happen when retained text is created or meaningfully changed, rather than on every changed position.

For example, a retained account about a broken promise can be indexed once. A later question phrased differently can retrieve it without searching for the exact same words.

| Step                                | What happens                                                                                                              | Query / limit                                                                                                                                                                                          | Writes, calls and waits                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Wake from eligible source work   | A durable queue tracks missing current embeddings.                                                                        | Register eligible NPC memory owners and page pending actors, taking up to 64 into the current round.                                                                                                   | No separate queue of every movement sample or speech-only indexing service. Optional indexing is skipped when not configured/admitted. |
| 2. Read one actor's pending sources | Select current eligible source revisions, then materialize their permitted text.                                          | One bounded batch per actor per round. Batch packing keeps at most 32 source texts, with adapter capacity 33 including an optional query; at most 8,000 bytes per text and 64,000 encoded batch bytes. | Oversized optional sources remain available through structured retrieval; they are not silently marked indexed.                        |
| 3. Admit the batch                  | Check current sources, actor control, shared execution capacity and remaining money after reserving interactive headroom. | Same shared background execution pool as other paid background work.                                                                                                                                   | Persist the attempt and spending reservation before dispatch. A denied actor does not block later actors' allowances.                  |
| 4. Embed outside the world lane     | Send all texts in one embedding request.                                                                                  | No automatic paid retry after a failed/uncertain request.                                                                                                                                              | Await the provider without holding native advancement.                                                                                 |
| 5. Publish only current vectors     | Recheck the exact selected revisions and privacy after the wait.                                                          | Reject obsolete results after correction, forgetting or restore.                                                                                                                                       | Write vectors in a fresh serialized publication turn. Record settlement and wake another bounded round if work remains.                |

Foreground optional selection has a separate small candidate/query-vector cache. It can reconcile that cache and embed missing candidates when a section is too large for direct judgment. Ordinary action-library retrieval is different again: above 300 actions, its path can process multiple missing-description batches before selecting 300. Those are distinct callers, not one globally shared free embedding cache.

**Measured activity:** the opening made no external embedding calls. The limits above describe potential work when indexing is admitted; they do not explain a measured share of that opening's CPU. Long-lived recall/indexing cost remains unmeasured by this specimen.

## Cycle 8: consolidate, reflect and learn during downtime

These activities change what remains useful in the character's mind. They do not run merely because a deer moved. They also do not guarantee that every short observation becomes a permanent summary before it expires.

### Scheduling maintenance

The scheduler looks for a safe opportunity and a concrete backlog. It does not keep a model alive while the character walks, works or waits for someone else.

## Cycle 9: retention, correction, saving and restoration

This cycle controls what remains available and what reaches disk. It is separate from deciding whether a memory is interesting.

Imagine someone walking around for ten years. Their current view should depend on what is around them now. Recent detailed history has a rolling limit. Only selected useful knowledge/accounts remain longer; expired detail does not automatically turn into an AI summary.

| Ordinary accepted change | Install coherent live state and collect its changed records.                                                                | Use semantic change information and the existing incremental encoder. Preserve ordered meaningful history appends rather than replacing their sequence with the last position.                                              |
| Scheduled save           | Capture the pending accepted prefix and hand it to the existing ordered writer.                                             | About one real second from the oldest pending acceptance, if no prior save is active.                                                                                                                                                                                                          | Bulk writes share a transaction; new live changes accumulate in another pending suffix. | Save completion          | Publish the saved revision and release compatible resident history.                                                         | Match the exact saved prefix; do not discard newer unsaved changes.                                                                                                                                                                                                                            | Wake decisions waiting for that prefix. Rebase the resident tail onto the saved state and schedule another save if needed.                                                                                                 |

## Two concrete sequences

### Walking past someone, then speaking

1. Your movement changes physical position and marks relevant sight inputs. This does not call an LLM.
2. At a due receiving opportunity, the observer tests actual visibility and updates their personally received position. Your unchanged appearance can reuse content; its checks/dates and identity permissions still need handling.
3. If you are in detailed attention, changed received samples enter recent chronology. If you are outside it, broad presence can update without saving the whole route. A glance cannot recover a route that was never personally recorded.
4. Quiet movement alone does not repeatedly purchase thought. Changed relation cues, meaningful outward events or a quiet discovery opportunity may create one eligible reconsideration.
5. You speak. Hearing is evaluated for that actual occurrence. The listener gets only the words and attribution supported by reception. Clear addressed speech can admit a direct reply job.
6. The server waits for necessary evidence durability, captures context, reads required speech and bounded recall, prepares choices and runs the admitted decision route. It does not rescan years of raw memories into the prompt.
7. You can keep moving while the model runs. When the answer arrives, the server checks the captured evidence and current action prerequisites before applying it. Spoken output creates a new occurrence; a thought stays private.
8. Ordinary changed state/history joins saves. Longer-term retention is independent of whether the model replied.

### Daughter, cliff and fifteen pursuers

1. Broad reception can contain all sixteen bodies. Ten detailed slots are not a ten-body visibility limit.
2. Familiarity can favor the daughter without a hardcoded family-role handler. Current work, explicit focus, urgent cues and stability also compete. There is no guarantee she wins every possible competition.
3. Received static boundaries do not consume one of the ten body slots. Geometry selection uses self, selected/work/direct anchors and bounded rotating broad regions; it can still be incomplete.
4. Native relation work looks for supported closing relations in bounded candidate visits. It does not calculate every relation among every body and object, and it does not conclude “enemy intends to kill daughter.”
5. Before AI responds, actual movement, collision, bodily consequences and already-installed native responses continue. A new semantic interpretation is not guaranteed before someone reaches the edge.
6. An admitted request can contain broad grouped counts/bounds, selected bodies, received cliff evidence, sampled recent changes and bounded relations. At most two nearby body and two boundary relations per selected anchor are initially rendered; this is not all fifteen chasers individually explained.
7. The model may infer the danger from the supplied evidence or request bounded expansion where that route allows it. Missing coverage is explicit. The system cannot promise a correct inference about a relation whose evidence was not acquired or supplied.
8. If the answer proposes a warning, interception or other action, normal current admission checks it. The record remains what the observer received and actually did, not an invented successful rescue.

This supports a crowded scene without making extra enemies invisible. It does **not** establish exhaustive danger understanding. The installed bounded heuristics, actual context coverage and model quality are separate limits.

## Why the tiny opening still consumes so much CPU

The measurements beside [world advancement/player output](#cycle-1-advance-the-world), [reception/attention/history](#cycle-2-receive-something-choose-attention-and-record-changes) and [saving](#cycle-9-retention-correction-saving-and-restoration) describe repeated work over a small population. Their [common measurement window and overlapping sample shares](#how-to-read-the-measurements-beside-each-cycle) matter: they are not independent CPU slices or promised savings.

The most important repeated sequence is:

1. Ask when perception next needs work.
2. Resolve selected bodies, contact dates and acquired identity to answer it.
3. Ask again while refining the physical interval.
4. Resolve much of the same information again when receiving actually runs.
5. Reconstruct track membership and attention candidates around that receiving boundary.
6. Resolve description inputs even when their final meaning is unchanged.
7. Read related facts again to produce the player's view and prepare changed persistence data.

The multiplication is approximately **observers × received subjects × requested fields × repeated reader lifetimes**, plus real physical work and storage representations. Ten attention slots reduce detailed sampling/history. They do not remove all broad sensing, candidate preparation, deadline derivation, output or persistence work.

The long indivisible updates and waits shown beside those cycles also affect responsiveness. Their maxima are not correlated per command, so they cannot be combined into an exact explanation of the reply delay below.

### What the normal-speed result establishes

The separate unsampled six-minute case kept up with normal game time: 100.0885% at input stop, partly repaying initial owed time. It still used **97.945% of one main CPU core**, with **1,136.66 ms command-reply p95**. “p95” means 95% of replies were at or below that delay; it does not measure first visible movement. The CPU number is for the main JavaScript thread, not 98% of the whole four-CPU machine. Worker threads, PostgreSQL and the test driver have additional costs; unused cores do not automatically speed up synchronous work on the main thread.

The comparison version—called the matched control—ran on the same machine and setup, with required repairs but without the candidate optimization set. It also kept up: 99.9925%, 98.330% of a main core and 1,167.37 ms p95. Different realized animal activity and the small CPU/latency difference prevent a robust overall speedup claim. Both versions running at normal time does not show that the changed version can process more work or has meaningfully more spare CPU.

The test did not run full autonomous paid cognition for all NPCs. Other people did not perform movement/work in that zero-model workload. It does not qualify dozens or hundreds of fully active characters, long-lived memory, or live model-response quality.

The [separate conversation-preparation specimen](#cycle-4-build-the-information-for-one-decision) shows substantial work before generation, but cannot be added to this opening as a universal cost per utterance or NPC.

## Where the evidence stops

- Current native work and current decision preparation are traced separately here. The zero-model CPU profile cannot tell us how much a fully funded town would spend on model preparation, reflection or search.
- SQL statement counts do not establish database CPU or explain an exact fraction of command delay. The recorded waits, native holds and reply latency are not correlated enough to add into a reliable per-request breakdown.
- The latest deadline/attention preparation redesign is **proposed**, not installed at the inspected revision. It targets repeated deadline reads, full candidate/track rebuilding and descriptive-field resolution before cache hits. Its algorithmic intent is not a measured gain.
- The broader situation-aware context redesign is also a separate pending design. This walkthrough describes the existing multiple preparation passes and current limits, not its intended unified replacement.
- Reflection's current workspace has bounded file access and supplied context. General selective memory-retrieval tools discussed in broader designs are not silently assumed to exist on that harness.
- Older prose that describes automatic whole-conversation-group coverage or nearest-16 broad entity preparation does not match the inspected bounded speech-suffix and detailed-subject path. The mechanical descriptions above come from the active callers.
- A useful brief account can survive when a legitimate recording/remembering/consolidation path admits it. It is not guaranteed that all attended history becomes a summary before expiry. Trivial sequences can disappear completely.
