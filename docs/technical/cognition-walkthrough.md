# How cognition runs, from movement to memory

This walkthrough explains what the server does when someone moves, observes, pays attention, thinks and remembers. It describes the code inspected on **November 5, 2026**, at `bec86d8af288e9c7f7a00e376c479403620063b1`. The measurements describe runtime `72eea53fd43f82b8f6a915c0e90383b6557005cb`, from the [completed November 5 investigation](../verification/performance/bookkeeping/2026/2026-11-05-native-execution.md). They do not measure subsequent runtime changes. No new game run or model call was made for this walkthrough.

The numerical defaults belong to the bundled world or server configuration. Another authored world can supply different rules.

## Start here: how the pieces fit together

The server repeatedly moves the world forward. During that work, it updates what characters can perceive. Some observations create reasons for an NPC to think. Preparing a decision, waiting for a model and applying its answer are separate activities. Saving, player updates and memory maintenance have their own schedules.

**The nine cycles below are responsibilities, not nine phases that run in order on every game step.** Cycle 2 runs within world updates and also handles observations caused by individual events such as speech. Cycles 3–6 run when a decision is warranted and admitted. Cycles 7–8 do background memory work. Cycle 9 saves and manages records produced throughout the system.

| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| [1. Move the world forward](#cycle-1-advance-the-world)                                                           | Move bodies, advance work and bodily conditions, handle collisions, choose when the next update is needed, and accept completed changes. | Calls cycle 2 when observations are due. Accepted changes can be shown to players and queued for saving. |
| [2. Step references include their cycle: **1.4** means cycle 1, step 4. Subtables use a letter, such as **4R.2** for the second recall step. Measurements use these same references.

**Native** means ordinary game code acting under installed rules, without an AI model call. Moving a deer and choosing its routine foraging behavior can both be native work. The measured opening made zero external model calls, yet still used almost an entire main CPU core.

**Async** means a job can wait while other work proceeds. It does not automatically put its JavaScript calculations on another core. Database/provider waits release the main JavaScript thread; synchronous scans, copies, sorting and encoding still occupy it. Some geometry calculations have a separate worker.

## The information these cycles operate on

An **observer** is the character whose senses and knowledge are being considered. A **subject** is a person, animal, item or other thing they observe. An **actor** is a participant that can act, such as a person or animal. A **candidate** is a subject, record or choice being compared before selection; it is not necessarily included in the final result. The following records have different purposes:

| Information                    | Example                                                                                     | Who uses it and how long it matters                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Physical world state           | A deer really is at position B and moving.                                                  | Cycle 1 simulates reality. An observer cannot read unseen reality directly into their thoughts.                                               |
| Current personal observations  | I last saw the deer at B; its appearance was checked earlier; I currently have sight of it. | Cycle 2 updates these facts. Player display and cycle 4 read them. Position, appearance, identity and other details can have different dates. |
| Detailed attention             | This deer is one of the subjects I am tracking closely.                                     | Cycle 2 chooses a small set for more detailed sampling/history. Selection is not itself a new observation.                                    |
| Recent observed changes        | I saw the deer at A, then B, then C; observation later stopped.                             | Cycle 2 records a bounded sequence; cycle 4 can read it. It is not the world's complete movement log.                                         |
| Retained personal accounts     | I heard a warning, completed work, or formed an interpretation.                             | Recallable experiences, memories and summaries can outlive recent detail under cycle 9's retention rules.                                     |
| Learned identity and knowledge | I recognize this individual, know their name, or know a place.                              | Useful knowledge can outlive the observed route that supported it. It does not grant current sight.                                           |
| Accepted self-understanding    | Personality, identity, beliefs and relationships in the character's mind documents.         | Used in decisions and revised through cycle 8's controlled reflection. It is not an ever-growing transcript.                                  |
| Operational records            | A request is pending, money is reserved, or an answer was already applied.                  | Prevent duplicate spending/effects. These are not experiences remembered by the character.                                                    |

An **evidence source** is a particular personal observation/account used to support a fact or interpretation. Its **revision** identifies which contents were used. A **source binding** is the server's lookup from a short label in a model request to that exact permitted source or offered choice. A **proof** is the fuller supporting information establishing what was received, when and under which permission; many ordinary reads do not need to expand all of it.

Shared storage can hold identical received content once. Each observer still has their own access, timing and identity association. Sharing the bytes for “red coat” does not let another observer know who wore it.

## Timing, limits and accepting changes

The normal bundled clock advances **60 game seconds per real second** if the server keeps up.

| Setting                             | Default                                                                    | Where it applies                                                                                                                              |
| ----------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Server wake opportunity             | Every 50 real milliseconds                                                 | Cycle 1 may process owed time. This is not one complete simulation step or model call; an occupied update is not started again concurrently.  |
| Broad sight opportunity             | Every 60 game seconds, about 1 real second                                 | Cycle 2 handles pending relevant physical changes. An unchanged scene need not get a fresh full sight pass just because the interval elapsed. |
| Detailed sight opportunity          | Every 30 game seconds, about 0.5 real seconds                              | More frequent sampling of selected subjects. Recognition and other finite sensory work have their own due times.                              |
| Nearby geometry and relation checks | Every 20 game seconds, about one-third real second                         | Cycle 2 checks received bodies and nearby surfaces/boundaries. This does not automatically require another broad sight pass.                  |
| Broad sight radius                  | 28 metres                                                                  | Spatial eligibility before visibility tests; not a cap on visible subjects.                                                                   |
| Detailed attention capacity         | Normally 10 subjects                                                       | Focus 50 gives 10. The world uses `round(5 + Focus / 10)`, giving 5–15 for Focus 0–100; an explicit actor capacity can override it.           |
| Attention stability                 | 120 game seconds, about 2 real seconds                                     | Protects an ordinary selected subject from small priority changes. Urgency can interrupt; this does not promise continued visibility.         |
| Recent detailed history             | At most 6 game hours, 8 MiB and 131,072 charged changes per actor          | Cycle 9 enforces whichever limit binds. Six game hours are about 6 real minutes, but not every record is guaranteed that lifetime.            |
| Ordinary save target                | About 1 real second                                                        | Cycle 9 can combine several accepted world updates into one database transaction.                                                             |
| Unsaved-progress ceiling            | 5 real seconds or 64 MiB                                                   | Holds further ordinary progress if the pending work reaches the limit. A small margin remains for emergency pause.                            |
| Immediate decision jobs             | At most 2 per world, at most 1 ordinary                                    | An urgent job may coexist with an ordinary one. An actor cannot have overlapping decisions.                                                   |
| Provider execution capacity         | 1 primary execution and up to 100 background operations per server process | Admission ceilings, not evidence that 100 active characters are performant. Money and per-world limits still apply.                           |

Only one writer may change a world at a time. This exclusive turn is called the **world-update lane** in code. A writer can calculate several internal steps privately, then **accept/publish** one complete result for other work to read. Saving that result to disk happens separately. Unchanged data can be shared between accepted states; changed data must be finished so later writes cannot alter an earlier state.

A **captured input point** fixes the accepted time/order and sources a job will use. Code calls an ordered point a **cut** or **prefix**. Waiting for it to be saved does not mean waiting for the world to stop moving. A **progress marker**, called a cursor, records what a job already processed. A **world generation** identifies the currently loaded world, preventing a job started before restoration from modifying the restored one. **Cold history** means history stored in the database rather than already loaded in memory.

When a table says **read**, it specifies whether this is an in-memory lookup or a database query. Even an in-memory lookup may traverse several structures and allocate temporary objects. A **visit** means examining one entry during a bounded search; it need not produce a returned fact. A **row** is an item in the particular query/output being counted, not necessarily a unique world object. A cap on returned rows or prompt bytes does not necessarily cap the work done before selecting them.

### How to read the measurements beside each cycle

Unless a note names a separate specimen, counts and CPU sample shares come from one completed diagnostic: **7 people, 20 animals, 74 objects**, one walking controlled player, ordinary speech, actual wildlife and player event-stream output. It used the standard AWS **m7i.xlarge, four logical CPUs/two physical cores and 16 GiB**, with no subsystem removals or external model calls. After 30 seconds of warmup, 90 seconds of input plus drain covered **92.440 real seconds / 5,574.206 game seconds**. Rates divide by 92.440 real seconds and are world-wide averages, not rates per character or peak rates.

A **CPU sample share** is how often the profiler caught the main thread inside an operation or a function it called. All shares use the same 83,387 samples. A nested operation's percentage is still of the whole sample set. Thus the 24.26% spent under observation updating is included within the 63.16% under world advancement; it is not 24.26% of 63.16%. **Do not add overlapping shares.** These approximate main-thread time, not percentages of the whole machine or removable waste. Counts are used rather than timestamp-weighted durations because the trace contains one negative timestamp delta.

## Cycle 1: advance the world

**Starts:** when elapsed real time creates owed game time. **Produces:** a complete accepted world state, new events/observations, and changes waiting to be saved. **Calls:** cycle 2 when sensory work is due; it does not wait for an NPC's model response.

Picture the player walking past a deer. The server must move bodies and respect walls, hits, completed work and observation times. It advances to the next point requiring attention, handles that point, then continues. Several such intervals can be processed before accepting one result.

| Step                                                | What the computer does                                                                                                                 | Work, limits and waiting                                                                                                                                                                                                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1.1 Account for elapsed time**                    | Convert real time since the previous wake into owed game time, using pause/speed and the 60:1 normal ratio.                            | Update a small balance. Ordinary busy processing leaves time owed; detected host suspension is handled separately. No memory or model read.                                                                                                                                      |
| **1.2 Obtain the exclusive update turn**            | Check initialization, pause, participation, pending-save age/bytes and required route preparation.                                     | Wait if another writer owns the world. An unfinished required route can postpone movement calculations; owed time remains.                                                                                                                                                       |
| **1.3 Choose the next physical stopping point**     | Read active movement, work, bodily changes, collision/navigation and rule deadlines to determine how far the world can safely advance. | Prepare/reuse calculations predicting the next relevant boundary; these are the report's “physical forecasts.” Changed dependencies can require rebuilding. One invocation offers at most one game day and 4,096 internal intervals; those are guardrails, not usual step sizes. |
| **1.4 Include observation stopping points**         | Also stop for due sight, recognition, nearby geometry, attention or expiry of observed-motion information.                             | In this revision, deriving some deadlines repeatedly reads selected subjects' body/contact facts. Interval refinement and execution can request the same information again, creating temporary sets and views.                                                                   |
| **1.5 Advance physical state**                      | Move bodies; apply bodily rates, work completion, collisions, hits and automatic responses at the proper time.                         | Use installed world rules and saved randomness; write actual changed state/events. An animal controller can choose routine behavior without a model.                                                                                                                             |
| **1.6 Update due observations**                     | Run the applicable parts of [cycle 2](#cycle-2-receive-something-choose-attention-and-record-changes) for affected eligible observers. | Read spatial candidates, visibility and personal facts; record reception at its actual game time. This completes before advancing past that required observation point.                                                                                                          |
| **1.7 Give other work a chance to run**             | At safe boundaries, let sockets and other I/O proceed.                                                                                 | Aim to yield after about 8 ms of host time. Request an accepted result around 32 ms or sooner if an operation is waiting. Yielding during a private edit does not release the exclusive update turn; waiting commands need a complete accepted boundary.                         |
| **1.8 Accept the completed update**                 | Finish changed structures and make the result the live world state.                                                                    | Share unchanged structures; finish changed ones so the accepted state cannot be altered accidentally. Prepare changed records for the pending save and notify consumers. This uses CPU and allocates objects even before disk writes.                                            |
| **1.9 Continue owed time or offer background work** | Continue simulation work and give the separate NPC opportunity scheduler a chance to inspect pending reasons.                          | The host permits only one concurrent thought-scheduler pass. The pass starts asynchronously after the update; physical time does not await a model. Starting a pass is not a model call for every actor.                                                                         |

Animals add work in **1.3–1.5** even without human-style memory or models. A due foraging choice can search nearby entities, test sight, assess food/prey or a remembered target, and prepare movement. Its saved reconsideration time only determines when to review the routine again. Changing that time alone does not invalidate the whole physical forecast; actual mode, target, route or outward changes can do so and can affect observers.

### Sending the accepted world to the player

**Starts:** after relevant accepted changes. **Reads:** the controlled player's permitted observations and related display information. **Produces:** visible rows and journal information sent to that player. The report calls this **player projection**; this section calls it **player view preparation**. It also prepares permitted inventory/known methods, the controlled character's state and display/control information; visible rows are one measured part of that output.

This is separate from NPC thinking. Preparing a player view can reread personal facts even if no NPC decision is running. It does not grant raw world knowledge to the player.

The diagnostic prepared **1,304 player views**, about **14/s**, with **49,214 output rows**, roughly **38 rows per view**. This work appeared on **8.83% of CPU samples**; its longest measured operation was **117 ms**. The rows describe repeated display preparation, not new objects or memories. Updates are already combined and compatible fragments reused, but remaining reads contribute to the shared observation-reading counts below. Browser rendering was not measured.

## Cycle 2: receive something, choose attention, and record changes

**Starts:** from step 1.6 when observations are due, or from a specific occurrence such as speech/contact. **Produces:** updated personal facts, selected detailed attention, recent observed changes and possible reasons to think.

Someone entering a clearing can see more people and animals than fit in detailed attention. Broad observation establishes what is present. Detailed attention chooses a smaller set for more frequent detail and history recording. Neither operation calls a model to interpret arbitrary interests: familiarity, current work, explicit focus and received cues supply ordinary code-based priorities. An interest such as blacksmithing is interpreted during thinking; sensing has no general semantic classifier matching every novel object to it.

The spatial cues in **2.12** include bodies closing on one another and approaching a received drop. Bundled thresholds include entering 4 m/clearing beyond 6 m for bodies, and entering 20 m/clearing beyond 25 m for a drop of at least 1 m. A supported distance decrease must be at least 0.25 m. These are generic authored heuristics. They can offer a reason to think, but do not infer hostile intent or guarantee danger understanding. There is no special daughter-and-pursuers handler.

### Reading observations is work too

To use a personal fact, a caller must find the right subject, received detail, dates and permission. A **current-read scope** is a short-lived cache used during one synchronous group of reads. It reuses a result within that group. Another caller or later scope may do the lookup again, even when the observed value is unchanged. A **field selection** chooses one detail using its kind, sensory channel and the conditions under which it was received; it can return a value, absence or ambiguity. A **track** in the source code means the selected subject/channel whose observed changes are followed over time; it is not the subject's entire objective path.

This reading supports steps **1.4, 2.2, 2.5–2.9**, player views and other consumers. Consequently, the following totals cannot honestly be assigned to one of those steps.

The costly multiplication is repeated access to a small scene, not millions of different remembered objects. Obstruction testing, unchanged freshness writes, recognition and forgetting lack separate timings in this evidence; their exact CPU shares remain unknown.

### What movement history actually means

If an attended person is observed at A, then B, then C, those changed samples can survive in recent history. The game need not label them “approaching the anvil” or guess an episode boundary. A later model can interpret the sequence using received surroundings.

This is not a continuous path between samples. A brief detour between samples can be missed. Starting detailed attention later does not grant an unobserved earlier route. Outside detailed attention, current broad knowledge can update without retaining every intermediate change.

## Cycle 3: decide whether an NPC gets a thinking opportunity

**Starts:** from a new reason such as heard speech, completed work, a meaningful bodily change or a supported spatial cue. **Produces:** at most one admitted decision job per actor, or a reason kept pending. **Next:** cycle 4 prepares the admitted job's information.

Repeated reasons for the same NPC are combined. There is no required model call every three real seconds and no general per-NPC autonomous-thought cooldown. New qualifying reasons can be eligible on the next pass, subject to saved evidence, capacity and money.

**Measurement boundary:** the zero-budget opening returns at **3.1** before preparing ordinary thoughts. Its large reading counts do not measure repeated model-context building. The paid paths in cycles 4–8 require separate evidence; their limits are not measured workload counts.

## Cycle 4: build the information for one decision

**Starts:** after a decision is admitted, or when another permitted job such as reflection needs context. **Reads:** only this character's permitted self-information, observations, experiences and choices. **Produces:** a bounded model request plus private server-side records of exactly what each offered label means.

For “Should I answer this stranger while continuing my work?”, the server needs the heard words, current work/body, relevant surroundings and memories. It prepares this information before the model reasons about it.

There are two preparation modes. **Native-only preparation** uses game code and existing cached results; it buys no extra relevance judgments, search embeddings or conversation summaries. The eventual decision can still use a model. The configured higher-model policy uses this cheaper preparation. **Ordinary preparation** may buy those additional services when eligible and funded; reflection and some other routes can use it. Jev is the service for judging supplied possibilities, introduced in more detail in cycle 5. An **embedding** is a numerical representation of text used for similarity search; creating one can require a model call.

## Cycle 5: decide what to do, and make model calls

**Starts:** with an admitted decision and permitted inputs from cycle 4. **Produces:** a selected offered choice, generated response/proposal, deferral or failure. **Next:** cycle 6 checks and applies results. Physical simulation keeps running while remote calls wait.

**Jev** judges supplied possibilities. A **generative model** writes speech, thoughts or proposals. They are different stages: even a “Level 1” decision can buy a judgment without generating prose. The branches below are alternatives and conditional continuations, not a list run in full for every thought.

### Automatic behavior and the supplied-choice route

Automatic behavior uses physical state, installed rules and actually received evidence with **zero paid calls**. An ongoing valid plan can execute its next game action without asking a model again.

For an eligible installed threat/response situation, the supplied-choice route works as follows:

| **5S.2 Judge purposes and interpretations** | Ask which personal purposes matter and which offered interpretations are supported, sharing one actor's permitted context. | One batched Jev call. | **5S.3 Judge concrete choices**             | Rate supplied choices using the accepted interpretations/relevance from 5S.2.                                              | One dependent Jev call, after the first, sharing the original deadline. Choose a sufficiently rated action/continue option or defer. No automatic higher-model fallback or generated speech merely to complete this route. |

The immediate decision has a **one-real-second dispatch window**. Its overall useful lifetime can extend to about **31 seconds from intake**. The higher attempt has a **30-second window from eligibility**, still bounded by that original deadline. The supplied-choice route declares both judgments in advance and can finish them in its original lifetime after the one-second marker. These are processing deadlines, not extra fictional action time.

An eligible higher-model handoff can replace ordinary deeper generation rather than run after every stage above. Therefore “two judgments and one generation” describes one observed route, not every decision. Automatic continuation may use no generation; supplied choices may use two judgments; preparation, summarization or scene expansion add calls only when enabled and needed. The higher-model policy is a specific permitted handoff, not a general retry-until-success loop.

Do not automatically repurchase a failed/uncertain call.                                                                                                                                                                               |
| **7.5 Accept current results**              | Recheck the exact revisions/privacy after the wait; reject obsolete results after correction, forgetting or restore. | Write accepted vectors in a fresh exclusive update turn, settle accounting, and offer another bounded round if work remains.                                                                                                                                             |

Decision preparation also has a small query/candidate-vector cache and can embed missing optional candidates when a section is too large for direct judgment. Action-library retrieval has another path: above 300 actions it can process multiple missing-description batches before choosing 300. These callers are distinct; they do not share one universal free embedding cache.

**Measured activity:** the opening made no external embedding calls. These bounds describe possible admitted work, not a measured explanation for that opening's CPU. Long-lived search/indexing cost remains unmeasured by this specimen.

## Cycle 8: consolidate, reflect and learn during downtime

**Starts:** at a safe eligible opportunity with actual pending memory/learning work. **Produces:** summaries, revised self-understanding or tentative learned methods. It does not run simply because a deer moves, and it does not guarantee every recent observation becomes a permanent summary.

The four subtables cover task scheduling, summarization, reflection and learning. Scheduling selects eligible work; it does not run all three activities every time. **8M**, **8C**, **8R** and **8L** identify those separate sequences.

**Measured activity:** the zero-budget opening does not measure paid summarization, reflection or learning. Batch sizes below are limits, not observed counts. Memory expiry/storage cleanup still happen separately in cycle 9.

## Cycle 9: retention, correction, saving and restoration

**Starts:** whenever live changes need saving, memory becomes ineligible, a correction/forgetting occurs, or a world is restored. **Produces:** durable state, bounded retained history and current permissions. These are different operations, not one sequence performed on every update.

A ten-year-old character should not need to load ten years of observations to see what is nearby. Current facts, bounded recent history and longer-lived knowledge/accounts serve different purposes. Expired recent detail does not automatically become an AI summary.

### Accept changes now and save them together

| Step/event                           | What the computer does                                                                                                                         | Limits and consequences                                                                                                                                                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9.1 Collect accepted changes**     | After an accepted world update, prepare only the changed records using the incremental encoder, which converts them to storage representation. | Reuse unchanged encoded content; separate changing timestamps where supported. Combine repeated current-state edits to their latest value, but preserve ordered meaningful history instead of replacing an observed sequence with its endpoint.                                 |
| **9.2 Start a scheduled save**       | Capture the pending accepted point and send it to the existing ordered writer.                                                                 | Target about one real second from the oldest pending acceptance if no save is active. Bulk writes share a transaction; newer live edits accumulate separately. Encoding uses CPU. Database work is awaited without holding the exclusive world-update turn for the whole write. |
| **9.3 Finish that save**             | Record the saved revision and release compatible in-memory history now safely stored.                                                          | Match exactly what was saved, retaining newer unsaved changes. Wake decisions waiting on that point; keep the unsaved suffix aligned with the saved state and schedule another save if needed.                                                                                  |
| **9.4 Handle save pressure/failure** | Hold further ordinary progress when pending work reaches its age/byte ceiling.                                                                 | 5 real seconds/64 MiB. Accepted work remains in RAM; a crash restores the last complete save. Money/access changes and explicitly protected operations retain stronger durability safeguards.                                                                                   |

## Two concrete sequences

### Walking past someone, then speaking

1. **Move: 1.3–1.5, then 2.1.** Your position changes and relevant sight work is marked. No model call occurs.
2. **Observe: 2.2–2.6.** At a due opportunity, the observer checks visibility and updates their received position. Unchanged appearance may reuse content while checking dates/identity permissions still takes work.
3. **Record if attended: 2.8–2.11.** Selected subjects' changed samples enter recent history. Outside detail, broad presence can update without the full route. A glance cannot recover unrecorded history.
4. **Consider thinking: cycle 3.** Quiet movement alone does not repeatedly buy thought. A meaningful relation/outward event or quiet-discovery opportunity may create a reason.
5. **Hear speech: 2.4 and direct-speech admission.** Hearing is evaluated at the utterance. The recipient receives only supported words/attribution; clear addressed speech can admit a reply job.
6. **Prepare and decide: cycles 4–5.** Wait for required evidence to be saved; capture context, required speech, bounded recall and choices; execute the admitted decision route. Years of raw history are not copied into the prompt.
7. **Respond: cycle 6.** You keep moving while the model waits. The server checks captured evidence and current action prerequisites before applying an answer. Speech becomes a new occurrence; a thought remains private.
8. **Save/retain: cycle 9.** Changes enter ordinary saves. Longer-term memory retention does not depend on whether the model replied.

### Daughter, cliff and fifteen pursuers

1. **Broad observation: 2.3–2.5.** All sixteen bodies can be received. Ten detailed-attention places are not a visibility limit.
2. **Attention selection: 2.7–2.8.** Familiarity can favor the daughter without a family-role handler. Work, explicit focus, urgency and stability also compete; she is not guaranteed to win every competition.
3. **Receive the cliff: 2.12.** Static boundaries use separate geometry coverage, not one of the ten body places. Selection uses self/selected/work/direct-interaction reference points and rotating broad regions; coverage can be incomplete.
4. **Notice changes in relationships: 2.12.** Bounded candidate checks can detect closing bodies or an approaching drop. They do not calculate every pair or conclude an enemy's intention.
5. **Keep the world moving: cycle 1.** Movement, collision, bodily effects and installed automatic responses continue before a model answers. Semantic understanding is not guaranteed before someone reaches the edge.
6. **Supply a decision: 4.5–4.8.** Input can contain broad grouped counts/bounds, selected bodies, received cliff evidence, recent changed samples and bounded relations. Initial output has at most two nearby bodies/two boundaries per reference point, not an individual explanation of all fifteen chasers.
7. **Interpret or ask for more: cycle 5.** The model can infer danger or request allowed expansion of captured evidence. Missing coverage remains explicit; the system cannot guarantee an inference whose evidence was not received/supplied.
8. **Act if still possible: cycle 6.** A warning/interception proposal must pass current action checks. History records what was received and actually done, not an invented successful rescue.

Extra enemies are not made invisible. Exhaustive danger understanding remains unproven: the heuristic rules, actual information supplied and model quality are separate limits.

## Why the tiny opening still consumes so much CPU

The [world-update measurements](#measured-work-in-world-updates), [observation reads](#reading-observations-is-work-too), [attention/history measurements](#measured-work-in-observation-and-attention), [player-view measurements](#sending-the-accepted-world-to-the-player) and [storage measurements](#measured-work-in-saving-and-record-lifetime) describe different views of repeated work on the same small population. They are not independent CPU slices or promised savings.

The repeated sequence is concrete:

1. **1.4 asks when observation is due**, resolving selected bodies/contact dates and acquired identity.
2. **1.3–1.4 refine the interval**, potentially asking for some of that information again.
3. **2.2–2.6 actually observe/update personal facts**, reading related state again.
4. **2.7–2.10 reconstruct selected subjects and attention choices**, including descriptive inputs read before discovering the description is reusable.
5. **Player view preparation reads facts again** to construct permitted display information.
6. **9.1 prepares changed records for saving.** Combining database writes later does not undo preparation already performed.

The growth is roughly **observers × received subjects × requested details × repeated reader lifetimes**, plus real physics and storage work. The ten attention places limit detailed sampling/history; they do not cap broad sensing, comparison candidates, scheduling reads, player output or all save preparation.

Long uninterrupted calculations and waits also affect responsiveness. Their recorded maxima are not correlated by command, so they cannot be combined into an exact explanation of reply delay.

### What the normal-speed result establishes

A **separate unsampled six-minute case** kept up with normal time: **100.0885%** at input stop, partly repaying initial owed time. It used **97.945% of one main CPU core**, with **1,136.66 ms command-reply p95**. This means 95% of replies were at or below that delay; it does not measure first visible movement. The CPU figure is not 98% of the four-CPU machine. Worker threads, PostgreSQL and the input driver have additional costs; unused cores do not automatically accelerate main-thread calculations.

Its matched control—the same setup with required repairs but without the candidate optimization set—also kept up: **99.9925%**, **98.330% of a main core**, **1,167.37 ms reply p95**. Different realized animal activity and small CPU/latency differences prevent a robust overall speedup claim. Running at normal time does not establish substantial spare capacity.

The workload ran no full autonomous paid cognition. Other people performed no movement/work in that zero-model opening. It does not qualify dozens/hundreds of fully active characters, long-lived memory or live model quality. The [separate conversation measurement](#prepare-choices-recall-and-final-text) cannot be added as a universal per-NPC or per-utterance cost.

## Where the evidence stops

- The measured opening explains ordinary simulation/observation/display costs. It cannot quantify a fully funded town's model preparation, inference, reflection or search.
- SQL spans do not measure database CPU. Storage waits, exclusive-update holds and reply delays cannot be added without per-command correlation.
- At the inspected revision, the deadline/attention redesign is **proposed**, not installed. It targets repeated due-time reads, selected-subject/candidate rebuilding and inputs read before description cache hits. Its intent is not a measured gain.
- The broader situation-aware context redesign is also pending at that revision. This document explains the existing multiple preparation passes, not the proposed replacement.
- Reflection uses supplied context and bounded mind-file access. General on-demand historical retrieval is not installed on that reflection path.
- Older descriptions of whole-conversation-group coverage or nearest-16 broad entity preparation do not describe the inspected bounded speech-suffix and detailed-subject paths.
- A useful account can survive through legitimate recording, remembering or summarization. Not all attended history is summarized before expiry; trivial sequences can disappear.
