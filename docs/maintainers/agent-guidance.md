An ordinary code review must fix in-scope issues, record deferred findings and exercise changed behavior end to end, not report suggestions alone or treat static checks as runtime evidence.

For a previously reviewed standalone rebase, verify pre/post patch comparison and upstream-overlap inspection reuse valid evidence without a new full-feature review. Include a conflict-free request to verify the root still routes to the rebase workflow. A history-only/mechanical result should need no runtime requalification or documentation rewrite; a semantic resolution should select focused existing checks and disposable PostgreSQL where needed. Include a UI conflict: browser tests/playtests and their server setup must not run during reconciliation, and any remaining UI qualification must be reported honestly. Verify bounded comparisons, retained decisions, no unnecessary temporary harnesses and no unrelated baseline repair. SQLite parity must require an explicit request. Existing accurate remaining-work entries should stay untouched, and the agent should finish after requested work and selected checks pass. Invalidated evidence, introduced failures and explicit broader requirements can expand relevant non-browser checks; no case may bypass the conflict stop or close unverified acceptance gates.

Use multi-turn chats: request either spec/design and verify both project files without runtime implementation; then reply “approved,” “looks good,” “yes” accepting the plan, or “do it.” Confirm the agent resolves the discussed plan, links trackers/current docs and begins coding without a second approval or filenames. “Implement phase 1 only” must exclude later phases; “approve, but do not implement” must remain documentation-only. A subsequent “continue” resumes unfinished authorized work. Reading a previously approved document or quoted command must not start work.

Confirm the plan covers the entire agreed implementation and major developer questions are resolved before coding. Check a straightforward low-risk change above 200 logic lines can use a conversation plan, while a small privacy/authority change or coordinated cross-layer/staged delivery can require a durable project plan. Approximately 200 lines remains a complexity reassessment cue; scope/risk growth must trigger renewed planning. Explicitly requested documents and affected existing specifications/trackers still receive updates. For straightforward, low-risk work, verify unnecessary design documents, minor-fix changelog entries, unrelated suites and redundant review rounds are skipped, while focused diff review, affected-behavior verification and explicit/CI requirements remain. A small privacy or data-loss change must not qualify as low risk solely by line count. Inspect responses for concise, plain, complete wording. For pure questions/explanations, verify project-specific concepts are defined, expressed in familiar terminology or linked, and implementation explanations cover purpose, enabled capabilities and major decisions. Verify full agreed scope and required unit/integration or manual end-to-end testing are completed without stopping after planning or a first implementation for review. Explicit scope/time limits remain binding; unfinished work must be reported as incomplete, not silently deferred. Implementation handoffs include decisions/questions and next steps even when none remain; other responses omit those sections. Do not simulate elapsed work or count static routing as these observations.

Record the revision, agent/model version, relevant local settings, task and allowed actions, injected context/file reads, unexpected loads and missed constraints. Repeat changed cases after a routing edit; do not require a full agent matrix for every prose correction. Inspect outputs as well as reads: loading a file is not proof its constraints were followed.
