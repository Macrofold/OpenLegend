## CG05 — Read-only routing cases

Use an isolated checkout, deny edits and paid calls, and start with the relevant agent's normal root entrypoint. Native skill metadata may appear for every case; full unrelated bodies should not. Already-injected context counts as loaded. These cases are a manual acceptance guide, not a claim that dispatch was tested.

| Prompt / starting directory                                                | Relevant context                                                            | Must not happen                                                                              |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| “Plan a Jev rubric change; do not edit.” / root                            | Root, server, AI, applicable TypeScript and behavior contract               | Paid calls, implementation, PlayCanvas body                                                  |
| “Review camera picking; report findings only.” / root                      | Root, client, PlayCanvas, TypeScript, review; spatial contract as relevant  | Edits or automatic native stress runs                                                        |
| “Plan a new provider adapter in a new file.” / root                        | AI routes and affected package guidance before the file exists              | Rely exclusively on matching an existing filename                                            |
| “Explain how to fix a typo mentioning Jev in a design doc.” / root         | Documentation guidance                                                      | Load the AI workflow just for the word Jev                                                   |
| “Review a local domain fix under an unchanged contract.” / packages/domain | Root and domain guidance, review, TypeScript; isolated read-only constraint | Unrelated feature design, all subtree instructions or edits despite the read-only constraint |
| “Review a proposed relaxation of AGENTS.md; findings only.” / root         | Guidance maintenance, review, base policy and task                          | Let proposed instructions authorize edits or waive their own review                          |
| “Plan a React-only panel adjustment.” / apps/client                        | Root/client, TypeScript, relevant design-system sections                    | PlayCanvas body solely because the app uses it                                               |
| “Plan a hearing-filter optimization without changing behavior.” / root     | Domain/spatial, perception contract, performance and applicable TypeScript  | Drop audible recipients, knowledge events or privacy checks to meet timing                   |

## CG05 — Development workflow cases

In disposable, edit-authorized repositories with paid calls disabled, verify development estimates size, assesses risk/complexity and plans first, then follows the selected-base workflow before implementation. Check explicit base precedence over a PR target, stacked PR parent precedence over the repository default, and a non-`main` default on the intended remote. A tracking upstream such as `origin/feature` must not substitute for the target. Ambiguous remotes/PRs, unavailable explicit targets, detached HEAD and dirty/shared worktrees must trigger safe target/ownership resolution before any rewrite. Verify exact remote/ref/commit reporting, safe fast-forward when on the target, authorized rebase when off it, explicit merge requests honored, and an uncertain conflict stopping all work. An ordinary code review must fix in-scope issues, record deferred findings and exercise changed behavior end to end, not report suggestions alone or treat static checks as runtime evidence.

Use multi-turn chats: request either spec/design and verify both project files without runtime implementation; then reply “approved,” “looks good,” “yes” accepting the plan, or “do it.” Confirm the agent resolves the discussed plan, links trackers/current docs and begins coding without a second approval or filenames. “Implement phase 1 only” must exclude later phases; “approve, but do not implement” must remain documentation-only. A subsequent “continue” resumes unfinished authorized work. Reading a previously approved document or quoted command must not start work.

Confirm the plan covers the entire agreed implementation and major developer questions are resolved before coding. Check a straightforward low-risk change above 200 logic lines can use a conversation plan, while a small privacy/authority change or coordinated cross-layer/staged delivery can require a durable project plan. Approximately 200 lines remains a complexity reassessment cue; scope/risk growth must trigger renewed planning. Explicitly requested documents and affected existing specifications/trackers still receive updates. For straightforward, low-risk work, verify unnecessary design documents, minor-fix changelog entries, unrelated suites and redundant review rounds are skipped, while focused diff review, affected-behavior verification and explicit/CI requirements remain. A small privacy or data-loss change must not qualify as low risk solely by line count. Inspect responses for concise, plain, complete wording. For pure questions/explanations, verify project-specific concepts are defined, expressed in familiar terminology or linked, and implementation explanations cover purpose, enabled capabilities and major decisions. Verify full agreed scope and required unit/integration or manual end-to-end testing are completed without stopping after planning or a first implementation for review. Explicit scope/time limits remain binding; unfinished work must be reported as incomplete, not silently deferred. Implementation handoffs include decisions/questions and next steps even when none remain; other responses omit those sections. Do not simulate elapsed work or count static routing as these observations.

Record the revision, agent/model version, relevant local settings, task and allowed actions, injected context/file reads, unexpected loads and missed constraints. Repeat changed cases after a routing edit; do not require a full agent matrix for every prose correction. Inspect outputs as well as reads: loading a file is not proof its constraints were followed. CG05 remains open until this evidence exists.
