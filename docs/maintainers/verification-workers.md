## Delivery order

- [ ] **VW01 — Atomic ownership and bounded lifecycle.** Implement the controller/table, fixed slots, cloud-allocation admission, fenced run/case claims, supervisor and independent deadlines/recovery through the [shared contracts](../projects/verification-workers-tech-design.md#runner-input-and-output). **Required pass:** concurrent claim has one winner; duplicate or changed-payload retries do not replay; stale run/case commands cannot affect successors; cleanup after expiry can stop a long-running child without lock deadlock; controller/laptop loss and stop/claim races recover or quarantine. Allocation/create/retire uncertainty cannot exceed the slot cap or reset spending. Exercise owned disposable fault scenarios, never active temporary workers.
- [ ] **VW02 — Reusable prepared machines.** Depends on VW01. Deliver pinned bootstrap, admitted one/two-slot allocation, required network/IAM connectivity, stop/start, fresh run state and pnpm store reuse. **Required pass:** warm reuse retains tools/package content without old game state; a lockfile change reuses unchanged downloads but builds the correct installation; native/toolchain changes invalidate affected preparation; source/package-link mismatch, foreign workload, failed cleanup and insufficient disk prevent measurement. Pruning holds an exclusive claim outside capture. Verify actual stop, retained EBS and budgeted retirement; no legacy environment adapter.
- [ ] **VW03 — One runner and complete evidence.** Depends on VW01–VW02. Implement the designed command/plan/result interfaces, source snapshots, ordered comparisons, provenance, complete timeline and artifact collection. **Required pass:** mixed dirty-source capture refuses; success, startup/transfer failure and lost client retain truthful outcomes; required artifacts cannot expire before acknowledgement; cleanup returns without waiting for idle stop, whose later receipt remains retrievable. **Required measurement:** fresh-machine and stopped/restarted cached-worker runs with the same standard opening, one controlled player, native actor activity, no paid AI, normal speed, five-second game warm-up and 300-second window. Both use fresh databases; distinguish machine-cache warmth from game warm-up. Report full setup/run/cleanup time, work, cache hits and cost; attribute poor overhead rather than claim speedup. Repeat only for concrete variance/failure questions.
- [ ] **VW04 — Rendered play and operational adoption.** Depends on VW03. Implement the [browser integration](../projects/verification-workers-tech-design.md#remote-browser-integration) in the existing driver/fixture: private loopback tunnel, run/case/source-bound ready metadata with actual selected settings, shared acknowledged start signaling and representative versus diagnostic rendering modes. **Required pass:** local and remote start paths work without duplicate Resume; stale markers cannot start another case; tunnel failure interrupts without replay; one visible representative-device journey demonstrates real input/rendered movement. **Required measurement:** frame pacing/stalls, responsiveness, backend progress and capture alignment/network limits; no software-rendering hardware claim. Publish runnable commands and measured setup overhead, remove temporary-script dependencies and close only demonstrated scope. GPU fleet/multi-device capacity remains excluded; installed-agent routing stays CG05.

No game-runtime changes, new automated test suite, paid model calls, GitHub CI, shared-host job mode or deployment of the game to production is part of these tasks. Authorizing implementation must include its actual bounded infrastructure/storage cost under the existing spending policy.
