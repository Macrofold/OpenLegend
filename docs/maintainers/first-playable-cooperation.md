# First-playable people and cooperation — implementation work

**Status: selected design complete; implementation and runtime/player acceptance open, 2026-10-17.** The [feature specification](../projects/first-playable-cooperation-feature-spec.md), [technical design](../projects/first-playable-cooperation-tech-design.md), [authored people](../worlds/base/first-playable-people.md) and [limits](../limits/first-playable-cooperation.md) define this scope. [FPV](first-playable-validation.md) coordinates the complete game; [CE](character-experience.md) retains ordinary-life and independent-character quality. This tracker owns only new cooperation/cast work and must not duplicate SPK/CTR/SH/AC's existing tasks.

Parent design coverage: DG02/DG06 and [ND10](needs-design.md#nd10--persistent-groups-shared-ownership-and-in-world-institutions). ND09 commerce, ND04 personality development and full institutions remain broader work, not hidden prerequisites. Design is settled for this first-playable slice; an unchecked task means delivery/evidence remains, not permission to script a successful interaction.

## Dependency order and handoff contract

CP01 and CP02 establish the authored data and exact consent. CP03 provides the shared independent-work binding before CP04–CP06 connect specific activities. CP07 can proceed after CP02 through existing combat/cancellation owners. CP08 integrates the user/agent surfaces as each slice becomes available. CP09 protects lifecycle/privacy/performance; CP10 qualifies complete independent behavior and player value after dependencies pass. Integrate per slice, not as one final dump.

Each implementation handoff identifies the exact owner edits, updates these checks and the project status tables, links actual evidence and states remaining limitations. Existing accurate CE/SPK/CTR/SH tasks remain open until their own evidence passes. No generated traces, private saves, provider keys or fabricated successful dialogue are committed as verification.

## CP01 — Preserve and author four distinct people

**Owners:** compiled base-world `people.yaml`, shared main initializer, current actor identity/knowledge/recognition owners. **Dependencies:** parent first-playable build-time compiler; survival method catalogue; accepted CTR Ada profile. **Design:** [world people](../worlds/base/first-playable-people.md#the-four-people).

- [x] Select four existing identities, exact additions, initial acquaintance boundaries, unchanged personal stock, no mandatory initial goals and no trait-derived mechanics.
- [ ] Move seed authorship to the compiled YAML source without duplicate writable TypeScript biographies; preserve prior useful identity text and selected CTR addition. Validate selected IDs/methods/traits before installation.
- [ ] Install actual ordinary recipe knowledge through its current owner, retaining authored origin/no invention credit and the rare field-sling discovery boundary.
- [ ] Preserve Mara/Tavin incident, exact differing beliefs and physical satchel/note evidence; install only the selected Ada/Mercenary acquaintance with observer-specific recognition.
- [ ] Verify each person's actual model-facing context, an uninformed player's view and a relocated/changed-possession counterfactual. No current camp, private stock or conditional next-action assertion may be encoded as permanent biography.

**Exit:** current new starts contain the four distinct, truthful seeds and their existing useful content; restored accepted people remain unchanged. A source-data pass does not close CE05/CP10.

## CP02 — Exact local proposals and shared offer admission

**Owners:** `outings.ts`/`outing-index.ts`, current handover offer admission, installed social policy, authenticated command transport and receipts. **Dependencies:** CP01's profile definitions; existing SPK/recognition and account/control boundaries. **Design:** [consent](../projects/first-playable-cooperation-tech-design.md#exact-consent-and-cancellation), [CPL02/CPL04](../limits/first-playable-cooperation.md#cpl02--pending-offers-and-finite-deadlines).

- [ ] Implement the finite typed guide/help/hunt terms, pending state, exact replies and receipt recovery; proposals require actual local reception and grant no work, custody or other actor's acceptance.
- [ ] Use one authored 7,200-game-second offer lifetime for the selected first-playable gift/barter/travel/help/compact families. Preserve deliberately different installed world profiles; remove duplicated numeric fallbacks in consumers.
- [ ] Enforce shared outgoing/incoming pending admission and one live pair/kind before allocation/evidence/provider work. Return neutral inbox-capacity failures; no queue/eviction.
- [ ] Implement revision-bound counterproposals, accepted-term replacement and expiry with truthful causes. Pending amendment expiry/refusal leaves previously accepted terms/work intact.
- [ ] Verify identical receipt replay, conflicting replay, changed terms/item/life, hidden references, local reception loss, expiry versus deliberate refusal, alternate world defaults and existing travel/trade regressions.

**Exit:** real human and NPC commands can offer/review/accept/decline exact current terms, and every refused attempt preserves costs/work/stock. Existing outgoing cap alone is not sufficient.

## CP03 — Independent chosen work and truthful endings

**Owners:** current goals/plans, activity execution, action occurrences, outings and participation. **Dependencies:** CP02 and the existing prospective-action/CTR busy-context work. **Design:** [finite episodes](../projects/first-playable-cooperation-tech-design.md#finite-episode-record-and-commands).

- [ ] Bind accepted cooperative purpose to each actor's independently selected work, with exactly owned goal/plan/activity references. Accepting starts no walk, attack, gathering or preparation.
- [ ] Offer continue/interrupt/replace/separate-work choices with their real consequences and ordinary current prerequisites; unrelated conversation changes cannot invalidate physical purpose.
- [ ] Close on exact conclusion/completion/deadline/withdrawal/unavailability causes. Cancel only still-owned unfinished work and unspent claims; preserve completed materials, recovery and released effects.
- [ ] Atomically detach any irreversible still-active phase from live episode ownership before deleting the terminal agreement; preserve its ordinary physical owner and historical attribution. Save/restore before it finishes must retain no dangling consent dependency or future agreed step.
- [ ] Permit exact own decline/leave during deliberate manual pause while preserving maintenance/storage/absence/control holds. Exercise ending after current work has already finished or stopped.
- [ ] Verify a participant changing priorities, finishing a partial phase, dying or departing, and a genuinely independent activity surviving cleanup. Record one personal experience per source, not a duplicate plan narrative.

**Exit:** a purpose can influence ordinary choices and end safely without compelling either actor or corrupting another owner's ongoing work.

## CP04 — Grounded guidance and practical preparation

**Owners:** selected guide/help families, known-place/knowledge, existing recipe manufacture and action-result owner. **Dependencies:** CP03, survival resources/known methods. **Design:** [help/guides](../projects/first-playable-cooperation-tech-design.md#help-guides-and-hunts).

- [ ] Offer only a personally known fixed place or supported known recipe/quantity. Mark remembered place/stock uncertainty and preserve attributed guidance rather than fabricate a witnessed discovery.
- [ ] Connect guiding to separately chosen native movement, real body routes and actual individual arrivals; separation grants no hidden companion/target coordinates.
- [ ] Count actual selected-purpose committed outputs in the declared unit for preparation completion; preserve multi-output side products and truthful partial results. Saying “done” cannot complete a task.
- [ ] Keep method advice in ordinary speech and exact method-record learning; a conversation is not implicit recipe installation.
- [ ] Qualify useful guide arrival and actual preparation, plus a lost guide, blocked route, unknown method, unavailable stock and changed definition. Compare the whole operation with walking/making alone.

**Exit:** someone can provide useful guidance or actually prepare a selected result, with valid stopping and failure. No new generalized teaching system or arbitrary prose executor is required.

## CP05 — Carrying and camp contribution through exact custody

**Owners:** handover, item placement, ordinary transport, camp phase/grant/assembly owner. **Dependencies:** CP03, existing gift/barter, camp construction SH delivery. **Design:** [help/guides](../projects/first-playable-cooperation-tech-design.md#help-guides-and-hunts), [camp phases](../projects/editable-shelters-tech-design.md#11-first-playable-camp-construction-and-defense).

- [ ] Carry terms bind one exact offered object and permitted destination; ordinary acceptance actually transfers possession before transport, and ordinary put/drop completes it.
- [ ] Show that this is actual custody transfer and voluntary transport, with no implied loan lien or remote retrieval right. Failed handover leaves the work unstarted/blocked, never an invisible carried object.
- [ ] Bind camp help to the reviewed phase and one complete grant for the exact inputs/outputs. Reuse all origin checks, real geometry, admission, serialization and interruption behavior.
- [ ] Qualify helpers working on different assemblies and refusal of conflicting edits on one assembly. No aid multiplier or automatic use of another's tools/materials.
- [ ] Verify disappeared/changed item, insufficient carrying/container capacity, blocked destination, revoked material grant, partial construction and save/reopen mid-task.

**Exit:** actual objects travel and actual construction changes under the existing owners; acceptance and friendship alone grant neither.

## CP06 — Useful independent hunting and actual sharing

**Owners:** cooperation purpose, ordinary perception/travel/combat, remains/harvesting, handover and action records. **Dependencies:** CP03, survival yield/weapon routes, CTR and danger/ranging behavior. **Design:** [hunt journey](../projects/first-playable-cooperation-feature-spec.md#hunting-and-sharing-something-real).

- [ ] Bind one quarry life observed when proposed, known meeting place, exact deadline and explicit no-guaranteed-yield terms. Permit acceptance after ordinary sight loss during reading/reply using separately remembered locations; current pursuit/strikes retain their own observation requirements. Do not spawn, weaken, lure by script or grant a hidden route for that quarry.
- [ ] Make each hunter's actual valid independent tactics available, including guarding, different approaches, waiting, withdrawing and walking to their own last observed point. Omitted alternatives cannot force cooperation success.
- [ ] Reuse real hit/recovery/flight/remains/harvest semantics. Do not award a shared kill or resource twice, create a new universal carcass title or equate matching species with the same quarry.
- [ ] Surface actual available yields for existing exact gift/trade after harvesting. No future-loot escrow, automatic fair-share algorithm or unseen inventory disclosure.
- [ ] Qualify native success and failure, lost sight, duplicate/contending harvest, a third independent actor, decline of a share and committed projectile after withdrawal. Natural willingness/usefulness remains CP10.

**Exit:** two independently controlled participants can make a useful actual contribution to a hunt and divide real available goods, without a scripted role or guaranteed result.

## CP07 — Revocable alliance, ceasefire and after-conflict evidence

**Owners:** focused `social-compacts.ts`, existing receipt/knowledge/event/attack cancellation and authority owners. **Dependencies:** CP02, CP03 cleanup, CTR current threats and ordinary permissions. **Design:** [compact contract](../projects/first-playable-cooperation-tech-design.md#mutual-alliances-and-finite-ceasefires).

- [ ] Add exact pair/revision/terms/assent and selected lifetime records for alliance and ceasefire. Do not replace these separate meanings with a friendship score, party membership or blanket grant.
- [ ] Ceasefire acceptance atomically cancels only each signer's still-cancellable unlaunched attacks on the other. Preserve released attacks/recovery/costs and show relevant known risk.
- [ ] New deliberate admissible harm ends that actor's ceasefire assent in the same transaction; inadmissible previews and already released contact do not falsely become new betrayal.
- [ ] Keep unilateral withdrawal authoritative but private until actual permitted communication/perception or a scoped failed continuation; stale remembered status cannot reveal remote death, work or location.
- [ ] Qualify counterproposal, refusal, manual-pause withdrawal, exact receipt replay, absence/death, later renewed consent and no inherited permission from friendship. No compelled apology/forgiveness/restraint or global ally hostility.

**Exit:** mutual intent and actual conduct can matter in later interpretation without replacing personal agency or granting authority.

## CP08 — Shared player, NPC and creator surfaces

**Owners:** existing server context/choice assembly, protocol, person actions, Character/Promises, chat and gift/trade UI. **Dependencies:** CP02–CP07 delivered incrementally; existing UI handbook/SPK/context ownership. **Design:** [shared disclosure](../projects/first-playable-cooperation-tech-design.md#shared-evidence-ai-and-player-disclosure).

- [ ] Use one terms/detail component with who/what/deadline/risk/actual material effects, readable known status, revise/decline/leave and links to permitted own outcomes.
- [ ] NPC choices contain exact consequences, current body/identity/goals, received terms and required experience. Explicitly preserve decline, no reply, continued separate work and unknown outcomes.
- [ ] Deliver actual acceptance once through the existing director's evidence/dependency handling so the accepting actor can independently choose its next action; no second player request, polling loop, combined new decision envelope or compulsory action.
- [ ] Keep present people separate from remembered people, private terms from public visible interaction and accepted agreement from completed effects. Recheck privacy/control/evidence fences after asynchronous reads.
- [ ] Preserve drafts/focus/selection on stale terms, refresh and reconnect; expose truthful no-offers/loading/unavailable/error/unknown-receipt states. No raw native IDs or coordinate entry in ordinary play.
- [ ] Exercise keyboard/focus, long names/terms, narrow layout, output withholding, permission loss and current-format reopening through actual controls. Required shared safety instructions remain installed without merging them into persona text.

**Exit:** each new native choice is discoverable and understandable through ordinary player and resident paths, not only a developer endpoint.

## CP09 — Current-format continuation, privacy and bounded work

**Owners:** canonical record tree, validation, storage, participant/pair/deadline indexes and exact admission. **Dependencies:** CP02–CP08. **Design:** [persistence/performance](../projects/first-playable-cooperation-tech-design.md#persistence-definitions-and-performance).

- [ ] Persist and validate current records, definitions, deadlines/lives and owned work bidirectionally; rebuild derived indexes and reject malformed phase/reference combinations before installation.
- [ ] Verify restore during partial help/hunt/ceasefire, accepted inactive cooperation awaiting reconnect, terminal evidence after live record removal, corrected/forgotten private evidence and revoked control/grants. No seeding, duplicate gifts or paid replay on restore.
- [ ] Measure cold and warm actual command/context/projection paths, six incoming offers concentrated on one actor, unrelated large inventory/history, independently increased live density and many accepted acquaintances. Report examined/hydrated records, latency, memory and model-call counts.
- [ ] Demonstrate no whole-world per-tick relationship scan, model poll or whole-history hydration. A required-work failure reports incomplete work; it cannot choose arbitrarily or silently omit terms.
- [ ] Exercise a materially different construct/charge-station profile and omitted cooperation family across availability, execution, UI wording and restoration.

**Exit:** lifecycle/privacy correctness and actual caller work are qualified for declared workloads. This does not establish unmeasured population capacity or enjoyment.

## CP10 — Whole episodes and player value

**Owners:** CE05, integrated FPV/playtest owner; this task supplies the new slice-specific coverage. **Dependencies:** CP01–CP09, required SPK/CTR/survival/camp acceptance. **Design:** [qualification](../projects/first-playable-cooperation-feature-spec.md#qualification-and-delivery-stages).

- [ ] Predeclare bounded ordinary-path episodes and record every attempt, independent choice, refusal, delay, useful effect, stopping point and actual provider cost; retain contrary behavior rather than rerunning until compliant.
- [ ] Observe each selected person outside direct player instruction and across competing needs/interests. Establish distinguishable conduct, natural variation, coherent refusal, voluntary useful aid and stopping when the reason changes.
- [ ] Complete at least one useful guide/preparation/carry/build/hunt/share/ceasefire episode using native capabilities; separate controlled capability proof from independently chosen behavior.
- [ ] Observe uncoached players choosing whom to approach, understanding terms/risks, benefiting from cooperation versus the solo route, recalling a particular shared occurrence and making a later choice affected by it.
- [ ] Retain confusion, repetitive begging, excessive administration, impossible timing, wasted supplies, model stalls and meaningless friendship claims as failures to fix. Apply existing shared spending/release requirements; fixtures cannot qualify natural language, independent behavior or safety.
- [ ] Reconcile CP/CE/FPV evidence and project tables; no “Completed” project status until actual agreed implementation and required verification pass.

**Exit:** the connected first-playable contains people and shared activity players can understand and value. A native green check or entertaining quotation alone cannot close this work.
