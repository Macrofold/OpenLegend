# Simulation boundary catalogue

This is a running design inventory for [simulation time](../simulation-time.md), not a second task tracker. PF13 owns the current delivery; PF/SW/EPR and feature owners retain future implementation tasks. Add a row when a mechanic gains a useful exact deadline, validity bound or unresolved coupling. A deadline predicts when work may matter; it never authorizes an effect or proves that an arbitrary larger interval is safe.

## How to extend the catalogue

For each scenario record: authoritative inputs; what remains constant; earliest deadline or conservative bound; invalidators; required boundary work; implementation/evidence status; and its existing owner. Use game-time deadlines for mechanics, monotonic real time for host/network/reading budgets, and rendering time for appearance. Never turn a timer unit into a universal update frequency. Inputs with unknown evolution need a bounded fallback rather than a speculative certificate.

**Status key:** integrated = current finite adapter contributes a bound or exact elapsed calculation; bounded = a deliberate approximation with known limits; candidate = not implemented. Current runtime evidence belongs in Verification; these entries are not universal mathematical or scale certification.

## Scaling direction, not a prerequisite framework

Start with the few implemented rate/deadline families. Next split dirty static/dynamic work and per-entity/local schedules so one fast flyer or tiny-radius contact observer does not shorten unrelated regions' intervals. Later consider a deadline heap, spatial dependency index, kinetic bounds and analytic dormant systems only when their inputs/invalidation are explicit and measurements justify them. Preserve one authoritative ordering/commit owner. An exact mechanical integrator plus approximate sampled perception must be described as such, not advertised as exact continuous reality.

## Observed global-deadline coupling

The current catalogue is consumed by one global minimum interval, not independent entity/region schedules. A crowded route/perch can require many small intervals and repeat work for unrelated actors. The actual 49-bird contested-perch scene fails 8x despite finite retry deadlines; PF13.9 owns the next isolation step.

| Scenario                               | Candidate boundary or invalidation                                                                                | Status / owner                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Blocked route/perch retry              | Existing saved wait reaches the next shared bundled retry boundary; current collision and occupancy are rechecked | Bounded implemented base policy, not fair crowd arbitration                                     |
| Occupied destination becomes available | Changed occupancy/obstruction can wake only its registered waiters instead of periodic rechecks                   | Candidate; SW12/PF13.9; requires complete mutation and load invalidation                        |
| Independent local movers               | Region or participant horizon until cross-region influence/contact; merge clocks only at actual dependencies      | Candidate; PF13.9; one writer, event-time evidence and chronological consequences remain strict |
| Floating-point endpoint residue        | Existing spatial/time tolerance resolves the same validated arrival/wait path, not repeated near-zero global work | Implemented finite numerical guard; SR28 retains partition/epsilon coverage                     |

A boundary becoming dense is a reason to revisit scheduling ownership, not proof that its effects can be discarded. Coalescing retries may add the explicitly accepted bounded wait; coalescing an actual collision, speech or required completion without a semantic rule is not equivalent.
