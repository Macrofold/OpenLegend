# Native and full-server profiling

The native-only profiler runs disposable deterministic scenarios without a database or provider. The full-server profiler below explicitly selects a disposable database. Neither changes a live save, enables gameplay mechanics or permits paid dispatch. These are performance experiments, not automated correctness tests. [Performance tracker](performance.md) owns remaining work; [Verification](../verification.md) owns measured evidence.

## Choose collection explicitly

Ordinary `pnpm dev` / `pnpm start` skip optional server performance collection. Set `OPEN_LEGEND_PROFILING=on` before starting to collect it; absent or `off` disables it, and other values (including empty) are refused. Restart to change the choice. Browser scene collection is independent: add `?profile=1` to that tab’s URL. Its Stop releases unfinished GPU timer queries immediately and preserves one completed bounded report; Start begins a fresh capture. The visible FPS meter remains available without profiling.

The server tools `scripts/profile-server.ts` and `scripts/performance/profile-server.mjs`, and the browser tool `scripts/performance/profile-browser.mjs`, accept `--app-profiling=on|off` after their ordinary arguments and default to `on`. Tools own one capture through setup, replacement factories and teardown. Use matching server and browser choices for an overhead comparison; readiness and reports identify each separately. Off-mode phase attribution is disabled/null, never a measured zero. External HTTP, process and browser callback observations remain active and must be reported as instruments.

Off rejects CPU/allocation/native-count/detailed-trace combinations. The browser’s fixed-coordinate path supports off mode; survival, near-start and wait-for-resume inputs currently require opted-in scene inspection and are refused. Missing scene movement evidence cannot pass a movement-completion gate. An overhead comparison needs identical scene, accepted workload, observation cadence and host conditions; a faster collector does not prove smooth3×. The existing full-game run allowance still applies. [PC01–PC06](profiling-controls.md), [architecture](../projects/profiling-controls-tech-design.md) and [runtime evidence](../verification/performance/profiling-controls.md) retain exact limits and remaining qualification.

The tools preserve ordinary request acceptance/refusal even when optional report decoding fails. Temporary-resource cleanup covers failed configuration and manifest export; independent shutdown owners are all attempted after an earlier failure. Enabled runtime intervals with no event-loop samples omit those fields, rather than reporting an invented zero. See the [review evidence](../verification/performance/profiling-controls.md#complete-implementation-review--october-18-2026-0008-edt).

## Primary performance baseline

**Use the full PostgreSQL-backed server as the primary production-performance baseline.** Include the real timer, command admission and durable acknowledgement, history projection, SSE, and representative cognition/maintenance load with paid dispatch disabled. Record database version/topology, actual workload, cold versus warm behavior, achieved simulation speed, debt, latency and memory. Native-only profiles remain useful for isolating engine CPU costs, but do not establish whole-server capacity.

PostgreSQL is required locally and in production. All database-dependent profiling uses owned disposable PostgreSQL databases. Historical SQLite measurements remain evidence of the version exercised, not current backend acceptance.

The full-server script now accepts an explicit `OPEN_LEGEND_PROFILE_POSTGRES_URL` for a loopback development PostgreSQL service. It creates a uniquely named database for each run; it never resets or profiles the database named by that administrative URL, and never inherits `OPEN_LEGEND_DATABASE_URL`. Missing the profiling URL fails clearly. The PostgreSQL history-only comparison remains repository-path evidence, not full-server qualification. Use the existing [PF00/PF11 tasks](performance.md) and [AR integration tracker](action-reconciliation.md) for remaining work; a working profiler does not complete capacity acceptance.

## Native CPU isolation

```sh
node --import tsx scripts/stress-native.ts scripts/performance/scenarios/gems.json /tmp/gems.cpuprofile > /tmp/gems-report.json
node --import tsx scripts/stress-native.ts scripts/performance/scenarios/mixed.json /tmp/mixed.cpuprofile > /tmp/mixed-report.json
```

Use a new output path per run. CPU profiles may contain local paths; keep profiles, reports and private input saves outside version control. Open `.cpuprofile` in a compatible CPU-profile viewer. Native reports include each measured call's CPU, actual game-time progress and `hrtime` window. Inspector profile timestamps can have a different monotonic origin: align them using the recorded bounds around `Profiler.start`, report the resulting uncertainty and exclude ambiguous edge samples. Do not compare the raw origins directly or add overlapping inclusive sample totals. Stderr reports loading/setup, warm-up, measured calls and output stages. A hard parent-process timeout covers setup as well as simulation; timeout exits with code 124 and is an incomplete result, never a capacity pass. A killed run may have no usable CPU profile or report.

Objects are synthetic resource entities with independent IDs, not stacks hidden inside one entity. Thus 500 gems means 500 ground objects. Objects can share tiles; people and animals obey spawn occupancy. This fixture accepts a finite material-property vocabulary: fiber, binding, flexible, rigid, shaft, pouch, point, projectile, food and fuel. Names such as “rare gem” are descriptive; rarity, market value and autonomous attraction are not invented by this harness. Food nutrition is real item metadata. The bundled person controller no longer chooses food automatically: eating, gathering and hunting require an admitted character choice. This native-only fixture does not exercise that cognition path; installed reservoir responses and animal movement remain separate native policies. Custom resource setup is isolated fixture construction, not a production authoring API.

Reports identify boundary-limited-prefix integration, setup/initial-freeze cost, offered versus accepted game time, interval counts/sizes, native call percentiles, total measured time, process CPU time, final heap usage, event/awareness counts, final-world digest and hot CPU functions. The native and scene drivers use the same startup-only workspace dependency check and report actual resolved entries: copied baselines linked into another checkout are refused before measurement. Headroom divides measured native throughput by `60 × speed`, using this profiler’s bundled-world rate assumption, not a universal engine clock: values below 1 cannot sustain that fixture rate even before persistence and other server work. Values above 1 do not prove end-to-end capacity. Compare identical input, scenario, warm-up, Node version and machine load; repeat runs rather than relying on one tail percentile. Digests compare native final state only, not all intermediate outcomes.

This first version excludes real-time clock debt, database commits, browser frames, cognition admission/context preparation and paid model calls. Use the running server's `/api/performance` for tick/debt and cognition spans. Long history, constrained cognition capacity and dense encounter fan-out remain distinct workloads; do not treat a successful gem scenario as 100-agent qualification.

## Actual progress and pending navigation

The profiler initializes the shared collision adapter before constructing/loading a world. Reports distinguish requested steps, attempted steps, completed steps and actual `simulatedSeconds`. A no-progress native call stops the measured loop with `status: blocked`; throughput/headroom use actual world-time progress, never requested iterations. This script does not run the navigation coordinator: a pending derived route requires the running-server diagnostic. Re-run on the same snapshot/seed for comparisons. CPU profiling adds instrumentation overhead, so the capacity gate remains an unprofiled full-server measurement.

For cadence comparisons, record offered and actually integrated game seconds, interval count and input state. Equal call counts do not mean equal simulated work. A one-second diagnostic remains useful as a numerical reference but is not the production clock contract. See [PF13](simulation-time.md) and [cadence evidence](../verification/simulation-cadence.md).

Browser recording limits, overflow behavior and acknowledged trace clocks live in [OB01](../limits/observability.md#ob01--explicit-browser-performance-capture). An oversized or incomplete trace remains failed diagnostic evidence; it cannot establish an absent stall.

## Full-server workload

Run a generated disposable scene through the real server timer, durable commands, SSE and a separate-process client. Set `OPEN_LEGEND_PROFILE_POSTGRES_URL` to a loopback administrative database.

`OPENLEGEND_PROFILE_SERVER_WARMUP_SECONDS` selects 0–60 real seconds per speed (default 0). Warm-up and measurement use one continuously running timer and load child, without a pause between them. The cutoff occurs at the next server event-loop opportunity; report actual elapsed/progress and debt rather than assuming the requested duration was admitted. Client samples belong to the phase where their request started; measurement includes outstanding-request drain and counts requests crossing the cutoff. Duration stages belong to the phase where they completed, with all-sample counts/totals/maxima and a bounded last-256 sample distribution. Report cold/warm failures and load/heap/RSS alongside measured results.

The restarted fixture explicitly takes character control through the ordinary player endpoint before play. Between speeds, normal pause admission still applies; final shutdown stops and drains the profiler's own timer. `native.iteratorCall` records each synchronous native generator call, `native.finalization` records immutable publication work, and `native.noYield` records the complete synchronous native segment between actual cooperative yields, including finalization. Queue, PostgreSQL and cooperative waiting are separate spans; host descheduling still contributes to these wall-time measurements. None changes native scheduling or its work budget. [NW12](../limits/native-work.md#nw12) distinguishes the current I/O-yield target from the coherent-world publication target; a private comparison must pin both separately.

The example credentials are for a disposable local service, not production. Only PostgreSQL URLs with host `127.0.0.1`, `localhost` or `[::1]`, without query/fragment overrides, are accepted. The helper creates `openlegend_fixture_<uuid>`, runs both setup and restarted measurement on that database, then drops only that successfully created database. It never force-drops databases or terminates other sessions. The report identifies the adapter, loopback topology, server version and generated database name without storing the administrative URL or password. A failed cleanup is a nonzero result; the generated name identifies any resource requiring manual inspection. Remote topology benchmarking needs a separately reviewed safe fixture mechanism, not bypassing this guard.

The profiler retains its own store through server startup so a failed initialization can close the connection/worker even before `createGameServer` returns a server handle. This does not fix the general factory's ownership gap for other callers; [AR07](action-reconciliation.md) remains separate. The current adapter initializes vector storage even when inference is disabled: plain PostgreSQL without `pgvector` is an initialization-failure workload, not a gameplay performance result. Keep a hard external deadline for manual profiling because native CPU work or broader shutdown failures can still prevent timely completion.

The output path must be new. The duration accepts 5–60 seconds per phase; supported requested speeds are 1, 3 and 8. An optional final argument sets the command interval to 25–1,000 ms (default 500); `... 60 1 25` requests a one-minute high-command-count run, and `... 30 8 25` a shorter accelerated run. Report successful counts and rejected/skipped requests, not just the requested rate. Setup creates a private temporary data directory, populates a generated scenario with the timer disabled, then restarts the same world for actual timed measurement. User-save inputs are rejected. The profiler removes only its own temporary directory and disables all paid dispatch. This path exercises the real PostgreSQL adapter; it does not qualify browser rendering, hosted multiplayer or live cognition.

A separate process reads state at 4 Hz, submits short move/cancel intentions at the selected interval (2 Hz by default), consumes SSE, and sends presence heartbeats every 3 seconds. Each request lane has bounded concurrency. The report separates rejected requests, errors, request-scheduling lateness and skipped intervals from successful command latency; it cannot silently count an ungenerated request as success. SSE reports bytes/chunks, not browser render completion.

With zero warm-up, the first measured phase includes acquisition after ordinary bootstrap; with warm-up enabled, its separately reported phase includes that cold work and may still leave debt or an in-flight request. Later speeds reuse the evolving world and start at their recorded simulation time; run one speed per fresh process when the comparison requires independent fixtures. Before/after runs use the same host and scripted load, but wall-timed physics can diverge and small samples have noisy tails. Native digests at matched admitted elapsed-time boundaries are separate evidence; a one-second diagnostic is not the production clock contract.

Report nominal elapsed-time achieved speed together with admitted/requested clock counters, pending debt and excluded gaps. Pending debt excludes elapsed wall time that an in-progress timer operation has not yet admitted. Existing >2-second callback-gap detection can misclassify long synchronous persistence as absence; the dense case does not qualify that boundary. Metric totals/counts are phase deltas, while `cumulativeMaxMs` is explicitly since startup. Keep initial presence-expiry runs separate from continuous-presence capacity evidence.

The short high-command-count SQLite cases and PostgreSQL history-only exercise have [recorded evidence](../verification/integration-summaries.md#dense-persistence-implementation). The [action reconciliation observations](../verification/action-reconciliation.md) separately record current-source full-server PostgreSQL diagnostics and their failed throughput/dense-tail targets. Long soaks, repeated independent percentile cases, genuine multiple players, slow consumers, remote database topology, browser rendering and no-network cognition/maintenance fixtures remain PF00/PF11 acceptance work. Phase heap usage is the main JavaScript isolate, not total process memory; `rssBytes` includes resident memory across threads. None of these phase-end values is a measured peak.

### Long-run growth checkpoints

The finite long-soak report retains a bounded series under `routines.soak.growth`. It samples at measurement start, at the existing completed-probe minute callbacks, and at cutoff. If the bound is exceeded, omitted records are counted and the final checkpoint replaces the last retained intermediate record, preserving both endpoints.

Each checkpoint also records cumulative elapsed totals and call counts for world calculation, complete saves, database requests, waiting for a world-change turn and public-view preparation (`operationTotals`). These reuse the existing duration observer. Differences between observations count an operation when it finishes: a save starting at59.9seconds and ending at60.2seconds belongs to the next observation period. ### Preserving a complete aged specimen

Set `OPENLEGEND_PROFILE_CHECKPOINT_DIRECTORY` to an explicitly chosen **absent** private directory to retain a complete current checkpoint after the measured report. After writing the original report, it pauses normally, requests one fresh UUID through the existing manual-save owner (which may wait for an earlier capture outside the world queue), and copies that exact completed manual slot into the ordinary `<directory>/<save UUID>/metadata.json` and `world.jsonl` layout with exclusive 0600 files. `preservation.json` separately records actual capture/copy/verification time, source/report identity, the paused world/time, checkpoint metadata/revision and difference from measured cutoff. Failure keeps the original performance report unchanged, records incomplete preservation and makes the process nonzero while ordinary owned cleanup still runs.
