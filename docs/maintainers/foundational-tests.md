# Stable foundational tests

This is the deliberately small regression-test plan requested in the [October foundation review](../verification/foundation-review.md). It protects reusable contracts that should survive new worlds, characters and gameplay. It is not a comprehensive coverage project, a percentage target, or permission to replace existing CI gates. The [verification policy](../../.agents/rules/verification.md) still controls other tasks.

## Selection rule

Add a test when its assertion describes a durable boundary, its fixture can be understood without a large authored world, and a realistic regression would damage multiple features or authority/privacy. Prefer public behavior of the owning module and a failure case over internal call counts, implementation snapshots or exhaustive permutations. A test should keep passing after changing dialogue, art, balance, starting content and feature composition.

Small pure fixtures are preferred. Use a real native transition or isolated PostgreSQL fixture when the guarantee crosses that boundary; do not pretend a mocked transaction proves durability. New tests accompany their owning fixes. Do not refactor a subsystem merely to manufacture a test seam or make a failing current contract pass by weakening the assertion.

## Deliberately excluded from this initial program

- Exact prompt text, NPC choices, model quality, token counts tied to prose, or paid calls in unit tests.
- Full starting-world snapshots, named recipe inventories, tuning constants, hunger rates, combat balance and exact random trait assignments.
- Screenshot/DOM snapshots of evolving panels, exact CSS/layout, or assertions that merely repeat an implementation's current structure.
- A broad generated test matrix, every action family, a new test framework, or a coverage percentage goal.

Existing relevant tests remain valuable and are not deleted because they are broader than this new program. Browser interaction, save/recovery drills and human play remain necessary where they establish things a unit test cannot, especially usability, enjoyment, real disclosure and durability.

## Maintenance discipline

Put tests beside the semantic owner. Reuse its supported operations, avoid importing one feature's fixture merely to reach a utility, and keep the assertion about the invariant. If a test breaks, first determine whether the accepted contract changed; do not update an expected result automatically. If repeated fixture churn reveals a missing module boundary, extract only the responsibility needed by a real caller, preserving one mutation owner. Keep this plan small and rerank before starting another slice.
