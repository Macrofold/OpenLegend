## What the current game does

### Sight, attention and warnings

Broad sight keeps track of who is nearby. The detailed list decides whose movements and other changes merit closer observation. The rules let an actor using the `npc` controller track at most one subject in detail solely because of ordinary cues such as movement. Within the same overall capacity, one subject whose current description has yet to be presented can receive detailed attention for discovery. Player characters keep the standard allocation. Speech, direct interaction, current work, warning cues and actual loss of sight use their existing rules. Dirty broad sight normally checks on a one-real-second schedule. Detailed sight is due twice as often. Individual checks can yield and resume in multiple pieces. [Current rules](../../../worlds/base/attention.md#selected-acquisition-cadence)

The limit on detailed attention does not limit how many candidates the engine prepares. It can build a complete list and then decide to keep the old choices. Preparing a candidate reads permitted body details and can measure, encode and hash them even when its visible description is unchanged. Relationship checks consider distance or support around watched subjects and keep some state about past checks. This can turn a routine movement into attention preparation and persistent records for other people. [Attention update](../../../../native/simulation/src/reception/attention_control.rs) · [Candidate preparation](../../../../native/simulation/src/reception/attention_control/candidates.rs) · [Relation checks](../../../../native/simulation/src/reception/attention_control/relations.rs)

### Deer, hares and residents

Deer and hares look for food, use hunger to choose whether to forage, stop to eat, and flee from qualifying perceived danger. They do not run the human decision system. Their own checks are only one cost. A moving animal can cause nearby people to recheck sight, compare what they remember and save new observations. The pasture rules already offer a switch for a fed animal to return home and rest in daylight. That gives us a small test if the new profile shows that the animal's total downstream cost is high. [Pasture rules](../../../../packages/domain/src/worlds/base/config/first-playable/ecology.yaml) · [Foraging flow](../../../../packages/domain/src/worlds/base/native/foraging.rs)

Residents with a reason to think first check their private evidence. This can wait for a save, read a cursor from PostgreSQL, build a small world snapshot, and sometimes read speech in a second pass. One decision can have several provider steps. Count opportunities, actual jobs and provider calls separately. The world can already turn off idle curiosity while keeping sight discovery, addressed conversation, blocked work and known danger. Quiet characters would initiate fewer spontaneous thoughts. [Decision scheduling](../../../../native/game-server/src/npc/schedule.rs) · [Reasons to think](../../../../native/game-server/src/npc/schedule/select.rs)

### Events, memory and saving

The game keeps one original for a consequential event and separate records of what each person actually witnessed. Eligible routine walks already skip departure and arrival announcements. A person who is watching can still acquire intermediate movement observations in their own chronological pages. The live view looks through recent event and observation records and rechecks the selected evidence before sending it. That protects privacy, but doing the same selection on a walk can repeat work even when the player learned nothing new. [Routine movement rules](../../../worlds/base/attention.md#recent-history-and-lasting-memory) · [Event capture](../../../../native/simulation/src/experience/player_events.rs) · [Final disclosure check](../../../../native/simulation/src/experience/player_events/fence.rs) · [Persistent witnesses](../../../../native/game-server/src/store/history.rs)

Accepted game steps prepare changed records and merge them with unsaved changes. This can revisit old pending rows even when a step only touched one table. The once-a-second save freezes an exact batch. The writer already groups records and commits the batch atomically. A failed save can retry that same batch while play continues to prepare newer changes. Fewer optional observations would save work both before and after PostgreSQL. Making the merge touch only affected tables would preserve those observations. [Pending records](../../../../native/simulation/src/records/save.rs) · [Atomic writer](../../../../native/game-server/src/store/write.rs)

### What triggers database reads

Before deciding whether a player update needs to send anything, the server can read recent AI jobs, recalculate monthly usage, read player preferences, and look up reply labels. Two display reads already share a transaction. A view with recent jobs still makes about six SQL statements including the transaction boundaries. A separate label lookup adds up to four when applicable. Those figures are from call paths and apply only to eligible attempts. The run will measure the actual total. For large results, some readers first query for the size, reserve memory and then query for the body in the same snapshot. A smaller, bounded display result can be a good place to simplify that. ## What to test, in order

The [Rust preparation design](../../../projects/completed/2026/native-simulation-hot-paths.md) turns proposals 1, 3 and 4 into separate experiments with caller checks and adoption criteria.

1. **Stop rebuilding what a character already knows.** Start with repeated current-field lookups and related-track selection inside an accepted world state. Use an already-known exact source identity or pass the prepared lookup to the next consumer. Reuse a description only while its visible fields match. A deer stepping a metre can change its distance and leave its visible markings unchanged. Count source lookups, rebuilt string keys and candidate encodes before and after. Compare exact choices, sensing and warnings through motion, loss, correction and restore. This targets the largest sampled group without changing the game rules. Avoid starting with a broader cache or spending time improving the rare ranking reuse alone.
2. **Try recording incidental movement only at useful points.** For an uninvolved resident, keep a cheap sense that someone is nearby, then update optional detail at arrival, loss, a meaningful distance change or a slower fallback. A shopkeeper can remember that someone crossed the pasture without remembering the path around each tree. Start with exact current sight and coarser optional history or ranking. If the cost is still upstream, try triggering ordinary detail work only when a relevant distance boundary changes. A resident could miss a short crossing or remember a coarser route. Keep speech, direct danger, deliberate focus, current work, and the player's visible response. Measure records and CPU before storage, how many crossings are missed, and the latency of direct events. If relation bookkeeping is still large, a separate stronger test would keep automatic warnings for oneself and current work, at the cost of fewer warnings about strangers.
3. **Let movement carry movement.** Start with selecting only the recent events the live view needs. Older story and world-event pages already load on demand. On the database side, distinguish round trips, growing query scans and size probes. Try combining exact scalar reads inside the current snapshot if the round trip is material. Moving settings or usage to on-demand refresh would change live browser behavior and needs separate review. Keep position, new speech, reply status, current permission and actual spending checks live.
4. **Prepare fewer save rows and decision inputs.** Follow the hot sizing and encoding paths before rewriting the pending merge. Reuse exact prepared record bytes or detect a relevant change before serializing a row. If later counts show a large pending suffix, keep untouched tables in place and merge only the ones that changed. For a decision job, inspect where an authorized structured read turns into JSON and immediately gets sized, decoded or projected again. Keep source revalidation and every budget check that protects real memory. These are separate exact-result experiments. Measure CPU, input and output bytes, changed rows and durability. Keep the current one-second save and exact retry.
5. **Only then try quieter animals or less idle thinking.** First measure how much animal movement causes humans to sense, store and save. If that cost is large, let fed animals rest longer with feeding and escape still active. The pasture may look less busy. Count distinct reasons for resident jobs before reducing idle curiosity. Keep addressed conversations, blocked work and supported danger. These are separate authored choices. Direct animal behavior itself is too small to justify cutting it first.
