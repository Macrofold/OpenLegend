## What the current game does

### Sight, attention and warnings

Broad sight keeps track of who is nearby. The detailed list decides whose movements and other changes merit closer observation. The rules already give a resident only one spare slot for following ordinary movement, alongside a slot for discovery. Players have their usual slots. Speech, direct interaction, current work, warning cues and actual loss of sight use their existing rules. Dirty broad sight normally checks on a one-real-second schedule. Detailed sight is due twice as often. Individual checks can yield and resume in multiple pieces. [Current rules](../../../worlds/base/attention.md#selected-acquisition-cadence)

The limit on detailed attention does not limit how many candidates the engine prepares. It can build a complete list and then decide to keep the old choices. Preparing a candidate reads permitted body details and can measure, encode and hash them even when its visible description is unchanged. Relationship checks consider distance or support around watched subjects and keep some state about past checks. This can turn a routine movement into attention preparation and persistent records for other people. [Attention update](../../../../native/simulation/src/reception/attention_control.rs) · [Candidate preparation](../../../../native/simulation/src/reception/attention_control/candidates.rs) · [Relation checks](../../../../native/simulation/src/reception/attention_control/relations.rs)

### Deer, hares and residents

Deer and hares look for food, use hunger to choose whether to forage, stop to eat, and flee from qualifying perceived danger. They do not run the human decision system. Their own checks are only one cost. A moving animal can cause nearby people to recheck sight, compare what they remember and save new observations. The pasture rules already offer a switch for a fed animal to return home and rest in daylight. That gives us a small test if the new profile shows that the animal's total downstream cost is high. [Pasture rules](../../../../packages/domain/src/worlds/base/config/first-playable/ecology.yaml) · [Foraging flow](../../../../packages/domain/src/worlds/base/native/foraging.rs)

Residents with a reason to think first check their private evidence. This can wait for a save, read a cursor from PostgreSQL, build a small world snapshot, and sometimes read speech in a second pass. One decision can have several provider steps. Count opportunities, actual jobs and provider calls separately. The world can already turn off idle curiosity while keeping sight discovery, addressed conversation, blocked work and known danger. Quiet characters would initiate fewer spontaneous thoughts. [Decision scheduling](../../../../native/game-server/src/npc/schedule.rs) · [Reasons to think](../../../../native/game-server/src/npc/schedule/select.rs)

### Events, memory and saving

The game keeps one original for a consequential event and separate records of what each person actually witnessed. The recent movement observations that belong to a person can also live in compact chronological pages. The live view still looks through recent event and observation records. It rechecks that evidence before sending it. That protects privacy, but doing the same selection on a walk can repeat work even when the player learned nothing new. [Event capture](../../../../native/simulation/src/experience/player_events.rs) · [Final disclosure check](../../../../native/simulation/src/experience/player_events/fence.rs) · [Persistent witnesses](../../../../native/game-server/src/store/history.rs)

Accepted game steps prepare changed records and merge them with unsaved changes. This can revisit old pending rows even when a step only touched one table. The once-a-second save freezes an exact batch. The writer already groups records and commits the batch atomically. A failed save can retry that same batch while play continues to prepare newer changes. Fewer optional observations would save work both before and after PostgreSQL. Making the merge touch only affected tables would preserve those observations. [Pending records](../../../../native/simulation/src/records/save.rs) · [Atomic writer](../../../../native/game-server/src/store/write.rs)

### What triggers database reads

Before deciding whether a player update needs to send anything, the server can read recent AI jobs, recalculate monthly usage, read player preferences, and look up reply labels. Two display reads already share a transaction. A view with recent jobs still makes about six SQL statements including the transaction boundaries. A separate label lookup adds up to four when applicable. Those figures are from call paths and apply only to eligible attempts. The run will measure the actual total. For large results, some readers first query for the size, reserve memory and then query for the body in the same snapshot. A smaller, bounded display result can be a good place to simplify that. ## A provisional order to test

These are experiments to rank again with the current CPU and work counts. They have no claimed savings yet.

1. **Reuse what a character already knows during attention.** A deer moving a metre does not change its visible markings. Reuse the description preparation while the relevant visible facts, ownership and permissions match. Keep distance, urgency, occlusion, corrections and actual selection current. Measure encodes per candidate and CPU, with exact choices and warnings as the check.
2. **Take display data that changes slowly off the movement path.** Refresh preferences and usage when their values change or when the player opens that panel. Keep new replies and real controls live. Reuse permitted journal results only while their evidence remains current, and load older optional history on demand. Compare queries per attempted view and per delivered frame, along with movement latency. Keep final authorization, forgetting, usage-window rollover and the actual spending check.
3. **Record ordinary motion only at useful points.** Try arrival, departure, big distance changes and consequential events for uninvolved residents. A shopkeeper will retain that someone passed through, with fewer details of the path. Start by keeping exact current sensing and reducing optional history and reranking. If candidate selection or sight remains the bigger cost, try a slower fallback for incidental movement. Preserve speech, direct danger, meaningful changes, exact movement physics and the player view. Test how many brief crossings a resident misses.
4. **Do less save preparation between commits.** Count pending rows revisited without changes. If that count is high, keep untouched tables in place and fold only changed ones. Keep database transactions atomic, the current one-second interval and exact retry. Preserve witness references and the order of events.
5. **Reduce quiet background activity only where it pays.** Count idle curiosity jobs before disabling them. Try longer fed rest for deer and hares only if movement drives substantial follow-on work, with escape and feeding still responsive. If optional bystander warnings dominate, test keeping self and current-work warnings while dropping automatic warnings about uninvolved strangers. Each is a separate world choice with a different gameplay cost.

Process memory will show actual server and PostgreSQL usage. The game separately accounts for temporary work, retained data and pending saves. Those peaks have different lifetimes and can occur at different times. The profiler has no qualified breakdown by allocation site, so accepted memory and observed process memory will be reported separately. SQL counts and elapsed waits also cannot assign PostgreSQL CPU to individual statements on their own.
