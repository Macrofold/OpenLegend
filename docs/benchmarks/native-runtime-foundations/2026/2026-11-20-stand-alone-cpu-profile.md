# Where the stand-alone Rust server spends CPU — November 20, 2026

## Result at a glance

The stock stand-alone release averaged **77.70% of one logical core for the Rust server**, **8.98% for PostgreSQL**, and **100.00% of intended game speed** over 180 seconds. The same source's stack replay put **38.5% of sampled server CPU in perception and attention**. Keep real motion, sound and disclosure. Start by doing less work to keep each witness's information current.

## What ran

The heavy opening has one authenticated player, ten human residents, ten deer, five hares, three pasture areas and 1,246 scenery records on a 62 × 54 m map. The residents start with fixture-supplied out-and-back routes and move through the normal simulation. The animals use the bundled world's grazing and alarm rules. The player moves through normal HTTP commands and steering, reads the live event stream, and starts two conversations through a controlled HTTPS provider. Ordinary saves run every second. The steady window is 180 real seconds after 10 seconds of warmup at the authored rate of 60 game seconds per real second. The game server is a stand-alone Rust process with a single simulation worker and a 2 GiB transient allocation allowance. The Node process running the client and fixture is accounted for separately.

The profiled source in Macrofold/OpenLegend was `a4a68040b95d01c9361dfaa04d82b23698a50d17`. The [managed worker](../../../../.agents/rules/verification-workers.md) was the standard 16 GiB, four-vCPU `m7i.xlarge`. Each replay used a fresh database on its exclusive PostgreSQL cluster. This workload covers a busy shared scene with one player. Its CPU is a cost for that scene and all its inhabitants. It does not establish the cost of one additional player, independent towns, mature histories, or the bundled world's unported combat and territorial behavior.

## How the measurements were separated

- **Ordinary replay.** Process counters measure the whole Rust server, including its threads, and the exclusive PostgreSQL cluster rather than adding independently sampled thread totals. The client sends actual authenticated requests, reads the stream and checks the new positions. This measures first receipt by the client. The earlier Chromium trace separately verifies the time to an actual displayed position. Command response and the later observation of a durable receipt are separate timers.
- **CPU stack replay.** The optimized release was built with frame pointers and source line tables. The separate stack replay samples each registered application thread every 10 ms of its own CPU time. A parked thread uses no CPU samples while asleep. Resolve application and inlined source frames and assign each stack to its deepest recognized owner. Callers can cause work owned elsewhere. For example, an animal movement can cause another resident's perception and a later save, so those samples belong to the perception and save groups. Libraries without a recoverable application frame remain unattributed. A separate ordinary replay used the same profiling executable without the sampler. The stock replay used an independently built executable with normal release flags. These profiles estimate where work went. They do not measure a speed change.
- **PostgreSQL wire replay.** A separate loopback relay counts actual server SQL completions, rows and bytes. Setup and the independent receipt observer bypass it. System CPU for PostgreSQL comes from the unrelayed run. Counts of statements, transferred rows, touched rows, database bytes and WAL answer different questions. There is no per-query PostgreSQL CPU measurement here.

**Private perception plus attention accounted for 38.5% of samples, roughly 27 points of one core in this replay.** That makes the cost of keeping observations and attention current a better target than turning off precise rays or reducing the game's clock rate. There were 691 stacks with a current-field lookup or freshness check and 372 with an attention deadline or relation-key function. For example, a [current observation read](../../../../native/simulation/src/reception/current_read.rs#L84) walks the groups of fields to find one eligible source. Checking whether an existing field is still supported can perform another body-field lookup. The [attention deadline path](../../../../native/simulation/src/reception/attention_control/timing.rs#L7) sorts and combines active anchors and constructs JSON keys while trying to answer when any one requires attention. These are small calculations that can repeat across observers. The clock appeared in 2,788 of 3,821 perception stacks and 787 of 1,014 attention stacks. Only 55 perception stacks also contained the recognized player publication path. Inlining and parking can hide the caller, so those counts identify a large real clock path without measuring an exact split across every caller.

One high-count line is a clone of recent-observation source IDs. Of 379 stacks at that line, 377 go through [personal history capture](../../../../native/simulation/src/experience/history.rs#L727). It sums the size of recent directories, then copies them to produce a fixed actor cut for history work. This sits in the perception and observation row above, before the database sees a write. Give the caller a narrower eligibility result when all it asks is whether one event can appear in a story. Where an independent reader truly needs the fixed directory, try sharing immutable, funded blocks for its required lifetime. Do not reuse whatever live directory happens to be current later.

**A large part of the work is handling data.** Across all stacks, 2,241 (17.8%) included a serialization frame, 887 (7.1%) included an explicit JSON size walk, 763 (6.1%) included deserialization, and about 2,200 each included cloning or dropping and hashing or equality work. These are overlapping stack markers and can include surrounding work. They are not a second partition of CPU. Many leaf samples are inside the system C library. Use the mapped Rust caller to assign those samples where possible. The exact split between memory allocation, copying, runtime and kernel work remains unresolved. Within resident work, 327 stacks included the same [funded JSON reader](../../../../native/game-server/src/npc/decide.rs#L879), which sizes a text input before parsing it. Prefer keeping a typed result for its next known consumer if doing so avoids a repeated conversion while preserving transfer and allocation bounds.

**Deer behavior itself was small.** There were 43 direct wildlife samples and 154 stacks with a wildlife controller or route on them even when a deeper owner took the exclusive sample. This does not measure the full cost of removing deer. Wildlife movement also causes perception, attention and records for other characters. The stack replay observed placement edits for all 15 animals and all ten residents. Animal placement revisions varied from 2,780 in the stack replay to 6,496 in the unrelayed no-sampler replay, including setup and drain edges. The number of local controlled judgments also varied, from 297 to 404, while both prompted replies completed in each. The partitions describe the sampled session. Treat them as priorities for controlled tests, not universal percentages or savings predictions.

## How this gameplay creates work

### The clock and physical motion

The server normally offers elapsed time about every 50 ms, roughly three game seconds at the selected speed. Within an offer it can stop at movement endpoints, status deadlines, animal reviews and sensory updates. Each accepted turn applies those changes in order so, for example, a sound cannot startle a deer before it arrives. Motion and approaching hazards can also provoke work for nearby observers. A routine turn can pay for checking who is due even if nobody changes course. The earlier browser trace found about 96–108 ms spent waiting for the world turn on its two slowest walks. Final permission, encoding and handoff took at most 0.45 ms once that turn was granted. Those figures describe where a walk waited in the earlier instrumented run. [Clock driver](../../../../native/game-server/src/game_clock.rs#L344) · [Earlier browser trace](2026-11-18-rust-game-server.md#managed-attribution)

The clock also advances continuous body needs and checks whether conditions cross a deadline. A warm clock continuation can reuse its roster. The physical roster does not include the 1,246 decorative scenery records. Individual slices can still rebuild lists of working actors and revisit status, sensory expiry and commitment owners. If the profile shows material cost here, one way to avoid repeated visits is to maintain the next due deadline by owner. A more ambitious option is to represent a quiet meter as its last value, timestamp and rate, and materialize it only when a rule reads it, a rate changes, it crosses a behavior threshold or it is saved. Exact crossing order, restarts and pause would be part of that design. [Participant preparation](../../../../native/simulation/src/time/participants.rs#L169) · [Warm continuation](../../../../native/simulation/src/time/advance.rs#L530) · [Status settlement](../../../../native/simulation/src/time/endpoint.rs#L102) · [Commitment deadlines](../../../../native/simulation/src/experience/commitments.rs#L133)

### Perception, attention and reaction

Perception asks what a particular character can see or hear. The nearby index narrows the list, then range and facing reject candidates before exact visibility checks. The bundled world normally checks broad sight for a changed nearby scene about once per real second; selected details can refresh twice per second. A character with ordinary Focus can follow about ten detailed subjects. It can still see other people and animals in broad sight and hear eligible sounds. There is also a separate local check for physical relations such as an approaching body or a drop. These rules lead to decisions and private records as well as what appears on screen. If several residents watch the same moving deer, the deer moves once, but each relevant witness can update its own observations. [Bundled world attention](../../../worlds/base/attention.md) · [Nearby exposure](../../../../native/simulation/src/reception/exposure.rs#L219) · [Visibility checks](../../../../native/simulation/src/reception/sensors.rs#L255)

Attention chooses what to follow closely, tracks changes, and keeps temporary warnings such as a nearby body closing in. The engine considers direct involvement, current activity, existing focus and competing cues. Detailed work can search the local index even when the due subject IDs are already known. The ranking reuse path still rebuilds candidates, including describing and measuring some evidence, because it also uses the rebuilt candidates to maintain real associations, losses and warning deadlines. Two different opportunities follow. Directly find subjects already selected for detail. Separately, measure which parts of the ranking work can be skipped while keeping warnings current. [Detailed reception path](../../../../native/simulation/src/reception/batch.rs#L629) · [Attention update and reuse](../../../../native/simulation/src/reception/attention_control.rs#L436) · [Candidate preparation](../../../../native/simulation/src/reception/attention_control/candidates.rs#L130)

### Deer, hares and human residents

The animals in this fixture have a real body, route, hunger, choice of food and response to danger. Their pasture profile seeks food below 50 fullness, stops eating at 85, grazes for about 1.5 real seconds per meal and reviews ordinary behavior after about 40 real seconds. A route ending or failing can trigger another choice sooner. Each food search considers nearby resource bodies, checks which are visible, updates the animal's limited food memory and chooses a reachable resource or a feeding action. Even fed animals can refresh food memory. Eligible speech can trigger escape. Repeated familiar sounds refresh the acoustic evidence without necessarily restarting the escape. A person's ordinary walking alone does not raise that alarm. This workload does not cover territorial deer, predation or combat, and the animals make no model calls. [Opening](../../../../packages/domain/src/worlds/base/rust-server-opening.ts#L83) · [Pasture rules](../../../../packages/domain/src/worlds/base/config/first-playable/ecology.yaml) · [Forage choice](../../../../native/simulation/src/native_controller/foraging.rs#L123) · [Speech reactions](../../../worlds/base/animal-sound-responses.md)

Human residents add three different costs. Their walking can change nearby witnesses' sight and records. The background thought scheduler revisits eligible residents after relevant changes, reads and picks evidence, and may run a background judgment. Directed conversations also gather and check current private evidence, validate the response, apply it to the world and save it. The model provider mostly waits outside CPU. Preparing evidence and deciding what still applies are local work. A previous heavy comparison counted 338–414 optional background judgments during 180 seconds alongside two directed generations. That motivates measuring background work separately from the conversations the player requested. [Scheduler](../../../../native/game-server/src/npc/schedule.rs#L225) · [Earlier provider counts](2026-11-18-rust-game-server.md#rollback-qualified-comparison)

### History, packing, and PostgreSQL

World chronology keeps one durable original for a consequential event. The hot list keeps IDs. Each permitted witness can hold a reference to what that character actually received. Past visibility and physical observations can live in compact chronological pages, independently of the player's story feed. Routine walking already suppresses repeated departure and arrival stories. Keeping less detail later cannot save the cost of gathering it now. Reducing optional tracking where it starts could remove sensing, history preparation and saves together. Preserve what is needed for important events, corrections, loss of sight, private conversations and current decisions. [Event save](../../../../native/simulation/src/events/save.rs) · [Witness records](../../../../native/game-server/src/store/history.rs#L287) · [What attention retains](../../../worlds/base/attention.md)

Rust journals changes during each simulation turn. Before accepting it, Rust identifies changed fields, measures and encodes records and prepares its undo and save products. At the normal one-second save, a captured prefix goes to a single PostgreSQL writer. It groups records by table and columns and writes batches atomically with command receipts. Acknowledgement advances the durable cut. Two credible places to avoid work before PostgreSQL sees it are [changed map packing](../../../../native/simulation/src/records/map_changes.rs#L101), which can size and encode both versions of an entry before finding it unchanged, and [temporal actor packing](../../../../native/simulation/src/received/state/save.rs#L137), which enumerates and sorts the actor roster before it skips unchanged actors. The first candidate needs a typed proof that stored content and position are equal. The second should use dirty IDs and stable ordering on ordinary turns, with the complete ordering path when membership changes. [Candidate save composition](../../../../native/simulation/src/simulation/save.rs#L21) · [Atomic SQL writer](../../../../native/game-server/src/store/write.rs#L139)

The player view mixes frequently changing position with slower profile settings, AI job history and spending numbers, and reply markers. Today preparing a view can read those slow parts again even when all that changed was a position. The usage display goes back over the actor's current UTC month. Some variable-sized SQL reads execute the same selection twice in a repeatable snapshot. The first counts and sizes its result to admit memory. The second fetches the actual rows. The writer already batches inserts and updates. A bigger connection pool can reduce waiting in the right case, but it does not make either duplicated query cheaper. [Player cognition display](../../../../native/game-server/src/store/view_cognition.rs#L59) · [Bounded read](../../../../native/game-server/src/store/read.rs#L497) · [Display-data contract](../../../performance/scheduling.md#browser-and-provider-polling)

The new relay counted **51,528 completed server statements over 180 seconds**, about 286 per real second or 4.76 per completed game-second. It saw 19,838 simple-protocol completions including transaction control, 31,690 extended executions, 57,734 returned data rows, 32.54 MB of returned row payload and 212.46 MB in bind frames. No relay failure, partial frame at a timed boundary or PostgreSQL wire error was recorded. In the separately run unrelayed session, database statistics reported 11,041 commits, 153.82 MB of WAL and 55.37 MB of database growth. The three view read families were 77% of operational read transactions. This share is a statement about the number of reads, not their CPU. They are the clearest way to remove calls without changing how the world behaves. The generic size preflight protects memory. Change it only for callers that can prove the maximum row count and row size before reading, or with a transfer design that preserves both the original snapshot and hard memory custody. NPC recall and exact source reads carry larger and different evidence. They should keep their snapshot guarantees.

The writer prepared about 43% of its typed rows for relation-scan progress and current attention latches. These represent work such as remembering where a local warning search stopped or whether a warning is still active. They are separate from dialogue text and old stories. The older writer spent 139 ms in typed batch preparation over the full diagnostic. The Rust work to determine and encode changed records, PostgreSQL statement execution, transaction waits and WAL are four different costs. Cutting stored history after capturing it would miss most of those opportunities.

## Candidate changes and what to check

These are proposals for later approval. Measure the complete server plus database, at the same game speed and input schedule. Count work avoided at the point where it is created so a reduction in stored rows cannot hide an unchanged sensing cost. Start with the current hot paths and keep large gameplay changes separate from representation changes.

For a larger product shortcut, treat distant, idle residents as running a timetable instead of physically simulating every small motion. For example, a distant deer can be resting or expected at the pasture until a player enters its area, an eligible sound reaches it, or a consequential event wakes it. The engine would still need a spatially valid return, intact populations and personal history, and a clear rule for activities that matter outside view. It would lose some offscreen ecology and might require new ownership machinery. A small trial of background detail or routine review intervals is cheaper to validate first.

Keep costly work off the hot path where possible. Starting more workers can shorten a suitable independent phase, but it leaves the same work to do and can increase total CPU. Earlier stand-alone screens found tiny gains from splitting exact geometry or splitting changed-record tables across workers. Reduce repeated work first. Revisit multiple cores when a current profile shows a large batch with independent inputs and outputs. Leave the exact collision, event-time hearing, permission, one-second save and save durability rules in their current owners. Changes to what deer remember, when villagers notice incidental movement or which thoughts are worth running belong to the bundled world. [Earlier independent geometry and row screens](2026-11-18-rust-game-server.md#active-area-geometry-eligibility)

An even simpler authored experiment is to give a few residents purposeful travel at any one time and have the rest work in place. Ten people walking on independent loops can make many witnesses update records without making ten distinct encounters more interesting. A resident can switch back to ordinary movement when the player approaches, an activity requires travel or a relevant event occurs. This would make the scene less continuously busy. Trial it in the opening after measuring the unchanged-world changes, with an explicit count of active routes and a comparison of encounters and replies.
