# Installed food preparation and finite casts

Characters can choose a food transformation using actual accessible ingredients and a perceived lit fire. Worlds install the recipe's exact ingredients, products, work time and heat requirement; the existing cooking action performs the work. Worlds can also install a finite source that supports one chosen cast with a compatible reusable tool. These are current finite native capabilities, not arbitrary generated effects or a population simulation.

## Preparation definitions and exact choices

`foodPreparations` contains versioned definitions with readable names/descriptions, distinct named input roles and positive whole quantities, distinct output definitions and quantities, positive game work seconds, the supported `lit` heat requirement and completion wording. All referenced item definitions must exist. Multiple outputs of the same definition must be consolidated into one quantity. The contract currently binds one exact accessible lot per input role; it does not aggregate several lots to fill one role. Different roles may bind the same lot when its free quantity covers their combined requirement.

Definition admission also retains the existing [256-operation atomic resource-group limit](limits/state-effects.md#st04): each ingredient role requires one operation, so preparations cannot declare more roles than that owner can commit. This does not add a total recipe or source count limit. Input roles use the same safe record identifiers at definition, command and learned-method admission; reserved JavaScript property names are rejected. Choice preparation first rejects aggregate shortages and too few usable portions across lots, then solves each material independently, trying larger roles first. Lots with equal remaining quantity are interchangeable for these definition-and-quantity requirements, except that a specifically selected inventory lot must participate. Every attempted assignment is charged to the existing work allowance; exhausting that allowance fails the read rather than returning incomplete choices. More specific future ingredient requirements must also participate in that equivalence check.

Definition text uses the existing 500-character action-text bound, and products use the existing 16-output action-record bound. Container products retain the object owner’s one-container-per-lot rule. Ingredient/product facts are structured in bounded groups with readable sentences, so many roles or a long valid role do not become oversized labels or silently disappear. Native capture checks the existing record/display envelopes before replacing work; cooking also checks its prospective completed receipt and material history before spending ingredients and again before producing items. A recipe within the atomic role count can still exceed those envelopes and truthfully refuse. Bounds remain operational, not additional world laws.

`food-preparation.ts` owns current definition resolution, choice preparation, input claims and saved bindings. A cook command names the preparation’s identity/version/digest, each exact input lot and the chosen heat entity. That digest includes the current meanings of all referenced item definitions, so changing only a product or ingredient definition also invalidates an old choice before costs. Its work binds the preparation and every input/output definition. Changed meaning refuses start or cancels pending work rather than substituting another recipe, ingredient or fire. Public commands, typed requests, NPC offers, plan result references and learned methods carry that same choice.

The kernel remains the physical mutation owner. Cooking approaches the selected heat, consumes exact claimed quantities when work starts and produces the declared real items once on successful completion. It rechecks heat, participation and current definition meaning during work and at completion. Stop, movement, lost permission or heat loss retains elapsed time and spent ingredients, with no output or refund. This preserves the previous cooking interruption policy. No fish-specific handler or alternate writable stock/food store is introduced.

Successful outputs pass through ordinary item creation and action records. A single-output preparation supplies the ordinary item receipt; multiple outputs require their named output ports. A later step binds an actual sufficient quantity, never an assumed future catch or product. Learned methods represent each ingredient as a reusable object role or an actual earlier output; private lot identities do not become shared method constants. Eating, nested packing, carrying and consent-aware offering use the existing body and possession owners.

Completed action records retain their captured facts if an installed preparation later changes. A reusable method cannot be inferred from that changed meaning, and a proposed method's consumption summary does not substitute current quantities for an obsolete preparation. Repeated ingredient roles that refer to the same earlier product contribute their combined quantity.

## Finite source attempts

`castDefinitions` holds the compatible tool kind, ordinary chance, game work time, line/stance geometry limits and world-authored text. A resource's cast capability names its definition, supported dry stance, endpoint and declared water footprint. Current-format validation requires those exact records and both named horizontal bounds; unrelated numeric fields cannot substitute for a missing water bound. Actual surface support and clear line are required; landscape color cannot grant the capability. The ordinary gather action refuses a cast source.

`finite-casts.ts` resolves the exact source, tool and output meaning. The existing approach/work action holds that accessible tool without requiring a permanent equipment slot. The attempt rechecks source, stock, participation, tool, stance, endpoint and line at its due simulation boundary. A lawful resolution draws the world's saved random sequence once. Success removes one supply unit and creates one real item atomically; an empty attempt draws once but removes nothing and produces nothing. Cancellation, stale tool/source meaning, invalid geometry or exhaustion before resolution draws nothing and debits nothing. Concurrent attempts resolve in the existing deterministic commit order, so the last unit cannot produce two catches.

The source pin includes its capability, placement and output meaning but excludes mutable quantity. Another actor's catch can therefore leave a still-lawful attempt pending; exhaustion is decided against actual stock at resolution. Neither inspection nor preview samples randomness. Public and NPC projections hide exact remaining catch stock; they may describe ordinary chance/time and an inspected exhausted source. Preview grants no execution or future outcome knowledge.

## Persistence, ownership and work growth

The current world format requires both definition maps. Selective PostgreSQL records store those maps; pending work retains exact definition/source/tool/input bindings, duration, remaining simulation work and actual consumption. Current-format validation rejects missing or changed definitions and malformed bindings/timing. Completed receipts and actual stock survive reopen without replay. Closing a player's control retains the separate existing departure/cancellation rule; a saved pending native attempt is not a promise to continue work after that player departs. [Save and load](save-and-load.md) and the [development save policy](../AGENTS.md#development-save-policy) remain authoritative; no legacy reader, reset or migration is added.

Domain code remains deterministic and serializable; no provider, wall clock or renderer enters food effects. Server callers supply permitted possessions and perceived sources/heat. A catalogue or rebuilt view prepares exact ingredients and captures their recipe content signature once within its unchanged synchronous read, then binds separate commands for each perceived fire. NPC choices sort permitted fires once and select the nearest one with sufficient fuel for each recipe. No persistent ingredient-eligibility cache is added; existing possession revisions refresh choices when holds change. Selecting usable food with no perceived heat retains an unavailable preparation and its missing-heat explanation. Cooking menu identities preserve the complete chosen command, and cast identities preserve the source/tool tuple; embedded delimiters cannot collapse distinct choices. Gathering shortcuts use actual permitted Gather offers and their reasons, choosing the nearest enabled source in one pass. They never infer gathering support or exhaustion from resource appearance or withheld quantity.

The existing definition-pin cache also reuses unchanged definitions through native draft snapshots; modified snapshots are recomputed, preserving live replacement checks without a second writable owner.

Ambiguous exact-lot assignment can still branch combinatorially for unequal quantities, bounded by the inherited work meter even outside a native transition; enclosing work allowances are also charged. Fishing indexes compatible tools once before expanding their uses over perceived sources. Native work visits active attempts at their existing deadlines, with no periodic scan of every source. The number of installed recipes, compatible tools and perceived sources can still grow; inherited work admission and request/storage envelopes apply rather than silently truncating valid choices. Larger-world capacity is unmeasured. Cooking previews retain the atomic ingredient transaction because its final quantity, reservation and work-admission checks can refuse after ordinary prerequisites; safely separating that read-only preflight remains with [AC11](maintainers/action-capabilities.md#ac11--usability-and-measured-efficiency) and [PF05](maintainers/performance.md#pf05--public-view-and-browser-responsiveness).
