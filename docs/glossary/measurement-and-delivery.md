# Measurement and delivery

[Glossary index](README.md)

## What does a check establish?

| Canonical term         | Meaning in OpenLegend                                                                                                                                                                                                                                                                | Source                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feature specification  | Describes what a player or operator should experience and the conditions under which the feature should work.                                                                                                                                                                        | [Project status and design ownership](../../.agents/rules/documentation.md#project-status-and-completion)                                                        |
| Technical design       | Describes how the proposed implementation will deliver the feature and satisfy its requirements.                                                                                                                                                                                     | [Project status and design ownership](../../.agents/rules/documentation.md#project-status-and-completion)                                                        |
| Limits inventory       | Records each constraint, its rationale, current status and when to revisit it. A proposed limit is still a choice under consideration.                                                                                                                                               | [Limits inventory](../limits/README.md)                                                                                                                          |
| Configured allowance   | The amount the application is configured to permit, such as a maximum number of simultaneous jobs.                                                                                                                                                                                   | [Kinds of limit and evidence](../limits/README.md#entry-structure)                                                                                               |
| External quota         | A bound imposed by a provider or platform, such as a limit on the requests it will accept from an account.                                                                                                                                                                           | [Kinds of limit and evidence](../limits/README.md#entry-structure)                                                                                               |
| Measured capacity      | Workload a system demonstrated it could complete under stated conditions. A configuration that admits 1,000 jobs supplies no evidence by itself about serving 1,000 players.                                                                                                         | [Kinds of limit and evidence](../limits/README.md#entry-structure)                                                                                               |
| Implementation tracker | The record of tasks, dependencies, delivery status and remaining gaps.                                                                                                                                                                                                               | [Maintainer work](../../.agents/rules/documentation.md#keep-maintainer-work-synchronized)                                                                        |
| Evidence record        | Identifies the version, workload, observations and limits of an actual check. A checked-off task alone supplies no measurement.                                                                                                                                                      | [Verification records](../../.agents/rules/documentation.md#verification-reports)                                                                                |
| Acceptance criterion   | The outcome a task promises, with the evidence needed to recognize it. A required measurement can finish with a failed result. A required behavior, such as continuing play after reopening a save, must actually work.                                                              | [Planning the outcome](../../.agents/rules/implementation.md#plan-the-outcome-and-evidence)                                                                      |
| Real caller            | The application code or interface that actually uses a behavior, such as the authenticated conversation endpoint that requests an NPC reply.                                                                                                                                         | [Representative scenarios](../../.agents/rules/verification.md#prepare-a-representative-scenario)                                                                |
| Fixture                | A controlled input or dependency supplied for a check. With a fixture returning a known reply, a check can exercise request preparation, transport, application and saving. Evaluating a live model’s choices or latency requires separate evidence.                                 | [Representative scenarios](../../.agents/rules/verification.md#prepare-a-representative-scenario)                                                                |
| Correctness check      | An observation or exercise that establishes whether a particular required behavior works.                                                                                                                                                                                            | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Diagnostic             | An investigation that collects detail to explain a result, for example counting how often a view was encoded.                                                                                                                                                                        | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Clean comparison       | A performance comparison of equivalent work under matched conditions, with diagnostic probes disabled when they would distort timings.                                                                                                                                               | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Implemented            | The behavior exists in the code. Use this status separately from the checks it has passed.                                                                                                                                                                                           | [Project status](../../.agents/rules/documentation.md#project-status-and-completion)                                                                             |
| Qualified              | The implementation passed specified checks on an identified version and workload. A Rust server can qualify for one opening while the TypeScript server remains the default.                                                                                                         | [Project status](../../.agents/rules/documentation.md#project-status-and-completion) · [Rust server decision](../maintainers/completed/2026/rust-game-server.md) |
| Adopted                | A decision has been made to use this implementation for the stated scope.                                                                                                                                                                                                            | [Rust server decision](../maintainers/completed/2026/rust-game-server.md)                                                                                        |
| Control (experiment)   | The reference version or setting against which the proposed change is measured.                                                                                                                                                                                                      | [Isolating a change](../performance/measurement.md#planning-comparisons)                                                                                         |
| Candidate (experiment) | The version or setting containing the change being evaluated. A [simulation candidate](runtime-and-storage.md#changing-and-reading-a-live-world) is pending work within the game.                                                                                                    | [Isolating a change](../performance/measurement.md#planning-comparisons) · [Simulation candidates](runtime-and-storage.md#changing-and-reading-a-live-world)     |
| Comparison arm         | One version or setting under the agreed experiment conditions. Each arm can be run repeatedly.                                                                                                                                                                                       | [Isolating a change](../performance/measurement.md#planning-comparisons)                                                                                         |
| Repetition             | One further run of the same arm under the agreed conditions.                                                                                                                                                                                                                         | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Interleaving           | Running the control and candidate in a planned mixed order on the same worker to limit the influence of when an arm ran.                                                                                                                                                             | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Matched work           | Both arms completed the agreed actions and effects under comparable conditions. Two submitted conversations count as two completed conversations only when both reach the required outcome.                                                                                          | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                       |
| Source identity        | Identifies the exact code used in a run. A branch name alone can point to different code between runs.                                                                                                                                                                               | [Source fidelity and build reuse](../projects/verification-workers-tech-design.md#verified-build-reuse)                                                          |
| Workload identity      | Identifies the scenario, settings and inputs actually exercised.                                                                                                                                                                                                                     | [Source fidelity and build reuse](../projects/verification-workers-tech-design.md#verified-build-reuse)                                                          |
| Build identity         | Identifies the source, dependencies, toolchain, target, flags and other inputs that can affect an executable. The artifact checksum identifies the bytes the build produced.                                                                                                         | [Source fidelity and build reuse](../projects/verification-workers-tech-design.md#verified-build-reuse)                                                          |
| Disposition            | The decision an experiment supports for its agreed scope. A comparison can support retaining a change, rejecting it, or leave its benefit inconclusive. Record incomplete work and unmet behavior separately, even if a capacity refusal already decides that particular experiment. | [Comparison decisions](../performance/measurement.md#planning-comparisons)                                                                                       |

## What was measured?

| Canonical term                      | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                     | Source                                                                                                                                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Measurement window                  | The interval whose work the reported numbers include. Steady play starts after setup and warmup and includes ordinary saves. A return to a running world, a server restart from its latest save, and an administrative restore of an earlier save are distinct journeys.                                                                  | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                                              |
| CPU usage                           | Processor time consumed per elapsed wall second, expressed as a percentage of one logical core. One CPU-second per wall second is 100%. Include any separate server worker processes. Whole-process CPU already includes its threads. Report server, PostgreSQL and client CPU separately.                                                | [CPU accounting](../performance/measurement.md#reporting-results)                                                                                                                                 |
| CPU per completed game-second       | CPU seconds consumed by the named processes divided by game seconds completed in the same window. If the world made no progress, report the CPU consumed and zero completed seconds. The ratio is undefined.                                                                                                                              | [CPU accounting](../performance/measurement.md#reporting-results)                                                                                                                                 |
| Intended simulation time            | Game time the configured clock should advance over the measurement window, including scheduled rate changes or pauses. Unexpected stalls remain in the window.                                                                                                                                                                            | [Game speed and manual offers](../performance/measurement.md#reporting-results)                                                                                                                   |
| Offered simulation time             | Game time that the clock or scenario driver actually asked the simulation to advance.                                                                                                                                                                                                                                                     | [Game speed and manual offers](../performance/measurement.md#reporting-results)                                                                                                                   |
| Completed simulation time           | Game time by which the simulation actually advanced. Finishing the manually offered time establishes completion of that batch.                                                                                                                                                                                                            | [Game speed and manual offers](../performance/measurement.md#reporting-results)                                                                                                                   |
| Achieved game speed                 | Completed game seconds divided by intended game seconds in the same window, expressed as a percentage. Report the percentage as inapplicable if intended progress is zero, or unavailable if it is unknown.                                                                                                                               | [Game speed and manual offers](../performance/measurement.md#reporting-results)                                                                                                                   |
| Drain                               | A period in which already outstanding work is allowed to finish. [Elapsed-time debt](gameplay-and-space.md#time-and-actions) can already exist at the start of a measurement. Report later catch-up separately from progress during ordinary play.                                                                                        | [Reporting progress and debt](../performance/measurement.md#reporting-results) · [Clock and elapsed time](../simulation-time.md#host-and-persistence)                                             |
| Command response latency            | Time from sending a command to the caller receiving the server’s answer. A successful response can precede both visible movement and durable saving.                                                                                                                                                                                      | [Server and client metrics](../performance/measurement.md#reporting-results)                                                                                                                      |
| View receipt latency                | Time from the stated input or publication until the receiving client obtains the affected view update. Name the start and how receipt was observed.                                                                                                                                                                                       | [Server and client metrics](../performance/measurement.md#reporting-results)                                                                                                                      |
| Visible-effect latency              | Time from the stated input until the browser first displays the change, such as the player’s new position. Receiving a message alone establishes only receipt.                                                                                                                                                                            | [Server and client metrics](../performance/measurement.md#reporting-results) · [Browser and actual walking](../maintainers/performance-profiling.md#browser-frames-and-actual-walking)            |
| Last eligible observer receipt      | For one action, the elapsed time from the mover sending input until every expected permitted observer has decoded the changed position. The p95 uses one last-observer time per complete action. A missing recipient leaves that action incomplete. The mover's own update and a browser displaying the change are separate observations. | [Concurrent player publication](../limits/native-runtime-foundations.md#nrf-l11--concurrent-player-publication)                                                                                   |
| Unsaved age                         | At a given moment, time elapsed since the oldest change still awaiting a save was accepted. Sampling this during play shows how far durability trails the live world.                                                                                                                                                                     | [Gameplay timing windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows) · [Ordinary save policy](../save-and-load.md#background-and-synchronous-world-saves) |
| Command-to-durable latency          | Time from the stated command start until the database acknowledges the commit containing that command’s effect. The wait for an ordinary scheduled save counts even when the transaction itself is fast.                                                                                                                                  | [Gameplay timing windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows) · [Ordinary save policy](../save-and-load.md#background-and-synchronous-world-saves) |
| Median (p50)                        | The middle value in an ordered sample. For an even sample size the usual median is the arithmetic mean of the two middle values. Identify the observations and units.                                                                                                                                                                     | [Reporting distributions](../performance/measurement.md#reporting-results)                                                                                                                        |
| Arithmetic mean (average)           | Sum of the observed values divided by their count. State what one observation represents, such as a command or an entire run, and give its units.                                                                                                                                                                                         | [Reporting distributions](../performance/measurement.md#reporting-results)                                                                                                                        |
| 95th percentile (p95)               | The threshold at or below which about 95% of observations fall under the stated percentile method. A pooled p95 across commands and a median of per-run p95 values summarize different samples.                                                                                                                                           | [Reporting distributions](../performance/measurement.md#reporting-results)                                                                                                                        |
| Wall time                           | Elapsed time between the stated start and end. It includes waits, preemption and nested work during that interval.                                                                                                                                                                                                                        | [Timing kinds](../performance/hierarchical-profiling.md#timing-kinds)                                                                                                                             |
| CPU time                            | Time the named threads or processes actually spent using a processor. A request can spend a long time waiting for I/O while consuming little CPU.                                                                                                                                                                                         | [Timing kinds](../performance/hierarchical-profiling.md#timing-kinds)                                                                                                                             |
| Queue wait                          | Time between entering a queue and gaining admission. When the wait occurs inside an operation, its duration is already included in that operation’s wall time.                                                                                                                                                                            | [Timing kinds](../performance/hierarchical-profiling.md#timing-kinds)                                                                                                                             |
| Memory reservation                  | An amount of memory budget set aside for a particular operation or owner. Reserved bytes and physical pages resident in RAM can differ.                                                                                                                                                                                                   | [Allocation and memory measurement](../performance/hierarchical-profiling.md#timing-kinds) · [Host accounting](runtime-and-storage.md#saving-and-continuing-play)                                 |
| Sampled peak RSS                    | The highest sampled operating-system reading of a process’s resident set size (RSS), the physical memory resident for that process. Adding process readings can count shared pages more than once.                                                                                                                                        | [Allocation and memory measurement](../performance/hierarchical-profiling.md#timing-kinds) · [Host accounting](runtime-and-storage.md#saving-and-continuing-play)                                 |
| Settled memory                      | Memory observed after the measured requests finish and normal garbage collection has had time to run. State when it was sampled.                                                                                                                                                                                                          | [Allocation and memory measurement](../performance/hierarchical-profiling.md#timing-kinds) · [Host accounting](runtime-and-storage.md#saving-and-continuing-play)                                 |
| Prepared rows                       | The database rows the application assembled for its writer. Count the rows separately from the bytes of their prepared payloads.                                                                                                                                                                                                          | [SQL and storage accounting](../performance/hierarchical-profiling.md#6-sql-storage-and-asynchronous-work)                                                                                        |
| SQL calls                           | The number of database statements the adapter executes. Report rows returned or affected separately. Two runs can end with identical stored records after different amounts of database work.                                                                                                                                             | [SQL and storage accounting](../performance/hierarchical-profiling.md#6-sql-storage-and-asynchronous-work)                                                                                        |
| WAL growth                          | Bytes added to PostgreSQL’s write-ahead log during the stated window. The log records information PostgreSQL needs for recovery.                                                                                                                                                                                                          | [SQL and storage accounting](../performance/hierarchical-profiling.md#6-sql-storage-and-asynchronous-work)                                                                                        |
| Database growth                     | Change in storage occupied by the measured database over a specified window. Report the separate WAL growth alongside it when measuring writes.                                                                                                                                                                                           | [SQL and storage accounting](../performance/hierarchical-profiling.md#6-sql-storage-and-asynchronous-work)                                                                                        |
| Active area                         | A part of the simulated world where players take actions and exercise local simulation, such as NPC decisions and animal reactions. Additional observers of the same mover add a different workload from additional independently active areas.                                                                                           | [Capacity claims](../performance/measurement.md#reporting-results)                                                                                                                                |
| Eligible observer (delivery metric) | A recipient whose permissions and in-world evidence entitle their client to a particular update. The set is determined for that update.                                                                                                                                                                                                   | [Capacity claims](../performance/measurement.md#reporting-results)                                                                                                                                |

## Who owns a remote run?

| Canonical term              | Meaning in OpenLegend                                                                                                                                                                                                               | Source                                                                                                                                                                                                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Managed verification worker | The remote machine reserved for a verification job, including its local database when used. Inside a game process, a [compute worker](runtime-and-storage.md#scheduling-simulation-work) is a thread doing simulation calculations. | [Managed worker procedure](../../.agents/rules/verification-workers.md#run-lifecycle) · [Game compute pool](runtime-and-storage.md#scheduling-simulation-work)                                                                                                                      |
| Verification runner         | The maintained software that prepares and supervises a verification job and collects its results.                                                                                                                                   | [Managed worker procedure](../../.agents/rules/verification-workers.md#run-lifecycle)                                                                                                                                                                                               |
| Verification campaign       | One submitted plan for the verification runner. Its jobs retain the plan’s declared source, inputs and conditions.                                                                                                                  | [Maintained runner plan and steps](https://github.com/Macrofold/OpenLegend/blob/0d9d2419a3a1951fdd268fc4fd4048d6a6f7efec/.agents/rules/verification-workers.md#current-commands-and-plan) · [Locating the runner](../../.agents/rules/verification-workers.md#current-availability) |
| Verification job            | The part of the runner’s plan that claims an entire worker and runs one or more cases there.                                                                                                                                        | [Maintained runner plan and steps](https://github.com/Macrofold/OpenLegend/blob/0d9d2419a3a1951fdd268fc4fd4048d6a6f7efec/.agents/rules/verification-workers.md#current-commands-and-plan)                                                                                           |
| Verification case           | A unit within a job with its own workspace and declared fresh databases. The runner executes the job’s cases in the specified order.                                                                                                | [Maintained runner plan and steps](https://github.com/Macrofold/OpenLegend/blob/0d9d2419a3a1951fdd268fc4fd4048d6a6f7efec/.agents/rules/verification-workers.md#current-commands-and-plan)                                                                                           |
| Verification step           | An operation inside a case. Steps can share that case’s database, for example to stop a server, restart it and check that the earlier step’s progress was saved.                                                                    | [Maintained runner plan and steps](https://github.com/Macrofold/OpenLegend/blob/0d9d2419a3a1951fdd268fc4fd4048d6a6f7efec/.agents/rules/verification-workers.md#current-commands-and-plan)                                                                                           |
| Worker controller           | The service that decides whether verification work may start and records who owns each worker.                                                                                                                                      | [Claim and execution contract](../projects/verification-workers-tech-design.md#claim-and-execution-contract)                                                                                                                                                                        |
| Worker claim                | The run’s exclusive right to use a specified worker. A stopped machine can still be claimed.                                                                                                                                        | [Claim and execution contract](../projects/verification-workers-tech-design.md#claim-and-execution-contract)                                                                                                                                                                        |
| Worker lease                | The time-bounded authority attached to a claim. An expired lease requires recovery before the worker can be reused.                                                                                                                 | [Claim and execution contract](../projects/verification-workers-tech-design.md#claim-and-execution-contract)                                                                                                                                                                        |
| Claim generation            | The identifier distinguishing the current worker claim from earlier claims on the same machine. A previous owner cannot act on a newer claim.                                                                                       | [Claim and execution contract](../projects/verification-workers-tech-design.md#claim-and-execution-contract)                                                                                                                                                                        |
| Run deadline                | The hard elapsed-time limit for finishing the run. A heartbeat cannot extend it.                                                                                                                                                    | [Managed run lifecycle](../../.agents/rules/verification-workers.md#run-lifecycle) · [Worker operating defaults](../projects/verification-workers-tech-design.md#operational-defaults)                                                                                              |
| Worker heartbeat            | A signal to the supervisor that the owner of an active claim is still present. A heartbeat does not authorize repeating the work.                                                                                                   | [Managed run lifecycle](../../.agents/rules/verification-workers.md#run-lifecycle) · [Worker operating defaults](../projects/verification-workers-tech-design.md#operational-defaults)                                                                                              |
| Result collection           | Retrieving the run’s identified outputs and checking the required artifacts and their checksums.                                                                                                                                    | [Worker lifecycle and interrupted campaigns](../../.agents/rules/verification-workers.md#run-lifecycle)                                                                                                                                                                             |
| Worker release              | Returning a worker to the available pool after verified cleanup. Stopping compute and retiring the machine and storage are separate operations.                                                                                     | [Worker lifecycle and interrupted campaigns](../../.agents/rules/verification-workers.md#run-lifecycle)                                                                                                                                                                             |
| Worker quarantine           | Keeping a worker unavailable when its cleanup or ownership cannot be verified.                                                                                                                                                      | [Worker lifecycle and interrupted campaigns](../../.agents/rules/verification-workers.md#run-lifecycle)                                                                                                                                                                             |
| Run outcome                 | The execution status recorded by the runner, such as completed, failed, interrupted or never started. A completed script can still have missed a required movement update.                                                          | [Runner outcomes and acceptance](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                                                                                           |
| Verification acceptance     | The determination of whether observed work satisfied the required check. A required measurement can record a failure. Missing evidence leaves the corresponding behavior unverified.                                                | [Runner outcomes and acceptance](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                                                                                           |
| Task spending ceiling       | The total authorized spending across the assigned task, its related follow-ups and all delegates.                                                                                                                                   | [Spending authority and reconciliation](../../.agents/rules/verification.md#spending)                                                                                                                                                                                               |
| Cloud allocation            | The part of a task’s authorized spending set aside for managed cloud work. Related work shares the remaining task balance.                                                                                                          | [Cloud allocation](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                                                                                                         |
| Cost reservation            | Money set aside for outstanding work before its actual cost is known. Reconciliation replaces the corresponding hold with the cost attributable to that work and keeps any unresolved amount visible.                               | [Spending authority and reconciliation](../../.agents/rules/verification.md#spending) · [Cloud allocation](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                 |
