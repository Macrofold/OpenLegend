# Measurement and delivery

## What does a check establish?

| Canonical term                                               | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                                     | Source                                                                                                                                                                        |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feature specification, technical design and limits inventory | The feature specification describes what the player or operator should experience. The technical design describes how to deliver it. The limits record which constraints apply, their reasons and when to revisit them. A proposed limit describes a choice still under consideration.                                                                    | [Project status and design ownership](../../.agents/rules/documentation.md#project-status-and-completion) · [Limits inventory](../limits/README.md)                           |
| Configured allowance, external quota and measured capacity   | An allowance is a limit set in our configuration. An external quota is set by a provider or platform. Measured capacity describes the workload that actually completed under specified conditions. A setting that admits 1,000 jobs does not establish that the game can serve 1,000 simultaneous players.                                                | [Kinds of limit and evidence](../limits/README.md#entry-structure)                                                                                                            |
| Implementation tracker and evidence record                   | The tracker lists tasks, dependencies, current status and gaps. An evidence record identifies the version, workload, observations and limits of an actual check. A design target or checked-off task by itself supplies no measurement.                                                                                                                   | [Maintainer work](../../.agents/rules/documentation.md#keep-maintainer-work-synchronized) · [Verification records](../../.agents/rules/documentation.md#verification-reports) |
| Acceptance criterion                                         | The outcome a task promises, with the evidence needed to recognize it. A required measurement can finish with a failed result. A required behavior, such as continuing play after reopening a save, must actually work.                                                                                                                                   | [Planning the outcome](../../.agents/rules/implementation.md#plan-the-outcome-and-evidence)                                                                                   |
| Real caller and fixture                                      | The real caller is the application path that uses the behavior, for example the authenticated conversation endpoint. A fixture supplies controlled inputs or dependencies. A controlled provider can exercise preparation, transport, reply application and saving. Live model quality and provider latency require their own evidence.                   | [Representative scenarios](../../.agents/rules/verification.md#prepare-a-representative-scenario)                                                                             |
| Correctness check, diagnostic and clean comparison           | A correctness check asks whether the promised behavior works. A diagnostic collects extra detail to explain a result. A clean comparison measures matched versions with those diagnostic probes disabled when they would distort the result.                                                                                                              | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                                    |
| Implemented, qualified and adopted                           | Implemented means the behavior exists in the code. Qualified identifies which checks passed on which workload and version. Adopted records a decision to use the implementation for a stated scope. For example, a Rust server can qualify for one opening while TypeScript remains the default.                                                          | [Project status](../../.agents/rules/documentation.md#project-status-and-completion) · [Rust server decision](../maintainers/completed/2026/rust-game-server.md)              |
| Control, candidate and arm                                   | The control is the version used for comparison. The candidate is the version with the change being evaluated. Each arm consists of runs of one version under the agreed conditions. In simulation code a candidate has a different meaning, a set of proposed changes to the world.                                                                       | [Isolating a change](../performance/measurement.md#planning-comparisons) · [Simulation candidates](runtime-and-storage.md#changing-and-reading-a-live-world)                  |
| Repetition, interleaving and matched work                    | A repetition reruns an arm. Interleaving alternates which arm runs at scheduled points on the same worker. Matched work means both versions completed the agreed actions and effects under comparable conditions. Sending two conversations counts as two completed conversations only if both reach the required outcome.                                | [Planning comparisons](../performance/measurement.md#planning-comparisons)                                                                                                    |
| Source, workload and build identity                          | Source identity identifies the exact code used. Workload identity identifies the scenario, settings and inputs exercised. Build identity includes source plus the dependencies, toolchain, target, flags and other inputs that can change the executable. An artifact checksum identifies the resulting bytes. A branch name alone can move between runs. | [Source fidelity and build reuse](../projects/verification-workers-tech-design.md#verified-build-reuse)                                                                       |
| Disposition                                                  | The decision an experiment supports for its agreed scope. A comparison can support retaining a change, rejecting it, or leave its benefit inconclusive. Record incomplete work and unmet behavior separately, even if a capacity refusal already decides that particular experiment.                                                                      | [Comparison decisions](../performance/measurement.md#planning-comparisons)                                                                                                    |

## What was measured?

| Canonical term                                    | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Source                                                                                                                                                                                            |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Measurement window                                | The interval whose work the reported numbers include. Steady play starts after setup and warmup and includes ordinary saves. A return to a running world, a server restart from its latest save, and an administrative restore of an earlier save are distinct journeys.                                                                                                                                                                                                  | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                                              |
| CPU usage and CPU per completed game-second       | For one process or named group, 100% of one logical core means one CPU-second per elapsed wall second. Whole-process server CPU includes its native and worker threads. PostgreSQL CPU and client CPU have separate owners. CPU seconds for the named group divided by completed game seconds measures the compute cost of progress. This ratio is undefined when no game time advances.                                                                                  | [CPU accounting](../performance/measurement.md#reporting-results)                                                                                                                                 |
| Intended, offered and completed simulation time   | Intended time is what the configured clock should advance in the window. Offered time is what the clock or driver actually asks the simulation to advance. Completed time is the advance the simulation accepts. Achieved game speed is completed time divided by intended time, expressed as a percentage. Finishing a manually offered batch establishes how much of that batch completed.                                                                              | [Game speed and manual offers](../performance/measurement.md#reporting-results)                                                                                                                   |
| Elapsed-time debt and drain                       | Debt is game time the simulation still owes from earlier clock advances. It can carry over from before the measured window. A drain allows outstanding work to finish. Later catch-up is a separate observation from keeping pace during ordinary play.                                                                                                                                                                                                                   | [Reporting progress and debt](../performance/measurement.md#reporting-results) · [Clock and elapsed time](../simulation-time.md#host-and-persistence)                                             |
| Command response, view receipt and visible effect | Command response ends when the caller receives the server's answer. View receipt ends when the receiving client obtains the changed view. Visible effect ends when the browser displays the result, such as the player's new position. Name the start and end observed for each latency.                                                                                                                                                                                  | [Server and client metrics](../performance/measurement.md#reporting-results) · [Browser and actual walking](../maintainers/performance-profiling.md#browser-frames-and-actual-walking)            |
| Last eligible observer receipt                    | For one action, the elapsed time from the mover sending input until every expected permitted observer has decoded the changed position. The p95 uses one last-observer time per complete action. A missing recipient leaves that action incomplete. The mover's own update and a browser displaying the change are separate observations.                                                                                                                                 | [Concurrent player publication](../limits/native-runtime-foundations.md#nrf-l11--concurrent-player-publication)                                                                                   |
| Save age and durability latency                   | Unsaved age is the elapsed time since the oldest still-unsaved change was accepted. It can be sampled repeatedly between saves. Command-to-durable latency follows one command until the transaction covering it is acknowledged. State the clock and endpoints used. Waiting for a scheduled background save contributes to the second measure even when the database transaction itself is fast.                                                                        | [Gameplay timing windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows) · [Ordinary save policy](../save-and-load.md#background-and-synchronous-world-saves) |
| Median, mean and p95                              | The median is the middle ordered value, conventionally the mean of the two middle values for an even count. The arithmetic mean is the sum divided by the count. The p95 is the value at or below which about 95% of observations fall, using the reported percentile method. Say whether an observation is one command, one observer or a whole run, and report units. A p95 across all commands answers a different question from a median of several runs' p95 values. | [Reporting distributions](../performance/measurement.md#reporting-results)                                                                                                                        |
| Wall time, CPU time and queue wait                | Wall time is the elapsed time a clock measures. CPU time counts actual processor work across the named threads or processes. A request can wait for admission or I/O with little CPU. A parent operation's elapsed time already includes its nested waits and work.                                                                                                                                                                                                       | [Timing kinds](../performance/hierarchical-profiling.md#timing-kinds)                                                                                                                             |
| Reservation, peak RSS and settled memory          | A memory reservation accounts for bytes admitted to a particular owner. RSS is the operating system's measure of physical pages resident for a process. Its sampled peak is the highest observed sample. Memory after requests finish and normal garbage collection runs helps show what remains held. Summing process readings may count shared pages more than once.                                                                                                    | [Allocation and memory measurement](../performance/hierarchical-profiling.md#timing-kinds) · [Host accounting](runtime-and-storage.md#saving-and-continuing-play)                                 |
| Prepared rows, SQL work, WAL and database growth  | Prepared rows and payload bytes measure what the application assembles for its writer. SQL calls and rows returned or affected measure database activity. Write-ahead log (WAL) bytes measure PostgreSQL's recovery log. Database growth measures the change in occupied database storage over the window. Equal final records can have different costs on all four measures.                                                                                             | [SQL and storage accounting](../performance/hierarchical-profiling.md#6-sql-storage-and-asynchronous-work)                                                                                        |
| Active area and eligible observer                 | An active area has players taking actions and the local simulation those actions exercise. An eligible observer has permission and the in-world evidence to receive a particular update. Many people watching one mover measure delivery to many connections. Several separated movers exercising their own NPCs and animals measure a different source of load.                                                                                                          | [Capacity claims](../performance/measurement.md#reporting-results)                                                                                                                                |

## Who owns a remote run?

| Canonical term                                      | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                            | Source                                                                                                                                                                                                                                                                              |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Managed verification worker and runner              | The worker is the remote machine reserved for a verification job, including its local database when used. The runner is the maintained software that prepares, supervises and collects that job. A compute worker inside a game-server process is a thread doing simulation work.                                                | [Managed worker procedure](../../.agents/rules/verification-workers.md#run-lifecycle) · [Game compute pool](runtime-and-storage.md#scheduling-simulation-work)                                                                                                                      |
| Campaign, job, case and step                        | In the maintained runner a campaign is one submitted plan. Each job claims a whole worker while it runs its cases. Each ordered case has its own workspace and declared fresh databases. Steps within one case may share those databases, for example to play, stop the server, reopen and verify saved progress.                | [Maintained runner plan and steps](https://github.com/Macrofold/OpenLegend/blob/0d9d2419a3a1951fdd268fc4fd4048d6a6f7efec/.agents/rules/verification-workers.md#current-commands-and-plan) · [Locating the runner](../../.agents/rules/verification-workers.md#current-availability) |
| Controller, claim, lease and generation             | The controller admits work and tracks ownership. A claim gives one run exclusive use of a worker. Its lease limits how long that authority lasts. Its generation distinguishes the current claim from an older one. A stopped machine can still be claimed and an expired lease needs recovery before the machine can be reused. | [Claim and execution contract](../projects/verification-workers-tech-design.md#claim-and-execution-contract)                                                                                                                                                                        |
| Deadline and heartbeat                              | A deadline bounds elapsed time for a run. A heartbeat tells its supervisor the owner is still present. A successful heartbeat grants neither extra time beyond the hard deadline nor permission to repeat a failed experiment.                                                                                                   | [Managed run lifecycle](../../.agents/rules/verification-workers.md#run-lifecycle) · [Worker operating defaults](../projects/verification-workers-tech-design.md#operational-defaults)                                                                                              |
| Collection, release and quarantine                  | Collection retrieves the identified results and verifies the required artifacts. Release returns the worker to the pool after cleanup. Quarantine keeps a machine unavailable when cleanup or ownership cannot be verified. Release, stopping compute and retiring the machine and its storage are distinct events.              | [Worker lifecycle and interrupted campaigns](../../.agents/rules/verification-workers.md#run-lifecycle)                                                                                                                                                                             |
| Run outcome and acceptance                          | The runner records whether execution completed, failed, was interrupted or never started. Acceptance asks whether the promised work was observed. A script can exit successfully while its player never sees the required movement. A missing measurement stays unavailable.                                                     | [Runner outcomes and acceptance](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                                                                                           |
| Task ceiling, cloud allocation and cost reservation | The task ceiling is the total authorized spending across related work and delegates. A cloud allocation sets aside part of it for the worker controller. A cost reservation sets aside money for outstanding work. When the actual charge becomes known it replaces the corresponding reservation.                               | [Spending authority and reconciliation](../../.agents/rules/verification.md#spending) · [Cloud allocation](../projects/verification-workers-tech-design.md#runner-input-and-output)                                                                                                 |
