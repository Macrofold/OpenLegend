## Which program runs the game?

| Canonical term              | Meaning in OpenLegend                                                                                                                                                                                                                                 | Source                                                                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript server           | The Node server running the TypeScript domain simulation. The default development launch uses this path. Earlier comparisons label this arm **Source**.                                                                                               | [Development launch](../../package.json) · [Server paths](../maintainers/completed/2026/rust-game-server.md)                                   |
| Node-hosted Rust simulation | The Rust simulation runs in the Node server process through a compiled addon. Rust changes live simulation state. Node handles network requests and database calls. Earlier TypeScript versus Rust addon comparisons label this arm **Native**.       | [Node application boundary](../projects/native-simulation-core-tech-design.md#4-nativeapplication-boundary)                                    |
| Stand-alone Rust server     | The Rust executable owns both the application and the linked Rust simulation. It handles requests, PostgreSQL and provider transport directly. The browser still runs its JavaScript client. Adoption evidence covers the specified playable opening. | [Binary and launch modes](../../native/game-server/src/main.rs) · [Measured adoption scope](../maintainers/completed/2026/rust-game-server.md) |
| Rule-controlled behavior    | Behavior chosen by an installed world rule, such as an animal fleeing a threat. Older profiling tools call this **native** even when the rules run in TypeScript.                                                                                     | [Existing TypeScript and Rust profilers](../maintainers/performance-profiling.md)                                                              |
| Game server                 | The program that authenticates players, admits requests, schedules work, saves outcomes and sends each player the information they may see.                                                                                                           | [Server and simulation responsibilities](../projects/completed/2026/rust-game-server-tech-design.md#boundary-and-implementation-order)         |
| Simulation                  | The part of the game that applies the installed world’s rules and determines what happens, such as how far a character moves.                                                                                                                         | [Server and simulation responsibilities](../projects/completed/2026/rust-game-server-tech-design.md#boundary-and-implementation-order)         |
| Client                      | The program on the player’s device. It displays the permitted view and sends requests, such as asking the server to move a character.                                                                                                                 | [Server and simulation responsibilities](../projects/completed/2026/rust-game-server-tech-design.md#boundary-and-implementation-order)         |

A new world starts from an [opening](worlds-and-creation.md#creating-or-changing-a-world) and uses its [installed definitions](worlds-and-creation.md#what-a-world-supplies). Reopening a save resumes the existing inhabitants and their progress. [Starting-world content](../save-and-load.md#starting-world-content-reconciliation) · [World and engine boundary](../projects/native-simulation-core-tech-design.md#world-and-engine-boundary)

## Changing and reading a live world

| Canonical term                 | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                              | Source                                                                                                                                                                                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Live state                     | The facts currently accepted in a running world. A player’s latest move can already be part of live state while its database save is pending.                                                                                                                                                                                      | [Canonical working state](../projects/native-simulation-core-tech-design.md#31-canonical-working-state)                                                                                                                                         |
| Mutation authority             | The component responsible for validating and applying a particular change to live state. For example, the simulation determines a character’s new position after a move request.                                                                                                                                                   | [Canonical working state](../projects/native-simulation-core-tech-design.md#31-canonical-working-state)                                                                                                                                         |
| Admission                      | The decision that an operation may begin with its required resources. A command admitted for execution can still fail a game rule.                                                                                                                                                                                                 | [Admission and capacity](../performance/scheduling.md#bounded-admission)                                                                                                                                                                        |
| Execution                      | The work of carrying out an operation under the applicable rules and computing its result.                                                                                                                                                                                                                                         | [Candidate acceptance](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                                  |
| Acceptance (world change)      | The point when the responsible part of the simulation makes the result of an operation part of live state. Durability depends on the database commit.                                                                                                                                                                              | [Candidate acceptance](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                                  |
| Simulation candidate           | The changes one operation proposes for the live world. Acceptance makes them part of live state.                                                                                                                                                                                                                                   | [Candidate settlement and rollback](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                     |
| Undo journal                   | The record of what the simulation needs to reverse changes from an unfinished operation, such as an actor’s earlier position.                                                                                                                                                                                                      | [Candidate settlement and rollback](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                     |
| Operation checkpoint           | A recorded point to which the simulation can roll back within an unfinished operation. It records undo and effect-list positions and the random and identity allocation state needed to restore that point.                                                                                                                        | [Candidate settlement and rollback](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                     |
| Rollback                       | Restoring state to where an unfinished operation or one of its steps began. The simulation restores affected clocks, allocated identities and random state as well as gameplay facts, preserving work accepted before that point.                                                                                                  | [Candidate settlement and rollback](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                                                     |
| Capture                        | The values retained for a particular reader from a coherent state of the world, such as the facts needed to prepare one player’s view.                                                                                                                                                                                             | [Stable consumer products](../projects/native-simulation-core-tech-design.md#61-stable-consumer-products-without-a-permanent-immutable-world-graph)                                                                                             |
| Read cut                       | The point in accepted world history that a read must describe. If a player is walking while saved history is being read, the reader combines only saved and pending facts belonging to its selected cut.                                                                                                                           | [Mixed-server read cut](../../apps/server/src/native-read-cut.ts)                                                                                                                                                                               |
| Database snapshot              | The committed database state visible to a particular read or transaction. When a world read also needs accepted but unsaved changes, its reader combines the snapshot with the pending changes through the requested read cut.                                                                                                     | [Database and pending reads](../projects/native-simulation-core-tech-design.md#62-direct-changed-record-saving)                                                                                                                                 |
| Timeline                       | One history of a world. Restoring an earlier checkpoint changes the timeline, so a view captured before the restore can refer to old facts even if a record’s revision number matches.                                                                                                                                             | [Restore and authority](../save-and-load.md#loading-as-an-authority-transition)                                                                                                                                                                 |
| Captured revision              | The version of a particular record or set of data at the time of a read. Readers compare the version for the relevant source and timeline. [Identity and references](identity-and-references.md) explains which identities can change.                                                                                             | [Checks when combining reads](../../apps/server/src/native-read-cut.ts)                                                                                                                                                                         |
| Pending read overlay           | Accepted changes through a reader's selected cut that are still needed to supplement the database snapshot. A reader can hold these changes independently while a save completes. Reading the latest database state again would answer a different question.                                                                       | [Capture and ownership of a read cut](../../apps/server/src/native-read-cut.ts)                                                                                                                                                                 |
| Command epoch                  | A server-issued generation and token that identify a retry window for player commands in one world. Recovering an earlier result also requires the original request identity, timeline and [current authority](access-and-participation.md#who-can-do-what).                                                                       | [Player command epoch](../../native/game-server/src/command_epoch.rs) · [Gameplay receipt lookup](../../apps/server/src/command-receipts.ts)                                                                                                    |
| Currentness check              | Checks whether the facts or permissions used to prepare a result still hold. An NPC forgetting the observation used for a reply can invalidate it. A clock tick matters if it changes a required fact or crosses a relevant deadline. The NPC scheduling design calls its check on the inputs to a decision a **freshness check**. | [Checking before use](../projects/native-simulation-core-tech-design.md#4-nativeapplication-boundary) · [NPC scheduling inputs](../projects/native-runtime-foundations-bridge.md#nrf13--prepare-the-parts-of-an-npc-wakeup-its-caller-consumes) |
| Disclosure                     | Handing permitted information to its recipient. For a player view in the Node-hosted Rust path, a synchronous disclosure lease keeps permission valid through payload selection, encoding and handoff to transport.                                                                                                                | [Native/application boundary](../projects/native-simulation-core-tech-design.md#4-nativeapplication-boundary) · [Rust player stream](../../native/game-server/src/player_stream.rs)                                                             |
| Response ticket                | The Rust simulation keeps the permitted input and prepared choices for one NPC decision request. Its ticket binds the returned answer to that request and tracks whether it can still be applied. The server can receive an answer after the ticket is cancelled or its evidence changes.                                          | [Rust ticket and application states](../../native/simulation/src/runtime/npc/bindings.rs) · [Cognition boundary](../projects/native-simulation-core-tech-design.md#cognition-boundary-and-equivalence)                                          |
| Player view                    | The information the server prepares for one player session about its character and the world, including perceived subjects and available controls. The character’s observations and the session’s current permissions determine what it may contain.                                                                               | [Player view publication](../projects/completed/2026/rust-game-server-tech-design.md#5-publish-only-what-each-player-may-see-rgs05)                                                                                                             |
| Player-view publication        | The server selects a permitted update and hands it to the connection for the intended recipient. Use **acceptance** for the earlier step that makes a change part of live world state.                                                                                                                                             | [Player view publication](../projects/completed/2026/rust-game-server-tech-design.md#5-publish-only-what-each-player-may-see-rgs05)                                                                                                             |
| Player-view delivery           | Receipt of the published update by the client. Rendering the change on the player’s screen happens separately. Specify the endpoint measured when reporting latency.                                                                                                                                                               | [Player view publication](../projects/completed/2026/rust-game-server-tech-design.md#5-publish-only-what-each-player-may-see-rgs05)                                                                                                             |
| Server-sent event stream (SSE) | A connection on which the server can send a sequence of events to one client. A view that has not changed can require no outgoing update.                                                                                                                                                                                          | [Stream selection and encoding](../../native/game-server/src/player_stream.rs)                                                                                                                                                                  |
| View patch                     | Changes from the preceding permitted view on the same stream. Applying the patch to that specific view produces the new view.                                                                                                                                                                                                      | [Stream selection and encoding](../../native/game-server/src/player_stream.rs)                                                                                                                                                                  |
| View reset                     | An update containing a complete, freshly authorized player view. The server can send a reset when a client first connects or when a patch cannot be used.                                                                                                                                                                          | [Stream selection and encoding](../../native/game-server/src/player_stream.rs)                                                                                                                                                                  |

## Scheduling simulation work

| Canonical term                    | Meaning in OpenLegend                                                                                                                                                                                                           | Source                                                                                                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Compute worker                    | A thread that runs ready simulation calculations, such as one range of work assigned by the host.                                                                                                                               | [Host compute pool](../../native/world-host/src/pool.rs)                                                                                                                                                                          |
| Compute pool                      | The bounded set of threads available to perform ready simulation calculations. Database and provider requests wait outside this pool.                                                                                           | [Host compute pool](../../native/world-host/src/pool.rs)                                                                                                                                                                          |
| Execution lane                    | An ordering rule for operations that compete for a resource, such as writes to the same world. An operation can wait for its turn before a compute worker starts it.                                                            | [Scheduling and work placement](../performance/scheduling.md#work-placement-and-buffering)                                                                                                                                        |
| Wake signal                       | A bounded notification that work is available for a specific consumer. For example, it can prompt the NPC scheduler to check for eligible work. The consumer still looks up the underlying evidence and decides whether to act. | [Events and reactions, six concepts](../events-perception-and-reactions.md#2-the-six-distinct-concepts)                                                                                                                           |
| Dirty work                        | Work whose previous result may need updating because an input changed. Movement can make a previous observation outdated before its next scheduled check.                                                                       | [Triggered work](../performance/scheduling.md#triggered-background-work)                                                                                                                                                          |
| Due work                          | Work whose scheduled time has arrived, such as an attention check whose deadline has passed.                                                                                                                                    | [Work selection](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm) · [Triggered work](../performance/scheduling.md#triggered-background-work)                                                    |
| Relevant work                     | Work that could affect the operation under consideration, such as checking bodies within reach of a moving character.                                                                                                           | [Work selection](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm)                                                                                                                               |
| Compute range                     | In the single-machine design, a bounded group of independent calculations using one coherent input. Whether splitting a particular workload across workers helps requires measurement.                                          | [Scheduling and disjoint work](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm) · [Measured work and limits](../limits/native-simulation-core.md#nsc-l02--compute-capacity-and-job-granularity) |
| Inline execution                  | The calling thread performs the calculation itself. A small range can take less work to run inline than to send to another worker.                                                                                              | [Scheduling and disjoint work](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm)                                                                                                                 |
| Join (parallel work)              | The point at which all calculations required by a dependent phase must finish before that phase can proceed.                                                                                                                    | [Scheduling and disjoint work](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm)                                                                                                                 |
| Cell (distributed design)         | A proposed unit of ownership for part of one world’s state. Several cells can share a machine. A creature can cross a cell boundary and stay in the same world.                                                                 | [Cells as units of ownership](../projects/native-simulation-core-tech-design.md#71-cells-are-ownership-units-not-gameplay-rooms)                                                                                                  |
| Read overlap (distributed design) | State owned by a neighboring cell that a proposed cell needs to read to calculate an interaction. Reading across the boundary leaves responsibility for changes with the authorized owner.                                      | [Read overlap](../projects/native-simulation-core-tech-design.md#72-read-overlap-and-interaction-ownership)                                                                                                                       |
| Backpressure                      | A slow consumer or full queue restricts additional work. For example, a server can defer sending more data to a connection with outstanding writes.                                                                             | [Publication under backpressure](../performance/scheduling.md#bounded-batching-backpressure-and-publication)                                                                                                                      |
| Cancellation                      | A request to stop outstanding work or withhold future output. If an outside service already accepted a request, its result and cost still need reconciliation.                                                                  | [Provider outcomes](../ai-providers.md#receipts-outcomes-and-accounting)                                                                                                                                                          |

## Saving and continuing play

| Canonical term          | Meaning in OpenLegend                                                                                                                                                                                                                                                                                               | Source                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Durable commit          | PostgreSQL has committed the transaction covering an accepted change. A player can see movement before that commit.                                                                                                                                                                                                 | [Background and synchronous saves](../save-and-load.md#background-and-synchronous-world-saves) · [Rust live saves](../../native/game-server/src/live_save.rs)               |
| Background save         | The server writes accepted world changes to storage on its ordinary schedule while play continues. The save is due relative to the first unsaved change, so later commands do not restart its timer.                                                                                                                | [Background and synchronous saves](../save-and-load.md#background-and-synchronous-world-saves)                                                                              |
| Save acknowledgement    | The database’s confirmation to the server that it committed a specified set of changes. Resources held only for that save can then be released. An independent reader can retain its own reference.                                                                                                                 | [Background and synchronous saves](../save-and-load.md#background-and-synchronous-world-saves) · [Rust live saves](../../native/game-server/src/live_save.rs)               |
| Changed record          | A logical record that an accepted operation created, edited or deleted. Saving the change can insert, update or remove a database row.                                                                                                                                                                              | [Changed-record saving](../projects/native-simulation-core-tech-design.md#62-direct-changed-record-saving)                                                                  |
| Save prefix             | All pending changes in order through a specified accepted change. Acknowledging that prefix can release its save resources while newer changes remain pending.                                                                                                                                                      | [Changed-record saving](../projects/native-simulation-core-tech-design.md#62-direct-changed-record-saving) · [Pending prefix](../../apps/server/src/native-pending-save.ts) |
| Pending save            | Accepted changes and the data held to persist them until the database acknowledges the corresponding save.                                                                                                                                                                                                          | [Pending prefix](../../apps/server/src/native-pending-save.ts)                                                                                                              |
| Gameplay receipt        | The stored result identified by a world and command ID. To recover it without repeating the effect, the retry must match the original input and pass the checks for that result’s scope and timeline. [Provider receipt](characters-and-cognition.md#what-an-ai-request-does) covers the separate external attempt. | [Gameplay receipts](../../apps/server/src/command-receipts.ts) · [Provider accounting](../ai-providers.md#receipts-outcomes-and-accounting)                                 |
| Gameplay checkpoint     | A coherent saved copy of the world and the personal evidence required to resume it. An operator can select a checkpoint for recovery.                                                                                                                                                                               | [Capturing and publishing a save](../save-and-load.md#capturing-and-publishing-a-save)                                                                                      |
| Checkpoint recovery     | Atomically replacing gameplay state from a validated checkpoint while preserving current access, privacy protections and financial authority.                                                                                                                                                                       | [Loading as an authority transition](../save-and-load.md#loading-as-an-authority-transition)                                                                                |
| Reconnect               | A client returns to a running world and receives the view its current permissions allow.                                                                                                                                                                                                                            | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                        |
| Cold reopen             | A new server process resumes the latest durable world from storage. Measure this startup separately from a client reconnecting to an already running server.                                                                                                                                                        | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                        |
| Checkpoint rewind       | An authorized operator restores an earlier gameplay checkpoint, deliberately returning the simulation to an earlier point. Ordinary player return uses the running world.                                                                                                                                           | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                        |
| Canonical record        | An authoritative stored record of facts needed for continued play.                                                                                                                                                                                                                                                  | [State ownership and save scope](../save-and-load.md#state-ownership-and-save-scope)                                                                                        |
| Derived index           | A lookup structure computed from authoritative data. It can be rebuilt when that data contains all required facts.                                                                                                                                                                                                  | [State ownership and save scope](../save-and-load.md#state-ownership-and-save-scope)                                                                                        |
| Hydration               | Reading a stored record into working memory when a supported operation needs it. A record can remain valid on disk while absent from RAM.                                                                                                                                                                           | [Partial residency](../projects/native-simulation-core-tech-design.md#partial-residency-and-hydration)                                                                      |
| Temporal evidence block | An ordered group of changes or occurrences a particular observer received. The block records the actor, life and evidence history it belongs to. Sharing the underlying values leaves each observer’s evidence separate.                                                                                            | [Shared temporal evidence](../save-and-load.md#shared-temporal-evidence-continuation)                                                                                       |
| Stable value            | An immutable piece of content that multiple evidence records can reference, such as a shared description. Each observer still needs their own evidence of having received it.                                                                                                                                       | [Shared temporal evidence](../save-and-load.md#shared-temporal-evidence-continuation)                                                                                       |
| Cursor                  | A stored position from which a particular reader or processor can continue through an ordered sequence.                                                                                                                                                                                                             | [Speech eligibility and ordering](../memory-architecture.md)                                                                                                                |
| Watermark               | A marker of how far a specific sequence has been seen or considered. For example, memory processing can have examined awareness through one position while an earlier unfinished utterance becomes eligible for interpretation only later.                                                                          | [Speech eligibility and ordering](../memory-architecture.md) · [Temporal references](../identity-and-references.md#selected-shared-temporal-references)                     |
| Resident state          | World state held in RAM for ongoing simulation. The host accounts separately for temporary work and changes awaiting a save.                                                                                                                                                                                        | [Canonical working state](../projects/native-simulation-core-tech-design.md#31-canonical-working-state) · [Native host limits](../limits/native-simulation-core.md)         |
| Transient workspace     | Memory used while performing a bounded operation, such as preparing a capture or recording undo data.                                                                                                                                                                                                               | [Native host limits](../limits/native-simulation-core.md)                                                                                                                   |
| Pending-save memory     | Memory the save owner holds for accepted changes awaiting database acknowledgement. An independent reader can retain shared data after that acknowledgement. Reserved bytes and the process’s resident memory are measured separately.                                                                              | [Native host limits](../limits/native-simulation-core.md)                                                                                                                   |
