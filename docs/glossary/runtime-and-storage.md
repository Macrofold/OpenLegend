## Which program runs the game?

| Canonical term                                      | Meaning in OpenLegend                                                                                                                                                                                                                                                                         | Source                                                                                                                                                                                         |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript server (Source)                          | The Node server that runs the TypeScript domain simulation. This is the default game path. Older comparison reports call it **Source**. Elsewhere, a source can mean the event or observation supporting a fact.                                                                              | [Server paths](../projects/completed/2026/rust-game-server-tech-design.md#boundary-and-implementation-order)                                                                                   |
| Node-hosted Rust simulation (Native in comparisons) | Node owns the application, including the network and database calls. A compiled addon connects it to the Rust simulation, which alone changes the live simulated world in this path. The two parts run in the same process.                                                                   | [Node application boundary](../projects/native-simulation-core-tech-design.md#4-nativeapplication-boundary)                                                                                    |
| Stand-alone Rust server                             | The Rust executable owns both the application and the linked Rust simulation. It handles requests, PostgreSQL and provider transport directly. The browser still runs its JavaScript client. Adoption evidence covers the specified playable opening.                                         | [Binary and launch modes](../../native/game-server/src/main.rs) · [Measured adoption scope](../maintainers/completed/2026/rust-game-server.md)                                                 |
| Native game behavior                                | A game rule or reaction executed by the simulation itself, such as an animal reacting to a received threat. Here _native_ identifies a rule-driven decision. It can run in TypeScript or Rust. Name the language and server path when discussing performance.                                 | [Existing TypeScript and Rust profilers](../maintainers/performance-profiling.md)                                                                                                              |
| Game server, simulation, client                     | The server authenticates the player, admits requests, schedules work, persists outcomes and publishes the permitted view. The simulation applies the installed world's rules and owns the resulting facts. The client displays its permitted view and can ask the server to move a character. | [Server and simulation responsibilities](../projects/completed/2026/rust-game-server-tech-design.md#boundary-and-implementation-order)                                                         |
| Opening and installed definitions                   | The opening supplies starting inhabitants, objects and conditions for a new world. Installed definitions supply the rules and vocabulary that apply throughout play. Reopening a saved world resumes its existing inhabitants and progress.                                                   | [Starting-world content](../save-and-load.md#starting-world-content-reconciliation) · [World and engine boundary](../projects/native-simulation-core-tech-design.md#world-and-engine-boundary) |

## Changing and reading a live world

| Canonical term                        | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                        | Source                                                                                                                                                                                                                  |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Live state and mutation authority     | The current accepted facts of a running world. Its simulation has a single authority for each change. A browser view, model answer or database read can supply input but cannot change those facts directly.                                                                                                                                 | [Canonical working state](../projects/native-simulation-core-tech-design.md#31-canonical-working-state)                                                                                                                 |
| Admission, execution and acceptance   | Admission checks whether a particular operation may begin and whether its resources are available. Execution computes its result. On acceptance, the responsible owner makes that result part of the live world. An admitted command can still fail its game preconditions.                                                                  | [Admission and capacity](../performance/scheduling.md#bounded-admission) · [Candidate acceptance](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                               |
| Candidate, undo journal and rollback  | A simulation candidate holds the changes proposed by one operation. Its undo journal retains what the simulation needs to reverse unfinished work. Rolling back a refused candidate restores its starting state, including the relevant clocks, identities and random choices, while preserving earlier accepted progress.                   | [Candidate settlement and rollback](../projects/native-simulation-core-tech-design.md#32-candidate-acceptance-and-rollback)                                                                                             |
| Capture and read cut                  | A capture holds the particular values a reader needs. Its read cut identifies which accepted state those values describe. For example, a player view may read saved history while a newer walk awaits a save. The read must combine only the saved and pending facts belonging to the selected cut.                                          | [Stable consumer products](../projects/native-simulation-core-tech-design.md#61-stable-consumer-products-without-a-permanent-immutable-world-graph) · [Mixed-server read cut](../../apps/server/src/native-read-cut.ts) |
| Timeline and captured revision        | A timeline identifies one history of the world. A read records the timeline and the revisions of the data it uses. A view captured before restoring a checkpoint can point to old facts even if a record number matches. For the different identities that can change, see [Identity and references](identity-and-references.md).            | [Restore and authority](../save-and-load.md#loading-as-an-authority-transition) · [Checks when combining reads](../../apps/server/src/native-read-cut.ts)                                                               |
| Pending read overlay                  | Accepted changes through a reader's selected cut that are still needed to supplement the database snapshot. A reader can hold these changes independently while a save completes. Reading the latest database state again would answer a different question.                                                                                 | [Capture and ownership of a read cut](../../apps/server/src/native-read-cut.ts)                                                                                                                                         |
| Command epoch                         | The server issues an epoch identifying the retry window for player commands. A retry is bound to its original identity and timeline. The server still checks the caller's [current grant and control](access-and-participation.md#who-can-do-what).                                                                                          | [Player command epoch](../../native/game-server/src/command_epoch.rs) · [Gameplay receipt lookup](../../apps/server/src/command-receipts.ts)                                                                            |
| Currentness check and disclosure      | Before handing data to a player or model, the owner checks that the relevant sources, timeline and permission still allow it. In the Node-hosted Rust path a synchronous disclosure lease protects the final selection, encoding and handoff. An earlier valid read may since have been corrected, forgotten or revoked.                     | [Native/application boundary](../projects/native-simulation-core-tech-design.md#4-nativeapplication-boundary) · [Rust player stream](../../native/game-server/src/player_stream.rs)                                     |
| Response ticket                       | The Rust simulation keeps the permitted input and prepared choices for one NPC decision request. Its ticket binds the returned answer to that request and tracks whether it can still be applied. The server can receive an answer after the ticket is cancelled or its evidence changes.                                                    | [Rust ticket and application states](../../native/simulation/src/runtime/npc/bindings.rs) · [Cognition boundary](../projects/native-simulation-core-tech-design.md#cognition-boundary-and-equivalence)                  |
| Player view, publication and delivery | A player view is the server's projection of facts that session may see. Publication selects an authorized update and hands it to transport. Receipt by a client and visible display by its browser are later, separately observable events. A simulation publication can also refer to accepting a world change, so name what was published. | [Player view publication](../projects/completed/2026/rust-game-server-tech-design.md#5-publish-only-what-each-player-may-see-rgs05)                                                                                     |
| Stream, patch and reset               | A server-sent event (SSE) stream carries updates to one connection. A patch changes the preceding permitted view. A reset supplies a complete freshly permitted view, for example at first connection. An unchanged view can produce no outgoing payload.                                                                                    | [Stream selection and encoding](../../native/game-server/src/player_stream.rs)                                                                                                                                          |

## Scheduling simulation work

| Canonical term                             | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                                               | Source                                                                                                                                                                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Compute pool and execution lane            | A compute pool supplies a bounded number of threads for ready calculations. A lane controls which operations may proceed together or in what order, for example writes to the same world. Time spent waiting for a database or provider belongs to its I/O path.                                                                                                    | [Host compute pool](../../native/world-host/src/pool.rs) · [Scheduling and work placement](../performance/scheduling.md#work-placement-and-buffering)                                                                                          |
| Dirty, due and relevant work               | Dirty data has changed in a way that can affect a result. Due work has reached a scheduled time. Relevant work can affect the current operation, such as bodies within reach of a moving character. A change can make a result dirty before a scheduled review is due.                                                                                              | [Work selection](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm) · [Triggered work](../performance/scheduling.md#triggered-background-work)                                                                 |
| Compute range, inline execution and join   | In the single-machine design a range is a bounded slice of independent calculations from one coherent input, such as processing selected observations. Inline means the current worker does the calculation itself. Joining waits for all selected ranges to finish before the next dependent phase. A proposed split still needs evidence that real work benefits. | [Scheduling and disjoint work](../projects/native-simulation-core-tech-design.md#51-initial-scheduling-algorithm) · [Measured work and limits](../limits/native-simulation-core.md#nsc-l02--compute-capacity-and-job-granularity)              |
| Cell and read overlap (distributed design) | A proposed cell owns a part of one world's state. Its calculations may read neighboring state needed for an interaction. A creature crossing a cell boundary still belongs to the same world. Several cells may share one machine. This is a design for future distribution.                                                                                        | [Cells as units of ownership](../projects/native-simulation-core-tech-design.md#71-cells-are-ownership-units-not-gameplay-rooms) · [Read overlap](../projects/native-simulation-core-tech-design.md#72-read-overlap-and-interaction-ownership) |
| Backpressure and cancellation              | Backpressure slows or restricts new work when a consumer or queue cannot keep up. Cancellation tells an operation to stop or withhold future output. If an outside service has already accepted a request, its outcome and cost still need reconciliation.                                                                                                          | [Publication under backpressure](../performance/scheduling.md#bounded-batching-backpressure-and-publication) · [Provider outcomes](../ai-providers.md#receipts-outcomes-and-accounting)                                                        |

## Saving and continuing play

| Canonical term                                              | Meaning in OpenLegend                                                                                                                                                                                                                                                                                                                                                       | Source                                                                                                                                                                                        |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accepted change and durable commit                          | A change is accepted when it takes effect in the live world. It is durable when the covering PostgreSQL transaction commits. A client can see movement before that commit. A save acknowledgement confirms which accepted changes the database has committed.                                                                                                               | [Background and synchronous saves](../save-and-load.md#background-and-synchronous-world-saves) · [Rust live saves](../../native/game-server/src/live_save.rs)                                 |
| Changed record, save prefix and pending save                | The writer prepares rows for the records changed by accepted work. It can save an ordered prefix, meaning all pending work through a particular accepted change. Acknowledging that prefix allows its save resources to be released while newer changes remain pending.                                                                                                     | [Changed-record saving](../projects/native-simulation-core-tech-design.md#62-direct-changed-record-saving) · [Pending prefix](../../apps/server/src/native-pending-save.ts)                   |
| Gameplay receipt and provider receipt                       | A gameplay receipt records the result for a bound command ID so an authorized retry can recover that outcome without applying it twice. A provider receipt concerns an external attempt, its outcome and financial accounting. Recovering either receipt observes the original operation.                                                                                   | [Gameplay receipts](../../apps/server/src/command-receipts.ts) · [Provider accounting](../ai-providers.md#receipts-outcomes-and-accounting)                                                   |
| Checkpoint and recovery                                     | A saved-world checkpoint captures a coherent world and the personal evidence required to continue it. Administrative recovery replaces gameplay state atomically from a validated checkpoint and preserves applicable current access, privacy and financial authority. An internal operation checkpoint is a position in the undo journal for a partly completed operation. | [Capturing and publishing a save](../save-and-load.md#capturing-and-publishing-a-save) · [Loading as an authority transition](../save-and-load.md#loading-as-an-authority-transition)         |
| Reconnect, cold reopen and rewind                           | Reconnecting opens a player's currently permitted view of a running world. A cold reopen starts a new server process from the latest durable world. A rewind deliberately restores an earlier checkpoint. Measure each journey separately.                                                                                                                                  | [Multiplayer measurement windows](../projects/native-simulation-core-tech-design.md#multiplayer-measurement-windows)                                                                          |
| Canonical record, derived index and hydration               | A canonical record contains facts needed for continued play. A derived index supports lookups and can be rebuilt when the authoritative data suffices. Hydration brings a saved record into working memory when a supported operation needs it. A record can be stored and valid while absent from RAM.                                                                     | [State ownership and save scope](../save-and-load.md#state-ownership-and-save-scope) · [Partial residency](../projects/native-simulation-core-tech-design.md#partial-residency-and-hydration) |
| Temporal evidence block and stable value                    | A block groups received changes or occurrences in order for the observer who earned them. A stable value stores content that several records can reference without keeping independent copies. Reusing its bytes grants no other observer the original observation.                                                                                                         | [Shared temporal evidence](../save-and-load.md#shared-temporal-evidence-continuation)                                                                                                         |
| Cursor and watermark                                        | A cursor records where a particular reader or processor can continue. A watermark marks how far a specified sequence has been seen or considered. For example, a memory worker can have examined awareness through one position while older unfinished speech only becomes eligible for interpretation later. The sequence and owner determine what the position proves.    | [Speech eligibility and ordering](../memory-architecture.md) · [Temporal references](../identity-and-references.md#selected-shared-temporal-references)                                       |
| Resident state, transient workspace and pending-save memory | Resident state is held in RAM for ongoing simulation. Transient allocations fund bounded work such as captures and undo data. Pending-save allocations hold accepted work through database acknowledgement. A reservation accounts for permitted bytes. Actual process RAM is measured separately.                                                                          | [Canonical working state](../projects/native-simulation-core-tech-design.md#31-canonical-working-state) · [Native host limits](../limits/native-simulation-core.md)                           |
