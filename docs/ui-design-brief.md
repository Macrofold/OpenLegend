# Open Legend UI design brief

## Whole-interface redesign scope

Mike's October 3 request covers the entire interface; inventory was an example. The first redesign delivery concentrated on inventory, contextual camp tasks, Crafting and conversation. The implemented continuation now changes the shared shell, Character and actions, reading/history, settings, creator navigation and entry/recovery presentation as one interface. This does not establish complete gameplay or usability acceptance. The [current source/evidence map](ui-ux/interface-coverage.md) retains the original 58 audited groups and five later integrated groups, including death, final-blow review, barter, known places and shared outings. It accounts for ordinary play, Character/history, entry/settings/saves, invention/creator editors, operations and diagnostics. The existing [feature specification](projects/game-interaction-redesign-feature-spec.md) and [technical design](projects/game-interaction-redesign-tech-design.md) own the full experience; [UIUX07–UIUX18](maintainers/ui-ux.md#uiux07) and the [verification report](verification/game-interaction-redesign.md) distinguish delivered behavior from the remaining native, input and player-observation checks.

The October 16 [world-first redesign](projects/player-experience-overhaul-feature-spec.md), tracked by [UIUX19](maintainers/ui-ux.md#uiux19), supersedes the former player transcript, Journal launcher, nested In view details and coordinate-entry building. The current left rail opens **Inventory**, **Character**, **Events** and **Character records**; the right rail opens **In view**, **Craft**, **Build**, **Create** and **Speak**. **Character records** is the primary home for story, promises and known places, without a redundant route through Character. **Game** provides return to play, persistence status, permitted checkpoints, **Settings & help**, **Intelligence & allowance**, and separately authorized **World editor**, **Inspect world**, diagnostics and operations. Deliberate authoring, policy and checkpoint review retain meaningful fields and consequences. Familiar game layouts guide task behavior; their quests, turn budgets, body slots, controller schemes or omniscient maps do not become universal world rules. Existing camera meanings, private knowledge, time, save and approval owners remain controlling.

Shared inventory and Character presentation use the installed world's supported capabilities. Base, touch-demo and reservoir-demo presets exist independently of theme selection. World/location/time labels, item/entity/action symbols and grouped-shortcut labels now come from authored presentation; shared UI code no longer derives wilderness verbs or symbols from item and creature identifiers. Preparation wording and input recognition belong to the bundled world. The clockwork presets now install a trusted recharge activity using the existing replenishment mechanism, while the bundled base world retains its own activity hosts. This is an actual alternate task presentation, not a general external-world loader, new electricity model or multi-slot equipment system. The [portability correction](verification/game-interaction-redesign.md#world-portability-correction) and current verification distinguish that finite support from broader acceptance.

## World presentation ownership

[World presentation](world-presentation.md) owns the accepted continuous right-drag orbit/pitch, Shift + right-drag or middle-drag pan, mixed sprite/mesh depth, default illumination, projected shadows and configurable local character-visible read-through. These are presentation settings, not extra bodily perception. Follow that owner where older camera-binding or unlit-art directions conflict; SW18 retains visual qualification and further art work.

## Spatial camera and floor UI

[Spatial-world controls](spatial-world.md#tactical-camera-and-perspective) own camera/floor behavior. The compact Camera toolbar keeps zoom, recenter, follow and Sight/Hearing visible. The combined **Camera settings** icon expands rotation/tilt, projection, rotation lock and shortcut help. There is no floor selector or floor-hiding dropdown. Holding Option (Alt) reveals already perceived subjects through camera-obstructing scenery; releasing the gesture restores the configured view. This uses [the existing read-through mechanism](world-presentation.md#local-read-through), preserving hidden contents and bodily sight. Pointing in the scene supplies the supported position to the server; ordinary players do not type coordinates. Camera changes cannot expose unpermitted people. Preserve accessible buttons, canvas keyboard focus, supported touch alternatives, panel shortcuts and non-canvas inspection. Rendering preferences do not expand what the character perceives, and broader touch/assistive-device qualification remains with the spatial owners.

React and React Aria are the current UI foundation; Motion remains unnecessary for the current modest transitions. This brief owns presentation and interaction behavior. See the [production UI ownership guide](../apps/client/src/design-system/README.md), [current architecture](architecture.md) and [cross-cutting validation queue](maintainers/TODO.md).

## Project and atmosphere

Open Legend is an open-source engine for authored realities with a playable bundled wilderness simulation and role-playing game. In that world, characters gather, craft, rest, converse, develop memories and pursue survival. Players can use supported invention and owner-authoring capabilities to extend their experience. The interface must support a growing catalogue of content without becoming crowded. Exploration, atmosphere and discovery should shape its ordinary interactions. Richer simulation and general world-agent authoring remain evolving work rather than capabilities implied by a menu.

Preserve the existing Wilderness theme's dark green adventure atmosphere: deep forest-green surfaces, warm ivory text, muted sage accents, restrained antique gold and subtle borders. That theme should feel intimate, tactile and grounded in the bundled wilderness. Other themes keep the same interaction behavior without assuming that setting. Explore restrained material texture and elegant serif headings paired with highly readable body text. Avoid ornamental overload, generic dashboard cards, bright default-blue controls and excessive labels. The world remains the visual focus. See the broader [visual direction](../archive/03-design-proposals/visual-direction.md).

## UI stack and boundaries

Use React + TypeScript with **React Aria Components** for accessible interaction primitives and custom Open Legend components and CSS for visual design. CSS handles current transitions; add **Motion** only when coordinated panel, tab or layout animation requires it. Keep **PlayCanvas** responsible for world rendering, camera interaction and frame-by-frame positioning.

React Aria supplies collection, selection and accessible control behavior without determining the game's appearance. Keep its use concentrated in game components and preserve the boundary between public game state, simulation rules and server-side action admission.

Keep library usage concentrated inside game components such as ActionPicker, InventoryGrid, WorldPanel and Tooltip. Keep public game state, simulation rules and server-side action admission separate. Coordinate focus, pointer events and keyboard shortcuts so UI interaction does not inadvertently move the character or camera. Do not route every world animation frame through React state. React must not share ownership of the same DOM subtree with legacy imperative rendering during migration.

Use **Lucide** for utility symbols such as close, back, search and settings. Use a stylistically curated selection from **Game-icons.net**, or custom artwork, for resources, equipment and actions; preserve asset attribution and licensing. Self-host selected fonts through **Fontsource**. A readable body family such as Source Sans 3 can accompany a theme-specific display font; decorative fonts should not carry dense descriptions or small status text.

## Design-system requirements

- Use the existing semantic typography, spacing, icon sizes, control sizes, panel treatments, focus states and motion rules. Check density with real long text and the shared panel dimensions rather than judging an isolated card.
- Support interchangeable world themes: wilderness, fantasy and science fiction share reliable behavior but can change fonts, materials, borders, shapes, artwork and animation character.
- Separate interaction behavior, game components and theme definitions. Theme changes must not alter game rules. Specialized presentations such as spellbooks or spaceship consoles should use the same underlying data and interaction contracts.
- Resolve world-authored symbols through the trusted semantic catalogue. A supplied resource symbol may combine with the native gathering badge; the client must not guess content identity from an item identifier. New invented content receives an immediate readable fallback. Any later bespoke-artwork capability must not block mechanics or be implied by a pending decoration. See the [invention lifecycle](../archive/03-design-proposals/generative-capability-lifecycle.md#symbolic-presentation-for-every-new-action-and-item).
- Prioritize readability over decoration. Include keyboard navigation, visible focus, reduced-motion behavior and UI scaling.

## Interaction direction to preserve and refine

- The compact upper-left summary names the controlled character and presents permitted authored condition attributes above the left launcher buttons. Current location sits beneath Day/time. Need status and meaning appear in structured hover/focus details, not persistent paragraphs. Branding and routine save status belong in Game, opened by unconsumed Escape; actual save failures remain visible. Current work appears in a separate collapsible panel below the summary, above the desktop buttons and behind other panels; its body scrolls within the available space. Starting or ending work must not move launcher rails or shrink open workspaces. Selecting the character opens Condition; reviewing work opens Capabilities without forcing the intention composer. A completed activity retained in history does not mean the character is still working.
- Circular launcher rails are vertically centered independently of condition and work panels; tight layouts use the existing horizontal strip. They follow the player-record/world-action hierarchy above. **Game** and **Settings & help** stay explicitly reachable. Hover/focus help uses the shared opaque, padded, pointer-anchored surface from the [controls handbook](ui-ux/controls.md); unfamiliar content keeps a readable name.
- Docked panels toggle independently, have close buttons and fit in opening order. Object inspectors are separate movable windows that can overlap and be raised deliberately. Narrow layouts retain a way to switch among open panels and inspections.
- In view stays a list of visible objects. Selecting one highlights it and opens the same independent inspector as left-clicking the object or choosing Look closer. Several inspectors may remain open; each reuses the contextual action browser for its Actions section.
- Create contains ordinary **Invent / Recipes / Requests**. The separately authorized **World editor** keeps **Chat / Saved changes** stable, while **Inspect world** is its own destination. Session selection, hiding and ending a conversation retain their distinct native meanings. The interface exposes only actual conversation, draft, review and activation capabilities.
- Bottom quick actions visibly separate up to three contextual suggestions from three player-configured shortcuts. Assignments remain stable when unavailable and explain the reason; configuration is a separate control. Suggestions retain still-offered identities while hovered/focused; retired actions are replaced immediately rather than leaving a stale Sleep or Wake up command. A grouped shortcut makes its exact current source reviewable before commitment and cannot silently replace that source.
- Right-click opens a compact, target-specific action picker with search and relevant immediate choices. Self-actions belong on the character, gathering on resources and speech on the selected person; empty ground does not expose the whole catalogue. Evade stays out of right-click menus while its native capability remains supported.
- Deliberate subject selection temporarily exposes the scene, with an **In view** list for keyboard/non-drag selection and explicit Cancel. It retains the original action task and subject until a choice is made. Selecting an object only binds that exact reference; sending remains separate. Choosing or dismissing a subject must not walk or trigger a shortcut.
- Left-click selects or walks; right-drag rotates/tilts and Shift + right-drag pans, as specified in [camera controls](world-presentation.md#camera-and-settings). Clicking the map to dismiss an action menu must not also move the character.
- Status text appears above the relevant character or object in white without a background. New notices stack above older ones. Work labels and smooth progress bars appear only when work begins, remain while incomplete and disappear immediately on completion. Walking gets no status. Keep a consistent gap above the subject, including beneath a progress bar.
- Speak opens a compact input; final perceived words appear over speakers and in Events, without a separate player transcript. Inputs grow with wrapping or explicit Shift+Enter newlines. Pending, failure and exact retry controls remain with the sending task, never inside fictional speech. Owner chats retain the shared conversation components and restrained message status. Native reply admission is unchanged: ordinary new awareness does not invalidate a reply; only an event meeting the current importance and urgency thresholds can trigger the existing single context refresh/retry, without looping. Pause does not discard an already generated reply. Actor unavailability disables sending with its specific reason; provider, validation and storage failures remain distinguishable. The [speech contract](narration-and-conversations.md#player-speak-and-descriptive-act) owns exact effects and recovery.

## Object-based inventory and everyday actions

**Implemented in the current interface; broader gameplay qualification remains open:** ordinary inventory uses readable item grids. Opening a physical supported container from the world opens that named container beside the player's belongings, and moving items between them is a direct action. The already-open object supplies the destination. This replaces the routine nearby-container selector and repeated exact-transfer review in ordinary inventory. Contextual tasks use trusted world-authored presentations with a compact summary and one deliberately opened editor. The final inventory and task layouts passed focused checks inside the actual shared panels. [UIUX08–UIUX11](maintainers/ui-ux.md#uiux08) and the [verification report](verification/game-interaction-redesign.md) distinguish this evidence from completed gameplay acceptance.

Use context to bind the selected actor/object/item and ask only for consequential unresolved choices. A requested partial stack amount belongs in a small control beside the item; adding fuel begins at the fire; known crafting begins from the relevant capability or station. Longer tasks show their chosen supply, spending limit and stop condition in a compact summary, with one focused editor opened deliberately when a value needs changing. Important costs and current-work replacement remain understandable before Start. Native authority, permissions, reach, stack identity and actual receipts remain enforced.

After a confirmed Start, current work and its Stop action lead. Further preparation opens deliberately and retains the player's previous choices. The acknowledgement describes starting or queueing work in ordinary language; it does not promise a completed result. Refusal or uncertain delivery keeps the draft and exact-request recovery available. This follow-through is implemented and component-checked; [UIUX09](maintainers/ui-ux.md#uiux09) retains the remaining native gameplay and broader input qualification.

Inventory is a deliberate two-collection workspace that may expand beyond an ordinary panel; narrower layouts retain both endpoint identities and the same task. Existing camera bindings, theme, conversation volume/composer layout and creator approval boundaries remain controlling. The [inventory chapter](ui-ux/inventory.md#open-the-object-and-keep-both-inventories-visible) and [world-interaction chapter](ui-ux/world-interaction.md#object-opening-and-contextual-activity) own the enduring interaction guidance. The [paired design](projects/game-interaction-redesign-feature-spec.md) scopes implementation, while the [game atlas](ui-ux/games/README.md) and [pinned audit](ui-ux/current-interface-audit.md) provide evidence. Illustrative chest/workbench content does not assert a shipped native family.

## Character and focused action tasks

Character now separates **Condition**, **Capabilities**, **Equipped** and **Record**. Condition uses the installed world's meters and status effects. Capabilities contains current work, intention review and the existing actions/learned-activities record. Neither section repeats a list of available actions; those stay with their contextual targets, shortcuts and the complete action browser. Equipped describes the actual equipped item; the Inventory launcher owns equipment changes. Record groups traits with hover/focus descriptions, memories and the permitted personal-mind route. Creator controls stay in a separately labeled God-mode disclosure. Do not add levels, bonuses, body slots, weapon sets or combat resources without an owning native capability.

Ordinary object and item actions execute through their existing native routes. The optional **Describe an action** task keeps the controlled character, exact subject, original words and explicit primary action together. A subject that leaves view remains named with a reason; changing global selection cannot silently retarget the request. Cancel returns to Character and preserves the draft. The former Target/Item/Tool/For/Amount worksheet is removed; contextual native tasks ask only for their meaningful unresolved choices. Revised executable actions keep their existing acceptance/rejection flow rather than gaining an invented universal confirmation step.

When the character has queued, running or paused work, the intention task exposes the existing queue, pause-and-resume, and replace meanings. The primary verb reflects that choice and replacement explains what is discarded. **Stop all work** follows native availability and discloses that paused work is also discarded. Detailed work steps remain authorized creator information. The task's longer content scrolls while commitment, Cancel and the possible interpretation-allowance notice stay reachable. Original words survive clarification, refusal and ambiguous delivery; explicitly retrying the same uncertain request retains its identity.

## Reading, settings and private continuity

**Events** is the unified history of perceived speech, actions and observations. **Character records** has its own primary launcher, retaining Promises, Beginnings, Your story and Known places without using those as event categories. Personal memories and authorized raw world-event editing keep their own scopes. Events and Character records use wider reading panels and an explicit expand control. New information offers a deliberate update or return-to-latest action, older pages keep a recognizable anchor, and searches explain which records were searched. Enlarging a panel never broadens the character's knowledge or creates a player map.

**Settings & help** is a wider workspace with retained **Appearance & reading**, **Camera & graphics**, **Controls & help**, and authorized **World permissions** tabs. Device-local preferences say they apply immediately; world policy retains its deliberate native save and permission behavior. Controls explain selection, object opening, subject choice, camera recovery, conversation and shortcuts in game terms. The optional frames-per-second display is off by default and reports rendering throughput, not simulation speed or reply latency.

Preserve supported task navigation and private drafts when hiding/reopening a panel or resuming the same permitted character. Their ownership uses the server's private-draft scope together with world, timeline and character. Requests and private readers still use fresh access/control scope: a same-owner Resume can keep the task while reloading its permitted records, so this is not a promise to retain every reading position across a required fresh read. Changed session/grant, character, world timeline or logout invalidates private work. Reject stale asynchronous completions without clearing words typed after the request began. [Tab Resume](projects/completed/tab-resume-feature-spec.md), [architecture](architecture.md) and the relevant record owners define those boundaries.

Focused native and browser evidence supports only its stated scenarios. Real operating-system input-method composition, assistive devices, broader text/viewport combinations, remaining client/server journeys and uncoached player observation remain open where recorded in [UIUX](maintainers/ui-ux.md) and the [verification report](verification/game-interaction-redesign.md). Keyboard-event checks or screenshots do not close those acceptance items.

Right-click quick suggestions show available actions for the clicked context. **All actions** also includes known but currently unavailable actions as dimmed, non-executing rows; hover and keyboard focus explain their meaning and blocking reason. Unknown actions stay hidden. There are no Walk here, catalogue-browsing, hide-unavailable or freeform-request controls. Primary click walks; the separate browser also omits walking entries. **Settings & help → Browse known actions** opens the separate situational action browser, where unavailable-action explanations remain available. Up to five immediate contextual choices appear first, including the relevant Speak, Act and Look closer utilities; categories containing one action show that action directly, and larger categories use right-opening submenus with a screen-edge fallback. A singleton already shown among immediate choices is not duplicated. Self-click omits Talk and Look closer, and inventory equip choices stay in inventory. [Speak and descriptive Act](narration-and-conversations.md#player-speak-and-descriptive-act) open the centered bottom text bar. Search displays matching known actions directly. Scrolling reveals later rows automatically, with **Show more choices** retained for keyboard use. [Ordinary discovery](action-experience.md#ordinary-player-action-discovery) owns behavior and [AP01](limits/interface.md#ap01--ordinary-action-discovery) owns display bounds.

## World-agent authoring and progressive technical detail

The [world-agent authoring workflow](../archive/03-design-proposals/world-agent-and-workshop.md#natural-language-world-and-mechanic-authoring) owns meaning, permissions and activation. This section owns its presentation. Natural language is the primary path for supported creation and refinement; technical inspection is available without being mandatory.

Keep the game visible. Use the existing World Agent conversation and reusable panels/pullouts rather than a separate engineering dashboard. A creator should see a compact explanation of the candidate: intended behavior, affected scope, reused parts, important defaults, unresolved decisions, and actual draft/validation/installation state. Use clear labels that distinguish a proposed change from a running mechanic; success styling must follow an authoritative receipt.

Offer progressive detail: a plain-English summary first, a concise parameter/behavior view next, then dependencies, raw configuration/source when applicable, and validation evidence. These views represent one candidate revision. Unknown, unsupported, unbound and failed are distinct; do not hide a missing required mechanic behind an attractive preview.

Clarification controls should ask about the experience in ordinary words. For a touch-only creature, ask about hearing, remembered places and affected creatures—not internal schema names. Defaults remain inspectable and can be revised conversationally. A user may choose raw editing, but it follows the same revision/validation flow and cannot directly commit arbitrary effects.

For reusable constructs, show the choices intentionally exposed by the author and which have already been bound. Allow a request such as “Keep everything else, but make the effect instantaneous.” Explain a compatibility or permission change before implying that substitution is supported. A shared template with required unbound inputs must not display a working Use/Cast affordance.

Preserve the existing Similar inventions modal and confirmed-conjuring flow. Avoid a new confirmation for every minor draft/tool step. A consequential scope/effect change requires the existing renewed review; a stale approval cannot activate a changed candidate. Show the relevant before/after behavior and any newly affected population or permissions.

Technical details remain in the creator/workshop surface, not between in-world character utterances. Keep pending/failed execution, art status and installed mechanics distinguishable without excessive diagnostic clutter. Reopening a panel, refreshing details or selecting an older version is read-only and cannot restart generation or activation.

Provide keyboard/focus support, readable validation errors and bounded views for long dependency lists. Render generated text as text, not executable markup. Accessibility and fallback presentation do not broaden actor knowledge. Validation and test results are labeled by their actual evidence; a preview is not a simulation result.

## Future character reactions

A later reaction mechanism may briefly show natural text such as “Hmm” above a character. Under the accepted narration design, an actual spoken reaction or observable gesture is an accepted speech/expression event and is remembered normally; its overhead presentation may disappear without deleting that experience. Private thoughts stay hidden. Loading dots are technical status and create no event or memory. Reaction vocabulary and timing should vary with character, player interaction and nearby events rather than using one fixed waiting phrase. Accepted gestures (the fixed expression vocabulary) now appear briefly above the gesturing character for viewers who perceived them, worded only from the viewer's own labels; varied “Hmm”-style reactions remain planned. [The reaction follow-up](maintainers/TODO.md#future-character-reaction-bubbles) tracks the rest and links the owning NC implementation tracker.

## Narration and perceived history

The [narration/conversation design](narration-and-conversations.md) and [perceived Events contract](perceived-world-events.md) own the evidence shown in the unified reader. Show non-speech reactions, actions and relevant world events in the same chronology as speech, without a fake speaker or internal thoughts. Consequences such as “lost 1 health” derive only from committed, permitted effects; raw before/after values belong in detail. Expressive actions without mechanics show no invented damage or condition change and need no repetitive “no effects” label. Thought-only/no-response outcomes finish the sending task without fabricating speech.

The Narrator can show stylized book-like text across the top of the screen and retain the same entry under Character records. Respect UI scale and reduced motion, and avoid stealing focus or blocking controls. Narrator voice changes future presentation only. Native conversation membership and merges remain independent of whether the Speak input or Events reader is open; any applicable owner-chat hide/end controls retain their distinct meanings.

Show stable chronological history when generation finishes late, preserve reading position and avoid rendering the same action twice. Authorization, membership, merges, source scope and privacy are defined in [Narration, agent responses and conversations](narration-and-conversations.md); the UI renders only the server-authorized projection. Delivery is tracked in the [Narration and conversations tracker](maintainers/narration-and-conversations.md).

## God-mode cognition debugging

The authorized **Game → Intelligence diagnostics** route opens the right-side Intelligence panel, following the [canonical debugger hierarchy](memory-architecture.md#god-mode-cognition-debugger): selecting a compact trigger/action row opens a full-width detail view with the standard panel back control. Rows and details expose stable trace/stage references. The detail renders the typed cause and concise trigger, outcome or error, Jev questions/choices/decisions, speech, context/retrieval and semantically named model/harness stages. Root-only world-agent records show the player message, response or error, and result code. Query-embedding stages show the model and number of vectorized inputs; the separate memory-context stage shows the semantic query, backing table and retained ranked results. Persistent JSON icons on the trace and each stage open combined application/provider records in a roomy left-side panel with icon-only copy; transport exchanges are not shown as numbered requests. Filters, paginated history and follow/pause updates preserve the reader's focus; deeper recovery and live-provider acceptance remain tracked separately.

## Requested design output

Use the screenshots as visual reference, preserving the appealing dark green atmosphere while improving consistency, hierarchy, compactness and polish. Deliver a cohesive design system with reusable component examples and interaction states, not just isolated screen mockups. Include representative empty, unavailable, loading, focus, hover and error states. Demonstrate the same core components in the wilderness theme and one contrasting theme to prove the theme boundary works.

Clearly distinguish existing functionality from future concepts such as richer character traits, generated artwork or remote world-agent sessions. Do not invent statistics or imply unavailable AI works. No full game-engine rewrite is required.
