# Inventory, equipment, containers and trading

[Handbook](README.md) · [Controls](controls.md) · [Game research](research.md#game-exemplars)

## Scope and design objective

Let the player see and handle their belongings, open a physical chest and move objects between the two without repetitive bookkeeping or accidental loss. The primary questions are **what do I have, where is it, what can I do with it, and what will change?**

The implemented Gildmoss presentation keeps belongings in Character and opens explicitly selected bags, containers and item piles as independent windows. One Inventory controller owns all native writes and receipt recovery; each open collection has its own bounded permitted reader. Earlier paired-layout rationale and evidence remain in the [feature specification](../projects/game-interaction-redesign-feature-spec.md), [technical design](../projects/game-interaction-redesign-tech-design.md) and [verification report](../verification/game-interaction-redesign.md). Current Gildmoss acceptance is tracked in its [verification report](../verification/gildmoss-interface.md).

## Open the object and keep both inventories visible

Opening a reachable, permitted container from its world object menu opens a separate named window. Carried and nested bags use the same window presentation. Reopening the same exact container raises its existing window instead of creating another reader. Desktop windows can be moved, raised and closed independently; each retains its own search, sort, filter, continuation and scroll. On narrow screens the active window becomes a sheet with an open-bag switcher and **Your belongings** return. Closing Character does not destroy its shared controller or the bags. Names, quantities and item actions come only from their currently permitted pages.

The ordinary presentation is a compact icon grid with a visible quantity and marks for equipped items, containers and reserved units. Each button's accessible name and hover/focus tooltip retain the full item name, quantity, state and available-unit information; missing artwork keeps a readable letter symbol. Tab and Enter provide ordinary button navigation and inspection, where the full name and item details remain visible; the grid does not claim composite arrow-key semantics. Cells organize presentation; native object identity, capacity and stack rules remain authoritative. Sorting is not merging.

The active bag supplies the usual belongings transfer destination; a bag defaults to moving back into belongings. Item details can explicitly choose another open destination for keyboard/pointer transfer without dragging. Shift-click / Shift+Enter quick move uses that current destination. Dragging between any two open collections captures the exact source item/container revisions and selects the exact current destination on release. A multi-unit stack drop opens the existing number/slider quantity chooser; a single individual object uses the same native transfer directly. Reserved units stay, and native admission still determines custody, capacity and legal quantities. **Move an amount…**, **Split stack…** and **Drop an amount…** retain exact drafts. Changing or raising another window never silently changes a move’s pinned destination.

Source and destination identities and revisions remain pinned through quantity editing and native submission. A release over scenery cancels; intentional Drop remains a separate action. The one Inventory command owner records the original request before submission, publishes its native result and refreshes current collections. Its recovery controls are available in the visible active bag or belongings without mounting a second sender or history reader. Unknown, missing or expired receipt status never authorizes replay; Check result reads the original receipt. Full capacity, moved items and lost access refuse rather than redirect a transfer.

Every window keeps the root under which it was explicitly opened. A world root that moves, loses access or leaves permitted reach withdraws its rows and requires a fresh explicit world opening; a nested bag must still resolve under that original root. Carried-bag reads require the original controlled actor root, so moving a bag into another person’s custody grants no continued contents access. Closing a window withdraws its reader and any unsent move that needs that endpoint, while the shared original-command recovery survives. A separately entered storage finder retains its own bounded permission-safe discovery; this UI adds no nearby deposit automation or native batch behavior.

The named collections sit side by side when the workspace fits them and stack at narrow widths. Each has a bounded contents scroller, while item detail uses an anchored popover. On the regular desktop it opens beside the selected item. In the App’s sheet layout it uses vertical placement, allowing the overlay owner to keep the complete detail within the viewport width. Keep the same mounted detail, selected item, amount and reading positions through layout changes; complete input/layout qualification remains in the linked evidence and tracker. Do not solve narrow fit by restoring the destination dropdown. An expanded inventory is a deliberate task workspace, with a clear return to the world; ordinary panel dimensions do not dictate its two-collection layout.

Each window’s visible and accessible name follows its exact current permitted page. Loading can use the name supplied by that explicit admitted opening; a refused or withdrawn read clears private contents and falls back to **Container**. It never relabels a nested bag as its original ground pile. The [native shared-storage observation](../verification/game-interaction-redesign.md#native-shared-storage--october-7-2026) preserves the original title defect and separate custody/access evidence.

When only belongings are open, that collection uses the available width; an unopened destination does not reserve half the workspace. The App supplies the Inventory heading once. **Controls** is an initially closed, keyboard-operable disclosure alongside the compact optional creator utility containing the preserved gesture and object-opening instructions. Equipment, collection names, search labels, location, capacity, availability and recovery remain outside that disclosure; ordinary scrolling reaches content beyond the viewport. Standalone Inventory retains its own heading. Belongings names its active move target; separate bag headings name each independent endpoint. Item cells use the shared compact slot size, with full names and state available on hover, keyboard focus and inspection; a single-node root breadcrumb is omitted while useful nested navigation remains. ## Current implementation and evidence

Current Open Legend has paired item grids, independent scoped search and finite contents pages, nested bags and breadcrumbs, exact quantity drafts, native movement/split/merge operations, equipment labels/comparison and object history. The October 16 overhaul adds equivalent-material grouping and stable same-owner reading through right-click, refresh and quiet pause; [its focused report](../verification/player-experience-inventory.md) separates native checks from the parent project's browser evidence. The redesign reuses the [PW04](../maintainers/parallel-batch-01-playable-week.md#pw04--inventory-for-exact-camp-tasks) native inventory work and existing custody/access owners. **Offer to a person…** is a separate consent-based handover task; it is not ordinary container movement or unrestricted access to another person's possessions.

The [game-interaction verification report](../verification/game-interaction-redesign.md) separates current implementation and actual observations from open native HTTP/PostgreSQL and J16 gates. Earlier [PW04 evidence](../verification/parallel-batch-01-playable-week-engineer-4.md#pw04--native-inventory-and-partial-browser-checks) remains historical evidence for its recorded revision and workload, not qualification of the redesigned workspace. This chapter also describes **future patterns** for broader search, bulk actions, loadouts and trading. Those patterns are not delivered features or new authorization; [persistent objects](../maintainers/persistent-objects.md), [base-world work](../maintainers/base-world.md) and existing action/authority owners retain implementation scope.

## Organize around player tasks, not container internals

Use a clear hierarchy: inventory scope and capacity; search/filter/sort tools; collection; selected-item detail; contextual actions. Keep the current object or selection visible while choosing an action. Do not require opening an editor merely to see a name or available quantity.

For this redesign, grids are the ordinary inventory and open-container presentation. Lists remain useful as an alternative for scanning long names and comparable facts; they are not the default transaction worksheet. Keep essential names accessible beyond hover, especially for newly invented items with fallback art, and provide the same operations through keyboard and nonvisual navigation.

Keep task-critical row information concise: recognizable identity, quantity, equipped/locked state where supported, and the most useful comparison fact. Put long lore, provenance and modifier breakdowns in detail. Do not place a full action toolbar on every row in a thousand-item collection. A selected-item action area, context menu and explicit multi-select mode are more scalable.

Distinguish **focus**, **inspect item**, **select for a batch** and **execute an action**. Opening detail must not also equip or mark an item for sale. Give a selection checkbox and a row's inspection action separate usable targets rather than nesting interactive elements. A visual grid does not require ARIA grid semantics; a composite keyboard grid brings additional navigation obligations. Carbon's table/selection guidance is useful for these task distinctions, not a mandate to turn inventory into an enterprise table. [S09](research.md#s09)

A wider workspace may show collection and detail together. When it narrows, retain the same object and draft; Back returns to the collection's previous filter and reading position. Resizing cannot clear a chosen transfer quantity or redirect it to a different item. [Adaptive layouts](foundations.md#adapt-the-task-not-just-the-boxes)

The current workspace keeps the two collection components mounted through ordinary hiding, layout adaptation and permitted same-character Resume. Each owns its location, search and continuation; item detail and quantity drafts are local supporting state. The world, character, private-draft scope and save timeline identify that retained work. Current access invalidates executable inventory reads immediately; retained drafts cannot execute until their required facts have refreshed. Same-owner control renewal, quiet pause and pending refresh retain the last authorized collection and reading position. An authoritative refusal, lost container root/access, or changed private owner clears the affected contents; obsolete completions cannot restore them. Private record details, history and merge previews still require their current evidence scope. Obsolete contents reads cannot replace a newer result. A selected item outside the current permitted page has an unavailable explanation without reusing its earlier inspection body. Quantity fields retain blank or intermediate text; All/Half fill the amount draft, and its named action submits it. Editing quantity does not clear a move's destination. A stale item or endpoint blocks submission while keeping the draft for deliberate refresh. A changed private owner, character, world or timeline clears the workspace's private work; original unresolved command recovery has its separate authorized lifetime described below. Source revisions, access and capacity remain checked by the native action owner when the player submits.

## Quick-slot bindings

The hotbar's ten slots retain exact item IDs for the current private character/session. Pressing a populated slot opens its current native actions; it stores no command authority. Right-click or Shift+F10 opens assignment, which reuses the inventory grid's search, continuation and carried-bag navigation. Choose an item, use **Open [bag]** to reach nested possessions, or choose **Empty slot**. Cancel preserves the previous binding. The slots resolve their own bounded current item facts, so owned items remain usable beyond the live view's summary window. Lost custody or container access makes a binding unavailable; neither a saved ID nor its earlier label authorizes an action. [Read envelope](../limits/interface.md#qs01--quick-slot-item-facts).

## Search, sorting and filtering at scale

Name the search scope: **This container**, **My accessible possessions**, **Nearby storage** or **Market listings**. The current inventory searches this container; a broader scope requires a permitted server query, not client-side inference or a hidden search of every world object. A result outside the current container needs its location and an intentional route to it.

Search matches the full permitted collection within the declared contract, not just currently rendered rows. When the backend examines a bounded window, say that more contents remain searchable and preserve continuation. Do not show a definitive no-results state before the search is complete. Keep query, filter and sort context when returning from detail; reset only when scope changes deliberately.

Each open collection reads one finite native page with its own search, breadcrumbs, **Next contents**, **First contents** and Refresh. There is one shared belongings reader and one reader for each explicitly opened bag, rather than another Inventory command owner per window. An inactive narrow bag suspends its read unless it is an explicit source or destination of the current quantity/detail task; closing it removes that reader. Pages also contain native Drop/manufacture choices, so relevant character support/free-placement changes invalidate those choices even if stock is unchanged. Search labels name that collection. An empty search window with continuation says that more contents remain; it does not claim the whole container has no match. A relevant native revision change invalidates actions and resets continuation to the first page with an explanation while retaining the visible collection during its refresh. Own carried contents do not refetch for unrelated camera, position or geometry changes; external storage still rechecks reach and access. Quiet disconnection, pause or hiding aborts pending reads without replacing the same private owner’s displayed belongings. Reopening requires fresh permitted results before actions become available. Opening a right-click action menu performs no inspection write and does not refresh or replace the inventory behind it. The [IW01 limits owner](../limits/interface.md#iw01--inventory-task-workspace) records page/scan bounds and their cold-index/native-admission exclusions.

**Controls** applies **Default order**, **Name A–Z**, **Name Z–A** or **Quantity high–low**, together with **All items**, **Equipped** or **Containers**, to the full permitted current-container collection before selecting the page. Equal sort values retain native order. Quantity means the displayed group's total units; these controls neither merge objects nor change which units a native action may use. Query, sort and filter bind the continuation and retained-result identity. Changing a control returns to the first page and withdraws stale actions while the new read settles; opening detail preserves the controls. **All items** clears filtering, and an empty filtered window with continuation remains incomplete. Merge-target selection retains its separate exact-lot eligibility and default order.

Native bounded storage discovery remains available to tasks that actually need a supply choice. Camp selection can name permitted carried/nearby storage and visible distant dropped bags by appearance/location; that exterior discovery grants no hidden contents or remote interaction. Approach and character inspection remain separate actions. The separate Offer task uses native recipient suitability for the exact source and amount, with its own search and continuation. Ordinary inventory pages do not discover every destination or unopened descendant. Partial and unavailable results retain distinct explanations and continuation/refresh routes.

Sort by a meaningful default with a stable tie-breaker; avoid moving rows while the player targets them. Changed price, quantity or condition should not unexpectedly teleport the focused row. Do not sort only a loaded page while labeling it globally sorted. Show active filters, a clear-all route and the distinction between zero items and zero matches. A selected-first presentation should use deliberate reordering points rather than move an option away mid-selection; Primer's picker implementation illustrates this concern. [S01](research.md#s01)

Filters that suppress loot require reversibility: show that filtering is active, explain why an item was hidden and allow inspection of hidden matches. Never infer **junk** from low rarity alone; usefulness depends on crafting, an authored world, a quest, a player's build and sentimental value. Diablo IV's 2026 loot-filter delivery and subsequent fixes illustrate both utility and incorrect hiding. [G02](research.md#g02)

## Item detail and comparison

Keep a stable fact order: identity and state; applicable use/equip action; requirements and costs; comparison-relevant values; deeper explanation and history. A selected item is not automatically equipped or consumed. Unknown properties are explicitly unknown, not silently absent from a comparison.

For comparison, show the candidate and actual comparison target together with identical units/conditions. Say **Compared with equipped iron knife**, not simply a green arrow. Distinguish base value, modifiers, effective result and uncertainty. Do not invent a universal item score or assume higher is always better; weight, noise, durability, reach and resource cost trade off. The world's permitted attributes define relevant dimensions.

The current comparison is deliberate and names the actual equipped object. Server-projected native characteristics supply meanings and units for both columns; the browser does not reproduce family formulas. Only matching characteristic identities and units enter the comparison; an unavailable value within a matching row is labeled unknown. No matching dimensions yields no comparison offer rather than a made-up score.

Make comparison deliberate and stable: a named Compare action or visible mode can coexist with a modifier-key shortcut. Do not make the shortcut the sole route or cover ordinary item inspection with unsolicited extra panels. Blizzard's July 2026 Classic UI follow-up restored comparison on deliberate input after an always-on regression. That is a caution about default behavior, not proof that Shift is the right binding for Open Legend. [S20](research.md#s20)

Keep equipment slots understandable but world-specific. Unavailable equipment explains unmet requirements. An offhand conflict, occupied slot or multi-slot item must be clear before commitment. A loadout, if implemented, stores intended choices with missing-item handling; it does not conjure absent gear, move inaccessible objects or authorize forbidden actions. FFXIV's gear-set/comparison workflows are task references, not a mandate to inherit its classes or equipment model. [G05](research.md#g05)

## Containers, stacks and identity

Equivalent homogeneous objects in one direct container appear as one quantity tile. Definition/version, units, actual item attributes and declared ownership must match. Containers, recipe records, attached equipment, individually authored objects and items with unsupported active state stay separate. Separate canopy posts are labeled **Individual object**; the UI does not invent condition differences between identical intact posts. Visual grouping leaves each physical identity, material origin and history intact. The current standard starting inventory’s nine physical cord objects appear as **Fiber cord ×11**.

A move or drop resolves a sealed current-container reference to exact members once, then commits through the existing atomic inventory owner. The command records the real members; capacity, custody, reservations, placement and revision failures change nothing. The existing native allowance is at most 16 source objects per operation; exceeding it refuses the whole choice with a smaller-amount explanation, never silently truncates. Each selected trade tile and other single-object uses explicitly identify the representative stack and its available amount; their quantity maximum and All/Half presets use that same stack. Groups do not acquire a new merge, barter or learning contract. Preparation and finite native evidence are recorded [here](../verification/player-experience-inventory.md).

Show location with breadcrumbs or an equivalent navigable path. Distinguish possession, location, declared ownership, custody and permission; the current declaration UI correctly explains that declaring an owner does not transfer an object or grant access.

For a move, make **source → destination**, quantity and relevant capacity visible. Retain the named source and open target while refreshing eligibility. Destination browsing belongs only to an explicitly entered storage-finding task. Explain invalid targets where permitted. A container cannot become its own descendant. If the target becomes full or inaccessible before completion, preserve intent and explain the changed condition without claiming success or demanding destination reselection. The player can deliberately choose another target or retry when valid.

Use an exact numeric input for quantities, with whole-unit rules only when required by the item/world. Show available quantity and the effect of Split, Move, Give or Drop. All/Half presets are accelerators, not ambiguous defaults. Do not turn blank draft input into a zero-unit mutation. Splits/merges must preserve server identity/history; visual sorting is not merging lots.

The current command path retains the exact command body, ID and epoch before sending, under a private native recovery scope. It prevents another inventory command while the outcome is unknown, including after a permitted reconnect/control change. **Check result** only reads the original receipt; it never resubmits or creates a fresh command. Session, account/grant revision, actor, world, timeline and audience changes do not inherit that recovery permission. Native custody, capacity, claims, contents and placement revisions remain authoritative. A resolved result refreshes both sides, and source focus follows the remaining neighbor or returned item only while that collection still owns focus.

Total holdings and units usable for the selected operation are separate facts. Defaults, selectable amounts and material-review dependencies use current usable quantities from the existing quantity/reservation owner; expose the total separately when it helps explain held units. Verify a partial hold that leaves the object eligible, such as six units with four committed to other work, rather than checking only fully free or fully unavailable lots. Current execution still follows [action admission](../action-capabilities.md#action-availability-and-temporary-execution); the chooser grants no reservation.

After a move, keep sensible neighboring focus and announce the actual result. Offer undo only when the backend can genuinely reverse the operation. Consumption, trading or irreversible world effects cannot acquire fake undo just because a toast has room for a button.

Delayed focus belongs to the initiating interaction and its exact collection. Hide, lost connection, a changed external container, later pointer/key input, window blur or removal cancels it. The later refreshed-item/neighbor step shares that same guard. Deliberately opening a bag beside belongings binds the new collection when that exact navigation commits; an old result cannot choose whichever collection is currently open. Ordinary popup return to the original item remains supported. This uses the existing Inventory owner and preserves the original request/receipt path; browser qualification and the older unresolved popup-dismissal cause remain separate in the [focused plan](../projects/game-interaction-redesign-tech-design.md#keep-inventory-focus-with-the-current-interaction).

## Bulk operations without bulk mistakes

Bulk mode is explicit. Show the number selected, scope and a clear exit. **Select this page** differs from **Select all matching results**. Changing filters either retains selection with an honest hidden-selection count or clears it with an explanation; never silently reinterpret selection.

Once a batch is being prepared, use a selection-aware action bar and avoid competing row commands that make it unclear whether one item or the batch will change. Read-only inspection can remain available when it preserves the batch. Do not indiscriminately freeze unrelated controls. This adapts Carbon's batch-action model to an inventory task. [S09](research.md#s09)

Show eligible, excluded and affected objects/units, with reasons for exclusions such as equipped, locked, reserved, quest-relevant or inaccessible only where those concepts are supported and disclosable. Keep valuable-object protection visible and reversible. Name the operation: **Move 12 stacks**, not **Apply**.

Backend atomicity determines UI promises. An atomic rejection changes nothing; a permitted partial result identifies what changed and what did not, with exact quantities and a retry only for the remainder. Do not blindly retry everything after a timeout. Preserve request identity and reconcile authoritative state before another consequential attempt.

## Reducing chores is better than hiding chores

Stable locations, categories, reusable filters and named equipment/storage presets can reduce repetition. RuneScape bank placeholders preserve organization when stock changes; this historical reference does not prove every game should reserve empty physical slots. [G03](research.md#g03)

ArenaNet's 2025 consolidation of travel/exchange convenience items illustrates reducing bookkeeping objects rather than merely enlarging bags. Adopt that only when their physical existence is not important to Open Legend's mechanics. Do not convert every key, currency or tool into an account entitlement without a world-design decision. [G06](research.md#g06)

BG3/GW2 player discussions show both friction and disagreement about workarounds. Make sort, sell intent, purpose and salvage consequences discoverable; do not interpret a few complaints as consensus or all complexity as bad. [P01](research.md#p01) [P02](research.md#p02)

## Trading: inspect, agree, commit

PX02 delivers direct item exchange and the Gildmoss integration adds baskets with several item kinds per side. Vendor purchase, auction/order placement, asynchronous listings and the commercial guidance below remain future scope; their guarantees and costs differ from direct exchange.

For **direct exchange**, show both participants and offered sets, exact quantities, relevant item identity/state, currency and fees. Distinguish your side from the other side. Offer edits invalidate agreement to the prior revision; highlight changes and require renewed acceptance. The server exchanges atomically or reports actual failure; a changed offer cannot retain a misleading accepted state.

**Current direct barter:** [PX02](../maintainers/parallel-batch-04-expeditions-and-exchange.md#px02--reciprocal-barter) now presents exact item sets and quantities per side, **You give / You receive**, current reply status and adjacent controls in the Trade window opened from a person’s action menu or Inventory. Its Gildmoss workspace puts a reused paged/searchable Inventory collection beside both baskets and perceived conversation, with one existing Speak owner for negotiation. Only previously disclosed other-person items appear, explicitly labeled last-known rather than live stock. Changed revisions require review; stale/refused attempts keep drafts. The person-menu and Inventory entries share the same draft and submission guard; the selected starting quantity is separate from the current available maximum. Reconnect/Resume/reopening retains private drafts within the same account, character and timeline, without resubmitting. Existing receipts and ordinary witnessed/private events show actual settlement. No currency, fees, vendor or listing is implied. [Selected actual evidence](../verification/reciprocal-barter.md) distinguishes client, database and controlled live resident results.

For **market/vendor purchase**, show unit price, quantity, total, currency, fees, destination and availability. Distinguish asking price from completed-sale history, with source/time window when displaying market evidence. Selecting a listing is not buying. A changed price or unavailable listing cannot be accepted silently. Review expensive/destructive consequences without confirmation fatigue for harmless browsing.

For **selling**, distinguish listing, immediate sale and destruction. Show net proceeds, fees and remaining quantity; protect equipped/locked objects where supported. Pending is not **Sold**. A successful exchange has a durable receipt/history; disconnection must not manufacture two apparent owners. Reopening a panel is read-only, not a second purchase.

These requirements follow transaction reasoning and existing authority principles. FFXIV's market guidance provides an interface example, not Open Legend's economic rules. [G05](research.md#g05)

## Representative acceptance tasks

Find an unfamiliar invented item; distinguish same-name items in nested bags; compare without memorizing values; split exact units; move after capacity changes; recover from a stale revision; repeat with keyboard only. Retain selection/quantity through pane adaptation. Direct-trade qualification includes changed baskets, duplicate submit and disconnection. Future bulk/market cases include hidden selection, row-versus-batch ambiguity, partial success and stale price. Measure success/errors before choosing a more elaborate visual inventory.
