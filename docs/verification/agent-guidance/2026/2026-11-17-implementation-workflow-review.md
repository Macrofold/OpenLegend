## The workflow in plain language

**Architecture.** A world defines its rules. The simulation checks an action against the installed rules and records its effects once. The server enforces access and chooses what each person or character can see. The client displays that information and sends intentions. For example, a world decides what someone can learn from inspecting a record. A label on the screen or a suggestion from an AI cannot grant that knowledge. Add world content when the existing mechanism can express the rule. Change the mechanism when the game needs a capability it lacks. [Architecture decision guide](../../../engine-and-world-boundaries.md#5-a-repeatable-boundary-decision).

**Implementation.** Describe what a person should be able to do and what would show that it works. Find the code responsible and follow its real callers. Make the smallest complete change there. Check an assumption early when getting it wrong could harm real resources or invalidate substantial dependent work. Once the connected behavior works, verify it through the actual entry point, review the affected changes, update the existing records and commit locally. A one-line fix can use a short plan in the conversation. Use a written plan when uncertainty is substantial, a contract spans layers, or the work is likely to span substantial stages or sessions. Reuse the existing project plan or tracker. [Implementation workflow](../../../../.agents/rules/implementation.md).

**Testing.** Choose evidence for the claim. If an access rule changes, exercise both a permitted request and a refused one. A controlled AI reply can prove the server sends a request, accepts a valid response and saves the result. It cannot tell us what a live model would choose. Run focused correctness checks locally when suitable. Time a speed comparison on the standard managed AWS worker unless Mike explicitly selects another environment. Plan expensive runs before spending. [Verification](../../../../.agents/rules/verification.md) and [comparison planning](../../../performance/measurement.md#planning-comparisons).

## Corrections made

The recurring problem was scope. A command shown as an example looked like a required check for every change. A rule for one experiment appeared to grant money to a later one. A statement about one revision of a tool appeared to describe the deployed service today. The fixes put the condition before the instruction and link to the owner of the detailed procedure. This keeps short tasks short without dropping the checks a higher-risk change needs.

## Where the existing rules already answer the question

- **Timing and aggregation.** Repetition counts, the primary metric and acceptable tradeoffs belong to the particular experiment. Apply an existing project threshold when there is one. Otherwise decide before seeing results, report the individual runs, and identify whether a percentile covers commands or entire runs. Three repeats in a named design do not set a universal minimum. [Measurement](../../../performance/measurement.md#planning-comparisons).
- **People and devices.** A functional browser check can establish that a control works. A claim about an uncoached player's understanding needs a participant. A proposed screen size or test fixture alone does not promise support for every device. [UI verification](../../../ui-ux/verification.md#choose-checks-by-changed-behavior).
- **Merge checks and tests.** The current workflow names task requirements, impacted checks and reconciliation checks. There is no documented universal full-suite requirement for every merge. Agents may run existing checks. They need Mike’s request to add a maintained automated test. A temporary scenario through a real caller is available when the needed check is missing. [Verification](../../../../.agents/rules/verification.md#select-checks-for-the-task).
- **Independent work and conflict stops.** Agents can coordinate changes within an authorized implementation. Standalone assignments prepared for separate chats must each be independently completable. An unresolved Git conflict has its own explicit all-work stop. A bad optional experiment can finish a measurement. A broken required player journey still needs repair. [Independent assignments](../../../../.agents/skills/create-parallel-tasks/SKILL.md), [reconciliation](../../../../.agents/skills/openlegend-rebase/SKILL.md#conflict-resolution) and [completion](../../../../AGENTS.md#completion-and-handoff--every-task).
