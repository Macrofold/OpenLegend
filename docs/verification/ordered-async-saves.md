# Background world saves and save recovery

[Plan](../projects/ordered-async-saves.md) · Trackers: [PF00/PF02/PF06](../maintainers/performance.md), [SL08/SL09](../maintainers/save-and-load.md), [D1/D2](../maintainers/production-data.md#remaining-d1d2-implementation-and-evidence).

All timings below are **shared-host** measurements: other agents were loading the same 10-CPU machine and its PostgreSQL 14.17 server (load averages about 100–360 in the reported runs). They show relative attribution and correctness, not acceptance or capacity. Runs used disposable PostgreSQL databases, `AI_BUDGET_USD=0`, zero-cost fixtures and no provider calls. Raw reports stay private under `/private/tmp/openlegend-save-stall-20260928/`.

Terms: a **background save** writes simulation progress while the game keeps running; a **synchronous save** (player commands, AI characters' finished actions and replies, pause/resume, editors, loads) holds the world mutation queue until written ([definitions](../save-and-load.md#background-and-synchronous-world-saves)).

## PF00 save-path attribution (stage 1)

Tooling: `scripts/profile-server.ts` gained `OPENLEGEND_PROFILE_SQL_DELAY_MS` (added per statement after queue admission, only on the fixture's own connections), per-commit attribution and an undelayed `SELECT 1` host probe on its own connection. `WorldService` records `mutation.hold`, how long each operation owns the mutation queue. See [profiling usage](../maintainers/performance-profiling.md#full-server-scene-profiler).

Attribution splits each world commit into: preparation plus writer-queue wait before the first statement (`preMs`), statement round trips (`statementMs`, storage including injected delay and PostgreSQL scheduling), and time between statements (`betweenMs`, main-thread work, GC and event-loop contention).

Baseline revision: `origin/main` `be68b1e0` plus the instrumentation only. 30-second 3× scene with cognition and speech fixtures, seed 73, 20 people, 20 animals, 100 objects.

| Injected delay | Load (1 min) | Achieved speed | Commits | Commit p50 / p95 / max | Statement share | Between-statement share | Pre-statement share | Probe p50 / p95 | Update gap p95 / max | `mutation.hold` p95 / max |
| -------------- | -----------: | -------------: | ------: | ---------------------: | --------------: | ----------------------: | ------------------: | --------------: | -------------------: | ------------------------: |
| 0 ms           |      185–191 |          1.53× |     168 |    80 / 658 / 1,214 ms |             94% |                    1.4% |                  4% |       5 / 63 ms |       285 / 1,175 ms |            370 / 1,229 ms |
| 25 ms          |      149–162 |          0.15× |      27 | 967 / 1,918 / 3,714 ms |             97% |                    1.4% |                  1% |       2 / 45 ms |     1,510 / 3,679 ms |          1,516 / 3,757 ms |

- Save-path time is dominated by statement round trips, not main-thread work. At 0 ms a commit averages 17.6 statements and 7.4 ms of statement time per statement (21,970 ms over 2,956 statements); the median commit spends 74 ms in statements, about 4 ms each, near the probe's 5 ms median round trip, so a typical statement costs roughly one scheduling round trip to a contended PostgreSQL; p95 spikes match probe p95 spikes.
- At 25 ms injected, statement time rose to 46.8 ms per statement (+39 ms) and the median commit from 80 to 967 ms, about 1.8× what 19.9 statements × 25 ms predicts. The excess is not attributed: the injected delay is a timer that fires late on the loaded event loop (timer lateness p95 40 ms), and the slowest commits wrote more rows. Two delay points do not establish linearity. Native time falls to 0.15× because on this base every save, including simulation progress, is a synchronous save that holds the mutation queue.
- The 100 ms case could not start: `CREATE DATABASE` exceeded the fixture helper's 5-second statement timeout twice under load (PostgreSQL error 57014). It is covered in the stage 2 matched runs.

## Background saves for simulation progress (stages 2–3)

Implementation: [ordering and failure design](../projects/ordered-async-saves.md#ordered-persistence-design). Before code, a four-lens adversarial review (ordering, history release, publication/paid work, failure/crash) was run against the design and the code. Its confirmed findings changed the implementation before any drill: a background save refused before `BEGIN` re-submits the same prepared change set instead of letting a later snapshot diff against the unreleased baseline (which would have deleted released records); any `storageError` assignment rejects durability waiters; waiting commands defer new background saves; durable marks carry the snapshot sequence and event counter, publish once per load and are delivered from a root context; and `flushMemorySources` takes a queue turn so an earlier forget commits first.

Correctness drills (ad-hoc, not repository tests) drove `WorldService` directly on disposable PostgreSQL with a host-like 50 ms timer, 3×, seed 73, 20 people, 21 animals, 60 objects, 40 ms injected per statement after a 6-second undelayed warm-up. Final run: 30/30 checks passed.

| Case                                         | Observed                                                                                                                                                                                                                                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Several pending saves                        | At most one world write at a time; revisions strictly `+1` in snapshot order, each expecting the previous revision; durable marks strictly increasing; every durability wait resolved by a mark covering its ticket; native time kept advancing while writes were in flight; all commands succeeded. |
| Capture during a background save             | Manual checkpoint requested while a background save was in flight captured a durable revision (flush waited for the write first).                                                                                                                                                                    |
| Busy before `BEGIN` (twice)                  | Same prepared change set re-submitted and committed; no storage error; SQL row counts did not decrease; every resident value present in SQL.                                                                                                                                                         |
| Busy past the retry limit                    | Storage error latched after four refused attempts; nothing written afterwards; durability waits rejected; restart recovered the last durable revision; no rows lost.                                                                                                                                 |
| Failed background save (record write throws) | Storage error latched, world paused, later command refused, no further write attempted; restart recovered exactly the last durable revision.                                                                                                                                                         |
| Failure at `COMMIT`                          | Storage error latched; a direct repository commit afterwards was refused (“baseline is unknown after a failed save”) instead of reloading and diffing; restart lost no rows.                                                                                                                         |
| Final durability                             | After `flush`, the durable head equalled the last durable mark and every resident value was present in a full SQL load.                                                                                                                                                                              |

Crash drills ran a child server process with 150 ms per statement:

- **SIGKILL during an in-flight background save:** restart recovered exactly the revision the write expected to replace, with the last durable mark's simulation time; full recovery audit passed.
- **SIGKILL after `COMMIT`, before the service settled the write:** restart recovered the committed revision; full recovery audit passed.

A second, code-level adversarial review then changed the implementation again: refused background saves now pause 0.5, 1 and 2 s between attempts (a full writer queue refuses instantly), one 5-second admission budget covers a command's wait for the in-flight write and for the queue, a refused synchronous save of simulation progress forgets its computed history release, and a load refused before its transaction restores the released baseline. The unchanged drills were rerun after these fixes (load average about 200) and passed 30/30 and 7/7, but they exercised only the retry pauses (case E: two refusals then a commit; case F: four attempts then a latch) and, through case C, an operation waiting for an in-flight write and then entering the queue with its remaining budget. They never ran out of that budget, never fell back to a synchronous save and never loaded a save during a write. The [hardening drill](#paths-the-final-review-found-unexercised) below covers those paths.

Across drill runs no simulation-progress snapshot needed the synchronous fallback (no retirements, terminal appraisals or contributions in that fixture). The matched scene runs below made only three background saves in total and never fell back, so fallback frequency is not yet established on a representative workload. Commands still use synchronous saves, because their effects must not be published before they are durable: at 40 ms per statement under load averages of about 305–315 (a run before the second review's fixes), one command commit held the queue for 6.9 s. The rerun after the second review's fixes had a worst hold of 4.8 s at a load of about 200, and the rerun on the final code 2.3 s at a load of about 105–115; with one run each on a loaded shared host, the drop is not attributed to the fixes.

After the final review's fixes, which changed routine-save timing and shutdown settling, the unchanged ordered-save and crash drills were rerun on the final code: 30/30 (load about 105–115) and 7/7 (load about 200).

### Paths the final review found unexercised

A final five-lens review with independent verification found that the reruns above did not exercise several changed paths. A separate drill drove `WorldService` on a disposable database with in-process faults: a write held before `BEGIN` (slow storage), a writer refusal of one background save, a writer refusal of one restore transaction after the complete world had become its diff baseline, and an injectable wall clock. Final run on the final code: 35/35 checks. An earlier run timed out because the drill itself waited for a tick that was waiting on the write the drill held, and two cases assumed timings a loaded host broke (a held save that happened to be synchronous, and a helper operation that missed its own admission window); the drill was corrected to retry such trials and rerun.

An HTTP drill ran the real server in-process (8/8): the autosave settings and acknowledgment routes worked through the fenced mutation path and still refused a stale revision; with the mutation queue held for 7 s, a load answered busy after 5.0 s at its pause step without latching a storage error (before the fix this locked the world until restart), and the same load succeeded once the queue was free. The revocation race that motivated fencing those routes was not reproduced (local mode has one account).

After the save code was renamed to the background/synchronous terms (names and comments only, 2026-09-29), the hardening, ordered-save and shutdown drills were rerun: 35/35, 30/30 and 5/5 (load averages about 145–215).

### Matched scene runs (PF00 delay cases)

Baseline `b06ee549` (instrumentation only) and candidate `ba4258ff` ran the same 30-second 3× cognition-and-speech scene as stage 1 (seed 73, 20 people, 20 animals, 100 objects) in ABBA order, back to back per delay, with 0, 25 and 100 ms injected per statement. One-minute load averages were 118–213 at the start of each run (114–217 at the end) and fell during the matrix. Two runs per build and delay; values are the mean of the two.

- **This scene's queue time is dominated by synchronous saves, which the change deliberately keeps.** Its slowest commits write player-command receipts and conversation transitions (speech and AI results), which change the world only after their own durable commit ([SB21](../limits/persistence.md#sb21)). They arrive often enough that simulation progress is almost always saved as part of one of them: across all candidate runs only three background saves happened. With 25 or 100 ms per statement both builds therefore still slow native time to 0.08–0.17× (single runs 0.07–0.18×), and every run at 100 ms had one speech request answered busy in both builds.
- At 0 ms the candidate's 95th-percentile queue hold fell (93 against 230 ms) and speed was higher, but its two worst holds were single synchronous saves whose time was almost all PostgreSQL round trips on the loaded host: a 2.1 s conversation commit and a 3.4 s synchronous save that wrote no command receipt or conversation records (its operation was not identified); with two runs each, neither the improvement nor the worse maxima is attributable.
- No run latched a storage error; no background save was retried or fell back to a synchronous save.

Simulation progress now uses background saves, but this scene does not yet show a stall-free world under slow storage: that now requires moving commands and AI results from synchronous to background saves, which needs durability-gated publication (PF05) and is an open decision.

## Save recovery (stages 4–7)

Ad-hoc drills (not repository tests) drove the real services on disposable PostgreSQL databases with `AI_BUDGET_USD=0`, load averages about 70–270 in the final runs. Faults were injected from outside the product: read-only save folders, PostgreSQL triggers and a preload that delays or fails the driver's statements. Final runs of the drills below used the final code, except the first Game panel walkthrough, which ran before the final review's panel changes (the settings-conflict check ran after them).

### Autosave settings, manual-save priority and failure records (C05, SL08-A)

One drill (final run on the final code: 36/36 checks, shared with the SL09-A/B checks below):

- **Settings:** defaults were on, every 5 minutes, keep 3 (revision 0). A stale revision and an out-of-range cadence were refused. Settings survived restart. A stored record that was not JSON was reported as invalid with automatic saves off, and an explicit save replaced it (before the fix it could never be replaced). A failed settings read (injected read error, not damage) was reported as a failed read, retried after 30 s of running time, recorded as a checkpoint failure after three failed reads and then recovered the stored settings, never defaults.
- **Busy count:** with two busy refusals, a real failure and then one more busy refusal, the real failure's record stayed; only consecutive busy refusals count toward the busy report.
- **Manual save ahead of the next autosave:** while an automatic capture held the capture slot, a manual save waited instead of failing busy; a second, different manual save got busy; an autosave opportunity during the wait deferred. The waiting save held its place for about 0.51 s (mostly the drill's own pauses) until the slot was released, then completed, and the next autosave ran after it. Retention followed the setting (two kept).
- **Failure record:** an unwritable save folder recorded an automatic-save failure; a refused load recorded a recovery failure. The record survived restart with the same identity until acknowledged, and the acknowledgment also survived restart.
- **Settings conflict (browser):** with an unsaved edit in the panel, another request changed the stored settings; saving from the panel was refused, the panel then showed the stored values with “changed elsewhere; showing the stored settings”, and re-applying the edit saved revision 2. Before the fix the panel kept the old revision and every retry conflicted.
- **Game panel (browser, disposable server):** the settings form saved 1 minute / keep 2; a manual save completed and the save-folder size appeared; a failed manual save and a refused load each showed “Checkpoint failure at …” with an Acknowledge button and the restart wording; the notice persisted across a page reload and cleared on acknowledgment; after the folder was writable again the load succeeded and a “Before last load” recovery slot was written. The check found that a refused load showed its notice only after a manual refresh; the panel now refreshes after a failed load or deletion.

### Load safeguard (SL09-A)

- **Unwritable save folder:** loading a healthy save was refused (“Load refused; the current world was kept (paused) …”). No storage error latched, the durable revision did not go back and simulation time was unchanged; the refusal was recorded as a recovery failure. After the folder became writable the same load succeeded.
- **Oversized current world:** a 1.1 MB memory record (above the 1 MiB record allowance) made capture impossible; the load was refused before any change, without a storage latch and at the same revision. Retained source-version history keeps that value, so this world stays uncapturable; [SB13](../limits/persistence.md#sb13) gives the operator path.

### Capture order and retention (SL09-B)

- Catalog and rotation followed the durable capture sequence. With the newest capture's wall-clock time set to 2001, rotation kept it and removed the older one; equal timestamps also ordered by sequence.
- A slot with broken metadata was not listed, was counted as a catalog issue and was never deleted by rotation. The reported save-folder bytes equalled the directory's actual file bytes, including that slot.
- **Cleanup failure:** with an old autosave made undeletable, the new autosave was published, the old one remained and the failure was recorded as “Autosave retention failed”.
- **Checksum-valid but invalid package:** a package with its world-settings record removed and its checksum and counts rewritten passed file verification but was refused when read for loading (“Missing world_settings record; recovery refused.”).

### Operational restore file reconciliation (SB18, D1/D2)

`scripts/restore-world.ts` ran as a child process against a real operational backup (three retained slots); a PostgreSQL trigger failed the installation. Final run after the review fixes: 18/18 checks:

| Case                                                          | Observed                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fresh target, failure during install                          | Restore failed; the three slots it copied were removed; database empty; source backup byte-identical. Retry after removing the fault installed every retained slot.                                                                                                                                              |
| Existing target missing one slot                              | Restore failed; only the one newly copied slot was removed; pre-existing slots untouched (same inodes); world head unchanged. Retry restored the slot.                                                                                                                                                           |
| Existing target, failure after install began (history insert) | Restore failed; its pre-restore recovery checkpoint (now written before the installation transaction) was removed, no slot was left behind and the world head was unchanged. Retry succeeded and left exactly one new recovery checkpoint. Before this fix the in-transaction recovery package leaked, unlisted. |
| Failure raised by `COMMIT` (deferred trigger)                 | Reported as an uncertain commit and kept the copied slots for inspection, naming them; the database had in fact rolled back.                                                                                                                                                                                     |

Earlier runs of this drill failed at the retry steps with “Unsupported backup schema” and “Unsupported save format”: `scripts/restore-world.ts` on `main` (`be68b1e0`) refused every current backup, because full restore compared the backed-up schema marker with '1' while the store writes '2', and existing-world restore sent payload format 'backup', which the save installer rejects. Both date from `104528f4`. This branch accepts only the current schema and save format, and the retries above are the evidence that operational restore works again.

Process death between copy and install and a data directory shared with another operation remain unreconciled ([SB18](../limits/persistence.md#sb18)).

### Bounded shutdown (PF06)

The real entry point (`apps/server/src/main.ts`) ran as a child process with a preload that could delay every statement or fail `COMMIT`; each case sent a signal while background saves were running. Final run after the review fixes: 5/5 checks:

| Case                                                                            | Observed                                                                                                                                                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 150 ms per statement, write in flight                                           | Exited 0 after 2.7 s: “Open Legend stopped; world saved at revision 10”, equal to the database head.                                                                           |
| Storage already latched (failed `COMMIT`)                                       | Exited 1 after 0.09 s: final save skipped with the storage message; “stopped WITHOUT a confirmed final save” with the last revision confirmed durable and its simulation time. |
| Two SIGINTs 5 ms apart (what `tsx watch` sends on Ctrl-C), 150 ms per statement | Exited 0 after 2.6 s with “world saved at revision 10”; the second signal was treated as the same request.                                                                     |
| 20 s per statement (stalled storage)                                            | Exited 1 after 31.0 s: the final save and storage close reported as past the deadline; “stopped WITHOUT a confirmed final save” with the last revision confirmed durable.      |

An earlier run of the stalled case exited only at the 45 s backstop because stuck database sockets kept the process alive after its report; the process now exits one second after reporting. Under `pnpm dev` itself (the `tsx watch` runner, which also force-kills the server 5 s after relaying a signal) shutdown was not run; the duplicate-signal case reproduces its relayed SIGINT.

### Slow-output snapshot pressure (SL09-C)

A 3× scene (20 people, 21 animals, 60 objects) ran for a 40-second window without a capture, then for a 40-second window while a checkpoint held its read snapshot and wrote through a file writer throttled per record. Durable move commands were issued throughout and the database was sampled every 0.5 s.

| same                                | 25 ms per record  | aborted by the two-minute deadline at 120.2 s | up to 85                           | 128 / 350 / 2,304 ms    |

After each abort the snapshot was released (age 0–1), no staging directory remained and no storage error latched. Not covered: a stall inside one filesystem write, sync or rename, which the between-record deadline cannot interrupt, and a larger write-heavy world on a quiet host.
