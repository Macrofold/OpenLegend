### Measurement method

A disposable PostgreSQL public-view fixture ran sequentially in Chromium WebGL2 with ANGLE Metal / Apple M1 Pro and SwiftShader. The scene has six rendered entities (person, deer, rock, crate and two fires), plus existing scenery; the dense fixture adds 120 deer for 126 total. Earlier 7/127-entity records below used a different fixture. The performance viewport is 1280×720, with the renderer's existing 0.8 scale producing a 1024×576 framebuffer. Camera is orthographic, focus `(13,0,12)`, yaw 0, pitch 0.88, zoom 6, following off; public time is paused at noon or midnight. Startup includes source/asset/shader warmup; steady samples follow 60 rendered warmup frames. GPU observations use PlayCanvas's asynchronous disjoint timer-query profiler; CPU is its update plus render time. Frame intervals are display-paced on hardware. Tracked graphics bytes are PlayCanvas allocations, not OS GPU-residency measurements. No CPU throttle is presented as GPU emulation.

Raw frame samples and integration counters are kept outside Git under the current verification policy. The initial flat-sprite filter comparison uses Detailed/Economy/Economy/Detailed ordering, 180 frame samples each, on both backends for day, night and dense day (24 runs). On Metal, median GPU times are approximately 2.29 → 1.01 ms for six entities, 3.30 → 1.24 ms for 126, and 1.10 → 0.82 ms at night. Tracked daytime graphics allocation falls from 41.4 MB to 16.2 MB. SwiftShader also benefits, but remains slow: representative daytime intervals are 125–134 → 87–89 ms; dense daytime 196–224 → 114–126 ms. These results justify an optional cheaper map/filter configuration, not automatic device detection or a claim that software rendering is a playable low-end target.

The first 96-sample relief candidate submitted about 0.91 million triangles in dense daylight. The final deer has 452 triangles idle and 448 in the exercised movement frame. Geometry is shared by texture/frame; neither quality choice adds a draw per body part.

The geometry comparison before the final reveal-order repair uses flat/relief/relief/flat ordering with 120 samples per case. Six-entity Detailed GPU medians are 2.27–2.28 → 2.37 ms. Dense Detailed medians are 3.29 → 3.24–3.96 ms; dense Economy is 1.23–1.24 → 1.78–1.85 ms. The geometry has a cost, and variation does not support claiming a Detailed speedup. Final dense Detailed versus Economy is therefore approximately 3.24–3.96 versus 1.78–1.85 ms. Final allocations are 41.9 versus 16.7 MB. Dense total/shadow draws change from 713/391 for flat Detailed to 719/397 for relief, due to the changed bounds/light coverage. Hardware median frame intervals remain near 8.3 ms; noisy GPU p95 values reach about 13.1 ms in this short run. This is renderer headroom on one host, not a full simulation/browser capacity pass or sustained tail-latency guarantee. Warm navigation-to-ready measurements are about one second for either representation and do not isolate asset-generation latency from browser/server setup.

The relief/software comparison before the final reveal-order repair uses 60 samples after 60 warmup frames for each of flat/relief × six/126 entities × Detailed/Economy. Final representative intervals are approximately 195.5/140.8 ms and dense 284.8/156.6 ms (Detailed/Economy); the flat dense baseline is 218.8/112.0 ms. Relief adds work on this backend too.
