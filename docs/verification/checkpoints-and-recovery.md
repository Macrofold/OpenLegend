### Workloads and measured bounds

The initial SQLite comparison kept the same active world and increased one actor's cold history from 1,000 to 100,000 sources. Original preparation materialized all 100,000 sources: 1,187 ms; original save took 3,390 ms, with a 2,970 ms maximum timer gap and 935 MB process peak RSS. The bounded selector prepared 128 sources in 14 ms; the worker checkpoint took 1,789 ms with a 26 ms maximum timer gap in the same isolated capture-style probe. Its 97,082,364-byte package exceeded 64 MiB and reconstructed the exact saved state. This comparison excludes native gameplay and must not replace the end-to-end results below. Initial main-thread streaming still produced 262–654 ms gaps and 13.5–18.2 second saves; that measured CPU cost justified the owned worker and correcting keyset queries to omit the fixed world-ID prefix from the cursor.

A warmed native walk/save run with 100,000 cold sources prepared 128 in 5.8 ms, published 100,480,528 bytes in 2,295 ms, completed 133 native ticks and moved the player from X=11 to X=14 while output continued. Capture RSS rose from 303 MB to 374 MB; the largest timer gap was 139 ms. Paused restore took 5,644 ms; full-process peak including candidate reconstruction and subsequent drills was 1,146 MB. A cold/unwarmed run was materially worse (6,593 ms save, 860 ms gap and 16,383 ms restore), so fixture construction, warmup and GC are explicit rather than hidden.

The checked-in `scripts/stress-checkpoints.ts` performs native warmup, scoped maintenance, walking and repeated immutable saves while ticking, then paused validation/restore. It reports hardware, per-stage distributions, timer gaps, RSS and bounded runtime attribution. Its continuation check compares a further native step across save/restore, including RNG, processes, inventory, definitions and evidence; only operational pause and absent-versus-zero archive count are normalized. No model response is used. Run with a new report path and, for PostgreSQL, an **empty disposable** database:
