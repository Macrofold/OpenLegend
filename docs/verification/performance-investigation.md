## Performance investigation

### Review runtime observations

A disposable native SQLite world ran through the production HTTP server with no provider credentials and zero AI budget. It accepted movement, returned the same result on duplicate and paused retries, reached `(12,13)`, delivered native speech, and exposed that speech in the first direct public projection while optional status was unresolved. The public view reported saved persistence and 11 visible entities. The history revision advanced after native narration fallback; explicit regeneration succeeded and advanced it again. The server closed cleanly. This verifies the no-provider fallback path, not generated prose, browser rendering, PostgreSQL or scale. The production build passes; no automated tests were written or run. The native run was repeated after the cancellation and Talk opening-signal fixes with the same successful command/speech outcomes and clean shutdown. Browser opening-scroll behavior and pending-read cancellation/edit races remain in [deferred coverage](../maintainers/TODO.md#deferred-performance-validation).

### Continued implementation runtime observations

The production build passes. No automated tests were written or run. Native verification used Node 22.23.2 on an Apple M1 Pro, local SQLite, isolated saves, no provider credentials and zero AI budget. [Raw samples](performance-continued.json) retain successful outcomes and timing data. These are small runtime observations, not browser, PostgreSQL, soak, AI-quality or population acceptance.

Twelve walks from cloned small-world snapshots compared the 250 ms and 50 ms cadences. Both contained 1,599 synthetic historical rows in addition to native events. First changed position received over SSE had a median of approximately 157 ms / 58 ms and a maximum of 164 ms / 63 ms, respectively. HTTP acknowledgement medians were approximately 9 ms / 13 ms. The clean candidate's native-step p95 was 4.81 ms and command-durable p95 was 11.70 ms across 24 move/cancel commands. These tiny samples do not establish tail percentiles. The first candidate run overlapped backup/restore work in another process and recorded a 339 ms movement outlier; it is retained in the raw evidence. No run measured browser paint. Each paused one-second sample observed zero SQL statements.

The application replayed a committed gameplay result before and after restart, rejected a conflicting body and an unknown command epoch, and served/deleted a cold event through the owner API. A synthetic history fixture produced 1,087 archived rows outside a roughly 550-event working set while preserving SQL history. The backup script exported it, the restore script loaded it into an empty target, and an existing-world restore removed a post-backup fixture event while preserving current receipts. Source authenticity and live cognition were not evaluated. Exact expiry/pruning boundaries, corrupt archives, concurrency/failure matrices, naturally aged worlds and PostgreSQL recovery remain in [deferred coverage](../maintainers/TODO.md#deferred-performance-validation).

### Original query-amplification baseline

A direct execution fixture before these optimizations, with seed 73, an in-memory SQLite store, explicit zero spending and no credentials, admitted one movement intention for the controlled actor. Instrumenting repository statement execution after initialization/presence admission counted 16 SQL statements for its one `action-started` event with two audience members. The PostgreSQL adapter additionally sends `BEGIN` and `COMMIT`: static path inspection predicted 18 serial database operations for that ordinary non-checkpoint case. Of the 16 statements, 12 belonged to history projection, including the existing-row check, revocation lookup and five deletions even for a new event. This is baseline query-amplification evidence, not current statement counts or measured PostgreSQL response time.

Configuration inspection exposed only a loopback/non-loopback classification; the configured PostgreSQL address is loopback. It does not establish the physical backend topology or latency. Earlier reasoning that attributed the delay to a remote database was not verified. Exploratory CPU runs on a copy of the older local SQLite save showed substantial draft-finalization work and sensitivity to retained history, but were not a controlled current-save before/after benchmark. Some initial command samples were rejected because that saved player was incapacitated, so those timings are not successful-walk evidence.

No live browser-to-PostgreSQL command trace was captured, no paid call was made, and no runtime optimization was implemented in this investigation. Reproduce with outcome validation, actual PostgreSQL timing and the same workload through [PF00](../maintainers/performance.md#pf00--baseline-and-attribution) before assigning a dominant latency cause or claiming a speedup.

### Performance foundation runtime observations

On 2026-09-21, the production client build and runtime TypeScript build passed on an Apple M1 Pro, Darwin arm64, Node 22.23.2. A disposable seed-1086 SQLite world ran through the actual loopback HTTP application with an empty environment except runtime paths, port, temporary data directory and an explicit zero AI budget. No automated tests or paid/provider calls were written or run. The existing Vite large-chunk and PlayCanvas worker externalization warnings remain.

The final native run recovered position `(12,13)` and paused/saved state from a clean restart, accepted 30 movement requests plus one separate walk, reached `(11,13)`, and reported saved persistence. Its 31 successful durable command samples had p50 2.88 ms, p95 17.75 ms and p99 30.22 ms. These are short-sample descriptive order statistics, not stable tail estimates. An earlier run measured p95 3.93 ms, illustrating run-to-run variation; neither establishes a controlled before/after speedup. The final run's 60 native-step samples included a 45.73 ms maximum, so an eight-millisecond continuous CPU budget is not established merely by yielding between steps. Paused idle observation issued zero statements over one second.

A separate accepted walk from `(11,13)` to `(12,13)` returned its HTTP acknowledgement in 6.46 ms and delivered its first changed position through SSE in 258.77 ms. This is stream receipt, not browser render time; it does not meet the proposed 200 ms first-position target and does not justify adopting a higher cadence before CPU qualification. The preceding combined run had no usable first-position sample. [Raw bounded samples and workload metadata](performance-native.json) preserve both observations.

No PostgreSQL runtime, browser/React paint, mature-world replay, narration-provider execution, crash-in-flight recovery, multiplayer admission or population/crowd qualification was performed. In particular, this does not establish support for 100 agents, 100 independent players or thousands of animals. Deferred regression and load coverage is recorded in [maintainer TODO](../maintainers/TODO.md#deferred-performance-validation), with incomplete implementation exits in [PF00–PF11](../maintainers/performance.md).

### Mature-world tick profiling

Read-only inspection of the running local PostgreSQL game on Apple M1 Pro / Darwin arm64 / Node 22.23.2 found approximately 93% of one CPU core in use. The bounded live native-step samples had p50 21.85 ms and p95 47.23 ms; mutation wait p95 was 896 ms. World commit p50 was 6.57 ms, public projection p50 0.21 ms, and PostgreSQL statement p50 0.77 ms. These are descriptive samples, not end-to-end browser timings. At 1×, 60 native steps are required per real second; even the median step cost exhausts that CPU budget.

A consistent read-only PostgreSQL snapshot contained 15 entities, 864 hot events, 209 personal memories and 1,585 awareness entries at simulation time 4,259,454. Offline execution of the actual native kernel, with 30 warm-up steps and 180 profiled one-second steps, took 3,752 ms (p50 18.97 ms, p95 29.19 ms). About 96% of sampled baseline CPU was in Immer finalization/traversal helpers. Diagnostic deep freezing of the input snapshot before warm-up reduced the measured loop to 73 ms (p50 0.34 ms, p95 0.71 ms). Both runs produced the same final-world SHA-256 digest. This excludes initial freezing cost and does not establish long-session or editor/migration compatibility. That input-only experiment preceded the server ownership-boundary implementation described below.

Independent disposable SQLite HTTP servers loaded that same snapshot with explicit zero spending and no provider credentials. Over approximately ten seconds, 1× accepted 413 simulated seconds (41.27 per real second); 3× accepted 444 (44.37 per real second), versus required rates of 60 and 180. The 3× run recorded 4.257 real seconds excluded by the existing greater-than-two-second suspension rule and a maximum completed tick of 2,186 ms. CPU gauges approached 100% of one core. In-flight batches were still running at observation; native work counts therefore exceed accepted simulated time. These short runs used SQLite, not PostgreSQL, and shared the machine with the existing live game. They reproduce saturation and clock loss, not stable tail estimates or population qualification. The live game's speed/state was not changed.

The profiler is reproducible without a running database or provider:

```sh
node --import tsx scripts/profile-native.ts /private/path/backup.json /tmp/native.cpuprofile
node --import tsx scripts/profile-native.ts /private/path/backup.json /tmp/native-baseline.cpuprofile 180 --mutable-snapshots
```

Input accepts a materialized SavedWorld or an existing `backup-world.ts` backup; raw checkpoint rows without journal replay are not sufficient. Output paths must be new. Profiles are created with owner-only permissions; keep snapshots and CPU profiles outside version control. The profiler reports aggregate timing, hottest self samples and a final-world digest. By default it freezes its parsed input and every step result, matching the server boundary. `--mutable-snapshots` reproduces the unfrozen baseline. It reports initial freezing separately from the measured loop. Complete outcome equivalence still needs broader qualification.

The authenticated local `GET /api/performance` endpoint adds bounded cumulative tick/persistence timings, requested/accepted clock counters, excluded-gap counters, process CPU/heap and event-loop/GC observations. Compare counter deltas across matching uptime windows; nested stage times overlap. Instrumentation requires running this updated build. [PF03](../maintainers/performance.md#pf03--native-cpu-and-incremental-admission) owns snapshot-boundary and overload qualification; [deferred coverage](../maintainers/TODO.md#deferred-performance-validation) records the unrun automated checks. No automated tests or paid calls were performed for this investigation.

### Frozen snapshots and bounded tick prefixes

With server-owned snapshot freezing and bounded catch-up batches, final independent ten-second runs on the same copied mature save advanced 601 simulated seconds at 1× (60.10 per real second), 1,802 at 3× (180.19), and 4,797 at 8× (479.67). Small differences from the requested rates reflect timer/control observation boundaries. None recorded excluded gaps; final fractional debt was below one simulated second. Latest process CPU gauges were approximately 4%, 10% and 21% of one core. Native-step recent p50/p95 were 0.45/1.74 ms at 1×, 0.37/1.00 ms at 3× and 0.36/0.82 ms at 8×. Individual outliers still exceeded eight milliseconds (up to 143 ms at 8×); the budget is a cooperative boundary between indivisible steps, not a hard latency guarantee. These remain short SQLite runs, not production PostgreSQL or browser latency acceptance.

An offline run including freezing every result completed 180 steps in 220 ms, with the same final-world digest as the unfrozen baseline. Initial input freezing took about 24 ms separately. A 10,000-step run took 4.35 seconds (p50 0.33 ms, p95 0.84 ms); this is approximately 2.8 simulated hours of native execution, not a real-time provider/history soak. It does not prove all workloads meet the eight-millisecond individual-step budget.

Actual application execution on disposable zero-budget saves accepted movement and duplicate retries, immediate speech, person edits, attributed event edits and event deletion. A continuous three-second interval explicitly marked as observed busy time advanced all 180 due steps across bounded prefixes. A speed-change command interleaved after the first step and completed in 18.76 ms without losing the remaining debt. A three-second interval using the default unobserved-suspension policy advanced zero steps. Clean close/reopen preserved the edited name and simulation time and restored frozen snapshots without storage errors. An initial invalid attributed-text edit was correctly rejected and is not counted as accepted editor evidence. Legacy-schema migration, failure/concurrency matrices and larger populations remain unqualified. Automated tests were neither added nor run.

### Perception and population follow-up

The next native CPU profile attributed substantial work to encounter projection and Immer proxy reads. A synthetic fixture added ten people through the actual spawn transition to the same mature copied save (25 total entities). With 30 warm-up steps and 1,000 measured steps, the previous code took 2,193 ms (p50 1.90 ms); scalar perception reads, prior-membership sets and stable visibility arrays took 858 ms, with a confirmation run of 663 ms (p50 0.56 ms). Both candidate runs matched the baseline final-world digest. This is 61–70% less native processing time for this fixture, not a claim about live cognition, browser rendering or every world. The original 15-entity save's 3,000-step median improved from 0.34 to 0.22 ms, but total duration varied from 1,217 to 1,259 ms in the final comparison; no consistent 40% whole-run gain is established there.

A crowded 100-added-person experiment did not complete warm-up promptly and was deliberately terminated. It provides no completed throughput result or 100-agent acceptance. Code inspection identifies pairwise encounter emission, witness fan-out and linear `experienceEntry` duplicate scans over growing awareness as remaining amplification paths. Separate instrumentation and bounded crowd qualification remain in PF03/PF09.

An actual `AiDirector.considerThought` execution on the ten-added-person fixture used explicit zero budget, an injected client that rejects provider execution, and synthetic hunger to exercise native-protection scheduling. One hundred admission passes took 41.7 ms; thought-signature refresh totaled 10.14 ms (p50 0.065 ms, p95 0.162 ms), and 14 maintenance-refresh samples totaled 0.97 ms. Provider call count was zero. This shows these idle/native-protection checks were cheap in that fixture; it excludes paid model latency, full context construction, embeddings and successful AI execution. The one-world workflow/global interval limitation is established by code inspection, not model-load measurement. The final build passed, and a disposable zero-budget HTTP run accepted movement/retries and speech, published updated state, and paused/closed cleanly after the perception change. No automated tests were written or run.
