## PF17.4 lexical projection checkpoint before code

The selected projection is the positioned full-text vector and its inverted index. Exact canonical bodies, current eligibility, `search_text`, immediate paged displayed-text search, place observations, corrections and forgetting remain synchronous. A separate derived document table holds the vector with its complete source identity and exact revision. Only indexed optional context selection needs to wait for that projection; exact/source-history readers do not.

Canonical source insertion/removal and a coalesced durable pending key commit together. Pending keys carry durable world generation/revision and exact source revision. One database-owned worker processes at most 128 sources / approximately 512 KiB of source text per batch (an already admitted oversized single source remains processable alone). Before acknowledging more than 65,536 pending keys or 8 MiB of conservative pending-key metadata, the current transaction catches up synchronously; this protects deferred debt without dropping evidence. These initial operational values are experimental, not measured optimal settings or limits on retained memories.

Coverage advances only after the generation's pending set is empty, through the then-current committed world revision. A search waits outside read snapshots, opens its actual snapshot, and checks generation/head/coverage again. If that snapshot became newer than readiness, it releases and repeats within one five-second preparation bound. An existing caller-owned snapshot that lacks coverage receives an explicit preparation-unavailable error rather than waiting while holding it. Shared selection reuse is admitted only after this coverage check. Worker publication joins the exact current canonical source revision, and replacement/removal never makes obsolete text searchable. Reopen resumes durable keys; restore rebinds only pending keys whose exact current source still exists and discards stale work. Normal close stops scheduling and awaits its current owned operation.

The overload tradeoff is explicit: an unusually large writing operation can still wait for lexical catch-up, rather than acknowledging unbounded delayed work. Root-owned commit/startup/close hooks and focused held-worker/reopen/restore/privacy checks are required integration, not future optional work.

The standalone actual PostgreSQL proof passes eleven groups: exact evidence while indexed search waits behind a held writer, a source arriving between readiness and snapshot, exact replacement publication, reopen resumption, generation-change fencing (including removal of unreachable derived documents), conservative admission saturation, explicit refusal inside an uncovered caller-owned snapshot, Unicode normalization/prefix behavior for dotted-I and accented words, startup before the first world exists, indexed search after a source-free world revision, and actual transferred body bytes. The startup and source-free cases count writer transactions: empty startup performs one preparation attempt without spinning, and the subsequent indexed search performs no writer transaction. With two 300,000-byte bodies and one 600,000-byte body waiting, each ordinary SQL result stays within 512 KiB and the oversized body travels alone; all pending keys drain. These are operation/byte-count checks, not performance timings. The synthetic fixture exercises the actual canonical writer, source insertion, reconciliation and search owners; it does not establish native gameplay, full restore, scale timing or browser behavior. Its first two incomplete attempts exposed omitted fixture setup (pgvector, then the ordinary `meta` table); those databases closed/dropped normally and the corrected fixture passes. No provider ran.

The waiting context read refuses its older disclosure assumptions in both cases. Once preparation resumes, a forgotten memory and the dependent summary invalidated by correction are absent from both fresh selected context and derived search documents. The correction ledger still names its exact newly perceived correcting event; the check does not invent a rule that all corrected original evidence must be deleted. This six-group combined account/privacy scenario passes and cleans up its owned database.

Review found and fixed a possible lost wake-up when a new source arrives between the worker's final empty check and release of its active promise. Release now schedules another run when known pending work remains. Source-free commits do not continually wake the worker. Restore additionally removes derived documents with no matching exact current canonical source; this avoids accumulating unreachable index data across restores. The worker now applies its body-byte prefix bound inside SQL before transferring text. The initial implementation fetched up to 128 complete bodies and only then applied the byte bound in JavaScript, which could transfer many oversized sources at once. SQL first selects at most 128 ordered pending keys, sizes that bounded set, and returns only the admitted prefix; the existing oversized first-body exception remains explicit.

## PF17.7 shared transport continuation

Canonical and recall-source inserts now share the same typed JSON batching helper, preserving PostgreSQL's text conversion, original row/parameter ceiling and complete encoded-byte accounting. The source insert also atomically creates its lexical pending metadata, retaining one caller round trip for that source batch. No prepared-statement cache is added: query shapes are now stable, but there is no measured repetition/plan evidence justifying another connection-owned cache. The unfinished private ordered-protocol pipeline remains a separate alternative, not part of this implementation.

## PF17.8 recommendation

The journal is an alternative architecture, not a required extra layer. Under a restricted existing-row/unchanged-column prototype, many frequent busy-world operations are ineligible: new events and observer accounts, visibility entry/exit, recent-result insert/eviction, exact source hash changes and new relationships. A one-pending-revision cap makes later commits/reads await prior materialization; it adds append/encoding work without removing the indexed writes. Full coverage requires coherent committed/applied reads for canonical bodies, history references, archived versions, receipts, privacy and checkpoints. This source analysis recommends retaining it as a high-risk alternative until a bounded prototype demonstrates useful actual coverage and complete-operation benefit. This is not a measurement proving all journaling designs ineffective.

## PF17.5 conditional design checkpoint — not implemented

Prepared October 16, 2026, while the ordinary combined comparison is pending. This is a source-based design for the gathering experiment, not authorization to change gameplay or a claim that it will improve speed.

### Intended player and character behavior

A bystander who notices another person beginning and finishing one ordinary gathering action may receive one compact optional recollection covering those two observations. Exact personal history still contains each original observation. A fresh reaction, a required decision, a promise, an injury or a direct inspection still uses the exact original source. The acting character keeps its normal detailed action record and result.

The compact account must say what was actually observed, for example: “I noticed Mike begin gathering; later I saw him gather 2 wood.” It must not claim “I watched Mike continuously” merely because both endpoints were visible. Names and material quantities appear only when that observer's original accounts permit them. The example is proposed wording, not a new implemented event.

### What the current gathering action actually produces

The installed `base:gathering` host exposes the ordinary `gather` command. The bundled Fallen branches resource supplies wood and uses the shared 420-second gathering duration. `executeCommand` admits one finite action; `completeAction` consumes available stock, creates the actual output and records `gathered`. The start path records `action-started` once. It does **not** record a routine gathering-progress event on each simulation slice. A gather may start while approaching; “started gather” is therefore not proof that physical work already began.

The first qualifying case must be an already-in-reach, already-working ordinary gathering attempt, with the installed host/definition pins unchanged and normal outcome. The observer must be a bystander, distinct from acting/directly affected participants. Both selected samples must have compatible event-time disclosure and belong to the same exact action occurrence. Approaching, failure, replacement, interruption, depleted stock, unusual/significant results and changed detail remain ordinary exact records. No material, output, work duration or physical resource rule changes.

This is a limited opportunity: one completed ordinary gather supplies a start/result pair, so the strict first slice can combine at most two routine optional records per fully eligible witness. Repeated commands have different action instances and cannot be merged under this rule. A parent activity or longer gathering-session policy would be a separate authored gameplay experiment.

### Identity, coverage and lifetime contract

The derived episode's complete key is world + observer + selected policy pin + exact action occurrence/action ID + acting participant + permitted target (or explicit unknown target) + disclosure class + observation-continuity token. Allocate its record identity through the existing identity owner. Matching display names, the same resource definition or a reused recognition handle cannot join two episodes.

Each source reference binds world, observer, `awareness` family, event ID and the canonical account's exact body revision. It also retains occurrence order/time. The storage owner already computes exact body revisions; the deterministic domain must not import Node crypto or invent a weaker authority hash. A projected episode revision covers its ordered exact references, policy pin, permitted roles and coverage/closure metadata. These references are an index over canonical awareness, not another editable evidence body.

Build the final derived episode change once per existing world commit, after all changed canonical accounts and exact occurrence links are available; several additions in that commit do not cause several SQL updates to the same episode. Active grouping metadata is bounded by currently observed qualifying actions, with at most one entry for each observer/acting-participant/action combination. Closed records follow their existing retained-source storage owner rather than accumulating in a native per-frame array. Incomplete cause, coverage or projection preparation keeps ordinary permitted recall available or explicitly refuses preparation; it cannot silently discard sources.

For this finite first slice, the reference set is bounded by the actual start/result pair. Coverage is the observed samples and their continuity segment. It does not assert attention or a continuously witnessed physical interval. Source/target loss, participant/target change, perception blocking, speech/threat/damage/significant interruption, action end/replacement, or policy/disclosure change closes the segment. A newly arriving observer begins with its first genuinely permitted sample; no earlier source is looked up and assigned to it. A return after a gap starts a distinct segment even if recognition reuses an old handle.

Forgetting or correcting either source invalidates the derived episode in the same transaction and restores only still-permitted ordinary optional sources where appropriate. Rebuilding may produce a singleton ordinary source, never a fabricated replacement account. The existing reverse-source dependency lookup can conservatively find candidates, but final resolution checks the complete family/observer/revision key. A pending lexical/vector result must check both the episode revision and all dependency revisions/current disclosure before publication. A retained old version grants no access.

Persist exact causal/continuity metadata and active grouping identity with their existing event/experience owner. Save/restore must carry or deterministically rebuild the derived header/links before optional selection becomes ready; current generation fences still reject old readers and workers. Reopen must not duplicate a source membership or join across a recorded gap. Hot-tail eviction retains canonical evidence. Missing source/account data refuses episode preparation; it does not borrow global facts or report successful empty recall. ### Source-write tradeoff and adoption gate

For `G` completed, fully eligible gathers and `W` bystanders, the narrow path offers at most `2 × G × W` routine start/result candidates as `G × W` closed optional episodes. That is an upper bound on **optional candidate count**, not a reduction in physical events or captured observer evidence. The exact awareness bodies, history references and required-source metadata still exist. New episode headers/dependency links and invalidation work add writes.

Indexing the open episode at start and updating it at completion still performs two index updates; it may reduce final row count without reducing update work. Publishing only a closed episode could reduce indexed bodies, but withholding the routine start from optional recall until closure is an additional explicit timing compromise. That choice must be stated before implementation; required triggering evidence and exact inspection remain immediate in either case. An implementation that merely hides raw results after indexing them has not reduced source-write cost.

The useful comparison must count qualifying pairs and actual source/catalog/history/lexical/vector writes, separately from episode/link writes and extra hydration reads. Test actual gathering, arrival/reentry, partial-to-full disclosure, interruptions, correction/forgetting during held preparation, active reopen and checkpoint restore. Compare whole-game command tails, sustainable 3× progress and pending preparation debt, followed by whether a witness can explain what it really saw. With current 420-second wood gathering and only two routine events per attempt, this candidate has a limited source-reduction ceiling and may be a net write regression. It should not be presented as the likely cure for a large native-simulation bottleneck without those counts.
