### Walking commands and background-save ordering audit

PF16.119 completes a source-only audit of whether a ground walking command must save an unnecessary pending snapshot before saving its own action. It does not: the action starts from the current live world, including unsent native progress, and the same world transaction writes the action, cumulative progress and durable gameplay receipt. Removing the in-memory command receipt is preparation for that transaction, not another database save. Pending commands defer periodic saves; successful commands clear unsaved progress and reset their cadence. A pending durability follow-up reuses that command commit and resolves without another write when no newer progress remains.

A previously prepared background snapshot is different. Its released history is already live; its exact prepared state/baseline/revision must commit or latch failure, even if its PostgreSQL transaction has not started yet. Replacing it would change history and accepted-baseline semantics. The existing deferral ceiling ends five real seconds after the last completed progress save, so a periodic save may deliberately start while a command is queued. That can require the older save followed by the command's own write, preserving the current crash-loss bound. It is not a five-second guarantee that database work completes. Authority is checked after admission and again within the world transaction; command identity/recovery, revision order, after-commit publication and durable-history eviction remain required barriers.

Walking to a remembered place is a separate conditional path. If that actor's relevant personal sources or revocations changed, its scoped SQL place lookup can require a source flush before the action commit; unrelated position/need progression skips that flush. The measured ground-position browser does not use this path, and no removable source-integrity barrier is established here. The66world-commit completion spans totaling36.8seconds overlap SQL, queues and other work and cannot be treated as avoidable cost. ## Further saving-design assessment — October15

The latest complete wait recording identifies actual time behind resident-plan and player-command saves. Two broad shortcuts were reconsidered while the command-layout trial ran; neither is selected for implementation.

- **Combine more database writes.** The current shared writer already combines independent writes to different tables into a single database request, with limits on request size. It also verifies required row counts and flushes before dependent reads or deletes. PostgreSQL's documented shared snapshot and unspecified sibling execution order mean that unrelated dependent statements cannot simply be combined while preserving their answers.
