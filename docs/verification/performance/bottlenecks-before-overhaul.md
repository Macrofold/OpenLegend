# Historical bottlenecks before the implementation batch

**Historical snapshot retained from October 16, 2026, before this implementation batch. Working findings: the requested smooth, sustained 3× game is not delivered.** Runtime experiments are stopped. This report explains the recorded results without requiring code knowledge; the linked records contain the technical detail and failed attempts.

The subsequent [Performance Overhaul Ideas](../../projects/performance-overhaul-feature-spec.md) project contains 23 source-backed proposals, including explicit gameplay compromises. Its [evidence audit](../../projects/performance-overhaul/evaluation.md) explains why the measurements below remain directional clues rather than unquestionable causal rankings. That documentation-only analysis adds no new measured result or implemented improvement.

## What we know now

**Slow commands and occasional drawing freezes are both still present.** Repeated world calculations consume substantial CPU, and saving changes delays player commands. The evidence identifies several large contributors, rather than proving that thousands of equally important tiny operations explain the problem.

**These best recent results come from private experimental copies.** The ten-minute game below combines a newer code library for changing the world, cheaper storage for recent character choices, and less frequent checks by idle territorial animals. Those three changes are not integrated into the normally launched game. The two most recent retained CPU improvements preserve command results and read material information more cheaply. No user's save has been replaced in these trials.

The latest complete graphical observation without detailed tracing lasts ten minutes with seventeen people, forty animals, one hundred added objects and three added sheds. All sixteen other people travel, work, eat food they gathered, sleep and wake. The player eats nineteen times and starts sleeping near the end. Everybody survives. This corrects the earlier Move-only test, whose player died because its script never ate.

The newest complete run still fails the requested experience. [Current graphical result](42-combined-graphical-survival.md), [freeze diagnosis and missing evidence](44-long-browser-freeze.md).

There is a useful measured improvement: on the same newer editing library and storage layout, four two-minute games compare ordinary versus slower idle territorial checks. Total CPU falls **8.3%**, and the mean of the separate runs' command-delay percentiles falls **579→428 ms**, while both versions stay very close to 3×. The slower animal may notice a visitor later or miss a brief visit. This is a controlled partial gain, not the final solution. [Comparison](39-combined-idle-reviews.md).

For historical context, an earlier ten-minute graphical version averaged **2.484×** and fell to **1.64–1.69×** in late working minutes. An older thirty-minute result was **0.091×**, roughly one eleventh of ordinary speed, with a **55.7-second** drawing freeze. Both were failures. They use different versions/scenarios/host conditions, so comparison with today's run is not a measured causal improvement claim. [Earlier evidence](06-sustained-game-and-browser.md).

**A 3× average can hide a serious slow period.** The latest five-minute diagnostic averages 3.000×, but one busy minute runs at **2.32×**, with **17.3 real seconds of game time queued** at its end. The next minute runs at 3.93× and catches up as residents sleep. This is not sustained smooth 3×. A second, fully recorded game also slows during its fourth minute; the costs are described below. ## What the database measurements actually say

The current version now has direct database timings as well. In a new thirty-second recording, the writing connection spends **11.43 summed seconds inside PostgreSQL**, versus **15.24 seconds until the application receives completion**. Reading requests take **0.41 / 1.80 seconds**; a trivial-query reference takes only **0.06 seconds in the database** but **1.46 seconds until completion reaches the application**. Database work and receiving its replies both matter.

Parsing and preparing write requests take **3.57 summed seconds**. One large save sends **4,949 separate values** and takes **262 ms** inside PostgreSQL, including **180 ms** parsing/preparation. The writer builds different query text for different row counts. This provides a measured reason to test a more compact batch format, while measuring its decoding cost too. The [compact-batch prototype](52-compact-world-record-writes.md) now preserves every compared game/temporary row and passes rollback/constraint checks. A request saving 526 placement records changes from **9,994 separate query inputs to one structured batch**. The database instructions shrink **21,248→701 bytes**, while all the records’ information still travels with them. Instructions for saving one record become longer. The actual timing series stops after its third run: the driver delays presence reports while commands are slow, so the game briefly marks the player away. That original final control remains withheld. The [driver correction](53-independent-player-presence.md) now matches the browser’s independent five-second reports. A fresh complete four-game comparison gives a partial transport improvement: mean saving time falls **16.1%** and the separate walking-percentile means fall **35.7%**, while smooth 3× still fails. No gameplay is removed, and the candidate remains private. [Complete current comparison](62-compact-writes-current-game.md). The current game still fails at **2.958×** with **907 ms** walking p95 and one missed input slot. [Current database breakdown](51-current-database-time.md).

## The remaining gaps that matter for the next decision

1. **Slow input is still unresolved.** The saving/command-order evidence is strong. A retained change must reduce the complete wait while preserving reliable saves and authoritative commands. No proposed queue or worker rewrite has been proved to solve it.
2. **The latest combination needs long-play evidence.** The completed graphical run keeps the player alive, with real meals and Sleep, but ends before waking and has only 499 accepted intentions. Slow clicks and a 1.89-second drawing gap independently fail the goal.
3. **We still repeat too much shared work.** The animal timing experiment demonstrates a broad design cost. A completed private experiment skips quiet territorial reviews only when no supported intruder could arrive. The first prototype failed when ordinary metabolism started. The revised version passes controlled wake-ups, a complete repeated world replay and real saving/reopening, and uses **12.5% less CPU** in four fixed-work runs. Residents finish some actions up to 10.6 game seconds differently (about 59 ms at 3×), with positions differing by up to 82 cm and some changed observations. It remains private: four actual two-minute games average **2.890→2.702×**, and walking-percentile means **697→799 ms**; one misses the activity target. Varying host load prevents a firm causal slowdown claim. It establishes no input or drawing improvement.
4. **Some attribution is unfinished.** The separate server/runtime profile still has 2.67 sampled seconds without a precise source explanation. Growth-related costs also need a clearer owner. Neither is evidence that every remaining operation costs equally little.
5. **Current graphical acceptance is missing.** The bounded actual-play trace completes, but does not contain the original rare 1.89-second pause. Its cause remains open. Retain the eight earlier unresolved warnings and qualify any cloth change separately. Current frame and movement tails already demonstrate failure.
6. **The full requested acceptance test has not passed.** Sustained crowded travel/work/food/rest, at least 1,000 actual player intentions, no growing clock debt, prompt input and no game/storage/graphics errors remain required. Higher player counts and live AI have their own unmeasured costs.

Development feedback also has a separate cost: complete older-world installation commonly takes roughly **45–58 seconds** in recent trials. One earlier five-minute launch timed out before measured play. It remains a failed setup, not a game-speed result. Reading and validating one recorded checkpoint took only 1.7 seconds; installation took 49.4 seconds. Those are useful separate targets, but speeding startup would not itself fix walking.

No claim is made that every possible implementation has been exhausted. Additional and cumulative game-provider/Jev cost for these experiments are **$0**. The coding assistant's subscription usage is not measured by that figure.
