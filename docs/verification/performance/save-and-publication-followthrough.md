## Next saving trial: finish related memory bookkeeping together

**Selected before implementation, October 17, 2026, 16:32 EDT.** When a character notices something, the server inserts that person's searchable evidence and then makes a separately awaited database call to update related search eligibility and preparation. The trial will try doing those related steps in one bounded statement. Characters keep the same evidence, memories, private access and correction/forgetting behavior.

The important complication is older information. For example, a newly recorded direct observation can mean an older remembered account of that same event should no longer appear as a second independent search result. Combining writes must still update that older account. New memories also need to see observations arriving in the same batch. PostgreSQL does not let related writes in one statement simply reread one another's changed tables; their required results must be passed explicitly.

The first candidate is deliberately conservative. It selects genuinely new observations and personal memories only when the existing small-batch limits fit. Summaries, edits, removals, privacy-wide changes, ambiguous shared identities and larger batches retain the complete ordinary path. These are selection conditions for the optimization; they do not reject or discard game information. Exact current storage, older linked records, search preparation, rollback and cold reopening must match before timing. The preceding removal experiment is a reminder that fewer database calls can still fail to make the whole operation faster.

**Qualification in progress, October 17, 2026, 17:05 EDT.** Ten actual PostgreSQL cases match the ordinary path, including same-batch observations/memories, older related memories, correction/forgetting, four nonempty archived versions, real transaction failure and cold reopening. The existing private-history checks initially pass eight cases and time out in one inspect/forget case at the unchanged15-second limit; that exact case passes separately in about 1.3 seconds. The original unexplained timeout remains a limit, not an erased failure.

Inspecting the database plan exposed an inherited problem shared by the ordinary and combined paths: two changed events cause roughly3,008 unrelated personal-memory rows to be visited. Exact row counts and separating matching branches remove some broad work, but do not fix the database's index choice. A larger VALUES parameter list and an ineffective lateral-query fence are rejected before installation. The selected refinement retrieves records for each changed event through the existing world/event index once, then checks the exact character/source family. This may visit other observers' derived identities for those same events internally; it neither reads their text bodies for the player nor changes disclosure. Many observers sharing one event must be qualified before retention.

The plans above are observed before a manual statistics refresh. PostgreSQL's official documentation recommends refreshing statistics after a substantial bulk load because poor estimates can select poor plans. That is a separate possible startup/restore cause to investigate, not a hidden prerequisite added to the candidate's benchmark. No global database setting, extra index or retained-history limit is changed. [PostgreSQL14 bulk-load guidance](https://www.postgresql.org/docs/14/populate.html#POPULATE-ANALYZE).
