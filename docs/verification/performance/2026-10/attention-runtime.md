The completed instrumented normal run attributes **160.242 s inclusive CPU to native execution**, **21.026 s to canonical record preparation**, **21.127 s to public-view preparation**, **17.989 s to GC**, and **4.972 s to journal encoding** in disjoint owner categories. Immer's 48.900 s SELF and record helpers' 34.533 s SELF cut across these owners and must not be added again. CPU work is substantial before PostgreSQL runs.

The dense write's **7.531 s elapsed** includes SQL, encoding/scheduling and waiting; it is not a measured database CPU total. Its 959 statements and 239.4 million writer-charged bytes describe application write amplification, not disk footprint/network throughput. Ending heap/RSS values are neither peak allocation nor retained-leak proof. Likewise reader/queue hold times overlap useful CPU and other requests; moving the same preparation to an async function does not eliminate it.

Source checks identify the repeated work to remove: `captureTemporalCurrent` loops selected fields before group packing; `selectedCurrentFacets` constructs a field array from selected exposures; current visual reconciliation traverses field records for availability; attention keeps full per-contact candidates; immutable sealing/diffing serializes the resulting structures. The database mirrors that fragmentation. Shared payload caches and description reuse are working, so adding another value cache or tuning an encoder cannot remove these upstream costs.

What genuinely differs by observer is received eligibility/precision/time, continuity, attention, recognition/names, private learning and later correction/forgetting. What can be shared is immutable equal received content, source geometry/preparation, and neutral rendering inputs. One receiver's grant/check/interpretation cannot be shared as another's knowledge. Independent field freshness is a **semantic distinction**, not a requirement for separate mutable objects and SQL rows. Fields checked together can inherit one actual check stamp, with exact exceptions for different support. Unchanged checks need no new value or full individual proof construction; a selected history reader may still need their actual sampled timing.

Uncertain quantities are the exact confirmation/change split, group fragmentation under real partial sensing, residual recognition/native-event cost, transitive retained bytes, cold rebuilding cost and actual savings after removing fanout. The existing evidence establishes the targets and rejects a small-codec-only explanation; it does not establish a replacement's throughput. No further profile, runtime change or resource provision occurred for this analysis.

### What happens during ordinary gameplay

1. **The host asks the world to catch up; one ordered world-change lane admits the transition.** That same lane serializes commands, computed-route installation and final history effects so they cannot race. During the sampled 301 s, 3619 actual mutation holds occupy 298.903 s. Other operations’ 324.010 s summed queue wait overlap one another and are not an additional 324 s of elapsed game time. The native clock requests 18052.805 g but advances 9550.376 g, leaving 8517.385 g pending. The server never intentionally paused.
2. **The world integrates the actors that are actually due.** The player walks; animals also wander/forage/flee, while the other human residents in this fixture remain still. 1,715 native publications integrate the measured progress, not a mandatory publication per game second. Status/animal/route boundaries, not only sight cadence, determine these native intervals. Native CPU is 96.511 s. Within it, status reconciliation is 7.320 s and status-deadline calculation 3.345 s, with overlap; 577081 status-rule considerations and 242573 animal-wander eligibility checks show remaining recurring work, but these are not the largest isolated CPU consumers.
3. **A changed/due sensory phase tests who can actually receive each nearby source.** 954 phases capture 7977 eligible receivers and retest 15335 observer/source pairs, with 56264 actual sense tests. Candidate indexing and unchanged-pair reuse already operate; these are not full-world all-pairs retests on every tick. The sight-acquisition path costs 41.024 s sampled CPU, including its attention/history work below. It creates 2705 rich source preparations and reuses 6411. Broad current information remains available beyond detailed-attention slots.
4. **Attention selects detailed subjects; their actual checks are recorded.** The selected-history capture path costs 25.960 s, of which appending receipts is 23.613 s and frame preparation 13.719 s (nested, do not add). 13,533 temporal operations append 261,449 selected fields, including actual unchanged confirmations. This is not 261,449 unique moving objects. The system reconstructs checkpoint/support metadata, interns exact source/fact/proof/detail declarations, preserves selected values and calculates encoded bytes. Packing alone is 9.175 s. The small counterexample chunk decomposition below explains why little fictional activity can still create substantial metadata work.
5. **Completed state is made safe to share and saved as scoped records.** Generic native/response command batches now publish once, with isolated private child checkpoints; the earlier 9 public-finishes-per 8 commands mechanism is removed. Yet whole-run completion still costs 10.914 s, evidence sealing 5.229 s (nested), and the record-preparation owner 14.372 s. These are total named-call CPU unions across actual callers; the narrower measured `persistence.prepareRecords` stage is 8.644 s and does not encompass every preparation performed elsewhere. 1,515 journal acceptances use the short durable path; 142 fallbacks are in the family category, 0 boundary fallbacks, and no repeated ordinary-expiry synchronous-save pattern remains. 142 direct transactions cost 5.280 s elapsed, while 1657 world commits total 37.918 s elapsed. Background application performs 22823 SQL statements in 1486 batches; that worker work is not all main-thread CPU.
6. **At the recent-history cap, ordinary foreground commits still go back to the database to decide what to remove.** `WorldService.prepareRetention` calls `prepareRetainedSourceClosure`; each closure round separately prepares source-version retention and personal-history retention. The latter reads chronological cold chunk headers, overlays hot chunks, selects expired/over-budget chunks, releases sparse support and checks local-person survivors. The entire `MemoryRepository.prepareRetention` callback stays inside a database read snapshot while this SQL and pure JavaScript/world cleanup run. This is a distinct remaining path from the fixed synchronous expiry barrier. The “header” query still selects `mind_temporal_chunks_read.source_refs`: that view unions immutable segment arrays using `unnest`, `DISTINCT` and sorting. Scalar-looking output therefore still rebuilds and decodes repeated reference lists. PostgreSQL array parsing costs 3.877 seconds SELF across the whole current trace; the evidence does not assign all of it to that one query.
7. **In parallel, background cleanup checks whether shared received-value slots still have owners.** Releasing a personal field/chunk nominates a shared block. A bounded pass reads physical source sizes, checks cold segment ownership by block, sometimes hydrates selected source blocks, and tests remaining individual value ordinals against cold segment ownership. It then re-enters the world-change lane to apply exact latest-state results. Bounds are 32 blocks/4 MiB/8192 ordinals per pass, but a bounded batch can still monopolize the sole reader for hundreds of milliseconds. The pass does not trim unrelated sources or bypass current/cold/captured/sparse ownership.
8. **Ordinary views and commands queue behind that reader work.** 2,590 public projections consume 13.346 s CPU but 94.778 s summed elapsed; most of that elapsed is not view construction CPU. The navigation worker's actual query execution is 1.056 s across 1049 queries, while request latency sums 442.600 s across 2263 requests because answers also wait for dispatch/publication/world ownership. Those overlapping waits are not 442 s of pathfinding computation. The sampled client receives 14.65 MB over 2605 stream chunks; command p50/p95/p99 is 242.519/750.199/971.185 ms. No transport or storage error invalidates this phase.

### Why the 100-person crowd fails before ordinary gameplay settles

1. All 99 scripted NPCs start real work/movement in one service transition using the canonical private COW batch. This no longer means 99 separate top-level commits/full publications. Admissions are successful; the fixture is not timing 100 idle statues.
2. Initial exposure has one actual sensory phase but 190 receiver geometry preparations/183 receiver captures as real physical/action events also request receivers. 17,949 observer/source pairs are retested and 54181 sense tests run. The actual work remains proportional to real recipients and visible sources; an attention limit does not mean everyone else is invisible.
3. For broad current perception, 137,321 `currentFacetWrites` are accesses to the per-observer current-field mutation owner, with 182 map copies; the counter is not 137,321 unique persistent SQL rows. 8,607 rich source preparations are reused 31865 times, and only 2687 shared received values are appended. Thus large value bodies are already shared, but each receiver/source/field still incurs exact grant, freshness, binding and immutable-record work. Sampled visual reconciliation costs 9.802 s in this failed 32.738 s window.
4. New social sightings also produce story/awareness wrappers. The installed world policy suppresses routine scenery/animal onset retention but gives social onset importance 3 without forcing thought. Each new social subject can still call the event owner, render its observer wording, resolve local individual/recognition and retain its received observation. There are 9123 events and 13716 awareness processing calls. `recordEvent` costs 4.960 s sampled CPU across all callers (4.163 s inside native); awareness acquisition 3.231 s (2.756 s inside native). These are processing counts, not proof that every wrapper survives long-term retention. Existing per-observer awareness admission is already batched; these event-time acquisitions/wording still occur per event.
5. Native attention costs 2.937 s; 63,565 description preparations compare the received appearance/attributes/association through native JSON strings. They are not LLM calls. World-local body-identity resolution costs 1.555 s and its fallback can scan an observer's local identities; those routines operate among the much larger receiver/source fanout.
6. Detailed temporal recording appends only 1313 operations/4836 fields, and its capture CPU is 0.754 s. It is far smaller than the broad-current/event intake in this first exposure. A smaller temporal codec alone cannot fix this crowded startup.
7. Native CPU totals 17.830 s; garbage collection 2.976 s; record preparation 1.221 s; journal-constraint preparation 1.399 s (overlapping encoding/helper calls). The view is only 18.1 ms CPU. 39 spatial builds/4877 queries visit 388443 candidates; geometry-query work is real but not enough evidence to blame all 9.802 s on ray tests or all-pairs relationships.
8. The main thread is busy 27.289 s of 32.738 s. One mutation owns the world lane 27.288 s and one native step takes 16.223 s elapsed; the longest single native iterator call is 2.103 s and event-loop delay reaches 4.358 s. Pending world changes expire at the existing five-second admission deadline, yielding four explicit `busy` failures. The initial large transaction also takes 7.368 s elapsed; there is one journal constraint fallback and one synchronous progress save. Its exact rejecting constraint is not identified by the counter, so no 512-row/byte threshold is claimed. Neither reader queueing (1.159 s total) nor projection preparation explains this dense failure.

Dense current history is only 7,409,585 B across 100 actors at failure (195 resident chunks), not 100 actors hitting 8 MiB each. This is a first-exposure fanout and representation problem before mature-history pressure. End heap/RSS is 1.030/1.923 GB; normal sampled end heap/RSS 1.080/2.425 GB. These are endpoints, not a heap-retention/leak proof.
