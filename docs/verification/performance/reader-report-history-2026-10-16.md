# Why OpenLegend is still slow

**Working report, October 16, 2026. The smooth 3× requirement is not met.** This report stands on its own. It distinguishes measured costs from suspicions and will change as the remaining experiments finish. It is not a claim that every possible implementation has been exhausted.

## What the player should expect, and what actually happened

The game’s normal clock advances one game minute per real second. At 3×, it should advance three game minutes per real second, or three game hours per real minute. Smooth drawing and quick reactions to clicks are separate requirements: a high average frame rate can conceal a long freeze or a character waiting to start walking.

The most recent completed ten-minute crowded test contained seventeen people, forty animals, one hundred added objects and three added sheds. Sixteen residents travelled, worked, ate food they produced, slept and woke again. They followed scripted plans through the game's ordinary action rules; this did not test live AI decision quality.

| Requirement               | Actual result in that test                                                                                                           | Meaning                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Sustain 3×                | **2.484× overall**; late working minutes fell to **1.64–1.69×**                                                                      | The world increasingly failed to keep up.                                                                      |
| Keep up with elapsed time | About **104 real seconds behind** at the end                                                                                         | Some time was waiting to be offered to the simulation; some had been offered but not processed.                |
| Smooth frames             | 88.7 average drawings per second; worst gap **569 ms**                                                                               | The average looked healthy while individual hitches remained visible.                                          |
| Prompt walking            | 95% of accepted command confirmations arrived within **722 ms**; 95% of measured idle clicks first showed movement within **885 ms** | Walking still felt delayed. These are observations after input, not proof of the exact moment an action began. |
| No graphics errors        | **Eight graphics-buffer warnings**                                                                                                   | Their cause is unresolved.                                                                                     |

An earlier thirty-minute test was much worse: **0.091×**, roughly one eleventh of ordinary 1× speed, and a **55.7-second drawing freeze**. That result is a failure, not “nearly 3×.” It used an earlier version and a standing-work scenario; it must not be mixed with the newer ten-minute result.

## What the main costs mean in ordinary gameplay

### 1. A small movement can trigger substantial shared bookkeeping

When a bird moves or a person finishes part of a task, the game does more than change a coordinate. It predicts upcoming changes, updates people and objects affected by them, and publishes a coherent new world that saving and screen updates can consume. Making each tiny change cheap is insufficient if it repeatedly causes this wider work.

Within the measured snapshot-finishing time, about **3.29 seconds** belonged to resolving temporary edits into completed records. We have not established which dictionary or collection accounts for most of that traversal. A proposed change that sealed completed snapshots earlier preserved all compared outcomes but used **5.2% more CPU** across four fixed-work runs. It is rejected. Replacing all world storage on the assumption that this cost is removable would still be guesswork. The new [copy-width counts](16-growing-dictionary-copies.md) identify **925 distinct entity-dictionary copies covering about820,000 keys**, and **225 distinct command-dictionary copies covering about697,000 keys**, in a busy-world phase. The command records prevent repeated requests from repeating their effects. Extra mutable observations are repeats rather than new copies. The command-record replacement is now integrated: it keeps every command result and lowers CPU by **4.93%** for identical older-world activity. It does not change entity storage. Nested collections and the CPU cost of copying each other collection remain open.

The newer fixed-activity counts make this repeated work concrete. Over forty game minutes, the baseline makes **17,499 visits to characters during body-rate processing**, across 307 passes. These are visits, not17,499 different characters or proof of that many changed values. Freezing all animals reduces visits to2,890. The same run makes160 territorial reviews. Health-related rules and serial calculations did not block deferred updates in this fresh scenario; most deferral stops were actual interval endings. Separately changing only idle intruder checks from every fifteen to every sixty game seconds now cuts fixed-work CPU by **19.4%** and published world updates **223→150**. The running-server comparison below shows why this partial saving is not enough.

### 2. Fast calculations do not guarantee fast walking

A click must reach the server, wait its turn, pass the walking rules, save the accepted change and get back to the browser. The browser must then receive and draw movement. Each stage can delay what the player sees.

The current ordinary ground-walking path already saves the walking action together with unsaved world progress in one transaction. A second, trivially removable save was not found. Separately, older prepared saves cannot simply be thrown away: they already own records needed to preserve the correct saved sequence. The complete recording described below now separates calculation, waiting for another world change, and database-request waits. It does not yet explain how much of a database-request wait belongs to the database itself or to the busy application. A recorded refused command after the browser stopped measuring remains a failure; it is not excluded to improve the result.

A newer external observation now confirms real database file I/O during slow clicks. During the worst **1.024-second** command, PostgreSQL is active and waiting on data files in **17 of 21 snapshots**. A **584 ms** command has such waits in **8 of 12 snapshots**. The next timestamped run identifies one: updating which place observation counts as a character’s latest. Two such requests take **451 ms** and **266 ms**, with repeated database file-read waits. Checking whether character evidence exists also takes **246 ms** in one request. The actual plan checks about **250 old/current records to update five current observations**. A proposed lookup checks only **five**, reducing its data-page accesses **355→10**. Refreshing statistics alone leaves the broader lookup. The full-game index test then fails qualification: one candidate reaches only **1.72×** and incomplete resident activity. Average progress is **2.42→2.12×**, with worse command delays. The index remains private. This is why the smaller query plan alone is not a gameplay speedup. This evidence does not justify treating every database wait as main-thread delay or weakening reliable saving. [Database diagnosis](20-database-activity.md).

### 3. Animals are a promising source of unnecessary repeated work

The private animal trial kept forty animals but slowed bird travel and reviewed an idle territorial animal less often. The latter can delay noticing an intruder or miss a very brief visit; active pursuit and attacks kept their existing review rules. Its isolated CPU reduction was real. In the first full graphical comparison, achieved speed rose **0.294→0.841×**, still a severe failure, and a late command was refused. That pair also processed different amounts of work under heavy host load, so it is not a clean 2.9× performance claim.

The complete freeze diagnostic now reduces calculation CPU **9.47→4.75 seconds**, about **50%**, while all sixteen residents still complete the required work, meals and physical return checks. Native world updates fall **223→170**. Stopping incremental noticing in a separate version reduces CPU **9.47→8.09 seconds**, about **15%**, while retaining 223 updates. These savings overlap and cannot be added. That split now shows **16.5% less CPU** when only the bird is frozen, and **28.5% less** when the thirty-nine ground animals are frozen, in a separate balanced comparison. Both groups matter; their percentages cannot be added. The subsequent counts confirm that animal activity causes repeated shared steps and body/sight work. A frozen-animal game is not an acceptable finished result.

Checking for intruders less often while idle is now tested separately from slowing birds. In four short running-server comparisons, mean speed changes **2.965→2.982×** and mean world-calculation elapsed time falls about **15%**. Mean whole-process CPU falls about **5%**, with substantial run variation. Each of the sixteen residents completes two real work/meal plans. Yet command confirmations still have per-run 95 th-percentile delays of **361–452 ms** in the candidate, and clock backlog remains. This is a partial saving, not smooth 3×. It can delay first intruder detection by an extra quarter-second at 3× and miss a very brief visit; active pursuit and attacks keep their earlier timing. It remains a private trial pending behavior, browser and long-session checks.

### 4. Visual compromises must be measured separately

The player's garment is simulated fabric with repeated stretching and body-contact corrections. An exact contact shortcut rejected many impossible pairs but still increased CPU by **8.4%**; it is rejected. Trying four correction passes instead of eight now saves **49.1% of isolated cloth CPU** across eight observations. Fabric motion changes and the typical link-stretch error measure rises about18%; some seam gaps improve. The numerical observer preserves the demonstrated trajectories exactly within each version. Actual appearance and whole-game frames still need checking. This quality reduction has not been retained.

## A separate problem is slowing development feedback

An earlier attempt to record command waits failed to reach measured play within **five minutes**. It successfully created its temporary database and copied the179 MBsaved busy world, then stalled later during restoration. We do not yet know which restoration operation was unfinished. It gives no game-speed result. The exact temporary database and files are now removed, and the original saved world was untouched.

A new recording with loading progress markers now reaches play: reading/validating takes **1.7 seconds**, installation **49.4 seconds**, and total restoration **51.5 seconds**. Its instrumented busy-world phase still reaches only **2.18×**, with **700 ms** command confirmation at the 95 th percentile. All28 commands are accepted and the normal-close recording is complete. The slowest command spends about **950 ms waiting for other world changes** before its own turn; about896 ms is behind a resident’s plan save. The clock itself spends10.2 seconds queued behind other changes, mostly resident-plan and player-command saves. Separately, recorded world calculations account for at least13.2 seconds. Both costs need work; the table of holders is in [the detailed wait report](15-actual-command-and-clock-waits.md). There are no command/storage errors in this new recording. Added diagnostics mean its speed is not a clean capacity comparison.

An earlier completed restoration took about51 seconds, but these were different runs under different conditions; this is not a controlled sixfold regression claim. The new restoration recording saves the name and time of each major operation as it starts and ends, so an interrupted attempt can identify its unfinished stage. Separately, a database cleanup operation was observed waiting for a housekeeping checkpoint to begin. That does not prove the restoration or walking delays have the same cause.

## Remaining evidence gaps and next decisions

1. **Separate whole categories directly.** The frozen-animal and frozen-noticing comparisons are complete. The single-bird and thirty-nine-ground-animal split is also complete. Repeated shared calculations are now counted, and slower idle reviews reduce fixed-work CPU by19.4%. Identify the remaining repeated work and qualify useful changes in the complete game. Record refused/incomplete actions and lost behavior.
2. **Explain the command waits.** Identify the actual operation holding up the world and the origin of refused commands, including activity after the nominal measurement cutoff.
3. **Identify what grows expensive.** Attribute snapshot copying and traversal to actual collections. A large allocation total is not proof of retained memory or a leak.
4. **Complete graphical measurements.** Explain the graphics-buffer warnings, qualify new drawing changes in the real browser, and retain freezes and input tails alongside average frame rate.
5. **Prove the actual goal.** After useful changes are integrated, repeat sustained crowded travel/work/rest tests at 3× with no growing clock backlog, no command/storage/graphics errors and prompt input. Isolated speedups and a short near-3× run do not pass this gate.

## Growing command records: first measured layout change

A layout that copies a short branch instead of the full command dictionary preserves the compared game behavior and passes real saving/loading/rollback checks. In a fresh world, total CPU falls only0.17%, which is neutral. This has not explained the main fresh-world slowdown. The completed older busy-world comparison confirms that the larger command dictionary mattered: the integrated replacement reduces CPU by **4.93%** for identical activity. Nothing is deleted or capped. [Trials and evidence](18-command-record-layout.md).

The completed older-world service comparison is more encouraging: average progress2.28→2.57× with the new command layout, and command-confirmation p95 falls from665/912 ms in the two baselines to282/365 ms in the two candidates. All issued commands succeed. The candidate also completes more work, so the12.6% progress difference is not an equal-work CPU result. The equal-work older-world check confirms 4.93% less CPU. Selected integration checks pass. Sustained smooth 3× remains open. [All four observations](18-command-record-layout.md#completed-older-world-bccb-comparison).

## Repeated material preparation now has a measured cost

Temporarily removing all cloth wetting/drying preparation cuts CPU by11.8% for the same older-world activity and reaches the same final world. This points to substantial avoidable preparation in that scenario. It is not safe to keep: separate examples show wet cloth would stop drying and rain would stop wetting it. Safe reading now saves10.0% CPU in the matched older-world comparison while matching42 controlled material cases and80 complete fresh-world checkpoints. It preserves wetting and drying. An earlier fresh-world timing was neutral; four running-game observations average **2.14→2.23×** with lower CPU per game second, but mean per-run 95 th-percentile confirmation worsens **868→971 ms**. This helps calculation cost and leaves slow walking unresolved. [Evidence and tradeoffs](19-material-preparation.md).

### Latest idle-animal comparison: modest full-game gain

On current code, letting a waiting territorial animal check for visitors every sixty game seconds instead of fifteen saves **20.03% CPU for identical fixed work**. The separate four-run server comparison improves mean progress **2.288→2.465×, 7.73%**, with individual speeds2.065/2.064/2.866/2.511×. Mean per-run command-confirmation p95 improves1,008→944ms; every run still fails smooth3× and responsive input. This helps, but does not explain or solve the remaining stalls. The candidate remains private because browser, sustained-play and endpoint-animal-life qualification remain open. All seventeen tracked people survive and every issued command succeeds; animal presence alone is not a life measurement. The compromise is a possible missed brief visitor while the territorial animal waits; pursuit and attacks preserve their original timing.
