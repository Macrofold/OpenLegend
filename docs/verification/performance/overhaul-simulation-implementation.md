## Implementation sequence and bounds

1. Prepare repeated status flow grouping once for a captured interval; preserve active episode checks, ordered clamps, periodic accounting and body-before-action execution.
2. Recheck only changed living targets for stationary observers, using the existing exposure cache and conservative full rescans for changed observer/map/order inputs.
3. Retain eligible/wet material membership through the existing object owner while reading rain, positions and shelter geometry live.
4. Move certified fixed-route walking stops into private motion slices and retain unrelated forecasts. Unsupported approaches and coupled changes retain their current handling.
5. Reduce repeated active-participant work, preserving phase ordering and saved random choices. An absolute wandering deadline must pause whenever its existing timer pauses.
6. Complete the current-read/accounting/save checkpoint for exact deferred continuous values before changing their representation. Coordinate the pure save materialization boundary with the server owner.
7. Complete the entity access/nested-draft/order checkpoint before selecting the persistent entity representation. Transparent object proxies cannot evade Immer's flat-directory copy while also preserving frozen-object/own-key invariants; that is not a valid shortcut.

The first four owners are estimated at roughly 700–1,100 runtime logic lines together. Active deadlines add approximately 250–400; deferred continuous values roughly 600–1,000 plus server integration; a complete persistent entity access migration may exceed 1,000 across callers. These are estimates, not claims of delivered scope or speed.

All caches remain derived, with cold/unknown/restore fallback. Cost grows with motion slices × actors/status rules/nearby targets/material lots; preparation is shared by captured mechanical intervals, owned exposure phases and object membership. Rate/definition/episode changes invalidate status preparation; observer/map/order changes invalidate pair reuse; custody/definition changes invalidate material membership. The root agent owns complete native/server/browser comparisons, at most five ordinary performance campaigns.

## Design checkpoints

### Continuous values

`readAttribute` currently takes a character and an installed definition, while direct numeric-state, episode-elapsed and charged-work readers also exist. Every current reader must receive a correct value independent of reader order, and saving must install the exact materialized candidate that became durable. A meter-only delayed write would be incomplete.

**Implementation checkpoint, 2026-10-17 01:46 UTC.** The installed metabolism rule has one self-targeted, non-health numeric rate on fullness and qualifies away from its condition thresholds. The first implementation will retain the exact ordered addition/clamping sequence, with one shared window of at most 64 integration segments. Each binding names the actual entity, status episode, attribute definition and first segment. The window holds no predecessor windows. Other effects, periodic changes, health, competing writers, supplies and unsupported episodes remain eager. The maximum is a compaction trigger, never a limit on game progress.

**Already implemented:** movement has private slices inside a shared interval; unchanged predictions can survive publication; a flyer's takeoff/landing can be reconsidered locally; unrelated linear changes can wait inside a native call; eligible exact meter calculations survive saves; and the browser smooths displayed positions between accepted updates. The remaining source-level coupling includes all-character endpoint visits when pending rates are applied, repeated activity-control visits during private slices, and publication when the server's 8 ms responsiveness allowance is exhausted. Existing reuse does not make these visits free.

The following are prioritized hypotheses for further implementation and measurement, not completed changes or promised speedups:

1. **Visit only characters needing each kind of calculation.** During a bird's movement, update its position and the observers affected by sight/contact; revisit a worker's action control only when that control, its dependencies or its deadline can change. Start with the existing captured participant/dependency owners and remaining all-character loops, rather than another scheduler. Unity's official guidance similarly recommends removing inactive update callbacks instead of calling them repeatedly to discover there is nothing to do. Membership must update immediately on action start/end, restrictions, due conditions and relevant interactions. [Unity: using a custom update manager](https://docs.unity3d.com/6000.2/Documentation/Manual/events-per-frame-optimization.html).

2. **Keep independent calculations reusable across movement-driven publications.** A bird's landing deadline need not restart a worker's unchanged bodily calculations. Extend existing exact pending-value and dependency owners narrowly, under one authoritative world clock; do not introduce separately writable character clocks. PhysX solves disconnected interaction groups independently. Box2D retains such groups between steps, joins interacting groups immediately and permits separation work to wait. The useful principle is dependency-specific grouping, not installing a general physics framework: seeing the bird links perception work, but does not inherently link the observer's hunger calculation. Shared effects, contact, ordered side effects and unknown dependencies require immediate conservative recomputation. [PhysX: island management](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/Simulation.html#island-management); [Box2D: simulation islands](https://box2d.org/posts/2023/10/simulation-islands/).

3. **Avoid distance-based movement samples only when complete-path checks prove them unnecessary.** Existing swept sight/contact predictions and crossing reuse could allow a known route section to advance directly to a real interaction, turn or landing deadline. Unsupported paths retain sampling. First compare the cost of route certification with the samples it removes. Simply increasing the current one-metre sampling distance is a separate gameplay compromise that may change when something is noticed. Browser smoothing alone cannot remove authoritative sensing/collision work: Unity documents the added display delay of interpolation and the collision overshoot possible with extrapolation. OpenLegend already smooths accepted positions; it must not disclose a hidden future route or invent travel through an uncertain support. [Unity: rigidbody interpolation](https://docs.unity3d.com/6000.0/Documentation/Manual/rigidbody-interpolation.html).
