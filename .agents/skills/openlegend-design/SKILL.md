# Design from playable behavior

Start with a few concrete player/NPC scenarios: trigger, available knowledge, intended interaction, visible outcome and a meaningful failure case. Specify the ambitious target separately from the next feasible end-to-end slice. No template bureaucracy for an already clear small change.

Read the relevant canonical specification and focused tracker, then apply the [engine/world decision procedure](../../../docs/engine-and-world-boundaries.md#5-a-repeatable-boundary-decision) and its P01–P12 principles. Do not copy their full catalogue into another owner.

Distinguish protected runtime integrity, reusable mechanisms, replaceable world policy and authored content. Could another coherent world differ? Compose existing operations first; add a narrow trusted capability only for genuinely missing computation. A native implementation may remain world-specific. Generality is not arbitrary strings, ambient permissions or generated executable code.

Follow the feature through ownership, inputs/units, permitted reads/writes, meaningful triggers, work bounds, interaction effects, initialization, cancellation, replacement, removal and save/restore. Include cognition/observation and player discoverability, not only storage fields. For invention/world-authoring work, expose supported inspection, creation and modification through the existing world-agent admission path with understandable consequences; document unsupported capabilities honestly.

Use a genuinely different scenario to challenge claimed composability. Localize necessary v1 specificity; record its owner, current limit, intended seam and extraction trigger rather than implementing an unused plugin framework. Logical modularity does not require new packages, services or an ECS replacement.

Resolve reversible choices and implement the agreed slice. Leave consequential unresolved decisions in their canonical owner, with options and implications; continue independent work. Use [documentation rules](../../rules/documentation.md) for specifications/tasks and [verification](../../rules/verification.md) for evidence. Existing subsystem IDs and acceptance gates retain their ownership.
