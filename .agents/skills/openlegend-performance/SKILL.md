# Bound work, preserve meaning, measure

Follow the [root read requirement](../../../AGENTS.md#performance-guidance-before-code-work).

Identify the workload and critical path: population/density/history, cold versus warm state, requested simulation speed, host/device and responsiveness. Distinguish 8× simulation speed from 8× workload size using the task and current contract. Define a measurable target with native/server/renderer headroom; speed configuration alone is no benchmark.

Before implementation, record four answers in the existing task plan: what makes cost grow; what preparation is shared; what changes invalidate reuse; and how the complete operation will be measured. Account for nested fan-out across requests, observers, candidates and retained data. A bounded result is not bounded work: select before loading bodies or preparing every item. Identify legitimate full-set work and retain its measured cost.

For work added to a shared execution path, estimate caller frequency × candidates visited × work per candidate, including nested queries. Include uneven relationships in relevant stress workloads: many invitations reaching one person can cost differently from the same number of disjoint pairs. A per-sender bound does not bound recipient work. Measure through the actual callers and mutation/publication lifecycle, preserving production cache eligibility (including mutable versus frozen state); an isolated helper benchmark cannot qualify that path. Count visited or recomputed items when timings alone do not explain the cost.

For server/native work read the applicable [performance contract](../../../docs/performance.md) and tracker; use the [native stress guide](../../../docs/maintainers/performance-profiling.md) only for native simulation experiments. Browser work uses browser/renderer measurements; an unrelated native benchmark provides no evidence. Compare matched inputs/versions/machines, including setup, tail latency, memory and elapsed work. Native headroom excludes persistence, browser and AI orchestration.

Remove unnecessary work first: meaningful change triggers, conservative rejection before exact queries, bounded candidates, existing indexes, shared immutable definitions and dependency-correct caches. Include observer scope, geometry/state revisions and lifecycle in invalidation; prefer relevant participant/item/region and component changes over global revisions when they completely cover the result. Budget exhaustion is not evidence of absence or unreachability. Hearing filtering must preserve actually audible recipients and privacy/intelligibility semantics.

Explicitly look for duplicate or overlapping queries across callers and consider reusing already-fetched data, fetching only missing data, or sharing identical in-flight reads. Reuse must match the required fields, permissions/observer scope and state or transaction snapshot. Prefer request-scoped reuse; longer-lived caches need clear ownership, bounded storage and complete invalidation, including edits, deletions and restores. Keep shared results read-only and indexes derived from their existing authoritative owner. Measure the complete path to confirm a real reduction in work without stale or unauthorized data.

## Repeated readers and fresh projections

Before building a repeated reader, count the scans, compilation and allocations per row and across its callers. A bounded page can still rescan all carried stock or revalidate the same definition for every row. Put shared preparation at the existing quantity/query/validation owner, using indexed membership and one compatible read scope; do not make each display invent its own totals. Separate the cold preparation cost from warm reuse and instrument work counts as well as elapsed time. [Expedition evidence](../../../docs/verification/rewarding-expeditions.md#requested-review--october-6-2026) shows why 16 records caused 32 compilations and repeated stock scans despite bounded paging; it does not establish a universal timing budget.

Separate exact definition validity from current permission, deliberate inspection, learned knowledge and executable stock. Reuse successful exact validation only where the owner guarantees immutable data and a complete dependency key; drafts/builders, changed snapshots and restore must see fresh values. A frozen outer object alone does not prove its contents immutable. Cached facts grant no disclosure or execution; preserve the owner's current authority checks. Retaining failed/partial checks also needs an explicit dependency contract. Weak ownership can release old snapshots; it does not establish correctness by itself.

For calculations depending only on an immutable definition, key reuse by that original definition before allocating stripped copies or wrappers: a fresh object per row defeats identity-based memoization. Stable definition identity alone cannot justify retaining world-dependent validation across changed worlds; first establish the compiler/query's complete dependencies. [Second expedition review](../../../docs/verification/rewarding-expeditions.md#second-requested-review--october-7-2026) distinguishes reusable recipe identity from fresh published-world validation.

Derive projection/memo dependencies from every displayed fact, not only the list's membership revision. Inspection/selection and learned knowledge can change while item identities and quantities stay identical. Verify the actual downstream display immediately after the relevant change, without an unrelated simulation tick masking a missing dependency; also check access revocation, changed definitions/materials and independent observers where relevant. Exercise changes initiated outside the selected component as well as its own successful mutations, including removal of facts and actions that are no longer permitted. Shared calculations must preserve current refusal, privacy and mutation checks. For client refresh/late-read behavior, frontend work also follows [React mutation guidance](../../../docs/ui-ux/react.md#effects-asynchronous-work-and-mutations).

## Existing fast paths, storage and scheduling

Before replacing a fast path with a shared helper, compare the conditions each actually handles; broader usefulness does not prove replacement coverage. In the selected checks, include a previously cheap case, the newly supported case and a meaningful refusal. Record whether each finishes directly or now requires deferred preparation, not only whether it eventually succeeds or its warm timing. Preserve a useful shortcut until the replacement covers its valid cases and cost, or document a justified tradeoff. [PX01's ramp review](../../../docs/verification/first-threat-encounter.md#px01-navigation-review--october-6-2026) demonstrates why: walking across ground edges did not cover entering a ramp inside a larger ground patch, so a successful route still regressed into unnecessary mesh preparation.

For paged SQL, a result limit or application scan allowance does not bound database work. Inspect the actual production query plan, including rows, repeated loops and buffer reads, on representative data before manually refreshing statistics; fresh bulk and naturally aged data are distinct workloads. A bounded first query can still multiply whole-history scans in later joins. Prefer indexed selection and batched related reads in the same snapshot when the plan demonstrates that problem. Count statements across the complete observer/source batch, not only one observer. A timeout disappearing is not sufficient performance evidence.

Move non-authoritative diagnostics/I/O off critical paths when ordering, durability and failure semantics permit. Coalesce replaceable snapshots, not distinct speech, acquisition events or committed effects; skipping work must preserve its required outcome. Add batching, queues, pooling, workers or hierarchy only for a justified bottleneck; bound concurrency/backlog and define cancellation/backpressure. Async syntax does not offload CPU. Preserve commit order, RNG draws, simulation steps, attribution and mechanical/disclosure checks unless an accepted behavior change explicitly allows otherwise.

Exercise a relevant bounded stress workload and the changed runtime path under [Verification](../../rules/verification.md). Use disposable worlds and new private output paths. Include cold rebuilds and changes that invalidate reuse, not only warm cache hits. Record matched before/after evidence, variance and remaining bottlenecks; unavailable baseline or runtime access is a limit, not invented improvement. A timeout is incomplete, not a capacity pass. Do not require stress for unrelated edits or weaken behavior just to hit a timing number.
