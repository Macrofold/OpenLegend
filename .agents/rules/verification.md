# Verification and paid execution

## Default delegated implementation

Do not author new automated tests by default. Focused existing unit, integration or browser checks relevant to the change are permitted; select explicit files, test names or projects and inspect their fixtures, database and side effects before execution. `pnpm check`, unfiltered `pnpm test` and unfiltered `pnpm test:browser` remain full validation, run by CI or when explicitly requested. Static checks and small manual/ad-hoc runtime scenarios are also permitted. Do not recreate a broad suite through many ad-hoc scripts, delete coverage, weaken CI or waive acceptance criteria.

Exercise changed behavior end to end through real downstream callers in a representative scenario and meaningful failure case where feasible, including fixes made during a code review. Prefer suitable existing verification tools or focused existing checks; inspect fixture compatibility before running or repairing them. Use a small ad-hoc scenario only for coverage they cannot supply, not a collection of temporary scripts recreating broad qualification. Reuse valid evidence instead of repeating the same coverage manually; static checks alone do not establish runtime behavior. Use disposable worlds, never replace someone's save. Native checks use `AI_BUDGET_USD=0` without unrelated credentials. UI work needs actual interaction/visual inspection when available, not only a build. Explicit findings-only reviews and design-only work do not require changing or running the game merely because a skill mentions verification. Missing access is a gap, not a pass.

PostgreSQL is the only local and production database. Use disposable PostgreSQL databases for database-dependent verification; the shared fixture helper requires an explicit loopback administrative URL and creates/drops only its own databases. Do not run SQLite parity checks or recreate SQLite support unless explicitly requested. If PostgreSQL is unavailable, report the verification gap. Existing CI/merge gates remain required.

Choose checks by impact: pinned Prettier on changed files, `pnpm typecheck` for TypeScript, `pnpm build` for production/build/client integration, `pnpm config:check` for generated configuration, and `pnpm guidance:check` for guidance. Documentation-only work needs content/link review, not game stress. Avoid repository-wide formatting churn. Inspect script side effects before execution. Restore temporary settings and stop processes you started; do not stop another contributor's runtime.

If a check fails, distinguish introduced failures from an existing baseline using the diff and available evidence. `pnpm typecheck` also checks test sources; stale tests can block it without proving the production build is broken. Report both outcomes where checked; never suppress diagnostics or claim the whole branch is green from a narrower pass. Required CI remains a merge gate unless maintainers explicitly decide otherwise.

Stress meaningful hot-path changes under the [performance skill](../skills/openlegend-performance/SKILL.md). Record specific missing coverage, reproduction and expected behavior in its focused tracker, using [TODO](../../docs/maintainers/TODO.md) only without a focused owner. Consolidate related gaps and remove only clearly obsolete requirements, not unmet checks. Deferred verification is not acceptance.

## Rebase verification

A history-only or mechanically resolved rebase does not require runtime requalification when [patch comparison and upstream-overlap review](../skills/openlegend-rebase/SKILL.md#review-and-verify-reconciliation) confirm unchanged behavior and valid prior assumptions. For semantic resolutions, run the smallest checks covering the affected behavior and a relevant failure condition. Repeat broader lifecycle, performance, browser or provider qualification only when those contracts or evidence assumptions changed, a failure gives a concrete reason, or the task explicitly requires it. Identify reused evidence and its limits; a rebase alone does not close existing qualification gaps. Follow the [root stopping rule](../../AGENTS.md#completion-and-handoff--every-task) once the selected checks and requested reconciliation are complete.

## Spending

Mike's standing authorization covers up to $10 total for a delegated implementation task using credentials he authorized for it. Contributors get no permission to charge his accounts. Other accounts need their owner's authorization; absent permission, stay native/no-cost. Documentation or a discovered key grants no authority.

Count settled cost plus outstanding/uncertain commitments across providers, actors, delegates, calls and compute against one task ceiling. Reserve conservatively before dispatch; application per-actor/monthly caps do not enforce this aggregate limit or create extra allowances. Use the smallest adequate bounded call and reuse evidence. Without a credible upper bound and accounting, do not dispatch. This ceiling covers the software/provider work launched for the task, not a claim to measure the coding assistant's own subscription or token billing. Cancellation, invalid output or missing usage do not prove zero cost. No automatic paid retry/fallback; ask before exceeding the ceiling.

Automated checks use explicit fixtures, the selected disposable database when needed, and no provider or external-service requests; live-provider experiments are separate. Label static, fixture, native, live-provider and stress evidence distinctly. Keep keys, private prompts/saves and raw profiles out of commits. Consult the [bounded live playtest protocol](../../docs/verification.md#bounded-live-playtest-protocol) for the applicable checklist, never as proof a check ran. Record results under [verification report ownership](documentation.md#verification-reports).
