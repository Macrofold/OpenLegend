# Verification and paid execution

## Local verification only

Repository checks run locally, never through GitHub Actions. Do not dispatch, enable, retry or wait for GitHub checks, or add or restore GitHub CI workflows. A push, pull request, merge command, skill or project plan does not authorize hosted verification.

Reuse installed local dependencies and the running local PostgreSQL service when suitable; database checks still use their own disposable databases. Existing requirements to run CI mean the applicable local checks selected under this policy, not remote status checks or automatic full-suite reruns. Full validation follows the risk and requirement selection below; ordinary work uses focused checks.

## Select checks for the task

Write new automated tests only when Mike asks; a project document, acceptance criterion or skill does not itself request test authoring. Use existing checks and tools, or a small disposable scenario through the actual consumer. Simplify repeated setup or fix its demonstrated defect; do not grow a parallel test suite or automatically replace one with a maintained suite. Select checks by actual risk and accepted requirements. Explicitly required tests and local verification/merge gates remain mandatory.

Full commands such as `pnpm check`, unfiltered `pnpm test`, and unfiltered `pnpm test:browser` are broad validation, normally consolidated after relevant implementation stabilizes. Run them locally when explicitly required or justified by cross-cutting uncertainty; otherwise use focused coverage and the required local gate. A targeted pass is not a successful full run. Inspect unfamiliar fixture/tool side effects once and recheck them after relevant changes.

Exercise changed behavior through real downstream callers in a representative scenario and meaningful failure case where feasible, including review fixes. Group checks around a connected player journey. Check high-risk assumptions early when they could harm real resources or invalidate substantial dependent work; otherwise verify connected behavior after implementation stabilizes. Touching permissions, private knowledge, saving or committed effects does not automatically require an early check. Preserve those guarantees with verification proportional to this zero-player development stage. Prefer existing tools and retained checkpoints with their actual permissions/history; before copying a retained world into a diagnostic, read the [checkpoint capture contract](../../docs/save-and-load.md#current-history-capture-boundary) and check fixture compatibility. Repeated setup failures call for simplifying the scenario or repairing the shared fixture owner, not growing a parallel temporary suite. Distinguish fixture repair from product delivery. Reopen valid evidence only for a specific defect or changed dependency; static checks alone do not establish runtime behavior. Use disposable worlds for checks; replacing incompatible local development state follows the [development save policy](../../AGENTS.md#development-save-policy), including coordination with active writers. Native checks use `AI_BUDGET_USD=0` without unrelated credentials. UI work needs actual interaction/visual inspection when available. Findings-only reviews and design-only work do not require running the game merely because a skill mentions verification. Missing access is a gap, not a pass.

A fresh authored fixture committed as saved state must first use its world's startup preparation; loading it correctly skips first-creation effects. Never replay that initialization to repair restoration. Continuation and timing fixtures must match their real caller's immutable publication or editable-builder boundary, while retaining separate coverage for each supported path.

For disclosure checks, first establish that the underlying event or committed effect actually occurred. Confirm the owning participant's evidence when the installed disclosure policy permits it. An observer account omitting health after a missed attack does not demonstrate private-health filtering. Use a controlled positive case when needed, and distinguish that native/disclosure proof from natural hit rates, encounter balance or autonomous choice. [The shield checks](../../docs/verification/shield-defense.md#focused-checks-and-lookup-measurement) record this fixture pitfall.

For interruption, recovery or replacement guarantees, also exercise the state after the earlier action has stopped or been cleared. A busy-action refusal can mask a missing longer-lived constraint. Inspect the ordinary offers and actual admission at that point, and include the later permitted choice when the constraint ends. The [shield review](../../docs/verification/shield-defense.md#second-implementation-review--october-7-2026) only exposed refused resident attack offers after Stop removed the guard action while body recovery remained. Use focused existing checks or the evolving ad-hoc scenario; this adds no automatic test-writing mandate.

PostgreSQL is the only local and production database. Use disposable PostgreSQL databases for database-dependent verification; the shared fixture helper requires an explicit loopback administrative URL and creates/drops only its own databases. Do not run SQLite parity checks or recreate SQLite support unless explicitly requested. If PostgreSQL is unavailable, report the verification gap. Existing required local verification and merge gates remain required.

Choose checks by impact: pinned Prettier on changed files, `pnpm typecheck` for TypeScript, `pnpm build` for production/build/client integration, `pnpm config:check` for generated configuration, `pnpm network:check` for browser request routes or network-policy changes, and `pnpm guidance:check` for guidance. Documentation-only work needs content/link review, not game stress. Avoid repository-wide formatting churn. Inspect script side effects before execution. Restore temporary settings and stop processes you started; for Macrofold shared with other agents, follow the [registered-use cleanup procedure](../../docs/live-ai-setup.md#local-macrofold-server-lifecycle). Do not stop another contributor's runtime.

Type checking includes test sources: stale tests can block it without proving the production build is broken. Report both outcomes where checked; never suppress diagnostics or represent a narrower pass as full validation. Do not delete coverage, weaken required checks or waive acceptance.

Before costly verification, confirm only prerequisites used by that run. Reuse still-valid observations during the session; recheck after relevant changes or failures. A native zero-budget check needs no paid-slot inspection. Reuse valid task-owned setup/checkpoints, with provenance, instead of repeating earned-world preparation. Use a fresh initializer when acceptance concerns the actual opening. Retain snapshots/raw output only for unfinished work, useful reproduction, or explicit preservation; storage-heavy runs must account for retained volume. Classify failures as product, fixture, or environment before repeating. Do not retry an unchanged environmental failure; continue independent work. Avoid overlapping owned workloads that invalidate timing. Clean up only task-owned disposable resources and preserve required evidence and accounting.

Use stress for an explicit requirement or a concrete growth, concurrency, latency, or retention risk. State its workload, question, pass/reporting obligation, and stop condition before an expensive run; use the existing plan or a short update, not a new form. Verify actual activity and completed work before interpreting timing. Repetition may measure variance, reproduce a defect, or evaluate a changed implementation. For optional diagnostics use ordinary or plausible near-term activity and the smallest workload that resolves the identified risk; expand only when needed. A diagnostic's maximum population does not automatically become a product gate.

Record specific missing coverage, reproduction and expected behavior in its focused tracker, using [TODO](../../docs/maintainers/TODO.md) only without a focused owner. Consolidate related gaps; deferred verification is not acceptance. Distinguish helper, service, HTTP and rendered-interaction costs; discard samples where the intended caller did not actually run. Never claim a full pass from a narrower check.

## Rebase verification

A history-only or mechanically resolved rebase/merge does not require runtime requalification when [patch comparison and upstream-overlap review](../skills/openlegend-rebase/SKILL.md#review-and-verify-reconciliation) confirm unchanged behavior and valid prior assumptions. For semantic resolutions, select the smallest existing checks covering the affected behavior and a relevant failure condition. Use applicable static checks; formatting targets changed files. Reuse prior results for unchanged contracts rather than repeating lifecycle, performance or provider qualification. Broaden only for a specific invalidated assumption, introduced failure or explicit task requirement.

For a routine merge, review the incoming change and actual destination overlap once, reuse valid source verification, run only checks required by the reconciliation, then complete the authorized history operation and push when authorized. Do not start runtime services, rebuild unchanged artifacts or repeat source qualification solely because code was merged. No CI, browser/playtest, live-provider, performance campaign or full test suite belongs to this default path. A specific introduced defect or invalidated assumption can require a focused local check; explain that reason before expanding verification.

When database/checkpoint formats, current-format admission or the standard starting-world definitions change, check the actual configured development destination. If it is incompatible, apply the [development save policy](../../AGENTS.md#development-save-policy) directly: replace disposable local data instead of copying old operational tables, retaining an old database, fingerprinting historical records or writing a recovery driver. Reconcile useful checked-in starting content under [starting-world reconciliation](../../docs/save-and-load.md#starting-world-content-reconciliation), and use existing current setup for account access and the installed artwork. Never edit an old schema marker to bypass validation. Reuse the same native startup/persist/reopen pass to establish readiness; do not add repeated HTTP/server cycles unless a changed HTTP path needs them. Keep paid dispatch disabled and stop only processes started for the check. If access, a missing current setup path or another writer prevents readiness, report that concrete gap rather than inventing a preservation project or claiming a pass.

**Do not run browser tests or browser playtests, or start a browser/server environment for them, during rebase/merge reconciliation, including UI conflicts.** Review the changed UI code and use relevant static checks; identify reused browser evidence and any remaining gap honestly. Required local checks and separately authorized implementation/player qualification remain separate and are not waived. A rebase alone does not close existing qualification gaps. Apply the [efficient reconciliation principles](../skills/openlegend-rebase/SKILL.md#keep-reconciliation-short) and [root stopping rule](../../AGENTS.md#completion-and-handoff--every-task) once the selected checks and requested reconciliation are complete.

## Spending

Mike's standing authorization covers up to $10 total for each task he assigns, using credentials he authorized for it. Spend within that limit without asking first; before the task would exceed it, stop and ask Mike to raise the limit. Contributors get no permission to charge his accounts. Other accounts need their owner's authorization; absent permission, stay native/no-cost. Documentation or a discovered key grants no authority.

Count settled cost plus outstanding/uncertain commitments across providers, actors, delegates, calls and compute against one task ceiling. Reserve conservatively before dispatch; application per-actor/monthly caps do not enforce this aggregate limit or create extra allowances. Use the smallest adequate bounded call and reuse evidence. Without a credible upper bound and accounting, do not dispatch. This ceiling covers the software/provider work launched for the task, not a claim to measure the coding assistant's own subscription or token billing. Cancellation, invalid output or missing usage do not prove zero cost. No automatic paid retry in experiments or adapters; the explicitly configured [server decision-escalation policy](../../docs/ai-providers.md#decision-escalation) is the narrow runtime exception. Its calls still share this task ceiling.

Automated checks use explicit fixtures, the selected disposable database when needed, and no provider or external-service requests; live-provider experiments are separate. Label static, fixture, native, live-provider and stress evidence distinctly. Keep keys, private prompts/saves and generated verification output out of commits; summarize relevant results under [verification report ownership](documentation.md#verification-reports). Before live gameplay or character-behavior experiments, read the [bounded live playtest protocol](../../docs/verification/playtest-protocol.md#bounded-live-playtest-protocol) and apply its relevant checklist; the protocol is never proof a check ran.

### Jev cost reporting

Whenever reporting on Jev calls or other Jev-related work, including progress updates, include the total USD cost for the reported scope and the cumulative task total. Preserve the available reported decimal precision; do not round to cents or present a nonzero cost as $0. Label provider-reported estimates, settled charges and reservations distinctly. If costs are missing or uncertain, report that explicitly rather than assuming zero. If no calls were made, state that the additional Jev cost is $0.
