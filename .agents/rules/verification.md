# Verification and paid execution

## Choose the execution location

Before running a check, decide what it must establish and where it will run. Use the developer's computer or an authorized AWS instance. GitHub Actions are disabled. Do not add, restore, enable, dispatch, retry or wait for those workflows. A push, pull request or merge grants no extra verification or spending authority. In older instructions, “CI” or “required local checks” means the applicable checks run under project control. A requirement for a specific device or environment still applies.

**Run speed tests on the standard AWS worker.** This includes short benchmarks, timing diagnostics, throughput, latency, profiling, frame pacing and input responsiveness. For a player-visible timing measurement, the server stays on the worker and the browser can run on a named client device approved under the [machine and device policy](verification-workers.md#standard-speed-test-worker). Other local timing requires Mike’s explicit request. An unavailable worker leaves a gap. Local preparation and ordinary correctness checks may proceed. Their incidental elapsed times supply no performance evidence.

| Work                                                                                                                                            | Default location                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Cheap, bounded static/correctness checks or functional debugging                                                                                | Local; reuse installed dependencies and suitable local PostgreSQL with owned disposable databases.                                             |
| Speed measurement                                                                                                                               | Standard AWS worker and, for player-visible timing, an approved client device. Select the workload and bound before execution.                 |
| Untimed check or build that has disrupted local work, is known to need substantial CPU, RAM or disk, or that Mike asks to move off his computer | Dedicated managed worker when available. For example, use it for a large population or storage experiment. Bound the workload before claiming. |
| Rendered functional play                                                                                                                        | Representative browser/device. Use the speed-measurement rule when timing the interaction.                                                     |

Explicit task instructions override the defaults in the table. For remote execution, follow the [managed-worker procedure](verification-workers.md) before starting, claiming or using a machine, including an already-running one. That procedure covers access, spending and [what to do when the managed runner is unavailable](verification-workers.md#current-availability). Ordinary focused checks stay local. Elapsed time alone does not move an untimed check to AWS.

When a local build or untimed scenario could interfere with Mike's work, use his report or take one quick look at current CPU load and memory pressure, for example in Activity Monitor. Consider the Mac's responsiveness and the expected CPU, memory and disk demand of the check. Use the managed worker when the workload is known to be heavy or would compete with current work. For example, a one-minute browser check can go to AWS when it would stall an already busy Mac, even if the worker takes longer overall. A small check with no plausible interference needs no separate load inspection. A busy Mac can still be the approved browser client for measuring play under normal use.

## Select checks for the task

Write new automated tests only when Mike asks. Adding a test case to an existing test file is still writing a new test. A project document, acceptance criterion or skill can require proof of an outcome without authorizing a new test. Use existing checks or a small disposable scenario through the real caller. Run checks explicitly required by the task, the affected contract or the applicable merge procedure. Select additional checks by what the change could break.

Reuse corrected scenarios through their existing owner. Assert required outcomes and relevant invariants; require a particular internal write, status or operation count only when the contract or experiment depends on it. For intermittent failures, retain the request/phase, refusal category and relevant already-computed dependency identities with the frozen source and inputs, respecting privacy and output bounds. Put additional tracing in bounded diagnostics. Choose comparison scope and repetition under [experiment planning](../../docs/performance/measurement.md#planning-comparisons); one successful pair does not establish intermittent reliability.

Use focused checks by default. `pnpm check` runs the full unit suite among other checks. Unfiltered `pnpm test` and `pnpm test:browser` also run whole suites. Run a broad command when explicitly required or when a change could affect several callers and focused checks leave that risk unresolved. Consolidate broad checks after implementing the changes they cover. If Mike excludes the unit suite, run the applicable allowed commands individually.

Exercise changed behavior, including review fixes, through the real caller in a representative scenario and a meaningful failure case where feasible. Group focused checks around the affected part of the player journey once it and its callers are implemented. When a project requires a final integrated release check, run its broad journeys, such as reconnect, restart and operator recovery, at that gate. Keep required stage checks and verify affected parts sooner. Check assumptions early if they could harm real resources or invalidate substantial dependent work. Changes involving permissions, private knowledge, saves and committed effects get the same timing decision. UI work needs actual interaction and visual inspection when available. Findings-only reviews and design-only work do not automatically require running the game.

A shared build can serve several checks even when each needs its own session, database or process. Share a running game when each step leaves the next in its required starting state and each outcome can be observed separately. Preserve the conditions that expose the behavior, such as a cold start, independent player sessions or a request still waiting during revocation. After a change or failure, keep earlier results only for claims their caller, setup and dependencies still support. If repeating a cheap check is simpler than establishing that its evidence still applies, repeat it.

### Prepare a representative scenario

Before designing a fix around a fixture, show how a supported producer and its admission rules reach the case, or identify the requested new path. Inserting a value by hand can exercise a helper without demonstrating that a player can reach it.

Use disposable worlds. Prefer existing tools and compatible retained checkpoints with their actual permissions and history. Before copying a retained world, read the [checkpoint capture contract](../../docs/save-and-load.md#current-history-capture-boundary). For incompatible local development data, follow the [development save policy](../../AGENTS.md#development-save-policy) and coordinate with active writers. Simplify repeated setup or repair its shared owner. Distinguish fixture repair from working product behavior.

When creating a saved fixture from a new world, run that world's normal first-start preparation before saving. A restore correctly skips first-start effects. For continuation and timing checks, supply the same kind of state that the real caller supplies. A completed, immutable world transition and a builder whose contents are still editable require separate coverage when both are supported. [Continuation and identity](../../docs/save-and-load.md#continuation-and-identity) explains the difference.

For privacy checks, first establish that the private event or effect occurred. Confirm what its owner sees when the world's rules permit that check. For example, have an attack actually hit before checking that another observer cannot see the victim's private health change. A controlled hit establishes what was disclosed. Natural hit rates, encounter balance and autonomous choices need their own evidence. [Shield example](../../docs/verification/shield-defense.md#focused-checks-and-lookup-measurement).

For interruption, recovery or replacement, exercise the moment after the earlier action stops. For example, a character that has stopped guarding may still be recovering. Check both the actions offered and the actions the game accepts during recovery and again once it ends. [Shield example](../../docs/verification/shield-defense.md#second-implementation-review--october-7-2026).

PostgreSQL is the only database for game state. For database-dependent checks, give the shared fixture helper an explicit loopback administrative URL. It creates and drops its own disposable databases. If PostgreSQL is unavailable, report the missing evidence. SQLite parity checks or support require an explicit request.

### Run and report the selected checks

Use pinned Prettier on the changed files it supports. Select other checks by impact.

| Affected work                            | Check                                                                |
| ---------------------------------------- | -------------------------------------------------------------------- |
| TypeScript                               | `pnpm typecheck`                                                     |
| Production build or client integration   | `pnpm build`                                                         |
| Generated configuration                  | `pnpm config:check`                                                  |
| Browser request routes or network policy | `pnpm network:check`                                                 |
| Agent guidance                           | `pnpm guidance:check` and review the affected instructions and links |
| Prose alone                              | Review the content and its links                                     |

Inspect unfamiliar tool or fixture side effects before running it, and again after relevant changes. Restore temporary settings and stop processes you started. For a Macrofold server shared with other agents, follow its [registered-use cleanup procedure](../../docs/live-ai-setup.md#local-macrofold-server-lifecycle).

Type checking includes test sources: stale tests can block it without proving the production build is broken. Report both outcomes where checked; never suppress diagnostics or represent a narrower pass as full validation. Do not delete coverage, weaken required checks or waive acceptance.

Before costly verification, confirm only prerequisites used by that run. Reuse still-valid observations during the session; recheck after relevant changes or failures. A native zero-budget check needs no paid-slot inspection. Reuse valid task-owned setup/checkpoints, with provenance, instead of repeating earned-world preparation. Use a fresh initializer when acceptance concerns the actual opening. Classify failures as product, fixture, or environment before repeating. Do not retry an unchanged environmental failure; continue independent work. Avoid overlapping owned workloads that invalidate timing.

**Keep a small verification record.** Record what was tested, its revision or working changes, the outcome and any material failure or limit in the existing handoff or evidence record. For measurements, include the workload, conditions and figures needed to interpret successful and failed attempts. Preserve required evidence and applicable collection and spending receipts. A generated report can embed a full trace. Retain the detailed export when required or when its detail has a specific use.

Before a large run, budget for the peak overlap of source extraction, builds and result collection. Reuse qualified immutable inputs where the comparison permits. Keep disposable builds, extracted source, installs and logs in task-owned scratch. Leave database teardown to its fixture helper, linked worktree removal to Git and shared cache eviction to the cache owner. The producer can release a bulky intermediate after its last dependent step, even in an ongoing task. Follow the [task cleanup rule](../../AGENTS.md#completion-and-handoff--every-task) and [development save policy](../../AGENTS.md#development-save-policy).

Retain the means to replay a run only for a specific need, such as a still-comparable control, an unresolved failure that needs its fixture, or an explicit preservation requirement. Use existing copies first. For source needed again, verify that a retained Git reference keeps the base commit available and that the saved changes reconstruct the tested source, including new files. A verified source bundle also suffices. A Git tree ID alone supplies identity without guaranteeing future access. Preserve exact inputs, settings, toolchain, command or binary where the next use depends on them. When that use ends, keep the result and its original context, retire obsolete replay instructions and release the extra files after their last user finishes.

Use stress for an explicit requirement or a concrete growth, concurrency, latency, or retention risk. State its workload, question, pass/reporting obligation, and stop condition before an expensive run; use the existing plan or a short update, not a new form. Verify actual activity and completed work before interpreting timing. Repetition may measure variance, reproduce a defect, or evaluate a changed implementation. For optional diagnostics use ordinary or plausible near-term activity and the smallest workload that resolves the identified risk; expand only when needed. A diagnostic's maximum population does not automatically become a product gate.

Record specific missing coverage, reproduction and expected behavior in its focused tracker, using [TODO](../../docs/maintainers/TODO.md) only without a focused owner. Consolidate related gaps; deferred verification is not acceptance. Distinguish helper, service, HTTP and rendered-interaction costs. Exclude runs that did not exercise the intended caller from valid performance comparisons; retain their outcomes, evidence and spending. Never claim a full pass from a narrower check.

## Rebase verification

A history-only or mechanically resolved rebase/merge does not require runtime requalification when [patch comparison and upstream-overlap review](../skills/openlegend-rebase/SKILL.md#review-and-verify-reconciliation) confirm unchanged behavior and valid prior assumptions. For semantic resolutions, select the smallest existing checks covering the affected behavior and a relevant failure condition. Use applicable static checks; formatting targets changed files. Reuse prior results for unchanged contracts rather than repeating lifecycle, performance or provider qualification. Broaden only for a specific invalidated assumption, introduced failure or explicit task requirement.

For a routine merge, review the incoming change and actual destination overlap once, reuse valid source verification, run only checks required by the reconciliation, then complete the authorized history operation and push when authorized. Do not start runtime services, rebuild unchanged artifacts or repeat source qualification solely because code was merged. No CI, browser/playtest, live-provider, performance campaign or full test suite belongs to this default path. A specific introduced defect or invalidated assumption can require a focused local check; explain that reason before expanding verification.

When database/checkpoint formats, current-format admission or the standard starting-world definitions change, check the actual configured development destination. If it is incompatible, apply the [development save policy](../../AGENTS.md#development-save-policy) directly: replace disposable local data instead of copying old operational tables, retaining an old database, fingerprinting historical records or writing a recovery driver. Reconcile useful checked-in starting content under [starting-world reconciliation](../../docs/save-and-load.md#starting-world-content-reconciliation), and use existing current setup for account access and the installed artwork. Never edit an old schema marker to bypass validation. Reuse the same native startup/persist/reopen pass to establish readiness; do not add repeated HTTP/server cycles unless a changed HTTP path needs them. Keep paid dispatch disabled and stop only processes started for the check. If access, a missing current setup path or another writer prevents readiness, report that concrete gap rather than inventing a preservation project or claiming a pass.

Routine reconciliation uses code review, relevant static checks and reusable browser evidence. If resolving a conflict changes what a player sees or can do and earlier evidence no longer covers the result, run a focused real-browser check of that interaction before reporting the merge or rebase ready. Start only the environment that check needs. Honor any task-specific prohibition and report the missing check if it cannot run. Broader playtests and separately required feature qualification keep their existing scope. Apply the [efficient reconciliation principles](../skills/openlegend-rebase/SKILL.md#keep-reconciliation-short) and [root stopping rule](../../AGENTS.md#completion-and-handoff--every-task).

## Spending

Mike's standing authorization covers up to $10 total for each task he assigns, using credentials he authorized for it. An explicit task-specific ceiling replaces that figure. Reading this policy grants a contributor no right to charge Mike's accounts. Use another account only with its owner's authorization.

Resuming, delegating or extending an assignment carries its spending and outstanding commitments forward. Mike will say when the balance resets. Until then, keep charging related work to the same balance. If the next paid step would exceed the ceiling, ask for an increase that includes the spending already incurred and the outstanding commitments. Continue independent work within the existing authorization.

Count settled cost plus outstanding/uncertain commitments across providers, actors, delegates, calls and compute against one task ceiling. Reserve conservatively before dispatch; application per-actor/monthly caps do not enforce this aggregate limit or create extra allowances. Use the smallest adequate bounded call and reuse evidence. Without a credible upper bound and accounting, do not dispatch. This ceiling covers the software/provider work launched for the task, not a claim to measure the coding assistant's own subscription or token billing. Cancellation, invalid output or missing usage do not prove zero cost. No automatic paid retry in experiments or adapters; the explicitly configured [server decision-escalation policy](../../docs/ai-providers.md#decision-escalation) is the narrow runtime exception. Its calls still share this task ceiling.

Automated checks use explicit fixtures and the selected disposable database when needed. Native checks run with `AI_BUDGET_USD=0` and without unrelated credentials. A cognition fixture can simulate an allowance and a provider through the real application transport when it cannot send paid requests. Keep live provider and other external-service requests out of automated check payloads. The worker runner separately admits its infrastructure calls. Live-provider experiments follow the spending rules above.

Label static, fixture, native, live-provider and stress evidence distinctly. Keep keys, private prompts/saves and generated verification output out of commits. Summarize relevant results under [verification report ownership](documentation.md#verification-reports). Before live gameplay or character-behavior experiments, read the [bounded live playtest protocol](../../docs/verification/playtest-protocol.md#bounded-live-playtest-protocol) and select the steps that apply to the agreed scenario.

### Jev cost reporting

For reports about Jev work, including progress updates, identify three USD figures.

- **New Jev spend** covers calls made during the reported work. Write “new Jev cost $0” when it made no calls. If an older call settles during this update, reflect it in the cumulative figure.
- **Cumulative Jev spend** covers Jev for this assignment to date, including the new spend.
- **Total task commitments** cover all providers and compute for the assignment, including Jev. Separate incurred costs from outstanding reservations or uncertain commitments. When a charge settles, replace its reservation with the charge. Count each amount once.

Use the available precision, including fractions of a cent. Label estimates, confirmed charges and unresolved costs. An unknown cost stays unknown. An incidental mention of Jev in an unrelated report requires no cost figures.
