# Playability, action discovery and controls

Status: **accepted product direction from the user's interface follow-up; proposed contracts and implementation sequence**. This document records requested behavior. The prototype now implements the finite native/learned action catalogue, compact text search, contextual one-second action tooltips and the saved Show Unavailable Actions preference. Ranking, remappable bindings, full logs and the invention workshop remain proposed. Slot counts, layout details and ranking weights remain tuning proposals. See [implemented architecture](../../docs/architecture.md) for current behavior and [world/player experience](world-and-player-experience.md) for the broader spatial interaction design.

## Status feedback above characters and objects

Status feedback is presentation, separate from authoritative work and entity state. Use concise player-facing language: **Resting**, **Gathering fallen branches**, or **Crafting a sling**, with an optional smooth progress bar directly below the label. Do not show redundant “started resting” / “finished resting” notifications. The work indicator belongs above its subject, not inside the health/food/energy panel. Completion removes its progress status; inventory gains and meaningful crafted results can still have their own short notices.

All labels are white without a colored background panel. Anchor the stack above the rendered sprite's top edge, keeping a constant 12 CSS-pixel gap between the sprite and the bottom of the closest entry, whether that entry ends in text or a progress bar. New entries appear at the top; when older entries fade, remaining entries slide down. Use restrained text shadow for contrast. Progress interpolates visually between authoritative samples rather than visibly jumping; rendering must never advance game work or manufacture completion.

Each status has a stable presentation identity and an entity owner. Its producer can update text/progress without reordering the stack, complete it, or explicitly remove it. Incomplete progress does not expire just because time passes or its subject leaves view. A paused task retains its percentage. Ordinary timed notices fade; progress entries remain until authoritative completion/removal. Buildings and other objects should use the same system, with the building owning construction progress and characters owning gathering/resting progress.

The current implementation connects player work to this generic object-capable presentation API and smooths updates over 250ms. Existing native work is still replaced/cancelled when another action is ordered; retaining resumable construction/crafting in authoritative task state is separate future work. The UI must not imply such a cancelled task remains resumable. Camera/visibility rules suppress labels for obscured subjects without changing their underlying work.

## Time controls and settings

The time bar exposes Pause/Resume and **0.5× / 1× / 3× / 8×**, plus a small **Time settings** panel. At 1×, each real second advances one game minute; a game day takes 24 real minutes. The panel explains that rate and contains the checkbox **Pause game when hidden**, checked by default. Both on and off choices persist in the local player profile, independently of the unavailable-action setting.

With the checkbox on, hiding the game tab or taking window focus away pauses the world. With it off, a connected game tab keeps running in the background, including when browser heartbeat timers are throttled. Manual pause remains authoritative. Closing all connections or stopping/suspending the server does not enable offline catch-up. Keyboard users can open the panel, toggle its native checkbox and dismiss with Escape; outside clicks dismiss it. See [time model](time-and-simulation-speed.md) for all rates and clock/AI implications.

## Camera gestures

Right-button hold-and-drag pans the camera; a right-click without dragging opens contextual actions on release. A small movement threshold tolerates hand jitter. Middle-button dragging and Space + primary dragging remain alternatives, with wheel/buttons for zoom and a recenter button. Dragging must not submit a walk/action command or show a menu at its end; cancellation and focus loss must not leave the gesture active. This is a local camera control, independent of the proposed viewport/perception changes below.

## Proposed perception indicators

The September 19 [perception follow-up](../00-source/perception-and-attention-followup.md) requests compact, independently toggleable **Vision** and **Hearing** indicators. Save their display preferences; switching an overlay off does not disable a sense. Prefer subtle gradients with optional faint dotted contours, starting with circles and later supporting occlusion-shaped fields. Vision conveys near/medium/far detail. Hearing shows the reach of a labeled reference sound, because a crash can carry farther than a whisper; it must not expose hidden sound-source identities or undiscovered geometry.

The player's embodied visual evidence should match the server-approved on-screen world view and character line of sight. Object inspection, labels, action descriptions and AI context receive the same permitted detail; god inspection and NPC perception remain separate. See the [full proposal](../07-technical-architecture/perception-and-attention.md) for camera/background tradeoffs, shared object descriptions and event-based sound. Toggleable indicators, graded semantic detail and viewport-aligned evidence remain **proposed**; retain the compact right-click menu and place the display controls elsewhere.

A subsequent user request authorized a narrower visual experiment: the prototype now uses a 28-unit distance-only sight radius and an untinted blur outside the clear central field. Previously seen objects outside sight retain bounded, frozen, noninteractive silhouettes. This always-on presentation does not yet implement the proposed toggles, hearing overlay, occlusion or description tiers; see [implemented architecture](../../docs/architecture.md).

## A complete way to discover existing actions

Right-clicking a person, item, resource, structure or ground location opens an action browser for that context without navigating the notebook away from its current tab. World-object menus contain only actions involving that object; empty-ground menus browse the broader actions available from the current situation. Selection, a visible interaction button and keyboard navigation offer the same catalogue for users who do not right-click. The browser responds to the selected target, nearby conditions, the player's inventory, skills, learned techniques, capabilities and relevant character traits. Personality can influence suggestions or an explicitly declared prerequisite; it must not silently hide an action merely because the character is unlikely to prefer it.

The requirement is expansive discoverability: players can browse **every existing action they are entitled to discover**, including relevant actions whose current prerequisites are missing. A recommendation list is an entry point into that catalogue, never its substitute. Separate these sets:

| Set                                                                            | Interface behavior                                                                                                                                                   |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing actions currently usable here                                         | Enabled and executable through ordinary authoritative action validation.                                                                                             |
| Existing discoverable actions blocked by a temporary or learnable prerequisite | Visible only with **Show Unavailable Actions** enabled, gray with a reason such as missing cord, insufficient skill, out of reach or unknown technique; offer a learning or preparation route when known. |
| Existing actions for other contexts                                            | Reachable through **All actions** and categories, with their target requirements. They need not clutter the initial target view.                                     |
| Existing definitions a character has not learned                               | Distinguish existence, permission to discover the entry and ability to execute. If discovery policy permits the entry, show it and explain that learning is needed.  |
| Private or intentionally undiscovered information outside a player's authority | Do not disclose the hidden definition or a prerequisite that reveals it. An ordinary character's limited view does not constrain a separately authorized god view.   |
| Actions that do not yet exist                                                  | Accept arbitrary text as a possible invention request; do not pretend an infinite space of future actions has been enumerated.                                       |

Catalogue discoverability and character knowledge need separate explicit rules. The default browsing goal should expose the widest permitted catalogue and actionable learning paths. Do not use a bounded NPC context window, retrieval top-K limit or generic privacy language to restrict authorized player or god discovery. A god with world inspection permission can enumerate the full world registry, including definitions unknown to characters, without automatically teaching anybody.

An action has a stable definition and target/parameter contract, rather than one menu entry for every combination of materials, quantities and locations. **Craft carrying bundle**, for example, can open a material/quantity chooser. Every discoverable definition and permitted parameter choice needs a reachable browsing or search path; enumeration does not require millions of expanded rows.

## Search, categories and availability

The right-click browser starts with a focused typeahead field. Players can type a name, verb, alias or descriptive phrase, or navigate categories such as Attack, Create, Gather, Care and Social. Category navigation and text filtering work together. Clearing the field restores the contextual catalogue, with an obvious route to **All actions**. Show the current target and let the user change or clear it deliberately.

**Latest accepted interface refinement:** default to available actions only. A bottom accordion control labeled **Show Unavailable Actions** reveals unavailable entries below all available entries and then reads **Hide Unavailable Actions**. The same choice governs typeahead matches. Persist both on and off choices in the player profile across menu openings, reloads and server restarts; never label this control Show All. The initial local profile is stored server-side, independently of world snapshots.

Search covers the entire authorized catalogue, including unloaded pages. Pagination or virtualized rendering can limit transferred/displayed rows while exposing a complete result count, continuation and an honest indication when more results remain. Proposed pagination uses a stable catalogue revision and deterministic tie-breakers so reranking or a new invention cannot skip or repeat entries. If that revision expires, restart visibly. Live availability may change; execution always checks current state. This is a proposed completeness mechanism, not a required database or index.

Action descriptors supply stable IDs, names, aliases, descriptions, target kinds, parameter schemas, category IDs, prerequisite descriptions, permitted discovery scope and presentation hints. The application derives availability from authoritative state; the browser renders it. Grey actions explain their blockers and can open inspection or prerequisite guidance. They cannot dispatch a physical action while unavailable. Group unavailable entries below usable entries in the current result/category without losing their search matches.

Categories evolve automatically as actions are admitted. Start with trusted tags and deterministic family mappings; allow multiple memberships while preserving one action identity. AI can propose new category labels or aliases during invention when useful, followed by validation, normalization and deduplication. A category is organizational data, not a new executable engine operation. Stable IDs preserve bindings across label changes. Uncategorized admitted actions remain visible under a catch-all until organized. Category merging/renaming needs explicit migration rules; each invention must not require a hardcoded client menu change.

Ordinary filtering, availability checks and category browsing use indexes and game rules without paid inference. Optional semantic search can improve paraphrases, but its failure must leave complete text/category browsing available. Relevance ordering can prioritize matches while retaining access to all results and alternate sorting.

## Compact menu and contextual descriptions

Keep the right-click menu small, with no visible title (the target remains an accessible label): a compact search input and close button on one row, action rows, and the **Show Unavailable Actions** drawer control. Use consistent search/row typography, subtle focus and hover treatments, and a thin rounded scrollbar. Put category tags at the right of each row; do not show row subtitles, a visible “Find an action” label, result counts, an invention button or invention help text. Preserve an accessible search label and concise loading, error and empty-result states. Available rows remain first; unavailable rows are gray and participate in search only while the saved preference is enabled.

After one second of uninterrupted hover or keyboard focus, show a detailed description beside the action menu. It explains the action's result, requirements and material consequences, tailored to the actual target and relevant current conditions. Put the authoritative unavailable reason in this tooltip as well. Moving away, filtering, scrolling or closing the menu cancels pending details; a displayed tooltip can be entered to read or scroll its text. World refreshes update the explanation without continually restarting the delay.

Reuse a small set of common situations instead of generating text for every permutation. The current implementation combines native family explanations with perceived target facts and the recipe/item prose already stored when an invention is admitted. Future action families should include bounded, versioned descriptions for meaningful target kinds or phases at creation, with a default fallback. A future Kill action would need different explanations for animals, NPCs and players, reflecting each supported consequence; the current executable game only implements animal hunting. Selecting prose must not grant combat capabilities or make generated text authoritative. Future variants are a schema extension, not an existing implemented field. No hover should cause a paid inference request.

## From a typed request to an invention

The September 19 compact-menu refinement supersedes the earlier right-click sparkle proposal: there is no invention button or invention helper text in the action menu. The typeahead searches existing actions; unmatched text does not submit generation. Players start an invention through the **Invent something** tab in the main composer, with an explicit Send step. Keep invention discoverable outside the compact context menu.

Invention submission is actionable only when the player invention lock is off, the account has authoring entitlement, the route is supported and AI execution has capacity and spending authorization. Explain unavailable configuration, allowance, permission or world lock. If support cannot be determined by ordinary checks, an explicit invocation can enter bounded classification and return unsupported; do not promise arbitrary text is implementable. With the player invention lock on, existing-action use/search remain available while player-origin invention is blocked, including requests delegated to an AI or NPC. The independent agent lock controls autonomous NPC invention and does not disable the player's invention entry. Owner controls expose two separate labeled toggles; a separately authorized owner workshop exception remains a proposal. [Invention governance and ownership](invention-governance-and-ownership.md) defines lock and authority behavior.

Selecting an existing action requests that action. Typing a partial match or pressing a browsing key must not silently buy generation or publish a mechanic. Explicitly sending an invention submits the intention through the [interaction protocol](interaction-protocol.md): reuse appropriate definitions, classify unresolved meaning, generate only when needed, validate and admit within policy. Proceed with sensible assumptions under normal authoring policy; ask only when unresolved consequential meaning needs clarification.

AI should name the action appropriately when the user's text is a sentence or an unsuitable label. Preserve the original request and provenance alongside the accepted name. Naming cannot grant a missing capability. Feedback distinguishes a proposal, an admitted definition, an unavailable request and an actual performed action. Admission does not spend crafting materials or magically execute the action.

After admission, the definition enters the searchable catalogue, categories and inventor's account history. Its inspected record provides **Workshop this invention**, linking to the [world agent and workshop](world-agent-and-workshop.md). Editing creates an explicit revision under governance, not an in-place mutation hidden behind a rename.

## Frequent actions and stable recommendations

Commonly used actions should rise toward the top using both community and personal signals. Keep independent counts for an account's own use, use within a world, and broader use across participating worlds. Offer choices such as **Suggested**, **My frequent actions**, **World popular**, **Global popular** and **Name**. Default blending, decay/window and minimum sample size remain tuning decisions. Compatibility, context and availability take precedence over an irrelevant global bestseller.

Count authoritative committed execution, not menu opens, clicks, duplicate intentions or model proposals. Each action family defines a once-only usage event: an actual shot can count even if it misses, while rejected dispatch, canceled pre-execution work and progress ticks do not. A completed craft counts once; its start and completion cannot both inflate the count. Keep attempts, completions and outcomes distinguishable for later analysis. Document aggregation across targets and parameter choices.

Proposed implementation: derive usage projections from committed events containing a unique execution/event identity, actor/account, world, action/version and declared usage marker. Deduplicate before incrementing any aggregate; replay, reconnection and rebuilding a projection must produce the same totals. Preserve version lineage across renaming without silently pooling materially different mechanics. Global counts need shared definition/lineage identity; names alone do not equate inventions. Exclude fixtures and distinguish NPC activity from player popularity.

Rerank in the background, but **do not move rows or change targets under pointer or keyboard focus**. Capture ordering when a menu/drawer opens or search changes; apply fresh popularity on reopening or deliberate refresh. Update availability in place immediately, so stale rows do not imply permission. Hold dynamic suggestions while hovered, focused or pressed; refresh after release or chooser dismissal. Cooldowns and animation remain playtest choices.

## Quick slots, categories and key bindings

Provide a configurable bottom action bar for ordinary actions and, where world rules support them, invented spells. The layout proposal is **three dynamic suggestion slots to the left of five user-configured quick slots**. These counts are tentative; keep the data model and responsive layout independent of them.

Each configured slot binds a specific action or category, plus a user-selected remappable key. Keys are not restricted to the number row. Explain conflicts, platform-reserved shortcuts and unsupported combinations; provide mouse/touch equivalents. Gameplay bindings do not fire while a text editor/composer has focus. Persist preferences by stable action/category identity and check world compatibility on world changes. Missing, revoked or unsupported bindings remain inspectable and repairable instead of silently becoming another action.

| Binding                              | Activation behavior                                                                                                                      |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Specific action                      | Try to initiate it against the visible selected/eligible target after authoritative checks; show a target/parameter chooser when needed. |
| Unavailable specific action          | Grey the slot and explain why. Its key does not submit an action already known to be blocked.                                            |
| Category                             | Open its complete contextual catalogue with typeahead; unavailable entries are greyed below available entries.                           |
| Dynamic suggested action or category | Show the current label, target and key; follow the same checks and chooser rules as a configured slot.                                   |

The user's example is **C → Create**. Pressing C opens creation choices prominently in the middle of the screen. A slot click can open a drawer growing upward from that slot; the same component may expand toward the center when keyboard-invoked or when more room is needed. Preserve both the centered category chooser and slot-associated drawer without fixing one geometry for every screen size. Focus the chooser, support arrow keys/typeahead/Enter, and let Escape close without executing. This layout proposal needs playtesting.

Dynamic suggestions respond to meaningful changes: nearby targets, inventory, work completion, needs and known opportunities. They can be categories or individual actions. Near an eligible agent, suggest **Talk** with a visible shortcut. Show whom it addresses and preserve that target through activation. With multiple nearby actors, respect explicit selection or show a target chooser; do not unpredictably switch partners. Opening Talk is separate from dispatching a paid response.

Suggestions use ordinary rules wherever sufficient. Optional bounded semantic ranking can improve unusual situations later; a call per frame or menu open is not acceptable. Recommendations never replace full catalogue access, rewrite configured slots or bypass world rules.

## World history, god history and invention inspection

Provide a visible, filterable world log. Ordinary players see authorized world events; a separate god-mode log provides authorized world-wide inspection. Its purpose is comprehensive operational and creative visibility, not a renamed local feed. God access includes permitted agent state/history and hidden-character invention records, without an arbitrary restriction to the observed area. It remains a separate authenticated mode; credentials and unrelated account data are not world context.

Players can add/remove filters for event kind, agent actions, inventions, actor, time, world region and definition/version. Show active filters and a route to all permitted events. **New inventions** must find every matching retained world invention record, including those outside the renderer's recent feed. A bounded in-memory feed is not complete durable world history.

Each invention entry links to its **full persisted inspection record**: identity/version, name, creator, originating world, permitted source request, lifecycle/admission status, inputs/prerequisites, work and resource costs, all technical parameters with units/defaults/bounds, effects, dependencies, declarative configuration, presentation bindings and provenance. Show the full structured definition alongside readable explanation, linked revisions and relevant outcomes. Declared effects describe allowed behavior; execution history shows what actually occurred.

For extensions containing custom scripts, inspection includes actual stored source/artifacts or source references, versions/hashes, dependencies and declared execution constraints under the viewer's authority. An AI summary does not substitute for inspectable technical content. The current prototype has finite declarative recipe families and no generated JavaScript execution; future script inspection does not authorize eval or arbitrary executable fields. Absent scripts should be visibly absent, not invented for display.

The log links to durable records rather than being their sole storage. Registry versions and invention details survive recent-feed truncation, reload and edits. Large artifacts can have paginated/downloadable inspection rather than being crammed into a row or model prompt. Proposed persistence, authorized full-world retrieval, workshop revisions and causal links are specified in [world agent and workshop](world-agent-and-workshop.md). Account-wide **My inventions**, world packs and reuse rights belong to [invention governance and ownership](invention-governance-and-ownership.md).

## Billing menu and cost breakdown

Add a small, keyboard-accessible **Billing / AI costs** control to the persistent interface. Clicking it opens a compact panel that can expand into a detailed report without leaving the world. This U15 requirement is documented future behavior. It reports incurred spending; opening it does not start an AI call or change the spending allowance.

The later accepted [subscription-tier direction](../06-marketing/business-plan.md#player-subscription-tiers-and-invention-allowances) adds the player's tier, included/used/reserved/remaining invention allowance and next renewal time to this panel. Keep invention units separate from monetary AI costs and world funding. Exhaustion explains when invention becomes available again while existing mechanics and retained inventions remain usable; available units never override the player invention lock. Free-tier examples of 10 or 30 per month remain undecided, and the current prototype does not enforce subscription quotas.

Offer **Current session**, **Past 24 hours**, **Past 7 days**, **Past 30 days**, **All time**, and **Custom range**. Current session means the current server process's run, from startup to now, not the browser tab or character play session. Show server startup and elapsed uptime. The rolling and all-time presets include previous server sessions; Custom accepts any start/end date and time. All periods use real time, with visible timezone and resolved boundaries, regardless of simulation speed or pause.

Lead with separate **LLM costs**, **Jev costs** and their combined inference total. Show [image/art generation costs](../07-technical-architecture/billing-and-usage-reporting.md#art-generation-costs) as a separate category when implemented; art jobs do not themselves consume player invention units. Show other Macrofold compute/storage/service charges separately, plus a clearly defined overall total where coverage permits it. Identify the selected world/project billing scope. Estimated costs, settled charges, unknown usage, credits and outstanding reservations must be distinguishable; an allowance hold is not an additional incurred expense. In BYOK mode distinguish estimated upstream provider spending from charges paid through Macrofold. Never add the same provider cost twice through both a workflow total and its child calls.

Allow expansion by provider/model and workflow purpose, with call counts, reported tokens or other billed units, individual invocation/charge details and receipt references. Include world/session filters when the viewer has broader billing access. An optional time-series view uses the same complete range and totals as the detail table. The user should be able to answer both “How much did Jev cost this session?” and “Which workflows accounted for LLM spending between these two times?”

Show last refresh, accounting completeness and pending reconciliation. Keep a cached report visibly stale while refreshing; an unavailable source is not zero cost. Refresh on demand and at a bounded cadence while the panel is open, independently of the simulation loop. Restrict reports to the payer or delegated billing viewer; controlling a character or a world does not automatically reveal someone else's account spending. The [billing and usage contract](../07-technical-architecture/billing-and-usage-reporting.md) defines Macrofold queries, time attribution, exact accounting and the Open Legend server adapter. The current local budget estimate does not yet implement this reporting interface.

## Implementation sequence and evidence

Stage these requirements without coupling them to a renderer, provider or database:

1. Define shared descriptors and application-owned discovery/availability queries. Prove complete paginated browse/search before personalization.
2. Feed right-click, selected-target controls and keyboard category choosers from that catalogue. Add explicit invention eligibility/status while preserving authoritative execution.
3. Persist quick-slot/category bindings and add contextual suggestions. Verify remapping, text-input isolation, target stability and accessible alternatives.
4. Derive deduplicated usage projections from committed actions. Add personal/world/global ordering without moving an active menu under its user.
5. Connect persisted world/invention history, player/god filters, account attribution and full inspection. Add workshop links as governance and versioned editing become available.

Acceptance cases include: browse an uncommon action beyond page one; find an alias on an unloaded page; inspect missing-skill guidance; see a new invention without client code changes; reopen a renamed bound category; press C while typing without opening gameplay UI; approach two people without talking to the wrong one; keep focused rows stable during ranking updates; replay usage without double counting; enable the player lock during player generation without admitting the result; change only the agent lock without incorrectly disabling player invention; inspect an invention after recent-feed pruning; and retrieve a permitted god record unknown to every resident. Paid checks remain separately configured live evidence; fixtures establish only contract/interface behavior.
