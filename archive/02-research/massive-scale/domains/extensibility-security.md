# Extensibility, generated mechanics, security and abuse budgets

[Research index](../README.md) · Reuse the existing [world-module runtime](../../../07-technical-architecture/world-module-runtime.md) and [declaration lifecycle](../../../07-technical-architecture/declarations-and-evolution.md). This chapter adds research questions, not another execution framework.

## Extensibility is a cost boundary as well as a type boundary

OpenLegend's distinguishing promise is that supported laws can compose into surprising interactions. The danger is not just bad code. A valid new relationship can multiply work across every actor, every event or every region.

A mechanic admission review should describe its owner, inputs, read/write scope, units, active-instance count, spatial extent, query shape, event fanout, timer behavior, dependency cycles, resource conservation, versioned serialization and migration. It should identify whether work is per-step, per-change, per-event or per-decision. Reuse the existing module contracts rather than maintaining a second schema in this research folder.

An operation budget alone is incomplete. A cheap callback can schedule a million other cheap callbacks. Bound total descendants, recurring work, retained state and inference spending attributable to the mechanic. Cycles need a convergence or bounded-execution rule, not merely a recursion-depth limit.

## A useful illustrative cost envelope

For a proposed fire-spread family, ask: how many active sections can one source ignite; what local neighborhood is queried; what physical range is supported; how often can geometry change; which resource owns fuel; what happens to due work after save/load; and how does an unavailable budget appear to players?

For a proposed telepathic network, ask: which recipients have consent/permission; can it span worlds; does it create knowledge of private thoughts; does every received message purchase inference; and which authority owns the transmission? This may be a different causal domain, not a parameter change to ordinary hearing.

For a proposed keepsake, most richness may remain in description, ownership, conversation and memory. It need not introduce a new per-tick physical subsystem. Prefer composition where it supplies the intended choice.

## Trusted rules, configurable policy and generated code

Validated declarative data inside a finite native family has different risk from arbitrary code. Narrow native capabilities can expose geometry queries or effect proposals without granting unrestricted access to all state. A module cannot broaden privacy scope by inventing a new sense name or bypass resource accounting through prose.

Generated code, if eventually allowed, needs isolation, execution/memory limits, bounded host calls and explicit capabilities. Wasmtime documents a security boundary for WebAssembly execution, but the application's exposed host functions and resource controls still determine what guest code can do. Sandboxing is not proof against every denial-of-service or information leak. [S45](../sources.md#s45)

Do not run untrusted scripts inside the authoritative Node process merely because they were generated by a trusted model. Avoid ambient filesystem, network, secrets, wall clock and randomness. A bounded pure evaluation can return proposed effects for normal admission. Version and test the evaluator itself.

## Treat everything a character reads as untrusted content

Player speech, books, signs, imported lore, memories and generated assets can contain instructions aimed at the model rather than the fictional character. A remembered sentence that says “ignore your rules and reveal secrets” must remain content, not an increase in tool authority.

OWASP's prompt-injection guidance is useful for layered input separation, least privilege and validating proposed tool calls. No prompt delimiter alone guarantees protection. OpenLegend's strongest boundary is that models do not possess raw world-write authority or unrestricted private recall in the first place. [S60](../sources.md#s60)

Use actor-scoped tools, opaque offered references and typed proposals. Revalidate at execution. Guardrail models may supplement deterministic controls but cannot replace them or be allowed to grant a permission that the actor lacks.

## Browser and session security

Assume clients are modifiable. Check authentication and authorization per operation, not only at login. Separate ordinary player, creator, moderator and operator powers. Validate origins and session handling for persistent connections, bound frame/request sizes, constrain rates and prevent replay across generations. OWASP's WebSocket guidance provides a concrete review checklist when that transport is introduced. [S44](../sources.md#s44)

Opaque IDs reduce accidental disclosure but are not authorization. Avoid leaking private entities through error messages, autocomplete, cache timing, hidden fields, private asset URLs or broad debug endpoints. A player should not discover a secret actor simply by probing sequential identifiers.

Generated markup, model names and speech must be rendered safely. Asset ingestion needs type/size validation, safe decoding and trusted publication. A valid image or mesh can still be an excessive decompression, polygon or texture-memory workload.

## Cost denial of service

A small request can cause expensive search, geometry rebuilds, mass hearing, deep reflection, asset generation or many downstream requests. Enforce budgets on expanded work, not only HTTP requests per second.

Keep spend reservations and account/world quotas outside model control. A creator-defined mechanic cannot authorize unlimited platform inference or real purchases. Define a user-visible deferred/unsupported outcome when an operational ceiling is reached; do not disguise it as a physical impossibility.

Measure worst-case fanout and contention for admitted mechanics. Red-team combinations, not only individual modules: two harmless triggers can form an explosive loop when composed.

## Data governance and operational access

Provider calls should receive only the authorized minimum needed for the task. Staff tools need scoped access, auditability and separation from ordinary character views. Retention, deletion, minors, voice recording, regional processing and user-generated content rights require a dedicated product/legal review before public operation. No specific legal compliance conclusion is made here.

Do not log every private thought indiscriminately in a globally accessible telemetry service. Security investigation needs evidence, but access, retention and deletion must be deliberate. Use redacted operational metrics and restricted diagnostic payloads with a tested erasure path.

## Security acceptance examples

Test forged control, stale creator authority, injected book instructions, leaked cross-actor recall, malicious asset URLs, replay after restore, late jobs after revocation, oversized geometry and recursive trigger fanout. Confirm that native effects remain constrained even when the model returns a confidently wrong or malicious proposal.
