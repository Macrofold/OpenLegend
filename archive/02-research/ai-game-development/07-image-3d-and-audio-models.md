# Image, 3D, animation, and audio models for OpenLegend

**Research date:** 17 October 2026. **Reviewed:** 17 October 2026. These are proposed tool trials and production practices, not installed integrations, purchased services, or qualified generated assets. [06-models-for-stories-and-characters.md](06-models-for-stories-and-characters.md) covers language models and explains why an agent directing an image or 3D service should not receive all the credit for that service's output.

## Recommendation

**Build a small, coherent asset family and judge what it contributes in the actual game, alongside its production cost.** For the first image audition, compare OpenAI GPT Image 2.5 and Google's Nano Banana 2.1 using the same references and output requirements. For bounded 3D candidates, compare current Tripo and Meshy routes on representative props or a carefully specified character. Preserve authored/procedural reusable parts and shared animation rigs as the production foundation. Open image, mesh, and motion models merit focused trials where distinctive output, control, adaptation, or repeated volume justifies their operating cost.

OpenLegend already has specific visual commitments: warm, dimensional wilderness; expressive people; readable equipment; intentional pixel detail; and a sharp interface independent of the world's pixel rendering. The current 3D character pilot does not imply a general imported/generated character pipeline has been delivered. Generated art must fit the supported manifestation of a real entity, rather than invent mechanics or silently upgrade everything to 3D. [Art direction](../../../docs/maintainers/art-direction.md); [3D pixel-art feature scope](../../../docs/projects/3d-pixel-art-feature-spec.md); [asset pipeline proposal](../../../docs/projects/3d-pixel-art-asset-pipeline.md); [invention-art pipeline](../../../docs/invention-art-pipeline.md).

Judge the intended visual and player-experience benefit separately from production throughput, using the existing [playability gates](../../../docs/projects/five-product-feature-specs.md#playability-gates) where an asset changes an interaction or episode. Record total effort and cost for the specified family, including selection, cleanup, import, validation, and rejected work. A more expressive or distinctive result can justify extra effort. Compare assets per hour or dollar only when the outputs serve similar purposes and meet the same acceptance conditions.

## 1. Assign each tool the job it actually performs

| Layer                          | Typical output                                      | OpenLegend acceptance question                                                    |
| ------------------------------ | --------------------------------------------------- | --------------------------------------------------------------------------------- |
| Language/vision agent          | Brief, reference selection, critique, tool requests | Did it make good creative decisions and respond usefully to screenshots?          |
| Image model                    | Raster art, concept variants, image edits           | Does the image match the family and remain clear at its real display size?        |
| Image-to-3D model              | Mesh and usually texture/material data              | Is the whole object correct, editable, economical, and suitable for our renderer? |
| Retopology/segmentation tool   | Revised surface or separated parts                  | Does cleanup preserve silhouette and make deformation/equipment possible?         |
| Auto-rigger                    | Skeleton and skin weights                           | Does this actual character bend correctly through the required motions?           |
| Motion model or clip library   | Joint motion and timing                             | Do feet, hands, weapons, and transitions behave properly in this game?            |
| Audio model                    | Voice, effects, or music                            | Does the sound convey the intended event or character and integrate cleanly?      |
| Engine and native game systems | Lighting, layout, playback, actual state changes    | Does the finished experience remain readable, responsive, and truthful?           |

A product can package several rows behind one interface. That can save integration effort, but it does not eliminate the distinctions when comparing quality or diagnosing a failure. The supplied WoW-style demo is especially informative as a coordinated pipeline; it is not an isolated test of Claude's native capacity to generate pixels or geometry.

### Managed workflows and consistent asset families

Scenario is a concrete managed-workflow candidate beyond the vendor-hosted customer accounts in the [case studies](02-developer-case-studies.md). Its documentation describes [reference editing, style/subject training, paired before/after editor training, and asset collections](https://docs.scenario.com/get-started/documentation/key-capabilities-at-a-glance), plus [saved multi-step workflows](https://docs.scenario.com/get-started/documentation/workflows-and-apps). These are available operations, not evidence of an OpenLegend quality advantage.

Compare a direct image route with a saved workflow for the same approved family: source reference → requested variant or edit → cleanup → final export. Keep the workflow definition/settings, inputs, selected model, and accepted files with the existing asset owner. Judge editing effort, repeatability, and coherence in the game. Try custom training when its expected artistic or consistency benefit warrants setup; it is optional. The workflow layer and underlying generator should receive separate assessments. [Tooling candidates](04-skills-and-tooling.md#27-scenario-managed-asset-workflows).

### Why a coherent inventory needs more than “fantasy UI”

The most promising first improvement is a **reference-driven icon and interface kit**, made for OpenLegend's actual item taxonomy and visual direction. This is a design recommendation, not a claim that the current interface has been visually audited in this research stream.

Choose a small set of representative items: an ordinary tool, a weapon, food, gathered material, protective equipment, and a crafted invention. Define the silhouette, view angle, apparent scale, material treatment, palette, lighting direction, outline treatment, internal contrast, and transparent padding once. Approve a few exemplars before generating the rest. Then request variations from those exemplars rather than repeatedly asking for unrelated attractive icons.

Evaluate them in the real inventory at its actual sizes and against its real background. A jewel-like image at 1,024 pixels may become a muddy spot in a small slot. The accepted set should distinguish similar categories immediately and remain readable when selected, disabled, equipped, dragged, or shown with quantity and durability. Compare unknown and partially known items too, because the art must not reveal identity or function beyond what the player is allowed to know. The last requirement follows OpenLegend's representation and disclosure boundaries. [Invention-art pipeline](../../../docs/invention-art-pipeline.md).

Use generated artwork for the illustrated parts that benefit from it. Keep item names, numbers, focus states, hit areas, scrolling, tooltips, and layout as live interface elements. Border corners and ornament can be reusable assets. This makes localization, responsiveness, and interaction states independently adjustable. A full-screen painted inventory is a useful concept, but copying it as one bitmap would not produce a functional inventory.

An example **brief structure**, to refine against an approved reference rather than treat as a magic prompt:

> Create a cutout icon of this specific worn field knife. Match the supplied approved OpenLegend tool icons: the same camera angle, warm iron-and-leather palette, restrained highlights, silhouette scale, and edge treatment. Preserve its single blade, leather-wrapped handle, and plain guard. Leave room for the interface's quantity and status overlays. Deliver the isolated artwork without labels, slot border, or background. It must read alongside the approved food and material icons at the inventory's actual display size.

The key is the **approved reference and acceptance view**, not the precise wording. Save the accepted source image, generator/version, inputs, edits, and final export. If a material recolor or slight silhouette adjustment can be done deterministically in the source file, avoid generating a new unrelated identity.

### Texture generation is not material authorship by default

An attractive painted surface may contain baked shadows, seams, false relief, or inconsistent scale. For a lit 3D world, test how its base color and associated maps react under the game's actual sun, shade, and indoor lighting. Repeating ground must be inspected tiled across a meaningful area, not as one attractive square.

The Project Tomorrow transcript supplied by the user demonstrates the alternative: author recipes and geometry-aware materials, then derive controlled variations. The broader research covers that non-AI workflow. Its direct implication here is that image generation should contribute references, motifs, or bounded source material where useful, while authored material graphs remain a strong option for controllable families. A text-to-image model need not repaint every patch of ground or every state of a building.

## 3. 3D generation: strongest as a candidate stage

### Current specialist routes

**Tripo** documents an asynchronous pipeline covering generation, texturing, segmentation, completion, retopology, rig checking, rigging, and retargeting. That breadth makes it a credible candidate for coordinated asset work, rather than merely a text-to-mesh demo. It still leaves the game's acceptance and import contract to us. [Tripo API introduction](https://developers.tripo3d.ai/en/docs/introduction).

Its current rig documentation is unusually important for OpenLegend's varied anatomy. The `v3.0-20260909` rig version improves humanoids and supports several other body families inherited from the preceding version; the API offers multiple humanoid rig conventions. The documented default remains the older biped `v1.0-20240301`, so select the version and body family explicitly. Its skeleton `spec` option applies to humanoids, not every supported family. A rig check precedes the rigging task. Supported family names do not prove a particular peacock-like mercenary, tail, feather arrangement, or equipment system will deform correctly. [Tripo rig API](https://developers.tripo3d.ai/en/docs/animations-rig).

**Meshy's current image-to-3D API** lists `meshy-7.1` for standard generation and `meshy-t2.5` for the current Smart Topology route; `meshy-7` is deprecated. It distinguishes geometry resolution, texture generation, PBR maps, remeshing, and target topology. The older `lowpoly` mode is scheduled to retire October 30. Consequently, old tutorials and a marketplace leaderboard can describe different routes from the ones we would actually test. [Meshy image-to-3D API](https://docs.meshy.ai/en/api/image-to-3d).

The inspected API also makes the reference-to-asset route concrete. Standard 7.1 permits `image_enhancement: false` to disable its automatic reference enhancement; Smart Topology rejects that option. Smart Topology ignores remesh/decimation controls and produces triangles. `remove_lighting` is accepted but ignored by 7.1, so inspect the actual maps for baked highlights and shadows. Request only consumed exports, such as `target_formats: ["glb"]`. Optional transparent and cardinal-view thumbnails help review, while the mesh and materials still need in-game inspection. These are dated adapter details; record the actual model/configuration with each trial and recheck the [API](https://docs.meshy.ai/en/api/image-to-3d) before execution.

Meshy's **programmatic rigging** documentation is more restrictive than general product marketing: it works well with textured, standard humanoid bipeds with distinct limbs, and task-ID inputs above 300,000 faces need reduction first. Its stated exclusions include nonhumanoid and untextured assets. Use this API contract when assessing an automated workflow; a web-app claim about other body types is not equivalent evidence. [Meshy rigging API](https://docs.meshy.ai/en/api/rigging).

**Microsoft TRELLIS.2** is a reproducible open image-to-3D candidate with geometry and PBR material generation. Its official repository describes MIT code/model licensing while separately identifying dependencies with their own terms. The documented setup is Linux with an NVIDIA GPU and at least 24 GB of VRAM. Its published timings use particular high-end hardware; they are not browser or laptop performance promises. Its representation of complex surfaces does not supply production skinning or a reusable character rig. [Official TRELLIS.2 repository](https://github.com/microsoft/TRELLIS.2).

**Tencent Hunyuan3D-2.1** supplies an open research/production-development path with separate shape and PBR paint components, released weights and code. Treat it as a specific inspectable release, not as the name of the newest hosted Hunyuan service or an automatically permissive commercial license. It is relevant when the expected benefit from shape/texture control or repeated generation economics justifies a trial against a hosted or authored baseline. [Official Hunyuan3D-2.1 repository](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1).

These are credible organizations and inspectable APIs/repositories. Their “game-ready” or quality descriptions remain provider claims until an asset works in our rendering, equipment, animation, and performance conditions. Neither polygon count nor the presence of a GLB extension settles readiness.

### A fitted production sequence

For production, use the project's existing order—appropriate authorized reuse, bounded procedural composition, and justified generation—as the starting point. A generator should produce a **candidate** for an accepted representation, while an honest fallback keeps the object usable. [Invention-art pipeline](../../../docs/invention-art-pipeline.md).

Exploration can also begin with an evocative image, motion, sound, or material and ask what behavior, place, or encounter it suggests. Keep that art-to-mechanic loop cheap and editable. Before it becomes a working entity, reconcile appearance, behavior, world meaning, and interaction requirements with the relevant design owner. Production requirements should guide acceptance without preventing creative discovery.

1. **Agree the production object's requirements.** Establish the anatomy, visible equipment, scale, required openings and moving parts, and supported native behavior. Art depicts those decisions; it cannot grant flight, create a functional extra limb, or decide collision authority.
2. **Approve a useful reference.** Use a neutral pose and clearly separated parts for a character. For objects with important hidden sides, supply consistent views where the chosen service supports them. If a generated second view contradicts the first, repair the reference before asking 3D reconstruction to reconcile it.
3. **Generate and inspect the whole object.** Orbit it, inspect the underside and back, compare silhouettes, and look for fused fingers, filled holes, intersecting surfaces, asymmetry, or texture-painted details that should be geometry.
4. **Prepare it for reuse.** Correct scale, pivot, materials, topology, UVs, texture size, and supported export. Separate weapons and equipment where reuse requires it. Test any texture reduction on the actual pixel-art presentation.
5. **Rig only after shape cleanup.** Validate deformation through the required poses. A mesh-changing operation can invalidate prior rig assumptions; do not treat a downloadable skeleton as proof that joints, weights, contacts, and equipment are correct.
6. **Test in the game.** Review camera orbit/pitch, lit and shaded views, idle/walk/combat, equipment changes, silhouettes at game distance, download/memory cost, and frame-time impact.
7. **Publish the accepted manifestation.** Retain source lineage, immutable final bytes, and the existing representation contract. Generation is an asynchronous authoring/provisioning activity, not a per-frame response to every world entity.

This sequence is a proposed application of the existing [asset pipeline](../../../docs/projects/3d-pixel-art-asset-pipeline.md), not a second importer or asset registry to build alongside it.

Choose an asset that exercises the opportunity or uncertainty being investigated. A knife tests silhouette and grip; a container tests an opening and pivot; a living character tests deformation, equipment, and identity. A prop is a useful simple start, while a character trial can proceed directly when expressive motion is the question. Compare with a trusted authored/procedural baseline and preserve successful outputs for reuse.

## 4. Animation: controlled motion matters more than a pleasing video

An image-to-video model can make an impressive clip without returning any skeleton, mesh, contact constraints, or editable animation suitable for the game. Evaluate footage as concept or marketing material unless the product explicitly provides the required game data. For OpenLegend, reusable motion on supported rigs is the more direct target.

NVIDIA's **Kimodo** is a relevant current research tool because it generates actual 3D motion with text and kinematic controls: pose keyframes, end-effector positions/rotations, paths, and waypoints. That is a closer match to “reach this workbench” or “walk along this route” than unconstrained video. Its documentation provides public methods and benchmark material; that establishes an inspectable motion tool, not a qualified OpenLegend animation solution. [Kimodo documentation](https://research.nvidia.com/labs/sil/projects/kimodo/docs/).

The current quick start lists **Kimodo-SOMA-RP-v1.2**, released October 15, under an NVIDIA Open Model license; other skeleton/checkpoint variants have different licensing entries. It documents about 17 GB VRAM for all-GPU generation, with a CPU text-encoder option reducing GPU memory below 3 GB at a speed cost. Pin the specific model and inspect its dependencies before evaluating deployment. [Kimodo quick start](https://research.nvidia.com/labs/sil/projects/kimodo/docs/getting_started/quick_start.html).

The useful first trial is **offline authoring of a few constrained clips** on a supported shared skeleton. Compare against a trusted clip library or authored motion. Check root movement, feet sliding, floor penetration, weapon contact, start/end transitions, looping, and equipment clipping. A lifelike five-second isolated motion is not automatically a responsive attack: the wind-up, contact time, recovery, and interruption must fit native gameplay. Body-family mismatch and retargeting remain real work.

Reuse animation across compatible body/equipment families where it remains expressive. Apply ordinary procedural controls for aiming, looking, and contact when they solve the specific problem. This follows the same leverage visible in the user's Project Tomorrow example: author a controllable system and reuse it. It does not require introducing AI inference into the render loop.

## 5. Voices, sound effects, and music

### Speech candidates

**ElevenLabs** currently documents expressive `eleven_v4`, `eleven_v4_turbo`, and other speed/quality options. It lists more than 90 languages for v4 and advertises about 100 ms median inference for v4 Turbo, explicitly excluding application/network latency. Those are vendor capability and timing claims. They justify a voice audition, not an end-to-end character-response guarantee. [ElevenLabs models](https://elevenlabs.io/docs/overview/models).

**Google Gemini 3.8 Flash TTS / Flash-Lite TTS** separate the verbatim transcript from structured delivery directions and offer designed/prebuilt voice choices. The current guide distinguishes higher-fidelity acting from bulk/latency-oriented use. It also documents limits on multi-speaker custom-voice combinations and voice persistence. Stable character identity therefore needs an explicit asset/voice choice, not repeated improvised casting prompts. [Google TTS guide](https://ai.google.dev/gemini-api/docs/speech-generation).

**OpenAI's speech guide** currently recommends `gpt-4o-mini-tts`, with promptable delivery and streaming; it notes that its built-in voices are optimized for English. That is a suitable baseline where existing integration makes it inexpensive to test, while non-English acting should receive its own review. The language model chosen for NPC decisions and the model performing the voice are separate choices. [OpenAI speech guide](https://developers.openai.com/api/docs/guides/text-to-speech).

Prefer a first architecture trial in which the existing server accepts the character's words before a TTS stage speaks them. It provides a clear place to preserve exact speech, hearing scope, policy, subtitles, cancellation, and receipts. Direct speech-to-speech can be more conversational, but it requires independent qualification of those same boundaries; an attractive voice demo does not establish them. This recommendation applies the project's current [AI delivery contract](../../../docs/ai-providers.md) and [accepted companion policy](https://github.com/Macrofold/OpenLegend/blob/main/docs/agent-content-and-companion-safety.md), not a claim that full voice integration already exists.

Cast a few voices using the same short lines: an ordinary greeting, an urgent warning, a dry disagreement, restrained grief, a quiet practical instruction, and invented names. Judge intelligibility, character identity, emotional range without exaggeration, pronunciation, repeated-line consistency, interruption behavior, and total time to first acceptable audio. Use native speakers for target languages. The text winner need not be the voice winner.

### Effects and music

ElevenLabs exposes distinct sound-effect and music models; its current music offering supports composition plans, references, and editing/inpainting workflows. Those features are more useful production evidence than a claim that an agent “made the soundtrack.” [ElevenLabs model catalog](https://elevenlabs.io/docs/overview/models).

For OpenLegend, first build small reviewed libraries: identifiable material impacts, footsteps, gathering/crafting cues, weather layers, and a few musical states that can transition cleanly. Require clean loop boundaries, appropriate length, loudness consistency, and separation from dialogue. A beautiful whole song is not automatically an interactive score. Keep wet reverberation and ambience separable where the game needs spatial placement. These are proposed audio acceptance criteria, not measured shortcomings of a particular vendor.

Generated trailer music and dialogue acting can be useful without becoming live runtime dependencies. Record the source, intended use, and applicable export/use terms during asset acceptance; no broader legal study is needed to compare creative fitness here.

## 6. What the supplied sites contribute

**Higgsfield** is a creative suite and access/orchestration layer spanning image, video, audio, 3D-related tools, and agent/MCP/API workflows. Its value proposition is convenient access and coordination. It should be compared with direct APIs on actual supported endpoints, exported artifacts, operational behavior, and total cost, not treated as one underlying generative model. The supplied link contains a referral parameter, and the user's transcript explicitly discloses sponsored credits; no affiliate economics or independent cash-spend audit was established. [Higgsfield](https://higgsfield.ai/?fpr=stefan84).

**Top3D** provides blind comparisons, same-input examples, and separate views of texture, geometry, low-poly work, segmentation, and UV-related tasks. That is helpful for narrowing a candidate list and inspecting examples. Its site identifies Stefan Vaskevich as founder and links the Learn3D training business; sponsored material is labeled in its content ecosystem. Treat the board as a discovery aid, with methodology and sample counts to inspect. A small rating gap is not proof of statistically meaningful superiority or of production skinning, import, or performance. [Top3D](https://www.top3d.ai/).

**Learn3D** is a commercial training business. Its published curricula describe a useful end-to-end progression through reference/concept work, generation, cleanup, retopology, texture, rigging, and engine integration. The instructor's years of experience and commercial-project counts are self-reported; this research did not independently establish named successful shipped games from those credentials. The workflow is useful on its merits, especially its explicit cleanup stages. Course marketing and selected before/after examples are not independent model comparisons. [Learn3D](https://www.learn3d.ai/en).

These links deserve study, but their related creator/business relationships mean they should not be counted as three independent confirmations of the same tool's superiority.

## 7. Skills and repeatable automation

A directly relevant first-party published skill exists at [ElevenLabs text-to-speech SKILL.md](https://github.com/elevenlabs/skills/blob/main/text-to-speech/SKILL.md). It declares its API-key/network dependency and documents actual speech-generation controls. That is stronger provenance for operating ElevenLabs than an anonymous generic “AI game developer” prompt. It has not been installed or executed here.

For OpenLegend, the most valuable reusable instructions would combine an existing tool skill with **our accepted artifact contract**: the approved icon reference, permitted output formats, required alpha/padding, chosen mesh profile, equipment conventions, and in-game acceptance captures. Tool instructions should describe how to perform the operation; project instructions should explain what counts as success. A large collection of unrelated skills is not a design system.

ComfyUI provides an alternative to a managed workflow for repeated image operations, with an [editable graph and API execution export](https://github.com/Comfy-Org/docs/blob/main/development/api-development/workflow-api-format.mdx). Its [official agent command](https://github.com/Comfy-Org/comfy-skills/blob/main/claude-code/commands/generate-image.md) starts from discoverable templates and checks connected outputs. Trial an existing suitable template, parameterize the approved inputs, export the required files, and reuse the transformation on another family member. Keep local/cloud execution explicit; see the [tooling candidate](04-skills-and-tooling.md#26-comfyui-saved-workflows-and-official-agent-tooling) for current operating details.

Saved graphs should retain their editable source and execution export, exact checkpoint, node versions, input assets, seed/settings where available, and postprocessing. Keep stable operating steps in project instructions and discover current model/template options when executing. Repeatability does not guarantee byte-identical stochastic regeneration across hardware or software versions. Save accepted final files and their lineage.

## 8. Proposed adoption order and decisive tests

These are trial priorities, not dependencies between unrelated work. A motion trial needs a declared compatible rig; a voice audition does not need the 3D pipeline to finish. Choose the smallest useful comparison for the current creative or production question.

| Priority    | Experiment                                                                                | Why it belongs here                                                                | Decision evidence                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1           | One inventory art family: GPT Image 2.5 versus Nano Banana 2.1, same approved references  | Directly addresses the user's UI concern with a bounded, visible result            | Blind in-inventory preference, recognition, consistency, alpha/export correctness, editing time       |
| 2           | Separate original composition with the same art kit from implementation of a fixed design | Isolates design judgment from artwork and implementation fidelity                  | Real interaction states, hierarchy, usable density, readability, necessary corrections                |
| 3           | Small prop set: Tripo versus Meshy 7.1/T2.5 as appropriate, plus trusted baseline         | Tests the full accepted-asset path before character complexity multiplies it       | Whole-object quality, supported import, texture/material behavior, total cleanup, frame/download cost |
| 4           | One shared-rig character and equipment change                                             | Tests what matters for OpenLegend's dimensional people                             | Deformation, all-angle identity, contact, equipment reuse, animation transitions, silhouette          |
| 5           | Kimodo constrained clips on a declared rig; a separate voice audition                     | Explores expressive motion and character acting with their own required inputs     | Actual motion integration; permitted spoken words, acting, pronunciation, delivery latency            |
| When useful | FLUX/Qwen image adaptation; TRELLIS/Hunyuan self-hosted geometry                          | Distinctive output, control, or repeated volume can justify specialized operations | Creative benefit, accepted output quality, operating effort, hardware cost, repeatability             |

Capability confidence is high where current primary documentation supplies an endpoint, model card, or artifact format. Comparative confidence for **OpenLegend output quality remains unmeasured**. The experiment should retain failures and count every generation and cleanup pass, including paid work that did not make the game. Sponsored credits, subscription allowance, cache-heavy token totals, and hypothetical API equivalents should remain separate from cash cost.

The strongest principle is stable across providers: approve the visual intent, reuse coherent systems, generate bounded candidates, and judge them inside the finished experience. That is how the research turns into a better OpenLegend game instead of a larger folder of impressive but incompatible assets.
